# 苹果风移动端前端

只要任务涉及手机上使用的界面（新建页面、改版、加组件、修交互），先读完本文件再动手。目标是让用户不必逐条纠正“这不适合手机”的问题。

默认前提：界面在手机竖屏、单手、手指操作下使用。没有鼠标，没有悬停，没有右键，屏幕宽度按 375 到 430 之间设计，先做手机再考虑更宽的屏幕。

## 动手之前：先定任务，再定做法

本文件的规则很具体，读完容易觉得“有把握了”。但规则只回答怎么实现，不回答这个页面在手机上该做成什么。实现方法明确不等于设计方向明确。在安排导航、卡片和抽屉之前，先完成下面两步，并把结果写给用户看。

第一步，写出这个页面在手机上的任务（几句话即可）：

- 谁，在什么情况下，用手机打开这个页面
- 打开后最需要看到什么，最需要做什么
- 哪些内容和功能可以后置、折叠，或留给桌面端

桌面端可以承载复杂功能，手机上必须取舍。统一外观不能替代这个判断，把更多内容塞进首屏也不能。以上每一条都要标明依据：是用户说的、从现有页面或数据里看出来的，还是自己的猜测。猜测就写“无依据，需确认”，不要当成事实往下做。关键的一条没有依据时，先问用户再动手。

第二步，列出“改动与保留”清单，再开始实现：

- 要改的地方：每处写明为什么值得改，也就是它在手机上妨碍了上面哪件事。“规则要求这样”只说明怎么改，不算值得改的理由；说不出理由的，不改。
- 原样保留的地方：每处写明为什么保留。默认是保留，原来顺手的地方就是成果，即使截图上看不出变化。
- 拿不准的地方：单独列出，交给用户定。

不要为了显得有成效而多改。改动的数量和截图上变化的大小都不是进展的标准，上面写下的任务完成得更顺才是。

## 一、触屏硬规则（任何情况下都不能违反）

1. 可点击区域不小于 44×44 pt。图标本身可以小，但要用内边距把点击热区撑到 44。相邻可点元素之间留至少 8 的间距。
2. 不依赖悬停。不用 hover 才出现的菜单、提示、按钮；所有信息和操作都要点按可达。hover 样式只能作为附加效果，并包在 `@media (hover: hover)` 里。
3. 主要操作放在屏幕下半部分，拇指够得到的地方。屏幕顶部只放标题、返回和次要操作。
4. 需要填写、多步或多项选择的临时任务，用底部抽屉（sheet）代替居中弹窗。居中警告框只用于必须打断用户的确认（如删除），按钮最多两个。普通提示和选项不多的下拉可以保留为轻量的非模态浮层，不必都改成 sheet。
5. 输入框字号不小于 16px，否则 iOS 会自动放大页面。按内容设置 `inputmode`、`type`、`autocomplete`、`enterkeyhint`，让系统弹出正确的键盘。
6. 留出安全区。视口加 `viewport-fit=cover`，顶部、底部和固定栏用 `env(safe-area-inset-*)` 补内边距，底部固定按钮不能压在横条上。
7. 高度用 `100dvh` 而不是 `100vh`，避免地址栏伸缩造成跳动和被遮挡。键盘弹出时，正在输入的框和提交按钮必须仍然可见。
8. 页面不出现横向滚动。需要横向滑动的内容（轮播、标签组）放进独立的横滑容器，并露出下一项的一部分作为提示。
9. 手势必须有可见的替代入口。滑动删除、长按菜单、下拉刷新都可以做，但同样的操作要能通过看得见的按钮完成。不要占用屏幕左边缘的滑动返回手势。
10. 每次点按都要有即时反馈（按下态、加载态）。按下态用 `:active` 的透明度或底色变化，不用 hover 样式代替。
11. 表格不直接搬上手机，也不靠横向滚动来看。在手机断点以下，把每一行数据改成一张卡片或一个列表行：标题字段放最上面，其余字段用“标签：值”逐行排列，行内操作按钮放卡片底部。卡片上保留用户做常见判断所需的摘要字段，让人不必反复进出详情页；留几个字段按判断需要来定，不为了紧凑而砍掉有用信息，只有很少用到的字段才进详情页。次要操作可以按需出现（展开或更多菜单），常用操作保持直接可见。桌面宽度下保留原表格。
    - 极长的名称和文本不能把行撑得很高：限制为一到两行并用省略号截断，完整内容在详情或展开后可见；连续的长英文和数字串要能断行。用最长的真实样本检查一遍。
12. 不做桌面端习惯的东西：多级悬浮菜单、密集工具栏、小号文字链接挤在一行、拖拽排序作为唯一方式、需要精确点击的小控件。

13. 弹层必须定位正确、焦点正确。先区分两类：模态弹层（sheet、action sheet、警告框）会打断当前任务；非模态浮层（普通提示、下拉、气泡）不打断。下面的定位和层级要求两类都适用，锁定滚动、限制焦点和 `aria-modal` 只用于模态弹层：
    - 非模态浮层不锁定焦点，不锁定页面滚动，不加遮罩和 `aria-modal`；点外部、按 Esc 或选中一项即关闭，焦点留在或回到触发元素。下拉用 listbox 或 menu 语义并支持方向键，提示用 `role="tooltip"` 配合 `aria-describedby`。
    - 定位相对视口而不是某个祖先元素。注意祖先上的 `transform`、`filter`、`overflow: hidden` 会让 `position: fixed` 失效或被裁切，必要时把弹层挂到 body 下。
    - 弹层完整落在可视区内，不被刘海、底部横条或软键盘挡住；模态弹层内容超高时在弹层内部滚动，背后的页面锁定不滚动。
    - 层级用统一的 z-index 变量管理，不临时写很大的数字。
    - 模态弹层打开时焦点移到弹层内第一个可操作元素，焦点被限制在弹层内；关闭后焦点回到触发它的元素。点遮罩和“取消”都能关闭。
    - 模态弹层带 `role="dialog"`、`aria-modal="true"` 和可读的标题。
14. 焦点状态可见。不要用 `outline: none` 去掉焦点环而不给替代样式；用 `:focus-visible` 提供清楚的焦点样式。
15. 读屏可用。图标按钮有 `aria-label`，表单控件有关联的 label，用语义化标签（button、a、nav、h1 到 h3）而不是全用 div，朗读顺序与视觉顺序一致。

## 二、苹果风的结构

导航
- 顶层页面之间用底部标签栏切换，2 到 5 个标签，每个都是图标加文字，当前项用强调色。标签栏始终可见，不要用来放操作按钮。
- 层级内部用导航栏：左侧返回，中间或左对齐标题，右侧最多一到两个操作。顶层页面用大标题，向上滚动后收成小标题。
- 不用汉堡菜单做主导航。
- 进入下一层是从右推入，临时任务（新建、编辑、筛选）用从底部升起的 sheet，带“取消”和“完成”。

列表与内容
- 设置类、选项类内容用分组圆角列表：浅灰页面底色，白色圆角分组，行内左侧标题、右侧值或箭头，行之间用细分隔线。
- 行高不低于 44，能进入下一层的行右侧放箭头。
- 多选操作用 action sheet（底部操作表），破坏性操作用红色并单独分组，底部留“取消”。
- 两到四个互斥视图用分段控件，开关用 toggle 而不是复选框。

视觉
- 字体用系统字体：`font-family: -apple-system, BlinkMacSystemFont, "SF Pro Text", "PingFang SC", "Helvetica Neue", sans-serif`。
- 字号层级参考：大标题 34、标题 22 到 28、正文 17、次要文字 15、脚注 13、最小 11。正文不要小于 15。
- 一个强调色贯穿全局，用于可点的文字、当前选中和主按钮。其余用中性灰阶。红色只用于破坏性操作。
- 留白充足，页面左右边距 16 到 20。圆角柔和（卡片和分组约 10 到 14，按钮约 12 或胶囊形）。
- 层次靠底色差和细线，少用重阴影。栏可以用半透明加背景模糊。
- 主按钮通栏或接近通栏，高度约 50，一屏只放一个主按钮。
- 支持浅色和深色模式，颜色用变量定义，跟随 `prefers-color-scheme`。
- 动效短而克制，约 0.2 到 0.35 秒，尊重 `prefers-reduced-motion`。

文案
- 按钮用动词，简短明确，如“保存”“新建任务”。空状态给出下一步，而不是只说“暂无数据”。

## 三、实现时的基础代码约定

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

```css
html { -webkit-text-size-adjust: 100%; }
body { margin: 0; min-height: 100dvh; overscroll-behavior-y: none; -webkit-tap-highlight-color: transparent; }
button, a, [role="button"] { min-height: 44px; min-width: 44px; touch-action: manipulation; }
input, select, textarea { font-size: 16px; }
.tabbar { position: sticky; bottom: 0; padding-bottom: env(safe-area-inset-bottom); }
.navbar { position: sticky; top: 0; padding-top: env(safe-area-inset-top); }
```

不要禁用用户缩放。固定在底部的元素要给页面内容留出等高的底部内边距，避免最后一项被挡住。

如果项目已有组件库或框架，优先用它自带的移动端组件实现上述结构，不要另起一套；库的默认行为与硬规则冲突时，以硬规则为准。

### 改造已有页面时（不能破坏桌面端）

- 动手前先确认项目现有的断点和样式组织方式，沿用它，不新造一套。
- 手机端的改动全部写在手机断点的媒体查询里（例如 `@media (max-width: 767px)`），桌面端的原有规则一行不动。改完后桌面宽度下的界面必须与改之前一致。
- 新样式用有作用域的类名（组件前缀或模块化样式），不改全局标签选择器和公共类。
- 样式不生效时先查是被哪条规则覆盖了（选择器优先级、加载顺序、行内样式），从源头解决；不用 `!important` 和堆叠选择器硬压，除非是为了盖过无法修改的第三方样式，并加注释说明。
- 同一个属性不要在多处重复定义。发现已有的覆盖链时，在回复里指出来。

### 改造时保留原设计里有用的部分

更紧凑不一定更好，换位置也不一定更好。改动布局之前先做三件事：

- 记下原页面首屏有哪些重要内容。改完后这些内容仍应在首屏可见；把按钮和文字放大到触屏尺寸后，要检查重要内容有没有被挤出首屏。
- 列出常用操作和它们各自需要几步。移动任何入口之前，逐个数一遍改动后的步数；一个入口换位置不能让另一个常用操作多走一步，做不到两全时保持原位，并把取舍告诉用户。
- 找出新手说明、引导和帮助文字。它们不能被后移到不显眼的位置或折叠掉；空间不够时缩短文字，而不是挪走。

信息的排序、密度，以及哪些原有设计值得保留，最终要靠实际使用来判断。拿不准的地方不要自行决定：在回复里列出改了什么、保留了什么、哪几处需要用户亲自体验后定夺。

## 四、交付前自查

自查分两步，两步都要做。逐条通过不等于页面合格：每个控件分别合理，整页仍可能笨重、重复、没有重点。

第一步，先放下清单，看整页。把自己当成第一次打开这个页面的人，对着手机宽度的实际渲染结果或截图（不是对着代码）回答：

- 三秒内能看出这页是干什么的、最重要的是什么吗
- “动手之前”写下的那件最需要做的事，现在是否最容易完成
- 有没有重复的信息、重复的入口，或者一样重的一排东西让人找不到重点
- 整页是否比原来更笨重、更长、更需要滚动
- 逐屏看一遍文字：有没有难看的换行、孤字、被截断或挤压的标签，窄屏（320）下尤其要看
- 回看已经做完的每处改动：现在还说得出它为什么值得改吗。只能解释怎么实现、解释不了为什么改的，考虑撤回

第二步，逐条核对下面的清单，有不符合的先改再交付：

- 每个可点元素的热区都不小于 44 吗
- 有没有任何功能只能靠悬停、右键或键盘完成
- 主要操作是否在下半屏，一屏是否只有一个主按钮
- 需要填写或多步的居中弹窗是否已换成底部 sheet
- 输入框是否 16px 以上，键盘类型是否正确，键盘弹出后是否挡住输入框或提交按钮
- 顶部和底部是否处理了安全区，是否用了 dvh
- 375 宽度下是否有横向溢出、文字截断或挤成一团
- 手势操作是否都有可见的替代入口
- 深色模式下是否每个颜色都可读
- 表格在手机宽度下是否已变成卡片或列表，没有横向滚动
- 模态弹层的定位、遮挡、滚动锁定、焦点进入和焦点归还是否都正确
- 普通提示和下拉有没有被错当成模态弹窗锁住焦点或滚动
- 用极长名称和极短内容各试一遍，行高和阅读节奏是否稳定
- 原页面首屏的重要内容是否仍在首屏，新手说明是否仍在原来显眼的位置
- 每个常用操作的步数是否都没有比改动前多
- 用键盘 Tab 走一遍，焦点是否始终可见、顺序是否合理
- 桌面宽度下是否与改动前一致，有没有新增的样式覆盖
- 在 320、375、430、768 和桌面宽度下各看一遍
- 加载、空、出错三种状态是否都有设计

### 交付时的说明

交付时附上更新后的“改动与保留”清单：改了什么及理由，保留了什么及理由，哪些重要性判断没有依据、需要用户确认。目的是让用户不必自己从截图里找问题，尽量减少需要用户亲自指出的错误。

## 五、验收标准

合格（必须全部达到才能交付，且只在已验证的条件下成立）：
- 内容不被错误裁切，不出现影响使用的横向滚动。
- 操作可以完成，出错后可以恢复。
- 手机端的改造没有破坏桌面端。

优秀（在合格之上尽量做到）：
- 重要信息自然可见。
- 常见判断不必反复进出详情页。
- 长内容和短内容都有稳定的阅读节奏。
- 真机上的触屏、软键盘和读屏都可靠。

交付时对照这两级说明达到了哪一级、哪几条还没达到，并写明是在什么条件下验证的（哪些浏览器、哪些宽度）。没有真机验证时，最多只能说“在已测试的浏览器范围内合格”，不能说达到优秀。

## 六、如实说明验证范围

在模拟器或浏览器窄屏里看过，不等于在真机上验证过。交付时必须写明哪些已经验证、哪些没有，不能笼统地说“已测试”。以下三项只要没在真实环境里试过，就单独列为“未验证”，并给出用户可以自己照做的检查步骤：

- 真实 iOS Safari：地址栏伸缩时布局是否跳动，底部固定栏是否压住横条，滚动回弹是否正常，`position: fixed` 的元素是否错位。
- 软键盘：逐个点输入框，看输入框和提交按钮是否被键盘挡住，弹层内的输入框是否还能看到，收起键盘后页面是否复位，键盘类型是否正确。
- VoiceOver：打开后左右轻扫走完整个页面，看每个控件是否读出有意义的名称，顺序是否合理，弹层打开后焦点是否进入弹层、关闭后是否回到原处。

同样，不要声称没有测量过的效果：

- 没有真人实际使用并计时，就不能说“效率提高了”或“更快了”。用固定样本做的前后对比只能说明界面有什么不同，不能说明使用效率。
- 说明改善时只描述看得到的变化（例如“首屏现在能看到某某内容”），不下“体验更好”这类结论。
- 如果这次改动参考了用户之前的反馈或其他来源，不要把改善都归到某一条规则上。
- 经用户指出方向后才做对的地方，如实说明是用户指出的。多轮之后越来越好，包含了用户的批评、对原页面的熟悉和重复实现的经验，不能当作首次独立完成的成果。

## 七、有冲突时

用户明确要求的做法优先于本文件。如果用户的要求会违反第一部分的硬规则（例如要求用悬停菜单），照做之前用一句话指出在手机上的问题并给出替代方案。
