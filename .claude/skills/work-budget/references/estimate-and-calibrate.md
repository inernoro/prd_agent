# 开工记录与校准

## 可审阅的开工卡

采用已有任务系统；没有系统时可生成会话附件/仓库外 Markdown 记录。不要为每个小任务强建账本或将临时报告提交到长期 doc/。卡片只写能影响用户选择的信息；以下字段不是要求每次填一张大表。

| 项目 | 记录什么 |
|---|---|
| 身份 | 任务/仓库/分支、源码 SHA、评估时间、技能版本；不知道的明确未知 |
| 交付 | 用户会得到的结果与证据、第一份有用产物、完整验收标准、权限终点、不做事项 |
| 工作量 | 必要工作包、依赖/并行/共享资源、主要返工来源；不能只数文件 |
| 预测 | 有效投入区间、外部等待区间、总时长区间；分别列出依据、覆盖/未覆盖项和置信程度，未知不等于零 |
| 建议 | 完整做/最小可用/短验证阶段的成果和代价；只在确有取舍时给多项，不强凑三个选项 |
| 预算 | 探查已用、建议实施硬上限与计时口径、成果检查点、安全收尾预留；复盘/技能修正另列预算，是否已获确认 |
| 未知 | 哪些会推翻目标/估时，先核实什么，哪些需要用户决定；大未知时只承诺短验证阶段的结果 |
| 决策 | 用户确认的具体卡片版本/选项/上限/授权；拒绝或只让估算也记录为该阶段完成，不启动实施 |

没有数据时用“低置信经验区间，尚未测 CI/真实供应商”这样的具体说明，不能虚构历史样本或写概率。CI 在请求完成后才能验收时，其延时在关键路径；可与实现重叠部分只计一次。人审等待无法有界时，给“到可提交人审”为一个明确交付终点，完整合并时间标不可可靠预测，不承诺几分钟交付已合并结果。

## 执行增量记录

保留原卡；事件记录至少包括时刻、实际动作/回执、阶段结果、可核查产物、累计已耗、剩余预算、剩余工作预测和状态。外部启动回执保留任务 ID、SHA、启动时刻、最后状态及取消权限，未知明示。实际无可用时间线时不要反算精确工时，标明哪些持续时间未知。恢复时先读原卡和最新事件，外部任务先查状态，不能直接重复触发。

分开记录投入与价值：

- “测试运行 40 分钟”是消耗；“同一断言旧版失败、新版通过”是证据；“用户可完整导出并播放”才是对应任务的业务产物。
- “写了 20 个文件”不能换算 80% 完成。按确认的验收条件说明已证明哪些、还差哪些；功能因环境无法完成时不能把 README 顶替最终成果。
- 原目标变更需有用户决定身份；外部故障不是自由延期理由，计入原口径并保留责任区分。用户暂停的时间单列，不能把整个缺日志区间都推定暂停。

## 偏差诊断

先对齐相同范围、相同交付终点与同一时间口径，检查原预测是否包含验收及等待。可量化时给实际/预测上沿的比值与绝对差；缺数据不补造。取消/中途停下不能当完整任务耗时样本，范围变化也不能混进原参考类。

| 证据支持的原因 | 修正方向 |
|---|---|
| 漏算测试、Review、真实预览或收尾 | 在对应工作包补必需活动与实际耗时来源，不让所有任务统一加倍 |
| 以为依赖/凭据/环境可用，实际不可用 | 开工短探查优先检查该前提；未知时拆有限验证阶段，不强猜全量 |
| 计划并行但共用环境/数据 | 修正关键路径与资源独占窗口，重算等待，不把累计 Agent 工时当总时长 |
| 用户后来扩大目标 | 保留旧卡，记录新范围/重新授权与增量预测；非估计错误的部分单列 |
| 反复搜索、重复触发、评论扩范围 | 修执行策略/复用证据/范围边界，停止无新信息循环；不能只加预算容纳低效 |
| 外部异常或宿主工具不可中断 | 记录实际事件、时限和暴露点；加独立等待边界及可恢复回执，不承诺能控制外部系统 |
| 耗时低但产物不符 | 修目标对齐和第一成果验收，不以更短耗时或测试数字粉饰 |
| 缺时间线/原卡 | 标不可可靠归因，下一轮补必要观测；不虚构旧估计，不重写历史 |

修复流程：原卡与事实对照 → 可证原因 → 小范围修改真实技能源 → 提升版本 → 重放能暴露该错误的案例 → 不同正常场景回归 → 下轮真实任务校验。历史任务记录留在任务证据里，技能只保留能泛化的判定，不嵌入个人聊天或整份日志。

先区分规则缺陷与执行未遵守：已有计时/检查点/上限规则却没执行，不能声称估算方法完全缺失，更不能靠叠加同义规则解决。修正应落在可观察的执行点或记录缺口，并验证实际遵守情况。例如评估超时需检查是否开头取时、是否把出卡算进预算，而不是只缩短代码实现估计。

## 收口状态

- ESTIMATED：评估完成，未实施或待用户选择。
- APPROVED/RUNNING：确认生效/执行中；这不是交付完成。
- DONE：达到确认产物、验收和权限终点。
- BUDGET_STOP：达到硬上限或已证实剩余预算不足而等待取舍，保留成果和续接。
- BLOCKED/PAUSED/CANCELLED：真实外部阻塞/用户暂停/用户取消，各自记录原因；不称 DONE。

交付给用户先说“得到了什么、还没得到什么、投入与预估差多少”，再给必要原因与下一步，不让用户从内部日志猜结果。
