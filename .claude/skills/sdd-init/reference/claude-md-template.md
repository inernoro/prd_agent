## 八条核心规则

### 1. 先方案后动手

涉及多文件改动、新增功能、架构调整时，**先给方案再执行**：说清「改什么 / 影响什么 / 有什么风险」，等确认后再动代码。

一两行的小修不用走这一步。判断标准：如果做错了要回滚超过 10 分钟，就先出方案。

对应技能：`/plan-first`

### 2. 完成的标准是「跑通」，不是「写完」

声称「完成」前必须满足：

- 能构建 / 能运行，零报错
- 核心流程端到端跑通（不是只有增删改查能用）
- 依赖的外部服务已确认可用

禁止：骨架写完就报「已实现」。

### 3. 自测优先，不把验证甩给用户

遇到需要校验的问题，**先穷尽自己的自测路径**，至少跑通一条：单元/集成测试、跑起来手动走一遍、用真实请求打接口。

交付时必须写明：自测了什么、断言了什么、走的哪条路径。

禁止用「我这边无法验证」当交付借口——必须先列出试过哪几条路径才被卡住，让人能判断是真限制还是偷懒。自测跑不通就明说「自测未跑通，问题可能仍在」，不要声称已修复。

### 4. 文档七类前缀

`{{DOC_DIR}}/` 下所有 `.md` 必须走 `{类型}.{主题}.md` 格式，类型七选一：

| 前缀 | 回答什么问题 |
|---|---|
| `spec.` | 做什么 |
| `design.` | 怎么做 |
| `plan.` | 什么时候做 |
| `rule.` | 为什么不能那样做 |
| `guide.` | 怎么操作 |
| `report.` | 做了什么 |
| `debt.` | 欠了什么（已知边界 / TODO 留尾 / 不确定风险） |

详见 `{{DOC_DIR}}/rule.doc.naming.md`。

**`debt.` 是最容易被忽略也最值钱的一类**：交付时主动声明的「已知边界」必须落到对应的 `debt.*.md`，不能只留在提交信息里——否则下次没人记得。

### 5. 变更记录走碎片文件

任何代码改动，提交前在 `changelogs/` 建一个碎片文件：`YYYY-MM-DD_<短描述>.md`，内容为纯表格行：

```
| feat | <模块> | 新增了什么 |
| fix | <模块> | 修了什么 |
```

类型只允许：`feat` `fix` `perf` `refactor` `docs` `chore` `test` `ci` `security` `style` `revert`。

**为什么不直接写 CHANGELOG.md**：多人/多分支并行时，直接编辑同一个文件必然在同一位置冲突。碎片文件各自独立，彻底消除合并冲突。发版时再合并。

### 6. 不许空白等待

任何超过 2 秒的等待，屏幕上必须有持续变化的内容：

- AI 响应用流式输出，逐字渲染
- 批量任务推进度（「正在处理第 3/45 个」）
- 长任务拆阶段，每阶段推状态

静止的「加载中…」超过 2 秒即为体验缺陷。做不到流式，至少给动画 + 预估耗时。

更一般的原则叫**预期管理**：用户任何时刻都该知道「现在在做什么 / 还要多久 / 接下来怎样 / 刚才变了什么」。

### 7. 验收必须闭环

验收的终点是「最终产物可见且正确」，不是「流程走了一半截图收工」。

- 触发了生成，必须等到产物**真的出现**才算完成
- 等待超时后的截图只能用于记录超时，**不得**用来宣称「已完成」
- 「接口返回 200」不等于「功能正常」——必须打开真实页面/真实产物确认

反面案例：截图上显示「正在生成…已等待 36s」，说明文字却写「渲染完成」。这叫断头验收，直接不合格。

### 8. 不假定不存在的能力

代码或方案里引用某个能力（语义搜索、实时协同、某个外部服务）时，必须确认它真的存在。

- 不存在 → 明确标注「当前不具备，需要 X」，给替代方案
- 不要静默降级或假装能做
- 做不到的不硬做，明确暴露 + 借用外力（换个服务 / 让用户提供 / 换个做法）

判断标准：**这个能力是运行时可验证的吗**（接口存在 / 文件在 / 服务能连上）？不可验证就必须标注为未实现。
