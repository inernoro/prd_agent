# 文档命名规范 · 规则

> **版本**：v1.0 | **状态**：已落地

## 格式

`{{DOC_DIR}}/` 下所有 `.md` 文件必须走：

```
{类型前缀}.{主题}[.{子模块}].md
```

两条铁律：

1. **类型前缀七选一**，否则不许落盘
2. **主题第一段是应用/领域名**，子模块用 `.` 续接，禁止用 `-` 把领域名和子模块黏死

## 七种类型

| 前缀 | 回答什么 | 典型内容 |
|---|---|---|
| `spec.` | 做什么 | 产品规格、用户故事、需求说明 |
| `design.` | 怎么做 | 技术设计、架构方案、技术选型分析 |
| `plan.` | 什么时候做 | 实施计划、里程碑、状态看板 |
| `rule.` | 为什么不能那样做 | 规范约定、红线、审计口径 |
| `guide.` | 怎么操作 | 操作手册、上手指南、排障备忘 |
| `report.` | 做了什么 | 周报、复盘、阶段总结 |
| `debt.` | 欠了什么 | 已知边界、后续可补、TODO 留尾、不确定风险 |

## 命名示例

```
正确：
  spec.checkout.md                 结算功能整体规格
  spec.checkout.coupon.md          结算-优惠券子模块
  design.checkout.payment-flow.md  支付流程技术设计
  debt.checkout.md                 结算模块的债务台账

错误：
  spec.checkout-coupon.md    领域名和子模块黏死，应点分
  checkout-spec.md           无类型前缀
  doc/samples/xxx.md         禁子目录，保持扁平
```

同一领域的文档第一段一致，文件列表会自动聚成簇，一眼就能建立心理预期。

## 文档头

每份文档 H1 之后紧跟一行元信息：

```markdown
# <标题> · <类型中文名>

> **版本**：vX.Y | **日期**：YYYY-MM-DD | **状态**：<状态>
```

状态枚举：`草案` / `规划中` / `开发中` / `已落地` / `已废弃`

## design 类特别要求

- **第一节必须是管理摘要**：30 秒让非技术读者看懂方案全貌
- **故事靠前，设计靠后**：管理摘要 → 背景 → 目标 → 决策 → 架构 → 数据 → 接口
- **代码有节制**：全文代码不超过 30%，每段代码前有一句话说明
- **永远替换，不留历史**：不写「v2.0 变更：xxx」，每次更新直接覆盖全文，版本追踪交给 git

## 为什么要有这条规则

没有命名规范时，`doc/` 三个月后会变成：`新方案.md`、`新方案-最终版.md`、`讨论记录0312.md`、`output-2.md`。
谁都不知道哪份是权威的，也不知道一份新文档该叫什么。

七类前缀强制回答一个问题：**你这份文档到底是在回答「做什么」「怎么做」还是「什么时候做」**。
答不上来的文档，通常本身就不该写。
