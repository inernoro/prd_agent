# 七类文档骨架模板

> `/sdd-init` 只生成第一份 `spec.*`；其余六类在用户需要时按本文件套用。
> 每个模板都保持「能立刻下笔」的粒度——章节标题给全，内容给一句引导语，不给假数据。

所有模板的头部统一：

```markdown
# <标题> · <类型中文名>

> **版本**：v1.0 | **日期**：YYYY-MM-DD | **状态**：草案
```

---

## spec.（做什么）

```markdown
## 一、要解决的问题

<谁、在什么场景下、遇到什么麻烦。写现象，不写方案。>

## 二、目标与非目标

**目标**
- <这次要达成的，可验证>

**非目标**
- <明确不做的，防止范围蔓延>

## 三、用户场景

| 角色 | 场景 | 期望结果 |
|---|---|---|
| | | |

## 四、功能需求

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| F1 | | 必须 / 应该 / 可以 | <怎么算做到了> |

## 五、已知边界

<这一版明确不覆盖的情况。写清楚比假装没有强。>
```

---

## design.（怎么做）

```markdown
## 一、管理摘要

<30 秒让非技术读者看懂：解决什么问题、选了什么方案、代价是什么。禁止代码。>

## 二、背景与约束

## 三、方案决策

| 方案 | 优点 | 代价 | 是否采用 |
|---|---|---|---|

<为什么选这个、放弃了什么。这一节比架构图值钱。>

## 四、架构

## 五、数据设计

## 六、接口设计

## 七、风险与回滚
```

---

## plan.（什么时候做）

```markdown
## 状态看板

> 最后更新：YYYY-MM-DD HH:mm | 距离可交付：<一句话>

| 阶段 | 进度 | 状态 | 当前阻塞 | 下一步 | 验收证据 |
|---|---|---|---|---|---|
| | | 未开始/进行中/已完成/阻塞 | 无 | <具体到做什么> | <可点击链接> |

## 里程碑

## 依赖与前置
```

看板的六列一列都不能少。「验收证据」必须是可点击的链接或可复现的命令，写「已测」不算。

---

## rule.（为什么不能那样做）

```markdown
## 一句话

<这条规则禁止什么 / 强制什么>

## 强制条款

1.
2.

## 反面案例

<真实发生过的事故。没有事故的规则大多是想象出来的，会被忽略。>

## 自查清单

- [ ]
- [ ]
```

规则文档的价值在**历史背景**那一段：写清楚这条规则是被什么坑砸出来的，后来人才会遵守。

---

## guide.（怎么操作）

```markdown
## 什么时候用这份指南

## 前置条件

## 步骤

### 1. <动作>
<命令 / 点哪里>
预期结果：<看到什么算成功>

### 2. <动作>

## 出问题了怎么办

| 现象 | 原因 | 处理 |
|---|---|---|
```

每一步必须有「预期结果」，否则用户不知道自己走对没有。

---

## report.（做了什么）

```markdown
## 摘要

## 完成项

| 项 | 说明 | 证据 |
|---|---|---|

## 数据

## 遗留与下一步
```

---

## debt.（欠了什么）

```markdown
## 台账

| 编号 | 类型 | 描述 | 影响 | 状态 | 备注 |
|---|---|---|---|---|---|
| D1 | 已知边界 / TODO / 风险 | | | 未偿 / 已偿 | |

## 明细

### D1 <标题>
- **是什么**：
- **为什么欠着**：
- **什么条件下必须还**：
- **不还的后果**：
```

交付时说的每一句「这版先不做 X」「后面再补 Y」，都要在这里落一行。只写在提交信息里等于没写。
