# 仓库自适应文档生成

> 版本：v2.0.0 | 仓库约定优先，模板只作兜底

## 核心原则

文档不是填表。先确认读者需要做什么决策，再选择最短且足够的结构。不得把某个项目的目录、命名法、状态枚举或产品标识强加给其他仓库。

## 第一步：发现约定

按优先级读取：

1. 用户明确指定的路径、类型和格式。
2. 最近的 `AGENTS.md`、`CLAUDE.md`、贡献指南、文档规则。
3. 文档索引、相邻同类文档和既有文件命名。
4. 仓库外部文档系统的明确接入说明。
5. 都不存在时使用本技能的中性默认值。

发现过程只读必要文件，不遍历整个大型仓库。规则冲突时列出冲突并请求选择，不自行覆盖高优先级约定。

## 第二步：确认文档任务

从用户话语推断并确认以下信息；能够可靠推断时不要反问：

- 目标读者：产品经理、业务专家、开发、测试、运维或管理者。
- 文档目的：决策、需求对齐、方案评审、实施、操作、验收、复盘。
- 生命周期：草案、评审中、已批准、实施中、已完成、已废弃。
- 事实来源：用户输入、代码、现有文档、测试证据或外部链接。
- 落盘位置：遵循仓库约定；没有约定时先给建议路径。

## 第三步：选择结构

常见文档结构见 [reference/templates.md](reference/templates.md)。它们是可组合模块，不是强制类型枚举。

推荐映射：

| 目标 | 推荐结构 |
|---|---|
| 讲清要做什么和为什么 | 需求说明 |
| 讲清怎么实现和权衡 | 技术设计 |
| 安排步骤、责任和里程碑 | 实施计划 |
| 让新人或操作者完成任务 | 操作指南 |
| 固化长期约束 | 规则或决策记录 |
| 汇报结果与证据 | 报告 |
| 记录已知限制 | 风险与技术债 |

## 第四步：写作与校验

1. 标题直接说明主题，不堆项目代号。
2. 开头先写结论、读者和状态。
3. 事实、假设、决策、建议和待办分开表达。
4. 面向非技术读者先写业务影响，再写技术细节。
5. 验收条件可观察、可执行，避免“体验良好”等空话。
6. 链接使用相对路径并确认目标存在；敏感信息只描述安全获取方式。
7. 若仓库要求同步索引、目录或元数据，必须一并更新；否则不擅自创建索引体系。
8. 完成后检查重复、矛盾、失效链接、未定义术语和无负责人的待办。

写作原则详见 [reference/writing-principles.md](reference/writing-principles.md)。

## 中性默认值

仅在仓库没有规则时使用：

- 路径：优先现有 `docs/`；不存在则建议 `docs/`，落盘前遵循用户选择。
- 文件名：小写短横线，表达主题，例如 `customer-import-guide.md`。
- 日期：绝对日期 `YYYY-MM-DD`。
- 状态：草案、评审中、已批准、已完成、已废弃。
- 元数据：标题、状态、更新时间、负责人；未知项写“待确认”，不编造。

## 输出

交付时说明：

```markdown
- 文档：<path or draft>
- 读者：<audience>
- 用途：<decision or action>
- 采用约定：<rule source or neutral default>
- 同步项：<index/metadata/none>
- 待确认：<none or list>
```

## 不可违反

1. 不强制固定目录、七类前缀或某个产品的 appKey。
2. 不把执行日志、密码、API Key 或临时截图塞进长期文档。
3. 不编造已通过的测试、已批准的决策或不存在的链接。
4. 不为了模板完整而制造无信息章节。
5. 不改写与本任务无关的既有文档。
