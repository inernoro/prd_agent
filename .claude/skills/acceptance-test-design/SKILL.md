# 验收测试设计

> 版本：v2.0.0 | 设计测试，不伪造执行结果

## 目标

回答四个问题：

1. 这次变化声称解决了什么？
2. 最可能在哪里失败？
3. 最少需要哪些高价值场景证明它？
4. 什么证据足以支持通过或不通过？

## 规则发现

按以下优先级建立验收契约：

1. 用户明确指定的标准、档位和范围。
2. 目标仓库中的验收规则、贡献指南、测试说明和 CI 契约。
3. 用户明确选中的组织级配置档。
4. 本技能的通用基线：[references/rules/baseline.md](references/rules/baseline.md)。

仓库没有特定规则时继续使用通用基线，不因缺少某个平台或内部文档而失败。若外部规则与通用基线冲突，记录冲突并采用更高优先级来源。

## 输入类型

- 需求或缺陷描述。
- PR、commit、分支差异。
- 指定页面、API、工作流或发布范围。
- 某个自然日或明确时间窗口。每日范围脚本支持 `--timezone`，不固定地域。

## 设计流程

### 1. 提取断言

把输入改写成可验证断言：

| 断言 | 用户 | 前置状态 | 动作 | 可观察结果 | 失败影响 |
|---|---|---|---|---|---|

拒绝“功能正常”“体验良好”之类无法判定的句子。PR、commit 或时间窗口中的每项变化都必须被测试用例覆盖、合并进可追溯的融合场景、标记为非运行时变化，或明确列为未覆盖，不能因不方便测试而消失。

### 2. 建立影响面

覆盖实际相关的层面，不机械全选：

- 用户入口与主流程。
- 权限、身份和多角色差异。
- 数据写入、读取、恢复和兼容。
- 异步任务、重试、重复提交和并发。
- 外部依赖、超时、降级和错误反馈。
- 响应式、主题、键盘、无障碍和浏览器差异。
- 部署、配置、迁移、回滚和可观测性。

对于录音、上传、转录、生成、同步、归档、部署等多阶段任务，必须建立连续性状态矩阵，分别覆盖正常、慢速、失败和恢复路径。即时反馈、首个可用结果、后台进度、刷新恢复、任务身份保持和返回上下文是不同断言，不能只检查最终完成页。

连续性场景还必须定义可测的页面抖动指标，例如文档启动次数、history 写入次数、内容加载器重复出现次数、首个反馈耗时和首个可用结果耗时。意外的整页刷新、路由往返、状态倒退或任务身份丢失均应有明确失败阈值。

### 3. 风险排序

风险分数建议使用 `发生概率 x 影响 x 不可发现性`，每项 1-5。优先覆盖高分项、不可逆操作、权限边界和用户主路径。

### 4. 设计融合用例

不要为每个断言各建一个孤立用例。把同一用户旅程中的功能、异常、权限、视觉和恢复行为合并为较少的完整场景。

每个用例包含：

```yaml
id: AC-001
title: 清晰描述用户目标
priority: P0
preconditions: []
steps: []
assertions: []
negative_checks: []
cleanup: []
evidence:
  provenance: deterministic-fixture | preview-live | integration-live
  primary: 页面、API 响应或持久化结果
  supporting: 日志、事件、截图或指标
  prohibited_substitutes: 不能替代主证据的内容
```

### 5. 设计证据矩阵

证据强度和替代边界见 [references/proof-strength.md](references/proof-strength.md)，融合策略见 [references/fusion-testing.md](references/fusion-testing.md)。

| 断言 | 主证据 | 证据来源 | 佐证 | 通过门槛 | 禁止替代 |
|---|---|---|---|---|---|

原则：页面改动优先用真实用户路径与可见状态；API 改动优先用真实请求与状态变化；部署改动优先用目标环境状态与入口请求。内部日志通常只能佐证，不能替代用户可观察结果。

证据来源必须标记为 `deterministic-fixture`、`preview-live` 或 `integration-live`。确定性注入可以证明界面状态机和布局，但不能冒充对象存储、语音识别、队列、大模型或其他真实外部依赖已经成功。

### 6. 形成执行简报

按 [references/output-contract.md](references/output-contract.md) 输出：范围、环境、账号角色、安全凭据来源、用例顺序、停止条件、证据要求、清理方式和未覆盖风险。

若目标仓库安装了浏览器、API、部署或报告归档技能，可把执行简报交给对应工具；不要硬编码技能名或宿主目录。没有执行工具时只交付设计，并明确“尚未执行”。

## 每日范围脚本

```bash
python3 scripts/daily_scope.py --repo . --timezone <IANA timezone> --date YYYY-MM-DD
```

未传日期时取所选时区的前一个自然日。脚本只盘点 Git 范围和风险线索，不决定 Verdict。

## 输出结论

测试设计本身只能给以下状态：

- `READY`：范围、环境、用例和证据契约完整，可执行。
- `BLOCKED`：缺少环境、身份、数据或规则冲突，无法可靠执行。
- `DRAFT`：仍有待确认断言或覆盖缺口。

只有真实执行并取得证据后，执行者才能给 `PASS`、`FAIL` 或 `PARTIAL`。

## 不可违反

1. 不把代码存在、组件渲染或容器启动当作业务通过。
2. 不用内部页面证明另一个系统或服务的改动。
3. 不从分支名猜预览地址，不在报告中泄露凭据。
4. 不固定某个组织、产品、平台、目录或时区。
5. 不用截图数量代替断言覆盖。
6. 用户可见改动不以接口成功替代页面主证据，也不以相邻页面替代目标行为。
7. 多阶段任务不以最终状态替代正常、慢速、失败和恢复四条路径。
8. 确定性注入证据不改称真实外部集成证据。
