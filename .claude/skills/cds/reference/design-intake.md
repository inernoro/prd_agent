# CDS 设计接入

从 CDS「设计」页的「接入 Agent」复制标准口令，再交办「请按说明接入并提交当前设计稿」。接入链接使用 `target=existing`、项目 ID、`skills=cds` 和 `mission=design-publish`。交付者和接收者通过项目里的私有稿件、版本和回执协作。

## 开工前

1. 在当前工作区用 `cdscli setup-check --host <CDS 地址> --project <项目 ID> --design-access publish` 自检。设计发布用 `publish`，实施反馈用 `feedback`，读取资料用 `read`。缺权限时，保持同一项目和角色，用 `cdscli connect --host <CDS 地址> --project <项目 ID> --design-access publish --agent <智能体名称>` 发起申请。系统所有者到「项目」页右下角的「授权申请」核对项目和角色后批准。智能体自动领取凭据，保存在本工作区，并再次自检。等待中断时继续原命令。MCP 从同一工作区以 `node <CDS 源码>/cds/mcp/src/server.mjs --design` 启动。
2. 调 `cds_design_read`，传 `{"view":"intake"}`。核对项目、框架和稿件，并从 `requirements` 按约定的 `designKey` 读取已确认需求原文、来源计划和对话。CLI 的同等入口是 `cdscli design intake`。接口为 `GET /api/projects/:projectId/design/intake`，当前协议版本为 `1`。已授权的设计凭据可直接读取项目中交给设计的单条需求，工程规划接口继续按现有范围控制。

交给设计的需求以系统所有者确认的原计划为来源。接入清单同时提供 `designs`。相同标识已有稿件时用原稿 ID 和读到的最新版续版，尚未有稿件时才用该标识发布首稿。指定的需求查不到时先核对项目与标识，请项目管理者从原计划交给设计。开工前有问题时，用 `cds_design_feedback` 的 `brief.reply`，提供 `designKey`、回读的 `expectedVersion`（即需求的 `planVersion`）、`requestId` 与 `body`。CLI 用 `cdscli design brief-reply <designKey> --expected-version <planVersion> --body <说明>`。服务端把澄清与需求原文一起回读，人和设计智能体可在同一处回复。
3. 先从清单定位与用户目标有关的稿件。按 `designId` 与 `latestVersion` 固定原稿，按框架 ID 与版本读取规则。目标项目、原稿、基线、改动范围或权限依然不明确时，在修改和发布前一次提清问题。已读到的信息直接采用。不同项目或已存在的历史相似稿件均按实际 ID 与授权范围处理。

同一工作区的设计凭据到期时，使用原接入口令续接。CDS 会核对原凭据，获批后保留原稿作者身份。

技能需要更新时，从接入说明提供的 `/api/skills/cds-pack/download` 匿名下载归档。用本机工具解压并核对 manifest，将完整五技能装到当前工作区，再以原来的设计授权自检。Windows 检出的技能文本只有 CRLF 与 LF 的差异时可以通过自检。

## 决定写入动作

| 意图 | `cds_design_publish` 的字段 | CDS 中的结果 |
| --- | --- | --- |
| 新稿 | `intent=create`，稳定 `designKey`，独立稿件子目录 | CDS 分配稿件 ID，从 V1 开始 |
| 同稿修订 | `intent=revise`，现有 `designId`，读回的 `expectedVersion` | 原稿件新增一版 |
| 新模块的首份稿 | `intent=create`，采用新模块段的 `designKey`，独立稿件子目录 | 新模块的独立稿件 |

`designKey` 使用 `module/draft`。两段用稳定的小写字母、数字和连字符，标题、文件名和换智能体都沿用原稿件接入标识。模块下可以有不同的稿件标识。`design.json.group` 用于页面展示分组。旧稿没有接入标识时，先用原 ID 续版。如已确认长期标识，可在一次已授权的续版中同时绑定。接口对项目内相同标识或已登记目录拒绝重复新建，过期基线须回读新版。已有稿件后，未声明意图的旧 Agent 可按原 ID 续版，新稿使用明确的创建动作。

基线冲突先回读对应稿件的新版本和变更，再确认希望继续的修订。发布权取决于该稿件的发布身份，以 `canRevise` 为准。项目读取权限让接收者查看版本和回执。

## 出稿与发布前自查

自检全部通过不代表稿件可用。每次新稿和续版都按下面的原则自查，发布前逐条回答，结果写进交付说明。问题要由设计方在发布前发现，不能留给用户。

| 原则 | 发布前要回答的问题 |
| --- | --- |
| 基线即约束 | 逐画面对照登记的实施基线，记录每处有意改动和回退。首稿或撤销定稿后，以确认的需求、项目采用的框架和可用的正式页面为依据，并在交付说明记录来源。基线和当前线上实现各自核对 |
| 宿主一致 | 是否在 CDS 的预览容器里测过？检查 375 CSS 像素的触控视口、桌面和 Windows 100%、125%、150% 的等效视口，记录实际浏览器、视口和深浅主题。控制台是否零报错？ |
| 重点优先 | 谁来这一页、第一件事做什么？首屏是否先给这件事？顺序：等我处理 → 新变化 → 进行中 → 参考资料 |
| 每样东西有根 | 需求和稿件是否归到所属模块，框架是否标明系统或模块适用范围？写明负责人、状态和下一步 |
| 变化可见 | 新稿、新版本、新反馈是否有「新」标记，看过之后是否消失？ |
| 动作可预期 | 每个按钮做的是不是它写的事？一页是否只有一个主动作？不可逆操作是否放在次要位置并二次确认？ |
| 一个状态一种写法 | 阶段和待办是否分开？同一件事是否只出现一次？ |

流程：

1. 出稿前，按可用对照依据列出已确认决定，从需求列出「角色 × 任务」。
2. 每改一处，按原则把同类问题一起修掉，不只修被指出的那一处。
3. 发布前：
   - 在预览容器里自检，零报错；
   - 逐画面做基线差异表，写明有意改动还是回退；
   - 按角色和任务亲自点一遍，记下步数、卡住和看不懂的地方，每条标上原则和级别；
   - 阻断、误导、数据错这类高优先级问题清零。
4. 交付说明附走查记录和基线差异表。
5. 验收项写意图和可测量的结果，例如「页头第一行在 1024 宽下不折行」，不要把布局细节写死。写死的布局会被实现方照做，问题会带进正式页面。

### 信息分层

「重点优先」和「一个状态一种写法」落到卡片、页头和详情上，按下面的规则。出稿前先把一页上会出现的信息逐条归类，再决定放在哪。

卡片和列表行上的信息分八类：

| 类 | 回答什么 | 卡片上 |
| --- | --- | --- |
| 身份 | 这是哪一份（缩略图、标题） | 放。标题一行，超出省略 |
| 变化 | 上次来之后有没有变（新稿、新 V4） | 放在缩略图左上角，有才出现，看过后消失 |
| 状态 | 到哪一步、结论是什么 | 放，只放一个 |
| 时间 | 多新 | 和状态同一行 |
| 待办 | 要不要我做什么 | 不重复。由「等你处理」这类分区表达 |
| 出处 | 谁做的、第几版 | 放到列表模式和详情 |
| 关联 | 框架、评论数、标签 | 放到列表模式和详情 |
| 明细 | 为什么是这个结论（自检明细、失败规则） | 不上卡片，放进详情 |

规则：

- **卡片**：文字最多两行，第一行标题，第二行状态和时间。缩略图上不贴和状态重复的标记。
- **状态**：一种对象只有一套状态词，三四个就够，每个都要说得清怎么离开这个状态。没人能「处理完」的记录（例如作者自检）不是状态，否则会一直挂在卡片上。卡片、分组、筛选、页头都用同一套词。
- **数字**：标签和分区上只放要动手的数（等我处理的、不通过的），只用一种写法（数字徽标）。总数、版本数这类只是信息的数不放。
- **顶部**：
  - 内容前的横条越少越好，不重复上一层已经给出的信息（例如稿件页头已有版本和基线，交付区就不再写）；
  - 同一行左右空着时合并（例如画布工具和版本动作分放两行的右边，省出一整行给预览）；
  - 简短状态并进主控件。影响下一步的原因保持可见，补充说明支持键盘和触控展开。
- **详情**：
  - 一条反馈或需求就是一个要求，按编号、大标题一条一条列：诉求 → 怎么算解决 → 问题 → 依据 → 往来；
  - 登记时诉求和怎么算解决必填，关闭时在复核说明旁对照「怎么算解决」。没有要求就没有约束；
  - 资料按「为什么要看」编号分组，每组写一句用途；
  - 验收先给一句结论（还差几件、差什么），再列要补的。

每一页先写下它要回答的问题，再按编号、大标题一条一条列。回答不了这个问题的内容，移到它该在的页，不在这一页重复。常见的三类页面：

| 页面类型 | 例子 | 怎么列 |
| --- | --- | --- |
| 流程类 | 做法验收、开始出稿 | 先给一句结论，再给编号的下一步：只有当前一步高亮并给主按钮，后面的写「先完成第 N 步」，已完成的打勾。还没开始的结果不要铺成「条目 × 视口」的矩阵，按状态分组 |
| 文档类 | 思路、交付说明 | 不管作者用什么标题，按意思归到固定顺序（目标 → 关键取舍 → 本版改动 → 依据 → 待定），其余小节按原顺序放在后面。顶部放目录，旧的「回顾」默认收起，开头的说明收成一行小字 |
| 对照类 | 规范、版本对比 | 先给差异，每条写「新增 / 修改」、「类别：名称」和一句说明。不出现原样 JSON 和内部编号，表头不算一条 |

改版式时，核对每条状态的含义、限制和恢复方式。保留「暂时无法核对当前预览提交」一类操作原因。遇到与稿件、实现或部署记录冲突的说法，按实际记录修正。发布前用同画面对照图检查这些信息。

### 导航

页头、工具栏和标签按下面的规则规划。出稿前把一页顶部的每个控件列出来，逐个决定留、缩、藏、并。

- **按使用场景安排**：
  - 核心状态（例如版本）和常用动作（例如大屏、评论、单屏 / 全部）留在外面；
  - 一次性设置（例如命令行、接入 Agent）合成一个菜单；
  - 偶尔用、只有少数人用的操作（例如定稿、撤销定稿、设置评审人、框架候选）放进「···」面板。
- **同一件事只用一个控件**：
  - 缩放用一个菜单，不用「− 适应 +」三个按钮；
  - 二选一用一个切换按钮；
  - 附属信息并进主控件，例如选择框直接写「V4 · 最新 · 基线 V2」，不再另放标记。
- **面包屑只表达位置**：
  - 写法是 `产品 / 模块 / 项目 ▾ / 文件夹`，到上一级为止，当前页由页面标题表达；
  - 项目这一段就是项目切换；
  - 标签、版本、筛选是页内状态，不进面包屑；
  - 有了面包屑，页面里不再放返回按钮或第二条路径；
  - 详情页在手机上只留「‹ 上一级」。回到模块入口可继续切换项目。
- **工具跟着它管的东西走**：只作用于画布的控件放在画布上或画布那一行，管整份稿件的放在页头。同一组控件在不同页面换位置时，写清每种页面放在哪。
- **先问每页回答什么，再决定合并标签**：
  - 用同一块内容的合成一页，例如预览和对比是同一块画布的两种模式；
  - 同一读者、同一目的的合成一页，例如思路和规范都是写给实现方读的；
  - 和别的页重复的内容并过去，不在两处各放一份；
  - 合并后旧地址要照常打开。

### CDS 预览容器

用[正式宿主预览](#按正式宿主预览)的 CLI 在本机核对入口、主题、控制台和 CSP 记录。测试嵌套画面时收集所有框架的错误。手机按 375×812 CSS 像素和触控模式测量，可使用 Playwright 移动设备参数或 DevTools 设备模拟。

## 提交与交付

- `design.json.project` 等于绑定的项目 ID。保留适用的固定框架和画面编号，包含 `design.json`、`思路.md` 与清单声明的单文件 HTML。标准新建由服务器分配 ID，清单和请求均省略稿件 ID。续版可沿用清单中的同稿 ID。
- 在工作区仅提交获授权的稿件子目录。若没有 Git 作者配置，可为本次提交指定智能体自己的作者身份。CDS 根据获授权的身份记录发布者。使用 `cdscli design publish --private --dir <稿件目录>`，按新稿或续版附上相应参数。提交保留在本地，稿件及归档摘要存入已获授权的 CDS 项目。
- MCP 通过 `cds_design_publish` 传 `sourceMode: "private"`、`zipPath`、本地 `sourceCommit`、仓库相对 `sourcePath`、`requestId` 和意图字段。用本地提交导出稿件目录的 ZIP，放在项目工作区内，避开 `.cds` 和 `.git`，稿件门禁上限 3.8 MiB。HTTP 使用同一项目的 `/design/packages`，内容为 ZIP，其余字段通过查询参数传递。
- 已获授权并已存在于项目 Git 的材料可以沿用 Git 核验方式。CDS 分别显示 Git 核验证据和私有归档。
- 在 `note` 记录原版、改动画面、原因和待核验项。发布后按回执的 `designId` 与 `version` 回读，核对项目、源提交和归档摘要。响应不确定时以原 `requestId`、来源、意图和稿件内容重试。设计接入按 ZIP 内的文件内容识别重试。接收者从同一项目回读固定的新旧版，定位差异后复拍受影响画面。缺实拍仍标待核验。
- 私有发布的版本摘要 `sha256` 来自上传 ZIP 的原始字节。清单同时保留每个文件的 `sha256` 和原型的 `prototypeSha256`，用于分别核对交付文件和原型。


## 完整交付资料

- 原型、清单、设计思路、交付说明、开发与设计文档、可重建源码、框架草案、截图和自检可一起提交。声明过的资料用包内相对路径，可用中文。版本会保留原 ZIP，以及每份文件的路径、类型、大小、摘要和可识别的文档章节。未知类型的附件也可按版本下载。附件内容是工作材料。
- `design.json` 可用 `docs` 列出设计、开发和决策文档，`source` 指向用于重建的源码，`frameworkDraft` 指向框架草案，`prototypeVersion`、`date`、`notes` 补充作者交付说明。CDS 自己记录稿件版本和发布时间。
- 画面共用入口时，可用 `entryActions` 依次选择原型内可见控件，用 `entryReadySelector` 声明原型状态就绪标志。它们随版保留。框架自动测量切换状态后等待对应的就绪标志，缺少状态证据时记录为待验证。`impl` 和 `readySelector` 用于打开与验收对应的实现页。画面与声明的行为不符时，先查看该版材料并提反馈。
- `cds_design_read` 的 `delivery` 读取固定版资料与验收缺项，用 `{view:"file",id,version,path}` 原文分段回读。接着传响应的 `nextOffset`，已到结尾时它为空。可以从稿件的「交付」下载原包或单个文件。继续使用历史版本的来源记录、原型、思路及验收数据。
- 作者的原型自检负责记录原型状态。实现路径、实现分支的验收证据及真人签收继续由各自的入口独立记录。共用入口不明确、缺实拍、缺实现地址或缺探针时，在反馈中说明要补的内容和复核方法。

## 实施版本与升降级

1. 从稿件读取最新版本、实施基线和最近签收的已实现版本。已实现版本只由 CDS 按签收更新。历史稿还没有签收时显示未知，实际分支和提交可用于独立核对升级起点。
2. 有权成员在开始时锁定本轮目标。CLI 用 `cdscli design start-upgrade <稿件> --version <目标> --expected-baseline <当前基线> --as-user <账号>`。`--version` 省略时，服务端锁定当时的最新版本。基线缺失时 `--expected-baseline` 传 `0`。后续发布会更新最新稿件，进行中的目标继续沿用锁定版本。
3. 调 MCP `cds_design_read`，传 `{"view":"diff","id":"<稿件>","fromVersion":11,"toVersion":17}`，或运行 `cdscli design diff <稿件> --from 11 --to 17`。CDS 用两端清单计算画面、验收项和交付文件的新增、删除和改动。调换两端即可核对回退。稿件附源码差异时，从固定目标版读取对应目录，再在实际起点核对能否应用。
4. 需要切到历史版本时，有权成员用 `cdscli design freeze <稿件> <历史版号> --reason "<原因>" --expected-baseline <当前基线> --as-user <账号>`。已有进行中的升级需要先完成，或凭升级编号和原因在页面取消，也可用 `design cancel-upgrade <稿件> --upgrade <编号> --reason "<原因>" --as-user <账号>`。
5. 按锁定版绑定实际页面并完成验收。有权成员签收后回读运行和已实现版本。新版本发布后可按新的两端重复流程。
6. 验收主用 CDS 自身代码时，`cdscli design accept <稿件> --installed --version <目标> --commit <已部署提交>` 只创建验收运行，锁定服务端实际读取到的构建。用 `design result` 回读运行、提交和入口后再取证。PR 预览沿用 `--pr`，两种入口分别选择。

## 发布门禁

CDS 按以下规则校验稿件。驳回回执返回规则编号。用 `intake` 里的 `versionHistory` 核对先前版本及源提交，再补齐版本登记和差异索引。修正交付内容后沿用原稿件，以最新已发布版本作为续版的 `expectedVersion`。

| 编号 | 提交条件 |
| --- | --- |
| G-01 | `design.json` 可解析，项目、标题、原型版本、日期与交付资料字段有效。 |

## 双向反馈

1. 实现方先读 `intake`、固定版 `delivery` 和已有 `feedback`。用 `cds_design_feedback` 的 `feedback.create` 记录复用建议、实施做法、需求缺漏、落地约束或验收建议。提供稿件、版本、分类、标题、理由、改动依据和可核对证据。对整份稿件或特定画面都可以登记。
2. 设计方通过 `cdscli design feedback <稿件编号>`（可选择版本，仍含未关闭的旧版反馈）读同一线程，调用 `design feedback-reply` 或 MCP `feedback.reply` 回复。需要改稿时按原稿 ID 和最新稿件版本续版，再在回复的 `revision` 引用自己发布的实际版号。只需解释、确认约束或说明方案取舍时，可以直接回复。
3. 原反馈者回读新版和同一线程，按证据验证。用 `feedback.resolve` 的 `close` 或 `reopen` 加说明保留复核结果。项目管理者也可处理。发布、反馈、实际做法验收和人类签收各自按项目权限执行。重试沿用原请求编号。

新反馈的 `body` 用 Markdown 的「## 诉求」和「## 怎么算解决」写清目标与完成标准，可以附「## 问题」。旧反馈由提出人或可访问项目的管理者在原线程补写这两个章节。页面选择「补写诉求和完成标准」，CLI 给 `design feedback-reply` 加 `--supplement`，MCP 的 `feedback.reply` 传 `supplement: true`。补写保留原正文、处理状态和回执。

针对交付文件提反馈时，从该版本的 `delivery.files` 读取完整 `path`，用 `feedback.create` 的 `filePath` 关联。服务端核对文件属于所选稿件版本。

需要提交对照图时，用 `feedback.attach` 提供原稿 ID、反馈 ID、图片说明、请求编号与工作区内 `imagePath`。CLI 用 `cdscli design attach-evidence <designId> --feedback-id <feedbackId> --title <说明> --file <图片.png>`。要标明截图来源时，加 `--version`、`--screen`、`--slot`，对应 MCP 的 `version`、`screenId`、`slot`。回读 `attachments` 核对回执、版本和截图。已授权成员可查看交付页或读取 `GET /api/projects/:projectId/design/artifacts/:artifactId`。每张 PNG 上限 1.5 MiB。逐规则的验收结论仍由做法验收记录。

正文走 `POST /api/projects/:projectId/design/feedback`，PNG 走 `POST /api/projects/:projectId/design/feedback/attachments`。固定版本资料可用 `GET /api/projects/:projectId/design/artifacts/:artifactId?view=text` 分段读取。

## 逐画面对照

稿件附 `设计文档/视觉验收标准.md` 时，实施基线的签收需要所有声明画面的同视口、同主题对照通过。进入稿件「验收 → 逐画面对照」，先看缺图和有问题的行。约定同一状态和数据规模，逐个指出页头、标签、主体、浮层、底部。写对齐误差和溢出等实测数值。标出每个差异及其设计依据。单独一句「一致」按缺证据处理。

1. 从 `cdscli design result <稿件编号>` 或 `cds_design_read` 的 `run` 读取实际运行与提交。确认画面绑定、预览、视口和主题。
2. 用 `cdscli design visual <稿件编号> --run <运行编号> --commit <提交> --screen <画面> --slot <视口-主题> --file <检查.json>` 记录一行。MCP 调用 `cds_design_acceptance` 的 `acceptance.visual`。检查文件以 V-01 至 V-10 为键，每项提供 `status`（`passed`、`failed` 或 `missing`）和 `evidence`。可分次提交同一组截图的检查。
3. 实拍用 `--implementation <实现图.png> --path <预览内绑定地址>`，或 MCP 的 `imagePath` 和 `measured`（宽高、主题、相对路径）。未随稿发布的对照图可用 `--reference <对照图.png>` 或 `referenceImagePath` 补交。桌面用 1280×800，手机用 375×812，每张 PNG 不超过 1.5 MiB。符合相同条件的稿件验收项实拍可复用。换图后重新检查。
4. 回读 `run.visual[画面/视口-主题]`，查两张图及 V-01 至 V-10。补交审核证据使用有验收写权限的项目凭据，单独的设计发布和反馈授权仍用于原有设计流程。重试沿用同一请求编号和内容。签收由有写权限的项目成员确认。

## 按手段验收

带有 `设计文档/验收手段.md` 或 `acceptancePlan` 的稿件，使用「验收」下的总览、MECE 覆盖、对照图、视觉、流程、人工、冒烟、验收债务。可用 `check=mece`、`compare`、`visual`、`flow`、`human`、`smoke`、`debt` 固定手段入口。

发布时在 `design.json` 的 `acceptancePlan` 按手段记录 `applicable`。省略的手段默认适用。标为不适用时写明 `reason`，例如 `"smoke": {"applicable": false, "reason": "本稿仅描述离线流程，不涉及页面或接口"}`。在各稿件验收项的 `dimension` 写一个维度。可选值为 `correctness`、`compatibility`、`performance`、`security`、`operations`、`experience`。旧稿未标维度的规则会列出来，由后续续版补齐。

1. **覆盖与取证**。先回读当前运行和真实提交。用 `risk-matrix` 检查六维度，用适用手段对应技能走完整场景。对照图需要同条件双图和 V-01 对照结果，视觉需要当前实拍和 V-01 至 V-10 的结果。可分别登记适用性。人工核对继续写入稿件验收格。
2. **流程和冒烟**。用 `cdscli design flow <稿件> --run <运行> --commit <提交> --file <记录.json>`，冒烟改用 `design smoke`。MCP 用 `cds_design_acceptance` 的 `acceptance.flow` 或 `acceptance.smoke`。每次写一条稳定 `id`，同运行同编号更新原记录，重试沿用原请求编号。
3. **输入与回读**。流程提供 `id`、`title`、`dimension`、`role`、`steps`，每步写 `action`、`expected`、`actual`、`status`。冒烟提供 `id`、`title`、`dimension`、`target`（`page` 或 `api`）、`path`、`expected`、`actual`、`status`。状态使用 `passed`、`failed`、`missing`。路径为预览内相对地址。用 `design result` 或 MCP 的 `run` 回读 `flows`、`smoke` 和 `visual`。
4. **签收**。手段的结果根据这次运行回填的证据汇总，空结果按缺证据。适用手段需通过，验收债务单列。项目成员在页面确认，运行需对应当前实施基线的预览提交。

有审批权的成员可在验收页停用一种手段，填写理由后确认。CLI 使用 `cdscli design disable-method <稿件> --version <当前基线> --method <编号> --reason <原因> --as-user <成员>`，恢复时使用 `enable-method` 并省略理由。原有证据保留，恢复后继续参加计算。MCP `delivery` 可回读当前稿件版本的 `methodSettings`，已签收运行保留自己的记录。

`design.json` 可定义 `demo`（按顺序填写 `screen`、`title` 和可选 `tip`），并用 `videos` 声明验收页的包内 MP4 及章节。章节按秒数递增，每个验收手段使用一个章节。配置了隔离截图浏览器的实例会在私有发布后为缺少参考图的画面自动截图。持续缺图时，先核对画面入口动作，再补同视口、同主题的参考图。

客观验收还支持从同一项目回填覆盖风险和历史易错：

- `design coverage <稿件> --run <运行> --commit <提交> --file <记录.json>`，对应 MCP `acceptance.coverage`。填写 `dimension`、`risk` 和 `ruleIds`，用当前版验收项覆盖具体风险。该维度不适用时，请有权成员填 `reason` 与空数组 `ruleIds`。
- `design known-create <稿件> --file <记录.json>`，对应 MCP `known.create`。填写 `problem`、`how`、`check`、`screenIds` 和 `sources`。空 `screenIds` 作用于整份稿件。每个来源写 `kind`、`ref`、`count`，来源类别可用 `defect`、`ticket`、`feedback`。通过 MCP 的 `design` 查看登记后的 `knownIssues`。
- `design regress <稿件> --run <运行> --commit <提交> --file <记录.json>`，对应 MCP `acceptance.regress`。填写历史易错的 `issueId`、本轮 `status` 与实际 `evidence`。`status` 使用 `passed`、`failed`、`missing`。

## 固定框架版本

使用 `cdscli design scaffold --framework <框架ID> --framework-version <版本> --dir <新目录> --title <稿件名>` 复用该版规范。框架初衷可随稿件的 `spec/charter.json` 一并提交，或在框架导入时提供同样的 `charter` 对象。字段包括 `status`、`intent`、`problems`、`nonGoals`、`scope` 和 `owner`。可附示意稿 `example`、规则来源 `ruleSources` 和模块差异 `moduleDiffs`。

首稿脚手架生成 V1 的清单、交付说明和空版本索引。框架的候选检查保留为未验证。出稿时在 `design.json` 按画面写入规则和预期，并用实际自检更新 `checks/result.json`。直接提交脚手架会被 G-05 驳回。已有脚本需要读取原脚手架结构时，可用 `--legacy-template` 生成历史格式。

从实施基线提取时，先用 `cdscli design extract <稿件ID> --into <框架ID>` 查看候选。采用时把预览里的 `sourceVersion` 传给 `--version`，把 `expectedVersion` 传给 `--expected-version`，并指定要采用的 `--apply` 项。目标框架在用时，用 `--resolve rules=keep` 或 `--resolve tokens=adopt` 逐项确认。

## 按正式宿主预览

`cdscli design preview --dir <稿件目录> --screen <画面编号> --theme dark` 在环回端口打印预览地址。打开地址即可检查就绪状态，控制台和终端同时显示错误摘要。命令只读取稿件目录中的入口，不需要登录。桌面与手机版依照画面声明分别使用 1280×800 和 375×812。

正式画布和本机预览都以 `sandbox="allow-scripts"` 和相同的响应头 CSP 运行原型。原型使用不透明源，不能访问父页、网络接口、浏览器存储或外部资源。子画面用内联 `srcdoc`，把状态存到原型内存中；图片和字体按响应头允许的类型内联。需要自动进入的画面在 `design.json` 声明 `entryActions` 和唯一可见的 `entryReadySelector`，默认等待 8000 毫秒，可为单屏在 `entryTimeoutMs` 指定 500–15000 毫秒。提交前逐项检查两种主题、375 真机宽度以及 Windows 100%、125%、150% 等效视口，并保留对照证据。

## 从系统和模块接入

先读同一项目的 `cdscli design intake` 或 MCP `cds_design_read` 的 `intake`。使用 `systems[].modules` 选择系统和模块。交接需求与原稿会附上 `scope`，已有的 `designKey`、稿件编号和来源路径仍可继续用。若 `design.json` 声明归属，可填 `scope: {"systemId":"<系统>","moduleId":"<模块>","related":[{"systemId":"<系统>","moduleId":"<受影响模块>"}]}`。服务端会校验所有归属在当前项目登记。同一稿件的续版沿用主归属，需调整时由项目管理者先登记变更。

稿件未指定框架时沿用原稿框架；新稿依次查模块和系统的默认框架，使用 `intake.frameworks[].adoptedVersion` 对应的可用版本并在发布时锁定。设计方先读该版框架的范围、示意稿和源码，属于模块的局部差异写在已有稿件反馈或接入需求线程。

首稿可以先用 `cdscli design brief-claim <接入标识> --expected-version <计划版号>` 认领，也可调用 MCP 的 `brief.claim`。接入清单回读实际出稿人，写作权限沿用现有项目授权。原出稿人和项目管理者可在未发布首稿时用 `design brief-release` 或 `brief.release` 交回。需要澄清的事项继续回复同一个需求线程。
