# CDS 设计接入

从 CDS「设计」页的「接入 Agent」复制标准口令，再交办「请按说明接入并提交当前设计稿」。接入链接使用 `target=existing`、项目 ID、`skills=cds` 和 `mission=design-publish`。交付者和接收者通过项目里的私有稿件、版本和回执协作。

## 开工前

1. 在当前工作区用 `cdscli setup-check --host <CDS 地址> --project <项目 ID> --design-access publish` 自检。设计发布用 `publish`，实施反馈用 `feedback`，读取资料用 `read`。缺权限时，保持同一项目和角色，用 `cdscli connect --host <CDS 地址> --project <项目 ID> --design-access publish --agent <智能体名称>` 发起申请。系统所有者到「项目」页右下角的「授权申请」核对项目和角色后批准。智能体自动领取凭据，保存在本工作区，并再次自检。等待中断时继续原命令。MCP 从同一工作区以 `node <CDS 源码>/cds/mcp/src/server.mjs --design` 启动。
2. 调 `cds_design_read`，传 `{"view":"intake"}`。回读项目、协议版本、稿件 ID、接入标识、已登记的稿件目录、最新版本、续版权限、待处理反馈数量和框架。CLI 的同等入口是 `cdscli design intake`。接口为 `GET /api/projects/:projectId/design/intake`，当前协议版本为 `1`。
3. 先从清单定位与用户目标有关的稿件。按 `designId` 与 `latestVersion` 固定原稿，按框架 ID 与版本读取规则。目标项目、原稿、基线、改动范围或权限依然不明确时，在修改和发布前一次提清问题。已读到的信息直接采用。不同项目或已存在的历史相似稿件均按实际 ID 与授权范围处理。

同一工作区的设计凭据到期时，使用原接入口令续接。CDS 会核对原凭据，获批后保留原稿作者身份。

技能需要更新时，从接入说明提供的 `/api/skills/cds-pack/download` 匿名下载归档。用本机工具解压并核对 manifest，将完整五技能装到当前工作区，再以原来的设计授权自检。Windows 检出的技能文本只有 CRLF 与 LF 的差异时可以通过自检。

## 决定写入动作

| 意图 | `cds_design_publish` 的字段 | CDS 中的结果 |
| --- | --- | --- |
| 新稿 | `intent=create`，稳定 `designKey`，独立稿件子目录 | CDS 分配稿件 ID，从 V1 开始 |
| 同稿修订 | `intent=revise`，现有 `designId`，读回的 `expectedVersion` | 原稿件新增一版 |
| 新模块的首份稿 | `intent=create`，采用新模块段的 `designKey`，独立稿件子目录 | 新模块的独立稿件 |

`designKey` 使用 `module/draft`。两段用稳定的小写字母、数字和连字符，标题、文件名和换智能体都沿用原稿件接入标识。模块下可以有不同的稿件标识。`design.json.group` 用于页面展示分组。旧稿没有接入标识时，先用原 ID 续版。如已确认长期标识，可在一次已授权的续版中同时绑定。接口对项目内相同标识或已登记目录拒绝重复新建，过期基线须回读新版。已有稿件后，未声明意图的旧 Agent 可按原 ID 续版，新稿使用明确的创建动作。

基线冲突先回读对应稿件的新版本和变更，再确认希望继续的修订。发布权取决于该稿件的发布身份，以 `canRevise` 为准。项目读取权限让接收者查看版本和回执。

## 出稿与发布前自查

自检全部通过不代表稿件可用。每次新稿和续版都按下面的原则自查，发布前逐条回答，结果写进交付说明。问题要由设计方在发布前发现，不能留给用户。

| 原则 | 发布前要回答的问题 |
| --- | --- |
| 基线即约束 | 和实施基线比，每处差异是有意改动还是回退？有回退不发布。复用正式页面、公共壳或组件时，模块页面的版式仍以实施基线为准 |
| 宿主一致 | 是否在 CDS 的预览容器里测过（见下文）？手机是否用真实 375 宽？Windows 100%、125%、150%，浅色和深色都测过吗？控制台是否零报错？ |
| 重点优先 | 谁来这一页、第一件事做什么？首屏是否先给这件事？顺序：等我处理 → 新变化 → 进行中 → 参考资料 |
| 每样东西有根 | 需求、稿件、框架是否都挂在所属模块下，并写明负责人、状态和下一步？不放浮在页面顶部、和谁都不挨着的面板 |
| 变化可见 | 新稿、新版本、新反馈是否有「新」标记，看过之后是否消失？ |
| 动作可预期 | 每个按钮做的是不是它写的事？一页是否只有一个主动作？不可逆操作是否放在次要位置并二次确认？ |
| 一个状态一种写法 | 阶段和待办是否分开？同一件事是否只出现一次？ |

流程：

1. 出稿前，从实施基线导出「已定决定清单」，从需求列出「角色 × 任务」。
2. 每改一处，按原则把同类问题一起修掉，不只修被指出的那一处。
3. 发布前：
   - 在预览容器里自检，零报错；
   - 逐画面做基线差异表，写明有意改动还是回退；
   - 按角色和任务亲自点一遍，记下步数、卡住和看不懂的地方，每条标上原则和级别；
   - 阻断、误导、数据错这类高优先级问题清零。
4. 交付说明附走查记录和基线差异表。
5. 验收项写意图和可测量的结果，例如「页头第一行在 1024 宽下不折行」，不要把布局细节写死。写死的布局会被实现方照做，问题会带进正式页面。

### 角色与注意力

稿件是给人和智能体一起用的。标签按协作中的角色分，不按信息类型分。每页只有一个主角，其他内容围绕它展开。

**三个角色**，每个角色一个标签：

| 角色 | 谁 | 包含 | 怎么做 |
| --- | --- | --- | --- |
| 交付 | 人 + 智能体 | 原始需求、画面、说明、反馈、资料 | 讲清要什么、长什么样、为什么这样 |
| 验收 | 人（以后自动化）+ 智能体 | 各验收手段（见「验收」） | 按客观规则执行。结论由条目算出，不能手工勾 |
| 记录 | 主智能体 + 子智能体 | 版本、定稿、验收运行、反馈往来 | 发布、验收、反馈时自动写入，人不手工修改 |

- 每个验收手段都写明由谁执行：人工核对由人做，以后改为自动化；冒烟测试由自动化执行；其余由智能体执行。
- 鼠标停在标签上时，提示这个角色由谁组成。

**注意力规则**：

1. **一页只有一个主角。** 稿件页的主角是画面。打开稿件先看到画面，不是一堆文字。
2. **文字跟着画面走。** 画面旁只放当前这一屏的需求、说明、反馈和资料，每段最多三条，并随画面切换。全文放到第二层，在画面上方打开；关闭后回到刚才那一屏。
3. **按角色分区。** 同一个角色负责的东西放在一起。例如需求、画面、说明不分成三个标签，都放进「交付」。
4. **只有要动手的才占注意力。** 徽标只用来标待办，一个角色只显示一个数字。

**需求可追溯**：

- 交付里能看到原始需求：来源、交接、原文和需求方的回复。
- 每条需求条款都对应验收项。条款结论由验收项算出：没有验收项是「漏项」，有一项失败是「不通过」，全部通过是「通过」，其余是「待验证」。
- 画面旁的需求段是从验收项所在的画面反推出来的，所以每条验收项都要写明画面。

发布前，对每个标签回答三个问题：
- 打开后第一眼看到的是什么？
- 那是不是这个角色最要紧的东西？
- 首屏有多少文字和当前画面无关？

### 程序做门禁，智能体只做输入

能用程序完成的，就不交给智能体。门禁、约束、规则、版本差异都由程序判定；智能体只负责程序做不了的输入，例如设计内容、文案和取舍。不满足程序要求的输入，程序直接驳回，智能体按规则编号修改后重跑，直到通过。这样多轮输入之后，结果仍然稳定、可以复现。

- **发布门禁**：稿件包里带门禁程序，规则编号固定。例如：
  - 清单能解析；
  - 画面和验收项编号唯一、互相指得上；
  - 验收项不超过 60 条，测量项写了「检查：」；
  - 自检没通过的项都登记了负责人和理由；
  - 标题版本号一致；
  - 不含真实站点、邮箱、密钥；
  - 压缩后小于 3.8 MiB。

  门禁不通过就不发布。例外只能登记在例外文件里，并且由人确认。
- **版本差异由程序算**：任意两个版本之间只给净变化，中间加了又删的不出现；升级和回退用同一个算法。源码差异用标准的 `a/`、`b/` 文件头，能直接 `git apply`。稿件包里带上从每个旧版本到这一版的结构化差异，实现方停在哪一版，就从哪一版一步升级到最新。
- **版本登记由程序写**：每次发布后，由程序登记版本号和来源提交，并打本地 tag（`design/<稿件编号>/v<N>`）。不手工维护版本对照。
- **没有 git 也能算**：从 CDS 下载两个版本的归档后直接比较，结果和用 git 算的一样。

程序在本技能的 `scripts/design/` 里，对任何稿件目录都适用，不用复制进稿件包。发布只走两条固定命令，版本号由程序推算：

```bash
# 发布前：生成 changes/（有旧版本时），跑门禁 G-01 到 G-09；通过后打印该用的发布命令
node <技能根>/cds/scripts/design/release.mjs check --dir design/<目录> [--full <实现所在版本>]
# 发布成功后：核对来源提交和工作区一致，写 versions.json，打本地 tag
node <技能根>/cds/scripts/design/release.mjs register --dir design/<目录> --commit <来源提交> [--design <稿件编号>]
```

- 驳回时退出码为 1，逐条列出规则编号。按编号修改，修完重跑，不跳过、不手改结果。
- 首发后第一次登记要带 `--design`。已经发布过、但还没有 `versions.json` 的稿件，先用 `--version <已发布的最新版>` 补登记，再出下一版。
- 自检没通过（包括未验证）的项，登记在稿件目录的 `tools/gate-allow.json` 里，写负责人和理由。新增例外要人确认。
- CDS 发布接口按同样的 G-01 到 G-09 复核。本地门禁先驳回，省一次往返；两边规则对不上时，以 CDS 的驳回为准，并把差异补进 `gate.mjs`。
- 不能出现在包里的真实站点，用环境变量 `CDS_DESIGN_FORBIDDEN_HOSTS` 传入，不写进稿件包。
- 单独算两个版本的差异：`version-diff.mjs --dir <目录> --from v<旧> --to v<新>`。交换两个参数就是回退方向。
- **交接清单由程序生成**：`check` 同时按目标生成稿件根目录的 `交接清单.md`（`handoff.mjs`），起点是实现方的实施基线（`--baseline`，没给就取 `--full` 的第一个起点）。它是交给实现方的唯一一份清单：
  - 按目标列验收项，标出相对实施基线新增、改了、不变；
  - 写明整份应用哪个源码差异；
  - 附回复模板：实现方按验收项编号逐条回复，没提到的编号视为没有接受。
  - 目标写在 `design.json.goals`（`id`、`goal`、`doneWhen`、`items`，在别的稿件里的写 `where`）。目标引用了不存在的验收项、或没写「怎么算做到」时驳回。
  - 不要在其他文档里另写一份「交给实现方」。

### 稳定、因果、有用

页面完成以后，按下面三条再审一遍。

**标签以上一动不动**：切换标签时，页头、标题、标签、动作的位置和大小都不变。
- 所有标签用同一个上边距；页头每一行固定高度，不随内容变高变矮。
- 管整份稿件的控件（版本、大屏、「···」）每个标签都放在同一个位置。只管某一块内容的工具跟着那块内容走，例如画布工具放在画面角上，不进页头。
- 某个标签暂时用不上的控件留在原位置、设为不可用，并提示原因，不要拿掉或挪走。
- 自检：在几个标签之间切换，量各元素的位置，误差为 0。

**先讲因果，再讲进度**：结论页先回答「为什么还不能完成」。
- 逐条列原因，每条写三件事：挡住了什么、影响哪条需求和哪个画面、从哪里处理。
- 根因排第一。例如预览提交没核对上时，补证据和签收都做不了，它就是根因。
- 同一个原因造成的多处问题合成一条，例如「缺少手机实拍 → A-07 浅色、深色」。
- 最后写一句：处理完这几条，哪个动作才能做。
- 给出「需求条款 → 验收项 → 条款结论」的追溯，以及「画面 × 结果」，让人看出问题集中在哪。
- 记录按版本写因果：这一版处理了什么、之后发生了什么。新版本里的修改，在定为实施基线之前不在实现里，要写明。

**没有区分度的不放**：
- 每行都一样的列、和别的列重复的列都删掉，例如全是「已启用」的列，或和进度条重复的状态列。
- 页面上的几个数字要说清口径和彼此的关系，例如「项」是验收项，「处」是验收项 × 视口。
- 给智能体看的标识（技能名、内部编号）放进悬停提示或详情，不占人读的位置。

**只写能推出的因果**：数据推不出因果时，只把事实并列，例如「同一画面在基线的验收里 A-02 不通过」，不替读者断定是哪一条造成的。

### 信息分层

「重点优先」和「一个状态一种写法」落到卡片、页头和详情上，按下面的规则。出稿前先把一页上会出现的信息逐条归类，再决定放在哪。

卡片和列表行上的信息分八类：

| 类 | 回答什么 | 卡片上 |
| --- | --- | --- |
| 身份 | 这是哪一份（缩略图、标题） | 放。标题一行，超出省略 |
| 变化 | 上次来之后有没有变（新稿、新 V4） | 放在缩略图左上角，有才出现，看过后消失 |
| 状态 | 到哪一步、结论是什么 | 放，只放一个 |
| 时间 | 多新 | 和状态同一行 |
| 待办 | 要不要我做什么 | 不重复。由「等你处理」这类分区表达 |
| 出处 | 谁做的、第几版 | 放到列表模式和详情 |
| 关联 | 框架、评论数、标签 | 放到列表模式和详情 |
| 明细 | 为什么是这个结论（自检明细、失败规则） | 不上卡片，放进详情 |

规则：

- **卡片**：文字最多两行，第一行标题，第二行状态和时间。缩略图上不贴和状态重复的标记。
- **状态**：一种对象只有一套状态词，三四个就够，每个都要说得清怎么离开这个状态。没人能「处理完」的记录（例如作者自检）不是状态，否则会一直挂在卡片上。卡片、分组、筛选、页头都用同一套词。
- **数字**：标签和分区上只放要动手的数（等我处理的、不通过的），只用一种写法（数字徽标）。总数、版本数这类只是信息的数不放。
- **顶部**：
  - 内容前的横条越少越好，不重复上一层已经给出的信息（例如稿件页头已有版本和基线，交付区就不再写）；
  - 同一行左右空着时合并（例如画布工具和版本动作分放两行的右边，省出一整行给预览）；
  - 整句的说明收成小标记，句子放进悬停提示。
- **详情**：
  - 一条反馈或需求就是一个要求，按编号、大标题一条一条列：诉求 → 怎么算解决 → 问题 → 依据 → 往来；
  - 登记时诉求和怎么算解决必填，关闭时在复核说明旁对照「怎么算解决」。没有要求就没有约束；
  - 资料按「为什么要看」编号分组，每组写一句用途；
  - 验收先给一句结论（还差几件、差什么），再列要补的。

每一页先写下它要回答的问题，再按编号、大标题一条一条列。回答不了这个问题的内容，移到它该在的页，不在这一页重复。常见的三类页面：

| 页面类型 | 例子 | 怎么列 |
| --- | --- | --- |
| 流程类 | 做法验收、开始出稿 | 先给一句结论，再给编号的下一步：只有当前一步高亮并给主按钮，后面的写「先完成第 N 步」，已完成的打勾。还没开始的结果不要铺成「条目 × 视口」的矩阵，按状态分组 |
| 文档类 | 思路、交付说明 | 不管作者用什么标题，按意思归到固定顺序（目标 → 关键取舍 → 本版改动 → 依据 → 待定），其余小节按原顺序放在后面。顶部放目录，旧的「回顾」默认收起，开头的说明收成一行小字 |
| 对照类 | 规范、版本对比 | 先给差异，每条写「新增 / 修改」、「类别：名称」和一句说明。不出现原样 JSON 和内部编号，表头不算一条 |

改版式时，正式逻辑给出的每一句状态提示都要保留，例如「暂时无法核对当前预览提交」。它说明按钮为什么不能点，少了就是回退。发布前用改版前后的同画面对照图逐句核对。

### 导航

页头、工具栏和标签按下面的规则规划。出稿前把一页顶部的每个控件列出来，逐个决定留、缩、藏、并。

- **按用途分四类**：
  - 核心状态（例如版本）和常用动作（例如大屏、评论、单屏 / 全部）留在外面；
  - 一次性设置（例如命令行、接入 Agent）合成一个菜单；
  - 偶尔用、只有少数人用的操作（例如定稿、撤销定稿、设置评审人、框架候选）放进「···」面板。
- **同一件事只用一个控件**：
  - 缩放用一个菜单，不用「− 适应 +」三个按钮；
  - 二选一用一个切换按钮；
  - 附属信息并进主控件，例如选择框直接写「V4 · 最新 · 基线 V2」，不再另放标记。
- **面包屑只表达位置**：
  - 写法是 `产品 / 模块 / 项目 ▾ / 文件夹`，到上一级为止，当前页由页面标题表达；
  - 项目这一段就是项目切换；
  - 标签、版本、筛选是页内状态，不进面包屑；
  - 有了面包屑，页面里不再放返回按钮或第二条路径；
  - 手机上只留「‹ 上一级」。
- **工具跟着它管的东西走**：只作用于画布的控件放在画布上或画布那一行，管整份稿件的放在页头。同一组控件在不同页面换位置时，写清每种页面放在哪。
- **先问每页回答什么，再决定合并标签**：标签按角色分（见「角色与注意力」），一个角色里的页再按下面的规则合并：
  - 用同一块内容的合成一页，例如预览和对比是同一块画布的两种模式；
  - 同一读者、同一目的的合成一页，例如思路和规范都是写给实现方读的；
  - 和别的页重复的内容并过去，不在两处各放一份；
  - 合并后旧地址要照常打开。

### 验收

稿件的验收项和验收页按下面的规则设计。按规则验收会漏掉位置、对齐、遮挡、原样内容这类视觉问题，所以必须加上逐画面对照和固定的易漏清单。

**手段**：全部列出，每个写回答什么、由哪个技能执行。

| 手段 | 回答什么 | 执行技能 |
| --- | --- | --- |
| MECE 覆盖 | 该验的有没有漏、有没有重复 | `risk-matrix`、`acceptance-test-design` |
| 对照图 | 实现和稿件逐画面是否一致 | `design-replication`、`cds-skeleton-review` |
| 视觉 | 位置、对齐、遮挡、深色、视口等易漏项 | `create-visual-test-to-kb`、`issues-visual-run` |
| 历史易错 | 以前出过的问题这次有没有再犯 | `stable-smoke`、`create-visual-test-to-kb` |
| 流程 | 按角色走完关键任务，每一步对不对 | `acceptance-scenario-orchestrator`、`flow-trace` |
| 人工 | 机器判断不了的，由人按清单核对 | `acceptance-checklist`、`human-verify` |
| 冒烟 | 部署后关键页面和接口能不能用 | `smoke-test`、`stable-smoke` |
| 验收债务 | 还有哪些说了但没证明 | `acceptance-debt-loop` |

**启用**：
- 手段全部列出，但只启用这份稿件需要的。
- 没启用的上锁：写理由，能看做法和示例，不显示空白结果。
- 启用后它的条目计入验收，签收前必须完成。

**进度**：
- 每个启用的手段有总进度（完成 x/n、有问题数）和逐条状态。
- 总状态只由条目算出（未开始、进行中、完成 · 有问题、已完成），不能手工勾，避免「里面全打勾、外面没通过」。

**逐画面对照**：一个画面在一个视口和主题下一行，列是 画面 · 验收方式 · 对照图 · 实现图 · 结论；点开并排或叠加对图。

**通用视觉检查**：每个画面都查。
- V-01 位置
- V-02 对齐（≤ 1px）
- V-03 遮挡与裁切
- V-04 溢出与滚动
- V-05 原样内容（Markdown 符号、JSON、内部编号、凭据串）
- V-06 一种写法
- V-07 深色（对比度 ≥ 4.5）
- V-08 视口（手机 375、Windows 125% 和 150%）
- V-09 状态（空、加载、出错、过期、无权限）
- V-10 数据规模

**证据规则**（给 AI 验收时尤其要守）：
1. 同视口、同主题、同状态、同数据规模才算证据；截图要在干净的环境里取，不用长时间运行过的浏览器。
2. 测量项写数值，对图项写在哪个区域看到了什么；只写「一致」按缺证据算。
3. 先列出查过的区块（页头、标签、主体、浮层、底部），再判通过。
4. 缺实拍、缺证据的不能签收。
5. 叠加出现的差异逐个解释：有意还是问题。

**历史易错**：缺陷、工单、线上吐槽里出现过的问题（例如翻页按钮不齐、按钮不用公共组件），同类合成一条，写来源和次数、怎么查、适用画面。出现过就永久检查，不因为通过了就删掉。

**每个手段都要写清楚**：怎么做（3 到 5 步）、看示例（用虚构数据从头做一遍）、通过标准、谁做、什么时候做。实现方第一次做时照着走。

**注意**：CDS 限制一份稿件最多 60 条验收项。超过时合并同一页面、同一目的的条目，不要删掉检查内容。

### CDS 预览容器

画布用 `sandbox="allow-scripts"` 的 iframe 打开原型，响应头 CSP 是 `sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; base-uri 'none'; form-action 'none'; frame-ancestors 'self'`。CDS 还会在 `<head>` 后注入桥接脚本，负责主题、布局框、滚动和入口定位。

- 原型里嵌套的页面不能用 `data:` 或 `blob:` 地址，会被 CSP 拦下（没有 `frame-src`），每个嵌套页面在控制台报一条错，画面空白。改用 `srcdoc`：同样的 CSP 下可以加载、可以运行脚本。原型 HTML 里的 meta CSP 不能放宽响应头的策略。
- 原型是不透明源，访问 `localStorage`、`sessionStorage` 会抛 `SecurityError`。直接运行正式 Web 代码时，先换成内存版存储。
- 不能发起网络请求，数据和图片都要内嵌。图片可以用 `data:`。
- 入口定位：桥接脚本点完 `entryActions` 后，等 `entryReadySelector` 约 1 秒。就绪标志要在首屏渲染后尽快出现。
- 本机自检要还原这个容器：按上面的响应头提供原型，注入 `cds/src/services/design-prototype.ts` 里的桥接脚本，放进 `sandbox="allow-scripts"` 的 iframe，通过 DevTools 协议收集所有框架的控制台和 CSP 违规。用 `file://` 打开原型测不出这些问题。
- 无界面 Chrome 的窗口最窄 500 px，`--window-size=375` 实际按 500 宽排版。手机画面要用 DevTools 的 `Emulation.setDeviceMetricsOverride` 设置 375×812。

## 提交与交付

- `design.json.project` 等于绑定的项目 ID。保留适用的固定框架和画面编号，包含 `design.json`、`思路.md` 与清单声明的单文件 HTML。标准新建由服务器分配 ID，清单和请求均省略稿件 ID。续版可沿用清单中的同稿 ID。
- 在工作区仅提交获授权的稿件子目录。若没有 Git 作者配置，可为本次提交指定智能体自己的作者身份。CDS 根据获授权的身份记录发布者。使用 `cdscli design publish --private --dir <稿件目录>`，按新稿或续版附上相应参数。提交保留在本地，稿件及归档摘要存入已获授权的 CDS 项目。
- MCP 通过 `cds_design_publish` 传 `sourceMode: "private"`、`zipPath`、本地 `sourceCommit`、仓库相对 `sourcePath`、`requestId` 和意图字段。用本地提交导出稿件目录的 ZIP，放在项目工作区内，避开 `.cds` 和 `.git`，大小上限 4 MiB。HTTP 使用同一项目的 `/design/packages`，内容为 ZIP，其余字段通过查询参数传递。
- 已获授权并已存在于项目 Git 的材料可以沿用 Git 核验方式。CDS 分别显示 Git 核验证据和私有归档。
- 在 `note` 记录原版、改动画面、原因和待核验项。发布后按回执的 `designId` 与 `version` 回读，核对项目、源提交和归档摘要。响应不确定时以原 `requestId`、来源、意图和稿件内容重试。设计接入按 ZIP 内的文件内容识别重试。接收者从同一项目回读固定的新旧版，定位差异后复拍受影响画面。缺实拍仍标待核验。
- 私有发布的版本摘要 `sha256` 来自上传 ZIP 的原始字节。清单同时保留每个文件的 `sha256` 和原型的 `prototypeSha256`，用于分别核对交付文件和原型。


## 完整交付资料

- 原型、清单、设计思路、交付说明、开发与设计文档、可重建源码、框架草案、截图和自检可一起提交。声明过的资料用包内相对路径，可用中文。版本会保留原 ZIP，以及每份文件的路径、类型、大小、摘要和可识别的文档章节。未知类型的附件也可按版本下载。附件内容是工作材料。
- `design.json` 可用 `docs` 列出设计、开发和决策文档，`source` 指向用于重建的源码，`frameworkDraft` 指向框架草案，`prototypeVersion`、`date`、`notes` 补充作者交付说明。CDS 自己记录稿件版本和发布时间。
- 画面共用入口时，可用 `entryActions` 依次选择原型内可见控件，用 `entryReadySelector` 声明原型状态就绪标志。它们随版保留。框架自动测量切换状态后等待对应的就绪标志，缺少状态证据时记录为待验证。`impl` 和 `readySelector` 用于打开与验收对应的实现页。画面与声明的行为不符时，先查看该版材料并提反馈。
- `cds_design_read` 的 `delivery` 读取固定版资料与验收缺项，用 `{view:"file",id,version,path}` 原文分段回读。接着传响应的 `nextOffset`，已到结尾时它为空。可以从稿件的「交付」下载原包或单个文件。继续使用历史版本的来源记录、原型、思路及验收数据。
- 作者的原型自检负责记录原型状态。实现路径、实现分支的验收证据及真人签收继续由各自的入口独立记录。共用入口不明确、缺实拍、缺实现地址或缺探针时，在反馈中说明要补的内容和复核方法。

## 双向反馈

1. 实现方先读 `intake`、固定版 `delivery` 和已有 `feedback`。用 `cds_design_feedback` 的 `feedback.create` 记录复用建议、实施做法、需求缺漏、落地约束或验收建议。提供稿件、版本、分类、标题、理由、改动依据和可核对证据。对整份稿件或特定画面都可以登记。
2. 设计方读同一线程，调用 `feedback.reply` 回复。需要改稿时按原稿 ID 和最新基线发布，再在回复的 `revision` 引用自己发布的实际版号。只需解释、确认约束或说明方案取舍时，可以直接回复。
3. 原反馈者回读新版和同一线程，按证据验证。用 `feedback.resolve` 的 `close` 或 `reopen` 加说明保留复核结果。项目管理者也可处理。发布、反馈、实际做法验收和人类签收各自按项目权限执行。重试沿用原请求编号。

HTTP 与 MCP 共用项目级设计接口。反馈写入走 `POST /api/projects/:projectId/design/feedback`。固定版本资料在工作区回读中，原文可以用 `GET /api/projects/:projectId/design/artifacts/:artifactId?view=text` 分段读取。
