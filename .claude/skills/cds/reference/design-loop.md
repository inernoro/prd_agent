# 设计闭环（`/cds 改 xx 模块的设计`）

> 入口是精准技能 `cds-design`（`/cds-design`），它按本文执行；`/cds` 里说的设计相关的话也会交给它。

用户只说一句话，例如「/cds 修复工程规划的看板，把逾期债务排到最前」。属于菜单「设计」。剩下的由本流程完成。

**交付物是 CDS 上的稿件地址**：用户说设计（提出设计、帮我设计、改设计），这一轮的结果必须是发布到 CDS 的私有稿件，并把稿件地址给用户（`release.mjs register` 会打印）。
- 没有设计发布授权时，第一步只能是申请授权（见「一、找到稿件」第 1 步），等用户在 CDS 批准。
- 稿件发布之前不改正式代码；Artifact、本地 HTML 这些原型只是出稿过程，不能代替稿件。
- 用户同时要求实现时，先发布稿件，再按本稿的 `交接清单.md` 实现（第六节）。

**交接在 CDS 完成。** 从原需求、评论和交接清单读取背景。将实施反馈和验收结果写回原线程。用户说明任务、确认产品取舍，必要时完成独立复核与签收。

## 一、找到稿件

1. 自检授权：`cdscli setup-check --host <CDS 地址> --project <项目 ID> --design-access publish`。缺少权限时按 [CDS 设计接入](design-intake.md) 发起申请，等系统所有者批准。不复制、不打印凭据。
2. 读接入清单：MCP `cds_design_read {view:"intake"}`，或 `cdscli design intake`。每份稿件有 `designKey`（`<模块>/<稿件>`）、最新版本、来源目录和能否续版。
3. 按用户说的模块匹配 `designKey` 或标题：
   - 匹配到一份：同稿续版，基于最新版本修改。
   - 匹配到多份：列出候选，问一次。
   - 没有匹配：新建稿件，`cdscli design scaffold --framework <框架编号> --dir design/<目录> --title "<标题>"`，`designKey` 用 `<模块>/<稿件>`。
4. 本地没有稿件目录时，从 CDS 下载最新版归档，解到 `design/<目录>`，再提交一次作为起点。

## 二、从 CDS 读上下文

动笔前读完下面几项，用户没说的不靠猜：

| 读什么 | 命令 | 用来做什么 |
| --- | --- | --- |
| 未关闭的评论 | `cdscli design comments <稿件编号> --open` | 本版要回应的意见，发布时用 `--resolves` 关闭 |
| 实施反馈 | MCP `cds_design_read {view:"feedback", id}` 或 `cdscli --workspace-credential design feedback <稿件>` | 读原稿所有版本的业务变化，包括已结案的反馈和设计复验记录 |
| 原型交接检查 | `cdscli design handoff <稿件编号> --version <版号>` | 当前版本是否可以开始实施、失败在哪一步 |
| 验收结果 | `cdscli design result <稿件编号>` | 哪些验收项没过、挡住了什么 |
| 实施基线和已实现版本 | MCP `cds_design_read {view:"design", id}` | 决定 `changes/` 要附完整源码差异的起点 |
| 交付资料 | MCP `cds_design_read {view:"delivery", id}` | 上一版的思路、交付说明和验收缺项 |

## 三、出稿

按 [出稿与发布前自查](design-intake.md#出稿与发布前自查) 修改原型、思路、交付说明和验收项，并按角色走查。设计内容、文案和取舍由智能体负责，其余交给程序。

续版前把「交付 → 反馈」中已确认的实施行为作为设计依据。原型和验收项一起沿用，交付说明引用原反馈编号并写明处理结果。新的方案与已确认行为有冲突时，先在原线程提出具体差异并澄清。

## 四、发布（程序门禁）

```bash
node <技能根>/cds/scripts/design/release.mjs check --dir design/<目录> --full <实现所在版本>
```

1. 被驳回就按规则编号修改，再重跑，直到通过。不手改 `changes/`、`versions.json` 和 `交接清单.md`（按目标生成，给实现方的唯一一份清单）。
2. 提交稿件目录，然后用 `check` 打印的命令私有发布。续版带上 `--resolves "<评论编号>=如何处理"`。
3. 回读：`cdscli design list`，核对版本号、来源提交和文件摘要。
4. 登记：`release.mjs register --dir design/<目录> --commit <来源提交>`。首发后第一次登记带 `--design <稿件编号>`。
5. 读取固定版本的交接检查。在同一稿件修正失败的交互。环境暂不可用时重试本版。需要执行场景时按[交接规则](design-intake.md#交接检查)补充。
6. 回复实施反馈：MCP `cds_design_feedback {type:"feedback.reply", revision:<新版本>}`，正文指向 `交接清单.md`，请实现方按验收项编号逐条回复。实现方从 CDS 读到回复，不用用户转告。

## 五、告诉用户

最多五行：

- 稿件编号和新版本；
- 本版改了什么，写 2 到 3 条；
- 从实施基线到新版的净变化，引用 `changes/v<基线>-v<新版>/changes.md` 的计数；
- 门禁结果、原型自检摘要和程序交接回执；
- 需要人做的事，例如独立复核或签收。接入清单允许实施协作时，智能体可用当前项目凭据确认本轮目标。

接入清单回显 `permissions.implementation` 时，智能体可沿用项目凭据处理基线与实施目标。需要成员签收时，把原稿、版本和运行链接写在同一线程。

## 六、实现方：按交接清单实现

用户说「/cds-build 帮我实现 DSN-xxx」或「/cds 帮我实现 DSN-xxx」时，先加载 [`cds-build`](../../cds-build/SKILL.md) 并回读获准的实施目标。稿件根目录的 `交接清单.md` 由程序按目标生成，作为实施依据。

1. **读稿件**。`cds_design_read`（view=delivery）读取固定实施版本，打开 `交接清单.md`、`设计文档/目标与验收.md`。
2. **先回复，再动手**：在实施反馈线程里按清单第五节的模板，逐条回复验收项编号（接受 / 怎么做 / 何时）。没提到的编号视为没有接受；做不到的写明原因。
3. **核对实施基线**。回读固定版的交接检查、实施基线和锁定目标。接入清单允许实施协作时，沿用本项目凭据确认交办的版本和绑定真实画面。其他项目由有权评审人确认。
4. **整份应用源码差异**：先用 `git apply --check` 对实际实现的提交做程序预检。兼容时应用发布差异。哪个文件不能直接用，在线程里逐个写文件和理由。
5. **绑定并取证**。实现方核对每个适用画面的实现地址和就绪选择器，补齐需要的绑定。用 `cdscli --workspace-credential design accept <稿件> --version <目标版> --pr <PR号> --commit <已部署提交> --start-only` 创建运行。验收主用 CDS 构建时用 `--installed` 选择来源。稿件清单中的预计地址只用于定位，运行负责核对已部署的提交。
   对照图两边用稿件指定的同一份演示数据渲染。采用程序取证的稿件用 `cdscli --workspace-credential design capture <稿件> --run <运行> --screen <画面> --slot <视口和主题>` 逐项取证。每处程序证据带三个字段：
   - `cell.dataset`：等于演示数据的摘要；
   - `cell.commit`：等于运行的提交；
   - `cell.capturedBy`：`cds`。
   历史稿按其版本的取证约定回填实拍。用 `design result <稿件> --run <运行>` 回读实际提交、画面和视口，并在「交付 → 对比」确认实拍可打开。
6. **跑验收**：`/cds 测试 跑 DSN-xxx 的验收`，逐项写结论和依据。缺部署、画面或证据时在原反馈写明对应项、处理人和下一步。
7. **请设计方复核**。如实施调整了业务行为，在原稿固定版的「交付 → 反馈」按画面或验收项编号写明原约定、实际做法、原因、应保留的行为及待澄清点。附实现提交和运行编号，设计方按同一条件独立复验。
