# 预览包判据细则与反面案例

本文件是 `SKILL.md` 里六件套判据的展开。写预览包时不必通读，自检卡壳时按小节查。

---

## 通用：什么叫「决策者能自己核」

判据的读者是**不看代码的人**。一条判据合格的充要条件：他照着字面做，能在不问作者的情况下得出「过」或「不过」。

| 写法 | 判定 | 为什么 |
|---|---|---|
| 「连问三句，第三句说『按你第一句说的那个来』，看它接不接得住」 | 合格 | 动作明确，结果肉眼可判 |
| 「多轮上下文正确传递」 | 不合格 | 他不知道怎么看「传递」这件事 |
| 「工具调用链路健壮」 | 不合格 | 没有动作，没有判定线 |
| 「故意写一句会让它失败的要求，看是否红态 + 写清原因 + 会话还能继续」 | 合格 | 三个可见特征，缺一即不过 |

**反面案例**：本仓库出过「验收步骤截图显示『正在渲染，已等待 36 秒』，文案却写『渲染完成』，结论判为通过」。判据当时写的是「PPT 渲染完成」——没写清「什么算完成」，于是超时截图也能塞进去。改法是把判据写成「幻灯片标题与正文在预览区可读」。

## 1. 操作页面演示

### 剧本怎么设计

一条剧本要覆盖**一个完整的用户目的**，不是把所有功能演一遍。三段式最稳：

1. 用户提出需求 → 系统干活（含等待态）→ 产物出现
2. 用户基于产物追加一个动作 → 产物被保存/流转
3. 用户换个场景回来使用之前的产物 → 证明闭环成立

第三段是关键。只演到「产物出现」的剧本，看不出这东西有没有留下价值。

### 等待态的最低标准

- 有阶段名，且阶段名会推进（排队 → 执行 → 写入）
- 有进度条或等价的形变
- 阶段名用产物语言，不用系统语言：写「模型出图」不写「调用中」

### 常见不合格形态

- 用截图拼贴冒充演示。截图是过去，演示是将来。
- 只做了一屏静态布局，点任何东西都没反应。
- 演示里的等待态是瞬间完成的，看不出真实体验里要等多久。
- 演示只有成功路径，看不到失败长什么样。

## 2. 架构图

### 三色是硬要求

新增、复用、不碰。少任何一色，图就失去了它最重要的功能——**证明这次改动很小**。

「不碰」框的写法：把要避开的部件画出来，用虚线红框标掉，旁边列出具体是哪几样。画出来才是承诺。

### 必须能回答的四个问题

1. 新增了几个对外容器？（答案是零最好；不是零就要按多容器拓扑规则逐个标注职责与出口）
2. 新增部件一共几个？（能一眼数出来）
3. 共享的基础设施有哪些，谁在共享？（共享库、共享缓存、共享密钥）
4. 写共享存储的数据怎么区分来源？（作用域标记）

第四问尤其容易漏。本仓库出过「共享库里的任务队列没有部署作用域，旧构建的执行器抢走新分支的任务，同一个错误反复复现」。

## 3. 数据流转与鉴权

### 鉴权表的三列不能省

**谁调谁 / 拿什么凭据 / 为什么不是新东西**。

第三列是重点。它逼作者回答「这次有没有偷偷发明一套新认证」。如果某一跳答不出「复用了什么」，那就是新增了认证面，必须显式提出来让人拍板。

### 失败表的四行起步

至少覆盖：上游服务失败 / 某个工具失败 / 用户中途离开 / 循环停不下来。

每行三列：**哪里坏了 / 用户看到什么 / 数据会不会烂在半路**。

第三列答「会」的，说明设计有洞，得先补设计再出预览包。

### 执行节点必须标明调用方式

「进程内直调」和「跨容器 HTTP」在图上必须看得出区别。这一条直接决定延迟、认证复杂度和排障难度——也往往是「上一版为什么难用」的根因所在。

## 4. 角色业务流

### 终点判定

| 终点写法 | 判定 |
|---|---|
| 「图显示在对话里」 | 合格 |
| 「链接能打开，内容正确」 | 合格 |
| 「任务已提交」 | 不合格，断头 |
| 「系统返回成功」 | 不合格，断头 |
| 「进入审核流程」 | 不合格，除非该角色的目的就是提交 |

### 角色选取

三类起步，且必须包含**最不懂技术的那一类**。只画开发和管理员的流程，等于默认用户会看文档——这是产品失败的常见起点。

如果某个角色的链路只有两步，说明要么这个角色不该单列，要么这个功能对他没价值，两种都得说清。

## 5. 验收方式

### 「不算数的证据」清单是必填项

固定五条起步，按本次特点增补：

- 接口返回成功、测试全绿（必要条件，不是验收本身）
- 截图里还在加载，文案却写已完成（断头验收）
- 旧版本截图充数
- 「我通读了两遍，逻辑没问题」
- 只测新建的数据，不测存量数据的兼容路径

### 证据形式

- 从真实入口点进去截的图，地址栏可见
- 双主题各一张
- 部署版本标记入镜，证明是最新那一版
- 生成类功能必须拍到产物本身

## 6. 范围契约

### 熔断线要机械可判

| 写法 | 判定 |
|---|---|
| 「连续八个提交没有新增可用功能」 | 合格，数得出来 |
| 「改动行数超过第一轮基线两倍」 | 合格，量得出来 |
| 「工具数量超过三把」 | 合格 |
| 「范围失控时停下」 | 不合格，没有判定线 |
| 「感觉做偏了就找人」 | 不合格 |

### 「本期不做」的写法

每条要写成**具体功能**，不是抽象类别。写「联网搜索、抓网页、上传文件解析」，不写「高级能力」。

抽象类别的问题：实现时总能论证「我做的这个不算高级能力」，契约就废了。

---

## 7. 决策点

每个决策点的结构固定：**问题 / 推荐选项（含理由）/ 备选项（含代价）**。

没有推荐选项的决策点等于把问题原样退回，是偷懒。作者调研过现状，本来就该有判断。

代价要写具体：写「会让第一版拖长一到两天」，不写「有一定成本」。

---

## 8. 成本与退出

### 阶段划分的自检

每个阶段问一句：**在这里停的话，用户手上有什么？**

答不出来的阶段划分是假的——它只是把一件事切成了几段代码，中间任何一处停下都是半成品。合格的划分里，每个阶段结束都能独立上线。

### 退出方式

具体到动作：关哪条开关、要不要迁数据、影响谁。

「可以回滚」不算答案，所有代码都可以回滚。要答的是**回滚的代价**。
