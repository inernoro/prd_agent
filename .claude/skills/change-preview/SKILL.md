# 重大改动方案预览（Change Preview）

> **版本**：v1.0.0 | **状态**：已落地 | **触发**：`/change-preview`、"效果提前"、"方案预览"、"我能得到什么"、"先看效果"

给**重大改动**做动手前的效果预览。产出物是一个自包含 HTML，决策者点开就能看到将来的操作页面、总体架构、数据怎么流、每个角色怎么用、凭什么算验收通过、以及这次的范围红线在哪。

## 为什么需要它

纯文字方案有三个治不好的毛病，每一个都在本仓库真实付出过代价：

| 毛病 | 症状 | 六件套里的解药 |
|---|---|---|
| 决策者看不见 | 「大概是个聊天页」批准了，做出来完全不是想的那样 | 操作页面演示（可点击） |
| 边界说不清 | 做着做着范围膨胀，两个月后交出一坨 | 范围契约 + 熔断线 |
| 验收靠嘴 | 交付时一句「我通读自审过」，用户一操作就崩 | 验收方式（每条判据用户能自己核） |

**判断口诀**：这次改动如果做砸了，代价是「返工几小时」还是「返工几周 + 用户信任」？后者就该先出预览包。

## 什么时候用

**必须用**：新增一个用户可见的一级入口 / 新增或替换一个 Agent / 跨三个以上模块的改造 / 预计工期三天以上 / 上一次同类改动交付得不好。

**不要用**：改文案、修样式、单点缺陷、纯文档、已经有明确设计文档且只是照着实现的任务。给小改动出预览包本身就是过度开发。

---

## 交付形态

**两份东西，缺一不可**：

1. **可交互 HTML** —— 放 `assets/prototypes/{topic}-preview.html`。单文件、零外链、双主题、不含 emoji。这份是给人**看**的。
2. **设计文档** —— 放 `doc/design.{appname}.{topic}.md`，遵守文档命名与导读三行规则。这份是给人**改**的，也是后续实现的依据。

HTML 负责「看见」，文档负责「留存与追溯」。只给文档等于没解决「决策者看不见」；只给 HTML 等于没留下可维护的真相源。

## 六件套（必出，缺一即不合格）

### 1. 操作页面演示（Demo Visual）

把决策者将来真正会看到的那一屏做出来，**可点击、有动效、能走完一遍完整流程**。

- 要有真实的应用外壳：侧边导航、页头、输入区，让人认得出这是自家产品。
- 要有一个**可播放的剧本**：点一下按钮，从提问到拿到产物完整演一遍，包括中间的等待态。
- 等待态必须在动（阶段名 + 进度），不能是一个转圈图标——这直接对应「禁止空白等待」。
- 用配色块、渐变、文字占位模拟图片和产物，**不外链任何图片**。

**判据**：静态线框图、截图拼贴、纯文字描述界面 —— 一律不合格。

### 2. 架构图

看总体设计有没有违规。三样东西缺一不可：**名字分清表、三色图、写与不写的分界线**。

**2.1 先用一张表把名字分清。** 图之前必须有一张表，逐个列出相关的名字：它到底是什么、跑在哪、有没有对外域名、本次动不动它。尤其要分清三类经常被混着讲的东西：

- **部件**（一个容器 / 一个服务）与**功能**（用某个部件去做某件事）。历史事故：决策者把「某个功能不好用」听成「那个部件不好用」，于是以为要重造一个部件——其实要换的只是部署姿势。
- **业务主体**与**它依赖的基础设施**（网关、运行时、队列）。
- **部署平台**与**跑在上面的东西**。部署平台不是并列部件，它是「在哪跑」。

**2.2 三色图。** 标清**本次新增 / 复用现有 / 明确不碰**，三种底色区分。「明确不碰」的部分要画出来并用虚线框标掉——画出来才是承诺，不画等于没说。标出容器边界：新增了几个对外容器？答案最好是零。

**2.3 写与不写的分界线（双栏）。** 左栏「别人写好的，直接用，一行不碰」，右栏「我们只写这几样」，右栏末尾必须有一条**明令禁止自造**的红线。这一栏是防止方案在实现期悄悄退化成「顺手自己写一个」的唯一硬保险。

判断口诀：**能用现成的就绝不自己写，我们只写把现成件粘起来的适配。** 如果方案里出现「我们实现一个 X 循环 / X 框架 / X 协议」，先问一句：这个 X 有没有成熟的现成实现？有就必须用它，把理由写进取舍。

**判据**：没有名字分清表 → 不合格。图上分不出新增与复用 → 不合格。没有「明确不碰」的框 → 不合格。没有「写与不写的分界线」→ 不合格。

### 3. 数据流转与鉴权图

看数据从哪来、经过谁、每一跳拿什么凭据。

- **每个鉴权点单独标号**，并配一张表逐个说清：谁调谁、拿什么凭据、为什么不是新东西。
- 标出**执行节点**：这一步在哪个进程/容器里跑，是网络调用还是进程内直调。
- 必须有**失败与降级**表：哪里坏了、用户看到什么、数据会不会烂在半路。

**判据**：只画了成功路径 → 不合格。鉴权是一句「走现有认证」而没逐跳说清 → 不合格。

### 4. 角色业务流

防断头应用。每个角色一条泳道，从进入到拿到东西。

- **每条链路的终点必须是「这个人手里拿到了产物」**，不能停在「系统提交成功」「任务已入队」。
- 终点格子要显式高亮，并配一行「终点检查」，写明什么情况不算到达终点。
- 至少覆盖三类角色：不懂技术的使用者、业务侧（产品/运营）、管理员或开发。

**判据**：任一条链路终点不是产物 → 不合格。只画了一个角色 → 不合格。

### 5. 验收方式

防自说自话自嗨。一张判据表，每条写清**要证明什么、怎么亲自核、谁来核、什么算过**。

- 判据必须是**决策者自己能核的**，不需要看代码、不需要问作者。
- 必须显式列出「**不算数的证据**」：接口返回成功、测试全绿、通读自审、旧截图、进度条截图配「已完成」文案。
- 生成类功能必须有一条判据是「产物真的显示出来了」，并注明停在进度条上不算。

**判据**：出现任何一条只有作者能核的判据 → 不合格。没有「不算数的证据」清单 → 不合格。

### 6. 范围契约

防止做成一坨。三段式：

- **本期做这些**：可数的清单，能一眼数出来有几件。
- **本期不做**：想做也不做的清单，写明「全进债务台账」。写在这里就是承诺不偷偷做，也不假装有。
- **熔断线**：命中任意一条立刻停下来找人。至少覆盖——连续 N 个提交无功能净增、清单外的东西被接进来、碰到了明确不碰的部分、改动量超基线倍数、同一份计划被反复重写。

**判据**：没有「本期不做」→ 不合格。没有熔断线，或熔断线不可机械判定 → 不合格。

## 三个附件（强烈建议，重大改动必出）

### 7. 决策点清单

把需要人拍板的岔路口列出来，**每个都给默认选项并标明推荐**。写清选另一个的代价。

决策者什么都不说就按默认走 —— 这样预览包既是征询也是提案，不会卡在「等你回复」上空转。

### 8. 成本与退出

- 分阶段，**每个阶段自己就能验收、自己就能停**，并写明「在这里停的话，你手上有什么」。
- 退出方式要具体到「关哪条开关、要不要迁数据、回滚影响谁」。
- 给规模量级（触及几个文件），并说明「超出这个量级就是走偏了」。

### 9. 一页结论（放最前面）

预览包的第一屏必须直接答「**你能得到什么**」，以及「**首版明确不给你什么**」。

后者尤其重要：把不做的事提前说出来，比事后被发现少了功能可信得多。

## 准入校验（拒收判据）

产出后逐条自检，任一命中就返工，不许交付：

- [ ] 操作页面演示是死图或纯文字，不能点、不能播
- [ ] 架构图前没有「名字分清」表，部件与功能、业务主体与基础设施混着讲
- [ ] 架构图分不出「新增 / 复用 / 不碰」三色
- [ ] 没有「写与不写的分界线」，看不出哪些是现成的、哪些是自己写的
- [ ] 方案里出现自造轮子（自研循环 / 框架 / 协议），且没论证过现成实现为什么不能用
- [ ] 数据流图只有成功路径，没有失败与降级
- [ ] 鉴权只写了一句「沿用现有认证」，没有逐跳说清
- [ ] 任一角色链路的终点不是「拿到产物」
- [ ] 验收判据里有决策者自己核不了的条目
- [ ] 没有列「不算数的证据」
- [ ] 没有「本期不做」清单
- [ ] 熔断线缺失或无法机械判定
- [ ] 决策点没有默认选项（等于把决策原样退回给用户）
- [ ] 页面出现 emoji 字符
- [ ] 页面引用了外部资源（图片、字体、脚本），断网就残
- [ ] 只做了黑夜或只做了白天一套皮肤

## 工作流程

1. **判断该不该出**：对照「什么时候用」。小改动直接走 `plan-first`，不要杀鸡用牛刀。
2. **先摸真实现状**：动笔前把仓库里**已有的砖**找出来（现成的队列、事件流、运行时、工具注册、权限模型、网关兼容入口）。预览包的说服力全在「新增的少、复用的多」，摸不清现状就只能画空中楼阁，还容易把已经有的东西再造一遍。这一步花的时间通常比写页面还多，别省。
3. **写 HTML**：从 `templates/preview-shell.html` 起手——它是**成品级模板**，主题系统、九个章节、图表元件、以及可复用的演示引擎（打字机、工具卡、阶段推进、产物出现、失败态）全部就位，打开就能渲染。只需替换大括号占位、按本次改动改 S1 的剧本数组。
4. **自检**：过一遍上面的拒收判据；再用「决策者视角」通读一遍——他读完能不能不追问就拍板。
5. **交付**：把 HTML 发给决策者当场看，同时落一份设计文档并同步文档索引。等确认后再动手实现。

## 与其他规则和技能的关系

- `plan-first`：小改动的轻量版。本技能是它在重大改动上的重型版本 —— 同样是「先方案后执行」，但产出物从一段文字升级成可看可点的预览包。
- `risk-matrix`：预览包答「能得到什么」，风险矩阵答「可能失去什么」。重大改动两个都出，顺序是先预览后风险。
- `scope-check`：范围契约里的「本期做这些」就是它的 owned 文件集基线，实现过程中拿它来卡越界。
- `create-visual-test-to-kb`：验收方式一节写的是**将来怎么验**，真到验收时由它执行并归档留证。
- `living-status-board`：预览包获批后，范围契约与阶段划分直接转成状态看板的阶段行。
- 相关规则：`closed-loop-acceptance`（产物可见才算完成）、`real-visual-acceptance`（双主题真视觉验收）、`expectation-management`（预期可控）、`blocked-state-circuit-breaker`（熔断线的出处）、`predicate-and-wiring-discipline`（验收判据要机械可核）。
