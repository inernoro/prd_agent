# 官方技能同步、发布与验证

仅在维护 MAP 平台仓库、用户要求“作为官方”上架或更新时阅读。普通下载和个人上传不需要这套仓库流程。发布权限沿用本次任务；本参考不授权新建 PR、合并、正式发布或修改发布策略。

## 1. 找到真正的同步入口

在目标仓库验证这些入口真实存在，再操作；没有它们时转交平台维护者，不在普通项目里创建同名文件。

| 事实源 | 用途 |
|---|---|
| `.claude/skills/<key>/` | 技能正文与随包参考文件的唯一源码 |
| `.agents/skills/<key>` | 宿主入口；先检查是否链接到同一源码，避免维护副本 |
| `scripts/bundle-official-skills.mjs` | 官方 INCLUDE、中文展示名/简介、标签与目录生成 |
| `scripts/skill-bundles.json` | 角色、硬依赖和角色套装；加角色不等于加入 starter 套装 |
| `prd-api/src/PrdAgent.Api/OfficialSkills/official-skills.generated.json` | API 内嵌资源，必须按合并后的源码重新生成并提交 |

API 的 Docker 构建上下文是 `prd-api/`，不会直接读取仓库根技能目录。只修改 `SKILL.md`、复制 ZIP 或 push 源码，都不会自动改变已运行的官方市场。

运行时由 `OfficialMarketplaceSkillInjector` 虚拟注入 `official-<key>`，由 `OfficialSkillsController` 动态生成 ZIP。官方路径不走个人上传、不新增市场数据库记录，也不维护第二份 C# 技能正文。`findmapskills` 的版本只在 frontmatter 更新一次；生成脚本兼容顶层 `version` 与 `metadata.version`。

## 2. 准备源码并同步主干

1. 核对 Git 根、分支、工作区和当前默认分支。记录已有改动的路径/哈希；用户的试验文件、截图、凭据、个人心得不进入通用技能包。
2. 首次上架登记 INCLUDE、中文展示、标签和角色；更新已有技能沿用其注册。新版本、正文与参考文件保持一致；README 若已存在也同步其操作说明，不额外创建无用途的副本。
3. 需要集成主干时沿用仓库冲突流程和已有授权。官方生成 JSON 冲突应在源技能与配置合并后重生成，不能机械取 ours/theirs。目录总数使用当前主干事实，不写死本次试用时的数量。
4. 生成前先确认目录、脚本本身没有未处理的他人改动。生成后审查本次目标条目和无关条目差异，保留不属于本任务的变化。

从仓库根执行：

```bash
node scripts/bundle-official-skills.mjs
node scripts/test-official-skill-bundles.mjs
python3 scripts/doc-readability-check.py --ratchet
git diff --check
```

现有分发测试会再次运行生成器并改写 `generatedAt`。只有时间戳变化不代表技能更新，也不能因为忽略时间戳就忽略内容差异。提交前复核暂存范围；已有脏文件不顺手纳入提交。参考文件必须进入 `entry.files`，正文未截断，依赖完整，角色可发现。

## 3. 分清三个交付状态

| 状态 | 实际完成什么 | 尚不能声称什么 |
|---|---|---|
| 源码与生成目录已提交 | 官方包已进入仓库，具备分发输入 | 运行中的市场已更新 |
| 已合并 | 主干包含该版本，合并提交有自己的 SHA | 正式 API 已发布 |
| 指定实例已发布并验证 | 实际 API、市场版本及 ZIP 内容相符 | 未执行的 UI、真实设备或技能效果评测已通过 |

提交推送后按仓库门禁查对应 SHA 的 CI、评审和部署；是否创建 PR、合并或正式发布取决于当前授权。head/base 改变后保留旧证据身份，按影响补验证；同树或同输入的历史证据只有证明完整输入一致时才能限范围复用，不能把当前未完成的检查记为成功。

明确获准正式发布时，使用仓库现有发布技能与真实环境目标。核对项目/仓库身份、完整提交、生产基线继承、同提交 CI、脚本正文指纹及回退版本。现有兼容目标保持其已审查策略；不为小技能更新临时换部署模式、热改服务器或直接重启容器。

预览入口从权威 `preview-url` 查询，正式入口从发布目标获取，不能靠旧机器人评论、控制台域名或分支名推算。发布后回读任务终态与实际运行 SHA，并验证公网 HTML、其真实入口资源、API 健康及本次相关服务；“容器 running”不能替代这些证据。

## 4. 在实际实例验证发现与取包

把本次的实例、完整提交、技能 key 与预期版本写入轻量回执，再执行：

1. 匿名搜索 `GET /api/open/marketplace/skills?keyword=<key>&limit=200`；先判断 HTTP 与 `success`。精确核对 `id == official-<key>`、`ownerUserId == official`、预期 `version`、角色与标签。
2. 使用该响应的 `zipUrl`，或详情响应的 `data.item.zipUrl` 下载。不需要个人 Key，也不必先 fork；保留请求与最终重定向地址、状态、类型和文件。
3. 实际打开 ZIP，确认技能目录、`SKILL.md`、版本、参考文件和依赖齐全，逐文件与发布提交的预期内容比较。用 `git show <发布SHA>:<路径>` 或干净的该提交副本，不能拿脏工作区当已发布源码。
4. `findmapskills` 单包下载会将地址占位符替换为该实例地址；按控制器的确定性替换得到预期内容后比较。没有这项转换的技能直接逐字节比较。ZIP 容器时间戳可能改变整包哈希，文件内容才是版本一致性的依据；整包哈希仍保留在回执中。
5. 结论分别写明：仓库提交、合并、发布任务、实际运行版本、公开搜索、真实取包与内容比对。接口验证不能写成登录态卡片交互或技能使用效果已验收。需要 UI 验证时走真实登录，不绕过 SSO。

## 5. 最小输出与续接

交付写清技能 key/版本、目标实例、提交/合并 SHA、CI/评审结果、发布记录和脚本指纹、搜索命中的官方条目、下载文件列表及内容比对、未完成项。留实际市场和下载链接；缺发布授权、凭据或入口时保留已完成的源码与包，不擅自发布，也不把尚未发布的版本说成线上可用。

实例：首次官方上架 `ios-style-mobile-frontend 1.0.0` 时，只需新增两份技能文本、登记目录并生成 API 资源；[PR #2043](https://github.com/inernoro/prd_agent/pull/2043) 合并后，发布包含该技能的 API，再从正式实例搜索和下载两个文件逐字节核验。成功依据是运行版本和真实包，不是上传回执或数据库中多了一行。
