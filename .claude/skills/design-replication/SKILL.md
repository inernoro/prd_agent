# 设计稿复刻（Design Replication）

> **版本**：v2.4.0 | **触发**：`/复刻`、"复刻"、"还原设计稿"、"贴稿"、"按设计稿生成页面"

## 一、核心命题

**复刻的验收面是证据，不是我的转述。**

失手的形态永远是同一个闭环：我读设计稿，读出一份规格；照这份规格写代码；再拿这份规格
验这份代码。两边同源，永远自洽——然后用户打开一看：「元素、样式、布局、功能，最多 40% 像」。

戳破这个闭环要三样**不经过我转述**的东西：

| 证据 | 戳破什么 | 谁产出 |
|---|---|---|
| 逐画板切图 + 逐条文案文件 | 「我以为稿子是这么写的」 | `extract-design.mjs` |
| 量出来的档位表（圆角/字号/字重/色） | 「圆角小一点、标题粗一点」这种拍脑袋数值 | `extract-spec.mjs` |
| 文案覆盖率 + 档位差 + 并排图 + 别人的审查 | 「我看了觉得像」 | `audit.mjs` / `pair.mjs` / 对抗式审查 |

同一套字号、圆角和文案可以完全命中，水印仍可能被撑到整栏高，图标也可能消失。对用户点名的对象，逐项核对所在状态、尺寸参照、可见内容和点击结果。版式取证与真实运行分别给结论。

## 开工前对齐基线

本技能用于方案选定后的真实页面接入与验收。还在选设计、需要准备第三方提示词或分享上下文包时，使用 [第三方设计委托](../give-me-prompt-to-gen-design/SKILL.md) 的第一次触发。拿到已选方案后，先从可复用的代码入口做起，再核对视觉与真实状态。

1. 列出最新用户确认的模板、画板或截图，以及当前真实页面。记录各自的版本、状态与截图范围。此后用户每次修改都更新对应项，同时保留先前确认的尺寸、顺序、语义和交互。只改标签时，逐项核对关联图标、触发区、键盘和无障碍名称。
2. 先走一次真实用户入口，复现缺陷并保存首次画面。按改动列出应体现的状态和操作结果。通常包括打开前、操作后、重开后。只纳入会受本次改动影响的状态。
3. 量对象与参照的关系，包括轴向、位置、实际绘制区域、最小可用宽度和拥挤时的保留顺序。标出每个值来自原稿测量、用户指令还是实际页面。截图经过裁切或缩放而无法还原 CSS 像素时，保留其相对关系，转到原稿或页面测量。遇到「塞满」「和它一样高」等尺度指示时，把参照写成可测的断言。
4. 涉及展开、异步预览、保存、生图或模型调用时，先读 [模板到真实页面验收](reference/live-page-validation.md)，用它的表记录真实数据来源、状态转换和复测条件。照片和截图以用户指明的用途使用。图片里显示的文字、红框和样例值只作为内容或取证，具体要改什么以用户消息为准。

## 二、精度是怎么丢的（六个成因，逐条自查）

| # | 成因 | 长什么样 | 唯一解 |
|---|------|---------|--------|
| 1 | **从没渲染过设计稿** | 只读稿子的源码/数据模型，把它当规格文档读 | Step 1 先渲染 |
| 2 | **用规格代替像素** | 把稿子读成一段文字笔记（"卡片内边距一档、chip 一档"），然后照笔记写 | Step 2 量档位表，照表写 |
| 3 | **token 层没先落** | 每屏对着截图现调数值，第二屏必然与第一屏漂移，还撞双皮肤棘轮 | Step 3 先补 token 再写组件 |
| 4 | **画板漏了** | 稿子 11 屏只做了主态，空态/只读/异常上线才发现是空白 | Step 1 产出画板清单，一个都不许跳 |
| 5 | **文案没逐字抄** | 稿子写「上传网页」，实现写「上传站点」；括号补充被砍掉 | 文案从 `text-*.txt` 复制，不凭记忆 |
| 6 | **检查是自证** | 「我按规格实现了」「我看了觉得像」 | Step 5 机械核对 + Step 6 对抗式审查 |

成因 1-3 是**生成侧**的精度（写之前手里有什么），4-6 是**检查侧**的精度（写完拿什么判）。
两侧都补齐，才是「更精准」；只补一侧，另一侧会把精度吃回去。

## 三、执行流程

```
复刻进度：
- [ ] Step 0: 确认基线、列保留项和状态，再起所需环境
- [ ] Step 1: 取证据 —— 画板清单 + 逐画板切图 + 逐条文案
- [ ] Step 2: 取规格 —— 量出设计系统档位表
- [ ] Step 2.5: 固化档位表进仓库（带来源指纹，改版时可 diff）
- [ ] Step 3: 将本次共享档位对到 token 层，记录局部对象的尺寸参照
- [ ] Step 4: 照证据写实现（一屏一屏来，文案从文件复制）
- [ ] Step 5: 同状态并排图、位置与尺寸断言，以及真实用户路径复测
- [ ] Step 6: 遮住实现说明复看证据，复核可定位的差异
- [ ] Step 7: 偏差归档（改掉 / 有理由保留 / 待办），再报完成
```

### Step 0：选择取证方式

画布源码走下方的解压与渲染流程。可运行模板在原始入口按状态取图。只有截图时，原样保留素材、画框范围和可见文案，逐张建立对照清单。用户提供局部截图时，核对该区域和会被它挤占、遮挡的邻区。Step 2 的 DOM 档位取量只适用于可渲染稿件。

```bash
SK=.claude/skills/design-replication
WORK=<scratchpad>/replication
bash $SK/scripts/setup.sh "$WORK" "<设计稿解压目录>" 8899
```

`setup.sh` 干三件事，缺一件都渲染不出来：装 Playwright；用 curl（走代理）把 React UMD
抓到本地——画布在浏览器里直连 unpkg 会 `ERR_CONNECTION_RESET`；起 http 静态服务——
`file://` 下画布 runtime 取自己的源码会被 CORS 拦掉，截图是一片空白。它最后会把每个画布
**URL 编码后**的地址打出来，文件名带中文时直接复制，不要手拼。

### Step 1：取证据（画板清单 + 切图 + 逐条文案）

```bash
node $SK/scripts/extract-design.mjs --url "http://127.0.0.1:8899/<编码后的文件名>" \
  --out "$WORK/design" --vendor "$WORK/vendor" --width 1600
```

产出 `index.json`（画板清单，含每个画板的 `top` / `height`，Step 2 要用）、逐画板 PNG
（超高的自动切段，一张糊成缩略图的整图等于没有证据）、`text-<画板>.txt`（逐条文案）。

它在两种情况下**硬失败**：正文字符过少（没渲染出来）、识别不出画板。宁可失败也不输出
一份「只有一个画板」的假清单——那会让后面每一步都以为稿子只有一屏。

**画板清单要写进交付消息**，让用户能核对有没有漏屏。然后逐张 Read 切图，看一遍。

### Step 2：取规格（量档位表，别读笔记）

对**每个要做的画板**各量一次（`--y-from/--y-to` 取自 `index.json`）：

```bash
node $SK/scripts/extract-spec.mjs --url "http://127.0.0.1:8899/<编码后的文件名>" \
  --out "$WORK/spec/board-01" --vendor "$WORK/vendor" --width 1600 \
  --y-from 1240 --y-to 3040
```

`spec.md` 会告诉你这一屏真实用了几档圆角（比如 5/6/7/9/10/11/12）、几档字号、
几个字族分别管什么。**这些是事实，不是我读出来的印象**——照着它写组件，才不会每屏靠感觉调。

已有双主题时分别测量；未提供该主题参考时，用真实页面验证可辨性和交互，并标明新增主题缺少同稿对照。

### Step 2.5：固化需要跨版本复用的档位表

`extract-spec` 的产物落在 scratchpad 里，会话一结束就没了。于是下次想回答「这一屏的圆角
到底有几档」「改版之后哪几档变了」，又得把整条取证重跑一遍——要画布文件、要起服务、
要装浏览器，多数时候没人跑，最后退回「凭印象说」。需要跨版本复用完整档位或比较改版时再导出。单处修正保留该对象的测量与来源：

```bash
node $SK/scripts/spec-export.mjs --design <稿子名> --source "<画布文件>" \
  --board "board-01=屏1主控台:$WORK/spec/board-01" \
  --board "board-02=屏2站点卡:$WORK/spec/board-02"
# → .claude/skills/design-replication/exports/<稿子名>/design-spec.{json,md}
```

导出带**来源指纹**（画布文件 sha256 + 量取时间）：说不清「从哪个稿子、什么时候量的」
规格，下次没人敢信，等于白导（`no-rootless-tree.md`）。深浅两套都导——把
`--y-from/--y-to` 那次的 `--theme light` 产物放在 `<目录>-light`，脚本会一起收。

稿子改版后再导一份，然后：

```bash
node $SK/scripts/spec-diff.mjs --a <旧 design-spec.json> --b <新 design-spec.json>
```

它只报档位集合的增减，不报次数波动、不报 sample、不报时间戳——报那些等于制造噪音，
噪音一多人就不看了。每一处增减都要落到 token 层。

### Step 3：落 token（闸门）

```bash
# 用刚量的（scratchpad）
node $SK/scripts/tokens-map.mjs --spec "$WORK/spec/board-01/spec.json" \
  --tokens prd-admin/src/styles/tokens.css --out "$WORK/spec/board-01"

# 或直接用固化好的那份（不必重跑取证）
node $SK/scripts/tokens-map.mjs --export "$SK/exports/<稿子名>/design-spec.json" \
  --board board-01 --theme dark --tokens prd-admin/src/styles/tokens.css
```

输出三类：**已有 token** / **接近但不等**（多半是同一档被写歪，判一下）/ **缺 token**。
本次新增的共享档位先在 token 层补上，按已有双主题约定填写。两个组件只要求等高或对齐时，沿用现有语义尺寸或收敛到共同的组件变量，再测两处渲染结果。

**为什么是闸门**：跳过这一步，设计稿多出来的那几十档值只能以字面量散进几十个组件——
撞 `.claude/rules/admin-dual-theme.md` 的硬编码棘轮，且「这一档到底多少」不再有单一出处，
下一屏必然漂移。补 token 的动作要写进交付消息（改了共享层）。

### Step 4：照证据写实现

一屏一屏实现并验证，先做会影响验收的代表性状态。保持图标、文案、触发、数据的来源和职责清晰：

- 固定文案从取证原件核对。用户明确改了文字、隐藏方式或省略规则时，以最新指令为准。
- 量到的数值带参照对象、单位和主题。对透明素材，用可见像素边界检查尺寸与对齐，同时看外层点击区。保留宽高比，从实际资产验证有无旋转、裁切、透明留白或素材本身倾斜。
- 媒体用真实业务渲染结果或上传资源。已知品牌用可维护的图标来源，未知品牌留语义明确的通用回退。把显示名、配置 ID 和运行时身份分别验证。
- 设计稿和项目约定冲突时，记录具体冲突和可见代价。沿用用户明确接受的取舍；遵循适用权限、可访问性与项目约定。对拿不到的数据，显示产品已有的空态或补齐已授权的数据源，写入偏差台账。
- 用户指出偏差后，保存证据和准确比较对象。将本次改动与保留项同时写进复测，先用该检查抓到旧错，再复跑当前页面和相邻状态。

### Step 5：同状态对照与真实路径复测

先对照相同状态、数据、主题、CSS 视口宽高、DPR 和裁切方式。同一按钮点完必须看到预期结果，再截该状态。对小屏测最容易拥挤的实际触控视口。用同源资产和等比例视图量对象相对位置、前后邻区可视面积、图片是否实际加载及省略或溢出。截图和档位核查各司其职。

```bash
# 分别捕获模板与实现，使用各自唯一的目标状态选择器
node $SK/scripts/render.mjs --url "<模板入口>" --out "$WORK/shots/design" --tag design \
  --width 1440 --height 900 --dpr 2 --expect-state 'default=<模板根选择器>'
node $SK/scripts/render.mjs --url "<预览域名深链>" --out "$WORK/shots/impl" --tag impl \
  --width 1440 --height 900 --dpr 2 --expect-state 'default=<对应状态根选择器>' \
  --storage "$WORK/auth.json"

node $SK/scripts/extract-spec.mjs --url "<预览域名深链>" --out "$WORK/spec/impl-01" \
  --storage "$WORK/auth.json" --width 1600 --scope '<这一屏的根容器选择器>'

node $SK/scripts/audit.mjs --design "$WORK/spec/board-01" --impl "$WORK/spec/impl-01" \
  --out "$WORK/audit/board-01"

node $SK/scripts/pair.mjs --design "$WORK/shots/design" --impl "$WORK/shots/impl" \
  --out "$WORK/shots/pair"
```

`audit.md` 给三个判据：**文案覆盖率**、**硬缺失条数**、**档位缺失数**。
这三个值是档位和文案层面的结论。并排图拒绝空清单、重复状态、失败截图以及视口高度、DPR 或截图方式不一致的配对。旧清单可供目测，严格对照需重截带完整元数据的截图。有意改动的文案和档位在台账说明，未解释的差异要处理。

**让覆盖率变成真判据**：设计稿里的样例数据（站点名、文件大小、「12 分钟前」）也算文案，
实现页跑另一套数据时会被算成缺失。混着这堆噪音，真正该盯的结构文案（按钮、列头、空态引导、
括号补充）就淹了——一个读不出信号的判据等于没有判据。

正解是**用设计稿那套数据渲染实现页**，走录制-回放，应用一行都不用改：

```bash
# 一次性：拿真机录一份响应当模板（形状来自真机，只手改里面的值）
node $SK/scripts/extract-spec.mjs --url "<预览域名深链>" --out "$WORK/spec/impl-01" \
  --storage "$WORK/auth.json" --record-fixtures "$SK/fixtures/<屏名>"

# 手改 fixtures/<屏名>/*.json 里的 body：站点名、大小、时间改成设计稿 text-*.txt 里的那些

# 之后每次取证都带上它
node $SK/scripts/extract-spec.mjs --url "<预览域名深链>" --out "$WORK/spec/impl-01" \
  --storage "$WORK/auth.json" --fixtures "$SK/fixtures/<屏名>"
```

三条纪律：

- **不许手写 fixture**。手写的形状一定跟真实契约漂移（字段改名、多包一层 ApiResponse），
  漂移之后页面渲染成空，而覆盖率只报「文案缺失」——你会以为实现漏了文案。所以形状永远来自录制。
- **混合态直接判失败**。回放时有接口没有对应 fixture 会穿透到真网络，那一屏就是「一半样例
  一半真数据」，量出来的清单没有可比性。`extract-spec.mjs` 遇到这种情况**退出码 4**，不是警告。
- **各自保留证据**：回放用于还原设计样例。保存、重开、媒体加载、生成结果和实际模型要另从真实入口测试，保存实际请求或业务结果。使用用户授权的环境和数据。
- **定期查漂移**：`node $SK/scripts/fixture-drift.mjs --dir <fixture 目录> --url <实现页> --storage <auth.json>`。
  只比键路径不比值；fixture 有而真机没有的键 = 已失效，退出码 1。

实在造不出对应数据的条目（后端根本没有那个字段）才用 `--ignore` 排掉，且要一条条排——
**不许**因为「反正是数据」整段无视。

**取实现侧规格前要确认这些条件**（不给的话那几屏根本量不到，或者量到的是另一屏）：

- `--click '<文案>'`（可多次，按顺序点）：设计稿画的很多屏**要点开才存在**——分享弹窗、
  上传弹窗、数据抽屉、访客抽屉、折叠的提问面板。点不到就当场失败退出码 5，不静默跳过：
  跳过的话量出来的是「没点开的那一屏」，而报告看上去一切正常。
- `--include-frames`：正文在 iframe 里的屏（访客阅读页的文档本体走 srcDoc）默认不收，
  因为多数 iframe 里是用户上传的内容、不是我们的设计；设计稿把它一起画进画板时要开。
- `--min-chars`：「渲染出来了」的下限默认 200，但壳子型的屏天然达不到
  （阅读页外层只有 95 字，其余都在 iframe 里）。按屏声明真实下限，别对着假失败发愣。
- `--fixtures-ignore '<正则>'`：预览环境注入的徽章/心跳流（CDS 的 `_cds/api/*`）不喂这一屏，
  既不该录成样例数据、也不该把这一屏判成混合态。被放行的会**打印出来**——
  这个口子不许变成「把守卫调绿」的开关。

然后**逐张 Read 并排图**，从粗到细（先看关系再看数值）：

1. 有没有整块内容缺失 / 多出来
2. 主次区块的面积比、列宽比例
3. 竖向节奏：分组间距是不是同一套档位
4. 字重与字号的层级差
5. 状态色的语义分配（严重度色不许和来源标签撞色）
6. 逐字核文案
7. 看图标的可见形状与操作热区，验证折叠、更多菜单及重开后状态。动态预览要有真实名称、实际加载的画面和清晰的失效表现。

抓取对照证据后，另用真实用户入口执行主流程。量验收目标，例如期望与实得的组件尺寸、源对象与结果的有序对应、重开前后的身份、最终上游模型。应用注入的预览徽标与产品遮挡分开记录。标明取证版本和尚未运行的环境。发布后的复测以已授权部署和目标版本实际生效为前提。

预览地址走 `python3 .claude/skills/cds/cli/cdscli.py --human preview-url` 取根域名，
路由按真实改动追加（`CLAUDE.md` §11），禁止手拼域名。登录态用 Playwright 的
`storageState` 存进 `$WORK/auth.json`，**凭据只走环境变量，不落文件**。

### Step 6：对抗式审查

按 [审查模板](reference/adversarial-review.md) 给审查者同状态截图、原始用户要求和可复现操作，先让其独立找差异，再核对原因。范围大或相同错误反复出现时，按风险分开看布局、资产与交互。小改动使用定向反例，优先让具体断言能够抓住错位、丢图标、错状态或假数据。保留审查中无法验证的项和原因。

### Step 7：偏差归档

每条差异必须落到三个去处之一，**不许「看着差不多就过」**：

| 处置 | 判据 | 动作 |
|------|------|------|
| **改掉** | 设计稿是对的，实现偏了 | 当轮修，重跑 Step 5 |
| **有理由保留** | 实现刻意不同（真实数据形态、既有 token、后端没这个字段） | 写进交付消息，一条一句理由 |
| **待办** | 该改但超出本次范围 | 落 `debt.{module}.md`，不许只留在对话里 |

台账模板见 `reference/deviation-ledger.md`。**改了后端就逐条列出来**——加功能还好，减功能很麻烦。

## 四、交付前核对

- 原稿、用户最新确认项与当前实现有明确版本和状态映射。每个范围内画板有同条件对照或说明参考缺口。
- 实测过用户点名的尺寸、顺序、图片可见范围和保留项。桌面与受影响的窄屏、实际可用主题都已查看。
- 状态触发后有结果断言。动态行为已在真实数据下复测，重开保存状态；需要发布后验证的事项标明待办和阻塞。
- 已用能暴露原偏差的反例复查，未解决差异进入台账。报告同时给复刻结果和业务复测结果，分别列出环境、证据及未验证项。

交付时简述改动、关键实测值、已覆盖的状态和保留的偏差；附代表性的并排图、可操作的预览路径及真实结果证据。发布或合并依照用户已授权的范围与顺序。
