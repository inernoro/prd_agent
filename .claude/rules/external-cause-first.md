# 先说外因，再说内因（External Cause First）

**一句话**：任何解释「为什么会这样」的输出——日志、报错、告警、排障回复——第一句必须说清是谁的什么动作引起的、要不要紧，程序内部的信号 / 异常 / 函数名只能当附注。
**什么时候撞上**：写日志文案、错误提示、告警、诊断结论，或者回答用户那句「它为什么坏了 / 它为什么停了」。

> 判定口诀：**把这句话念给没看过代码的人听，他能不能接上「哦，是因为我（或谁）刚才做了 X」？**
> 接不上，就是一条只讲内因的日志——它描述了现象，没有回答问题。

---

## 一、外因与内因的分界

| | 内因（程序视角） | 外因（人的视角） |
|---|---|---|
| 主语是谁 | 容器、进程、函数、信号 | 人、Agent、定时器、上游系统 |
| 动词长什么样 | 退出了、抛了异常、收到 signal 9 | 点了「部署」、改了环境变量、推了一个 commit |
| 回答的问题 | 系统内部发生了什么 | 是谁做了什么，才让它发生 |
| 谁在用 | 改代码时定位到行 | 判断要不要紧、下一步做什么 |

内因不是错的，是**不够**：它是现象，不是原因。「某函数抛了空引用」不是原因，
「用户提交了一份没选模型的表单」才是；「容器收到 signal 9」不是原因，
「有人在 14:22 触发了部署」才是。

两者都要留——**顺序决定了它是给人看的还是给日志检索用的**。

## 二、外因五要素（缺一即不合格）

1. **谁**：具体到人 / 哪个 Agent / 哪个定时器 / 哪个上游服务。`source=container.runService`
   是一个**函数**，不是一个施动者。
2. **做了什么**：人话动作（点了「部署」、保存了项目环境变量、推了一个 commit），
   不是 operation code。
3. **从哪个入口**：分支面板 / cdscli / GitHub webhook / 定时任务 / 自动重试。
4. **于是怎样**：用户能感知的后果（旧容器被替换、预览中断约 30 秒、这一次调用降级到备用模型）。
5. **要不要紧 + 下一步**：「这是正常步骤，无需处理」或「这是异常，去做 X」。

## 三、四条硬约束

### 1. 第一句给外因，内因下沉成附注

信号量、退出码、operation、requestId、堆栈全部保留——排障要用——但它们排在后面
（或折叠区、或次级行）。**顺序就是优先级**：读者只读第一行时拿到的，必须是他能行动的那一半。

### 2. 「要不要紧」不许只藏在字段里

程序读得到 `unexpected: false`，人读到的却是「导致容器停止 signal=9」，于是一次正常的
滚动替换被当成事故追了半天。**结论要写进人读的那句话里**，不能只存在于机器字段中。

### 3. 追不到外因就明说追不到，不许拿内因冒充

「没有匹配到任何 CDS 操作意图，可能是外部人工 docker kill 或宿主干预」是合格的——
它如实交出了「外因未知」这个结论。编一个像模像样的原因，比承认不知道糟得多
（`no-rootless-tree.md`：不假定不存在的根）。

### 4. requestId 是桥，不是答案

日志给出 requestId / operationId 之后，必须有一步就能走到「谁、什么时候、做了什么」的路
（把它解析成人话写进同一句，或给出可点开的操作记录）。只丢一串 hex 让人自己去查，
等于把外因的推导工作转嫁给了读者。

## 四、真实案例（2026-09-09，CDS 容器停止日志）

现状（`cds/src/services/docker-lifecycle-classifier.ts` 的 cds 意图分支）：

```
CDS 生命周期操作导致容器停止：cds-cds-self-...-cds-cds-self signal=9；已匹配 CDS 意图
cds-pre-run-replace：部署前替换同名旧容器（operation=deploy-pre-run-replace
source=container.runService requestId=adcf3f7e operationId=op_16ea554a-c24
actor=ai trigger=manual）
```

逐条对照就能看出它错在哪：

| 要素 | 这句话给了吗 |
|---|---|
| 谁 | 只有半个词 `actor=ai`，混在第 40 个字之后的括号里 |
| 做了什么 | `operation=deploy-pre-run-replace`——是代码里的枚举名，不是「触发了一次部署」 |
| 从哪个入口 | 给的是 `source=container.runService`，那是调用它的函数 |
| 于是怎样 | 「容器停止」是内部事件，用户看到的是「预览短暂断了一下」 |
| 要不要紧 | 只存在于 `unexpected: false` 字段里，人读到的第一印象是「被 signal 9 杀了」 |

它该长成这样——同样的信息，换一个次序和主语：

```
分支 cds-acceptance-report-homepage 正在部署（AI Agent 手动触发），CDS 按流程停掉了上一版
容器：这是替换旧容器的正常步骤，无需处理。
技术细节：signal=9 · cds-pre-run-replace · op_16ea554a-c24 · req adcf3f7e
```

同一个文件里的 `external-docker-kill` 分支反而是**做对了**的参照：它明说「没有匹配到
CDS 停止/删除/重部署意图」，如实交出了「外因未知」，读者立刻知道要去查宿主上的人工操作。

## 五、这条也管 AI 给用户的回复

用户问「为什么坏了」，回答不许停在「某函数报了空引用」「接口返回 500」。至少要给出：
这次是由哪个操作 / 哪份输入引发的、是普遍问题还是这一次的特例、要不要紧、下一步做什么。
把内因当结论交出去，用户拿到的是一个他无法处置的名词。

## 六、自查清单（写任何解释性文案前）

- [ ] 第一句的主语是人 / Agent / 上游系统，还是容器 / 函数 / 信号？
- [ ] 五要素齐吗（谁、做了什么、从哪个入口、于是怎样、要不要紧）？
- [ ] 「要不要紧」写进人读的那句话了吗，还是只在机器字段里？
- [ ] 外因推不出来时，我是如实说「未匹配到任何操作」，还是拿内因顶上了？
- [ ] 给出的 requestId / operationId，读者能一步走到「谁做了什么」吗？
- [ ] 内因细节还在（排障能用），只是排在后面，而不是被删掉了？

## 七、与其他规则的关系

- `expectation-management.md`（预期管理总纲）：那条管「接下来会发生什么」，本条管
  「刚才那件事为什么发生」——事前与事后的同一件事。
- `conclusion-before-numbers.md`：形状同源。那条说先给结论再给数字，本条说先给外因再给内因；
  都是拒绝把「自己算」的工作转嫁给读者。
- `no-rootless-tree.md`：外因编不出来就说编不出来，硬约束 3 直接引用它。
- `predicate-and-wiring-discipline.md`：把内因当成原因，会让人去修那个抛异常的函数，
  而真正该改的是让它拿到坏输入的那条路径——修错地方的成本远高于诊断本身。
- `closed-loop-acceptance.md` / `e2e-verification.md`：诊断的终点同样是「人能行动」，
  不是「程序把内部状态打印完了」。

## 八、历史背景

2026-09-09，用户看到 CDS 分支面板上那条容器停止日志后指出：
「这个日志是有问题的，只能说明内因，而不是外因。外因就是用户或 CDS 本身的某个操作导致了问题，
内因是某个函数报错、异常。我们应该追寻更接近人类的外因而非程序的内因。」

那条日志其实已经采集齐了外因所需的全部字段（actor、trigger、operationId），
只是把它们摆在了内因后面的括号里——**信息不缺，次序错了**。本规则由此固化：
采集内因是工程的本分，把外因摆在第一句是对读者的义务。
