# 账在哪，货就在哪（持久等级必须一致）

**一句话**：一条记录的元数据和它的实体必须存在同一个持久等级上——账进了库、货落在容器本地盘，容器一重建就得到一本翻得开却取不出货的幽灵台账。
**什么时候撞上**：写任何「库里存一行、盘上存一个文件」的功能——报告、附件、导出包、截图、生成的产物。

---

## 判定口诀

**把承载它的容器删了重建，这条记录还说得通吗？**

说不通就是持久等级不一致。三种结局，只有第一种可接受：

| 元数据 | 实体 | 重建之后 | 判定 |
|---|---|---|---|
| 持久 | 持久 | 都在 | 对 |
| 易失 | 易失 | 都没了，列表干净地空着 | 可接受——难看但诚实 |
| **持久** | **易失** | **列表满满当当，点开全是 404** | **缺陷** |

第三种最坏，坏在它**看起来是好的**：列表有 23 条、有标题有结论有时间，一切正常，
直到有人点进去。而且它不报错、不变红、通读代码也挑不出来——只有真的点一下才显形。

---

## 三条硬约束

### 1. 实体默认进对象存储，本地盘只配当读缓存

「本地盘」在容器时代不是存储，是缓存。判断一个目录是不是缓存很简单：**删了会不会丢东西？**
会丢，那它就不该是唯一副本。

- 写：先写对象存储（权威），成功了再落元数据。反过来会在上传失败时留下幽灵记录。
- 读：本地缓存优先，未命中回对象存储并回填。回填失败不许影响本次返回。
- 删：元数据删掉是主目标，远端删失败最多留个孤儿对象（占空间，不是数据丢失），
  绝不能因为删远端失败就把元数据留下——那又造一条幽灵。

### 2. 凭据不全时拒绝静默回退本地

半套凭据只会写出一批取不回来的对象。要么整套配好走对象存储，要么**显式**声明用本地，
不许「检测到一半就凑合」。这条是 prd-api 的 `AssetStorageProviderResolver` 立下的，
它的原话是「已拒绝在凭据不完整时静默回退本地，以免资产写入容器本地盘、重部署后丢失」。

### 3. 退化了就写在脸上，别等用户点开才发现

真的只能落本地时（没配对象存储、离线环境），元数据上必须留下**机器可读**的标记
（如 `storage: 'local'`），让接口和界面能当场说清「这份正文重建就没」。

「读不到」的几种成因要分得开，它们的下一步动作完全不同：

- 没配对象存储，正文只在本地 → 去把凭据配上
- 归档于本次改动之前的历史数据 → 无法挽回，重新生成
- 配了、也存了，但取不回来 → 这是故障，去查桶和网络

压成一句「HTTP 404」等于什么都没说。

## 自查清单（写任何「库里一行 + 盘上一个文件」时）

- [ ] 把容器删了重建，这条记录还取得出货吗？
- [ ] 实体写的是对象存储，还是容器本地盘？
- [ ] 写入顺序是「先实体后元数据」吗？（反过来会在失败时留幽灵）
- [ ] 凭据不全时是拒绝，还是悄悄回退本地？
- [ ] 退化成本地时，元数据上有机器可读的标记吗？
- [ ] 「读不到」的几种成因，接口分得开吗？
- [ ] 测试里**删过**那个本地目录吗？（不删缓存的测试永远是绿的，也就永远测不出这个 bug）

最后一条是这类缺陷唯一可靠的机械判据：**测试必须模拟一次容器重建**。

## 已知边界（本仓库现状，2026-09-10 扫描）

| 位置 | 元数据 | 实体 | 判定 |
|---|---|---|---|
| CDS 验收报告正文 | Mongo | 曾在容器本地盘 | **已修**：进对象存储，本地盘降为读缓存 |
| CDS 快捷提缺陷（记录 + 附件） | 本地 `records.jsonl` | 本地 `attachments/` | 同生共死，不是幽灵；但容器重建会**静默丢失**全部缺陷，仍待迁移 |
| CDS 容器日志归档 | Mongo | 内联 `logs: string` | 干净 |
| CDS skill-proxy 缓存 | 无（纯缓存，可回源） | 本地 | 干净 |
| CDS 各类 `*-ledger` / uptime / release-history | 自包含 JSON 文件 | 同一文件 | 同生共死，易失但诚实 |
| prd-api 资产 | Mongo | 对象存储（R2 / COS） | 干净，且已有拒绝静默回退的防线 |

## 历史背景

2026-09-10，用户打开 CDS 验收报告首页，点任意一份报告都是
`GET /api/reports/<id>/raw 失败 (HTTP 404)`，原话「以及出现了大量的404，我认为你需要重新捋一下」。

根因：`AcceptanceReportMeta` 存在 `CdsState`（跟着 backingStore 进 Mongo，持久且跨分支共享），
正文却是 `fs.writeFileSync` 到 `<dataDir>/reports/<id>.<ext>`。CDS 跑在容器里时（CDS-in-CDS 的
分支预览正是如此）这个目录不是卷，容器重建即清空。那条分支当时已经部署 11 次，进容器一看，
正文文件**一个都不存在**，而元数据 23 条完好——一本翻得开、取不出货的台账。

同一轮还暴露出一个连带缺陷：`fetchReportRaw` 抛错时把响应体传成了 `undefined`，
服务端明明回了原因，用户看到的却是「服务拒绝了请求，但没有返回可读错误原因」——
最需要原因的那一屏恰好把原因扔了。

用户的指令是「报告永远存储在对象存储」，本规则由此固化。
