# 合并前必须重新拉一次 review（Pre-Merge Re-Check）

**一句话**：按下合并那一刻的复核，必须包含「重新拉一次 review 线程」——CI 绿、范围对、全量过都证明不了「刚才没有新意见到达」。
**什么时候撞上**：拿到合并授权、准备合并 PR 的那一步。

> 判定口诀：**我最后一次看 review 线程，是几分钟前？** 答不上来，就是没看。

---

## 一、这条为什么单独成规

合并前的复核天然会做「重的那几项」——跑全量、查 CI、核变更范围。这些都要花时间，做完会
产生一种「我已经很仔细了」的完成感，于是最轻的那一项反而被跳过：**再拉一次 review 线程**。

它轻到不像一个步骤，却是唯一一个能捕捉「就在刚才到达的意见」的动作。其余几项查的都是
**代码**的状态，只有它查的是**别人对这段代码说了什么**的状态——而后者在你复核期间仍在变。

---

## 二、强制动作

按下合并之前，除既有的构建 / 测试 / 范围核对之外，必须**紧挨着合并动作**再做一次：

1. 拉取该 PR 的 review 线程，确认没有未处理的未解决项；
2. 确认自动 reviewer（若仓库启用）针对**当前 head** 的那一轮已经结束，不是还在跑；
3. 若期间有新意见到达：回到分类流程（§5.5 分 A/B/C），**不要**因为「都走到合并这一步了」
   就顺手合掉。

第 2 条尤其容易漏：自动 review 是异步的，「上一轮全绿」不等于「针对这个 head 的那一轮
也全绿」。看的必须是 reviewed commit 和当前 head 是不是同一个。

---

## 三、明令禁止

| 反模式 | 为什么错 |
|---|---|
| 用「CI 全绿」代替「没有新 review」 | CI 查代码，review 查判断，两者不互相覆盖 |
| 用「上一轮 review 已处理完」代替「针对当前 head 的这一轮」 | 每次 push 都会触发新一轮，上一轮的结论不继承 |
| 复核开始时拉一次，之后不再拉 | 复核本身要花几分钟到几十分钟，新意见正好落在这个窗口里 |

---

## 四、自查清单（合并前）

- [ ] 我刚刚（不是复核开始时）拉过一次 review 线程吗？
- [ ] 未解决线程都有明确处置（已修 / 已记台账 / 已说明不采纳）吗？
- [ ] 自动 reviewer 针对**当前 head** 的那一轮结束了吗？reviewed commit 和 head 是同一个吗？
- [ ] 有新意见时，我是回到分类流程，还是因为「就差合并了」而顺手合掉？

## 五、历史背景

2026-09-02，CDS 总览重排 PR 合并。合并前我查了 CI（20 项全绿）、`mergeable_state`、
变更范围（17 个文件全部在范围内、无遗留临时文件），并在**真正的合并 head** 上重跑了全量
（445 文件 / 6471 用例）——唯独没有重新拉一次 review 线程。

而就在合并前 3 分钟，自动 reviewer 提交了两条 P2，其中一条是那个 PR 自己引入的回归：
分支正在部署（`building`）时总览会谎报「分支未运行」、就绪计数清零、当前值被抹掉。
渲染探针实测三项全中。回归因此直接进了 main 并上了共享环境，随后靠一个额外的
非快进 release 切换才收回。

复核清单里最重的几项都做了，最轻的那一项没做，而恰恰是它该拦住这次合并。

后续修复 PR 上这条规则立刻兑现了价值：CI 二十项全绿、准备合并时按本规则再拉一次，
发现自动 reviewer 针对当前 head 的那一轮**仍在跑**；等它跑完，果然又报出两条真问题，
其中一条是那次修复自己引入的、比原缺陷更糟的回归（并发守卫会把轮询饿死）。
若按「CI 绿就合」，那条回归会直接进 main。

- `CLAUDE.md §5.5`（Review 范围熔断）：那条管「收到意见怎么分类」；本条管「合并前有没有去看有没有意见」。
