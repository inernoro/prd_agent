# 好用四原则（首席设计师视角）

**一句话**：按用户工作、上下文、可预测性和可信结果判断整条任务；速度、减法与点击数只是诊断，不能代替成熟且自然的产品体验。
**什么时候撞上**：交付任何用户直接操作的界面之前。

> 用完整任务和真实用户可见证据判断好用，不能把实现手法当作原则，或用局部通过替整页背书。
>
> 历史背景：2026-06-02 用户对"再加工里的视觉/文学创作"发出灵魂拷问——"好用吗？"。审下来四项里两项不及格（等待体感、信息过载）。根因是一直在堆功能，没站在首席设计师角度"剃"。本规则把那次审视固化成标准。

---

## 核心主张

先按[预期管理总纲](expectation-management.md#产品和用户相互可预测)判断：产品是否理解用户来此要做的工作，用户能否预测自己的下一步及系统结果。下面四条是诊断方法，不能取代这个原则；减法、少点击和自动化都不是目的。合理的确认、可见选择和工作空间应保留。

---

## 第一原则：快速启动，无需等待

等待就是偷用户的时间。

**判定**
- [ ] 从用户目标到可操作对象是否自然？多出的每次选择、跳转或等待有无必要的任务理由？
- [ ] 有没有"开局空白等待"？（首屏 loading、要先选一堆东西才能开始）
- [ ] 不可避免的等待（LLM/生图）有没有**边等边看**？（逐字流式 / 进度 / 预估耗时 / 可中止），静止 spinner 超 2 秒即不及格（呼应 `CLAUDE.md §6` 禁止空白等待）
- [ ] 能预取的提前预取（异步预热模型/拉选项），别让用户点了才开始转

**怎么剃**：默认就绪（免选直接能用）、乐观更新、流式反馈、预取。

**反面案例**：再加工选视觉创作要"点选择器→点视觉创作"两击才到面板；生图 30s 只有一个 spinner。

---

## 第二原则：强大且奥卡姆——复杂可控，但剃掉不需要人类的地方

强大不等于把所有旋钮怼到用户脸上。

**判定**
- [ ] 首屏是否优先当前用户的高频任务？低频内容按任务和发现成本安排，不能把所有次操作机械塞进菜单
- [ ] **只有一个可用选项时可省去选择动作**；对象及作用范围仍须可见，不能隐藏用户据此建立预期的事实
- [ ] 已有可靠上下文时减少重复选择；预填对象及范围可见、可改，不能代用户越权或作不可逆决定
- [ ] 复杂能力要"够得着但不挡路"——专家能展开细调，新手用默认就出活
- [ ] 每个控件是否对应必要决策？系统可承接上下文，但用户仍应理解其作用和后果

**可选手法**：有任务理由时使用就地编辑、上下文预填或渐进披露；折叠、隐藏和自动化本身不构成收益。

**反面案例**：视觉 mini 面板把千行的 `WatermarkSettingsPanel` 全摊开；模型只 1 个还显示下拉；参考图/水印一上来全亮出来，信息过载。

---

## 第三原则：可视化、不遮挡、够明显、够顺畅、合心智

用户的眼睛和直觉是第一交互界面。

**判定**
- [ ] 关键操作/结果**不被任何浮层遮挡**（z-index 查表，模态高于全局 FAB；见 `frontend-modal.md` / `cds-theme-tokens.md`）
- [ ] 主操作**一眼可见**（大小/颜色/位置符合视觉权重），次操作弱化
- [ ] 结果**看得清**（生成的图/数据不能小到看不清，要能点开/全屏）
- [ ] 操作**顺手**（点击区够大、反馈即时、不跳变、滚动不穿透）
- [ ] 合**用户心智**：这个页面是什么、现在什么状态、下一步做什么，3 秒内懂（呼应 `guided-exploration.md`）

**怎么剃**：视觉层级、状态可见、结果可放大、空状态有引导。

**反面案例**：发送按钮曾被铃铛 FAB 遮住（已修）；生成的图在 640px 抽屉里太小看不清，没法点开。

---

## 第四原则：顺用户习惯，不杜撰长链路，能短就短（但笃定 > 步数）

每多一步，就多一处流失——**但更要紧的是每一步都笃定无歧义**。

> Krug 第二定律修正（来自 `ux-heuristics` 技能）：用户不在乎点几下，在乎的是**每下点击是否轻松、明确、建立信心**。**3 次笃定的点击胜过 1 次困惑的点击**。所以别为了减步数把多个决策硬塞进一屏制造困惑——先保证每步笃定，再压步数。

**判定**
- [ ] 每一步是否**笃定**（点之前就知道会发生什么、自己在哪、对不对）？困惑比步数更致命
- [ ] 完整任务是否连贯？每次跨页、确认、选择和返回是否有必要，上下文是否保留？
- [ ] 有没有"为了演示而硬造的长链路"？（自动跑一串智能体、强行多阶段）
- [ ] 顺**已有习惯**（同类操作在别处怎么做，这里就怎么做，别另搞一套）
- [ ] "选中即就绪、输入即可执行、产出即可用"——把中间确认/跳转压到最少

**怎么剃**：合并步骤、就地操作（不跳页）、复用既有交互范式、默认串好下一步。

**反面案例**：配图链 文学→为这段配图→面板→生成→插入 = 5 步；E9 早期版本默默自动跑一串智能体（被用户批"杜撰长链"）。

## 产品与内部交付记录的边界

产品页面只呈现用户完成业务所需的操作、结果、当前状态和恢复指引。每个入口、面板、提示都必须能回答：用户要用它完成什么业务，或据此采取什么行动？

- **禁止把内部交付记录产品化**：为本次开发、迁移或发布生成的迁移详情、验收报告、证据明细、覆盖矩阵、交付台账、历史验收待办、固定“已通过”横幅等，不得新增为产品页面、导航、页签、统计卡或常驻面板。改名、默认折叠、收进帮助浮层不能改变这条边界；也不得为证明开发完成而另建产品流程或测试记录列表。
- **内部记录归交付系统**：按项目约定归档到 CDS 验收中心、PR、CI 或其他已授权的交付系统；临时材料留在仓库外的任务目录。不得为了展示内部报告而新增业务 API、数据实体或存储。对用户的交付回复可链接证据，产品运行界面不承载这些交付材料。
- **保留实际业务能力**：必要的调用日志、操作审计、任务进度、配置变更与回滚记录，以及用户主动创建或管理的业务报告继续保留。CDS 验收中心本身的验收管理、缺陷验收、知识库报告属于用户业务能力；判断依据是业务用途，不按“迁移”“验收”“报告”等词一律删除。
- **状态必须真实且可行动**：只展示与当前用户任务相关的运行事实、影响和可执行的下一步；缺少本次提交的验收样本不等于业务失败。保留故障、权限限制和恢复入口，不得为了清理内部展示而削弱后端权限、发布校验或删除保护。

交付前自审：逐项核对新增或改动的入口、页签、提示和统计卡是否服务于真实业务，是否混入本次交付过程或验收结论，是否应外置归档；用真实用户路径确认必要的操作、状态和恢复指引仍然有效。报告归档成功不能替代产品行为验证。

## 交付前自审（每个 UI 功能必过）

- 用户为何来此，页面是否直接支持其工作，而非要求先学内部对象？
- 产品承接了哪些可靠上下文，用户下一步是否自然且仍有控制权？
- 点击前能否预测对象、结果、影响和返回方式，同类操作是否一致？
- 正常、失败、结果未知、权限受限时，事实和恢复动作是否可信？
- 整页层级、比例、对齐、密度是否形成稳定秩序，必要内容是否完整可达？

用实际操作和整页截图回答，不能用控件数、点击数或通过的测试数代答。

存在误导、任务断裂或未验证的核心路径时，保留否决或未验收结论，不声称好用。

## 评价边界

四条检查通过只能证明基本可用性，不能直接宣称可上线或优秀。预取、乐观更新、一键直达等实现手法不自动加分。需在真实入口、目标角色和代表性状态下完成任务，独立判断心智匹配、上下文承接、结果可预测、状态可信与整页视觉秩序；严重误导、越权或核心路径未验收时不得用总分抵消。

## 与 `ux-heuristics` 技能的关系（established 框架 + 项目强调）

`.agents/skills/ux-heuristics`（从技能生态 `npx skills add wondelai/skills@ux-heuristics` 安装，3.1K installs，Krug「Don't Make Me Think」+ Nielsen 10 启发式 + WCAG + dark-patterns + 0-10 评分）是**通用、经过实战检验的可用性框架**；本规则是它之上的**项目强调**：

- **跑评分用 `ux-heuristics`**（触发词：`usability audit` / `UX review` / `heuristic evaluation`），它给 0-10 分 + 严重度 + 信息架构建议。
- **守项目底线用本规则**（四原则里的「奥卡姆剃刀剃掉不需人类处」「不杜撰长链」是本系统反复踩坑后的强调，通用框架未必突出）。
- 二者互补：先用 ux-heuristics 量分找问题，再用本规则的「怎么剃」给项目化的修法。

## 与其他规则的关系

- [预期管理](expectation-management.md)是原则总纲；本规则与输入、引导和等待规则提供不同的诊断视角，不能互相替代整条任务判断。
- `frontend-modal.md` / `full-height-layout.md` / `cds-theme-tokens.md` 保证第三原则（不遮挡/撑开/对比度）。
- 本规则只定"判定标准"，具体实现手法去对应子规则。
