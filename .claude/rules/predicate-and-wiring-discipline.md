# 判据与接线纪律（Predicate & Wiring Discipline）

**一句话**：五种编译过、测试绿、通读也挑不出的形状：判据太窄、链路只建一半、判据分裂漂移、测试反向锁死 bug、用变更前状态去 gate 那个会改变它的变更。判据是「改动删掉后测试仍全绿就需要一条守卫」。
**什么时候撞上**：新增判定函数、新增模块、新增测试时。

> 本仓库连续多轮 review（发布系统 PR #1273 七轮 + #1281 一轮，共 25+ 条 P1/P2）里，**几乎每一条**
> 都不是「逻辑写错」，而是下面四种形状之一。它们的共同点是：**代码看着对、编译过、全量测试绿、
> 我自己通读也挑不出毛病** —— 只有 review 或线上事故能发现。所以靠「写仔细点」是治不好的，
> 必须用机械判据在提交前扫出来。

---

## 一、四种形状（先认形状，再谈修法）

### 形状 1：判据比它该管的范围窄

判据只覆盖了「最直观的那一种输入」，换个等价写法就漏。

| 真实事故 | 窄在哪 |
|---|---|
| `a.trim() === b.trim()` 当「同一个目录」 | 没规范化：`/opt/site` 与 `/opt/site/` 判成不同，共用保护被关掉，回收删了另一个目标的生产产物 |
| 条数 + 时间窗当「这条预检还有没有用」 | 没看引用：把在途 run 依据的结论删了，审计链接指向空气 |
| `imageAssetId != null` 当快照 fallback 的入口条件 | 太严：有 workspaceId 无 imageAssetId 的旧数据被整个跳过 |
| `Status=Queued` 当「这条 run 该我认领」 | 没带部署作用域：旧构建的 worker 抢走新分支的任务 |

**自查**：写下判据后问一句 —— **有没有一种「语义上相同、写法不同」的输入会让它给出相反答案？**
路径要规范化，标识要带作用域，「还有没有用」要看引用而不只看年龄。

### 形状 2：链路只建到一半（删掉不会红，只会静默退化）

模块建好了、单测全绿，但**没有任何人调用它**；或者算出来了却没进传输面/渲染面。

真实事故（同一个 PR 里出现六次）：`buildReleaseLogSnapshot` 全 src 无人调用 /
`release-remote-watcher` 整个模块无人 import（定时器从不启动）/ `setReleaseDriftNotifier` 从不注册
（退化成 `console.warn`，一个从没响过的铃）/ `releaseEstimate` 没进响应 /
`getReleaseTargets` 没接进监控 state 源 / incident 的 `releaseId` 算出来了但前端不渲染。

**为什么单测测不到**：单测注入的是自己造的桩，测的是「函数对不对」，不是「有没有人用它」。

**自查（机械可执行）**：每新增一个 export，跑一次
```bash
grep -rn "<新符号名>" src/ web/src/ --include=*.ts --include=*.tsx | grep -v "定义它的那个文件" | grep -v tests/
```
**结果为空 = 你建了一半**。若这条接线「删掉不会红」，必须补一条源码守卫测试
（照抄 `cds/tests/services/release-observability-wiring-guard.test.ts`）。

### 形状 3：判据分裂成多份，然后各自漂移

同一个判断被抄了 2-3 份，改一处忘一处。真实事故：步骤推断三份拷贝（后端 + 发布中心 + 分支侧向导）、
探测目标判定两份（预检 + 存活监控）、终态表两份、回收自建在途判定（撞上既有守卫才发现）。

**自查**：写判断前先 `grep` 有没有人已经在判同一件事。已有 → 抽成唯一判定源 + 加「防再修一边」守卫；
守卫的形式是「扫全仓，该判断的定义只许出现在这一个文件」。缓迁某个文件要**显式列进 allowlist 并写明原因**，
不许把断言注释掉。

### 形状 4：测试自己坏了（比没有测试更糟）

两种：

- **反向锁死 bug**：逐字要求某个错误实现存在。真实事故：`expect(source).toContain('fixed bottom-4 left-4')`
  （字面要求那个遮挡布局存在）、`expect(branchListSource).toContain('执行 ${scriptOne.replace')`
  （字面要求硬编码存在）。**谁修 bug 谁的 CI 红**，于是没人敢修。
- **静默空跑**：前置条件不满足就整套跳过，还是绿的。真实事故：真 sshd 端到端用例的私钥默认路径写成
  session 级 scratchpad 绝对路径，换会话即 `existsSync` 失败 → 三条用例变成空跑的绿灯，
  **而债务台账正引用它当「真实环境证据」**。

**自查**：
- 断言的是**行为**还是**某段实现的字面存在**？后者一律改写成行为断言（或至少断言「走共享判定源」）。
- 会跳过的用例：跳过时**必须打印跳过原因**；判断有没有真跑**看耗时**（毫秒级 = 没跑）。
- **一个不会红的证据比没有证据更糟** —— 它会让下一个人以为这件事已经验过了。
- **测试写完要确认「谁在跑它」**：本仓库 `scripts/tests/` 下曾有 4 个 `test_*.py` 没有被任何
  workflow 引用（`grep -rn "scripts/tests" .github/workflows/` 只列到另外几个），写了等于没写 ——
  这是形状 2 与形状 4 的合体：测试本身就是一条没接上的线。

### 形状 5：用变更前的状态，去 gate 那个会改变该状态的变更

判据本身没写错，但它**取值的时刻**错了：在变更 A 执行之前，去检查「A 将要修复的那个东西是否正常」。
于是坏状态把唯一能修好它的动作永久挡在门外，形成死锁——而且重试毫无意义，因为每次重试都在同一个
「变更前」时刻取同一个坏值。

真实事故（2026-07-30 生产发布）：`gateway_route_self_test` 门禁用**发布前**还在运行的旧容器做鉴权
判定。旧容器带着轮换前的密钥，必然 401；而这次发布走到 `docker compose up` 时恰恰会用新 `.env`
重建容器、自动消解这个不一致。stage 脚本里 `run_prod_preflight` 排在 `exec_dep.sh` **之前**，
于是「上一次没做完的轮换」把「本可以修好它的这次发布」挡了两轮。

**为什么难发现**：门禁逻辑孤立看完全正确（发流量前确认网关可用，天经地义），失败信息也「如实」
报告了 401。错的是**判据与被判据对象的时序关系**，这在单个函数里根本看不出来。

**自查**：写任何 pre-flight / pre-check 时问一句 ——
**这条检查失败时，我要 gate 的那个动作本身会不会正好修好它？** 会 → 它就不该阻塞，
至多是提示；否则你造的是死锁而不是护栏。同时确认**检查取的是哪个时刻的状态**：
变更前的运行态，通常只能证明「上一版还活着」，不能证明「这一版能上」。

## 二、提交前自查（5 条，逐条过）

```
- [ ] 形状1 判据：有没有语义相同但写法不同的输入会让它翻转？（路径规范化 / 标识带作用域 / 看引用不只看年龄）
- [ ] 形状2 接线：每个新 export 都 grep 过「谁在用」？为空就是建了一半。删掉不会红的接线补源码守卫。
- [ ] 形状3 分裂：写判断前 grep 过有没有人已在判同一件事？已有就抽 SSOT + 守卫。
- [ ] 形状4a 测试：断言的是行为，不是某段实现的字面存在？
- [ ] 形状4b 测试：会跳过的用例打印了跳过原因？耗时确认它真跑了？
```

**红绿闭环是这五条的兜底**：把修复临时改回事故行为、确认对应用例变红、再恢复。
用例不变红 = 它没在测你以为它在测的东西。

---

## 三、这条规则本身的教训

被 review 抓到不丢人，**同一类形状被抓 25 次**才是问题。抽 SSOT + 加守卫测试这套动作，
应该是写代码时的**默认动作**，而不是被 review 逼出来的补救。

判断标准很简单：**如果这处改动删掉之后，测试仍然全绿，那它就需要一条守卫。**
