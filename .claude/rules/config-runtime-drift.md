# 声明态与运行态漂移（Config-Runtime Drift）

**一句话**：改的是源头，生效的是副本——改完配置必须让所有持有者重新读一遍（recreate 而非 restart），并 reload 指向它的代理。
**什么时候撞上**：改 .env、compose 环境变量、密钥、上游地址这类被进程启动时快照的配置。

> 配置文件里写的值，不等于进程此刻实际持有的值。进程在**启动那一刻**把配置快照进了内存，
> 之后源头再改，进程一无所知。改了源头却没让持有者重新快照，就制造了一个**看起来已经生效、
> 实际从未生效**的状态——它不报错、不告警，只在下一次有人拿新值去对账时炸开。

---

## 一、核心判定

改完一个配置值后，只问一句：

> **谁在持有这个值的副本？他们重新读过了吗？**

持有者没重新读，这次修改就**没有生效**，无论文件里写得多正确。「文件已改」是意图，
「进程已重新持有」才是事实——两者之间隔着一次重启 / reload / 重连。

判据口诀：**改的是源头，生效的是副本。副本不刷新，等于没改。**

---

## 二、三条已知漂移通道（改这些值时逐条对照）

| # | 通道 | 谁持有副本 | 刷新方式 | 不刷新的症状 |
|---|---|---|---|---|
| 1 | `.env` / compose `environment` | 容器进程（启动时快照进环境变量） | `docker compose up -d --force-recreate <svc>`；**改 .env 后 restart 不够**，要 recreate | 新旧值并存：一侧用新值调用、另一侧用旧值校验，表现为莫名其妙的 401/403/签名不符 |
| 2 | 服务发现 / 上游地址 | nginx、连接池、DNS 缓存（启动或 reload 时解析一次 IP） | 重建被代理的容器后**立即** `nginx -s reload` | 上游全 502，但被代理的服务自身完全健康——最容易误判成「应用挂了」 |
| 3 | 密钥 / 令牌轮换 | 所有消费方（签名方、校验方、加密方、解密方） | 全部消费方同轮更新；跨副本的要盘点清单 | 一侧签的另一侧验不过；加密类的更糟——旧密文永久解不开（见 `cross-project-isolation.md` 通道 2） |

三条的共同点：**源头改动是原子的，副本刷新不是**。所以漂移窗口天然存在，纪律的作用是让这个窗口尽可能短、并且可被发现。

---

## 三、强制动作

1. **改完源头，同一次操作里刷新全部副本**。密钥轮换尤其不许拆成两次「先改文件、回头再重启」——中间那段时间系统处于自相矛盾状态，而且极易被忘掉（本次事故就是忘了几十小时）。
2. **盘点持有者**。改一个 env key 之前先 `grep` 它在 compose 里被注入给了哪些服务。本仓库的 `LlmGwServe__ApiKey` 就同时注入 `api` / `llmgw-serve` / `llmgw-serve-b` 三个服务，漏掉任何一个都会留下半生效状态。
3. **重建非代理容器后必须 reload 代理**（通道 2）。这条在 `doc/rule.platform.production-release-safety.md` 的发布脚本里已经落地，但**手工重建容器时没有任何护栏**——手工路径要自己补这一步。
4. **对账只用哈希前缀，绝不输出明文**。核对「文件里的值」与「容器里的值」是否一致时，两边都取 `sha256 | cut -c1-12` 比对。这既能定位漂移，又不会把密钥泄进日志（同 `ssh-exec-failure` 的脱敏纪律）。

## 三点五、运行态自述必须双值对账（一个值没法自证）

漂移最阴的形态是：**你用来确认「有没有生效」的那个指示器，本身就是副本**。
版本端点报的 commit、健康页显示的配置、启动日志打的上游地址——如果它们读的是
运行时可被改写的 env，那它们只能证明「有人希望我是这个值」，不能证明「我真的是」。

所以任何「我现在是哪一版 / 我连的是哪个上游 / 我用的是哪份配置」的自述，必须给两个值：

| | 从哪来 | 能证明什么 |
|---|---|---|
| **实际值 actual** | 编译期烤进制品（程序集属性、构建常量、镜像 digest） | 运行时改不了，这才是事实 |
| **期待值 declared** | 部署时注入（env、启动参数、配置中心） | 只代表「本次部署希望跑哪个」 |

并且必须**当场对账**：两者不一致就在同一个响应里标出来（`match` / `mismatch` / `unknown`），
不要让人事后自己比。缺任一边只能判 `unknown`——**缺证据不等于没问题**，不许乐观判 match。

判据口诀：**这个值运行时能被改写吗？能，它就不能用来自证。**

落地范例：`/api/v` 返回 `actualCommit`（`-p:SourceRevisionId` 烤进
`AssemblyInformationalVersion`）+ `expectedCommit`（env 注入）+ `commitMatch` + 不一致时的
`commitWarning`；判定逻辑在 `PrdAgent.Core/Diagnostics/BuildIdentity.cs`，守卫测试
`BuildIdentityTests` 锁死「事故值必须判 mismatch」「缺一边只能判 unknown」。

**只写进 ENV 不算烤进制品**：容器启动时平台注入的同名 env 会覆盖镜像里的 ENV，
覆盖后指示器立刻开始撒谎，且看不出来。

## 四、受限运维通道的使用纪律

生产机往往**故意**不给自由 shell（本系统 CDS 只有发布通道）。这是安全设计，不是缺陷。
当排障确实需要在目标机执行命令时，可以把发布通道当作**受控远程执行通道**（建临时发布目标、
挂一段脚本、跑一次 run），但必须守住四条：

1. **只做幂等且可逆的操作**。删除类先跑 dry-run 看清单再执行（`POST /releases/targets/:id/reclaim` 就是这个范式）。
2. **只读诊断优先**。先用只读命令（`df` / `du` / `docker inspect` / `docker logs`）把事实搞清楚，再决定要不要写。
3. **输出必须脱敏**。诊断密钥类问题只打哈希前缀和长度，不打值。
4. **临时目标用完立刻归档**，并在归档理由里写清它干过什么——否则它就是一个绕过所有发布门禁的后门。

**并且要预判副作用**：临时通道跑的命令不经过发布脚本的编排，发布脚本替你做的那些收尾
（reload 代理、等待 readiness、探公网表面）一件都不会自动发生。本次就是在这里踩了坑——
手工重建容器后没有 reload nginx，公网 502 了约 4 分钟。**手工做了发布脚本会做的事，
就要手工补齐它的收尾动作。**

## 五、自查清单（改任何被快照的配置时）

- [ ] 这个值有哪些持有者？我 grep 过 compose / 代码确认清单了吗？
- [ ] 我在同一次操作里让**全部**持有者重新持有了吗（recreate 而非 restart）？
- [ ] 有代理 / 连接池 / DNS 缓存指向被我重建的东西吗？我 reload 了吗？
- [ ] 我是用哈希前缀对账的，没有把明文打进日志吗？
- [ ] 走受限通道时：只读优先、可逆、用完归档、收尾动作补齐了吗？

## 七、与其他规则的关系

- `cross-project-isolation.md`：管「一份状态被多个项目共享」（空间维度）；本规则管「一份状态被快照成多个副本后源头变了」（时间维度）。密钥轮换同时命中两条——那边管「轮换会打哑谁」，这边管「轮换有没有真正生效」。
- `predicate-and-wiring-discipline.md` 形状 5：本次 401 之所以变成死锁，是因为门禁拿变更前的运行态去 gate 那次能修好它的变更。判据侧的教训记在那条规则。
- `doc/rule.platform.production-release-safety.md`：MAP 生产发布安全合同 SSOT，条目 9 是本规则在生产发布链路上的强制落地。
- `no-rootless-tree.md`：对账必须读真实运行态（`docker inspect`），不许凭「文件里写了所以它就是这个值」推断。
