# 用户输入最小原则（Minimal User Input）

**一句话**：凡是系统自己查得到、猜得准、能从上游拉回来的值，都不许摆成输入框让用户填；用户只该提供系统无从得知的那几个字段——通常就是密钥和选择。
**什么时候撞上**：设计任何「接入 / 配置 / 注册」类表单，尤其是接第三方服务。

---

## 判定口诀

对表单里每一个输入框问一句：**这个值，系统能不能自己知道？**

| 能不能自己知道 | 该怎么做 |
|---|---|
| 系统本来就知道（内置注册表、上游 API、已有配置） | **不许出现输入框**。直接用，最多在高级区放一个可覆盖的字段 |
| 系统能高置信推断（按类型、按命名规则、按同类历史值） | 预填 + 允许改，**不许留空让用户想** |
| 系统猜得到但不确定 | 预填 + 明确标「这是猜的，请核对」 |
| 系统无从得知（密钥、用户的业务命名、用户的偏好） | 这才配做必填输入框 |

一个接入表单的必填项数量，应当等于最后一类的数量。多出来的每一个，都是把系统的工作转嫁给了用户。

---

## 三条硬约束

### 1. 已知的上游不许让用户手填地址

接第三方服务（模型供应商、对象存储、消息通道、支付网关）时，必须内置一份**上游预设注册表**：
显示名、接口地址、协议类型、密钥获取页链接、默认并发/超时。用户的动作是**搜索并选择一个平台，然后只填密钥**。

- 预设注册表是后端 SSOT（对齐 `frontend-architecture.md`：前端不维护业务映射表）。
- `baseUrl` / 超时 / 并发这类**有正确默认值**的字段，一律收进「高级」折叠区，默认不展开。
- 预设里没有的上游，保留「自定义」入口——但那是兜底，不是主路径。

判据：**用户需要打开浏览器去搜供应商的 API 地址，就已经输了。**

### 2. 能从上游拉回来的，不许让用户抄

密钥填完之后，凡是上游自己提供查询接口的信息（模型清单、模型能力、价格、配额、区域），
必须由系统去拉，让用户在**拉回来的结果里勾选**，而不是照着供应商文档往输入框里抄。

- 拉不到就明说拉不到（`no-rootless-tree.md`：不编造），并退回手填——但手填是降级路径。
- 拉回来的值要标**来源与时间**（「取自上游 /models，2026-08-11」），让用户知道该不该信。

### 3. 推断出来的值必须可见、可改、可追责

自动填上的东西不能是黑箱：

- 界面上要能看出**哪些字段是系统填的**（来源标记 / 不同底色 / 一句「已按 X 自动填写」）。
- 每一项都可被用户覆盖，覆盖后不再被自动逻辑改回去。
- 推断规则要能说出依据（「按模型名含 `embedding` 判为向量用途」），不许玄学。

---

## 与「可观测性」的连带义务

最小输入不等于少给信息。恰恰相反：**用户少填的每一项，系统都欠他一个「我填了什么、对不对」的交代。**
所以凡是走最小输入的接入流程，必须同时具备：

- **当场自测**：填完密钥立刻能点一次「测试连接」，给出成败、耗时、失败原因（不是等到业务调用时才炸）。
- **结果可见**：接入完成后能看到系统替他配了什么（拉到几个模型、用了哪个地址、并发多少）。
- **失败可诊断**：错误要给可执行的下一步（密钥无效 / 地址不通 / 区域不支持 / 余额不足），不是一句「操作失败」。

三者缺一，最小输入就退化成「让用户蒙着眼睛少填几个字」。

## 自查清单（做任何接入 / 配置表单时）

- [ ] 每个必填项都属于「系统无从得知」那一类吗？
- [ ] 第三方上游的地址是内置预设，而不是让用户去搜吗？可搜索选择吗？
- [ ] 有正确默认值的字段收进高级区了吗（默认折叠、可覆盖）？
- [ ] 上游能查的信息（模型 / 能力 / 价格）是系统拉的，还是让用户抄的？
- [ ] 自动填的值标了来源与时间、可被覆盖吗？
- [ ] 填完能当场测一次、看得到系统配了什么、失败给得出下一步吗？

任一为否，回去减字段。

## 历史背景

2026-08-11 用户在 LLM 网关控制台接入 OpenAI 后反馈：「配置过程中很麻烦，应该去内置一些上游，
我总不能去找 openai 的 api 地址吧，应该是选择平台、输入密钥即可（还给人搜索）；高级选项里面
新增、更改 baseurl 地址」「价格方面都能自动完成最好，用户不应该输入很多内容」。

核对线上真实数据印证了这不是主观感受：该部署 3 个 Provider 下共 17 个模型，**价格字段全部为空**
（要用户自己查价再手填三个数字，于是没人填）；新接的 OpenAI Provider 密钥已配好，**名下零个模型**
（加完密钥没有任何「拉一下看看有什么模型」的入口，流程就断在这里）。本规则由此固化。

## 与其他规则的关系

- `zero-friction-input.md`：管「别让用户对着空白框发呆」；本规则更进一步——**那个框根本不该存在**。
- `anti-detour.md`：管「别让用户离开当前流程去准备文件」；本规则管「别让用户离开产品去查资料」。
- `chief-designer-usability.md` 第二原则（奥卡姆）：本规则是它在接入表单上的可执行判据。
- `no-rootless-tree.md`：自动填的值必须有根，拉不到就说拉不到，不编。
- `expectation-management.md`：最小输入的连带义务（当场自测 / 结果可见 / 失败可诊断）是它在接入场景的落地。
- `frontend-architecture.md`：预设注册表是后端 SSOT，前端不另维护一份。
