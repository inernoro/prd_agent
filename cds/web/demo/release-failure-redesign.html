发布失败诊断改版

截图里那一屏难看，根子不在配色，在于结论位被塞进了一整段 stderr。 FailureDiagnosis 的 headline 设计成「一句话结论」，但当日志里没有结构化门禁报告时 它退化成 errorLines[0]——一条内嵌 19 行 stderr 尾巴的复合错误串， 被 17px 粗体、换行折叠地铺成八行文字墙。改版把这一屏拆成四层：结论、影响面、判据、原文。

样本 rel_9759ead9be9405e3 提交 53dcf3c · main 结果 发布失败 · 耗时 38s 现状代码 cds/web/src/pages/release-center/FailureDiagnosis.tsx

四条根因

每条都能在截图里指出来，编号对应 demo 现状态上的标记

1信息层级

结论位承载了整段原始日志

没有门禁 JSON 时 headline 取 errorLines[0]，而这条 error 本身就带着 --- stderr(tail) --- 的 19 行尾巴。一句话的位置装了 1418 个字符。

2排版错配

日志被当成散文排版

日志靠换行传达结构，<h3> 里换行全被折叠成空格，17px 粗体让每个字都在喊。 既不像结论，也不像日志。

3轻重倒置

最该看的那句被压成灰色小字

「目标仍在 06efeb6，未切换到本次版本」= 生产没受影响，是失败时用户最想先确认的事， 现在挂在文字墙下面 11px 的一行尾巴里。

4噪音未收敛

五条一模一样的重试告警各占一行

curl 的 retry 告警逐字重复五遍，把屏幕吃掉三分之一；真正有信息量的是下载地址和 404 这两件事。

边界

这版方案刻意不做的事

不改后端接口

  • 全部信息都从 run.logs 里现有的行提取，不新增字段、不新增端点。
  • 识别不出来时如实说「未能提取结构化判据」，退回原文列表，不编造原因。

不做通用日志解析器

  • 只加「产物下载失败」一种形状，和磁盘护栏一样是精确匹配。
  • 不为了覆盖率把 WARN 全当噪音——那等于关掉一整类真实告警。

不碰颜色系统

  • demo 里所有颜色取自 cds/web/src/index.css 现有 token，双主题各写全一套。
  • 红色只用于状态标识（左侧竖条、chip、失败步骤底色），正文一律常规前景色。

demo 数据取自 rel_9759ead9be9405e3 的真实失败记录；日志行为按截图中的 stderr/stdout 尾部还原，未做美化。

「推断」块中的镜像前缀结论尚未在目标机上证实，按未证实处理。
