方案 A · 数据流轨道

节奏感最强

呼吸改成有方向的流动：左轨是自上而下穿行的光段（像 CI 日志在往下滚），卡片边框有一道流光沿周长巡一圈，AI 徽章内部一条扫描线掠过。三个动效同源同向，读出来的信息是「AI 在持续推进，没卡住」。适合当默认态——它把「活着」这件事表达得比呼吸更确定。

方案 B · 思考脉冲

信息量最大

动效带上正在做什么：AI 徽章向外一圈圈发射涟漪（心跳源），下面一条 7 柱波形按不同周期跳动（幅度随 AI 活跃度走），右侧打字机滚动当前动作文案。用户不用点开 AI 面板就知道 AI 此刻停在哪一步——直接消灭「不知道现在在干嘛」这一种预期失控。

方案 C · 工位接管

最克制 零额外行高

把「AI 占用中」画成一种环境光：一道极淡的光带每 5.6s 斜掠过整卡（像有人在这张工位上开了灯），左轨按当前操作的阶段数分段（这里是部署，building → starting → running 三段），徽章外一圈光带沿环巡行，右下角机器人按钮带一层呼吸光晕说明「这个操作现在归 AI」。整体频率低、幅度小，长列表里十几张卡同时亮也不会晕。

阶段信息放在页脚 sha 与部署状态之间那块闲置横向空间里，不再往标题下面另起一行——卡片高度和基线完全一致，读起来还顺：头像是谁，紧接着是在做什么、做了多久，再往右才是上一次部署什么时候。左轨和页脚轨由同一份状态驱动、共用同一个渲染函数，不各自跑 CSS 循环，避免两处进度互相打架。

  • 取舍：单看一张卡最安静，但也最容易被忽略；页脚活动条和「部署成功 N 分钟前」并列会让页脚偏挤，窄屏下文案先隐藏、只留进度轨。

鲁棒性 · 段数从来不是固定的

必读

AI 对 CDS 的操作绝大多数根本没有阶段。cds/src/types.ts 里分支状态是 7 值状态机（idle / building / starting / running / restarting / stopping / error），只有部署这一条路径像流水线，而且是 building → starting → running 三段；改环境变量、停服务、查日志、改构建配置这些只是一串 /api/* 调用，没有总量可言。

所以纪律是：不知道总步数，就不许画分段。分段这个形状本身在向用户承诺「共 N 步」，他会据此估还要等多久——估错就是预期失控。下面五档由同一个 renderRail(el, state) 渲染，形态差异全部来自数据，没有一处写死段数。

  • 接口只有一个：renderRail(el, state)，左轨（纵向）和页脚轨（横向）共用。上面七行的形态差异全部来自 state，段数没有一处是常量。

  • 降级方向永远是往信息更少的那一档退，不许往上编。拿不到阶段就退 indeterminate，拿不到 label 就退 heartbeat，最差也就是回到现网基线，不会更糟。
  • 超时与失败必须停掉流动并换色。缺了这一档，AI 掉线后卡片会永远停在「正在启动中」——那是彻头彻尾的谎，比没有动效更坏。

想要「一眼看出还活着」

选 A。方向性流动比呼吸更能表达进行时，改动最小，不动布局。

想要「知道 AI 在干什么」

选 B。多一行换来动作文案 + 活跃度波形，直接兑现预期管理里的「在做什么」。

想要「十几张卡同时亮也不吵」

选 C。频率最低、幅度最小，同时把构建阶段画进左轨，是信息密度和克制的折中。
