# CDS Agent Key 管理 · 思路（V1）

## 目标

用户来 Agent Key 页只为两件事之一：签发一把符合当前任务的 Key，或者找到一把已有 Key 并管理它。设计要让这两件事一眼可分，细节只在需要时出现；并让用户在签发之前就准确知道这把 Key 拿到手后能做什么。

具体对应 `design.json` 的五个目标：

1. T-01 一页两件事：列表是主体，右上角只有一个主动作「签发新 Key」；项目卡进来是同一页加项目筛选。
2. T-02 签发前看清后果：三步签发，旁边一栏实时说明能访问、能做、不能做、何时失效和风险等级；回执和列表详情用同一份说明。
3. T-03 有效期默认永久，可设 1/7/30/90 天或指定日期；用户选的到期日不随使用推迟。
4. T-04 来源分三类：用户签发、AI Agent 签发、来源未记录；无法确认的如实保留。
5. T-05 状态与鉴权一致，吊销二次确认、记录保留，结果不明时不重复提交。

## 关键取舍

| 取舍 | 选了什么 | 没选什么，为什么 |
| --- | --- | --- |
| 入口 | 三处入口（项目卡弹窗、项目列表全局 Key 弹窗、系统设置页签）合成系统设置里的一页，项目卡只是带 `?project=` 的入口 | 保留项目卡弹窗：两套 UI 会继续分叉，用户要先分清「项目 Key」和「全局 Key」才知道去哪 |
| 签发入口形态 | 弹窗，左边三问、右边说明栏 | 页内常驻表单：用户一打开就要处理配置和历史两类信息，这正是要解决的问题 |
| 详情形态 | 点行原地展开 | 侧滑抽屉：吊销的二次确认在抽屉里再套一层浮层，手机上层级过深 |
| 权限模型 | 一期沿用现有能力：单项目可选完整读写或只开放一个模块；跨项目 Key 只能完整读写并写明原因 | 直接做五类权限自由组合：需要逐个接口补鉴权，放到二期，避免页面承诺后端做不到的事 |
| 项目管理员 | 一期不单列：当前「项目完整读写」本身就能为同项目签发与吊销 Key，说明栏如实写出 | 先画一个不存在的开关：签发出去的 Key 与说明不符 |
| 来源判定 | 服务端按签发通道写 `issuedVia`；历史 Key 只认结构化字段 | 解析标签文字：标签是自由文本，用户签发时可以写成任何样子 |
| 状态判定 | 列表与鉴权共用一个可用性判据 | 前端按 `revokedAt` 推「有效」：旧列表正是这样把过期、主体停用的 Key 报成「未吊销」 |
| 多项目 | 一期一把 Key 只指定一个项目，页面写明替代方案 | 先放多选：签发接口目前会以 `multi_project_scope_unsupported` 拒绝 |

## 本版改动

首版，没有更早的稿件。相对正式页面（实施基线 db09b441a 的系统设置「AI Access Key」页签）：

- 页签改名为「Agent Key」，签发表单从常驻改为弹窗，列表按时间分组并可原地展开。
- 新增来源筛选、来源说明与来源链，新增与鉴权一致的状态。
- 签发新增有效期选项和实时能力说明。
- 项目卡菜单「Agent Key」改为跳转本页；项目列表里的两套旧弹窗删除。
- 保留原页的三类保护：签发结果未知、明文只显示一次（30 分钟内切页可回看）、吊销结果未知。

## 依据

- 框架 FW-CDS-UI V3：R-01 公共导航、R-02 双主题、R-03 字体尺度、R-04 模块规则、R-07 窄屏、R-11 对照依据。
- 正式代码现状：`AccessKeysTab.tsx`、`ProjectListPage.tsx` 的两套签发弹窗、`types.ts` 的 `AgentKey` / `GlobalAgentKey`、`state.ts` 的鉴权判据。
- 仓库规则：预期管理（签发前可预测结果）、最小惊讶、结果未知不得重复提交。

## 待定

1. 二期权限模型：分支与部署、构建配置与环境变量、工程规划、设计稿、数据库五类分档组合，加单独勾选的项目管理员。需要逐个接口补鉴权，排期待定。
2. 三期多项目：一把 Key 指定多个项目。
3. 是否给全局 Key 也提供「只开放一个模块」的受限权限，取决于二期鉴权改造。
