# 快速创作 · 成片时长与浏览器渲染（给实现方）

**一句话**：成片多长由旁白字数决定，开工前让用户定、由服务端按公式写够并校验；成片交付成「能播放的网页」，播放和导出视频都在用户浏览器里完成，服务器不渲染视频。
**谁该读**：实现快速创作视频产出的智能体与工程师；评估服务器成本的人。
**读完能做什么**：按这里的公式实现时长控制，按推荐的框架和契约实现浏览器播放与导出，并知道哪些浏览器要走兜底。

---

## 一、为什么现在的成片只有二三十秒

1. Lemo-Opuscar 的风格样片本身就是 15–30 秒（「自制风格」的示例写的是 15–30 秒的样片，请求示例是 30 秒、40 秒）。
2. 生成时没有告诉模型要多长，模型照着样片的长度写分镜，教程也被写成了二三十秒。
3. 这件事不能靠「提示词里写长一点」解决：模型对时长没有概念，只有字数是可控的。

## 二、时长的物理关系

**成片时长 ≈ 旁白字数 ÷ 配音语速。** 画面跟着配音走，配音多长，片子就多长。

| 量 | 取值 | 来源 |
|---|---|---|
| 配音语速 | 约 4.2 字 / 秒（每分钟约 250 字） | 取所选音色的实测值，每个音色各测一次，存进音色配置 |
| 每幕时长 | 约 14 秒（一个画面讲一件事） | 可按风格调整：快节奏风格 8–10 秒，讲解类 15–20 秒 |
| 幕数 | 目标秒数 ÷ 每幕秒数，取 4–40 | 服务端计算 |
| 每幕旁白字数 | 每幕秒数 × 语速 | 服务端计算，写进给模型的分镜要求 |

**服务端校验（不交给模型自觉）**：

1. 写完分镜脚本后，按「旁白字数 ÷ 语速」算总时长，必须落在目标的 ±15%。不够就让模型补写不足的幕，超出就压缩，最多两轮；两轮后仍不达标，照实告诉用户差多少。
2. 配音生成后以实际音频时长为准，画面时间轴跟着音频走，不靠调快、调慢语速凑时长。
3. 成片完成后在任务里记下目标时长与实际时长，用来校准语速和每幕时长。

**「自动」怎么定**（服务端给出，前端只显示）：

- 有稿件：全文照念的时长 × 0.35，落到 1 / 3 / 5 分钟三档中最近的一档。例：1,840 字的稿件全文照念约 7 分钟，自动取约 3 分钟。
- 没有稿件（只靠对话）：约 1 分钟。
- 培训、教程类内容：对话里先问一次「想要多长」，并说出自动的估算值。

**用户在哪些环节定长短**（越早越便宜）：

| 环节 | 用户看到什么 | 能做什么 |
|---|---|---|
| 开工前，输入框 | 「时长 · 风格」按钮上写「3 分钟 · 视觉笔记」；面板顶部写「自动 · 约 3 分钟」和依据 | 选约 1 / 3 / 5 / 10 分钟 |
| 对话起稿 | 创作简报里的「时长」；教程类会被问一次 | 说「5 分钟」「长一点」 |
| 分镜脚本（开工前一两分钟） | 每幕秒数，合计与目标 | 「短一点 / 长一点」重写这一版，不花生成的钱 |
| 生成中与完成后 | 任务里写目标；完成卡写实际时长与目标 | 不满意再做一次（从脚本开始） |

**生成耗时随时长变化**：预计耗时下限约 20 + 5 × 分钟数，上限约 30 + 8 × 分钟数（约 3 分钟的片子是 35–54 分钟）。整条超时取「2 小时」与「预计上限的 2 倍」中较大的一个。实现后改用同风格、同时长的历史中位数。

**接口**：`POST /api/quick-creation/estimate`，输入产出、资料编号与时长选择，返回目标秒数、自动秒数、全文照念秒数、幕数、预计耗时与一句依据（见 `QcEstimate`）。创建任务与出分镜脚本都带上 `duration`；脚本接口支持 `adjust: shorter | longer`。

## 三、为什么能在用户浏览器里渲染

**物理上可行的前提**：Lemo-Opuscar 的风格本来就是 Canvas 和 WebGL 页面逐帧画出来的。每一帧就是画布上的像素，可以直接交给浏览器的硬件编码器。如果画面是任意的 HTML 和 CSS，浏览器没有办法把它逐帧变成像素（只能截图，且只支持部分 CSS），这条路就走不通。所以**画面代码必须是 Canvas / WebGL**，这是本方案的硬约束。

**省了什么**：

| | 服务器渲染（现在的默认做法） | 浏览器渲染（本方案） |
|---|---|---|
| 服务器 CPU | 每支片子要逐帧截图再编码：3 分钟、24 帧 / 秒就是 4,320 帧，单核要跑几分钟到十几分钟 | 不渲染视频。服务器只做写代码（模型调用）、配音、打包 |
| 观看带宽 | 每次观看下载视频文件：1080p 约每分钟 30–60 MB，3 分钟约 90–180 MB | 下载画面代码约 300 KB + 配音约每分钟 1 MB，3 分钟约 3 MB |
| 发布到网页托管 | 上传并存视频文件 | 发布的就是这个能播放的网页，不传视频 |
| 要视频文件时 | 已经有了 | 用户点「导出」，在自己浏览器里合成，文件留在本机 |

服务器上的 30–60 分钟主要花在智能体写画面代码上，不在渲染；去掉渲染后，这段时间不变，但服务器不再为每支片子付出渲染的 CPU 和存储。

**仓库的历史也支持这个方向**：2026-04 之前 prd-api 用过服务端 Remotion 渲染，在只读容器里跑无头 Chromium 修了好几轮（PR #481、#483），之后整条路径被删掉。

## 四、推荐的框架

**首选：自有的轻量播放运行时 + WebCodecs 编码 + Mediabunny 封装。**

- **画面**：风格说明决定用 Canvas 2D、WebGL 或 three.js，统一包成一个模块，导出 `prepare()` 和 `renderFrame(ctx, t)`。
- **编码**：浏览器自带的 WebCodecs（`VideoEncoder`），优先 H.264；浏览器编不了 H.264 时退到 VP9。
- **封装**：[Mediabunny](https://mediabunny.dev/)，MPL-2.0 许可，可用于闭源商业产品，只要求保留源文件里的许可声明。它支持 MP4 与 WebM，把画布帧和已编码的音频包写进文件，是旧 mp4-muxer 的接替者。
- **理由**：风格本来就是 Canvas / WebGL，不需要再套一层框架；没有许可费；没有 CSS 子集的限制。

**备选：Remotion（Player + `@remotion/web-renderer`）**，适合想用 React 写场景的情况。它已支持在浏览器里导出 MP4（底层同样是 WebCodecs + Mediabunny），但要注意：

- 公司达到一定人数需要购买公司许可，费用以 Remotion 官网为准，接入前要确认；
- 浏览器端渲染只支持部分 CSS，官方列出的不支持项包括 z-index、writing-mode、object-position；`<Html5Video>` 要换成 `@remotion/media` 的组件；
- 导出在当前标签页里跑，会占住页面。

**不推荐作为默认**：

- 服务端无头浏览器截图 + ffmpeg：CPU、内存、带宽都在我们这边，而且仓库已经踩过容器里跑 Chromium 的坑。只作「请服务器导出」的兜底。
- `MediaRecorder` + `canvas.captureStream()`：只能实时录，帧率不稳，页面在后台会停。只在 WebCodecs 不可用、又必须在本机导出时考虑。

## 五、画面代码的契约（播放和导出用同一份）

1. **同一个 t 永远画同一帧**：画面只由时间 t 决定。不许用 `Date.now()`、`performance.now()`、不带种子的随机数，也不许靠 `requestAnimationFrame` 的节奏推进动画。
2. **先准备，再画**：字体、图片在 `prepare()` 里加载完，返回 Promise。中文字体由服务端按片子里实际用到的字做子集，避免下载几 MB 的整套字体。
3. **固定画布**：1920 × 1080、24 帧 / 秒（与 Lemo-Opuscar 的默认一致），与屏幕像素密度无关。
4. **播放**：t 取配音的 `currentTime`，画面跟着声音走。
5. **导出**：第 i 帧 t = i / 24，离线逐帧画，不受屏幕刷新率影响；所见即所得。
6. **隔离**：画面代码是模型写的，按不可信代码对待。放在 Worker（OffscreenCanvas）或 `sandbox="allow-scripts"` 的 iframe 里运行，不给网络与存储权限，用 ImageBitmap 把帧交给导出器。
7. **服务端检查**：静态扫描上面禁止的写法，再抽 3 帧在隔离环境里试画，确认不报错；不整片渲染。

## 六、浏览器导出的步骤（实现 `browserExport.ts`）

1. 取成片包：画面代码模块、配音音轨、时间轴（`QcPlayBundle`）。
2. **声音不在浏览器里编码**：配音是服务端生成的，服务端顺手编成 AAC（m4a）和 Opus（webm）各一份。导出时把已编码的音频包直接写进文件，不需要浏览器有音频编码器。这样 Safari 16.4 起就能导出（Safari 的音频编码器到 26 才有），也避开 Firefox 编不了 AAC 的问题。
3. **画面**：在 Worker 里用 OffscreenCanvas 逐帧画，`new VideoFrame(canvas, { timestamp })` 交给编码器，帧用完立即 `close()`；编码队列超过约 30 帧就等一等，防止内存涨满。
4. **封装**：Mediabunny 输出 MP4（H.264 + AAC）或 WebM（VP9 + Opus），得到 Blob 后生成下载。
5. **进度与取消**：每 24 帧回报一次（第几帧、已用、还需）；可以取消；失败时说清是编码器不支持、内存不足，还是第几帧画面代码出错。
6. **后台**：渲染循环不用 `requestAnimationFrame`，页面切到后台也能继续；仍提示用户保持页面在前台，因为浏览器会降低后台页面的速度。

**速度预估**：桌面浏览器的硬件编码通常比实时快，按约 2 倍速估（3 分钟的片子约 1.5 分钟导完）；手机按 1 倍速估，并提示会发热。画面复杂的 WebGL 风格可能慢于实时，实现后按风格实测校准。

## 七、哪些浏览器能导出

先用 `VideoEncoder.isConfigSupported()` 按编码逐个试，不按浏览器版本判断。

| 浏览器 | 能否本机导出 | 说明 |
|---|---|---|
| Chrome、Edge 94 起（桌面与安卓） | 能 | H.264 + MP4 |
| Safari 16.4 起（Mac、iPhone、iPad） | 能 | 画面编码可用；声音用服务端编好的 AAC |
| Firefox 130 起（桌面） | 能 | 编不了 H.264 时退到 VP9 + WebM |
| 安卓 Firefox | 不能 | 没有 WebCodecs，走兜底 |
| 不带专有编码的 Chromium（部分 Linux 发行版） | 通常能 | 退到 VP9 + WebM |

**兜底**：本机不能合成时，页面说清原因，并给两条路：用电脑上的 Chrome、Edge 或 Safari 打开同一页导出；或者「请服务器导出」，排队执行，完成后通知。服务器导出是唯一还要服务器渲染的地方，应当很少用到；实现后统计它的占比，超过 10% 就要回头看原因。

## 八、怎么验收（对应《目标与验收.md》）

| 编号 | 验什么 | 通过标准 |
|---|---|---|
| A-55 | 开工前能看到并定时长 | 放入示例稿件后显示「自动 · 约 3 分钟」和依据；改成约 10 分钟后，任务里写「约 10 分钟」 |
| A-56 | 脚本按目标写，能改长短 | 脚本合计时长在目标 ±15%；「长一点」后目标变成下一档，幕数相应增加 |
| A-57 | 浏览器播放与导出 | 播放不下载视频文件；导出显示帧数进度，可取消，完成后可下载；发布不传视频文件 |
| A-58 | 浏览器不支持时有兜底 | 没有 WebCodecs 时说明原因，给「换浏览器」和「请服务器导出」 |

还需要真实环境证明的（记在验收债务）：

- **D-06 真实时长**：3 份不同长度的稿件 × 4 档时长，实际成片时长都落在目标 ±15%。
- **D-07 导出速度与兼容**：一台常见办公笔记本上的 Chrome 导出 3 分钟成片不超过 3 分钟；Safari 16.4 能导出带声音的 MP4；安卓 Firefox 出现兜底。

## 九、风险与取舍

| 风险 | 影响 | 处理 |
|---|---|---|
| 画面代码写得不确定（用了当前时间或随机数） | 播放和导出出来的不一样 | 契约第 1 条 + 服务端静态扫描与抽帧检查 |
| 手机导出发热、慢 | 用户等得久 | 手机按 1 倍速预估并提示；推荐在电脑上导出 |
| 模型写的代码在用户浏览器里运行 | 安全 | 隔离运行，不给网络与存储权限 |
| 长片（10 分钟以上）导出占内存 | 浏览器崩溃 | 编码队列限流、帧及时释放、分段写入 |
| 选 Remotion 的许可费 | 成本 | 首选方案不依赖 Remotion |
