# 用户可理解错误规则

本规则约束所有会进入普通用户界面的 API、SSE、任务记录、toast、弹窗和页面错误文案。

触发范围：`**/*.{cs,ts,tsx}`。

## 核心原则

普通用户看到的错误必须回答两个问题：发生了什么，接下来能做什么。内部诊断信息必须留在服务端日志、调用日志或仅管理员可见的诊断详情中。

## 强制约束

1. 禁止向普通用户透传上游响应原文、异常 `Message`、堆栈、SDK 错误或数据库错误。
2. 禁止在用户文案中出现 HTTP 状态、token、Provider 名、内部模型名、端点、字段名、请求体、类名或英文协议错误。
3. API 错误必须分层：稳定错误码供程序判断，中文用户文案供界面展示，原始诊断写日志并关联 requestId、traceId 或 runId。
4. 用户文案必须包含明确结果和恢复动作，例如“图片生成等待超时，请稍后重试”，不得只写“调用失败”“未知错误”或原始错误。
5. 可预期错误至少归入：输入不完整、能力不支持、服务不可用、请求过多、等待超时、内容安全、权限不足、未知故障。
6. 当系统持有备用 Provider 或 Offering 时，能力不匹配、模型不存在、端点不可用和服务异常应先自动切换；全部失败后再返回用户文案。
7. 管理员诊断详情也必须脱敏，禁止记录密钥、签名 URL、完整授权头或用户隐私内容。
8. 每次新增外部服务调用必须补失败态测试，至少断言错误码稳定、文案包含恢复动作、原始诊断关键词未泄漏。
9. 前端不得把 `error.response`、`error.message` 或任意未知对象直接字符串化后展示；必须通过统一错误映射入口。
10. 反复出现过的上游错误必须补回归测试和明确分类，禁止只为单条错误替换文案。

## 标准返回结构

```text
code: 稳定、可枚举的机器错误码
message: 中文、简短、包含恢复动作的用户文案
traceId/requestId/runId: 可选的问题定位编号
rawDiagnostic: 仅服务端日志或管理员诊断详情，禁止进入普通用户响应
```

## 生图示例

错误：上游把合法多图请求误判为空输入。

- 系统行为：先切换同一逻辑模型的下一 Offering。
- 用户文案：当前生图模型暂时无法处理这组参考图，请更换模型或减少参考图后重试。
- 日志内容：保留上游状态、原始错误、模型 Offering 和 runId，供管理员定位。
