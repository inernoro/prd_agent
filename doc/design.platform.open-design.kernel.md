# OpenDesign 内核与能力边界

> **版本**：v1.0 | **日期**：2026-09-14 | **状态**：已落地

**一句话**：OpenDesign（无头设计编排器）自己不写作品也不调模型，它给的是设计法则、版式档位与流程编排，外加一张把二十八种外部命令行助手声明成数据的注册表，真正动手的是另装的那个助手。
**谁该读**：判断这套东西值不值得接、接到什么程度的人；以及想知道它能不能反哺自家 Agent 编排的人。
**读完能做什么**：说清它的内核是什么、边界在哪、为什么说它不含 Codex、以及有哪三样东西值得搬回自家运行时。

---

## 一、管理摘要

把它想成一个**设计总监**：他自己不画图，但他手里有一套审美规矩（字阶、配色、可达性、反 AI 味）、一柜子成品风格档案，以及一本通讯录，上面记着二十八个外包画师怎么联系、怎么确认在不在、会哪几种手法。活来了，他拆任务、定风格、写要求，然后照通讯录打电话叫人干活，干完他验收。

所以四个结论：

1. **它是编排层，不是生产层。** 内容由被它调用的助手产出，它产出的是「该怎么做」的约束与顺序。
2. **它不含任何助手。** 通讯录里记的是「这个助手的命令叫什么、怎么探测、会哪些模型」，助手本身要你自己装。这就是「不包含 Claude Code、Codex」的准确含义。
3. **接入成本低、替换成本也低。** 它与助手之间只有命令行这一层契约，换助手等于换一条通讯录记录。
4. **有三样东西值得搬回自家运行时**，见第五节。

## 二、它的内核由什么构成

| 组成 | 是什么 | 对我们意味着什么 |
|---|---|---|
| 常驻服务 | 一个 Node 守护进程，另带一套自用网页界面 | 我们只用守护进程那一半，界面可以不露出 |
| 设计法则库 | 十余篇成文的硬规矩：字阶层级、配色、动效克制、可达性基线、状态覆盖、双向文字、表单校验，还有一篇专门讲怎么避开「一眼 AI 味」 | 这是它最难复制的部分，也是「效果优先」诉求真正的着力点 |
| 风格档案库 | 数十套成品设计系统预设（苹果、蚂蚁、Airbnb、Arc、艺术风等） | 让产出不是千篇一律，用户可指定风格 |
| 任务包 | 几十个按场景打包的技能，例如网页原型、品牌提取、杂志排版、广告创意、图像与视频模板 | 我们当前只用到网页原型那一个；其余是后续场景的现成砖块 |
| 提示词模板 | 按图像、视频两类分目录的模板 | 说明它的目标形态不止网页 |
| 运行时注册表 | 二十八份助手声明 | 见下节，这是理解它的关键 |

## 三、为什么说「它不包含 Codex」

注册表里每一份助手声明，本质上只是一小段**数据**，说清四件事：

- 这个助手的可执行命令叫什么名字；
- 用哪几个参数去问它「你在不在、装的什么版本」；
- 用哪几个参数去问它「登录了没有」；
- 它会哪些模型，以及有没有速度档位之类的可选项。

真正干活的时候，它拼一条命令行把助手当子进程拉起来，用一个参数把本次工作区目录交过去，再要求助手用结构化流把过程吐回来。

**于是三件事同时成立**：

1. 镜像里没有助手，助手得另装——这正是我们在镜像里额外装 Codex 的原因。
2. 文件不需要在两者之间传输，因为它们**看的是同一个工作区目录**。这与我们「不建双向同步系统」的诉求天然吻合。
3. 换助手的成本极低，因为契约只有命令行这一层。

反过来也划出了它的能力边界：**助手能力的天花板就是它的天花板**。助手写不出好网页，它的设计法则也救不回来；它能做的是把要求说清楚、把风格钉死、把过程管住。

## 四、它与我们四个场景的适配度

| 我们要的 | 它现成提供 | 我们仍要自建 |
|---|---|---|
| 生成完整网页（含样式、脚本、图片、字体） | 网页原型任务包，自带模板、版式参考与自检清单 | 产物完整性校验、冻结成版本、预览发布回退 |
| 按知识库内容生成 | 无。它不认识我们的知识库 | 把知识快照装进工作区，并冻结来源与版本 |
| 模型由我们派发 | 支持按次指定模型与接口地址 | 由我们统一签发短期凭据并记审计 |
| 演示文稿 | 有排版类任务包可复用 | 页面形态与来源留痕仍要我们定 |
| 局部修改只动被点名处 | 助手本身支持指定范围 | 基于历史版本开工作副本、逐字节核对未点名文件 |

结论：**它替我们省掉的是「怎么设计得好看」，替不掉的是「怎么把知识、版本、权限、审计管起来」**。这与把它定位成可替换的无头能力、而不是新业务主系统，是一致的。

## 五、值得搬回自家运行时的三样

1. **运行时定义即数据。** 新增一种助手，只加一份声明，不碰编排层。我们的运行时注册表目前是硬编码的五项，且只描述「能不能用」，不描述「怎么探测、怎么列模型、怎么拼命令」。把后三样也纳入声明，新增执行器就不必再改编排代码。

2. **探测与鉴权分成两问。** 它对每个助手分别问「装没装」和「登录没登录」，两个问题的失败要给不同的话。我们当前把二者混在一次能力判定里，用户看到的理由因此不够具体。

3. **设计法则成文且可被引用。** 把审美要求写成可检索的成文规矩，而不是塞进一段长提示词。这一条对我们的「效果要对标成熟产品」诉求直接有用——评分标准可以直接引用同一批法则，评分者与生成者对齐同一套判据。

## 六、风险与已知边界

- **上游更新速度快**：设计法则与风格档案会持续增补。我们锁固定版本可控，但要有意识地定期评估升级，否则效果优势会随时间流失。
- **助手版本耦合**：我们在镜像里装的助手版本与运行时探测要求必须一致，否则会话在每个节点都判不可用。这条已经踩过一次，现在有守卫盯着。
- **它的界面我们不露出**：意味着它的交互能力（阶段展示、即时预览）我们享受不到，得自己在入口侧做。这是「等待时屏幕必须一直有变化」那条诉求的主要工作量所在。
