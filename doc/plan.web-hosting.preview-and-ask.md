## 二、为什么要拆（这一节是本文档存在的主要理由）

原 PR #1351 一条 PR 装了三件事：54 个文件、+5733/−84 行、15 轮 review、44 条意见。拆分不是因为「文件太多」，是因为下面四件事同时成立。

### 1. 评审面太大，收敛不了

到第十四、十五轮，review 抓出来的仍然是**第一版就写错的东西**（srcDoc 判据漏掉不带引号的 `type=module`、错误文案把网关原始错误透给匿名访客）。这说明评审者每一轮都在这个 diff 里发现新的一块，而不是在收尾。一条 PR 的评审面超过评审者一次能装下的量，轮数就不会收敛——只会一直发现新东西。

### 2. 我的修复在生产新缺陷

第 5、6、7、11、12、13 轮的意见，都能追溯到我上一轮的修改：

- 第 6 轮我引入了一个 `SemaphoreSlim` 却没 `Release()`，整个提问链路第二个 SSE 事件起永久卡死——而 **CI 全绿**，因为当时没有任何东西真的写过 SSE。
- 第 11 轮我把「不支持的形态」两个方向一起灰掉，造出一个 owner 想关都关不掉的死状态。
- 第 12 轮我修了一处体积上限，漏了 PDF 那条兄弟分支。

修复速度超过验证速度时，PR 越修越不安全。拆小之后每条线的改动量回到「能被一次评审装下」的规模。

### 3. 三件事的验收方式完全不同，捆在一起谁也验不了

| 线 | 怎样才算验过 |
|---|---|
| A 预览修复 | 打开三个原本白屏的页面，看到内容 |
| B 向我提问 | 有人真的问一句、看到答案流出来 |
| C 检索底座 | **现在验不了**，缺供应商 key |

C 永远验不了，但它捆着 A 和 B 一起等，等于让「能验的」陪「不能验的」一起卡着。

### 4. 三件事的风险等级差三个数量级

- A：纯修复，改的是判据，最坏情况是回到原来的坏行为。
- B：新功能，**会花钱**（每次提问烧模型 token），且有匿名访问面。
- C：目前没有任何调用方，合进去是惰性代码，唯一的实际效果是「embedding 拿不到专属池时失败关闭」——这条本身就有独立的安全价值（防止拿 chat 模型算出垃圾向量写进库）。

把风险最高的和风险最低的绑在一张审批票上，只会让低风险的那份跟着一起被卡。

## 三、固定回合收敛规则（防止再次无限延伸）

每个 PR 从提出之日起，**最多两轮 review 修复**。第二轮结束后：

1. 仍未解决的意见，**一律记进对应 `debt.*` 台账**，不在当前 PR 展开。
2. PR 直接进入「合并或关闭」二选一，不再开第三轮。

只有以下三类意见可以**阻塞合并**，其余全部记账：

| 可阻塞 | 判据 |
|---|---|
| CI 红 | 编译失败、测试失败、守卫失败 |
| 新增面上的安全问题 | 本 PR 新加的端点/入口引入的越权、注入、无界资源分配 |
| 功能根本不工作 | 本 PR 声称做到的那件事，实测做不到 |

不可阻塞的（一律记账）：性能优化建议、扩展到本 PR 目标之外的语义、既有代码的问题、「如果将来 X 就会 Y」的推测性变体、措辞与同义词。

**触发熔断立即停手的信号**（任一命中）：

- 连续两轮 review 仍在产生**新的语义类别**（不是同一问题的细化）
- 单个 PR 的 review 修复提交达到 **6 个**
- diff 超出首轮基线的 1.5 倍，或改到首轮清单之外的文件

熔断后不再追加修复，把剩下的写进债务、合并或关闭。

这套规则是对 `AGENTS.md §5.5`「Review 范围熔断」的收紧：那里的阈值是 8 个修复提交 / 3 轮 / 2 倍 diff，#1351 走到 15 轮 44 条时**一次都没有数值触发**——因为每一条单看都成立、每一次修改都不大。所以这里把阈值压到大约一半，并且加一条不看数值的硬闸：**两轮为限**。

## 四、三条线各自的目标与不变量（范围基线）

### PR-A 预览修复

**目标**：托管站点的三处预览（卡片缩略图、站内大预览、分享页）不再因为「load 事件迟迟不来」而显示为失败或空白。

**不变量**：托管内容与主站的跨域隔离不得削弱（srcDoc 路径始终不给 `allow-same-origin`）。

**明确不做**：不改上传通道、不改分享权限模型、不动评论。

**首轮基线**：11 个文件。

### PR-B 向我提问

**目标**：访客在托管页面右下角提问，模型只依据该页正文回答。

**不变量**：`AskEnabled` 默认 `false`（存量站点反序列化不得被顺带打开）；所有门禁判定必须在写出第一个 SSE 字节之前完成。

**明确不做**：不接知识库（那是三期）、合集分享不暴露提问入口。

**首轮基线**：约 30 个文件。

### PR-C 检索底座

**目标**：把网关的 embedding 通路接上，并让「专属池不可用时失败关闭」覆盖 embedding。

**不变量**：向量必须带着算它的模型标识一起存；跨模型同维度判为不兼容。

**明确不做**：建索引 Worker、检索服务、引用注入、前端挂库——全部等 key。

**首轮基线**：17 个文件。

## 五、已知边界（交付时就承认的）

- **用户最初报的那三个打不开的页面，我从未验证过修好了。** 它们不在我能访问的这套部署里。A 修的是从代码与线上响应头直接读出来的两条根因，与具体站点无关；但「那三个页面现在能打开了」这句话我没有证据。
- **B 从未被任何人用浏览器点开过。** 我的沙箱 Chromium 没有出网能力，Playwright 连 `example.com` 都打不开。B 在 #1351 期间出过一个「设置抽屉被预览弹窗完全遮住、功能根本打不开」的 z-index 缺陷——那是一次点击就能发现的问题，它的存在本身就说明这条线缺真人验收。
- 其余逐条欠账记在[网页托管债务台账](./debt.web-hosting.md)；向量供应商的选型结论随 PR-C 一起落台账。
