# 同批运行容器恢复

适用于部署曾失败、保留入口与当前候选不一致，但整批当前容器已经创建且需要重新核验的分支。恢复不会重建数据库、删除旧容器、执行初始化脚本或修改历史部署运行的结论。

`POST /api/branches/:id/recover-runtime` 接收 `expectedCommitSha`（40 位）和 `expectedContainers`（本分支全部服务 ID 到完整容器 ID 的映射）。客户端先读取分支快照，再提交同一快照；范围、提交或任意容器改变即拒绝。只允许调用者有权限的本地分支，远端执行器不能从控制面代为恢复。

恢复按分支写操作租约执行：核对全部当前容器的项目、分支、服务标签和完整 ID；将当前容器接到同一张新分支网络；只摘除这些容器自己的旧分支网，保留共享基础设施网络和历史容器；原地重启项目声明的应用以刷新连接，分支额外数据库、缓存和存储不重启；最后按每个服务的就绪或启动信号契约验证。全部通过并持久化成功后才切换入口。数据库内容与历史失败运行保持原状。

SSE `progress` 给出当前阶段，`complete` 返回网络与服务清单，`error` 返回首个失败原因。传输中断不代表服务端未受理；先核对该分支操作与容器状态，禁止重复提交。恢复中的新操作会使旧租约失效，执行槽在命令启动前重新核验租约。

任何未就绪、身份不符或落盘失败都不能宣布恢复通过。网络接续或应用重启失败后，已发生的连接变更会保留以便诊断，入口指针不发布为成功；恢复不是跨整个环境的网络事务。复测须保留首试失败，并从同一身份快照的实际状态重新检查。

验收仍需访问最终公网 HTML、实际入口资源和业务页面，完成真实命令、结果回查、负向与恢复流程。容器就绪不能替代业务验收。
