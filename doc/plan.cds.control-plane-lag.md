# CDS 控制面卡顿治理 · 计划

> **版本**：v1.0 | **日期**：2026-10-08 | **状态**：进行中

**一句话**：CDS 页面卡顿的主要嫌疑是 master 单线程里「每次都把整份数据重做一遍」的同步工作，宿主过载与构建排队是另一条并行的病；本计划把两条病拆开治，先统一线上代码版本、先量清楚，再按数据动手。
**谁该读**：CDS 平台负责人、运维，以及 mdimp / miduo-backend 的部署负责人。

## 为什么做

用户反馈「很卡顿」，同一问题此前优化过多轮。2026-10-08 的回溯报告与代码核对得出三条判断：

1. **卡顿与宿主负载不同步。** 09-15 宿主 5 分钟负载 71 时，控制面事件循环 p99 为 380ms；10-08 负载只有 25–31，p99 却到了 2.9 秒。按 CPU 权重计算（控制面 1000、容器 100），控制面在争抢时仍能分到数核，单线程不该被饿到秒级。秒级停顿的形状是「一段同步代码一口气跑了几秒」。
2. **前几轮治的是另一条病。** 历次优化处理的是「争抢时谁优先、队列别堵死」（权重、并发闸、审计熔断、webhook 降噪），它们都生效了；但事件循环 p99 从 09-09 起一直没达标，而「瓶颈在 master 进程内部」这批工作一直没开始。
3. **线上跑的不是 main。** 线上产物来自一条从未合回 main 的分支，修复只存在于运行产物里；控制面又被所有 Agent 共用，任何人自更新都会把它切到自己的分支。修了的东西不一定在跑，量到的数字也不一定是自己的代码。

## 两条病与两条线

| 病 | 症状 | 归谁治 |
|---|---|---|
| master 主线程整份重做 | 页面接口秒级、实时状态迟滞 | CDS 线 |
| 构建需求超过宿主容量 | 排队几十个服务任务、部署一等就是小时级 | CDS 线（闸门与硬顶）+ mdimp 线（减需求） |

**顺序约束**：CDS 第 0、1 步先上线并留一到两个工作日基线，mdimp 的改动再上。反过来的话，mdimp 一减量，主线程的热点就抓不到了——问题被藏起来不等于治好了。两条线的上线至少错开一个完整工作日，否则改善分不清是谁的功劳。

## 各步骤要点

### 第 0 步 · 统一版本

把线上运行产物所在的分支合回来，作为所有后续治理的同一个基线。合并时有意不带入两类东西：main 已经删掉且有测试断言其不存在的前端组件，以及内容已汇总进总更新记录的旧更新碎片。

### 第 1 步 · 先量清楚（只读，不改任何行为）

| 量什么 | 回答的问题 |
|---|---|
| 事件循环被卡时间占比 | 一分钟里主线程有几秒被占着（p99 只说明最慢的 1% 有多慢） |
| 已知同步工作的分段耗时 | 状态快照克隆、逐实体序列化、分支列表计算、分支事件推送、探活历史落盘、同步 git，各花了多少 |
| 卡顿归因 | 每次 ≥200ms 的卡顿里，哪几段工作恰好在那段时间里结束；对不上的部分记为「未标注」 |
| GC | 每分钟暂停多久、最长一次多久 |
| SSE 长连接 | 当前多少条，预览页挂件占多少条、不限项目的占多少条，每分钟写出多少字节 |
| CPU 采样（按需） | 「未标注」过半时，热点到底在哪个函数 |

判据：能回答「部署高峰的一分钟里，主线程有多少秒在干什么」，排名前五的工作能解释八成以上的被卡时间。

### 第 2 步 · 主线程只做变化的那份（候选，按第 1 步排名取舍）

- 状态落盘：构建输出不再逐行进状态；高频调用点声明改动范围，热路径新增「整份重做」由守卫拦下。
- 分支事件推送：一个事件只序列化一次，所有连接共用；预览页挂件只订阅自己所在的分支，连上时不再收全量快照。
- 其他同步块：分支列表的全量扫描每次请求只做一次；探活历史增量写盘；同步 git 改异步。
- 前端不放大：请求有超时，过载响应不立即重发；轮询统一为「上一轮回来再发下一轮、隐藏页暂停、慢了退避」。

### 第 3 步 · 构建闸门拆成两段

编译名额只覆盖真正吃 CPU 的阶段；等待就绪改用独立的启动名额。过载判据从「一分钟负载」改为 CPU 压力加可用内存，并保留一个最低放行名额；单项目占用编译名额设上限；预构建失败默认不再悄悄回退到宿主编译。

### 第 4 步 · 资源总量硬顶（待拍板）

给托管容器的低权重组设总 CPU 配额，把组外容器逐个迁入；CDS 自更新的构建改到独立低权重单元。

### mdimp 线

- **A 切极速版**：项目级切到 CI 预构建，并把存量分支迁过去（CDS 现在只在建分支时复制项目默认模式）。
- **B 前端运行时配置**：三个前端改为容器启动时注入分支级地址，使静态包也能预构建，不再常驻开发服务器。
- **C 降就绪超时**：极速版启动快，就绪超时从 1200–1800 秒降到 300 秒左右。
- **D 修启动失败**：迁移失败等项目侧根因，由项目负责人处理。

## 验收标准

同一把尺子：控制面度量脚本输出改前改后两张表。每一步都带开关，关掉后指标回到原样、打开后改善，才算这一步的功劳。压测在独立 docker 宿主上用「占 CPU 的假服务」回放 10-08 的形状（8 个部署共 31 个服务任务 + 100 条挂件长连接），不压线上。

| 验收对象 | 合格线 | 怎么量 |
|---|---|---|
| 版本一致 | 线上运行的提交、前端产物的提交与 main 的某个提交三者相同，产物未过期 | 自检状态接口 |
| 主线程 | 部署高峰连续 30 分钟：事件循环 p99 < 200ms、最大 < 1 秒；每分钟被卡时间 < 5%；单次 GC < 200ms | 主线程诊断，每分钟一次 |
| 状态落盘 | 单次全量快照 < 100ms，或全量快照不超过每 10 秒一次；状态体积降到基线三分之一以下 | 分段计时 |
| SSE | 100 条挂件连接 + 部署风暴下事件循环 p99 仍 < 200ms；每条挂件连接收到的字节下降九成以上 | 压测环境 |
| 只读接口 | 分支列表服务端计算 p95 < 150ms，含排队 p95 < 500ms | 接口计时与访问日志对照 |
| 页面可操作 | 已登录真实账号（成员与所有者各一）走「项目列表 → 分支页 → 详情 → 部署页签」：首屏 2 秒内出现，交互 200ms 内有反馈；部署高峰时段，双主题截图 | 无头浏览器直连线上域名 |
| 构建闸门 | 过载时等待就绪的服务占用编译名额为 0；最老等待有上界；单项目不超上限；离队原因分开计数 | 闸门状态接口 + 回归测试 |
| mdimp 极速版 | 已切换分支的宿主上 Maven / 前端开发服务器进程为 0；单分支部署时长与占槽分钟数下降 | 运行模式、进程与镜像提交交叉核对 |
| 复测 | 上线后 48 小时与一周各复测一次，写进性能债务台账 | 度量脚本 |

## 已知边界

- 卡顿归因只认得已埋点的工作；「未标注」高时需要按需 CPU 采样补齐，采样本身会给主线程增加少量开销，只在定案时手动触发。
- 被卡时间由事件循环直方图推算，空闲时有约 1–2% 的计时抖动底噪。
- SSE 计数从本版本上线起才有；升级前建立的连接不在计数里，重连后才会被计入。
- 控制面度量脚本没有接入任何流水线，只有本地自检。
- 自更新的确认与最小间隔、第 4 步的资源硬顶，都需要负责人决定后再做。
