**一句话**：在已有规则、产品管理和验收能力之上补上决策理由、替代关系与适用范围，从一个业务领域验证后再推广。

## 1. 结论与证据范围

本项目已经具备原则、规则、设计、术语、需求追溯、状态流转和验收基础。优先补足的是它们之间的关联：**为什么这么选、当前哪条有效、变化对谁生效、如何证明落实。**

本指南以业务提交 `fc26e26c6` 的文档、关键实体、处理路径和已完成的聚焦运行证据为依据，未对所有业务流程做运行验收。“未发现”限定于所检查的入口，不能据此断言全系统不存在相关能力；文档漂移也不能直接等同于线上故障。本分支结果不表示主分支已合入或生产已发布。

文档类型已按用户指令接入，技术与产品提议不因此自动接受。顶层方法见[ADR 原则][adr-principles]与 [PDR 原则](../pri.pdr.md)；未落实的治理边界登记在[平台债务台账](./debt.platform.md#决策治理2026-11-06)。

已有结果包括[一页产品结构](./design.product-agent.md#首个试点的一页产品结构)、[冲突与关闭条件](./debt.product-agent.md#产品结构与决策治理2026-11-06)、[正式申领变化与业务实例](./spec.product-agent.version-claims.md)。关联填写漏发和需求版本引用越界已修复；组件、隔离数据库和公网需求排期路径已有证据，未修改既有业务对象。完整正式申领公网路径及其他联动的边界仍保留。

### 3.3 一次变更的闭环

1. 找到该业务范围的现行规则与相关决策，确认它们适用于本次版本和用户群。
2. 区分“既有决策内的实现调整”和“改变重要取舍”；只有后者建立新记录。
3. 将事实、假设、候选方案、代价和适用边界写清，由现行决策机制完成审查与选择。
4. 新选择被接受后，维护替代链接，更新现行规格，并登记尚未迁移的遗留项。
5. 变更描述引用受影响决策；测试验证业务行为，发布证据证明实际生效版本。
6. 到重议条件或观察节点时检查结果：继续沿用、补证据，或提出新的替代记录。

评审允许异步完成；小团队可以由已有授权的负责人直接决策并留下依据。这里不另设审批层级，也不要求每个代码修改都新增记录。

## 4. 为什么产品领域适用，但仅靠 ADR 不够

架构选择通常关注结构与质量属性；产品选择还必须回答用户价值、商业结果、业务规则和适用人群。PDR（本文简称产品决策记录）可复用“背景—选择—后果—历史”的结构，但需要补用户证据、预期结果与验证方式。

产品也有根基和承重结构：用户任务与价值提供根基，领域对象、生命周期、权责与对外承诺形成被多处依赖的结构。本文使用[产品基础结构工作模型](../pri.pdr.md#2-技术有技术栈产品有什么)，不把“产品栈”当成统一行业标准。改变承重约定要识别联动与历史影响，而不是禁止产品变化。

频繁变更本身未必有问题。新的客户证据、法规和市场变化本来就应改变产品。混乱更可能来自：每次改动没有明确归属；同一术语含义不同；新旧规则混用；客户特例扩散成全局行为；只交付功能，没人检查原假设。

建议采用下面的知识链，各环节保留自己的职责：

**用户问题与证据 → 产品选择 → 当前业务规则 → 验收实例 → 上线结果 → 重新评估。**

决策记录保存选择理由，业务模型表达可执行的行为，结果验证决定是否继续投入。大量低风险细节可以直接进业务规则与测试，不必都写 PDR。

## 5. 产品与业务还需要哪些方法

以下是本文补充的方法，不来自附件。优先顺序针对“业务逻辑变化多、项目混乱”的问题，不是完整的产品管理课程。

| 建议顺序与方法 | 解决什么 | 最小产物与用法 | 适用信号与局限 |
| --- | --- | --- | --- |
| 1. 领域建模与统一语言 | 同名不同义、职责归属不清、特例跨模块蔓延 | 一页业务对象与术语表，明确每条规则属于哪个业务范围；同一词可在不同范围有不同定义 | 大家对“完成”“客户”“版本”说的不是同一件事时先做；不意味着必须拆微服务 |
| 2. 决策表与状态机 | 条件组合、例外、角色权限和流转靠长段文字描述 | 条件 → 结果的表格；状态 → 允许动作 → 新状态的表格，明确默认和禁止行为 | 频繁加 if、同一状态能否退款说不清时；仍需验证规则是否有业务价值 |
| 3. 实例化需求与 BDD | 产品、开发、测试各自理解规则，边界反复漏测 | 共同列出正常、边界、拒绝和历史兼容实例；重要实例转成回归用例 | “需求写了但实现不是这个意思”反复出现时；不是把所有中文句子机械翻译成测试 |
| 4. 用户任务分析与机会解法树 | 把客户点名要的功能直接当成真正问题 | 写清用户在什么情境想完成什么；把业务结果、用户机会、候选解法、验证实验连起来 | 功能越堆越多、价值证据不足时；树上的假设仍要访谈或实验验证 |
| 5. 故事地图与小步交付 | 页面和需求列表齐全，用户仍走不通完整流程 | 画用户从起点到产物的活动链，每次交付切出能完成任务的一条路径 | 经常“每个模块都完成但整条业务不能用”时；不能替代细节规则与权限设计 |
| 6. 变更影响分析与规则版本 | 新规则误伤旧订单、旧合同、报表和外部集成 | 变更前列客户、业务对象、历史数据、接口、报表、权限、迁移、测试及恢复影响；说明生效条件 | 已有存量业务、客户差异和跨版本语义时；版本字段本身不会自动解决兼容性 |

对于其他混乱项目，我会先推荐 **统一语言 + 决策表/状态机 + 实例化验收**，让大家先知道业务是什么、规则如何运行；同时对重要取舍使用 PDR。若最大问题是“做了很多却没有用户价值”，则把用户发现与机会解法树提到最前。

## 6. 一个贯通示例：折扣规则变化

以下为虚构的电商场景，仅演示方法，不是本项目的新需求或业务决定。

背景：活动调整折扣，客服担心旧订单价格被改。先确认“订单创建”“支付成功”“活动生效时间”的业务定义，再列方案：所有未支付订单跟随新价；按订单创建时规则保价；或设置明确保价期限。比较客户承诺、促销成本与实现复杂度。

假设团队选定“按创建时规则保价”，一条简短 PDR 应说明：适用哪些活动和渠道、为何接受旧单不能享新价的代价、依据哪些客户证据、谁作出选择、何时复查。此处的选择仅用于举例。

| 当前规则的条件 | 预期结果 |
| --- | --- |
| 订单在新规则生效前创建，之后支付 | 沿用创建时价格与规则版本 |
| 订单在生效时刻或之后创建 | 使用新规则；必须明确时区及边界时刻是否包含 |
| 旧订单取消后重新下单 | 按新订单创建时规则计算；不沿用已取消订单价格 |
| 客户享有独立合同价 | 按明确的合同优先级处理，不默认为一般促销价 |
| 同一订单重复收到支付通知 | 不重复改价或执行优惠；异常按既定支付规则处理 |

落地时将这些实例交给产品、开发与测试共同确认，再转为必要的回归用例。实现是否需要保存价格快照、规则版本和解释记录，由真实审计与复算需求决定。上线后同时观察价格争议、支付转化和优惠成本，不能因为“决策记录已接受”就宣布效果良好。

下一次改变保价方式时，新 PDR 取代旧选择，当前规则更新；仍适用旧规则的订单仍能找到对应版本。这里同时需要**决策历史、现行规则、适用条件和验收实例**，缺少任一项都可能继续混乱。

## 7. 如何推广到其他项目

建议用一个迭代试点，长度随团队节奏确定。以下是建议行动与验收标准，角色是职责建议，尚未任命具体人员。

| 阶段 | 行动 | 责任角色 | 完成标准 |
| --- | --- | --- | --- |
| 开始 | 选一个反复变化的业务领域，梳理一条真实变更及现行规则 | 试点负责人 + 业务专家 | 找得到当前规则、关键术语、影响对象及已有验证证据；未知项明确列出 |
| 第一次变更 | 用顶层模板记录一个重要取舍，按现行机制完成决定 | 决策所有者 + 有权决定的负责人 | 有真实理由、代价和适用范围，未发生的接受或拒绝不预填 |
| 实现与发布 | 更新规则，补正常、边界、负面和历史兼容实例，关联发布证据 | 开发 + 测试 + 产品 | 新规则可验证，存量对象的行为明确；实施状态与实际证据一致 |
| 复查 | 请未参与原讨论的同事回答“现在怎样、为何如此、何时重议” | 试点负责人 | 能独立定位有效规则、解释取舍；找不到的地方先改入口 |
| 扩展 | 比较试点前后收益，再决定是否增加模板字段或自动守卫 | 产品与工程负责人 | 返工或重复讨论有所改善，新增记录成本可接受，再扩到第二个领域 |

可以记录三个基线指标：找出当前有效规则的耗时；因口径或历史适用不清导致的返工次数；每项决策的记录与审查耗时。先观察真实基线再约定目标，不用记录总数或文档字数衡量成效。

其他项目可只带走顶层原则和模板，再结合自己的业务补规则表与实例。不要复制本仓库的目录命名、数据库选择、网关路由、分支策略或审批角色，也不要先采购工具、搭大型决策中心。

## 8. 后续开发应如何排序

**先完成已有试点的证据，再决定软件改造。** 结构、词典、决策表、回放实例及引用与请求修复已有结果；下一步按[问题卡](./pdr.product-agent.002.version-claim-boundary.md#下一次变更问题卡登记完成与交付证据)取得实际使用证据，按实操指南完成独立回放，同时保留[模块清单](./debt.product-agent.md#产品结构与决策治理2026-11-06)中尚未验证的运行场景。随后确认规则历史适用的必要粒度，再考虑结构化关系、查询视图或自动校验。

若试点证明确需产品化，可复用现有产品规则、文档空间、需求关联、活动记录与验收能力。验收至少包括：能从需求找到当前规则和决策；旧选择取代后仍可追溯；接受、实施、生效范围分得清；无证据的历史批准不会被自动补造；原有对象权限继续生效。具体数据与接口改造应作为独立需求设计。

目前已建立原则体系、独立决策类型、结构图、冲突台账、两种业务语境的变化回放、可执行的接手者检查与索引校验，并完成需求流转请求和版本引用的聚焦修复及代表性公网验证。产品规则历史存储、网关行为、业务审批与状态承诺没有借此扩展。治理债务只有在各自对应的运行与价值证据具备后才能关闭。
