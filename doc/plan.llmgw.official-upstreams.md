# 官方上游迁移与管理简化 · 计划

> **版本**：v1.0 | **日期**：2026-11-11 | **状态**：实施中

**一句话**：保留 MAP 的画师、日光及稳定模型标识，把供应方线路迁移到可用的官方上游，并让代理切换和上游清理可见、可操作。
**谁该读**：管理供应方的管理员、视觉与文学创作负责人、发布验收人员。
**读完能做什么**：理解接入与授权边界，按顺序迁移线路，并判断何时可以删除旧上游。

## 用户目标与范围

| 用户问题 | 交付行为 | 不变量 |
|---|---|---|
| apiyi、薇薇安无法删除 | 允许移除停用线路，再统一清理未被线路引用的模型与旧上游 | 不级联删除公开模型或 MAP 昵称；在途任务与最后可用线路必须受保护 |
| 模型列表层层滑动，登记与补登难懂 | 同页搜索与批量接入，模型行直接展示可调用的公开标识 | 用途不明仍需明确处理，不因换文案而放宽校验 |
| 官方与 OpenRouter 同名模型能否接续 | 经规范模型身份匹配后添加线路，保持原公开模型 | 不按任意同名字符串合并不同模型、版本或价格变体 |
| 新上游能否被 MAP 使用 | 接入模型后沿用原公开模型的应用授权；新公开模型仍按业务开放策略选择 | 上游存在不代表模型已接入，模型接入不代表所有应用获权 |
| 列表看不清代理与直连 | 列表显著显示实际连接方式，点击标签直接修改 | 代理不等于一定更快；不把未测线路标成加速成功 |

## 数据与职责

供应方持有地址和加密凭据；物理模型属于供应方；公开模型保持业务身份，下面可以挂多条供应方线路。MAP 只保存业务名称、开放列表、默认项及用户意图，执行线路由 Gateway 负责。视觉创作与文学插图分别核对自己的调用方授权和能力契约。

接入同一个模型的新官方线路，可以接续原业务身份；接入不同模型不能靠复用昵称伪装成同一个模型。官方 API 凭据的可用性必须用真实调用验证，列表接口成功不能替代生成验证。

## 实施顺序

1. 获取最新代码，在隔离分支工作；核对正式运行版本，发布候选必须保留正式环境已有热修。
2. 读取现有画师、日光及其他 apiyi 引用，备份待迁移配置。使用管理员现有官方凭据，不新增或输出密钥。
3. 并行改进列表交互与后端安全清理；两部分合流后统一验证。
4. 接入官方同模型线路，先测试新线路；确认文生图、参考图编辑和文学配图可用，再停用旧线路。
5. 等待在途任务结束，移除停用线路；无引用后清理物理模型和旧池成员，最后删除供应方。
6. 构建与回归通过后发布固定提交，验证公网入口、资源、版本及正式业务；保存截图和回滚证据。

## 验收标准

- 连接标签能直接编辑，取消不改配置；保存后只改变目标代理字段。转接上游并发修改被明确拒绝。
- 同模型第二上游接入后，公开模型身份和 MAP 昵称保持不变；原应用授权保持不变。
- 仍启用的线路不可直接删除；在途任务和缺少替代的业务模型不能被清理成空路由。
- 删除未使用上游会清理其孤立模型、旧池成员及当前组织的同源历史配置副本；重新加载后不会从旧副本复现，不删除其他供应方、公开模型、密钥或业务默认值。
- 调整线路后重新读取网关的实际主备顺序；保存成功但状态读取失败时明确区分两者，不沿用旧顺序判断线路不可用。
- 正式画师、日光通过实际生成与参考图路径；文学配图从真实入口成功回填产物，并能追到官方线路。
- apiyi、薇薇安完成清理后，重新加载配置与业务页面仍可用；缺少官方替代的依赖要明确报告，不能冒险删除。

## 风险与取舍

配置跨集合检查仍有并发窗口，正式迁移必须串行，并在执行前重读状态；不能将条件写入宣传成跨集合事务。安全删除优先于一键强制清空。若官方线路鉴权、额度或能力不满足，保留原可用线路并明确阻塞原因，不以牺牲画师、日光换取清单变短。

测试证据、截图与运行结果归验收记录，不写入长期设计文档；未完成边界记录到对应债务台账。
