### 本周最该注意的三条

**第一条：验收体系整周停摆，最后一份报告停在 08-17。** 部署平台验收中心里 `prd-agent` 项目累计 174 份报告，最新的一份是 08-17 的「缺陷复测 · 视觉创作 / 生图能力兼容修复」——**08-18 到 08-23 六天零新增**，连过去每天雷打不动跑的「每日验收 · 全量变更」也断了。这与上周的问题性质完全不同：上周是「报告很多但都不在验新功能」（覆盖面问题），本周是「根本没有报告」（可观测性问题）。后果很直接：本周落地的基础设施安全加固、备份恢复修复、跨环境数据同步这三件事，**全部只有开发者自己的自证，没有任何独立结论**。而这三件恰恰是出错代价最高的一类——它们动的是数据本身。**必须先查清巡检为什么停，再谈通过率。**

**第二条：备份链条上一周之内暴露出七处缺陷，其中五处是「报成功、其实什么都没做」。** 先分清两种形态，混在一起会高估静默损坏的数量：**五处是假成功**（接口回 200、界面显示成功、实际产物是空的或没写进去），**两处是显式失败但长期没人看**（会报错，只是没有人盯着那个报错）。逐条是——全站 redis 备份因为口令判据写反而全部失败（E34，**显式失败**——备份状态是红的，只是没人盯）；mysql 手工下载走错分支，导出的是 22 字节空壳却回 200（E41）；mysql 恢复读到的是管道另一端的退出码，解压失败被吞成「已恢复」（E42）；恢复接口的上传体被日志中间件读光，落盘 0 字节仍走到「已恢复」（E43）；redis 恢复往运行中的容器写快照，容器关闭时的自动保存把刚上传的内容覆盖掉，接口仍回「已恢复」（E35）；备份脚本写死用 root 账号，随机 root 口令的库报 Access denied、长期零备份而无人察觉（E45 第一层，**显式失败**）；换成应用账号后缺一个开关，产出 20 字节空 gzip（E45 第二层）。**它们全部已修复**，但证据强度要分开说：备份侧与 mysql 恢复侧有真机证据——6 个 redis 手工备份回真快照、一个大型 mysql 库完整回灌（上传 7,045,292 字节、表数 139 → 442、以 root 身份独立复核 337 张建表语句）；**唯独 redis 恢复那条（E35）只有代码级证据**——它是 08-18 收窄端口时读恢复流程发现的，当时那台恰好是空库、没有踩到，修复的验证是「顺序由纯函数产出并被断言（改回事故写法两条用例变红）」加源码守卫，**没有跑过一次非空 RDB 的完整回灌**。把它当恢复能力的证据时要记得这条差别。但要说清楚：**在这周之前，这套备份的可靠性是「以为有」**，而 8 月初刚发生过服务器被攻击、主库被清空的事。

**第三条：离机备份的上传仍是断的；本地副本能不能留下来，这份报告答不上来。** 这一条要分两段说，混在一起会得出相反的结论。

**修复前（观测于 08-18 19:25 UTC，加固计划看板 S2.4 的原始记录）**：每一轮周期备份走的是「导出成功 → 校验通过 → 上传离机存储返回 401 → 连同本地那一份一起删掉」，因此本地周期备份自当天 12:30 起零新增（E44）。

**修复后（08-19，PR #1402）**：上传失败不再删本地副本，并对重试做了止损。**但这条修复之后是否真的有周期跑成并留下文件，本报告未能核实**——加固计划看板的那行证据停在修复之前，周报采集器不覆盖这一项。**要说清的是：查得到的手段是有的**——部署平台自带一个备份历史查询能力，能逐个列出某个服务已保存的自动备份文件、大小与修改时间，并把「备份目录不存在」和「有目录但没有匹配项」分开报，零备份不会被伪装成一个空列表（具体端点见附录 C）。只是本次采集没有走通它：命令行工具没有对应子命令，而手拼部署平台地址是明令禁止的。所以「本地副本还在」现在只有代码依据、没有运行时证据，**但这是一次调用就能补上的空白，不是查不到**。

**没有变的是**：上传本身仍是 401，根因是离机存储凭据不对，需要用户核对配置，代码侧做不了。这条挂在看板 S2.4，状态是阻塞。**在它恢复之前，异地容灾这一层确定是没有的。**

### 1. 托管数据库的备份与恢复，从「以为有」变成「实测能恢复」

- **谁受益**：运维；以及所有数据托管在这套平台上的项目
- **以前**：备份任务显示成功、恢复接口回「已恢复」，但产物可能是 22 字节的空壳、可能根本没写进库、可能被容器关闭时的自动保存覆盖掉。**没有人知道备份是假的，直到真要恢复的那一天**
- **现在**：导出、恢复两侧都带可核对的数字（收到多少字节、恢复前后表数各是多少）；解压失败、空上传、格式不支持一律当场拒绝而不是伪装成功；恢复前先自动存一份当前状态，存不下就中止。六个 redis 实例的手工备份全部回真快照，一个大型 mysql 库完整回灌并以独立身份复核过
- **意味着**：出事时可以挑对象、可以核对结果，不必再整实例归档还原。但边界要说三层：① **有真机证据的只有缓存库备份与关系库恢复**（S2.2 留证）；② **缓存库恢复只有代码级证据**，没跑过非空快照的完整回灌（见质量闸第二条），把它当恢复能力证据时要打折；③ 以上全部只覆盖**手工**链路，**不覆盖自动周期备份**——那一层的离机上传仍是断的，本地副本的实际留存情况本报告未能核实（见质量闸第三条）

### 2. 数据端口从「对全网敞着」收到内网，新建的库一律要口令

- **谁受益**：安全与运维；间接是所有租户
- **以前**：平台托管的数据库端口默认绑在全部网卡上，靠宿主防火墙挡着——而防火墙规则重启即丢，丢了立刻恢复暴露；其中还有几个库根本没有口令
- **现在**：新建实例默认只绑私网并拒绝公网发布绕过；四类主流数据库（文档库、关系库两种、缓存库）新建时强制启用认证；每日从独立机器做全端口外部扫描，白名单之外的开放端口一律告警。暴露面自检从 14 项警告降到 2 项，剩下两项是没有挂数据卷、按决定暂不重建的服务。**但扫描目前只覆盖 IPv4**：巡检跑在托管运行器上，该运行器发不出 IPv6 报文（实测同一台主机 IPv4 扫得到 22/80/443、IPv6 全端口 1.3 秒零结果），因此部署平台与正式环境两处的 IPv6 暴露面**已登记为「不查」**，复审期限 2027-02-18
- **意味着**：IPv4 侧能打到的面显著收窄，且「有没有收窄」不再靠人记得去看，每天自动量一遍。**IPv6 侧是已知盲区，不是已验证安全**——本周在这上面的真实进展不是「扫上了」，而是把盲区从「静默存在」变成「显式登记、写明理由与残留风险、到期自动重新变红」（#1387）。登记里对正式环境写的原话是：若源站开着全局 IPv6 而防火墙只按 IPv4 配，多余端口不会被这条巡检发现
- **验收背书**：本周未验收；证据为自检输出与外部扫描记录

### 3. 部署平台不再「一个后台任务失败就整台停摆」

- **谁受益**：所有用这套平台部署与预览的人
- **以前**：一个后台任务抛出的错误没人接管，会直接掀翻整个平台进程。08-18 就是这样：**离机审计日志**上传收到存储侧 401，失败被重新抛进一条没人接住的链条，进程被判定为致命错误直接终止；重启后启动时又发事件、又 401、又死，重试超限后彻底停摆，平台全站不可用 18 分钟。（注意是**审计日志**上传，不是备份上传——两条是不同的管道，只是都撞在同一个存储凭据上）
- **现在**：进程装了总保险丝——无人处理的异步失败记一笔继续跑，真正的未捕获异常留下调用栈再退出；平台主进程与转发进程两个入口都装了。**离机审计**上传在同一个 401 下连续失败 46 次，平台没有中断过
- **意味着**：单点后台故障不再升级成全站事故；且这条修复是**在真实故障持续存在的情况下实证的**，不是造场景测出来的
- **验收背书**：本周未验收；证据为线上连续 46 次失败期间平台持续可用
- **技术出处**：#1390 #1391 #1392（细节见附录 B）
- **用量口径**：`none:基础设施`

### 4. 一套环境可以向另一套环境申请一次性授权，把业务数据搬过来

- **谁受益**：运维与交付；需要把正式环境内容同步到另一套环境的任何场景
- **以前**：跨环境搬数据只有「从整实例备份还原」一条路——要停机、是整实例的、挑不了范围，而且做完之后没有任何记录说明是谁批准的
- **现在**：发起方填对方地址 → 先握一次手确认对方是谁、协议对不对 → 跳到对方站点，**对方管理员当场看清「要走哪些集合、不会走哪些」并勾选同意** → 换一张只用一次、跑完即废的令牌 → 执行前先给一张「源站多少条 / 本站多少条」的对照表让人确认 → 分页拉取，进度实时推。全程两台机器之间**不存在任何长期共享的密钥**
- **意味着**：搬数据这件事第一次有了「谁批的、批了什么范围、什么时候失效」的书面答案；不停机、不动密钥、不把访问权一起搬过去

### 5. 「模型池配置好了却没有可用模型」这个故障族被治住

- **谁受益**：所有用到平台 AI 能力的用户与租户
