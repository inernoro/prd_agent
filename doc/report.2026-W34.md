### 本周最该注意的三条

**第一条：验收体系整周停摆，最后一份报告停在 08-17。** 部署平台验收中心里 `prd-agent` 项目累计 174 份报告，最新的一份是 08-17 的「缺陷复测 · 视觉创作 / 生图能力兼容修复」——**08-18 到 08-23 六天零新增**，连过去每天雷打不动跑的「每日验收 · 全量变更」也断了。这与上周的问题性质完全不同：上周是「报告很多但都不在验新功能」（覆盖面问题），本周是「根本没有报告」（可观测性问题）。后果很直接：本周落地的基础设施安全加固、备份恢复修复、跨环境数据同步这三件事，**全部只有开发者自己的自证，没有任何独立结论**。而这三件恰恰是出错代价最高的一类——它们动的是数据本身。**必须先查清巡检为什么停，再谈通过率。**

**第二条：备份链条上一周之内暴露出七处「报成功、其实什么都没做」。** 这不是七个独立 bug，是同一种形态：接口回 200、界面显示成功、实际产物是空的或没写进去。逐条是——全站 redis 备份因为口令判据写反而全部失败（E34）；mysql 手工下载走错分支，导出的是 22 字节空壳却回 200（E41）；mysql 恢复读到的是管道另一端的退出码，解压失败被吞成「已恢复」（E42）；恢复接口的上传体被日志中间件读光，落盘 0 字节仍走到「已恢复」（E43）；redis 恢复往运行中的容器写快照，容器关闭时的自动保存把刚上传的内容覆盖掉，接口仍回「已恢复」（E35）；备份脚本写死用 root 账号，随机 root 口令的库长期零备份而无人察觉（E45 第一层）；换成应用账号后缺一个开关，产出 20 字节空 gzip（E45 第二层）。**它们全部已修复并在真机上验过**——6 个 redis 手工备份回真快照、一个 44 万行级别的 mysql 库完整回灌（上传 7,045,292 字节、表数 139 → 442、以 root 身份独立复核 337 张建表语句）。但要说清楚：**在这周之前，这套备份的可靠性是「以为有」**，而 8 月初刚发生过服务器被攻击、主库被清空的事。

**第三条：离机备份仍然是断的，本地周期备份自 08-18 12:30 起零新增。** 每一轮周期备份现在的实际走向是：导出成功 → 校验通过 → 上传离机存储返回 401 → 连同本地那一份一起删掉（E44）。本周已经修掉「上传失败就把本地副本也删了」这个止损问题，但**上传本身仍是 401**，根因是离机存储凭据不对，需要用户核对配置，代码侧做不了。这条挂在加固计划看板 S2.4 阶段，状态是阻塞。**在它恢复之前，异地容灾这一层是没有的**——本机备份还在，异地副本没有。

## 二、本周做成了什么（业务价值看板）

> 每条都是「谁现在能做什么」，不是「改了哪些文件」。

### 1. 托管数据库的备份与恢复，从「以为有」变成「实测能恢复」

- **谁受益**：运维；以及所有数据托管在这套平台上的项目
- **以前**：备份任务显示成功、恢复接口回「已恢复」，但产物可能是 22 字节的空壳、可能根本没写进库、可能被容器关闭时的自动保存覆盖掉。**没有人知道备份是假的，直到真要恢复的那一天**
- **现在**：导出、恢复两侧都带可核对的数字（收到多少字节、恢复前后表数各是多少）；解压失败、空上传、格式不支持一律当场拒绝而不是伪装成功；恢复前先自动存一份当前状态，存不下就中止。六个 redis 实例的手工备份全部回真快照，一个大型 mysql 库完整回灌并以独立身份复核过
- **意味着**：8 月那次「库被清空只能从整实例归档还原」的处境不会重演——恢复手段从一条变成了可挑对象、可核对结果的常规操作
- **验收背书**：本周未验收（验收体系停摆，见质量闸第一条）；证据为真机实测记录，非第三方结论
- **技术出处**：#1385 #1386 #1388 #1393 #1394 #1397 #1398 #1399（细节见附录 B）
- **用量口径**：`none:基础设施`

### 2. 数据端口从「对全网敞着」收到内网，新建的库一律要口令

- **谁受益**：安全与运维；间接是所有租户
- **以前**：平台托管的数据库端口默认绑在全部网卡上，靠宿主防火墙挡着——而防火墙规则重启即丢，丢了立刻恢复暴露；其中还有几个库根本没有口令
- **现在**：新建实例默认只绑私网并拒绝公网发布绕过；四类主流数据库（文档库、关系库两种、缓存库）新建时强制启用认证；每日从独立机器对 IPv4 与 IPv6 双栈做全端口外部扫描，白名单之外的开放端口一律告警。暴露面自检从 14 项警告降到 2 项，剩下两项是没有挂数据卷、按决定暂不重建的服务
- **意味着**：外部扫描能打到的面显著收窄，且「有没有收窄」不再靠人记得去看，每天自动量一遍
- **验收背书**：本周未验收；证据为自检输出与外部扫描记录
- **技术出处**：#1381 及本周 17 条安全类提交（细节见附录 B、附录 C）
- **用量口径**：`none:基础设施`

### 3. 部署平台不再「一个后台任务失败就整台停摆」

- **谁受益**：所有用这套平台部署与预览的人
- **以前**：一个后台任务抛出的错误没人接管，会直接掀翻整个平台进程。08-18 就是这样：离机备份上传失败往上抛，平台全站不可用 18 分钟
- **现在**：进程装了总保险丝——无人处理的异步失败记一笔继续跑，真正的未捕获异常留下调用栈再退出；平台主进程与转发进程两个入口都装了。同一个故障（离机上传 401）之后连续失败 46 次，平台没有中断过
- **意味着**：单点后台故障不再升级成全站事故；且这条修复是**在真实故障持续存在的情况下实证的**，不是造场景测出来的
- **验收背书**：本周未验收；证据为线上连续 46 次失败期间平台持续可用
- **技术出处**：#1390 #1391 #1392（细节见附录 B）
- **用量口径**：`none:基础设施`

### 4. 一套环境可以向另一套环境申请一次性授权，把业务数据搬过来

- **谁受益**：运维与交付；需要把正式环境内容同步到另一套环境的任何场景
- **以前**：跨环境搬数据只有「从整实例备份还原」一条路——要停机、是整实例的、挑不了范围，而且做完之后没有任何记录说明是谁批准的
- **现在**：发起方填对方地址 → 先握一次手确认对方是谁、协议对不对 → 跳到对方站点，**对方管理员当场看清「要走哪些集合、不会走哪些」并勾选同意** → 换一张只用一次、跑完即废的令牌 → 执行前先给一张「源站多少条 / 本站多少条」的对照表让人确认 → 分页拉取，进度实时推。全程两台机器之间**不存在任何长期共享的密钥**
- **意味着**：搬数据这件事第一次有了「谁批的、批了什么范围、什么时候失效」的书面答案；不停机、不动密钥、不把访问权一起搬过去
- **验收背书**：本周未验收（视觉验收已在预览环境以真人路径走过三屏并双主题留证，但未归档成验收报告）；**已知边界 16 条**，逐条写在债务台账里，其中两条是高危：附件的二进制不搬只搬地址（两站不共用同一个对象存储时图片与录音会打不开）、没有跨实例身份归并（两边都自建过同名管理员账号时会留下两行同名用户）
- **技术出处**：#1404（细节见附录 B）
- **用量口径**：`route:/instance-sync`

### 5. 「模型池配置好了却没有可用模型」这个故障族被治住

- **谁受益**：所有用到平台 AI 能力的用户与租户
- **以前**：模型池反复出现「配置看着是对的，实际候选为 0」的静默故障——界面上不报错，功能就是不工作；失败原因还会把「配置写错了」显示成「供应商宕机」，让人往错的方向查

- **意味着**：同一类故障从「靠猜」变成「点名到具体一步」，且配置不兼容时会在用户遇到失败之前就把服务标红

- **用量口径**：`llm:visual-agent`

> **七条承诺，零达成，且其中三条是连续第四、五周顺延。** 上周的规律判断是「定位到具体对象的事情才会有进展」——本周提供了一个反面印证：这七条**全部**已经定位到具体对象了（哪个入口加去重键、哪三条能力补验收、哪三条债务先清），却仍然一条没动。
>
> 原因不在优先级排得对不对，在于**本周的实际投入全部被两件计划外的事吃掉了**：08-18 的全站事故与随后的备份链条连修（占掉周一周二两天、超过全周六成的提交），以及跨环境数据同步那条链路上五十二轮自动评审的收敛（占掉周四周五）。两件都不是可以推迟的——一件是正在发生的事故，一件是已经开工的功能。
>
> **该纠正的不是执行，是排法**：连续五周把同一批事排进 P0 而它们连续五周被计划外工作挤掉，说明这套排法没有对「本周还剩多少可支配时间」做任何假设。下周的优先级因此只留三条，并且第一条是恢复度量能力本身——**在看不见的情况下排出来的优先级，本身就不可信**。

## 七、术语表（本周正文出现的内部说法）

| 内部代号 | 说人话 |
|----------|--------|
| 部署平台 / CDS | 把代码自动变成可访问在线环境的平台，同时托管这些环境用的数据库 |
| 主系统 / MAP / prd-agent | 本产品主系统 |
| 模型网关 / llmgw | 统一管理所有 AI 大模型调用的中枢，对外可独立接入或售卖 |
| 模型池 | 一组可互相替代的模型，其中一个坏了可以切到另一个 |
| 能力契约 | 「这个模型能干什么」的统一写法；两边写法不一致时，配置看着对、实际调不到 |
| 熔断 | 坏掉的上游先摘出去不再发流量，过一段时间再放小流量试探 |
| 离机备份 | 把备份传到另一处存储保存，防止本机整体损坏时备份跟着一起没了 |
| 快照 / dump | 数据库某一刻全部内容的导出文件 |
| 收窄端口绑定 | 让数据库只能从本机和内网连，外面连不上 |
| 认证门禁 | 强制要求数据库必须设口令才允许启动 |
| 双栈扫描 | 对新旧两种网络地址格式（IPv4 与 IPv6）都做一遍外部端口检查 |
| 进程保险丝 | 让单个后台任务的失败不会掀翻整个服务进程的兜底机制 |
| 一次性授权 / PKCE | 每次操作都要人当场批准一次，批准的范围写进一张短时效、只能用一次的票据 |
| 脱敏 | 数据搬运时把密钥、口令这类敏感字段抹掉再送出去 |
| 网页托管 | 把一份内容发布成对外可访问网页的功能 |
| 视觉创作 | 出图与图片加工模块 |
| 自动评审 / Review 轮次 | 自动化工具对一次代码改动反复提意见，每一轮修完再评一次 |
| 债务台账 | 明确知道但当期不修的问题清单，写下来防止变成无人知晓的欠账 |
| 守卫 / 棘轮 | 写在代码里的自动检查，同类错误再次出现时会让流程当场失败 |
| 熵减 | 文档与台账的定期清理对账 |
| 验收结论 / 通过 / 有条件通过 / 未通过 | 一次检验的客观结果；有条件通过 = 能用但有已知限制 |
| 功能验收 / 每日巡检 / 发布验收 / 缺陷复测 | 四类例行检验；**只有功能验收**专门验「这个新功能做得对不对」 |
| 用量口径 | 每条能力标注的机器可读标签，用于下一期度量「这个能力有没有人用」 |
| PR | 一次代码改动的提交单元 |
