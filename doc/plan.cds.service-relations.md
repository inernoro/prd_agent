## 目标

CDS 上一个项目往往是前后端分离、多个 API、多个子域，现在又开始跨项目互相调用。用户的痛点是三件事：前后端关系在画布上全是水平的看不出主从；跨项目的地址埋在几十个环境变量里，不好切换也不好重启；出了问题没有一处能一眼看出「配置错在哪、引用断在哪」。本计划用一份关系模型解决这三件事，模型的每条边都带来源，声明高于推断，推断结果必须标出来。

## 已拍板的决策

1. 引用变量写法用 `${CDS_REF:项目/服务}`，可选带分支，和现有的 `${CDS_HOST}` 一家，不引入第二种模板语法。
2. 界面上的修正直接开 PR 回写仓库根的 compose，同时写入分支覆盖立即生效。仓库根始终是配置真相，CDS 侧不长出第二份。
3. 全局概览是左侧导航里独立的「概览」菜单，项目列表页只放一行结论。
4. 探活路径出现在路由前缀里按错误阻断；同一 host 上同一前缀被多个服务声明按错误阻断。没有场景需要两个服务共享一个前缀。
5. 老代理的按名选服务规则删除，改为复用转发器的判定，只留一个路由大脑。

## 关系模型

节点是服务、基础设施、外部端点。边分五类：

| 边 | 事实来源 | 状态 |
|---|---|---|
| 路由 | host 加前缀，与转发器发布规则同源 | 第零批已落地：主域名承载根路径的是壳，其余按前缀挂在壳下，每个子域各成一站 |
| 调用 | 环境变量里的地址引用，或显式声明 `cds.calls` | 推断已落地，显式声明待第一批 |
| 依赖 | compose 的 depends_on | 已落地 |
| 数据 | 服务到共享库、缓存 | 已落地，画布标明同项目所有分支共用 |
| 跨项目引用 | 引用变量指向别的项目的已发布入口 | 第三批新增，必须走公网入口，因为各项目容器网络互相隔离 |

服务角色分 web、api、worker 三种，判定顺序固定：显式声明，强路由事实（用户入口、不监听 HTTP、承载根路径且探活是页面），服务名词根，弱路由特征，默认 api。每个结论带来源与理由，界面把非声明来源标成推断。

## 各批次要做什么、怎么验收

### 第一批 · 体检规则与生成器修正

- 体检项：前缀冲突、探活路径进前缀、子域与根路径双占、一个服务两个公网面、游离服务（无路由、无调用方、无声明）、引用断裂、模板变量缺失。分错误、警告、建议三级。
- 规则只写一份放 CDS 后端，画布、导入审批页、cdscli verify 三处调同一个接口。错误级阻断导入。
- cdscli 扫描生成器不再给所有 Java 模块复制同一份前缀清单；探活类路径不进前缀；删除从未被解析的复数前缀标签。
- 验收：用 mdimp 当前 compose 跑 verify，必须报出 `/`、`/health`、`/open/` 三处冲突和探活前缀，并给出修正 diff；给 mdimp 生成的 PR 里每个 Java 服务的前缀各不相同。
- 已落地（2026-09-02）：体检模块、导入审批闸门（错误级 409，可 force 放行）、`POST /api/compose/lint`、`GET /api/branches/:id/service-graph`、`cds.calls` 声明边、cdscli verify 接服务端体检、`cdscli topology` 文字树、生成器按模块扫控制器前缀并删除死标签。未落地：修正 diff 与一键开 PR（并入第四批「修正」）。

### 第二批 · 路由收敛与可观测

- 主域名前缀去重改为按服务 id 确定性排序，重复前缀在体检里已被阻断，发布器只做数据面兜底。
- web 不可用时的默认站改为等待页，不落到任意运行中的服务。
- 老代理的兜底改为调用与转发器同一个判定函数、读同一份路由表。
- 响应头新增判定来源（转发器或老代理兜底）与服务 id；面板加「路由判定查询」，输入 host 与路径返回当前命中的路由和最近若干次实际落点。
- 验收：构造两个服务同前缀并打乱服务键序，发布结果一致；同一批 URL 在转发器与老代理下判定一致；能从日志定位一次「入口 A 落到端口 B」的判定来源。

### 第三批 · 引用变量与配置页「引用」分区

- 引用变量在部署时解析成目标项目的公网入口；目标分支不指定时绑默认分支，分支级可以钉到目标项目的某个分支。
- 配置页签新增「引用」分区，从全部环境变量里单独抽出引用变量、值是网址的变量、键名以 URL、BASE、ENDPOINT 结尾的变量，显示指向哪个项目哪个分支、目标现在活没活、来自哪一层。
- 每条引用旁给切换目标分支和重启受影响容器两个动作；切换写入分支覆盖，不动项目根；「同步到仓库」开 PR。
- 验收：设计稿画板 4 在预览域名上真视觉验收；把一条引用切到另一个分支并重启后，容器里的值确实换了。

### 第四批 · 关系缩略卡、半屏与全屏、概览菜单

- 分支总览页加关系缩略卡，卡上先写结论再画缩略图；点开默认半屏抽屉，可切全屏，全屏有独立路由可分享。
- 全屏图在第零批画布之上新增外部项目框、断裂边、共享基础设施标注、只看问题开关。
- 「概览」菜单：每个项目一个分组，分组之间画跨项目引用边，分组顶上是体检结论，右侧按严重度列需要处理的事项，点任一条跳到对应分支的关系图。
- 验收：设计稿画板 1、2、3、5 在预览域名上真视觉验收，双主题各一遍。

## 多分支怎么兼容

关系是项目级事实，分支只是它的实例。项目根 compose 定义骨架，所有分支继承；分支级只允许临时额外服务、配置覆盖、引用变量改指向三种偏离，界面上偏离项目根的节点和边标黄。副本共享所属服务的全部关系，不单独成节点。关系只认服务名和 host，永远不认端口。

## 取舍与风险

- 名字推导保留但降级：它比探活路径可信，比配置声明不可信，所以排在中间。mdimp 十个服务里名字推导会错三个，这是它不能当第一判据的证据。
- 引用必须走公网入口，多一跳转发器。换来的是跨项目隔离不破、引用随目标分支切换即时生效。
- 第一批把前缀冲突升级为阻断后，存量项目导入会红。缓解：verify 同时给出修正 diff 和一键开 PR。
- 老代理兜底改为复用转发器判定，需要它读同一份路由文件；同机同文件，可行，但要保留转发器完全不可用时的等待页。

## 明确不做

- 不做跨项目的容器网络打通。
- 不在 CDS 侧长出第二份配置真相。
- 不自动帮项目决定 `/open/` 归谁，这是业务判断，只报出并给两个可点的选项。
