# CDS 部署方式选择 · 指南

> **版本**：v2.6 | **日期**：2026-10-11 | **状态**：现有接入已落地；候选治理实施中

**一句话**：三种接入方式怎么选：普通项目走可视化托管，已有成熟编排走编排导入，批量操作走 Agent 接入。
**谁该读**：第一次接入项目的人；纠结选哪条路的工程师。
**读完能做什么**：按项目现状选对方式，并知道已有项目怎么升级。

---

CDS 保留三种项目接入方式，但新版不再把三条路当成同等复杂的选择题。普通项目优先使用可视化托管交付；已有成熟编排的项目继续使用 Compose；需要 Agent 批量操作或自动化时使用项目级技能。

## 先做选择

| 你的项目 | 推荐方式 | 需要准备什么 |
| --- | --- | --- |
| 普通网站、后台、前后端项目 | 可视化托管交付 | Git 仓库地址 |
| 已有稳定的 `cds-compose.yml` 或复杂 Compose | Compose 导入 | 现有配置文件 |
| 希望由 Codex 或 Claude Code 操作 | Agent 项目接入 | 页面批准一次 |
| 特殊网络、多容器严格编排、自定义镜像 | Compose 导入 | 明确的高级配置 |

三种方式最终进入同一套部署记录、版本复用、预览和回滚流程，可以混合使用，不需要为新版重建已有项目。

## 方式一：可视化托管交付

这是新项目的默认方式。

### 怎么使用

1. 打开项目列表，点击“一键部署项目”；
2. 粘贴 Git 仓库地址，或从 GitHub 选择仓库；
3. 点击“检测仓库并自动填好配置”；
4. 确认识别到的应用、目录、命令、端口和依赖；
5. 配置把握不高时，先点击“试运行验证”；
6. 创建项目并观察准备、构建、启动和检查阶段；
7. 部署成功后打开预览地址。

### 用户需要确认什么

- 应用目录是否正确；
- 前端、后台和后台任务是否被正确区分；
- 启动命令和端口是否符合项目；
- 数据库、缓存和其他依赖是否齐全；
- 是否存在必须由用户提供的环境信息。

普通项目不需要先写完整构建配置。标准 Compose 只声明了构建、没有启动命令时，CDS 会继续从项目自身信息推导；确实无法判断时才要求补充。

## 方式二：Compose 导入

适合已有成熟编排，或需要精确控制服务、网络和启动顺序的项目。

### 怎么使用

1. 确认仓库根目录存在 `cds-compose.yml` 或受支持的 Compose 配置；
2. 在项目创建或设置中查看导入预览；
3. 检查应用服务、基础设施、端口、环境声明和依赖顺序；
4. 批准导入；
5. 选择目标分支并部署；
6. 在同一条部署记录中查看过程和结果；
7. 打开预览并验证核心操作。

### 新版如何减少 Compose 调试

- 已有配置不会因为切换到托管模式而被删除；
- 标准项目缺少启动命令时，会先尝试从项目清单推导；
- 部署失败会先显示问题归属和失败阶段；
- 相同成功版本可以直接再次部署；
- 新版本异常时可以恢复以前的成功版本。

Compose 仍然是高级控制方式。特殊网络、复杂脚本和自定义镜像不会被托管模式强行改写。

## 方式三：Agent 项目接入

适合希望让 Agent 完成扫描、部署、查看状态、诊断和恢复的用户。

### 怎么使用

1. 打开“一键部署 > 接入 Agent”；
2. 选择 Codex 或 Claude Code；
3. 选择已有项目或新项目；
4. 把无密钥接入口令交给 Agent；
5. 在 CDS 页面批准；
6. 让 Agent 继续扫描、部署或诊断。

### 权限和电脑环境

- 不需要把长期 Key 发到对话；
- 不修改 `.zshrc`、`.bashrc`、系统环境变量或全局 PATH；
- 凭据只保存在当前项目；
- 权限默认只覆盖当前项目；
- 新项目创建权限使用一次后自动失效；
- 短暂网络波动不会要求重新发起同一申请。

Agent 接入不是第四套部署系统。它只是操作 CDS 的安全入口，部署结果仍以 CDS 页面里的部署记录和版本为准。

## 已有项目怎么升级

| 现状 | 建议 |
| --- | --- |
| 现有 Compose 已稳定运行 | 保持 Compose，不必迁移 |
| 配置多但大部分是常规网站或后台 | 在设置中试用托管模式，先检查最终生效配置 |
| 仍通过环境变量给 Agent 长期 Key | 改用页面批准；旧方式只保留兼容 |
| 私有仓库每次都重新粘贴 Token | 改用 GitHub App 单仓库授权 |
| 失败后靠反复部署碰运气 | 打开本次部署记录，按失败归属处理 |

切换交付模式前后都应保留一条已验证的成功版本。这样出现识别偏差时，可以立即恢复，而不是重新排查整个项目。

## 部署后的统一操作

无论从哪条方式进入，日常操作都是一致的：

1. 推送代码或手动发起部署；
2. 查看同一条部署记录；
3. 打开预览验收；
4. 代码未变时复用成功版本；
5. 新版本异常时恢复旧版本；
6. 失败时按代码、配置、CDS 或外部服务归因。

## 验收标准

| 检查项 | 通过标准 |
| --- | --- |
| 仓库来源 | 能确认仓库、默认分支和触发来源 |
| 运行方案 | 应用、命令、端口和依赖与项目一致 |
| 部署过程 | 刷新后仍能继续查看同一条记录 |
| 服务结果 | 每个服务状态清晰，不混成一个笼统结果 |
| 用户预览 | 页面或服务入口及核心操作正常 |
| 再次部署 | 能判断成功版本是否可直接复用 |
| 恢复 | 可以选择以前的成功版本恢复 |

## 精确极速制品与运行结果

声明 `cds.prebuilt-commit-policy: exact` 的预构建服务（部署模式可声明 `commitPolicy: exact`）使用精确制品准入。普通部署按本轮拉取的完整40位SHA，点名提交或重放版本按指定SHA；固定的仓库digest保留原身份。实际 `docker pull`、宿主架构、Linux镜像、OCI revision和镜像ID必须一致。固定digest及缓存ID还要核对RepoDigests归属。目标制品缺失、鉴权或身份不符时明确失败；不换旧提交、不隐式源码编译。

整分支及执行器入口先准备目标制品集合，再进入容器变更；固定版本使用版本快照，当前分支模式覆盖不能绕过其准入。单服务也执行精确检查。当前制品检查保留旧容器的保证仅覆盖准入失败；候选就绪后再替换的完整治理仍按联合计划P3实施，不能承诺启动失败已经无中断。

运行记录分别保存实际执行镜像ID（`deployedImage`）、可跨执行器拉取的仓库引用（`deployedArtifactRef`）、实际预构建属性及提交号。DeploymentVersion保存仓库引用；本机bare ID不能当成另一宿主的拉取地址。

分支卡黄闪电只表示实际服务全部已证实运行预构建产物，蓝闪电表示部分，并列出源码或未知例外。实际分母含未回收的额外/孤儿服务，缺少实际戳、非运行状态和矛盾模式均不能继承配置判通过；停止分支仅展示配置意图。`actualPrebuiltCoverage` 与配置 `prebuiltCoverage` 分开。

版本状态独立计算：全部极速仍可能显示“版本待更新”。以本轮冻结的 `targetCommitSha` 对比每个运行服务的 `deployedCommitSha`，`actualVersionStatus=current` 才表示目标版本一致；缺完整身份为unknown。最新仓库HEAD与本轮冻结目标是否一致还须在验收前单独核对。旧数据不能补猜版本。线上验收须同时确认实际极速覆盖、目标版本、健康与真实入口。

## 候选替换契约（实施中）

候选交付冻结目标SHA、配置指纹和服务图，使用独立容器身份、端口和交付网络。在线服务图继续指向旧实例，完整候选就绪后才能进入切换。创建前保存新旧运行身份并等待可靠落盘；账本不复制环境变量、日志或凭据。未完成实际容器对账的候选与旧实例继续占用容量和端口，失败或取消不能自动解除预留，也不能因终态记录裁剪而丢失恢复依据。

现有服务清理也遵循实际回收结果：Docker删除失败不能返回成功，整分支与空清单清理不能因此删除服务身份或释放端口。失败记录继续可见，部署以错误收尾，明确“已不存在”才可按已回收处理；不能把未确认回收的实例从实际极速分母和容量账本中抹掉。

部署完成须先持久化最终run快照，再确认内存终态和发送完成响应；写盘或租约确认失败时，run仍可合法失败或取消，不允许响应已失败而旧run封为成功。暂存期间其他实体保存必须保留暂存run及新owner状态，同一run不能被并发更新。当前本地已接空清单、整分支与单服务入口，其他入口及实际存储/重启证据按P4补齐，不据此宣称全平台可靠落盘。

同名候选容器与网络须验证实例、项目、分支和交付归属。启动前只能删除已停止且身份完全匹配的候选容器，并按检查过的不可变ID执行非强制删除；未知归属、运行中或已切换的实例须保留并失败关闭。该校验不能代替部署取消后的Daemon侧对账。

切换须先保存意图和恢复点，再发布路由，并确认实际路由消费者已应用完整目标映射，最后回收旧实例。写路由文件成功或数量相等不等于消费者确认；确认目标须冻结映射值，诊断失败、取消和超时须有界结束等待。失败时先恢复并验证旧路由，恢复结果未知则保留两组实例及容量事实。worker、固定端口、独占写卷须有明确替换约束；不能证明并行安全时采用保留旧实例的停止与恢复流程。

当前本地代码已完成候选身份、启动归属边界、创建前账本、路由消费者确认与带恢复的切换事务组件，切换事务仍未接入实际部署路由与Daemon恢复；不得据此承诺线上已支持无中断替换。JSON持久化屏障的同一失败会报告给每个等待者，仅后续成功保存才能恢复可靠状态。联合计划P3的实际Daemon、切流、取消、重启和完整分支验收通过后，以对应自动门禁和报告替代本段临时实施状态说明。

## 常见问题

| 现象 | 处理方式 |
| --- | --- |
| 默认分支不是 `main` | 以仓库真实默认分支为准，不手工猜测 |
| 容器运行但预览失败 | 检查端口、健康路径和服务日志 |
| 私有仓库拉取失败 | 检查该项目的 GitHub App 单仓库授权 |
| 自动识别不准确 | 修改最小声明或改用 Compose 高级控制 |
| 相同代码仍在重新构建 | 检查目标版本是否标记为产物可复用 |
| 页面刷新后没有过程 | 回到分支详情并打开对应部署记录 |

### 新发现制品的默认选择

新增或更新应用Profile时，如果项目尚未明确设置该Profile的新分支默认模式，并且存在真实prebuilt模式，自动补上极速默认。已有明确模式（含源码例外）和已创建分支的覆盖不变；无prebuilt定义不能自动制造极速配置。该规则只填新分支模板，不证明镜像已可用、部署已极速或已有分支已对齐；这些事实分别由制品准入和运行结果判定。
