# CDS 部署方式选择 · 指南

> **版本**：v2.10 | **日期**：2026-10-24 | **状态**：稳定存储与源码兼容修复验证中；历史原生回执按各自提交记录，完整并发验收进行中

**一句话**：三种接入方式怎么选：普通项目走可视化托管，已有成熟编排走编排导入，批量操作走 Agent 接入。
**谁该读**：第一次接入项目的人；纠结选哪条路的工程师。
**读完能做什么**：按项目现状选对方式，并知道已有项目怎么升级。

---

CDS 保留三种项目接入方式，但新版不再把三条路当成同等复杂的选择题。普通项目优先使用可视化托管交付；已有成熟编排的项目继续使用 Compose；需要 Agent 批量操作或自动化时使用项目级技能。

## 先做选择

| 你的项目 | 推荐方式 | 需要准备什么 |
| --- | --- | --- |
| 普通网站、后台、前后端项目 | 可视化托管交付 | Git 仓库地址 |
| 已有稳定的 `cds-compose.yml` 或复杂 Compose | Compose 导入 | 现有配置文件 |
| 希望由 Codex 或 Claude Code 操作 | Agent 项目接入 | 页面批准一次 |
| 特殊网络、多容器严格编排、自定义镜像 | Compose 导入 | 明确的高级配置 |

三种方式最终进入同一套部署记录、版本复用、预览和回滚流程，可以混合使用，不需要为新版重建已有项目。

## 方式一：可视化托管交付

这是新项目的默认方式。

### 怎么使用

1. 打开项目列表，点击“一键部署项目”；
2. 粘贴 Git 仓库地址，或从 GitHub 选择仓库；
3. 点击“检测仓库并自动填好配置”；
4. 确认识别到的应用、目录、命令、端口和依赖；
5. 配置把握不高时，先点击“试运行验证”；
6. 创建项目并观察准备、构建、启动和检查阶段；
7. 部署成功后打开预览地址。

### 用户需要确认什么

- 应用目录是否正确；
- 前端、后台和后台任务是否被正确区分；
- 启动命令和端口是否符合项目；
- 数据库、缓存和其他依赖是否齐全；
- 是否存在必须由用户提供的环境信息。

普通项目不需要先写完整构建配置。标准 Compose 只声明了构建、没有启动命令时，CDS 会继续从项目自身信息推导；确实无法判断时才要求补充。

## 方式二：Compose 导入

适合已有成熟编排，或需要精确控制服务、网络和启动顺序的项目。

### 怎么使用

1. 确认仓库根目录存在 `cds-compose.yml` 或受支持的 Compose 配置；
2. 在项目创建或设置中查看导入预览；
3. 检查应用服务、基础设施、端口、环境声明和依赖顺序；
4. 批准导入；
5. 选择目标分支并部署；
6. 在同一条部署记录中查看过程和结果；
7. 打开预览并验证核心操作。

### 新版如何减少 Compose 调试

- 已有配置不会因为切换到托管模式而被删除；
- 标准项目缺少启动命令时，会先尝试从项目清单推导；
- 部署失败会先显示问题归属和失败阶段；
- 相同成功版本可以直接再次部署；
- 新版本异常时可以恢复以前的成功版本。

Compose 仍然是高级控制方式。特殊网络、复杂脚本和自定义镜像不会被托管模式强行改写。

## 方式三：Agent 项目接入

适合希望让 Agent 完成扫描、部署、查看状态、诊断和恢复的用户。

### 怎么使用

1. 打开“一键部署 > 接入 Agent”；
2. 选择 Codex 或 Claude Code；
3. 选择已有项目或新项目；
4. 把无密钥接入口令交给 Agent；
5. 在 CDS 页面批准；
6. 让 Agent 继续扫描、部署或诊断。

### 权限和电脑环境

- 不需要把长期 Key 发到对话；
- 不修改 `.zshrc`、`.bashrc`、系统环境变量或全局 PATH；
- 凭据只保存在当前项目；
- 权限默认只覆盖当前项目；
- 新项目创建权限使用一次后自动失效；
- 短暂网络波动不会要求重新发起同一申请。

Agent 接入不是第四套部署系统。它只是操作 CDS 的安全入口，部署结果仍以 CDS 页面里的部署记录和版本为准。

## 已有项目怎么升级

| 现状 | 建议 |
| --- | --- |
| 现有 Compose 已稳定运行 | 保持 Compose，不必迁移 |
| 配置多但大部分是常规网站或后台 | 在设置中试用托管模式，先检查最终生效配置 |
| 仍通过环境变量给 Agent 长期 Key | 改用页面批准；旧方式只保留兼容 |
| 私有仓库每次都重新粘贴 Token | 改用 GitHub App 单仓库授权 |
| 失败后靠反复部署碰运气 | 打开本次部署记录，按失败归属处理 |

切换交付模式前后都应保留一条已验证的成功版本。这样出现识别偏差时，可以立即恢复，而不是重新排查整个项目。

## 部署后的统一操作

无论从哪条方式进入，日常操作都是一致的：

1. 推送代码或手动发起部署；
2. 查看同一条部署记录；
3. 打开预览验收；
4. 代码未变时复用成功版本；
5. 新版本异常时恢复旧版本；
6. 失败时按代码、配置、CDS 或外部服务归因。

## 稳定存储与源码生命周期

部署源码快照只承担可回收的源码，宿主挂载保持只读。普通源码命令先将固定暂存路径的源码复制到容器可写层，再在原工作目录安装、编译和运行；受管构建在独立临时层生成镜像。源码工作目录与稳定卷、工具或临时挂载重叠时在替换前拒绝，避免复制污染数据卷；镜像内工作目录的符号链接也拒绝。构建镜像自带的匿名数据卷必须在创建前识别并拒绝。预构建镜像不挂源码，但声明的宿主配置、受控初始化和其他明确源码依赖仍可能需要检出。镜像层、缓存和日志仍占磁盘，必须分别设置保留代数和日志上限，不能把“极速版”解释成磁盘零占用。

可写存储必须明确用途与归属：固定实例、项目、项目共享或分支私有范围、服务和挂载键；分支私有另含分支身份。提交号、部署流水号和源码快照目录不能充当数据身份。普通源码只读，先核验真实路径、非符号链接和文件身份，并在实际执行槽复核；这是重复身份围栏，不是 Docker 内核固定挂载。用户配置或缓存的宿主绑定无论只读或可写，均在缺乏原生固定挂载证明时拒绝创建，不能把只读 socket 当安全，也不能先建目录再推测安全。平台自有工具由服务器独立添加并核验，HTTP 配置不能授予该能力。命名卷只复用已核实归属和物理类型的现存卷，禁止镜像内容自动填充新卷。已有历史服务及数据保持原位，原容器可以按精确身份复用或唤醒；唤醒失败不能转为删除并重建空库。

CDS 启动在状态库加载后先确认稳定存储实例身份，再开放运行与首次分配。显式配置、已保存实例身份以及所有既有出生记录和存储映射必须一致；没有历史身份的安装生成一次随机身份并等待持久确认。缺失、冲突或写入失败时拒绝启动，不替历史卷改名或生成新归属。该身份属于平台状态，配置快照回滚不能覆盖；默认安装不再要求人工补环境变量。MongoDB 新预设同时为 `/data/db` 与 `/data/configdb` 显式分配稳定卷，已有历史 Mongo 不会因此被重建或补空卷。

替换部署须先完成整图镜像和存储核验，之后才允许初始化、清理旧实例或改变运行图。含稳定卷或需预先连接网络的运行路径将容器创建与业务启动分开，创建后核对真实容器、镜像、挂载及卷身份，再按精确容器身份启动。未知、缺失、被替换或未确认持久化的出生记录均拒绝启动并保留原数据。首次分配是独立、明确的新资源动作：原意图、至多一次创建、原生归属与配置公开必须有持久确认；普通部署、恢复和重试不能推断授权，更不能换身份绕过未决意图。独立停止服务不以新目标存储可用为前提。

手工创建和基础设施快速部署使用 `initializeStorage: new-only` 明确首次分配。可视化预设新增及新项目预设直接按目录声明完成新资源分配，确认后才返回成功；无卷预设不分配。已有项目无该标志的原有预设操作仍允许追加独立数据库，单例重复为无操作；显式 `new-only` 重试严格保留原目标，不自动新建第二库。手工创建省略该字段时，新持久卷或目录内有状态服务在首次写入前拒绝，不能保存保证无法启动的配置；无卷服务仍须核验真实镜像无隐含卷声明。快速发现、导入和重新同步的真实页面在创建前明确确认全新存储并发送该标志。仅对全新服务的目录内已知数据库路径，旧 named 声明可在精确原生证明原名不存在后转换为新的归属绑定；不挂载、改名、删除或复制原卷。原名存在或不可确认、宿主绑定和未知路径均拒绝。已有服务只报告已存在，不重启或覆盖；未决原出生仍拒绝重复分配。新分配先确认原意图和原生出生身份，再分别确认私有记录与公开配置的持久化；未决结果保留原 nonce 和卷，不自动删除或再次创建。快速部署只有在运行状态重新保存并确认后才返回启动成功。分支私有配置使用独立的分支归属，不能复用其他分支的出生凭据。

官方目录 Elasticsearch 8.11.0、SQL Server 2022 与 Kafka 3.7.0 的全新空数据卷仅在显式首次分配、出生已持久确认为 confirmed 且公开配置尚未发布时，执行固定的根目录权限准备：保留 UID 0，将 Elasticsearch 的组保留为 0，SQL Server 的组设为 10001，Kafka 的组设为 1000，目录设为 0770。镜像用户及实际账号身份必须分别为 1000:0、mssql/10001:10001、appuser/1000:1000；身份变化拒绝发布。Kafka 的数据、密钥与共享配置三个声明目录必须全部显式绑定，同一辅助容器先验证全部根目录为空且原身份为 0:0:755，再执行变更，禁止隐含匿名卷。镜像解析及全部卷声明核验在出生意图之前完成，失败不分配新卷；后续固定同一镜像身份。准备前后核验同一卷出生、精确辅助容器和全部挂载；目录扫描或 stat 失败、非空、未知权限、清理未确认均拒绝发布并保留原出生记录。辅助进程禁网络、根文件系统只读、内存与日志有界，只有改变组时赋予 CHOWN 能力；不启动业务入口、不递归改权限、不向旧卷复制镜像内容。普通运行、恢复和已有卷不能触发该初始化。

自动数据库迁移使用已准入的固定制品，不能再次被模式覆盖为基础镜像；组件制品执行仓库根迁移时，仍使用同一固定镜像并复制本次根源码。手动迁移绑定受理时本地 HEAD 的独立源码快照，兼容系统迁移的工作树链接，不直接放宽宿主绑定规则。

编译缓存默认留在容器可写层，重建为冷缓存；需要跨重建保留时使用显式分支私有存储分配。启动迁移和缓存修复只归档精确匹配旧目录模板的挂载声明，保留原文与物理文件，不回填宿主绑定。未知或手工挂载须另行核对，不能猜测退休。

受管构建器使用服务器生成的独立临时身份和空卷计划，不继承最终应用的存储归属；最终应用仍使用原身份并核验全部保留卷。受管源码产物经同一构建并发队列生成，整图验证先于业务初始化或旧服务清理；复制前核对固定源码 HEAD，导入与后续启动使用同一源码路径和提交。纯镜像导入不创建源码工作树。导入的基础设施启动范围限于当前所属项目。

分支私有首次分配由 `POST /api/branches/:id/storage/provision` 明确指定 `profileId`、`initializeStorage: "new-only"` 和 `freshMounts`（挂载键、容器路径、用途）。此动作只向尚无原运行实例的新目标添加明确的新挂载，不修改项目底座或其他分支；已停止的旧实例也不视为新目标。双重持久确认前，普通运行仍拒绝使用该卷；失败保留原出生意图，不换 nonce 重试。分配后切换到未确认的远端服务器会在派发前拒绝，不能静默丢失绑定或创建空数据。源码工作区与新持久挂载不得相同或互为祖先，分配前使用与运行时相同的重叠判据；纯镜像无源码工作区时按实际挂载计划核验。

已有出生记录或未决存储分配的服务、所属分支及项目禁止直接删除；配置回滚和撤销也不能抹去其完整配置或原凭据引用。删除与整组替换在任何停机、清理或新分配前拒绝，保留完整配置与卷，仍可正常停止。手动、Webhook、TTL、启动残留、批量清理和恢复出厂设置共用该保护；执行器明确因保留存储拒绝时，主节点也保留分支声明。

基础设施重新同步先对整批声明和所有替换目标完成镜像、存储、认证及配置版本核验，再进行明确的新资源分配，最后才允许停止或移除旧服务。任一目标无法确认时，旧图保持运行；显式历史挂载不会被推断成首次分配。

## 验收标准

| 检查项 | 通过标准 |
| --- | --- |
| 仓库来源 | 能确认仓库、默认分支和触发来源 |
| 运行方案 | 应用、命令、端口和依赖与项目一致 |
| 部署过程 | 刷新后仍能继续查看同一条记录 |
| 服务结果 | 每个服务状态清晰，不混成一个笼统结果 |
| 用户预览 | 页面或服务入口及核心操作正常 |
| 再次部署 | 能判断成功版本是否可直接复用 |
| 恢复 | 可以选择以前的成功版本恢复 |

## 常见问题

| 现象 | 处理方式 |
| --- | --- |
| 默认分支不是 `main` | 以仓库真实默认分支为准，不手工猜测 |
| 容器运行但预览失败 | 检查端口、健康路径和服务日志 |
| 私有仓库拉取失败 | 检查该项目的 GitHub App 单仓库授权 |
| 自动识别不准确 | 修改最小声明或改用 Compose 高级控制 |
| 相同代码仍在重新构建 | 检查目标版本是否标记为产物可复用 |
| 页面刷新后没有过程 | 回到分支详情并打开对应部署记录 |

普通基础设施停止保留经核对的原容器身份并确认冷态。旧卷无新归属时只能唤醒同一原容器，不借停止动作重绑或创建数据；显式重建和凭据轮换必须先通过严格存储核验，未知停止或删除结果不继续后续动作。 原容器被精确确认不存在时，删除或已通过存储核验的重建可继续；超时、非零未知诊断或身份冲突不能视为不存在。导入在首个配置写入前完成整批存储计划和旧名不存在证明；逐项分配失败可保留已确认出生，不能把整组分配称为事务回滚。

新分配的卷声明必须为有效列表；完整 YAML、嵌套 YAML 和 JSON 三种导入形式均在归一化前拒绝显式 null，不能因解析成空列表而推导新建空卷。

手动创建目录已支持的数据库须明确确认新空卷，Mongo 使用目录中的数据与配置两个持久路径。未确认的自动填充卷和自定义裸卷在写入服务前拒绝，不能先显示创建成功再让启动失败。自定义历史数据卷不自动接管；无卷的无状态自定义服务保留原流程。

持有已分配、待确认或仅声明归属的存储时，普通配置修改不得改变服务身份或卷声明，私有存储所属的构建服务也不得删除、移出项目或被同名配置遮蔽。导入与配置复制在首次写入、快照或新卷分配前核验整组候选，拒绝时保留原配置；名称、环境和运行状态等不改变存储声明的正常编辑仍可使用。无卷自定义服务在显示创建成功前核验真实镜像的卷声明，未绑定的数据目录不能留到启动时才报错。
