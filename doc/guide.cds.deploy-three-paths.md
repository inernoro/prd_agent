# CDS 部署方式选择 · 指南

> **版本**：v2.69 | **日期**：2026-10-11 | **状态**：现有接入已落地；候选治理实施中

**一句话**：三种接入方式怎么选：普通项目走可视化托管，已有成熟编排走编排导入，批量操作走 Agent 接入。
**谁该读**：第一次接入项目的人；纠结选哪条路的工程师。
**读完能做什么**：按项目现状选对方式，并知道已有项目怎么升级。

---

CDS 保留三种项目接入方式，但新版不再把三条路当成同等复杂的选择题。普通项目优先使用可视化托管交付；已有成熟编排的项目继续使用 Compose；需要 Agent 批量操作或自动化时使用项目级技能。

## 先做选择

| 你的项目 | 推荐方式 | 需要准备什么 |
| --- | --- | --- |
| 普通网站、后台、前后端项目 | 可视化托管交付 | Git 仓库地址 |
| 已有稳定的 `cds-compose.yml` 或复杂 Compose | Compose 导入 | 现有配置文件 |
| 希望由 Codex 或 Claude Code 操作 | Agent 项目接入 | 页面批准一次 |
| 特殊网络、多容器严格编排、自定义镜像 | Compose 导入 | 明确的高级配置 |

三种方式最终进入同一套部署记录、版本复用、预览和回滚流程，可以混合使用，不需要为新版重建已有项目。

## 方式一：可视化托管交付

这是新项目的默认方式。

### 怎么使用

1. 打开项目列表，点击“一键部署项目”；
2. 粘贴 Git 仓库地址，或从 GitHub 选择仓库；
3. 点击“检测仓库并自动填好配置”；
4. 确认识别到的应用、目录、命令、端口和依赖；
5. 配置把握不高时，先点击“试运行验证”；
6. 创建项目并观察准备、构建、启动和检查阶段；
7. 部署成功后打开预览地址。

### 用户需要确认什么

- 应用目录是否正确；
- 前端、后台和后台任务是否被正确区分；
- 启动命令和端口是否符合项目；
- 数据库、缓存和其他依赖是否齐全；
- 是否存在必须由用户提供的环境信息。

普通项目不需要先写完整构建配置。标准 Compose 只声明了构建、没有启动命令时，CDS 会继续从项目自身信息推导；确实无法判断时才要求补充。

## 方式二：Compose 导入

适合已有成熟编排，或需要精确控制服务、网络和启动顺序的项目。

### 怎么使用

1. 确认仓库根目录存在 `cds-compose.yml` 或受支持的 Compose 配置；
2. 在项目创建或设置中查看导入预览；
3. 检查应用服务、基础设施、端口、环境声明和依赖顺序；
4. 批准导入；
5. 选择目标分支并部署；
6. 在同一条部署记录中查看过程和结果；
7. 打开预览并验证核心操作。

### 新版如何减少 Compose 调试

- 已有配置不会因为切换到托管模式而被删除；
- 标准项目缺少启动命令时，会先尝试从项目清单推导；
- 部署失败会先显示问题归属和失败阶段；
- 相同成功版本可以直接再次部署；
- 新版本异常时可以恢复以前的成功版本。

Compose 仍然是高级控制方式。特殊网络、复杂脚本和自定义镜像不会被托管模式强行改写。

## 方式三：Agent 项目接入

适合希望让 Agent 完成扫描、部署、查看状态、诊断和恢复的用户。

### 怎么使用

1. 打开“一键部署 > 接入 Agent”；
2. 选择 Codex 或 Claude Code；
3. 选择已有项目或新项目；
4. 把无密钥接入口令交给 Agent；
5. 在 CDS 页面批准；
6. 让 Agent 继续扫描、部署或诊断。

### 权限和电脑环境

- 不需要把长期 Key 发到对话；
- 不修改 `.zshrc`、`.bashrc`、系统环境变量或全局 PATH；
- 凭据只保存在当前项目；
- 权限默认只覆盖当前项目；
- 新项目创建权限使用一次后自动失效；
- 短暂网络波动不会要求重新发起同一申请。

Agent 接入不是第四套部署系统。它只是操作 CDS 的安全入口，部署结果仍以 CDS 页面里的部署记录和版本为准。

## 已有项目怎么升级

| 现状 | 建议 |
| --- | --- |
| 现有 Compose 已稳定运行 | 保持 Compose，不必迁移 |
| 配置多但大部分是常规网站或后台 | 在设置中试用托管模式，先检查最终生效配置 |
| 仍通过环境变量给 Agent 长期 Key | 改用页面批准；旧方式只保留兼容 |
| 私有仓库每次都重新粘贴 Token | 改用 GitHub App 单仓库授权 |
| 失败后靠反复部署碰运气 | 打开本次部署记录，按失败归属处理 |

切换交付模式前后都应保留一条已验证的成功版本。这样出现识别偏差时，可以立即恢复，而不是重新排查整个项目。

## 部署后的统一操作

无论从哪条方式进入，日常操作都是一致的：

1. 推送代码或手动发起部署；
2. 查看同一条部署记录；
3. 打开预览验收；
4. 代码未变时复用成功版本；
5. 新版本异常时恢复旧版本；
6. 失败时按代码、配置、CDS 或外部服务归因。

## 验收标准

| 检查项 | 通过标准 |
| --- | --- |
| 仓库来源 | 能确认仓库、默认分支和触发来源 |
| 运行方案 | 应用、命令、端口和依赖与项目一致 |
| 部署过程 | 刷新后仍能继续查看同一条记录 |
| 服务结果 | 每个服务状态清晰，不混成一个笼统结果 |
| 用户预览 | 页面或服务入口及核心操作正常 |
| 再次部署 | 能判断成功版本是否可直接复用 |
| 恢复 | 可以选择以前的成功版本恢复 |

## 精确极速制品与运行结果

声明 `cds.prebuilt-commit-policy: exact` 的预构建服务（部署模式可声明 `commitPolicy: exact`）使用精确制品准入。普通部署按本轮拉取的完整40位SHA，点名提交或重放版本按指定SHA；固定的仓库digest保留原身份。实际 `docker pull`、宿主架构、Linux镜像、OCI revision和镜像ID必须一致。固定digest及缓存ID还要核对RepoDigests归属。目标制品缺失、鉴权或身份不符时明确失败；不换旧提交、不隐式源码编译。

整分支及执行器入口先准备目标制品集合，再进入容器变更；固定版本使用版本快照，当前分支模式覆盖不能绕过其准入。单服务也执行精确检查：以本次完整目标上下文展开镜像模板，检查本服务及声明`dependsOn`的项目内应用传递闭包，不检查无关服务。闭包缺Profile、跨项目、循环或非exact预构建依赖时失败；只有项目内已登记为running的基础设施可从应用制品集合排除，这不替代实际基础设施探活。依赖制品齐备前不改变在线容器，也不由单服务请求隐式重部署依赖。当前制品检查保留旧容器的保证仅覆盖准入失败；候选就绪后再替换的完整治理仍按联合计划P3实施，不能承诺启动失败已经无中断。

运行记录分别保存实际执行镜像ID（`deployedImage`）、可跨执行器拉取的仓库引用（`deployedArtifactRef`）、实际预构建属性及提交号。DeploymentVersion保存仓库引用；本机bare ID不能当成另一宿主的拉取地址。

分支卡黄闪电只表示实际服务全部已证实运行预构建产物，蓝闪电表示部分，并列出源码或未知例外。实际分母含未回收的额外/孤儿服务，缺少实际戳、非运行状态和矛盾模式均不能继承配置判通过；停止分支仅展示配置意图。`actualPrebuiltCoverage` 与配置 `prebuiltCoverage` 分开。

版本状态独立计算：全部极速仍可能显示“版本待更新”。以本轮冻结的 `targetCommitSha` 对比每个运行服务的 `deployedCommitSha`，`actualVersionStatus=current` 才表示目标版本一致；缺完整身份为unknown。最新仓库HEAD与本轮冻结目标是否一致还须在验收前单独核对。旧数据不能补猜版本。线上验收须同时确认实际极速覆盖、目标版本、健康与真实入口。

## 候选替换契约（实施中）

候选交付冻结目标SHA、配置指纹和服务图，使用独立容器身份、端口和交付网络。在线服务图继续指向旧实例，完整候选就绪后才能进入切换。创建前保存新旧运行身份并等待可靠落盘；账本不复制环境变量、日志或凭据。未完成实际容器对账的候选与旧实例继续占用容量和端口，失败或取消不能自动解除预留；唯一不涉及Daemon清理的本地释放是未进入starting的prepared阶段：冻结身份和旧图不变、从未发出stop/create，且释放快照可靠落盘后才可解除预留，也不能因终态记录裁剪而丢失恢复依据。

私有网络的创建意图先可靠落盘；创建后实际inspect确认网络不可变ID、实例/项目/分支/交付归属和完整配置摘要，在创建任何应用容器前保存。并行服务共享该run的串行持久化边界，不覆盖已确认网络身份，不保存IPAM或Options明文。失败回收先按不可变ID清理已确认候选容器，再复查该网络的原身份、配置和实际端点；仍有端点、归属漂移或查询失败时保留网络和恢复预留，不强行断连。只按已捕获网络ID删除并再次确认消失后，才能继续原worker恢复。即使未停止旧服务，存在私有网络创建意图的回滚也须延后released，完成实际网络回收后才释放恢复预留，不能仅按空stopBeforeStart判定收尾完成。网络创建结果未知仍需要Daemon对账，不能凭名称不存在、客户端结束或一次成功rm推断闭合。取消与租约检查覆盖网络查询等待和创建前后。此处仅受控整分支入口已接线，未证明启动后自主reconciler或全部网络生命周期；对应正式门禁完成后移除实施状态说明。

逐服务创建意图先落盘；Daemon创建返回后，以真实inspect核对不可变ID、运行归属、精确镜像和配置摘要，在连接共享网络或启动前保存结果并等待可靠落盘。并行成员的创建事实按run串行合并，不能丢掉兄弟身份；已确认的ID与摘要不得被另一结果覆盖。连接或启动失败时保留已创建ID用于实际回收，未知创建仍不能按缺失快照或客户端结束推断不存在。后续候选连接与启动按已创建不可变ID操作。

事务阶段的内存确认必须等待该阶段快照落盘；等待期间禁止同一run推进竞争阶段，并在确认前复核运行归属、目标和配置。每次异步确认或删除旧实例前，还须重新核对冻结的服务运行事实，包括镜像、提交号、就绪状态和身份；仅容器名称与端口不变不足以证明可以回收。事实漂移时保留新旧实例及预留，不得删除旧实例或覆盖新owner。恢复阶段改名若无法安全落盘，保留原未释放阶段，而不是为了改名覆盖已变化的run。

现有服务清理也遵循实际回收结果：Docker删除失败不能返回成功，整分支与空清单清理不能因此删除服务身份或释放端口。失败记录继续可见，部署以错误收尾，明确“已不存在”才可按已回收处理；不能把未确认回收的实例从实际极速分母和容量账本中抹掉。

部署完成须先持久化最终run快照，再确认内存终态和发送完成响应；写盘或租约确认失败时，run仍可合法失败或取消，不允许响应已失败而旧run封为成功。暂存期间其他实体保存必须保留暂存run及新owner状态，同一run不能被并发更新。当前本地已接空清单、整分支与单服务入口，其他入口及实际存储/重启证据按P4补齐，不据此宣称全平台可靠落盘。

同名候选容器与网络须验证实例、项目、分支和交付归属。启动前只能删除已停止且身份完全匹配的候选容器，并按检查过的不可变ID执行非强制删除；未知归属、运行中或已切换的实例须保留并失败关闭。该校验不能代替部署取消后的Daemon侧对账。

恢复进程必须另取整分支独占租约，绑定唯一终态未释放run、项目和冻结提交/配置；手动或未知来源、活跃run、未知合同/阶段和多个未释放run不授予恢复写入权。本进程内取消或被取代仅撤销当前写入权，旧执行者的等待仍登记为未结束；原执行流程用原租约完成前，即使active列表已空或后继stop已完成，也不能授予恢复租约。复制租约或已完成代际的重复完成调用不改变当前写入者、未结束登记或pending；同operationId续约到新generation后，旧完成不能撤销后继租约。该内存门禁不是Docker Daemon闭合证明，也不能在重启后按空列表判断旧客户端或迟到创建不存在；实际恢复仍需持久化身份、进程与Daemon对账。本地恢复租约门禁已实现，定时/启动reconciler与实际Daemon证据未完成；对应正式自动门禁完成后删除实施状态说明。

恢复依据须在stop/create前可靠落盘：旧容器不可变ID、实际镜像ID、原运行意图和运行配置摘要，以及候选各服务的精确目标SHA与镜像ID。摘要覆盖完整返回的Config、HostConfig和挂载字段，按稳定字段排序生成SHA-256，账本只保存摘要和显式投影，不复制环境凭据或挂载选项明文。候选图和旧图的依据必须完整对应，显式未知分代、错误类型、身份或目标不符均拒绝写入；只有未提供依据的历史组件记录保留读取兼容，不能据此自动恢复或回收。该依据不能证明Daemon创建已结束，也不能替代旧版本就绪与实际路由确认。

候选替换的停止、恢复与回收另用已捕获的不可变容器ID；每次操作都先实际inspect核对实例/项目/分支/Profile、镜像、绑定端口、挂载和交付归属，在inspect等待后复核租约，再操作ID并复查结果。恢复只启动原容器，保留原配置，不用当前Profile重建旧版本。停止消费者前还须冻结其当前部署版本ID和完整版本摘要，版本归属、提交号、实际镜像及Profile合同分代须与原运行事实一致；恢复使用该原版本的启动信号与就绪探测，不借用待上线Profile。旧依据缺失、类型错误、未知分代或运行身份不符时，在停止/创建前拒绝；等待期间旧版本漂移也不得重新冻结。未释放交付引用的原版本免于历史裁剪，直到交付已实际对账释放。Daemon仍报告ID存在或检查失败时，回收不得记为完成。

受保护容器不进入替换操作。挂载事实须来自完整inspect，缺失、未知类型或读写矛盾不得视为空挂载；模式、传播方式与返回的挂载字段进入冻结比较。字段口径参见[Docker Engine inspect API](https://docs.docker.com/reference/api/engine/version/v1.56/)与[绑定挂载](https://docs.docker.com/engine/storage/bind-mounts/)，未知格式保留实例并明确失败。

`cds.replacement-strategy`允许`parallel`与`stop-and-restore`；未声明的worker（含现有角色推断）及有配置/实际可写挂载的服务默认停止后恢复，显式`parallel`不能替代隔离证明，存在上述约束时准入拒绝。固定端口等资源约束应显式声明`stop-and-restore`，不能据动态分配端口承诺无中断。角色、替换策略、挂载和exact策略纳入配置指纹与版本快照；停止意图及旧不可变ID须在停止前落盘。当前该策略已接本地整分支候选编排，停止/恢复仍须联合计划P3完成真实Daemon验证；单服务、执行器与导入入口尚未完成候选接线。

新版本快照以`replacementContractVersion=1`冻结上述字段的存在与未声明状态；新快照中缺少角色或策略、空挂载及未声明exact均按当时事实物化，不继承后来配置。只有缺少该分代字段的历史快照保留现有兼容读取；显式未知版本或错误类型必须拒绝物化，不能退回历史兼容路径，不能将这种兼容当成完整候选恢复证据；历史版本如需用于正式替换，应补齐其实际运行事实或明确拒绝准入。

本地整图候选编排组件已串联精确制品、显式容量准入回调、私有依赖图、实际不可变容器ID、启动/就绪与切换事务。旧实例在候选就绪前保持在线，worker停止意图和ID先落盘；启动结果未知时保留旧实例停止状态及端口，不盲目恢复重复消费者。停止事实只允许以已冻结身份更新日志，其他运行字段漂移不得重新冻结为恢复证据。已确认候选失败后须先清理该交付候选，再原ID启动旧worker、就绪探测及旧路由确认。本地整分支入口已接线：`CDS_CANDIDATE_REPLACEMENT=1`启用受控路径，必须同时存在Forwarder实际消费者、容量与归属绑定，否则保留旧实例并报错，不回落旧破坏性流程。候选流程不隐式执行扫描发现的自动数据库写入，涉及此类操作须先有独立确认的迁移或恢复合同。启动/恢复生命周期意图在实际inspect确认后、不可变ID操作前记录，并再次复核租约。恢复已启动但未就绪时记录有界recoveryFailure阶段码并报告待对账，不以存活代替恢复完成。显式取消或取代以租约失效为依据；容器创建拒绝的原始abort reason，以及启动信号/就绪等待返回false，都须先核对租约再归类，保持run、落盘终态与SSE的cancelled一致。恢复探针及最终旧路由ACK也可等待，最终抛出前须再次核对租约，恢复期间取消不能继续返回原失败分类。层内兄弟失败触发的共享abort不构成租约取消，不得把真实失败改写为取消。取消后的未知Daemon结果仍保留旧实例、候选及预留等待对账。启动扫描与自动重启只认已发布服务图的容器名及本实例归属，同branch/profile的候选不能按Docker行顺序覆盖旧实例；查询失败、重复身份或归属未知时保留状态。等待期间服务图已推进时不改后继映射。通用孤儿收割器保留未释放账本中的两图和protected/candidate容器，候选清理须另经不可变ID对账，不能凭run失败或Profile退场按名字停止。未released账本不因run失败或取消成为新写入的通行证：新启动/部署/重启/删除准入须先确认其两图已完成对账；拒绝替换须发生在撤销现有租约前。相同目标并入及pending合并不新建执行者，重放仍重新检查。明确stop仍可取消执行器并请求停止已发布图，但须报告candidateReconciliationPending，不能宣称所有未知候选都已停止或释放预留。直接候选编排同样拒绝本分支旧未释放记录。真实Daemon取消/重启、网络回收、Master直连及其他入口仍未证明；完成对应正式验收后删除本段实施状态说明。

### 新发现制品的默认选择

### 交付请求合并范围与有界待执行目标

整分支与单服务是不同交付范围。同项目、同分支、同Profile（或双方均整分支）、双方实际钉住同一40位提交和相同有效配置摘要，且没有版本/一次性选项时，重复请求才可加入同一在途操作；来源仍按原请求记录。部署入口仅在所选范围全部为exact预构建、路径实际尊重请求提交时声明钉住；源码pull始终取当前HEAD，不以请求里的SHA冒充。缺摘要、短SHA、缓存SHA不能证明同一目标。

阻塞中的请求按项目、分支及Profile分别保留最新目标，不用另一服务覆盖。手动单服务请求只有明确完整提交、摘要且无版本/一次性选项时可以排入部署类操作之后；stop/delete等终止意图保持拒绝，不能在停止完成后自动启动。兼容旧整分支合并规则。每分支最多64个待执行范围，全局最多512个；同范围替换不新增占用，满载明确拒绝新范围，不谎报已排队。完成时仅取无其他冲突在途操作或未消费force-rebuild续约的待执行目标；到期续约先按自身范围清理，整分支须等全部冲突Profile结束。取消分支清理本分支所有待执行范围及保留续约。force-rebuild的deploy续约同样按Profile范围保存，不得被兄弟服务覆盖；续约仅承接本项目、范围和来源的原operationId。到期仅清理与该续约冲突的待执行意图，不能删除无关服务。重放单服务必须调用对应Profile入口，不扩大为整分支；仍重新准入和读取有效配置，不声称保存了不可变配置快照。

后台任务完成和路由内任务完成共用同一个内部重放入口，按原请求的整分支/单服务范围、提交、trigger与来源重新准入；派发前核对原项目与当前分支归属，项目变化或未知、分支矛盾、单服务缺Profile、整分支带Profile或非部署kind均明确丢弃，记录原归属及有界原因，不改归新项目或扩大范围；两处适用相同的有界观察与脱敏规则。内部重放的HTTP 200仅说明收到响应，不能替代部署成功：明确的complete.ok、error、取消、joined/merged受理结果与未知结果分别记录。已受理状态只认joined/merged，未识别或与完成矛盾的operationStatus记为未知，不将started/rejected当作完成；明确error.cancelled保留取消归因。响应中的合法run ID用于关联实际部署记录；不把原始输出、错误响应体或凭据存入派发事件。连接响应头等待最多5秒，整个观察最多30分钟；观察截止只保留一个当前读取等待者，已读日志不累积截止回调；读取保留至多256KiB的当前SSE帧，非成功HTTP响应直接关闭，不全量读入正文。缺终态、断流或超时记录未知，不能据此自动重试、断言Daemon已停止或释放交付预留。观察连接结束不取消实际部署，实际完成仍以持久run和容器对账为准。

单服务精确制品部署在准入前记录本次目标SHA，缺制品失败仍归属于该目标，不得被旧运行提交覆盖；拉取和目标解析完成后重新检查实际租约，已取消的操作记取消，不将后到制品错误记为失败。尚未进入容器执行的取消不触发容器清理，保留旧运行服务；旧运行服务的提交元数据不随失败目标改写。

### systemd启动命令执行边界（P2-06，本地待真实验收）

启动装配将当前共享ShellExecutor传入并await systemd同步。command -v发现路径3秒、daemon-reload与runtime weights10秒、Forwarder restart15秒均在共享Worker执行；库的嵌入fallback限1执行/3排队。单次调用在首次await前冻结unit目标与安装意图，同一实际unit在等待期间只准一个写入者（真实路径与dev/ino同时锁；未创建按真实父目录/basename并解析悬空链接），最多32个不同unit并行请求、无排队或自动重放；冲突/满额明确返回error。备份/写入/reload/权重或restart保持原串行顺序。reload失败恢复旧unit，首次安装失败删除本次文件；执行失败不伪报权重或重启已生效。预览模式仍跳过宿主操作。

这只迁移启动native子进程，不改systemd安装配置，不对共享宿主执行命令；小unit文件仍同步读写，statfs准入迁移见下文，其他文件热点与实际Master性能未闭合。TDD覆盖共享执行接线、held reload不提前继续、失败恢复/首次失败、权重与restart结果、异步目标冻结；实际自更新与平台性能另按正式门槛验收。

实际目标在发现命令前冻结，systemctl保留原请求unit名（linked unit的名字不能用外部文件basename代替），写入前和reload完成后核原路径绑定；改向或未知即error，后续权重与restart不执行；写入前重新登记身份，创建后补inode锁，符号链接/硬链接和目录别名不能绕过同一写入权。无法确定身份明确error，不执行命令；32容量按同步unit调用计数，不按多个身份键计数。实际宿主与重启对账仍待正式验收。

命名兼容依据：[systemd.unit官方文档](https://github.com/systemd/systemd/blob/main/man/systemd.unit.xml)区分load path内alias与路径外linked unit；不能仅由realpath basename推断可启动unit名称。物理锁识别共享文件，但不声称不同hardlink服务名是同一Daemon运行实例。

回滚与首次失败清理在每次写入/删除前核冻结实际路径仍指向本writer已登记inode；文件被换成其他inode或符号链接时保留备份并返回error，不覆盖或删除替代文件。no-drift也先核绑定，权重与restart结束以及成功返回前再次核验；命令在途改向时结果未知、需要Daemon对账，不报告已应用或已重启。结束检查不能撤回已发出的命令，不声称跨宿主外部写入的全局原子锁。

已点名的pending凭证不得因排队期间部署模式变化而失去固定资格：原commitPinned=true时，接收端必须仍为true；原有效configHash存在的精确请求还须指纹相同，模式/运行配置/服务图漂移均拒绝旧请求。未点名manual whole的现有configHash包含已展开缓存SHA，不能用其直接阻止合法缓存推进；本补强不声称未点名配置漂移已冻结，SHA无关的意图指纹仍为待补缺口。历史缺原指纹的兼容记录仍保留，不能补猜原配置。临时说明在完整自动意图/配置门禁接管后退场。

新受理的whole/Profile待部署请求另存pendingConfigHash：使用同一有效配置计算器，将仅用于镜像模板展开的ciTargetSha/githubCommitSha固定为40位零占位后计算，原分支身份、模式、运行参数、服务图与合并env不变。字段只存摘要；不得替代版本的configHash。派发凭证兑换时原pendingConfigHash存在就要求相同，故缓存提交推进不改变该摘要，模式/服务图/运行配置漂移会拒绝。字段为schema1已知可选字段，历史缺字段不猜补；重载历史仍需既有恢复对账。此临时说明由实际意图指纹门禁及完整P3报告接管后退场。


### 待部署可观测投影（P3-01/P3-08，实施前冻结）

现有GET /api/branches/:id通过原项目权限检查后，额外返回pendingDeployments。只按当前Branch的projectId与id投影可靠journal；同id改属其他项目不能继承原项目记录。不得输出actor/requestId/source/reason、配置摘要、环境或派发凭证内容。投影只含原operationId/generation、Profile、trigger、受理时参考提交及点名资格、更新时间、journal阶段、是否待恢复和已经可靠保存的合法run ID；提交参考不当执行提交，claimed/accepted不当Daemon已启动或完成。

### 原待部署请求与实际run关联（P3-01/P3-08，实施前冻结）

经过协调器一次凭证核验并取得当前租约的whole/Profile重放，在任何pull/派发/容器动作前将pendingOrigin v1写入本次实际DeploymentRun：原operationId/generation/Profile与原project/branch范围相配，执行operationId保持新执行编号，不挪用旧编号。不从未核验HTTP header写关联；普通或joined/merged占位run没有该字段。字段不可改绑，历史无字段不猜补；query中字段存在只证明原请求与run关联，执行结果仍以实际run终态及运行证据判定。

关联复用既有run独立draft持久化屏障，最多5秒，可靠ACK后才公开字段并放行；失败/未知/超时不执行外部动作。新await前后核原Branch引用与id/project/branch/worktree/createdAt、当前租约、有效配置SHA中性指纹及原项目权限；cacheSHA/notes变化不拒绝。缺追踪依赖失败关闭。关联阶段失败/取消必须终结本次租约并记录本次run结果，不能漏掉cleanup，也不能清理旧容器；不使用旧active为空、进程消失或HTTP200证明Daemon闭合。

沿用GET /api/deployment-runs，用pendingOperationId+pendingGeneration查询；二者必须同时合法，并指定project与branch（项目凭据可提供项目范围）。先按项目/分支/原op/gen筛选再应用既有limit，不能先裁剪最近run再漏掉原请求。返回仍使用现有run summary/权限与敏感信息投影，不新增路由、不输出派发凭据。旧generation、新项目或其他分支不能继承结果；多条实际匹配按现有历史保留规则如实返回，不猜唯一或完成。此为本地关联实施，不是Master/Daemon安全重放、历史永久保存、UI或正式验收；完整P3历史关联自动门禁接管后退场临时说明。


### 分阶段耗时事实合同（P0-04，实施前冻结）

部署run新增可选timing v1，记录原run/op、同进程测量纪元、阶段、实际观测边界、Profile范围、开始/结束及单调时钟耗时。冻结九阶段：CI runner、CI build、artifact、capacity、pull、startup、readiness、switch、cleanup；不得用可裁剪日志或Branch可变累计反推历史。旧run无字段和未接入阶段均为not-observed/null，不能以0或相邻日志替代。CI排队与构建须有精确provider run/attempt/job证据，推送接收至completed不能直接当runner排队；本地阶段测量不伪造外部CI记录。

每run最多512段并明确truncated；观测边界使用有界枚举，不持久化命令、env、原始异常或任意标签。运行记录始终由原run引用及原op控制；测量段以不可变id和开始事实识别，可靠draft替换内部对象后仍能结束原段；回调失效/重复结束/开始事实改变/重复id/终态/新owner不能写后继，计时本身不能改变动作顺序、重放或取消任务，也不增加准入等待。观察器在run绑定本次执行op后创建。开始以save记录，正常终态沿用run可靠落盘屏障；未结束段在终态/重启收敛时只标unknown，不猜实际外部动作结束时间。测量失败或时钟非法显式无测量值，不影响原业务结果。

并行Profile区间使用同纪元单调偏移取并集作为已观测墙钟区间，另列工作时长总和，不能直接相加冒充用户总等待。开放/unknown/truncated段使汇总带incomplete；汇总分别列completed/failed/cancelled，observed不等于动作成功。completedWallMs只是已观测边界的闭合区间，不是九阶段完整端到端耗时或真实性能pass。每段以commitShaAtStart保留开始时记录中的提交（可能尚未解析），并以run最终目标另行读取，不把缓存提交冒充执行目标。

接入首先覆盖实际whole/Profile的非skip pull、exact artifact准入、源码槽实际onQueued等待，以及候选容量核验、预构建启动、就绪、路由消费者ACK和回收/失败恢复。边界需明确：capacity-check与source-slot-wait不同，runtime预构建启动与源码编译不混合，route-ack只测实际ACK而非整个切换。尚未接入的执行器路径、普通终态之后的收尾、外部CI及页面展示保持缺口，不据局部记录宣布P0-04完成。该临时实施说明在九阶段实际自动门禁与正式P0/P6报告完整接管后退场。
