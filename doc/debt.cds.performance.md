## 2026-10-10 重采与连续测量

只读重采确认 Master 与 Web 仍为昨日止血版本。普通 API 单次约 2.7–5.5 秒，源码队列为空而宿主负载约 35/18 核、可用内存约 45 GiB。完整一分钟事件循环 P99 约 778ms，最长约 2.1 秒；状态复制仍有秒级阻塞。新的 CPU 采样再次命中同步进程创建，主要来自容器诊断和启动准备。提高优先级和减少保存次数未消除永久瓶颈。

新增只读连续窗口测量，保存失败、超时、JSON 形状检查、完整分钟指标、实际版本和部署负载，使用同一统计口径对比前后。采样不足、版本变化或没有足够负载不能当作高峰通过；CPU 归因采样和正式性能窗口分开。工具只增加证据能力，不改变服务器运行行为，也不意味着性能优化已生效。

运行中的基线已出现约 23.6 秒公网长尾和一次 TLS 传输失败。另一时刻本机接口约 0.6–0.8 秒，不能从不同时间的差值推算网络耗时。后续窗口新增连接与首字节累计计时、逐次保存脱敏诊断；首字节等待也含网络，不能直接当作纯服务端处理时间。当前旧窗口保持原协议，不重启或移除失败样本。

长期目标与独立监理按[性能治理蓝本](./plan.cds.performance.optimization.md)和[待办清单](./plan.cds.performance.todo.md)推进。当前独立压力宿主尚未就绪，其他活跃任务也在实施执行隔离与 CI；须核对其实际提交后再集成，不能重复覆盖或把未发布计划视作恢复。

本批进一步修正受理先创建占位记录导致的重复保存和假取消：先判断同目标身份与范围，重复请求等待原受理写盘并沿用原记录；新待办保持排队状态，重放继续同一记录。新目标和终止操作按操作身份及代次更新被替代记录，合法排队不套用执行心跳超时；写盘失败释放相应受理，不启动 Git 或容器。HTTP 覆盖整分支、单服务、原目标回归、受理期间替代和失败路径；候选仍未上线，不表示线上排队与卡顿已解决。

运行记录增加可选范围与代次字段，旧记录保留兼容；当前关联仅覆盖本进程可知的协调器状态。协调器待办与五分钟重放凭据依旧在内存中，异常重启只收敛遗留运行记录，不恢复原队列；其他生产者未关联的待办也须后续对账。实际配置快照、跨范围顺序与全过程容量预算仍未闭环，记录复用不能抵扣 A06/A08 完整验收。

本批跨范围候选进一步复现整分支与单服务待办的覆盖和顺序漏洞。新整分支目标淘汰其覆盖的旧服务待办与尚未到达的派发凭据；新单服务意图保留其他服务，等待较早整分支意图，避免执行后被旧整分支覆盖。派发领取期间仍作为顺序屏障；撞上重建或活动任务时，重放重新排队保留原操作、代次与记录。派发失败立即释放后继，既有每分钟看门狗负责过期领取后的推进；停止和分支移除仍取消其覆盖的全部待办。

五项协调器旧代码反例和两项真实HTTP旧代码反例均失败；候选定向回归通过，Docker及就绪仍用测试替身，定时接线与真实容器环境尚待独立验收。跨范围执行顺序有候选修正，不代表持久化调度闭环；当前重建续接还缺单独消费身份，配置未快照，队列与领取凭据仍不能在重启后恢复。传输失败当前沿既有取消终态，运行记录的取消说明仍过于通用，具体原因展示按 T16 补齐。全过程容量和公平性、标准上线、公网及正式稳定观察仍按原蓝本推进，不签完整A06/A08/A10。

**持久恢复候选（2026-10-11，未上线）**

本批为已受理任务保存配对私有输入，Mongo 使用同一任务实体保存两者，JSON 使用原子文件保存。公开任务与事件不附带私有配置；密钥配置沿用已有封存策略，内容摘要校验请求与完整输入。启动仅恢复可靠配对且尚未领取的排队任务；领取先保存执行身份，再进入 Git 或容器操作。真实子进程强制退出验证原任务与输入恢复，第二次在领取保存后退出不会重复领取。测试还覆盖磁盘写入失败、不可读密钥、内容损坏及内部派发仍保留原机器请求的极速版限制。

此候选不等于 A08 完成：Mongo 多实体写入可能部分成功，受理返回失败与磁盘已存在意图之间须补明确凭据；停止操作没有部署任务记录，持久取消和部分写入恢复须专项闭环。正在执行的任务只收敛为中断，实际实例与版本的重建、续接消费身份、容量、公平性及独立真实容器恢复尚未交付。上述测试包括真实 JSON 和子进程，但 Mongo 与 Docker 仍使用替身，不能抵扣隔离风暴或正式上线。独立 VZ 与 QEMU 环境均启动失败，未修改共享默认环境；后续采用符合冻结资源条件的隔离环境验证，不能在生产宿主补压力证据。

**关键实体持久凭据候选（2026-10-11，未上线）**

旧实现五条反例复现：自己的任务与输入已保存，却被无关记录失败或阻塞误判未受理；写入失败后没有新业务便不再重试；BSON 默认把可选空字段写成 null，破坏恢复身份。候选按本任务精确配对记录确认；写入确认丢失时只接受主节点多数读取匹配的原内容，普通任务更新与导入也保持可选字段语义。保存失败保留脏状态，原五秒窗口内自动对账；故障未恢复时健康检查失败，错误日志不含输入。

专用 CI 的真实 Mongo 和六个强退子进程试验只验证整分支及单服务持久受理、领取和重启协议，结果以固定提交的 CI 产物为准；实际应用部署、容器就绪、网络分区、容量与性能均未验证。写入确认和主节点读取同时不可用时仍存在确认歧义，服务端超时不等于客户端连接硬超时；停止持久取消、续接消费身份及实例恢复仍须补齐。该组件试验不是 T12/T18 或 A08 完整通过，阶段门、线上与冻结 48 小时验收保持原要求。

**停止持久取消候选（2026-10-11，未上线）**

真实 HTTP 复现：停止时取消记录保存失败，本地仍停止容器、远端仍发送停止请求；成功返回后立即读盘，原排队任务仍可能恢复。另复现保存期间其他分支新增历史把待确认取消记录提前裁剪。候选先确认覆盖范围原任务的取消记录，再停止或删除实际实例；保存失败不执行破坏操作，也不确认成功。保存期间保留关键记录，确认结束后恢复正常历史回收。停止者被更新操作取代后不继续处理后续服务或改写最新状态，项目和非重叠服务独立；正常调度降温不套用终止语义。

JSON 文件与真实强退回归已覆盖停止确认后不恢复旧待办；专用 Mongo 演练新增两条取消记录部分成功、失败返回后强退、恢复原未确认任务、再次停止确认及强退后无重放，结果以固定提交 CI 为准。原 f3100a0d4 的真实 Mongo 受理与领取组件证据已由监理独立确认，不抵扣完整 A08。候选没有上线。

仍欠：删除构建配置等批量路径先修改配置、再逐分支尽力清理的最终确认协议；实际停止失败或在途部署退出后的容器与版本对账；普通最终分支状态保存受无关实体失败影响；确认写入与主节点读取同时失败的歧义；续接身份、实际租约时限、多实例恢复与混合版本归属。另须专项复核普通保存与关键保存的交错：普通写入的内存确认缓存可能绕过多数写入升级，当前单实例演练不证明副本集条件下所有关键路径均有持久确认。此批只封住取消记录与物理操作之间的组件窗口，不能把整套终止、容量、就绪切换或线上性能声明完成。

**关键确认与普通缓存交错候选（2026-10-11，未上线）**

普通写入内容相同、本地冷启动缓存相同，都不能证明已经取得本次关键操作的多数持久确认。旧实现五条反例复现假确认或冷启动找不到原任务，另两条复现迟到写入跨越新变更或导入后仍复用旧凭据。候选分开内容缓存与强确认凭据，要求覆盖相关任务最新变更代次；导入撤销此前凭据，迟到旧确认不能恢复它。无关任务和全局更新不迫使已确认原任务重写；删去的任务清理对应凭据。关键写入另设置五秒多数等待时限，但服务器等待时限不代表客户端硬时限。

专用 CI 增加三节点实际 Mongo 演练，暂停本次创建的两个副本，使较弱普通确认已经保存取消、多数读取仍保留原排队内容，再验证关键取消明确失败、恢复副本后重试和冷启动确认。固定提交 9d40a3196 的真实三节点 CI 试验通过，并由监理独立复核：确认不足时明确失败，恢复后重试及冷加载取得多数确认；临时数据库和容器已清理。九次强退恢复与另外两项构建 CI 同样通过。此结论只覆盖限定组件。资源只在专用 CI，随机数据库和归属校验阻止操作共享容器；不部署应用或改变生产环境。

仍欠：读写都不可用时的确认歧义、客户端连接硬预算、导入与在途普通写入整体排序、实际停止及版本恢复。保守全量更新会撤销所有部署凭据，可能增加关键写入成本，须在 T11 收窄真实脏范围并测量。有限确认组件不能替代完整 A08，也不证明页面卡顿、容量和公网长尾已经改善。

**实际停止确认候选（2026-10-11，未上线）**

旧实现四条反例复现：停止命令失败、结果不可读或仍观测到运行，容器层仍返回成功；分支接口进一步写成全部停止和空闲。候选把未确认停止明确作为失败，实际仍运行的服务保留运行事实和错误提示；其他服务继续处理，失败分支与原任务取消先落盘，不增加成功停止统计。副本停止未确认同样不能使整分支接口报告全部成功。失败日志区分已确认与未确认，公开错误不输出原始诊断。

## 构建并发治理 + 两个假设证伪（2026-06-22 专项，实测取证）

用户追问"为什么一个构建要 11 分钟"。在真实实例（18 核 / 96GB RAM）逐项实测：

### 落地：全局构建并发闸（已交付）
- 病根：CDS 每次部署在临时容器里跑 `install + 编译`，**无任何并发上限**。多分支同时部署时 N 个构建一起把 CPU 吃满、彼此饿死。
- 实测铁证：同一分支 admin 构建 isolated ~353s；误触发双部署重叠时被拖到 **636s / 754s**（纯争抢膨胀）。
- 修复：`cds/src/services/build-gate.ts` 全局 FIFO 并发闸（槽位转移防超额），上限 `CDS_MAX_CONCURRENT_BUILDS`（默认 3）。排队状态写进部署日志 + SSE + `/api/cluster/status`，用户看到「排队中，前面还有 N 个」而非疑似卡死。6 个单测覆盖。

### 证伪一：pnpm 跨设备复制 —— 不成立
`/pnpm/store` 与 `/repo/node_modules` 同为 device `2049`（同一 ext4），hardlink 正常工作，**无跨设备复制拖慢**。共享 pnpm store + NuGet 缓存早于 2026-06-20 落地（`cache-catalog.ts`）。

### 证伪二：vite build 并行度被压成 1 拖慢 —— 不成立
同容器顺序 A/B 实测：maxParallelFileOps=1→**353s**，=4→**369s（反而略慢）**。放宽零收益，已 revert。瓶颈在 transform/bundle 的 **CPU 阶段**，非文件 I/O。

### admin 部署构建拆解（baseline 598s）
- vite build ≈ 353s（59%，CPU 固有）；corepack+install+容器开销 ≈ 245s（41%）
- api（.NET）≈ 354s：`dotnet clean`+`--no-incremental` 全量重编，无持久 bin/obj 卷（fresh worktree 必然全编）。改增量无收益且重蹈 MSBuild 增量误判，故不动。

### 结论
admin/api 的编译耗时是 **CPU 固有成本**，I/O/并行旋钮榨不动；可动的是"别让构建互相饿 CPU"=并发闸。再快需减 bundle / 换机器 / 分布式构建。

## 回答用户两个问题

- **"是不是 mongodb 索引问题？"**：当前**不是主因**（热数据在内存环形缓冲）。前端缓慢主要来自**主机资源被 docker 垃圾 + 残留 infra 容器拖满**（CPU 100%）。mongo 索引是**迁移后的将来风险**，应提前补但单靠它解决不了现状。
- **"为什么构建越来越长？"**：**Docker 层 + 构建缓存累积 + 残留 infra 容器**三者叠加 → 磁盘/IO/CPU 逐次恶化。首步已清悬空镜像 + 构建缓存；剩余步（停残留 infra、卷清理、索引、热路径缓存）按上表逐步推进。

## 控制面过载治理（2026-09-08）

**现状**：09-08 线上取证：18 核宿主 load1 26.2 / load15 20.6，49 个托管容器合计 CPU 只有 348%，
负载大头是部署翻车式重建（24h 154 次部署，mdimp-main 一个分支 22 次、每次拆装 14 个容器）、
CI 噪声 webhook（12h 8678 条、91% 不触发动作、每条走完整落盘链）、离机审计外发热循环（连续失败
54256 次、每秒 2 条错误事件）；探活监控一轮 await 卡死 24 小时无告警。本批落地：托管容器挂低权重
slice + 控制面 systemd 权重、同 commit 部署并入、webhook 噪声廉价 ack、审计熔断、探活硬 deadline
与看门狗、构建闸门负载自适应、/healthz pressure 快照。

**仍欠**：

- P1 docker 若用 cgroupfs driver，`--cgroup-parent` 只能归类不能设权重（healthz 会报
  `workload-cgroup-unmanaged`）；正解是切 systemd driver，属宿主运维动作。
- P2 dashboard 的 SSE 流（`/_cds/api/activity-stream`、`/_cds/api/branches/stream`）在约 120s 处被
  外层链路切断后重连（24h 2054 次 502 aborted）；forwarder 与 nginx 模板都不是 120s，来源未查清。
- P2 forwarder 自己被饿死时不会留下任何记录，「打不开」的那几分钟在 HTTP 日志里仍是盲区；现在只能靠
  /healthz pressure 的事件循环延迟与宿主 load 事后回溯。
- P3 mdimp 分支部署反复失败（Flyway 迁移、镜像缺失）是项目侧根因，每次失败仍会拆一遍容器；CDS 侧只能
  靠 joined / merged 减少重复，不能替项目修代码。
- P3 部署运行列表接口的条数上限是 200 且没有翻页游标，窗口内部署超过 200 次时度量尺只能拿到最新的
  200 条。现在会显式把数字标成下界并写明被截断，但要拿到完整计数得给那个接口补分页——那是新契约、
  要动前端消费方，不在本批范围内。
- P3 度量尺脚本只有判据自检（`--self-test` 跑截断判断那一条），整体没有进 CI 的守卫；它取的字段跟着
  接口漂移时不会有人变红。
- P3 不带 commit 的手动部署不参与「同 commit 并入」：它要落地的是执行到拉取那一刻的分支 HEAD，
  分支上缓存的旧 SHA 判不出它到底要部署什么，判错的后果是新提交静默不被部署。所以这类请求维持既有
  语义（按优先级取代或排队），少省一次重复拆装。想吃到并入收益就带上 `--commit`（webhook 天然带）。
- P3 短 SHA 的手动部署同样不参与并入：7 位前缀在同一仓库里可能对应两个提交，无从判断唯一性，
  按前缀并入等于可能把请求并进「碰巧前缀相同」的那次部署。判据收敛为「两边都是 40 位全长且完全相等」，
  要吃并入收益就传完整 SHA。真要支持短 SHA，得在判定前把两边都解析成完整提交 ID——那要在部署热路径上
  加一次 git 解析，与本批「治过载」的目标相悖，不在本批范围。
- P2 executor 宿主上只有容器归组、控制面没有提权：executor 是接入时以后台进程直接拉起的，不走
  控制面那份 systemd 单元，拿不到里面的 CPU/IO 权重与优先级，所以「控制面 1000、容器 100」这个
  保护比在那些机器上不成立。现在健康状态如实报「已归组、未受保护」并说明原因，真要保护得让
  executor 也跑在带优先级的单元里——那要改接入流程与装机步骤，不在本批范围。
- P2 并入判据的身份里不含「只用预构建镜像」这条执行策略：Agent 钥匙发起的受限部署与普通 webhook
  部署即便同提交同配置指纹，落地方式也可能不同（前者被去掉了回退到源码构建的路径）。两者相撞时会
  并入，于是受限那次可能拿到「允许源码构建」的结果，或反过来让 webhook 那次失去它本该有的回退。
  要治得把执行策略并进并入身份，或干脆不跨这两类调用方并入——都是并入语义的扩展。
- P2 被压掉的 webhook 耗时从路由内开始计，而请求到达与 body 解析发生在更早的中间件里，所以这个数
  偏小、与按 HTTP 日志统计的历史口径仍不完全可比。要治得把请求到达时间从日志中间件传进计数器。
- P2 归组只对此后新建的容器生效，升级前就在跑的容器要等下次重建才进组；长命的共享基础设施可能很久
  不重建，那段时间里它们仍与控制面同权。状态已如实声明覆盖面，但要真正全量得巡检每个容器的实际归属
  再逐个重建——那是运维动作（且会造成一次全量抖动），不在本批范围。
- P2 分支面板点「部署并打开预览」时，若恰好并入在途部署，会提示「已并入在途部署」但不再自动打开预览
  （与排队合并走同一条路径）。并入那次跑的是同一份代码同一份配置，本可以跟到它结束再打开。当前是
  降级但有明确告知、用户可自行再点，不是静默失败；要治得在分支列表与详情两处加轮询跟随，是新交互逻辑。
- P2 构建闸门的先来后到在负载回落的间隙会被绕过：老等待者因过载排队后，负载在两次周期复查之间恢复，
  新到的请求会直接拿到空位插到它前面。上限本身不变，影响是排队顺序与「前面还有几个」的显示不准。
  要治得让新请求在有人排队时先唤醒队列再入场。
- P3 「控制面已被提权」目前只看进程落在哪个 systemd 单元下，不读真实生效的权重值。升级既有单元时
  热应用权重那一步允许失败并留待重启，那个窗口里进程已在单元下、权重却还没生效，状态会报「已保护」。
  要治得读有效权重或把热应用结果传下来——新增运行时读取，不在本批范围；窗口仅限「升级且热应用失败
  且尚未重启」这一段。
- P3 恢复演练那条之外，其余自动发生的托管 docker 作业已全部挂上低权重 slice（部署期间的数据库隔离
  克隆、无人值守的定时命令作业于 2026-09-08 补齐）。判断标准是「自动发生的才算日常负载」：
- P3 恢复演练（R2 到 Mongo 的灾备演练）走的是独立命令行入口，没有初始化容器归组决策，它临时拉起的
  Mongo 与随后的导入照旧不在低权重组里。这是手动触发的运维演练，不在本批诊断出的日常负载来源里
  （日常负载是部署、构建、webhook），要治得在那个入口也初始化一次归组决策——独立入口的接线，不在本批范围。
- P2 并入判据复用的 `DeploymentVersionService.computeConfigHash()` 不覆盖全部运行时字段：
  `cacheMounts` / `fallbackImage` 这类会影响挂载与选像的字段不进哈希，所以只改了它们的同 sha
  部署仍可能被并入（改动既不生效也不排队）。改哈希算法会让所有存量不可变版本的 configHash 失效、
  影响版本复用判等，属于既有机制的行为变更，不在本批展开。要治得么扩哈希字段集并处理存量版本，
  要么给并入判据另起一份「完整运行时快照」比较——两条都是新契约。
- P3 构建闸门的负载比用 `os.availableParallelism()` 当分母、`os.loadavg()` 当分子。若将来给
  cds-master 加 CPU 亲和或配额，两者作用域会不一致（分子是宿主全局、分母是进程可用），闸门会偏保守。
  当前 systemd 单元明确不设 CPUQuota / CPUAffinity（本批的前提就是不给上限），所以尚无真实路径；
  哪天要给控制面加 CPU 限制，这两处（`build-gate.ts` 与 `control-plane-pressure.ts`）要同批改。

- P2 宿主过载告警的文案里仍写着「控制面与容器、构建同权抢 CPU」，那是治理前的世界。权重接管成功
  （`weightManaged=true`）之后再冒出这条告警，用户看到的原因与系统自己声明的状态互相打架，会被引去
  查一个已经修好的方向。要治得让这条文案按归组状态分岔：已接管时说「已分权但宿主整体仍过载」，
  未接管时才保留原文。改的是告警措辞与它的取数依赖，不在本批「治过载」的代码路径上。
- P2 构建闸门算出的「这次排队是被负载压住的，不是被上限压住的」（`throttledByLoad` 与当时的负载
  快照）没有传到用户眼前：两处消费方只取了「前面还有几个 / 在跑几个 / 上限多少」，把这两个字段丢掉了。

  回落。要治得把这两个字段接进队列反馈与部署日志文案——是新的展示语义，不在本批范围。
