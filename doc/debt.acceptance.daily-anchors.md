## 文案锚点债务

`PAGES` 里每条路由用一句**产品文案**当锚点，判「这一屏渲出来了没有」。文案归属的页面文件与锚点之间**没有任何机械关联**：

| 锚点 | 归属页面 | 在 CI 过滤器里 |
|---|---|---|
| 选一个智能体开始创作 | 智能体接入台 | 否 |
| 资产库 | 网页托管的分享工作区 | 否 |
| 新建知识库 | 文档空间首页 | 否 |
| 提交缺陷 | 全局缺陷提交弹窗 | 否 |
| 今天做什么图？ | 视觉创作工作区列表页 | 否 |
| 先看见故事，再开始生成 | 视频创作工作台（2026-10-03 新增） | 否 |
| 新建文件夹和文章 | 文学创作作品列表（2026-10-03 新增） | 否 |
| 邮箱通道 | 开放平台标签页（2026-10-03 新增） | 否 |
| 站内通知、待处理事项与外部推送订阅 | 站内通知面板（2026-10-03 新增） | 否 |

后果：**纯 UI 改文案的 PR 一路全绿，第二天例程判红，而页面其实是好的**。2026-09-08 修的那次（锚点还写着改版时已删的「AI 驱动的设计助手」）就是这个形状，只是当时没人意识到它是五条共有的。

## 为什么 PR #1511 没有当场还

按 `CLAUDE.md` §5.5 判为 **B 类（有价值但扩范围）**，且当时已命中 Review 范围熔断（连续 3 轮产生新语义类别 / diff 达首轮 2.75 倍 / 文件范围 3 → 5）。三条具体理由：

1. **它是新语义类别**：今天没有任何一条锚点做源文件交叉校验，加这个等于给守卫新增一项能力，不是修一处缺陷。
2. **只修被点名的那一条会犯「不横扫同类」**：五条同形状，单修一条正是判据与接线纪律里形状 6 明确警告的复发路径。
3. **最直白的实现方式本身就踩形状 6**：去页面源码里 grep 那句文案，属于「扫源码字面量而非求值结果」——正是同一轮 review 前两条批评过的写法。文案还可能被 i18n、被 JSX 拆成多个节点、由变量拼出来，grep 判据会既漏又误。

## 还债时该选哪条路

**不要**做「锚点字符串 ↔ 源文件 grep」的交叉校验。正解是给这五个页面各加一个**稳定的机读标记**，让验收判据不再依赖产品文案：

- 参照网页托管主控台已有的取证范围标记（`data-acceptance-scope`）写法；
- 验收脚本的路由表每条都声明取证范围，判据从「整页计字 + 文案锚点」改成「作用域内有内容」；
- 顺带解决另一笔已知边界：没声明取证范围的路由，字数判据靠外壳恒真（导航外壳本身就够门槛），等于只有锚点那一半在防白屏。

这条路要改产品代码（五个页面各加一个属性），所以是独立一笔工作，不塞进验收脚本的修复 PR。

## 触发条件（何时该还）

满足任一即启动：

- 再发生一次「锚点过期导致例程误报」——说明频率够高，值得上机械保障；
- 有人要给验收路由表加第六条——加之前先把取证范围机制补齐，别再摊一条同形状的债（**2026-10-03 已触发**：为让每日验收覆盖全部核心功能线，锚点表扩到九条，这笔债按原形状又摊了四条；缓解是同批新增的只读接口断言与深度自检——页面锚点过期时，同一功能线还有接口判据兜着，误报只会落在锚点那一行，不会把整条功能线判死）；
- 这五个页面中任何一个要做主文案改版——改版那次顺手加标记，成本最低。

在此之前，现状（锚点 + 每日例程判红）能发现问题，只是发现得晚一天，且需要人来判「是产品坏了还是锚点过期」。

## 附：48 小时冒烟心跳分不清定时与手动运行（2026-10-03 提出，open）

每日验收里「稳定性基线自身」那一行，读的是 CDS 验收中心最近一份「核心业务稳定冒烟 stsmk-…」报告的时间与结论。问题在于：定时运行和手动运行用的是同一个运行器，生成的报告标题、档位、调度模式完全相同。所以只要有人在功能分支上手动跑一轮且通过，这一行就会一直是绿的，哪怕定时那一轮早就停了。

当前 PR 只收紧到「只认运行器自己的标题格式」，排除了「发布验收」这类别的报告；区分定时与手动属于新契约，按 §5.5 归为 B 类，未展开。

还债方式：给稳定冒烟运行器加一个结构化的触发来源（定时 / 手动），归档时写进报告的元数据，每日验收只认「定时」。触发条件：出现一次「定时已停但心跳仍绿」，或要改稳定冒烟的归档逻辑时顺手补上。

## 附：应用依赖（Redis 等）就绪没有每日判据（2026-10-03 提出，open）

每日验收的「对象存储读写就绪」只判 `asset-storage` 组件。`/api/health/ready` 同时还报了 MongoDB 与 Redis 的就绪状态：MongoDB 有后端深度自检的数据库往返项兜着，Redis 目前没有任何每日检查读它。Redis 掉线而其余全绿时，这份报告会是绿的。

PR #1655 第 4 轮评审提出，当时已命中 §5.5 的熔断（连续 3 轮评审都在产生新类别），按 B 类记账。还债方式：新增一行「应用依赖就绪」前置项，逐个组件读 `components`，任一 `ready !== true` 即判失败并点名组件。触发条件：出现一次 Redis 相关故障而每日验收没报，或下次改这批前置项时顺手补上。

## 附：覆盖守卫靠源码字面量，查不出「检查被摘出主流程」（2026-10-03 提出，open）

覆盖守卫判断「每条功能线都有每日检查」，是在主脚本源码里找 `featureLine` 的字面量。如果有人把某个检查函数从主流程里摘掉、但函数本身和兜底补登还留着，字面量照样在，守卫照样绿；而每天的报告里那条功能线只剩兜底补出来的「未执行」。

PR #1655 第 7 轮评审提出，当时已命中 §5.5 熔断，按 B 类记账。还债方式：把各检查登记进一张注册表（检查函数 + 它产出的结果 id + 功能线），主流程只遍历这张表；覆盖守卫改为读注册表，断言台账每条功能线都有注册项、且每个注册项都会被调度到。触发条件：下一次给每日验收加检查，或出现一次「功能线只剩兜底未执行」。
