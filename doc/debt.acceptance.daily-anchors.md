**一句话**：每日验收靠五句产品文案当锚点，而文案归属页面改字时没有任何机械关联会红，锚点过期只能等第二天验收判红才发现。

## 债务的形状

`PAGES` 里每条路由用一句**产品文案**当锚点，判「这一屏渲出来了没有」。文案归属的页面文件与锚点之间**没有任何机械关联**：

| 锚点 | 归属页面 | 在 CI 过滤器里 |
|---|---|---|
| 选一个智能体开始创作 | 智能体接入台 | 否 |
| 资产库 | 网页托管的分享工作区 | 否 |
| 新建知识库 | 文档空间首页 | 否 |
| 提交缺陷 | 全局缺陷提交弹窗 | 否 |
| 今天做什么图？ | 视觉创作工作区列表页 | 否 |

后果：**纯 UI 改文案的 PR 一路全绿，第二天例程判红，而页面其实是好的**。2026-09-08 修的那次（锚点还写着改版时已删的「AI 驱动的设计助手」）就是这个形状，只是当时没人意识到它是五条共有的。

## 为什么 PR #1511 没有当场还

按 `CLAUDE.md` §5.5 判为 **B 类（有价值但扩范围）**，且当时已命中 Review 范围熔断（连续 3 轮产生新语义类别 / diff 达首轮 2.75 倍 / 文件范围 3 → 5）。三条具体理由：

1. **它是新语义类别**：今天没有任何一条锚点做源文件交叉校验，加这个等于给守卫新增一项能力，不是修一处缺陷。
2. **只修被点名的那一条会犯「不横扫同类」**：五条同形状，单修一条正是判据与接线纪律里形状 6 明确警告的复发路径。
3. **最直白的实现方式本身就踩形状 6**：去页面源码里 grep 那句文案，属于「扫源码字面量而非求值结果」——正是同一轮 review 前两条批评过的写法。文案还可能被 i18n、被 JSX 拆成多个节点、由变量拼出来，grep 判据会既漏又误。

## 还债时该选哪条路

**不要**做「锚点字符串 ↔ 源文件 grep」的交叉校验。正解是给这五个页面各加一个**稳定的机读标记**，让验收判据不再依赖产品文案：

- 参照网页托管主控台已有的取证范围标记（`data-acceptance-scope`）写法；
- 验收脚本的路由表每条都声明取证范围，判据从「整页计字 + 文案锚点」改成「作用域内有内容」；
- 顺带解决另一笔已知边界：没声明取证范围的路由，字数判据靠外壳恒真（导航外壳本身就够门槛），等于只有锚点那一半在防白屏。

这条路要改产品代码（五个页面各加一个属性），所以是独立一笔工作，不塞进验收脚本的修复 PR。

## 触发条件（何时该还）

满足任一即启动：

- 再发生一次「锚点过期导致例程误报」——说明频率够高，值得上机械保障；
- 有人要给验收路由表加第六条——加之前先把取证范围机制补齐，别再摊一条同形状的债；
- 这五个页面中任何一个要做主文案改版——改版那次顺手加标记，成本最低。

在此之前，现状（锚点 + 每日例程判红）能发现问题，只是发现得晚一天，且需要人来判「是产品坏了还是锚点过期」。
