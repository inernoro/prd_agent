# MAP 核心业务稳定基线 · 设计

> **版本**：v1.1 | **日期**：2026-08-03 | **状态**：开发中

## 一、目标

无论团队如何并行开发，P0/P1 业务功能都必须有可追踪的业务链路、固定版本测试计划、双环境证据、失败通知和可执行回滚。入口能打开只代表第一层可用，不代表上传、生成、恢复、产物和清理已经通过。

本体系行业归类为 Synthetic Monitoring，项目内名称为“稳定冒烟”，自动化标识为 `stable-smoke-48h`。

## 二、权威产物

| 产物 | 权威位置 | 用途 |
|---|---|---|
| 业务功能台账 | `.claude/skills/stable-smoke/reference/business-function-catalog.json` | 功能线、面包屑、代码映射、双环境策略、用例、清理和回滚 SSOT |
| 用例矩阵 | `.claude/skills/stable-smoke/reference/test-matrix.md` | 正向、负向、恢复、产物和清理断言 |
| 永久回归台账 | `.claude/skills/stable-smoke/reference/regression-ledger.md` | 逃逸问题只出现一次 |
| 固定版本计划 | `scripts/stable-smoke-plan.mjs` 生成的本地运行产物 | 固定 catalogVersion、commit、功能线和 caseId |
| 48 小时执行器 | Codex 桌面端本地自动化 `stable-smoke-48h` | CDS 环境后正式环境、证据保留和 MAP 通知 |
| 验收报告 | CDS 验收中心与同轮本地运行目录 | 按模块记录结果、证据、差异、清理和恢复动作 |
| 发布与回滚记录 | CDS ReleaseRun | 固定 commit 发布、current/previous、健康检查和回滚审计 |

## 三、业务功能线模型

每条功能线必须记录：稳定 id、业务名称、P0/P1 等级、负责人、三层以上面包屑、入口路径、自动化现状、required caseId、active regression、源代码前缀、CDS 环境策略、正式环境安全策略、产物断言、清理动作和回滚动作。

业务面包屑描述用户实际完成工作的链路，例如：

```text
首页 → 视觉创作 → 添加两张或三张参考图 → 组合描述 → 生成结果
```

代码变更通过 `sourcePrefixes` 映射功能线。PR 自动纳入受影响功能线并追加所有 active 永久回归；48 小时任务固定纳入全量。核心代码无法映射时门禁失败，要求先补功能台账，避免新功能进入系统却没有稳定性责任。

## 四、复测手段

| 层级 | 手段 | 主要发现 | 通过标准 |
|---|---|---|---|
| L0 | 目录校验、静态检查、单元和协议测试 | 字段漂移、协议错配、错误文案泄漏、变更漏映射 | 全部通过，P0/P1 变更均有功能线 |
| L1 | API 链式测试和 Playwright 合成登录 | 登录、权限、阶段、状态恢复、移动端入口 | 业务状态和用户文案正确，不只检查 200 |
| L2 | 最小真实产物与视觉验收 | 模型、上传、生成、尺寸、遮挡、真实结果 | CDS 环境全量，正式环境安全变体，产物可读取 |
| L3 | 清理、双环境差异和 CDS 回滚演练 | 数据污染、配置漂移、无法恢复 | 残留为零；版本和回滚记录可追溯 |

CDS 环境允许完整正向、负向、故障恢复和清理。正式环境只使用 `stsmk-` 专用资源、最低成本真实产物和自然失败，不主动关闭 Provider、打满限流或修改真实用户数据。

## 五、48 小时节拍

Codex 桌面端本地自动化使用 `RRULE:FREQ=DAILY;INTERVAL=2;BYHOUR=2;BYMINUTE=17`，按 `Asia/Shanghai` 每 48 小时唤醒。同一时刻只允许一轮，先跑 CDS 环境，再跑正式环境。CDS 环境发生 P0、数据污染或清理失败时，正式环境只执行只读健康检查。

自动化执行环境必须是 `local`，工作目录固定为 `/Users/inernoro/project/prd_agent`。调度不依赖 GitHub Actions；CDS 只负责 CDS 环境、部署状态和预览入口证据。自动化创建后必须立即手动运行一次，不能把“提示词或代码已存在”等同于“定时任务已经运行”。

## 六、账号与凭据

| 层级 | 保存内容 | 保存位置 | 禁止项 |
|---|---|---|---|
| 仓库 | 变量名、账号命名和配置规则 | `.env.template`、技能文档 | 真实密码、密钥、token、一次性票据 |
| 本机 | CDS 与正式环境独立密钥、独立账号 | git 忽略的 `.env.stable-smoke.local` 或本机安全存储 | 提交、复制进报告或写进自动化提示词 |
| CDS/正式 | 合成登录开关、白名单和部署密钥 | 环境部署密钥 | 全局密码破窗 |
| 数据库 | `stsmk-` 专用用户和隔离资源 | 各环境自己的用户库 | 使用日常真人管理员做无人值守测试 |

合成登录使用 1 至 5 分钟单次票据和最长 30 分钟不可续期会话。每轮先检查账号存在、启用、白名单和权限；账号问题归类为 environment，报告和通知必须给出恢复动作。

## 七、失败处理与通知

```text
失败 → 保留首轮证据 → 最多一次确定性重试 → 分类 → 阻断对应功能线
     → MAP 定向站内通知 → 修复 → 新增 REG caseId → 双环境复测 → 关闭
```

失败分为 product、environment、flaky、test、cleanup。conditional 或 fail 必须发送到 `map.ebcone.net` 的 MAP 站内通知，内容包含模块、caseId、环境、requestId、证据地址和恢复动作。通知必须定向配置用户；缺少目标用户 ID 时拒绝发送，禁止退化为全员通知。本体系不发送 Slack。

## 八、发布、紧急态与回滚

正式发布和回滚统一通过 CDS ReleaseRun：发布固定 commit 和不可变产物，完成预检和公网入口验收，成功后保留 `current` 与 `previous`。毁灭性问题触发紧急态时，先暂停对应写入或禁用异常 Offering，再由 CDS 选择上一个成功版本回滚；回滚完成后重复入口、真实产物和数据完整性检查。

回滚不是删除记录或手工覆盖服务器文件。发布、失败、回滚目标、操作者、时间、健康检查和最终入口都必须保留在 CDS 审计链中。

## 九、验收报告契约

每轮报告按模块列出：功能面包屑、环境、caseId、执行结果、阶段或产物断言、requestId、截图或日志证据、清理结果、恢复动作和双环境差异。结论只有 pass、conditional、fail；任一必跑功能线未运行、真实旅程仍为 planned 或证据缺失时最多为 conditional。

视觉证据通过标准验收技能归档到 CDS 验收中心，不把报告图片提交到 `doc/`。本地运行目录按策略清理，CDS 报告和永久回归台账长期保留。

## 十、补充治理

- 成本预算：正式环境按模块设最低成本和单轮上限，超出即停止写入并报告。
- 数据隔离：所有写入使用 `stsmk-` 前缀、独立工作区和幂等清理。
- 依赖预检：模型健康、配额、对象存储、ASR、浏览器和域名证书在执行前检查。
- 抖动治理：唯一一次重试通过仍记 flaky，连续出现升级为稳定性问题。
- 变更治理：新增功能、模型、协议、输入格式或错误恢复路径时，同一提交更新功能台账和 caseId。
- 完整性声明：当前入口和协议自动化不等于真实旅程全覆盖；未补齐部分必须持续显示为 conditional。
