# 公共藏书阁 · 结业考 · 判定口径

> **版本**：v1.0 | **日期**：2026-09-16 | **状态**：已落地

**一句话**：结业考是尺子不是闸门，所以同一个分数在读过和没读过两种情形下是两个结论，看板只认读过再考过的那一种。
**谁该读**：接手藏书阁看板或考试的工程师；要改及格线、改「通关」定义的人。
**读完能做什么**：说清一次成绩从交卷到落库要过哪几道判据，以及为什么「取更好的那次」不能只比分数。

---

## 为什么考试不设门槛

一本没读也能考。这不是漏洞，是定位：**「已读」是用户自己点的勾**，没有任何东西能证伪它。
给考试加一道「读完才准考」的闸，唯一的效果是逼人先点一批假已读——把仅有的真实记录也污染掉。

所以门槛不设，改为把上下文记进成绩里：交卷那一刻这一卷已读几本、共几本。同一个 5/7，
裸考说明「底子在、这两处判断还没形成」，读完 11 本还错说明「这两处没读透」——
两句话指向完全不同的下一步。尺子必须说清它量的是什么。

## 三种姿态与「通关」的定义

| 姿态 | 判据 | 看板怎么算 |
|---|---|---|
| 裸考 | 交卷时这一卷一本没读 | 单独计数，**不计入通关** |
| 部分 | 读了一部分 | 及格即通关 |
| 结业 | 整卷读完才考 | 及格即通关 |

裸考不计通关的理由很直接：读完整卷的人和一本没读的人在看板上显示成一样，那个数字就废了。

## 「取更好的那次」为什么不能只比分数

成绩合并的第一版判据是「正确数更高才盖掉旧的」。它漏掉了一整条真实路径：

```
一本没读，先摸个底 → 考了满分（裸考，不计通关）
  ↓
认真读完整卷 11 本
  ↓
再考一次 → 还是满分 → 正确数没涨 → 这一次被丢弃
  ↓
已读数永远停在 0 → 看板上永远不通关
```

用户做对了每一步，系统给不出他应得的结论，而且他无从知道自己卡在哪。

同一个判据反过来也错：已经通关的人再裸考一次，只要分数高一点就会把记录**降级**回裸考。

所以判据改成两级：**先比这一次算不算通关，同档再比正确数**。裸考升级为结业是一次升级
（哪怕分数没涨），结业降级为裸考不是（哪怕分数涨了）。

## 及格与否由服务端算

前端有一份及格线，只负责交卷那一屏的即时反馈。**落库的结论不接受前端送上来的布尔值**——
接口是公开的，客户端可以提交「0 分但已通过」。服务端按自己的及格线重算，请求体里那个
`passed` 字段只为兼容旧客户端保留，读不读它都不影响结果。

同样的不信任还有两处：正确数越界（负数、超过总题数）整条丢弃；已读本数为负一律按 0 处理
——宁可少算一次通关，不许凭前端一句话虚增。

## 取舍与已知边界

- **及格线有两份**（服务端 `BookshelfExamScoring.PassRate`、前端 `exams.ts` 的 `PASS_RATE`），
  改一处要改两处。接受这份判据分裂，是因为另一条路是把及格线塞进接口让前端告诉服务端
  「我及格了」，代价更大。
- **已读数是快照，不是实时值**。交卷之后再去读书，不会让那次成绩回溯升级——要升级得再考一次。
  这是有意的：成绩记录的是「你在那个状态下答成什么样」。
- **卷 id 是不透明字符串**，服务端不校验它是否还在书单里。内容侧删一卷不该让存量成绩报错。

## 判据落在哪

| 判据 | 位置 |
|---|---|
| 及格线、通关口径、取更好的那次 | 服务端的结业考评分类（唯一权威） |
| 同一套口径的展示侧副本 | 前端藏书阁库里的考试上下文模块 |
| 守卫 | 后端结业考评分单测、前端成绩合并单测；把判据退回「只比分数」两边都会红 |
