# OpenDesign 接入 · 债务台账

> **版本**：v1.0 | **日期**：2026-09-11 | **状态**：开发中

**一句话**：记录 OpenDesign（无头设计编排器，负责拆解设计任务并驱动工具改文件）接入过程中交付时已声明的已知边界——哪些断言还没被真实跑过、哪些环境结构上就验不了、以及哪几个坑下一个人容易原样再踩一次。
**谁该读**：接手把这套东西推到能发布的人；以及验收时想知道「这一条到底验没验过」的人。
**读完能做什么**：不重复已经排除的可能性，不把别人的锅算进自己的改动，并且知道每条欠账要怎样才算还清。

## 一、还没被真实跑过的断言

| 欠账 | 现状 | 怎样才算还清 |
|---|---|---|
| 「工作室真的开张」的后半句 | 运行时可用性已由产品自身代码判定为可用（换回旧销钉即判不可用并给出具体理由），但「选定模型 → 真的生成出文件 → 审计里记的是同一个模型 → 一个任务标识串起四段证据」这一整条从没跑过 | 在一个能起容器的共享环境里完整跑一次，并由独立方出具地址可打开的报告 |
| 其余五步 | 都只有候选实现与本地测试，没有任何一步取得过独立验收报告 | 各自按计划里的「最直白的通过方式」跑通并留证 |

## 二、环境结构上的缺口

**预览型实例验不了这个功能。** 用于验收平台自身界面与接口改动的那类预览实例，故意禁用了宿主的容器操作命令。而本功能全部依赖容器操作去准备镜像、执行能力探针、启动会话容器。所以把特性分支部署成一个这样的实例**不能**用来验收本功能——它能证明服务启得来、路由注册得上，仅此而已。

这不是配置错误，是那类实例的设计定位。要验本功能，需要一个具备容器能力的实例运行该分支代码；现实里只有生产那套具备，而让它切到未合并分支会影响所有在用的人。**这条目前没有干净的解法，属于平台能力缺口，不是本功能的缺陷。**

## 三、容易原样再踩的坑

| 坑 | 表现 | 下次怎么避开 |
|---|---|---|
| 判据只验形状不验来源 | 供应链守卫断言销钉「长得像一个摘要」即放行，于是销钉与构建描述漂移了整整一批提交都没人发现，全程绿灯 | 凡是「指向一个外部产物」的判据，必须真的去取那个产物验一次，不能只验标识符的格式 |
| 拿未授权响应推断路由是否存在 | 子实例对目标接口返回未授权，看似说明它认得这条路由；实测对一条瞎编的路径同样返回未授权——鉴权排在路由之前 | 任何「某响应说明某事」的推断，先用一个必然为假的输入做对照实验 |
| 给探针加「标准错误必须为空」 | 只读文件系统下工具会往标准错误打一行无法创建别名的告警，不影响退出码 | 判据只看退出码；要看输出就得先确认正常路径下输出是什么 |
| 守卫自己没接上线 | 流水线的路径过滤不含被守文件，「只改那个文件」的改动根本不触发守卫 | 加守卫时问一句：只改被守文件、不碰守卫本身的那个改动，这条守卫会跑吗 |
| 环境失败与目标失败同码 | 校验脚本第一版在容器守护进程不可用时也返回 1，读者无法判断是守卫发现了问题还是守卫没跑起来 | 环境类失败与判定类失败用不同退出码 |

## 四、不属于本功能但撞见的

**共享库字段漂移打挂了本分支的一个服务。** 本分支预览环境里网关服务崩在启动阶段，原因是共享数据库中存在别的部署写入的新字段，本分支的类反序列化不了。时间戳早于本轮全部改动，与本功能无关，本轮未处理。

这是共享基础设施的老问题在新场景的又一次显形，判据与台账见跨项目隔离规则里的共享数据库通道。

### 撤回一条误判：分支预览的 admin 其实是跟着源码重建的

先前在这里记过一条「分支预览的 admin 不跟随源码重建，这个分支上任何前端改动都没法
在预览上验收」。**这条是错的，已撤回。**

错在取证方法，不在结论表述：我只取回了入口 bundle 去搜 `resolvedModel`，而本轮改动
落在路由级懒加载 chunk 里，入口里本来就不会有；`resolvedModel` 还是个标识符，
express 模式的镜像构建开着 minify，它会被改名——**用一个会被重命名的符号，去搜一个
它本来就不在的文件，搜不到是必然的。**

改用「本 PR 才引入的字符串字面量」重新取证，结论相反：
`assets/WebPagesPage-*.js` 命中 `网页生成已取消` / `producedArtifactSiteId`，
`assets/SiteEditPanel-*.js` 命中 `AI 正在生成隔离草稿` 与徽章那行的 class——
这些字符串在 origin/main 上一次都不出现。admin 跑的是 express 模式，
镜像 `sha-b9109e5ff...` 与分支 head 对得上，前端代码确实在预览上。

那么徽章当时没出现的真实原因只有一个，就是同一天修掉的那条：
`PublicGenerationStreamEvents` 白名单里没有 `model`，事件在出口被丢掉了
（形状 2，链路只建一半的第三段）。

留在这里当教训：**判据取值取错了对象，会把一个已修好的链路报成一个不存在的环境故障，
并让下一个人绕路去查 CDS。** 对照 `predicate-and-wiring-discipline.md` 形状 6——
我扫的是「一个真实存在但不生效的文件」，日志里一切正常，只有把它和真正生效的那份
并排放才看得出不是同一个东西。

### 一、OpenDesign 运行时的实际模型无法可信上报（P1，但当前无解）

`runtime=open-design` 的那条完成路径只产出 `delta` 与产物文件，从不产出 `model` 分片，
所以 OpenDesign 跑出来的 run，`ResolvedModel` 恒为空，两个面板都显示不出模型。

为什么不在本 PR 顺手补：

1. **值的来源在进程外**。MAP 内置执行器的模型来自网关 `Start` 分片的解析结果——那是网关
   自己说的、经过模型池换人与故障转移之后的真值。OpenDesign 的模型调用发生在 CDS 容器里
   （容器内的 Codex CLI 直接打网关），MAP 这一侧根本收不到 `Start` 分片。
2. **容器自报的值不算证据**。要让远程结果带上模型，最直白的做法是让容器报一个字段回来。
   但 `ai-model-visibility` 第 2 条要的就是「值来自网关解析、不许推断」——一个跑第三方 CLI
   的沙箱自报的字符串，性质上是推断不是解析。真要做，正解是按会话去查网关自己的调用记录，
   那是另一套机制。
3. **跨三层的协议变更**。哪怕决定做，改动要穿过容器 → CDS daemon → 工作区结果包 →
   `agent-workspace-session-runtime.ts` → `remote-hosts.ts` → MAP 的会话接口，是新的跨服务契约。
4. **无法验证**。OpenDesign 端到端一次都没在真实 CDS 上跑通过（见本 PR 的风险段），
   这条路径上写的任何代码都没有办法证明它对。

**下一步**：等线上 CDS 自更新到含 OpenDesign 半边的构建、端到端真跑通一次之后，
再按「查网关调用记录」而不是「信容器自报」的思路补这条可见性。在那之前，OpenDesign 的
run 显示不出模型是已知边界，不是回归。

**2026-09-16 补**：同一处（`DesignArtifactExecutor.cs` 远程 `Done` 分支）已被自动 review
提了三次，而那一行源码此前一个字都没写——答案只活在 PR 描述与本台账里，换一个 head 重新扫
就会再提一遍。已把上面四条理由压成一段注释锚在那个 `yield return` 之前，并指回本节。
判据同批复核过一遍仍然成立：`workspace.Model` 是发给容器的**请求**值（`StartAsync` 的入参），
不是 `GatewayStreamChunk.Start.Resolution` 那种经过模型池换人与故障转移之后的**解析**值，
拿它去填徽标等于把请求冒充成结果。

## llmgw-serve 的就绪声明其实没在评估依赖（2026-09-15 发现，2026-09-16 已按用户授权落地）

CDS compose 给 llmgw-serve 声明的就绪路径是 `/gw/v1/readyz`，
但这条声明**一次都没有真的执行过**：readyz 带密钥门，而 CDS 的探针是匿名 GET
且把一切 < 500 当就绪——401 也算就绪。所以实际行为等价于「HTTP 端口起来了」，
Mongo 等依赖是否可用从未被门控。这是一份看起来成立、其实不成立的证据
（`predicate-and-wiring-discipline.md` 形状 8）。

**为什么不在本 PR 顺手改**：这个状态是两条**各自刻意**的契约合起来造成的，
且两条都有守卫钉死：

| 契约 | 守卫 |
|---|---|
| llmgw-serve 必须声明 `cds.readiness-path: "/gw/v1/readyz"` | `DeploymentStorageProviderContractTests`、`GatewayDataDomainGuardTests` 各一处 |
| readyz 不许脱离密钥门（不许把它加进免鉴权白名单） | `GatewayDataDomainGuardTests` 的 `Assert.DoesNotContain("!path.StartsWith(\"/gw/v1/readyz\"")` |

动其中任何一条都要作者决定，且改测试去迁就改动就是把守卫改到能过。三个候选：

1. **给 CDS 探针加鉴权**——最贴近本意，但改的是 CDS 核心探针语义，影响所有项目；
2. **另开一条匿名的脱敏就绪路由**（只回 ready/not-ready，不吐依赖细节）——不碰 readyz
   的密钥门，但新增一处公网可达面，要单独评估；
3. **把声明改成 `/gw/v1/healthz`**——一行，让声明与事实对齐（真实行为本来就等价），
   但要同时改掉上面两条契约断言，等于承认「这里只做存活检查」。

**曾经试过方案 3 并撤回**：本 PR 第六轮先按方案 3 改了 label，全量 `dotnet test`
撞红那两条契约断言才发现它不是一行改动。记在这里，免得下一个人再走一遍。

### 2026-09-16 结论：走方案 2，并且真正的根因不是「两条契约打架」

用户把这条的决定权交回来之后重新查了一遍，上面那张「两条契约」表描述得不完整。
把两条契约摆在一起看，它们并不矛盾——矛盾的是**同一个 `cds.readiness-path` 被两个
要求正好相反的消费者共用**：

| 消费者 | 要什么 | 能带密钥吗 |
|---|---|---|
| 容器就绪门控（`container.ts` 的 `probeHttp`） | 只要一个状态码 | 不能，它是匿名 GET |
| 凭据轮换（`infra-credential-rotation-runtime.ts` 的 `verifyReadiness`） | 逐组件明细，判 `gateway-mongo` | 能，它从容器 env 里取得到 key |

一个字段当两件事用，才是这条修不动的原因。所以三个候选都不够：方案 1 改 CDS 核心探针
语义、影响所有项目；方案 3 直接放弃依赖门控；方案 2 对，但还要把那个共用解开。

落地的是**方案 2 + 解耦**：

1. serving 新增 `/gw/v1/healthz/ready`——匿名、与 `readyz` **判据同源**（同一个
   `IGatewayServingReadinessProbe`），区别只在端出多少：只用状态码表态（200 / 503），
   正文只有 status / commit / time，没有组件名、耗时与摘要。`readyz` 的密钥门与明细一字未动。
2. `cds.readiness-path` 指向这条脱敏路由，容器就绪门控从此真的在按依赖门控。
3. 凭据轮换不再要求「声明的路径等于我认得的那条」（原先用 `contract_mismatch` 把两件事
   焊死，就绪声明一改它就炸），改为按形态取自己那条深检路径。

**匿名可达为什么安全**：就绪探针自带缓存（`LlmGateway:Readiness:CacheSeconds`，默认 10 秒）
与单飞锁，一个缓存窗口内最多真探一次，构不成打穿依赖的放大面。脱敏口径与
`/gw/v1/healthz/deep` 完全一致——那条早就是匿名的，理由写在它自己的注释里：
CDS 的探针刻意不携带任何密钥，要鉴权它就永远打不进来。

**守卫**：就绪声明必须指向匿名那条且不得指回 readyz；脱敏路由必须存在、必须按状态码表态、
不得端出组件明细；白名单必须精确匹配（退化成前缀放行会让 401 重新冒充就绪）；
轮换深检在声明为脱敏路径时仍须打带密钥的 readyz。四处分别撤回都当场变红。

## 两条「该由服务端定的事，现在在浏览器里推断」（2026-09-15，已按作者指示落地）

Codex 在 `b09fb61` 上报的两条，形状完全一样：一个只有服务端知道的结论，
现在由前端拿一个近似的代理量去猜。两条都不是一行能改的，都要在响应里加字段。

### 一、分享页的「站点编辑坞」门开错了

判据是 `isOwner = data.createdBy === currentUserId`——那是**谁建了这条分享链接**，
不是**谁能编辑这个站点**。后端明确允许团队编辑者创建分享，所以：站点真正的主人
和其他有编辑权的成员反而进不去编辑坞，只会被引导去「存一份副本」；而一个没有
编辑权、只是建过链接的人却会看到它。

判据本身是存量的（main 上就有，原本服务于「非创建者 → 存副本」那类提示，在那里
它是对的）。本 PR 把它**复用成了一道新的门**，这才是问题所在。

不是安全洞：真正的编辑接口在后端仍然鉴权，这里只是入口给错了人。

修法要在分享响应里带上「当前访问者对这个站点能不能编辑」，由后端算完给结论。
这个方向恰好是同一个 DTO 自己的注释写过的原则：「已由后端把取舍完毕，前端不要
再自己合并一遍（那正是判据分裂的起点）」。

### 二、生成任务的目标空间没落到服务端

在团队空间发起「引用知识生成」，归属目前发生在浏览器的完成回调里。用户在终态事件
到达前关掉页面或切走，服务端照样把站点生成完，但它会留在个人空间；换个标签页恢复
也重建不出原来的目标。回调还可能读到「现在选中的分组」而不是「发起时的分组」。

本 PR 已经做的是「浏览器还在就归属正确」（含发起时快照空间、深链路径补快照），
这一半是真的修好了。剩下的一半——把目标冻结进 run 请求、由服务端建站时应用——
是跨前后端的契约改动。

### 落地结果（作者拍板后同 PR 完成）

两条一起做，因为它们是同一个决定的两面：**哪些结论必须由服务端给**。

第一条：分享响应的每个站点带上 `viewerCanEdit`，由后端用编辑端点那同一道角色门算出来，
匿名恒为 false；判定抽成 `CanEditSiteAsync`，编辑入口自己也改走它，两处不可能再分叉。
前端编辑坞的门换成这个字段；「存一份副本」那类提示仍用 createdBy——在那里它问的正是
「这条链接是不是我建的」，两个判据服务的是两个问题。

第二条：目标团队随创建请求冻结到 run 上，**在用户还在场的那一刻**就用
`CanPublishIntoTeamAsync`（与 SetSharedTeamsAsync 同一条判据）校验，不通过当场 403；
建站时由服务端应用。应用失败不让整轮失败（站点已经建好了），但也不静默：原因写在
run 上并随终态事件下发，前端照旧提示「已生成，但归属团队失败」。

**仍留在浏览器里的那一层（已知边界）**：分组归属。它依赖「当前视图的分组」，服务端不知道；
而且丢了只是没进文件夹，网页仍在团队空间里看得见，与「整个站点从列表里消失」不是一个量级。
要把它也挪到服务端，得先把分组归属那套权限判断从 controller 里抽成服务方法——那是另一次
重构，不在这次范围内。

## 删除围栏挡不住「删除期间新开始的一次发布」（2026-09-15 发现，2026-09-16 已按用户授权落地）

站点删除的围栏是「内容版本与更新时间都没变过」。但本 PR 新引入的借用登记只改
「发布中的键」与租约字段，不碰这两个值——所以「读站点」与「登记键」这两步一交错，
删除就会拿着过期的键清单成功执行：发布方随后把对象传上去，却发现站点没了，
键也释放不掉，那批对象既不在删除任务的清单里，也没有任何人认领。

看起来一行就能补：把「发布中的键」一起写进删除的比对条件，变了就重试。但顺着往下走
会撞上第二个问题——重试时重新采集的键清单只含「当前文件」与「待清理键」，仍然不含
「发布中的键」，于是重试多少次都补不进去。真要补全，就得把发布中的键也算进删除清单；
而这批键在借用场景里**恰恰是源站自己的文件**（保存分享时借用源站对象正是用同一套登记），
把它们扫掉等于在别人读取途中把源文件删了。

也就是说：这道围栏该怎么与借用登记共存，是一个要一起想清楚的并发设计，不是给谓词
多加一个字段。在想清楚之前贸然加字段，比现在这个窗口更危险——现在至少只在一个很窄的
交错时刻漏对象，改错了会在正常的保存分享流程里删源站文件。

现状影响：需要「删除」与「发布或保存分享」几乎同时发生才会命中，且后果是对象残留，
不是数据错乱或越权。

### 2026-09-16 结论：上面第二段理由是错的，正解比设想的小得多

用户把决定权交回来之后重读代码，**上面「重试时重新采集的键清单仍不含发布中的键」不成立**：
`ReservePublishKeysAsync` 同时往 `PendingAssetCleanupKeys` 与 `AssetPublishInProgressKeys`
两个数组里写（`HostedSiteService.cs` 的 `AddToSetEach` 两行紧挨着），而重试时采集的
「当前文件 + 待清理键」本来就覆盖了发布中的键。当时把这两个字段看成互不相交了，
于是顺着一条不存在的死路推出「必须把发布中的键并进删除清单」，再由那条死路推出
「会删掉源站文件」的风险。两层推论都建立在同一个读错之上。

真正的缺陷形态是教科书式的 check-then-act：读取时那道租约判断（「租约未过期**且**
有发布中的键 → 推迟删除」）本身完全正确，它只是**没有和删除在同一次原子操作里**。

所以正解是把那道判断原样并进删除围栏，判据逐字一致，**键清单一个字都不用改**：

- 登记落在「读站点」与「删除」之间 → 围栏不匹配 → 抛「站点内容在删除期间发生变化」→ 重试；
- 下一轮读取时看到活跃租约 → 走既有的推迟分支，按租约到期时间重排。

因为键清单没动，「在别人读取途中删源站文件」的风险从一开始就不存在——租约的语义是让
删除**等**，不是让删除**跳过或扫掉**这些键。

**守卫两层**（CI 默认过滤跑不到 `Category=Integration`，只写集成用例等于守卫没接上线）：
结构层断言渲染出的查询里租约与发布中的键以「或」的形式在场，且围栏里不出现任何键清单比对；
真库层六例覆盖 Mongo 里 `null` 与「字段整个不存在」的判定差别、租约过期、键已释放但
时间戳未回拨、存量无字段文档仍可删。撤回围栏条件时两层各变红一条。

## 第十六轮复审（2026-09-15，head `0bbb19c`）

三条 P2，两条按 A 类修掉，一条按 B 类记这里。

### 一、远程会话处置：登记账本失败后回不到直接停止（A 类，已修）

`OpenDesignRemoteArtifactExecutor.ExecuteAsync` 的 `finally` 里，直接停止写成了挂在
「登记账本」分支上的 `else if`。于是只要走过完成事件那一支，账本登记失败就再也落不到停止：
返回 null 落不到，抛错被外层 catch 吞掉同样落不到。而 `RecoverPendingStopsAsync` 的候选
条件是 `CleanupRequestedAt != null`——没有账本的会话它一条都捞不回来，远程容器会一直占着
直到 CDS 自己的生存期上限。

复审给的成因（「完成轮次谓词不匹配且无人抢先登记」）其实不对：那一支 `ScheduleStopAsync`
抛的是 409，不是返回 null。真正能返回 null 的只有会话文档不在了；而抛错那条路径
（完成事件缺 `clientMessageId` 或 `CdsSessionId` 时的 502）才是会真实漏掉会话的入口。
成因不同，缺陷形状相同，照修。

修法是把处置决策抽成 `DisposeRemoteSessionAsync`（与同文件 `WaitForSessionReadyAsync` 同一
写法，收委托），登记失败一律往下落到直接停止。这里敢无条件停止，是因为会话由 `ExecuteAsync`
开头按 run 新建、`IsolationMode` 为 SessionContainer，除本执行器外没有第二个写入方，
执行器一退出直接停止永远是正确处置。守卫 `DesignArtifactSessionDisposalTests` 六条；
把写法退回 `else if`，其中两条（返回 null、抛错）当场变红。

### 二、保存失败不标终态：三条 false 出口只有一条标了 error（A 类，已修）

`PersistRunDoneAsync` 有三条返回 false 的出口，原本只有「来源内容不完整」那条调了
`PersistRunErrorAsync`，另外两条（运行时资源未解析、写库异常）把 run 留在 `running`，
等 15 分钟的陈旧扫描收尾。SSE 那几条路径还有流在推进，`local-edit` 这种同步端点根本没有
第二个写入方——用户拿到 500，版本列表却挂着一条没人推进的幽灵版本，十五分钟后变成一条
`Error` 为 null 的失败版本，连原因都没有。

没有逐条补调用，而是把失败收敛成唯一出口：内层 `TryPersistRunDoneAsync` 只负责返回
「成功 null / 失败原因」，外层统一落 `PersistRunErrorAsync`。于是「返回 false 必已标 error」
成为结构性质，由编译器保证，不再依赖三处各自记得照做（对齐 `external-cause-first.md` 第四节：
能用类型表达的不变量不许降级成测试断言）。这条没有配套守卫，因为写错的变体写不出来。

### 三、本地编辑重试去重（B 类，不在本 PR 做）

复审要求：服务端提交成功但响应丢失时，重试会用同一个父版本和同一份 HTML 再建一条
`manual-edit` run，应该按幂等键或内容哈希返回既有子版本。

成立还要一个唯一索引——按 `no-auto-index.md`，索引是 DBA 执行的迁移，是本 PR 之外的动作。
本 PR 的 §5.5 熔断早已触发，不在此展开。后续做的时候一并考虑「用户确实想从同一个父版本
改出两份相同内容」这个合法场景要不要折叠。

上一轮为 OpenDesign 的 202 恢复放行了 `GET /api/projects/{id}/agent-sessions`，注释里写的是

处理器把缺省的查询值当成「不过滤」，所以只按路径放行，等于把这把连接凭据名下的整份会话与
预约清单（clientUser、模型端点、工作区、仓库、容器、运行时元数据）一起开了出去。

改法是给路由规则加一层查询串判据：方法与路径都对上之后还要它点头，这条规则才算命中；
不点头就当没命中，落到表尾即拒绝（fail-closed）。鉴权入口把 `req.query` 一并传进去。

顺带把跨服务接线守卫从「方法 + 路径」升到「方法 + 路径 + 查询参数名」，并让它能扫到跨行拼接的
字面量（MAP 那条路径与 `?clientRequestId=` 正好分在两行）。于是 MAP 哪天不再送这个参数、
或白名单哪天不再要求它，两头都会红——而不是又一次靠注释维持。

### 二、写库歧义失败被无条件降级（A 类，已修）

上一轮把「返回 false 必已标 error」做成了结构性质，但写库那一支的失败**无法区分**
「没写进去」与「写进去了、回执丢在路上」。于是一次 ack 丢失会把一条真的完成版本改写成
`error`，用户再也打不开它——比不标终态更糟，而且是这次修复自己造出来的新洞
（改之前那种情况会留在 `done`，陈旧扫描也不碰它）。

改法：只有写库那一支标为「不确定」，由调用方回读权威状态（`Status == done` 且 `HtmlHash`
等于本次算出的那个）再决定；回读也读不到时**不下结论**，留给 15 分钟的陈旧扫描兜底，
而不是猜一个可能抹掉用户作品的结论。决策抽成 `ResolveSaveFailureAsync`（收探测委托，
与同批的 `DisposeRemoteSessionAsync` 同一写法），四条守卫覆盖三种走向加「非歧义失败不打库」。

## 第三十六轮复审（2026-09-16，head `b32b3767ac`）

## 第三十七轮复审（2026-09-16，head `11e2bbd29c`）

一条 P2，A 类修掉。这条是我自己前几轮加的东西——**合并本身变成了第二个故障**。

### 单飞合并没有过期，卡住之后永远恢复不了

Redis 的 `PingAsync` 不收取消令牌，半失活时会直接挂住，所以早先给就绪探测加了单飞合并，
避免编排每几秒一次的轮询攒出成百条谁也停不掉的在途操作。合并的判据写的是
「上一次还没结束就复用」。

问题正出在这条判据的边界：挂死的那一次**永远不会结束**。于是之后每一次就绪检查都复用
这条死任务、每一次都超时——Redis 恢复了也没人再去 ping，只能重启 API 才能重新变健康。
并发闸纪律第四条说的就是这个：卡住的持有者必须有人来收。

补一个过期窗口：在途探测活过窗口就当它没救了，下一次调用重新发起。

窗口大小不是随手取的。它**必须显著长于单次依赖超时**——编排每几秒来一次，每次都等满超时
才走人，窗口若等于超时，下一次轮询看到的必然是「过期」，合并就被打散回一次请求一条，
等于把当初要解决的问题原样退回去。取十二倍：默认 5 秒即一分钟，跨十几次轮询仍然只有一条
在途，而 Redis 一旦恢复最多一分钟就重新探到。

代价写在注释里，不藏着：故障期每个窗口会多留一条孤儿探测。`PingAsync` 停不掉是它的性质，
不是这里的选择；一分钟一条，比一次请求一条好一个量级。

守卫一条，三段：窗口内仍合并（不许为了能恢复就退回一次一条）、熬过窗口后重新发起并恢复
健康、挂死那条仍然挂着（证明我们只是不再挡路，没有假装能停掉它）。撤掉过期窗口当场变红。
