# 监控自发现协议 · 规格

**一句话**：服务在自己的健康自检响应里申报「该怎么监控我」，CDS 插上一个地址就把监控项建起来，像插 USB 一样——不需要任何声明文件、导入或审批。
**谁该读**：给服务加监控的人（不管是人还是 Agent）、实现自检端点的后端作者、维护 CDS 监控中心的人。
**读完能做什么**：给一个服务加上常设监控——在它的自检端点上写几行自描述，然后在监控中心插上那个地址。

版本：1（2026-09-11）

---

## 为什么不是一份声明文件

上一版把监控声明放在仓库根的一份 yml 里，由 CDS 导入。它有三个治不好的毛病：

- **要有人导**。写完不生效，得再走一次导入/审批，于是「声明了」与「在监控了」是两件事，中间那段落差没人看得见。
- **必然漂移**。服务改了自检端点，那份 yml 不会跟着改。两边从那一刻起说的话就不一样了，而且不会有任何东西变红。
- **放错了地方**。「我这条指标该怎么判」这件事，最清楚的是写这个指标的人，而他人就在服务那一侧。

把声明挪进服务自己的响应里，这三条同时消失：改了立刻生效，没了自动下线，判据和指标写在同一个文件里。

心智是 USB：主机只需要知道**一个地址**（插上），设备自报描述符。

## 协议

### 载体：不另造格式

用 IETF `draft-inadarei-api-health-check`（`application/health+json`）。它的 `checks` 本来就是半个描述符——每条 check 自带 `componentId` / `observedValue` / `observedUnit` / `status` / `time`，只缺「该怎么判我」。按该草案允许的扩展方式，在 check 上挂一个 `cds:monitor` 段补齐。

键名带冒号是刻意的：与 check 键本身的「组件:度量」同风格，且不会与草案保留字相撞。

### 自描述段

挂在任意一条 check 上。**没挂的 check 不生成监控项**——自愿申报，不是默认全抓；默认全抓会让服务加一条调试用的 check 就凭空多出一条会叫人的告警。

| 字段 | 必填 | 含义 |
|---|---|---|
| `op` | 是 | 比较运算，有限枚举：`eq` `ne` `lt` `lte` `gt` `gte` `exists` `absent` |
| `value` | 除 `exists`/`absent` 外必填 | 期望值。**`0` 是合法值**——「数量等于 0」正是最该写的那种判据 |
| `name` | 否 | 监控名。缺省用 `componentId` |
| `field` | 否 | 判 `observedValue`（默认）还是 `status` |
| `intervalSeconds` | 否 | 探测间隔，默认 21600（6 小时）。范围 60–86400 |
| `failuresToAlarm` | 否 | 连续几次失败才算故障，默认 2。范围 1–10 |
| `severity` | 否 | `P0` / `P1`（默认） / `P2` |
| `observeMode` | 否 | `active`（默认）自己发一次真请求；`passive` 读真实流量的窗口统计 |
| `sampleComponentId` | `passive` 时必填 | 样本量取哪条 check 的 `observedValue` |
| `publicVisible` / `publicName` | 否 | 是否上公开状态页、对外叫什么 |

判据刻意是**结构化三元组**而不是一句可解析的表达式：自由文本判据一旦开口，下一轮就会被要求加同义词和嵌套语法。

### 例

```
"checks": {
  "serving:unhandled-exceptions": [{
    "componentId": "serving.unhandled-exceptions",
    "observedValue": 0, "observedUnit": "count", "status": "pass",
    "cds:monitor": {
      "name": "网关 serving 近期未处理异常数",
      "op": "eq", "value": 0,
      "intervalSeconds": 21600, "failuresToAlarm": 1, "severity": "P0",
      "observeMode": "passive", "sampleComponentId": "serving.requests"
    }
  }]
}
```

## 三条命门

改这套东西之前先读这三条。每条都有守卫，删掉实现就红。

### 一、自描述只决定「判什么」，不决定「打哪」

服务可以说「我这条 check 该断言等于 0」，但**不能说「去打另一个地址」**。CDS 探测的永远是登记时那一个端点。

少了这条，一个写错（或被攻陷）的服务就能把 CDS 变成内网扫描器。所以协议里根本没有地址类字段，解析器也从不从文档里读地址。

### 二、端点打不通 ≠ 这些监控不需要了

- 端点通、某条 check 不在了 → **那条下线**（拔出）
- 端点整个打不通 → **一条都不下线**，它本身就是故障

一次网络抖动把一整个项目的监控删干净，比故障本身更糟：删完之后连「谁不见了」都没人知道。代码里这两种情况用不同的值表达（`undefined` vs 空数组），不允许用一个空数组同时表示两件事。

### 三、一条写坏不连累其它条，也不许拿默认值蒙混

非法声明**跳过并记下原因**，摆在监控中心上给人看。既不整份作废（其余条目本来是好的），也不落默认值——那会把一条写坏的声明变成一条永远绿的假判据，比没有更糟。静默跳过同样不行：那条监控凭空消失，没人会发现。

## 谁能插

与登记监控同一道闸，不新造语义：

| 主体 | 能插什么地址 |
|---|---|
| 项目级 Key（Agent） | 只能插本项目分支预览台账里的地址（堵 SSRF） |
| 管理员 | 任意 http(s)——他本来就能加任意监控 |

插上和拔掉都会**当场跑一轮对账**，不让人对着空列表等下一轮。

---

## 自发现监控的定义不许手改

改了下一轮会被端点的声明覆盖，那是漂移源。要改就去改服务自己的自描述。界面上这类监控标「自检端点自报」，编辑入口关闭。

---

## 取舍与已知边界

- **拒绝的声明只在监控中心展示，不外发告警**。一条写坏的声明是开发期问题，不该在半夜叫人。
- **一个 componentId 只能申报一条监控**。要对同一个指标判两次（比如同时判上限与下限），拆成两条 check。
- **对账频率跟着探测轮次**，所以改了自描述最长一个轮次后生效，不是立刻。
