## 目标与已有事实

前轮已修复缺陷润色、指定移动端布局和预览背景，结果见[前轮排查计划](./plan.defect-agent.submit-reliability.md)。本计划承接[遗留债务](./debt.defect-agent.submit-reliability.md)，不重复计算已完成工作。

创建计划时已核对的事实：

- 八个服务、十五处调用仍写有同类供应商推理参数；这说明存在同类风险，不代表十五处均已被证实故障。
- 仓库已有模型就绪检查和场景判据测试；尚未查明它们为何没有阻止本次用途授权遗漏。
- 全局提交流程等待附件上传后，没有检查其业务返回是否成功，就继续提交。该控制流已确认；实际丢附件、重复建单等后果仍需复现。
- 历史头像和附件图片出现加载失败或 503，故障环节尚未确定。

本轮已获授权开始实施，下列任务仅在取证后更新状态。执行者负责复现、修复和取证；相关模块维护者负责核对协议、配置与发布规则。

## 顺序与依赖

1. 建立证据基线，并先验证附件上传失败是否会导致错误提交；如果证实数据保护缺陷，优先止损。
2. 治理同类调用，逐项核对协议与所需能力，随后补齐配置就绪检查与发布验收的接线。
3. 在隔离灰度数据中完成真实创建、上传、提交和回查，再验证失败恢复与重复操作。
4. 独立定位图片请求失败，按确认的故障环节修复并检查同类资源。

真实模型验收依赖协议和路由就绪；真实提交验收依赖隔离测试账号和可识别的测试记录。图片归因单独记录，避免把不同故障混成一个原因。

## 工作一：同类调用治理

范围以当前发现的八个服务为起点：日常记录润色、PR 总结、PR 对齐、TAPD 缺陷辅助、演讲、营销咨询、项目管理和涌现服务。当前十五处调用的数量作为基线，执行时按真实调用链复核。

- [ ] A1：为每处调用登记业务入口、目标模型与协议、必要能力和当前请求行为。
- [ ] A2：确认哪些参数确实不兼容，哪些是所需能力的一部分，分别记录失败证据和有效样本。
- [ ] A3：复用既有网关适配能力，消除业务层不恰当的协议绑定；保留合法能力，不做一刀切删除。
- [ ] A4：验证严格拒绝未知参数的上游，以及支持相应推理能力的上游；覆盖成功、能力不支持和上游故障。
- [ ] A5：逐项通过真实业务入口验收，并将已证实故障加入永久回归；未具备环境的入口明确保留未验证状态。

**因果验证**：保持模型、输入和其他配置一致，比较协议修正前后的实际请求与结果；同时证明需要的推理能力没有被修复动作意外移除。

**完成标准**：十五处调用均有结论；已证实故障有修复和验证；合法差异有依据；共享修复覆盖哪些调用方可查询。仅搜索不到某个字段不能证明完成。

## 工作二：配置就绪检查闭环

- [ ] B1：追踪已有就绪检查的覆盖范围、执行时机、运行判据和发布消费方。
- [ ] B2：查明这次遗漏属于漏覆盖、未执行、判据不一致还是结果没有接入门禁，并保存证据。
- [ ] B3：针对真实断点修复，复用生产路由判据；优先采用不发送模型请求的只读检查。
- [ ] B4：在隔离配置中构造“模型存在但用途未授权”、模型禁用、无可用线路和能力不匹配等状态。
- [ ] B5：证明缺失配置时检查失败并指出受影响功能，恢复配置后转绿，与实际路由解析结论一致。
- [ ] B6：证明检查结果确实进入相关发布验收，而非只有一个可手动调用的检查入口。

**因果验证**：只改变一项隔离配置，记录检查结果与实际路由结果如何共同变化；再验证失败结果确实使相应发布验收不通过。

**完成标准**：相关功能的配置故障能在用户调用前被发现，并给出恢复动作。检查按启用功能和发布范围组织，不能因为无关、未启用功能没有模型配置而使整站不可用。

## 工作三：真实缺陷提交与失败恢复

- [ ] C1：选择隔离灰度数据和测试账号，记录本次生成的对象编号；自指派，避免通知真实业务人员。
- [ ] C2：先复现附件上传业务失败时的实际行为，确认是否继续提交、错误提示是否准确、草稿和附件如何保留。
- [ ] C3：对已证实缺陷修复成功判定和恢复路径；复用已有草稿、幂等与重试机制，避免重复创造一套状态。
- [ ] C4：完成真实创建、上传、提交、列表回查、详情回查和附件读取，核对内容、状态、指派人与附件一致。
- [ ] C5：验证上传失败、最终提交失败、响应丢失、连续点击和重试；分别检查保留内容、不漏附件、不重复建单和不误报成功。
- [ ] C6：验证润色不可用时仍可按规则提交已有描述；清理本次测试数据，保留脱敏证据。

**因果验证**：在指定步骤制造可控失败，比较实际存储状态与界面反馈；修复后重复同一步骤，确认错误提交或数据损失不再发生，并检查正常提交未回退。

**完成标准**：真实流程和必要失败分支都得到验证，且有稳定对象编号串起创建、上传、提交和回查。受控响应的界面测试与真实存储验收分别记账。

## 工作四：图片请求失败归因

- [ ] D1：选取可稳定复现的失败图片，记录所属记录、预期资源和浏览器现象。
- [ ] D2：逐层检查业务记录、存储对象、源站、CDN 和浏览器，定位首次偏离预期的环节。
- [ ] D3：根据证据区分对象缺失、权限或链接有效期、响应类型、缓存、访问路径及网络问题，不按 503 文案直接猜根因。
- [ ] D4：只修确认的故障环节，再从真实页面加载同一资源，验证响应与实际显示。
- [ ] D5：检查同一生成方式的其他资源及一个正常对照样本，记录不同环境的适用范围。

**因果验证**：先证明资源链路在哪一层断开；修复该层后，同一资源应经真实页面恢复。若故障只发生在诊断网络中，须明确该边界。

**完成标准**：有明确根因、同一失败样本的恢复证据和同类样本验证。仅增加占位图或隐藏控制台错误不算修复。

## 验收与状态规则

每个问题维护以下记录：

| 项目 | 必须包含的内容 |
|---|---|
| 身份与范围 | 问题编号、入口、环境、版本、影响对象、负责角色 |
| 失败基线 | 可复现步骤、预期与实际、请求或对象关联编号 |
| 原因与根因 | 支持证据、已排除解释、仍待求证内容 |
| 修复 | 改动目的、影响层次、恢复或回退方式 |
| 正反验证 | 原失败是否消失、正常能力是否保留、失败恢复是否符合预期 |
| 同类覆盖 | 已检查入口、修复覆盖范围和未覆盖边界 |
| 结论 | 已验收、已修复待验收、待求证、待修复或受阻，不能只写“测试通过” |

永久测试防回归，真实入口验证证明本次行为，二者分别提供证据。模型路由故障、上游请求故障、界面故障和存储故障分别下结论；某一层成功不能代替其他层成功。

实施时按改动模块执行既定类型、编译、测试和文档检查；涉及页面的改动还需核对桌面、手机尺寸、明暗主题及失败状态。推送后核对相同代码提交的 CI、真实部署与公网入口。截图、原始响应和临时报告存放在验收证据渠道，不写入长期文档；凭据不进入日志或报告。

## 实施中已获得的因果结论

- 业务层推理字段来自旧生成规则；严格原生上游拒绝该字段。同模型、输入、推理意图只改变协议编码后成功；精确 OpenRouter 仍携带其合法字段与推理预算。规则同步纠正，避免后续再次生成。十五次业务解析涉及十四个唯一用途，全部未选出可用逻辑模型；随后核对两分支四个运行态的脱敏配置指纹一致、同一默认模型七项名单与这十四个用途无交集，证实是既存授权范围外；未擅自扩授权，也未把契约通过写成业务推理通过。
- 实例健康原本允许部分用途配置不全，场景能力检查原本只覆盖图片，发布缺少聊天功能范围。新增只读范围检查复用真实路由；一项隔离故障对应一项失败，恢复转绿；删除范围传递会误放行，恢复接线会拦截。没有通过摘掉整个实例掩盖局部配置问题。
- 浏览器基线中上传返回失败，但仍调用最终提交并显示成功。两个入口现共用失败恢复；服务端利用已有唯一主键与原子更新，隔离 Mongo 中并发建单仅一份、附件不重不丢、提交仅一个赢家。客户端保留当前内容和文件，重试复用身份；两个真实渲染入口在三种视口下均通过受控上传失败与恢复，未产生真实写入。短屏编辑区域可滚动，提交操作固定可达；业务状态由服务端判断；最终提交响应丢失显示结果待确认，重试回查，不能误报未提交或成功。
- 旧附件域名在实际 API 容器中也证书过期，同 key 的可信 COS 对象长度和内容匹配。历史头像 R2 同名对象缺失、COS 原图完整，正常 R2 对照可读。修复读取兼容，不修改历史记录或切换新上传提供方。

当前声明限于代码及上述验证，未部署的页面和未配置的业务入口仍待验收。通知副作用仅保证至多一次；状态提交后进程崩溃的最终送达需要可靠消息机制，列入债务。
