# MAP 自动化测试五步法 · 指南

> **版本**：v0.3 | **日期**：2026-10-20 | **状态**：草案

**一句话**：让会用 Codex、测试经验少的开发者，照着同一套步骤完成审查、视觉测试、单元测试、联合测试和交付核对。
**谁该读**：用 Codex 开发和修复问题的人，以及负责验收其交付的人。
**读完能做什么**：为一次改动写清预期、执行测试、保留有效证据，并判断哪些已经通过、哪些还不能交付。

## 开始前准备一张任务卡

目标是“人人照做，人人都会”。每次只拿一个明确问题练习：先写用户应该得到什么，再让工具验证。下面的提示词可以直接复制给 Codex；方括号由操作者填写，不能原样执行。

本指南把既有规则编排成学习顺序，不另设一套验收规范。判定以 [MAP 企业级自动化验收规范](./rule.acceptance.map-enterprise.md) 为准，编译和测试的权威位置见文末的验证位置规则。课程安排见 [教程视频计划](./plan.platform.testing.tutorial.md)，可录制的文案及停顿安排见 [教程口播与节奏](./guide.platform.testing.script.md)。

| 任务卡字段 | 填写示例 |
|---|---|
| 要解决的问题 | 用户点“探测”失败，但开发者只验证了授权页能打开 |
| 预期行为 | 从页面完成授权，返回后探测成功；重启后连接仍可用 |
| 本轮范围 | 当前修复涉及的连接、授权、探测与持久化链路 |
| 版本 | 仓库、分支、目标提交 SHA；实测时另记运行版本 SHA |
| 环境和身份 | 分支预览、测试账号的角色、依赖的服务；凭据从安全渠道获取 |
| 成功与失败 | 正常授权并探测成功；失效连接显示可恢复错误；越权被拒绝 |
| 证据 | 每条行为对应测试结果、页面状态和必要的内部佐证 |

第一次可以这样开始：

> 请读取本仓库 AGENTS.md、受影响模块规则和已有测试。我要解决的问题是：[问题]；预期用户行为是：[预期]。先把它写成任务卡，列出本轮范围、可观察断言、所需环境、对应验证入口和缺口。遇到可从仓库查到的信息自行查找，不编造命令、账号、预览地址或测试结果。先完成范围与断言，再开始测试。

学习章节按下面五章展开。日常执行可以先跑成本低的检查和单测，再部署取证；视觉测试与联合测试可以共享一次真实用户操作，但每条断言都要有对应证据。

## 第一章 Codex 代码审查

### 本轮教学补充

本章补充 GitHub PR 评审的设置入口、仓库和个人策略、触发事件与完成确认，具体操作及口播见 [教程口播与节奏](./guide.platform.testing.script.md)。先确认评审真正运行，再按下面的方法处理意见。

### 做什么

审查回答“这次改动可能在哪里出错”。它能发现遗漏的权限检查、契约变化和异常分支；审查结论需要用运行证据验证。

### 照着做

1. 告诉 Codex 本轮目标、比较基线和目标提交。检查工作区里是否还有未提交改动，避免审错版本。
2. 让它沿实际调用路径检查：用户输入、前端请求、后端校验、存储、异步任务和外部依赖。
3. 每条意见必须能说明触发条件、用户影响和证据位置。要求它提出复现办法，而非只说“可能有风险”。
4. 按仓库 A/B/C 分类处理：直接缺陷在本轮修复；扩范围建议进入后续事项；缺少真实路径的推测不直接实现。
5. 修复后复审受影响路径，保留“发现—处理—复测”记录。严重级和停止条件引用现有规则。

> 请对[基线与目标提交]做代码审查，目标是[本轮目标]。读取真实调用方和相关测试，优先检查权限、数据隔离、错误恢复、并发、持久化及兼容性。每条发现给出触发步骤、实际影响、文件位置、证据及建议验证办法，并按 AGENTS.md 的 A/B/C 分类。不要把推测当缺陷，不扩大本轮需求。审查完列出仍需通过运行测试证明的断言。

### 怎样算做到了

每条直接缺陷都有处理结论与复测办法；没有已知阻断项被遗漏。“未发现问题”只表示本次审查未发现问题，不代表其他四章已经完成。

### 卡住时

若自动审查没有运行、额度耗尽或没有返回结果，记录“未执行”及原因，安排独立复核，不能写成“审查通过”。连续审查扩范围时按 `AGENTS.md §5.5` 熔断，不以清空所有机器意见为目标。

## 第二章 视觉测试

### 本轮教学补充

本章围绕正式技能 `create-visual-test-to-kb` 讲获取、下载、安装识别、使用及 CDS“验收报告”查收；用户所称 `/create-visual-to-kb` 对应本项目的这项技能。完整步骤见 [教程口播与节奏](./guide.platform.testing.script.md)，下面的真实入口与证据要求继续保留。

### 做什么

视觉测试回答“用户是否看得懂、点得到，并得到正确反馈”。既要看布局和主题，也要触发操作后观察成功、等待、失败和恢复状态。

### 照着做

1. 取得真实预览入口，核对实测 SHA。预览地址由仓库的 CDS CLI 查询，不能根据分支名猜测。
2. 用测试账号从登录或首页沿可见入口点击，记录路径。排查时可以直达路由，验收时补齐正常入口。
3. 执行任务卡的核心动作。拍入口、关键操作、结果和必要的失败状态；让截图说明“发生了什么”。
4. 检查明暗主题、文字可读性、布局溢出、滚动、弹层遮挡和按钮可达性。连续任务检查正常、慢、失败、恢复四态。
5. 用户可见 Web 页面的 L1/L2 验收按主规范独立使用触控移动 context；不能只缩窄桌面窗口。记录视口、触控和独立入口路径。
6. 逐图读回，确认图片、说明和断言一致。视觉缺陷的框选、截图数量、档位及报告准入按主规范和证据指南执行。

> 请对[目标行为与提交]做视觉测试。按仓库现有验收技能读取规范、冻结范围、核对预览版本，再从登录或首页沿真实入口点击。覆盖适用主题、桌面与触控移动端、关键操作及失败恢复；每项记录步骤、预期、实际和证据。诊断路径与正常用户路径分开记录，fixture 演示不能写成真实依赖通过。先读回截图，再给结论；没测到的明确列入缺口。

### 怎样算做到了

能从证据中定位用户动作及其页面结果；适用的主题、设备和状态已覆盖。截图数量下限及移动端条件以 [主规范第 11 至 13 节](./rule.acceptance.map-enterprise.md) 为准，报告操作见 [证据交互指南](./guide.acceptance.report-evidence.md)。

### 卡住时

503、登录失败或预览版本漂移先作为环境或覆盖问题处理。按钮看得见却无法完成动作，是用户路径失败。不能拿登录页截图或 API 成功响应替代结果证据。

## 第三章 单元测试

### 本轮教学补充

本章补充 SSOT 与单元、消费者、工作流的对齐。规则函数正确，还要确认所有相关出口都使用它，并有检查能发现重新复制的旧实现。项目案例选择 CDS 预览地址和 MAP 首页片花，详见 [教程口播与节奏](./guide.platform.testing.script.md)；用户后续案例继续追加。

### 做什么

单元测试回答“一条独立规则在正常、边界和异常输入下是否正确”。例如连接状态如何转换、重复请求如何处理、过期结果是否会覆盖新结果。

### 照着做

1. 让 Codex 找一个已有、写法相近的测试，确认运行器和模块命令。
2. 把任务卡中的规则写成“给定条件—执行动作—预期结果”，优先测可观察行为。
3. 缺陷修复选择一条能复现原问题的回归用例，在隔离环境中证明修复前会失败、修复后会通过。保留已有修复时，可用独立临时 worktree 做对照，不回滚当前工作区。
4. 按风险增加相关的边界或负面用例，例如空值、超时、重复操作或乱序返回；不要机械地给每个函数凑同样数量的测试。
5. 先跑目标用例，再跑受影响模块按规则要求的回归检查。记录命令、版本、通过数、失败数和跳过项。

> 请为[业务规则或缺陷]设计最小但有效的单元测试。先读取现有相邻测试及运行命令，以用户可观察行为为断言，避免照抄实现。选择能抓住原缺陷的代表用例，证明修复前失败、修复后通过；按真实风险补边界和异常。先跑定向用例，再跑模块要求的回归。输出实际命令、结果、跳过项和 mock 边界。

### 先分清几种绿灯

| 绿灯来自哪里 | 可以说明什么 | 还需要补什么 |
|---|---|---|
| 类型检查 | 类型约束满足 | 业务行为和 CSS 构建检查 |
| Vitest 或 xUnit 单测 | 实际执行的用例断言成立 | 真实接口、依赖和用户路径 |
| 镜像构建 | 该构建实际包含的项目能编译打包 | 未包含的测试项目与运行态验证 |
| CI 的 Server Build & Test | 当前 CI 过滤范围内的构建和 xUnit 结果 | Integration / Manual 类按范围点名验证 |

仓库前端统一用 pnpm。前端源码改动按 `AGENTS.md §5.2` 执行类型检查、lint 和测试；CSS 改动另跑 build。后端 CI 当前使用 `Category!=Integration&Category!=Manual`，不能把它表述成全部集成测试通过。真实命令及触发范围每次从模块和 workflow 读取。

### 卡住时

用例没有执行、全部跳过或测试进程无法启动，都不能算通过。mock 只证明隔离范围内的规则。涉及真实服务的 Integration / Manual 类按类名点名运行，先确认前置依赖，避免直接启动全量外部调用。

## 第四章 联合测试

### 做什么

本教程把“联合测试”解释为两层：先验证模块交界处的集成契约，再沿真实用户路径验证端到端闭环。多个相关断言可以按主规范融合取证，但一个场景仍须逐条说明覆盖了什么。

### 照着做

1. 画出本轮链路：用户动作、前端、接口、权限、存储或队列、依赖服务、最终页面结果。
2. 检查每个交界处的请求、响应、身份和状态是否一致。先测最小集成路径，帮助失败时定位责任层。
3. 在隔离测试环境从真实入口完成一次核心流程。使用本次生成的对象标识串联页面、API、日志与存储结果。
4. 按风险验证刷新、重新登录或重启后的持久性；涉及授权凭据的案例必须检查重启后的可用性。
5. 覆盖至少一条与本次改动相关的负面路径，例如无权限、依赖超时、撤销或重复提交，断言明确错误及无错误副作用。
6. 验证恢复动作，并清理本轮测试数据。最终回到页面确认结果。

> 请对[功能与目标提交]完成联合测试。先列出真实链路与各交界契约，再用隔离测试身份从可见入口完成核心流程，关联页面、请求、对象标识及必要的内部状态。按本轮风险覆盖负面、恢复和持久化，记录测试数据清理结果。真实服务、假上游和 fixture 证据分别标明。若一个场景覆盖多条断言，给出逐条证据映射与剩余缺口。

### 贯穿案例 授权后探测

案例依据文末本地连调规则第 6.1 节的 MAP/CDS 事故记录；以下是练习设计，结果由学员实测填写。

| 步骤 | 要证明什么 | 应观察的结果 |
|---|---|---|
| 页面发起授权并回跳 | 用户能走完入口链 | 返回 MAP，连接出现在列表中 |
| 页面点击探测 | 凭据生产者与消费者契约一致 | 页面探测成功，内部证据对应同一连接 |
| 隔离环境重启后再次探测 | 凭据与解密材料可持续使用 | 已有连接仍能探测 |
| 撤销后重连 | 双方状态迁移一致 | 撤销可见，重新授权不被旧连接错误阻止 |
| 无权限身份执行 | 权限边界成立 | 动作被拒绝，未产生越权连接或数据 |

首次上手不要求新人自行改造部署设施。课程提供预置隔离练习环境，Codex 负责解释执行条件；重启和撤销只对练习资源执行。

### 卡住时

按“页面症状—请求—权限—服务—存储—依赖”的顺序定位。环境缺失记为覆盖缺口；可复现业务失败记为缺陷。假上游可以证明部分集成契约，真实服务未验证的部分继续保留缺口。

## 第五章 遵循这些做法的标准 严厉版

这里把现有规范变成操作者的交付核对表。严格检查的是承诺、版本、行为和证据之间的一致性；严重级、Verdict、证据下限和停止条件继续引用主规范，不提高轻微问题的级别。

### 交付前逐项回答

| 核对问题 | 必须能拿出的内容 | 处理依据 |
|---|---|---|
| 测的是这次改动吗 | 任务卡、目标 SHA、实测 SHA、断言映射 | 主规范第 7 节 |
| 审查意见处理了吗 | 直接缺陷的处理与复测；扩范围事项的去向 | AGENTS.md §5.5 |
| 绿灯覆盖到哪一层 | 实际运行的 job、命令、过滤条件和结果 | cds-first-verification 规则 |
| 用户真的能完成吗 | 正常入口、动作、页面结果及相关内部佐证 | 主规范第 8 至 10 节 |
| 主题与移动端齐了吗 | 适用主题、触控 context、独立路径和截图元数据 | 主规范第 11.2 节 |
| 连续任务失败后能恢复吗 | 适用的正常、慢、失败、恢复状态证据 | 主规范第 11.3 节 |
| 失败被如实表达了吗 | 缺陷、未执行、环境阻塞、跳过和假服务边界 | 主规范第 7.1 至 7.2 节 |
| 证据能打开且图文一致吗 | 读回结果、可定位截图、标准报告链接 | 证据交互指南与归档门禁 |
| 该停止了吗 | 已覆盖关键风险；追加测试是否改变判断 | 主规范第 11.1 节 |

### 不凭一句“通过”交付

直接使用主规范第 7.1 节的五项结论：产品质量、验收完整性、综合结论、发布建议、判定性质。综合结论使用 `pass`、`conditional`、`fail`，其中 `conditional` 中文为“原则性通过”。目标版本无法复现且未发现产品失败时，应解释覆盖缺口；不能推导成产品坏了。

> 请按现有验收规范审计本轮交付。逐项核对目标与实测版本、审查处理、实际测试结果、真实用户路径、主题与移动端、相关负面及恢复、证据读回和覆盖缺口。输出产品质量、验收完整性、综合结论、发布建议、判定性质；非 pass 项补根因链与关闭动作。严格区分产品失败和验收不完整，不把未执行、跳过、mock 或入口冒烟写成完整通过。关键风险覆盖充分后停止追加无关测试。

### 每次复用的交付卡

| 字段 | 填写要求 |
|---|---|
| 范围与版本 | 本轮目标、目标 SHA、实测 SHA、实际预览入口 |
| 审查 | 实际是否执行、直接缺陷处理、仍需跟进事项 |
| 单测与构建 | 实际命令或 CI job、结果、过滤范围、跳过项 |
| 用户路径与联合测试 | 入口到结果的操作、逐断言证据、真实依赖范围 |
| 失败与缺口 | 复现事实、影响、根因链、负责角色和关闭动作 |
| 五项结论 | 按主规范逐项填写，不能只写“全部通过” |
| 归档与读回 | 使用现有验收技能生成和归档标准报告；确认链接可打开 |

验收规范和执行报告的治理见 [SSOT 规则](./rule.acceptance.ssot.md)。本指南是教学入口；单次截图、日志、结果报告与教学导出视频放在仓库外的产物位置，不提交进 git。

## 第一轮练习怎样验收

学员在提供好身份与环境的条件下，独立完成一张任务卡、一次真实失败的定位与复测，并交出可读回的交付卡。带教者只根据指南观察，不代替操作。记录卡住的步骤、原因和耗时；对需要口头补充的地方修改教程后再试。

使用五个检查点：选对版本、写对断言、复现失败、证明修复、如实结论。任何一项需要带教者代做，本轮仍需练习。阅读完或视频播放完不等于掌握。
