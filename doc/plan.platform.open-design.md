# OpenDesign 六步实施计划

> **版本**：v2.0（推倒重写） | **日期**：2026-09-11 | **状态**：六步全部未验收，S1 卡在一个已证实的镜像缺陷上

**一句话**：把 OpenDesign（无头设计编排器）接进统一会话工作区，按基座、存储、通信、场景、稳定性、效果六步走完，每步必须由独立智能体出具可打开的验收报告才准勾选。
**谁该读**：接手开发与验收的智能体、产品负责人，以及 MAP、CDS、LLMGW、网页托管四侧的负责人。
**读完能做什么**：知道现在卡在哪、下一个动作是什么、每一步凭什么算过，并且不会重做已经做完的事。

---

## 一、为什么推倒重写

上一版计划把 S1 写成「候选实现已提交，待独立验收」。核对镜像仓库与运行时探针后，事实是 S1 **不是待验收，是必然失败**：钉住的镜像里装的是 opencode，而候选代码在同一个提交里把要求换成了 codex 并加了硬探针，镜像销钉没跟着换。探针必然红，会话在任何 CDS 节点都起不来。

一份把必然失败写成待验收的计划，后面五步的排序全是空的。所以不是打补丁，是重排：**先承认 S1 现在是红的，再谈顺序**。

三条改动口径：

- **进度只记验收，不记开发。** 代码写完不加分，拿到可打开的报告才加分。所以下表六行现在全是 0%。
- **每步都配一条机械判据。** 「最直白的通过方式」是给人看的，机械判据是给机器跑的，两者都过才算过。
- **删掉「细化任务数」。** 上一版那列写着 6/6/7/5/4/7/5/8/6，没有任何东西为这些数字背书。

## 二、六条不变的原则

1. 只有「最直白的通过方式」实际发生、且验收报告地址能打开，才准勾选。代码存在、单元测试通过、容器健康、接口返回成功，**四者单独或加起来都不算**。
2. 开发与独立验收并行。每完成一批立刻委托验收，不等六步全做完再统一验。
3. 开发者不给自己的功能签最终通过。签字权在独立验收方。
4. 验收样本、截图、报告进 CDS 验收中心，本文件只回填可访问地址，不把验收产物写进文档目录。
5. 报告没有可访问地址，等同于没有验收。
6. 用户等待时屏幕必须持续有变化。静止等待超过两秒即体验缺陷，不是「以后优化」。

### 5.1 验收链路的两个阻塞（2026-09-11 实测，不是产品缺陷）

按本计划的原则，验收要有独立方出具、地址可打开的报告。本轮走了一遍验收链路，走不通，如实记在这里。两条都属于验收链路问题，不是产品失败。

**阻塞一：线上那套 CDS 根本不跑这条分支的代码。** 线上实例跑的是主干上的某个版本，向它请求本特性的运行时接口直接返回「未知接口」——说明这套 OpenDesign 会话运行时在主干上还不存在。所以「工作室真的开张」这条端到端断言，**现在没有任何环境能验**：不是验不过，是无处可验。要么把这条分支作为一个 CDS 实例部署一次，要么等它合进主干。

**阻塞二：进控制台要操作员口令，而那对口令不许我自己动。** 浏览器取证通道已经搭通（出站可达、接口鉴权可用），但控制台是表单登录，点「进入控制台」会落到登录页。那对口令是项目级共享的，同项目其他分支也在用；按跨项目隔离的规矩，Agent 不得为了自测去轮换它，只能由人提供。所以视觉验收判**验收链路失败**，不出报告——按规矩，登录页截图不能充当功能证据，本地草稿也不算验收报告。

**顺带发现（不在本次范围，未处理）**：本分支的预览环境里 `llmgw-serve` 容器起不来，崩在启动阶段，原因是共享数据库里有别的部署写入的新字段，本分支的类反序列化不了。时间戳早于本轮全部改动，与本次修复无关。已记录，未动。

## 四、逐步详解

每步四件事：目标、最直白的通过方式（给人看）、机械判据（给机器跑）、失败了怎么办。

### S1 基座 —— 真实跑起来，且模型由 MAP 说了算

**最直白的通过方式**：在 MAP 选定一个模型，任务跑完真的产出了文件；去 LLMGW 的审计里查，记的是同一个模型；拿一个任务标识，能串起入口、执行、模型、产物四段证据，且全程看不到密钥。

**机械判据**：镜像探针在目标节点的退出码为 0；把镜像销钉临时改回旧值时，供应链守卫必须变红。守卫不变红，说明它没在测你以为它在测的东西。

**这一步内部是串行的三件事**：

- **S1a 先量后修。已完成（2026-09-11）。** 拉下钉住的镜像，原样跑探针命令，逐条拆开量：

  | 探针的五个条件 | 钉住的镜像实测 | 判定 |
  |---|---|---|
  | `codex --version` 等于 `codex-cli 0.143.0` | codex 根本不存在，报 `codex: not found`；实际装的是 opencode | **不满足** |
  | 网页原型的 SKILL.md 存在 | 存在，5865 字节 | 满足 |
  | 网页原型的 assets/template.html 存在 | 存在，16603 字节 | 满足 |
  | 网页原型的 references/layouts.md 存在 | 存在，10995 字节 | 满足 |
  | 网页原型的 references/checklist.md 存在 | 存在，4679 字节 | 满足 |
  | **探针整体退出码** | **1** | **不满足** |

  **结论：五条里四条满足，只差 codex 一条。** 修法是窄的——只要重建重钉，构建描述和资源路径**都不用动**。原先担心资源路径可能对不上（上游镜像里叫什么名字本仓库没有证据），实测证明路径完全正确，这个担心可以撤销。

  **顺手把下一步也验掉了，省一轮流水线往返**：按仓库现有构建描述在本地构建了一次候选镜像，构建过程里那句「断言 codex 版本串完全等于 codex-cli 0.143.0」自己就通过了，说明该版本的包存在且版本串一字不差；对构建出来的镜像跑原样探针，**退出码 0**。所以 S1b 只是把这次本地构建搬到流水线上重做一遍。

  **一个要记下的边角**：只读文件系统下 codex 会往标准错误打一行「无法创建 PATH 别名」的告警，但不影响退出码。将来若有人给探针加一条「标准错误必须为空」的断言，会凭空把一枚好镜像判红。
- **S1b 重建并重钉。已完成（2026-09-11）。** 在当前分支触发了运行时镜像的构建流水线，构建成功；从镜像仓库读回新摘要（结尾 `59da2b7c`，不手抄）替换掉旧的（结尾 `c4d2d53a`）。对新销钉跑原样探针，**退出码 0**。
- **S1c 补一条能变红的守卫。已完成（2026-09-11）。** 原先的守卫只用正则断言销钉「长得像一个摘要」，不校验它由哪份构建描述产出，所以镜像漂移能静默通过。**这一点先实测坐实**：把守卫的七条断言照原样复算，此刻全部通过，而同一时刻被它「保护」的那枚镜像探针退出码是 1——守卫绿着，东西是坏的。

本轮补了三层，每一层都做过红绿闭环（先证明它会红，再证明修好后会绿）：

| 层 | 防的是什么 | 红绿闭环怎么证的 |
|---|---|---|
| 探针进流水线 | 销钉过期后永远不可能再是绿的 | 旧销钉退出码 1，新销钉退出码 0 |
| 跨文件版本一致 | 构建描述、运行时常量、第三方清单三处版本各改各的 | 把运行时常量改成另一个版本，守卫立刻红 |
| 守卫接线本身 | 闸门的路径过滤不含被守文件，只改销钉的改动一路全绿 | 删掉一行路径过滤，守卫立刻红 |

两个设计上的讲究：校验脚本的判据（镜像、版本、资源目录、资源文件清单）**全部解析自运行时源码**，不在脚本里另写一份清单，避免判据分裂成两份各自漂移；解析不出来一律判红，绝不静默跳过。另外脚本把「环境不可用」和「镜像不合格」分成不同退出码——两者都返回同一个码的话，读者无法判断是守卫发现了问题，还是守卫自己没跑起来。

顺带清掉一处旧账：几个测试把镜像摘要写成字面量，换一次销钉要手改五处。已改为引用常量。

**失败了怎么办**：连续两次重建后探针仍红，停手，按第七节升级，不要继续刷脚本。

### S2 存储 —— 知识进得去，产物出得来，两个会话互相看不见

**最直白的通过方式**：页面里引用的内容，能在原始知识文件里逐句找到；两个并发会话互相读不到对方的文件、凭据和日志；把对话断开，结果仍然在。

**机械判据**：并发开两个会话，A 的工作区路径在 B 里读取必须失败；产物冻结进对象存储的时刻，必须早于任何工作区回收的时刻；把冻结这一步去掉，断连用例必须变红。

**已知的坑，必须在这一步正面回答**：会话工作区是内存盘，宿主重启或卷回收后内容归零。「对话断开后结果仍在」到底靠什么保住，必须在这一步写清楚，不能拖到 S5 故障注入才发现没人保。

### S3 通信 —— 整站能打开，局部改只动被点名的地方

**最直白的通过方式**：预览能打开首页，脚本、样式、图片、字体全都加载得出来；要求只改某一处时，其余内容一个字都没变；中途中断能继续，或者明确告诉你失败在哪。

**机械判据**：抓一次完整站点的资源清单，逐个请求必须成功；局部修改前后对全部文件做一次逐字节比对，**没被点名的文件必须字节完全相同**。这条比「只改要求的部分」强得多，因为它可以自动跑。

**失败了怎么办**：只要出现「为了让校验过而删掉脚本和资源」的倾向，立刻停——那是把作品阉割成能通过的样子，属于第七节的升级项。

### S4 场景 —— 四个入口各自从正常导航走通一次

四个场景共用同一份工作区合同，所以放在同一步里，但各自独立验收、各自出报告。

| 编号 | 场景 | 最直白的通过方式 |
|---|---|---|
| S4.1 | 网页托管引用知识库，补两句话生成整站 | 用户只选知识、只说两句话，最后拿到一个已保存、能再次打开的完整网页 |
| S4.2 | 在知识库里选智能体，直接生成网页 | 从知识库正常导航进入就能生成、预览、保存，不需要把原文复制到别处 |
| S4.3 | 网页托管的「帮我修改」闭环 | 发布前线上不变，发布后更新，回退后恢复，所有历史版本仍能预览 |
| S4.4 | 知识库生成 HTML 演示 | 每一页都能打开，内容确实来自所选知识，刷新不丢，还能接着改 |

**机械判据（四个场景共用）**：验收必须点击导航进入，禁止地址栏直达隐藏地址；截图里产物必须真的渲染出来了——停在转圈或「正在生成」的截图不算数，那是断头验收。

### S5 稳定性 —— 断了能回来，坏了能退回去

**最直白的通过方式**：任务不会串线，不会重复发布；失败时告诉你下一步该干什么；升级坏了能回到上一个可用版本。

**机械判据**：快速连续发布两次，线上最终版本必须等于最后一次操作的结果，旧请求不许回写；宿主重启一次之后，产物仍然能打开——这一条专治 S2 里那个内存盘的坑，必须真的重启，不能只在代码里推演。

### S6 效果 —— 匿名评分打得过成熟产品

**最直白的通过方式**：匿名视觉评分不低于 85 分，对抗审查没有阻断项，密封盲验的每一项都判通过。

**机械判据**：验收清单必须在评审者看到实现之前就写完并密封，事后不因实现结果放宽。所以这一步的清单工作**现在就能开工**，不必等 S1。

## 五、顺序与并线

- **串行**：S1 是所有人的共同前置，它红着，S2 到 S5 一步都开不了工。
- **并行**：S1 绿灯后，S2 与 S3 弱耦合，可以各自独立工作区同时推；S4 的四个场景共用同一份合同，同步开发、逐个验收，不必排队。
- **现在就能开工的**：S6 的密封清单不依赖任何代码，今天就可以写。别让它等到最后变成瓶颈。
- **合流前**：跑一次预合并解冲突加全量回归，确认并线没引入行为回归。

## 七、熔断线

出现下列任一情况，立即停止产出进度类文档和脚本，合并成**一条**升级说清最小外部输入，然后切到不依赖该阻塞的工作或挂起：

- S1b 重建后探针仍红，且连续两次重建都没让它变绿；
- 本计划连续被重写三次，而第三节看板没有任何一行状态翻转；
- 真实模型调用拿不到可用的网关凭据，且穷尽自测路径后仍无替代；
- 出现「为了让校验通过而删掉正常作品内容」的念头。

判定净进展只看两件事：阻塞是否翻转、功能代码是否净增。脚本数量、报告数量、文档行数**一律不计**。

## 八、已确认不构成阻塞的事

写在这里，免得下一位再花时间去查：

- 运行时镜像与其上游基础镜像都在，且可匿名拉取，CDS 节点不需要额外凭据。
- 重建镜像不必先合主干，当前分支已命中构建流水线的允许条件。
- 分支已经部署在 CDS，两个预览入口都在。S1 缺的不是部署，是会话运行时。
- 提供者注册表里把 Codex 标成未实现是设计如此，不要去「修」它——它不作为独立可选运行时暴露，由设计守护进程在会话内驱动。
- 工作区的存储配额靠内存盘实现，不依赖特定文件系统，所以这道闸在普通节点上大概率能过；要留意的是它的代价（见 S2）。
- 网页原型那四个资源文件在镜像里的路径与文件名完全正确（S1a 实测），重建时不用改任何路径。
- codex 的那个版本在包仓库里存在，且版本串与探针要求一字不差（S1a 本地构建实测）。

## 九、独立验收角色分工

| 角色 | 能看到什么 | 只负责什么 | 失败时怎么处理 |
|---|---|---|---|
| 清单编写者 | 只看原始诉求和用户路径，不看实现 | 预先写「过或不过」的直白清单并密封 | 清单不随实现结果放宽 |
| 开发者 | 代码、日志、自测 | 开发、修复、自测、部署 | 不给自己的功能签最终通过 |
| 对抗审查者 | 候选、真实日志、故障注入结果 | 主动找串线、丢文件、泄密、假成功、不可恢复 | 阻断项全清后重新审 |
| 视觉评分者 | 匿名产物与同类成熟产品 | 按内容、布局、可读性、交互、完整性严厉打分 | 低于 85 分返工 |
| 盲验者 | 密封清单、入口、最终结果，不看开发说明 | 每项只判通过或不通过 | 任一核心项不过，该步不得勾选 |

每份报告必须包含候选版本、环境、实际入口、输入、操作、预期、实际结果、截图或日志证据、通过与否、阻断问题、复验结论。报告没有可访问地址，等同于没有验收。
