## 二、本周做成了什么（业务价值看板）

### 1. 外部的 AI 助手可以直接调用本系统的五块能力

**谁受益**：外部客户（用 Claude、Cursor 这类客户端的人）、内部团队。
**以前**：本系统的视觉创作、文学创作、知识库、网页托管、海鲜市场这五块能力，只能在自己的网页里点。外面的 AI 助手要用，得有人手写一层对接。
**现在**：接入台给出一把钥匙 + 三份客户端配置，复制粘贴就接上，19 个工具（生图、创作、知识库写入、网页托管发布、市场取用）直接可调。钥匙的能力范围走**自动档**——不存一份固定清单，鉴权时现算「主人当前有什么权限 ∩ 平台当前开放了什么能力」，平台新增能力自动跟进、权限被收回立刻失效；想钉死的话再进高级设置手动选。接入台面板里能看见挂了哪些客户端、今天用掉多少额度（每日生图 50 张、写入 200 次、每分钟 60 次调用）、每次调用做了什么以及产出的东西在哪，失败行整行染色并给出原因与下一步。
**因此**：本系统第一次能作为「别的 AI 助手的工具箱」被使用，而不必为每个客户端单独开发对接层；钥匙给出去之后，权限跟着人的实际权限走，不会因为「钥匙上写死了」而在权限回收后继续生效。
**验收背书**：**通过**——3 份 PR 验收全部通过（09-04 ×1、09-05 ×2），另有 1 份功能验收有条件通过（已知边界见上表）。
**关联 PR**：#1484 #1493
**用量口径**：`route:/mcp-console`

### 2. 多个分支同时开发，数据库不再互相踩

**谁受益**：内部团队（任何在同一个项目下开多条分支的人）。
**以前**：同一个项目的所有分支共用一个数据库。A 分支跑一次数据迁移，B 分支的预览立刻跟着变；想给某条分支单独一份数据，只能手工建库、手工改连接串，改漏一处就是「建了库但应用还连着老库」。
**现在**：项目设置里多了「数据库隔离」页签，每个服务可以选共享库或分支独立库，**保存前先写明这会影响哪些分支**。选了独立库之后，连接串里的库名会自动跟着改（硬编码的串直接改、模板串不动，并明确标出「已跟随」还是「未跟随」）；初始化方式可以选「从共享库时间点克隆」，首次部署前自动拷一份，克隆完逐表数行数核对，对不上的表连同两边行数记进台账。所有派生出来的库进一本**数据台账**，按血缘成树，可备份、可演练验证（还原到临时库核对对象数）、可丢弃（门禁：必须有演练验证过的备份，或者手动复述库名）。分支上改出来的数据要回主库的话走**派生库回写**：先列出「主库在克隆之后改过哪些表」的冲突清单，回写前自动备份并演练验证（演练不过整个回写中止、目标库一个字节不动），回写后逐表校验，事后还能一键回退到回写前的快照。删分支时先展示会留下什么——派生库默认保留并转成台账孤儿条目，数据不丢。
**因此**：多分支并行开发第一次有了「各自一份数据、要合的时候有门禁和后悔药」这条路；此前要么共用一份互相踩，要么手工建库然后忘记它的存在。
**验收背书**：**通过**——7 份功能验收（6 通过 / 1 有条件），且**全部在合并前完成**；含一轮真实 mysql 分支复验（工单系统 MTS：部署前克隆 58 张表一致 → 回写 → 回退）。
**关联 PR**：#1490
**用量口径**：`none:平台能力`

### 3. 钥匙丢了不再等于身份丢了；一个仓库能挂多个项目

**谁受益**：内部团队、运维。
**以前**：部署平台的钥匙就是身份本身——钥匙文件丢了（换机器、重新 clone、挪目录），就等于这个人不存在了，要走一次人工批准重新来过。而一个代码仓库只能绑一个项目，同一个仓库里放两个项目的话，push 只会触发第一个。
**现在**：身份拆成三张表（主体 / 用户级凭证 / 项目授权）。判据从「这个项目是不是我建的」改成「我在不在授权名单里」；钥匙丢了只要授权还在，当场自动补发，全程零人工；撤掉用户级凭证，它签出去的全部下游钥匙同时失效。系统设置里新增「权限总览」页，按人聚合、可撤销可停用，退役凭证折叠、超 90 天归档，未认领的存量凭证明确标出来。凭据自检把「未授权」拆成五类可分辨结论——有效 / 已吊销 / 从未签发 / 项目前缀不符 / 查不了，其中「项目改过名字导致存量钥匙前缀对不上」这种以前会静默跳过鉴权的情况，现在会直说并给出重新签发的指引。多项目那一侧：push 按仓库分发到该仓库名下的**全部**项目；每个服务可以声明自己的构建输入范围，只改到某个项目的代码时不会把整仓所有项目重编一遍；预览地址改由服务端派定，输出 `[项目 · 入口] URL`，取不到时分三种情形说清楚（与该项目无关 / 还没有这条分支 / 分支在但没有入口），不再压成一句「取不到」。
**因此**：换机器不再是一次求人事件；一个仓库放多个项目从「只有第一个会动」变成「全部按各自范围分发」。
**验收背书**：**本周未做功能验收**（证据空白）。
**关联 PR**：#1472 #1475 #1477
**用量口径**：`none:平台能力`

### 4. 打开分支总览，能看出它这半小时是什么状态

**谁受益**：内部团队、运维。
**以前**：分支详情的总览是八个等重方块（其中四个常年显示 0）加每服务一张大卡；抽屉一关，指标历史就丢了，窗口只有 5 分钟；而且它会说谎——部署正在进行时报「分支未运行」、就绪计数清零、当前值被抹掉。
**现在**：换成分段健康环、CPU 堆叠面积图、内存横向构成条、吞吐双向图（网络一行、磁盘一行）、部署耗时柱状图与入口卡组。指标历史下沉到服务端常驻采样（45 秒一轮），窗口拉到 30 分钟，抽屉关掉不再丢；没采到的时间桶留空、**不画成 0**（缺口就是缺口）；图的分辨率不细于采集节奏，避免整张图画的其实是采集节奏而不是 CPU。出图前先给图形骨架 + 诚实进度（已有 N 帧 · 约还需 X 秒），不再是一个虚线空框。谎报那一类问题的根治是把总览的判断句、色调、入口卡副标题、骨架屏注解四处文案收敛到**同一张有限状态表**（九档全覆盖），替换掉原来五层嵌套的三元表达式，并配 25 条守卫钉住。
**因此**：总览从「一屏装饰性数字」变成能用来判断的东西，且一屏之内不再自相矛盾。
**值得单独记一笔**：#1480 修的正是 W35 合并时漏检的那条回归——CI 二十项全绿、变更范围核过、全量跑过，唯独没有在合并前重新拉一次 review 线程，而自动评审恰好在合并前 3 分钟报出了它。这条教训本周落成了一条规则（#1481，「合并前必须重新拉一次 review」），并在同批的后续修复上立刻兑现了一次。

### 5. 上传原型包时看得见进度，也知道它能瘦多少

**谁受益**：外部客户（把原型包发布成网页的人）。
**以前**：上传一个原型压缩包，文件数一多就被上限拦下（且不告诉你怎么办）；包大的时候是一次长请求，传到一半超时就不知道结果；包里带着一堆依赖和开发文件，也没人提醒。
**现在**：文件数上限提高并补了超限后的恢复指引；大包改成分片上传 + 后台分析，界面上能看见传输与安全检查的进度；检查出冗余时给优化建议，**可以先预览优化后的效果，再决定保存原文件还是优化版本**；剪枝规则只剪能静态确认的依赖，确认不了的一律保留（宁可少剪不可误剪），不可安全精简的超限包禁止自动保存。临时优化会话用不可推导的存储位置 + 短期令牌代理预览，并明确排除在跨实例数据同步之外。文件夹那一侧收口了创建删除的并发竞态，桌面与移动端的创建、持久化、拖拽反馈与站点所有者权限一并补齐。
**因此**：发布原型这条路从「传上去看运气」变成「看得见进度、看得见能瘦多少、自己决定存哪版」。

### 6. 授权失败第一次有一个地方能问「为什么」

**谁受益**：内部团队、运维。
**以前**：用户会话、AI 访问钥匙、Agent 钥匙、稳定冒烟签名、部署身份，五种授权各失败各的，都返回一个 401，看不出是哪一种、能不能恢复；更糟的是任何一个 401 都会触发前端刷新会话，于是一次 Agent 钥匙失效会把正在用的人踢下线。
**现在**：新增授权健康中心页面，把五种身份的授权状态聚成一页；401 按可恢复性拆成结构化诊断码；多种认证方案并行时只写一次 401 响应；**非会话类的 401 不再刷新或退出当前用户会话**；受限管理页给出明确的权限提示而不是空白。
**因此**：「为什么突然没权限了」从一次排查变成一次查看——**前提是它自己先验通**。

### 7. 视觉创作：选了哪个模型就用哪个，等待时看得见进度

**谁受益**：产品用户。
**以前**：模型选择器里混着一堆写死的推荐型号，选了之后后端可能静默换成默认池里的另一个；换分辨率档会把 16:9 悄悄改成 1:1；生图等待时是一块纯平深色方块，进度条还会在放大或平移画布后跑出屏幕。
**现在**：选择器只展示业务模型（开放列表、默认项、排序和用途说明都在业务配置里显式管理，不自动采用网关排序），**显式选择在授权范围内解析、禁用静默回退**，结果里透传实际执行的模型；比例判定先认后端目录再退静态表，换档不再改比例。等待态改版：进度画在画框上，尺寸、阶段、剩余时间合并成底边一行，配色下沉到设计令牌、组件内零硬编码颜色；进度层跟着画布可见区域定位，缩放结束后补齐最后一次状态，选中时内缩到选择框里侧不再被盖住。
**因此**：「我选的是这个、跑出来的是那个」这类困惑消失；等待期从一块静止的深色方块变成有产物形状的进度。

> 连续四周同一个模式，说明问题不在排序也不在收敛条数——**W35 已经把 P0 收敛到两条并附了可核对读数，仍然零达成**。下周因此换一种排法：P0 只留有硬期限的那一条，和能被硬期限倒逼的那一条；其余全部降级。

## 六、下周 (W37) 打算做什么

| 优先级 | 方向 | 要达成的业务结果 | 为什么是它 |
|--------|------|------------------|-----------|
| P0 | **认证迁移的窗口定下来**（**09-17 到期，下周内必须有结论**） | 一份写着日期的清单：六个无口令库各自的切换时间与消费方清单；或者一条写着「这几个决定不加」的台账条目。线上两台 nacos 单独给结论（E54 的三件一起：补 nacos 预设 → 接进门禁 → 排迁移窗口，或明确决定推迟豁免期） | **这是本周唯一一条到期会直接造成停机的事**，且期限落在下周之内。它已经连着两周排在 P1 而没动——P1 这个位置显然不够。**结论是什么都行（迁移 / 推迟 / 决定不加），但必须有一个，且必须落成文字** |
| P0 | **授权健康中心验通，然后拿它诊断采集凭据** | 两个读数：① 授权健康中心一份判「通过」的功能验收；② 下周报告的六源可读数（2/6 → ?/6，逐条列出可读或不可读及原因） | 这两件是同一件事的两半：本周新造的诊断工具没验通，而它要诊断的正是连续四周读不出来的那三源。**先修工具、再用工具**，一条链上两个动作，一次做完。W35 把第二条单独排成 P0 而零达成，本周把它挂到一个具体工具上，让它有落点而不只是一个愿望 |
| P1 | **核心业务稳定冒烟：给出书面结论** | 一份写清「卡在第几步、谁在修、什么条件下算通」的结论，落进台账 | **连续第五周**。本周第一次有了相关提交，但六份未通过报告仍指向同一处。**要的不是再多几次修补，是一句结论**——包括「这条预检已经不适用、决定重写」也算结论 |
| P1 | **给身份层与多项目补一份功能验收** | 一份带明确结论与双主题截图的功能验收报告 | 它是本周三条无验收能力里最该先验的：它改的是「谁能进来、进来能看到谁的项目」，出错代价是越权可见。总览重排与导航治理可以排在它后面 |
| P2 | **E52 补一次真容器验证**（线上两台 nacos 的备份导出与回灌） | 跑一次真容器用例，把「代码已改、未验证」翻成「验过」 | 台账里明确标着未验证；两台 nacos 里存着两个项目的全部配置。**它与 P0 第一条同源**——那条的结论如果是「nacos 接进门禁」，这条就是它的前置 |

> **本表比 W35 又调了一次排法。** 前四周的教训是：可核对读数解决了「说得清有没有做到」，但没解决「为什么总是不做」。本周的观察是——**能嵌进开发流程的事会自然发生，需要单独腾时间的事四周都不会发生**。所以下周两条 P0 的选法变了：第一条靠硬期限倒逼（不做就停机），第二条靠挂在一个具体工具上（修工具是开发动作，不是"腾时间做一次调用"）。这是对排法本身的第三次调整，如果下周仍是零达成，问题就不在排法上，需要换的是投入结构。
