# LLM Gateway 故障止血与恢复 · 指南

> **版本**：v1.1 | **日期**：2026-08-12 | **状态**：部分落地

**一句话**：发生上游故障时只隔离最小对象，优先恢复同池能力，跨池变更必须经业务授权，并始终保留恢复和回滚入口。
**谁该读**：处理线上模型故障的 MAP 值班人、LLMGW 管理员和发布负责人。
**读完能做什么**：在不发起默认付费探测、不扩大故障范围的前提下完成定位、止血、恢复、验证和回滚。

---

## 一、先判断故障属于谁

| 现象 | 责任域 | 第一动作 |
|---|---|---|
| 单个 Provider、Endpoint 或池成员 429、超时、5xx | LLMGW | 查看实际成员与错误分类，隔离最小成员 |
| 用户所选池没有可调度成员 | LLMGW 路由事实，MAP 负责提示 | 确认 AppCaller 是否允许跨池代选；默认按严格失败处理 |
| 模型卡推荐、排序或文案不合理 | MAP | 调整业务关系，不修改 LLMGW 健康状态 |
| 模型目录只剩一个或全部消失 | 目录契约故障 | 保持 MAP 主页面可用，恢复 AppCaller 获准池目录 |
| 通知没有到达 | 通知链路 | 直接从日志和控制台处理，不等待通知恢复 |
| 所有池都不可用且没有恢复入口 | 产品级事故 | 立即恢复控制面入口；不得通过继续禁用对象止血 |

## 二、十分钟止血流程

### 第一步：确定影响范围

从站内通知或 LLM 日志确认：

- AppCallerCode；
- 用户请求的模型池；
- 实际失败的池成员或 Offering；
- 错误类别、首次时间和最近一次时间；
- 同池是否还有健康成员；
- 其他模型池和 MAP 页面是否仍可用。

预期结果：能够把故障缩小到“一个成员”“一个池”或“目录链路”，而不是笼统判断为“整个生图系统坏了”。

### 第二步：隔离最小对象

优先隔离实际失败的池成员。只有证据表明整个池的所有成员都不能执行时，才把池标记为无可调度成员。

禁止动作：

- 批量禁用全部 generation 池；
- 清空 AppCaller 配置；
- 因通知失败关闭模型入口；
- 把 Open 直接改成 Healthy 伪造恢复；
- 在 CDS 或循环任务中持续发起付费生图探测。

预期结果：故障成员不再承接普通流量，同池健康成员和其他模型池不受影响。

### 第三步：决定是否跨池

先查看 AppCaller 的“允许跨池代选”：

- 关闭：保持用户选择，返回结构化失败；MAP 建议用户手动换池。
- 开启：仅按显式候选顺序代选，并检查目标池能力是否兼容。
- 紧急临时开启：必须填写原因、影响范围和失效时间；事故结束后自动关闭。

如果业务只想恢复默认体验，可以更换 AppCaller 默认池，但这不等于允许替已经显式选择其他池的用户跨池。

预期结果：每次模型变化都有业务授权，不会出现“为了成功率偷偷换模型”。

### 第四步：保持 MAP 可用

MAP 应继续显示全部获准池，并对故障池显示风险事实、最近 10 次成功率、平均耗时和样本数。用户仍可查看历史结果、切换其他池或坚持提交原池。

目录暂时读取失败时保留上次成功目录并标记更新时间，不得将空响应直接覆盖成本地空列表。

预期结果：局部上游故障不会把输入框、画布、模型选择器和恢复入口一起锁死。

## 三、恢复流程

### 第一步：进入 HalfOpen

冷却期结束后，对目标成员执行“进入 HalfOpen”。HalfOpen 只放行规定数量的新真实业务请求，不创建合成探测。

如果操作者要求主动测试，界面必须提前说明供应商、请求类型、预计次数和可能费用，并单独确认。

### 第二步：观察真实结果

- 成功：成员恢复 Healthy，连续失败清零，记录恢复事件；
- 失败：成员重新 Open，增加退避时间，记录失败原因；
- 用户错误或取消：不改变成员健康，HalfOpen 名额按策略归还或忽略；
- 结果未知：保持隔离，禁止自动重放。

### 第三步：恢复业务配置

如果事故期间更换了默认池或临时开启跨池代选：

1. 确认原池已经有稳定真实成功证据；
2. 回滚临时 AppCaller 配置；
3. 确认跨池授权已关闭或按原值恢复；
4. 检查 MAP 推荐关系是否需要恢复；
5. 发送恢复通知并关联原事故。

预期结果：恢复的是原有责任边界，不把临时应急配置永久化。

## 四、人工操作入口

控制台应始终提供以下入口，即使没有健康模型：

| 入口 | 用途 | 安全要求 | 当前状态 |
|---|---|---|---|
| AppCaller 路由配置 | 查看获准池、默认池和跨池策略 | 保存前预览影响，请求原因和失效时间 | 多池、默认池和跨池开关已落地；原因和失效时间待补 |
| 模型池详情 | 查看成员健康、近期指标和实际失败 | 默认只操作单个成员 | 已落地近期成功率、平均耗时和成员状态 |
| 隔离成员 | 立即停止故障成员接流量 | 写审计并保留撤销入口 | 待补专用操作 |
| 进入 HalfOpen | 允许受限真实请求验证恢复 | 不直接伪造 Healthy | 已落地“恢复候选”，仍保持不可用并由原子租约放行真实请求 |
| 切换默认池 | 改变未显式选择用户的默认行为 | 不影响显式选择语义 | 已落地 |
| 临时跨池代选 | 业务明确同意时应急 | 默认关闭，必须到期 | 开关已落地，自动到期待补 |
| 回滚上次配置 | 撤销错误止血操作 | 展示前后差异 | 待补 |

尚未落地的入口由具备生产权限的负责人执行单对象、可审计、可回滚的数据修复；不得把临时数据库操作描述为最终产品能力。

## 五、完成确认

一次事故只有满足全部条件才算恢复：

- MAP 主页面、模型目录和历史结果可用；
- 所有获准池仍在目录中，状态与近期指标真实；
- 故障成员保持 Open，或已经通过 HalfOpen 真实成功恢复；
- 用户显式选择不会未经授权跨池；
- 临时跨池授权和默认池变更已恢复或明确保留期限；
- 通知包含故障与恢复两种状态；
- 审计能还原隔离、切换、恢复和回滚的完整过程；
- 验证过程没有未经确认的付费探测。

## 六、回滚条件

出现以下任一情况立即回滚本次人工配置：

- 影响范围从单 AppCaller 扩大到其他 AppCaller；
- 用户选择与实际池不一致且没有跨池授权；
- MAP 模型目录再次被清空；
- HalfOpen 并发超过限制；
- 非幂等请求发生重复提交；
- 通知或控制台被错误地变成数据面前置依赖。

回滚后保持故障成员隔离，恢复上一份 AppCaller 配置，再重新评估，不得为了“看起来恢复”批量重置健康状态。
