## 管理摘要

复制集让一条分支的某个服务同时跑多个版本，入口不变、权重可调、每个成员还有自己的直达入口。这等于已经把一台 **A/B 负载对比台**搭好了一半：多版本并排、流量可控、落点可指定。缺的只有三件事——**打流量、收指标、出结论**。本设计把这三件事补齐。

用户在复制集页签点「压测」，选好并发与时长（都有默认值，可以直接点开始），CDS 就会对**主实例和每一个运行中的副本同时加压**：同一个入口域名、同一条路径、同一个时间窗，唯一的变量是版本。跑的过程中屏幕上是一条**逐秒生长的曲线**（每秒的吞吐与 p95 延迟），配阶段文案和预计剩余时间；跑完给出一句人话结论——「副本 1 的 p95 比主实例高 18%，吞吐低 9%」——以及并排的完整指标表。

这不是要做一个 JMeter。它只做复制集独有、别的压测工具做不到的那件事：**在同一套真实流量入口下，把两个版本摆在一起比**。

## 用户场景

| 场景 | 今天 | 有压测之后 |
|---|---|---|
| 新版本性能有没有退化 | 只能凭感觉，或者把版本发上去等线上告警 | 新旧版本各起一个副本，同时压 30 秒，直接读 p95 差异 |
| 灰度前想知道能扛多少 | 无 | 先压出饱和点，再决定权重从 5% 还是 20% 开始 |
| 依赖升级/参数调优 | 改完只能看功能对不对 | 改前改后两个版本并排，数字说话 |
| 副本到底有没有在分流 | 只有「分流实测」看落点分布 | 压测报告里逐落点的 servedBy 分布同时验证了钉选是否真的生效 |

## 三条不可动摇的前提

这个功能天生危险：它在**生产 CDS 宿主**上主动制造负载，还要按入参向某个 Host 发大量请求。三条前提写死在实现里，不是可选项。

**1. 不许打外网（防 SSRF）。** 执行器永远只连本机 forwarder（`127.0.0.1:<forwarderPort>`），被压的落点由 `Host` 头加 `__rs=<profileId>:<memberId>` 钉选决定。而 `Host` 必须落在「本分支已发布域名」白名单里：域名后缀命中 CDS 根域清单，余下部分是**单个标签**且等于主入口 slug、命名子域或成员直达域之一；自定义域走全串精确匹配。判定与复制集「分流实测」同源，且被单测钉住了三类经典绕过（外部域名、`slug-other` 这类前缀相似域、`slug.evil.com` 这类换根域）。调用方拿不出任何一种能让 CDS 替它访问任意主机的入参。

**2. 不许把宿主打死。** 并发（单落点 20 / 合计 60）、时长（3-300 秒）、总请求数（20 万）、并排落点数（6）、同时在跑的压测任务数（1）全部有硬上限，越界一律拒绝并说明超了哪一条——**不做静默截断**：用户填了 500 并发却按 20 跑，报告上的结论就是假的。磁盘处于 `freeze` 档（`disk-guard`）时直接拒绝发起：恢复期不能再添乱。

**3. 等待期必须有产物。** 报告在跑的过程中就逐秒长出来，前端 1 秒轮询一次，画的是曲线本身而不是一个转圈图标；同时给阶段文案（预热中 / 加压中）、已耗时、预计剩余。这条对齐 `artifact-is-experience` 与 `expectation-management`。

## 并发闸怎么设计的

按 `.claude/rules/concurrency-gate-discipline.md` 的五件套逐条落地：

| 五件套 | 本模块的做法 |
|---|---|
| 等待可取消 | **不排队**。超出上限直接拒绝，并在错误里报出当前占用者是谁、跑了多久。压测是人盯着的即时动作，排到十分钟后自己跑起来只会吓人——不排队是「等待可取消」的最强形式 |
| 持有者身份 | `activeHolders()` 逐条给出 runId / branchId / profileId / 发起时刻 / 已跑秒数，`GET` 列表端点直接透出 |
| 只锁真实资源 | 占位只覆盖「真的在打流量」的那段；读报告、看历史都不占位。跑完（含异常、取消）在 `finally` 语义位置统一释放 |
| 周期收敛 | 每个请求都会先调用 `reapStale()`：心跳超过 90 秒没更新的 `running` 记录判定为异常中断，标 `error` 并释放闸位。心跳由每次记账刷新，卡死的执行器不会永久霸占入口 |
| 健康不变量 | `health()` 断言「占位数 === running 记录数」「占位数不超过上限」「没有心跳过期却仍在 running 的记录」，随列表端点返回。选的是真不变量——不会把合法状态误报成故障 |

fan-out 也守纪律：所有 worker 走 `Promise.allSettled` 等**全体落地**才收尾。任何一个 worker 脱管都会让闸位提前释放而它还在继续打流量，那正是「并发上限形同虚设」的经典成因。

## 指标与结论

每个落点独立记账，按秒分桶：

- **吞吐**：测量期总请求数 ÷ 测量秒数（预热期的样本只进时间序列，不进指标——预热就是为了排除冷启动的干扰）。
- **延迟**：p50 / p90 / p95 / p99 用 nearest-rank 计算。空样本返回 0（报告里 0 表示「没有样本」，比 NaN 更适合直接渲染），单样本时任何分位都等于那个值。
- **错误分类**：超时 / 连接失败 / 5xx / 4xx / 其他。5xx 与 4xx 分开——前者是被压垮，后者多半是路径打错了，两者的处置完全不同。
- **落点核对**：统计响应头 `X-CDS-Replica` 的实际分布，用来验证「钉选真的生效」，而不是我们以为它生效了。

结论以**主实例为基线**（它是「现在线上的样子」，拿它当参照最符合直觉；没有主实例时取第一个落点）。对每个副本给出 p95、吞吐、成功率的相对差异，差异小于 5% 一律判为「基本持平」——**不制造虚假结论**。最后一句总结指出谁最快（p95 最低）、谁最稳（成功率最高）。

## 接口

```
POST   /api/branches/:branchId/replica-loadtests            发起（202，返回 running 快照）
GET    /api/branches/:branchId/replica-loadtests            列表 + 硬上限 + 占用者 + 健康
GET    /api/branches/:branchId/replica-loadtests/:runId     报告 / 实时进度（前端 1s 轮询）
POST   /api/branches/:branchId/replica-loadtests/:runId/cancel  取消
```

发起入参：`profileId`（必填）、`memberIds`（省略 = 主实例 + 全部运行中副本）、`concurrency`、`durationSec`、`warmupSec`、`method`、`path`（省略 = 按服务的 `pathPrefixes` 自动推导）、`host`（省略 = 分支主预览域名）、`headers`、`body`。请求头名受限于字母数字连字符，`Host` / `Content-Length` / `X-CDS-Loadtest` 等保留头不许覆写——覆写 `Host` 等于偷换被压目标。

## 界面

复制集页签底部新增「压测」按钮（容器级与项目级两个画布都有），打开一个模态：

- **表单**：落点自动带出（主实例 + 副本，未运行的置灰并说明原因），并发与时长有默认值，方法/预热/路径收在「高级选项」里。打开就能点「开始压测」，不需要先去别处准备什么。
- **运行中**：主视觉是两张逐秒生长的折线图（吞吐、p95），配阶段文案、进度条、预计剩余，以及一个醒目的「停止压测」。第一个采样点到达前显示「正在采集第一个秒级采样点」，不是空白。
- **结束后**：先是一张结论卡（一句人话），再是并排指标表（请求数 / 成功率 / QPS / 四个分位 / 错误分类），最后是历史压测列表。

配色走复制集画布同族（禁红禁琥珀——红专属错误、黄专属草稿预期），全部颜色来自 token / Tailwind 语义类，双主题可读。

## 已知边界

| 边界 | 说明 |
|---|---|
| 压的是 forwarder 全链路 | 请求穿过本机 forwarder 再到容器，测得的是「用户视角的端到端延迟」，不是容器裸性能。做版本对比时这不影响结论（两侧同链路），但不要拿这个数字当容器基准 |
| 单进程发压 | 发压端是 CDS 自己的 Node 进程，合计并发 60 的上限也是为此设的。要压出更高量级需要外部压测机，不在本设计范围 |
| 报告在内存里 | 每分支保留最近 20 条，CDS 重启即丢。压测是即时诊断动作，不做持久化；需要留档就把结论截图进验收报告 |
| 无 API label | 新增的四个端点尚未登记进 `server.ts` 的 `resolveApiLabel()`（该文件属其他轨道），Activity Monitor 上会显示裸 URL。待并线合流后补 |
| 预热期样本 | 预热样本进时间序列（负秒）但不进指标，图上只画测量期，避免冷启动尖峰误导 |
