# CDS 分支详情「总览」 · 债务台账

> **版本**：v1.0 | **日期**：2026-09-02 | **状态**：开发中

**一句话**：记录总览视觉化重排里故意先不做的几件事，以及各自什么时候必须补；已解决的保留原文并标注，用来记住当初「做不了」的理由错在哪。
**谁该读**：接手总览面板或容器指标历史的工程师；看到总览曲线不对劲、想先确认「是不是已知边界」的排障值班。
**读完能做什么**：判断眼前的现象属于已知取舍还是新故障，并知道该改哪一处。

## 总览

2026-09-02，分支详情「总览」页签从八个等重方块（其中四个常年显示 0）重排为分段健康环、
CPU/内存图、吞吐图与部署耗时柱状图，并把容器指标历史从「前端 React state 里的 60 点 ring」
下沉到服务端（查询契约借 Netdata 的 after / before / points / group 形状）。

那一轮 Review 出了二十条意见，绝大多数已修。本台账只记**有意延期**的边界项，
防止下一次接手的人以为它们没人看见。

同批教训已固化成「判据与接线纪律」那条规则（路径见文末）：本模块反复撞上的
是同一个形状——**判据数的是格子，不是数据**；或者一个判据同时回答了两个问题。
八次里没有一次是「逻辑写错」。

## 债务清单

### D1. 缺口在图上被画成 0（P2）—— 已解决 2026-09-02

**曾经的问题**：服务端对没有样本的桶如实返回 `null`，前端却把它映射成 0 才能参与堆叠。
一段真实的采样断档在图上表现为「掉到零又爬回来」，和「这段时间确实很闲」长得一模一样。
真人验收的线上截图里就有这样一道谷，而那一刻没有任何服务空闲过。

**当时为什么先不做**：判断逐点排除 `null` 会让堆叠各层的下标错开——那正是更早那个
「黑色缺口」缺陷的成因。

**实际怎么解决的**：不逐点排除，而是按「有样本的连续区间」把几何切成多段子路径，
各层共用同一个轴级掩码，因此断在同一处、下标不会错开。这是 Netdata 的画法：
没有的值一律不画。桶内某个容器单独没有值仍按 0 计（那是「它当时没在吃资源」，
不是「没测到」）。单桶孤岛给一个桶宽的方块。

**守卫**：几何层五条 + 组件层渲染冒烟一条，均做过红绿闭环。留在台账里是为了记住
「当时判断做不了」的那个理由错在哪：错在把「逐点排除」当成了唯一实现。

### D2. 远端 executor 分支没有指标（P2）

`branch.executorId` 指向远端执行器时，容器不在主控本机。两个写入方——常驻采样器
（executor 模式下根本不构造）与 `/metrics` 端点（走本机 `docker stats`）——都覆盖不到它，
于是总览永远只有空桶。

**这不是本次重排引入的**：旧的实时资源面板同样取数于 `containerService.getServiceStats`，
全程没有 executor 代理，远端分支一直就是空的。重排只是把同一个空白换了种呈现。

**当前表现**：`filled` 为 0 时不画曲线，也不画成零线，走的是「还没攒够帧」那一档。
问题是那一档的文案承诺「约还需 N 秒出现曲线」——对远端分支那是永远不会来的曲线。

**什么时候必须补**：远端 executor 进入常规使用时。届时要么做 executor 侧 stats 端点 +
主控代理，要么让 executor 把样本推给主控；在此之前**至少**应给这一档单独文案
（「该分支运行在远端执行器，主控暂不采集其容器指标」），先别让骨架屏撒谎。

**改哪里**：指标历史模块的写入侧、分支路由上的两个指标端点，以及总览骨架屏的文案。

### D6. `/metrics` 的 status 抄自持久化状态，不是当下的运行事实（P2）

容器在 CDS 之外消失（外部 `docker rm`、宿主重启）时，持久化状态里仍写着 `running`，
而 `docker stats` 已经取不到它。`/metrics` 端点返回的 `status` 直接取自持久化状态，
于是总览把它当成在跑：图例给它算当前值（退回历史最后一个桶的旧读数），合计也把它算进去。

**这不是「状态不新鲜」**——那条已经修了（成员集合与状态都取自每 5 秒的 `/metrics`）。
这条更深一层：**那份「新鲜」的状态本身就不是运行事实，只是被新鲜地复述了一遍**。

**为什么先不做**：正确的做法要引入第三种状态语义（「记录说在跑、但这一刻取不到读数」），
并决定健康环、图例、合计各自怎么呈现它——这是新的语义类别。而且不能简单地
「取不到读数就判停」：`docker stats` 偶发超时是常态，那样会让健康环闪烁，
比偶尔多算一个已消失的容器更糟。

**什么时候必须补**：有人在总览上看到一个早已不存在的容器还挂着读数并因此误判时。
届时要一起做的还有：区分「这一刻没取到」与「连续 N 次没取到」，只有后者才降级。

**改哪里**：分支路由上 `/metrics` 的响应装配（status 那一处），以及总览把
「历史最后一个桶」当作当前值的那条兜底。

### D7. 图按下标定位，不按每点的绝对时间（P2）

服务端每个点都带了时间戳，前端没用——图是按数组下标等距画的。

**目前没有误差**：服务端保证「桶等宽 + 轴长度恒定」，所以下标与时间线性对应。
两端的标签也已经改成真实钟点，不再说含糊的「现在」。

**为什么先不做**：改成按时间戳逐点定位，等于把「各序列长度必须一致」这条不变量
从服务端搬到前端。这条不变量破掉的后果是有前科的——各容器各自跳过自己的空桶时，
前端按下标堆叠会算出 NaN，整段路径静默不画（图上一块黑）。搬到前端意味着每一处
几何都要自己处理时间对齐，出错方式更多、更难发现。

**什么时候必须补**：桶宽不再恒定的那一天（例如按事件对齐、或允许非等宽的自适应分桶），
下标与时间的线性关系一破，就必须改。

**改哪里**：几何函数的 x 坐标计算，以及抽屉侧把时间戳一并传下去。

### D3. 指标历史是内存态，进程重启即丢（P2）

有界内存（保留时长 / 单容器点数 / 容器总数三重），CDS 自更新或重启后需要重新积累，
约 2-3 分钟才有像样曲线、30 分钟才是完整窗口。

**为什么先不做**：观测视图不是审计账本，不值得为它引一张表。要长留存应接外部时序库
（Netdata Agent 以 HTTP 方式接入，进程分离、许可证干净）。

**什么时候必须补**：有人要用它做事后追溯（「昨天下午那次 OOM 前 CPU 什么样」）时。

### D4. 入口可达性没有历史（P1）

设计里的「24 小时可达色块阵列」未实现——`cds.readiness-path` 的探测结果目前不落库，
总览只能显示「此刻通不通」。

**改哪里**：探测结果需要一处存储，然后在总览的入口卡下方补色块阵列。

### D5. 崩溃循环在总览上看不出来（P1）

反复重启的容器在总览上表现为「running」，因为状态取的是当下那一帧。要看出崩溃循环
需要 `docker inspect` 的 `RestartCount`，目前没有采集。

**改哪里**：容器服务的状态采集侧补 `RestartCount`，总览健康环对它单独标记。

### D8. 指标历史的自身统计没有接进诊断面（P2）

历史存储里有一个「当前跟踪多少容器、多少点」的统计函数，本来注释写着「用于排查内存
增长」——但全仓没有任何端点、监控或日志消费它，那句话是兑现不了的承诺。已把它降级为
测试用（`__` 前缀）并删掉那句承诺，不再假装生产可观测。

**为什么先不做**：接进诊断面要新增一处生产可观测表面，超出本 PR「总览重排」的范围。

**什么时候必须补**：真出现指标历史吃内存的疑虑时；或下次动 CDS 自身诊断端点时顺手带上。

**改哪里**：把这个统计接进已有的自检 / 诊断端点，同时把函数改回公开命名。

### D9. 部署去重靠时间邻近，不是稳定身份（P2）

合并「实时操作记录」与「持久化操作日志」两个来源时，判定「是不是同一次部署」用的是
「构建类 kind 归一 + 起始时刻相差 3 秒内」。这个判据两头都会错：两次真实的构建在
3 秒内先后发起（快速失败后立刻重试）会被并成一条；而服务端的 `OperationLog.startedAt`
是拿到租约、做完预处理之后才落的，与前端记的发起时刻可能差出 3 秒以上，重复就漏掉了。

**为什么先不做**：正解是按稳定的运行身份去重，而现在**两边都没有这个身份**——
`OperationLog` 只有 `type` / `startedAt` / `commitSha` / `status`，前端的操作记录按分支
id 作键。要做就得在服务端给操作日志加一个运行 id 并透传到前端，那是后端契约变更，
超出本 PR「总览重排」的范围。

**什么时候必须补**：部署柱状图的成功率 / 中位数要被当作正式指标看待时；或下次动
操作日志契约时顺手带上。

**改哪里**：服务端操作日志加运行 id 并进 API 响应，前端发起部署时记下同一个 id，
去重改为按 id 比对，时间窗口降级为兜底。

### D10. 部署并打开成功后，柱状图要等重开抽屉才更新（P2）

「部署并打开」成功时，那条实时记录会被「打开预览」的记录覆盖，导航成功后又被清空；
而抽屉的操作日志快照是打开时拉的、之后不刷新。于是刚部署完的那一次在柱状图和
「上次构建耗时」里暂时看不到，要重开抽屉才出现。

**为什么先不做**：需要在部署完成后重新拉一次操作日志（或让它跟着 SSE 走），属于新增
一条数据刷新链路，不在本 PR 范围内。注意这**不是本 PR 引入的**——在「打开预览」还
借用 `preview` 这个类型的年代，同样会被覆盖和清空。

**什么时候必须补**：与 D9 同批做，两者都动部署历史这条链路。

**改哪里**：部署完成的回调里重新拉一次该分支的操作日志，或把操作日志接进已有的分支
SSE 流。

### D11. 在途状态的文案分档已到复杂度上限，需要换写法（P2）—— 已解决 2026-09-03

**曾经的问题**：执行器新建分支时，分支先以「构建中」落库、服务集为空，随后才拉代码
并分配 profile。此时「还没起来的服务数」是 0，判断句会走进「正在部署，当前服务仍在
运行」这一档，而同一屏另一处又写着「尚未配置服务」。空服务集属于「正在开通」，不该
套用「零缺口」那一档。

**为什么先不做**：这是同一片区域连续第六轮出现的同类问题。判断句已经是五层嵌套三元、
内含一层三元，每加一个条件都会在别处冒出新的矛盾——前五轮每一轮的修复都带出了下一轮
的发现。再补第六个条件是重复那个动作，不是解决它。

**该怎么做**：把「这一屏该说什么」从散在各处的三元表达式，改成一个**显式的状态判定**：
先由（生命周期、服务集是否为空、就绪数、异常数、历史帧数）归约出一个有限状态
（正在开通 / 正在部署 / 部分就绪 / 一切正常 / 已停机 / 有异常），再由状态查表得到
判断句、色调、入口卡标签、骨架屏注解。这样新增一档只动表、不动条件树，且每一档都能被
单测穷举——正如轮询那套并发取舍抽成独立模块之后才真正测得住。

**实际怎么解决的**：照上面写的做了——先把（生命周期、服务集是否为空、就绪数、异常数）
归约成八档有限状态，再由状态查表取判断句、色调、入口卡副标题、「为什么没有曲线」这四处
文案。条件树整个消失，四处消费点各自那套条件也一并删掉。

动手时还发现了同类的第二例，Codex 六轮都没点名：分支在跑、服务集为空时，判断句会说
「还有 **0** 个服务没起来」，而同一屏另一句写着「尚未配置服务」。它和 D11 原本记的那例
是同一个病根（缺口数为 0 时那一档没人管），一并修掉。

顺带两处文案调整：静止态且没配服务的判断句由「分支未运行」改为「尚未配置服务」——
后者是根因，前者只是它的结果；「正在开通」这一档不再劝用户「先去构建配置」，分配服务集
的是执行器不是用户。

**守卫**：状态表自身 23 条（八档全覆盖 + 四条跨两百多种事实组合的不变量），面板侧 4 条
渲染断言证明四处文案真的接上了这张表。全部做过红绿闭环；其中把接线抽掉那一次，表的
23 条仍然全绿、只有面板侧变红——这正是要防的「形状 2」。反例用例把**被替换掉的那串
嵌套三元**一字不改地搬进测试，证明这些不变量不是「怎么写都绿」。
