# CDS 验收报告首页的聚合口径 · 设计

> **版本**：v1.0 | **日期**：2026-09-16 | **状态**：已落地

> **关联实现**：CDS 服务端的两个只读聚合（跨项目流水线、单项目结论）与验收报告正文的持久层
> **关联设计**：[design.acceptance.system.md](./design.acceptance.system.md)（验收体系本身）、[design.acceptance.kb.md](./design.acceptance.kb.md)（报告归档进知识库）
> **一句话**：验收报告首页不再是报告列表的放大版，而是先给一句挂着数字的判断，再给支撑它的图。
> **谁该读**：要改 CDS 验收首页、或要新增一种「报告与改动对不上」判定的工程师。
> **读完能做什么**：说清首页每个数字的口径从哪来、为什么这么定，改动时知道哪条线不能动。

---

## 1. 为什么有这篇

首页此前是报告列表的放大版：一排计数（改动 5 / 部署 4 / 验收 1 / 合并 0、漏 3、另有 18 份无从核对）。每个数字都对，合起来不告诉人任何事。我们判定它有两层不合格：看得懂的人也读不出结论，看不懂的人连「这个页面是做什么的」都答不上来。

首页服务的不是处理单条待办的人。它服务的是老板、观察者、架构师——他们要纵观全局，不动手改某一份报告。所以首页既不该是待办队列，也不该是某一份报告结论的放大。

改版因此做两件事：把读者要的那句判断算出来；把支撑这句判断的口径收敛成唯一一份，防止同一屏出现两个打架的数。

判断句摆在哪一层是分开的：选了项目时它就是第一屏；不选项目时第一屏只给图，判断句要点「放大」才出来。这一处与设计初衷有落差，已记债务（见第 9 节）。

这篇记的就是那些口径，以及每一条为什么定成现在这样。**实现细节不进本文，要细节直接读源码**；这里只回答「为什么」和「动它会踩什么」。

## 2. 两层视图

首页按「选没选项目」分成两层，两层回答的问题不同。

| 层 | 何时出现 | 回答的问题 | 主体 |
|---|---|---|---|
| 跨项目流水线 | 不选项目 | 现在多少改动、卡在哪一环、在往哪走 | 紧凑态：一条总览分流条 + 三张走向折线。放大态另加判断句与逐项目明细 |
| 单项目结论 | 选了项目 | 这个项目现在能不能用、谁的问题、下一步动谁 | 结论头条 + 发布闸 + 结论分布 + 根因集中度 + 台账 |

两层共用同一份报告数据与同一套判定口径，只是聚合的轴不同：前者的轴是「改动」，后者的轴是「验收对象」。

---

## 3. 跨项目流水线：轴是改动，重点是环与环之间的落差

### 3.1 改动单元与五步流水线

CDS 里一条改动的完整路径是固定的：**开分支 → 起预览 → 跑验收 → 出结论 → 合并主干**。首页只统计中间的部署与验收两环。

这个范围**本该写在屏幕上**，否则读者会把首页的数误当成全量工作量。早先版本确实有一条五步流程条讲这件事，但在放大态改成与紧凑态同一套视觉语言那一次被一并删掉了，现在屏幕上没有任何一句交代范围。这是对着第 1 节那个目标的回归，已记债务。

改动单元的身份是分支名。它同时可能带着 PR 号与提交号，这三样构成后面对齐报告用的钥匙。

### 3.2 四种漏，以及被删掉的第五种

对这批读者有信息量的不是每一环的绝对数，而是环与环之间掉下去的那部分：

| 漏 | 含义 | 为什么它是漏 |
|---|---|---|
| 部署了没人验 | 起了预览，一份报告都没有 | 验收没跟上开发 |
| 合并了从来没验过 | 进了主干，一份报告都没有 | 最危险的一种 |
| 验了没过还是合并了 | 有报告且结论是未通过，仍然合并 | 门形同虚设 |
| 报告没记它验的是谁 | 分支、提交、PR 号三样全空 | 证据永远挂不上，是归档流程的缺口 |

曾经有第五种「报告对不上任何分支」，**已经删掉**。拿主实例真实数据核过：153 份对不上的报告里，152 份点名的分支根本已经不在 CDS 上（现存只有 71 条）。CDS 不保留几个月前的分支，对不上是常态不是异常。把常态报成漏，等于首页喊一次狼，以后真漏出现时没人再信。它现在只作背景数。

**这条取舍是本设计里最值得记住的一条**：一个指标要能当漏点名，前提是它在健康系统里应该接近零。做不到就别放进漏的那一栏。

### 3.3 三段分流必须恒等于总数

总览条把改动拆成三段：没起预览 / 待验收 / 已验完。三段相加**恒等于**改动总数，靠的是逐级夹取（部署数先夹进改动数，验收数再夹进部署数），不是三段各自取非负。

分别夹会在脏数据上失守：当验过的比部署的还多时（一份报告挂在一条从没部署过的分支上就会这样），中间那段被夹成零而最后一段原样留着，三段之和大于总数，画出来就是分段条比总长还长。

这个函数是唯一一份，图、逐项目明细、第一屏那句判断共用它。此前有两份实现、口径不同，而两份都「看起来对」，结果是屏幕上「都验过了」配一张画着未验收方块的图。

## 4. 单项目结论：轴是验收对象

### 4.1 标题合同与版本折叠

报告标题遵守三段式合同：`{前缀} · {对象} · {日期}`，前缀限定在九类之内，不在此列的归「其他」。解析在服务端做，是唯一事实来源——前端不得自己再实现一份。

同一个（项目 · 前缀 · 对象 · 目标日）只保留创建最晚的一版，早期版本记成「被取代」。这是通过率分母的前提：不折叠的话，反复归档同一个目标会把分母撑大，通过率变成归档次数的函数而不是质量的函数。

被取代的那些版本**也要带着解析结果返回**。台账展开旧版本时，前端如果查不到它们的类别，会整批掉进「其他」——页签计数虚高，点真实类目又看不到它们。

### 4.2 生效结论：只在一个边界上换算

写入侧允许结论字段与缺陷数打架：一份标着「通过」却记了 P0 的报告，接口照收。而验收规范写的是「P0/P1 存在，总 Verdict 不得 pass」。两者必须有一个裁判。

**裁判只有一个，而且只在数据进入聚合的那一个边界上跑一次**：有阻断缺陷即判未通过，否则按报告自己写的那个。换算之后，计数、通过率、根因簇、日历、发布闸、跨项目流水线、台账行、回写 GitHub 的检查结论全部自动跟上，谁都不必也不许再判一遍。

这条边界是被逼出来的。前三轮都是逐个消费方补：改了首屏，发布闸照旧说「可以发布」；改了发布闸，跨项目流水线还按原始结论计数；改了流水线，台账行又显示着「通过」。补一个漏一个，因为判据分散在每个消费方手里。第四轮改成边界收敛，同类问题一次性消失。

报告自己写的那个结论仍然保留，但**只给措辞用**：需要指出「它自称通过、实际有阻断缺陷」时才拿出来，让矛盾看得见，而不是直接说成「未通过」把矛盾藏起来。

**动这块的判据**：如果你正准备在某个消费方里再写一次「有没有阻断缺陷」，停下——那意味着边界漏了一个出口，该补的是边界，不是这个消费方。

### 4.3 缺陷计数先夹再加

缺陷数写入侧不拦负数，而下游用「大于零」与「等于零」两个分支分流，负数两边都不落。所以每一项在参与任何计算之前都夹成非负；簇内求和也是**先夹再加**——直接相加的话，同一簇里正负两份会抵消，根因那一行说「没有记录阻断缺陷」，而首屏说「有功能坏了」。

### 4.4 发布闸

发布闸看的是最近一份发布验收的生效结论。带阻断缺陷的「通过」不放行，且措辞要让矛盾露出来。

已知边界：它认的是全历史最近一份发布验收，**不认当前要发的那一版**。这条记在债务台账里，正解要把闸绑定到候选版本。

## 5. 报告与改动的对齐：三把钥匙，对不上就说对不上

两边都可能记着分支名、提交号、PR 号。对齐规则按可信度排序，且每一条的强弱不同：

| 钥匙 | 用法 | 为什么 |
|---|---|---|
| PR 号 | 两边都记了就以它为准，相等即命中，**不等即否决** | 分支名会被复用：同一条分支跑完一个 PR 再开下一个。退回分支名会把上一个 PR 的报告挂到新改动上，首页据此报「已验收」，而这条改动其实一份报告都没有 |
| 提交号 | 只做正向信号，**不做否决**（允许任一方是前缀） | 改动侧给的常常是合并提交，报告记的是分支头提交，两者天然不同。拿它否决会把正常的合并覆盖判成没验，比漏判更糟 |
| 分支名 | 兜底 | 最弱的一把 |

三把都对不上就是对不上，**绝不猜**。

这套判据在改版过程中被要求生长过四次。**它已经到了不该再长的地步**：每加一把钥匙或一条同义规则，误挂的风险就上升一分，而误挂的后果是首页给出一个「已验收」的假保证。后续要提高对齐准确率，正解是给改动单元一个稳定身份（一张改动事件表），不是继续往这个自由文本判据上加分支。这一条连同它派生的四笔债务都记在台账里。

## 6. 正文的持久层：账在哪，货就在哪

改版中修掉的最严重的一个缺陷与展示无关：报告元数据在数据库里（持久、跨分支共享），正文却写在容器本地盘。CDS 跑在容器里时容器一重建正文全没、元数据还在——列表里 23 份报告，点开每一份都是 404。

现在的划分是：

- **正文进对象存储，那是权威地址**；本地盘降级为读缓存，未命中时回源并回填。
- **写入顺序是先正文后元数据**。反过来会在上传失败时留下一条点不开的幽灵记录。
- **凭据配一半时拒绝启动**，不做「有几个算几个」的降级——半套凭据只会写出一批取不回来的对象。
- **真的只能落本地时要写在脸上**：元数据上留机器可读的标记，让接口和界面当场说清「这份正文重建就没」，而不是等人点开吃 404。
- **「读不到」的几种成因必须分得开**：没配对象存储、归档于本次改动之前、配了但取不回来——三者的下一步动作完全不同，压成一句 404 等于什么都没说。

这条纪律已经提升为全仓规则（元数据与实体必须同一持久等级），本文不重复它的通用判据，只记 CDS 报告这条链路的具体走法。

已知边界：元数据记的是对象键，不记它当时落在哪个桶。换桶之后，换之前的报告会被拿新桶去找。这条记在台账里，正解是元数据记下落点。

## 7. 第一屏那句判断

这句判断是**规则生成**的，不是大模型生成的。理由是首页要秒开、要可复现、出错能定位到具体分支；大模型更适合长文本汇报，不适合仪表盘头条。

三条自律：

1. 每句挂着真实数字。「整体表现良好」放到任何团队都成立，等于没说。
2. 算不出来就不出这句，不为凑版面降低标准。
3. 覆盖率干净不等于结论干净。三类漏都为零时，「已验完」那一段里仍然可能有未通过，这时候不许绿着说「都验过了」。

第三条是踩出来的：漏为零就落到「都验过了」，而同屏的总览条正把那几条画成红的。同一屏一个说好一个说坏，读者第一眼看的恰好是说好的那个。

这句判断出现在两个位置，行为不一样：

- **选了项目**：它就是第一屏那句结论头条，带支撑点与下一步。
- **不选项目**：紧凑态只渲染总览条与走向折线，**判断句不在**；点「放大」才出现。

紧凑态少字多图是定下来的取舍，不是遗漏。但「判断句整个不出现」与第 1 节「先给一句挂着数字的判断」有落差，取舍是否要调整由人定，不由自动审查定，已记债务。

## 8. 怎么证明这些口径还成立

哪些有守卫、哪些只是约定，必须分清——把「约定」说成「有守卫盯着」，下一个人就会以为可以放心改。

| 口径 | 有没有守卫 | 判据形状 |
|---|---|---|
| 三段分流之和恒等于改动总数，脏数据下也成立 | 有 | 直接断言三段相加等于总数，并喂脏数据（验过的比部署的还多） |
| 「对不上」不计入任何一档漏 | 有 | 构造一份点名了已回收分支的报告，断言它落进背景数而不是漏 |
| 被取代的版本也带解析结果 | 有 | 断言旧版本的类别不是「其他」 |
| 正文持久性 | 有 | 测试真的删掉本地缓存目录，模拟一次容器重建 |
| 回写 GitHub 与台账「不通过」视图走生效结论 | 有，但**按站点写死** | 扫那两个文件，断言它们不再读原始结论 |
| 生效结论的换算只在边界发生 | **没有** | 见下 |
| 对齐判据只有一份实现，前端不得另写 | **没有** | 见下 |
| 标题解析是服务端唯一事实来源 | **没有** | 见下 |

后三条是约定不是闸门，现状如实说：

- 换算函数当前有两个调用点——数据进聚合的那个边界，以及回写 GitHub 的路由（后者是刻意的，
  它不走聚合）。没有任何东西扫描「还有没有第三个消费方自己判了一遍阻断缺陷」，那正是前三轮
  补一个漏一个的成因。
- 对齐判据与标题解析目前确实各只有一份、前端也没有另写，但没有守卫拦住后来人去写第二份。

这三条都记了债务。写新的消费方时先看第 4.2 节那条判据，别等 review 抓。

## 9. 已知边界

改版期间判定为「有价值但超出当前范围」的共 20 条（其中两条各记两笔，合计 22 笔），加上本文与代码对照审查新记的 3 笔，全部固化在 [debt.cds.md](./debt.cds.md)。其中最值得先做的三笔：

1. **改动事件表**：记「改动 / 项目 / 开启时刻 / 首次部署时刻」。它一旦有稳定身份，第 5 节那个越长越复杂的对齐判据、走向图里缺失的部署那一环、以及墓碑写死已部署这三件事会一起消掉。
2. **报告元数据记落点**：换桶之后旧报告才取得回来。
3. **同一份报告并发改写的串行化**：目前回滚会覆盖后到的那一版。
