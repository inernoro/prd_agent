# CDS 多 Web 入口配置与验收 · 指南

> **版本**：v1.0 | **日期**：2026-08-11 | **状态**：已落地

**一句话**：用一份项目配置声明主页面和其他独立页面，由 CDS 自动去重、排除健康地址，并把用户定义的名称展示到所有入口位置。
**谁该读**：要为一个 CDS 项目增加、删除或改名多个页面的人；代用户维护部署配置和验收结果的智能体。
**读完能做什么**：独立完成多入口配置、部署和公网验收，并能处理入口重复、名称错误、页面仍显示旧数据等问题。

---

## 一、你将完成什么

照本指南操作后，CDS 的“应用已上线”区域会只显示真实的用户页面：

- 主页面只出现一次。
- 每个独立页面使用产品名称，不使用容器名或“网关健康”。
- 健康检查地址不会出现在入口列表。
- 分支侧栏、完整详情页和预览地址命令得到同一组结果。

## 二、开始前先分清三件事

| 你手里的信息 | 应该放在哪里 | 示例 |
|---|---|---|
| 用户打开后要操作的页面 | Web 入口名称和页面路径 | 项目控制台、帮助中心 |
| 服务如何获得独立网址 | 路由前缀或命名子域 | 根路径、帮助中心子域 |
| CDS 如何判断服务已启动 | 就绪检查路径 | 健康或就绪接口 |

不要把三者合成一个字段。健康检查返回成功，只能证明服务可用，不能证明它是一个适合用户打开的页面。

## 三、推荐的维护方式

用户不需要自己寻找 CDS 后台中的多处配置。最简单的做法是直接告诉 Agent：

> 请把这个项目的用户入口整理为四个：项目控制台、帮助中心、开放平台、知识库。主页面只保留一次，页面地址不要使用健康检查路径。请更新项目根配置、校验、导入 CDS、重新部署并验收。

Agent 应完成以下工作：

1. 读取项目现有服务和页面，而不是仅凭服务名称猜测。
2. 更新项目根的 compose 配置。
3. 校验页面名称、路径和唯一主入口。
4. 把配置提交到 CDS，并等待目标分支重新部署完成。
5. 从 CDS 返回的实际入口数据取地址，逐个打开验收。
6. 用人话汇报最终名称、数量和可访问结果。

## 四、最短成功路径

### 第一步：列出真实用户页面

先回答“用户会主动打开哪些页面”。不要把以下内容算入：

- 健康、就绪、存活检查。
- 只提供数据的 API。
- 构建器、任务执行器和内部 Worker。
- 同一个主页面的备用路由。

### 第二步：确定唯一主页面

通常，承载根路径的已命名 Web 服务就是主页面，不需要额外声明。只有多个服务都可能成为主页面时，才显式指定一个主入口。

### 第三步：给其他页面独立路由和产品名称

每个需要单独展示的页面同时声明：

- 一个独立命名路由。
- 一个用户能理解的产品名称。
- 一个用户实际落地的页面路径。

只声明命名路由而不声明页面名称，表示“这条路由可访问，但不应出现在用户入口清单”。

### 第四步：把探活路径留给机器

就绪检查可以继续使用健康地址，但 Web 入口路径必须指向真正页面。CDS 会拒绝把健康、就绪、存活类路径作为用户入口。

### 第五步：校验、导入并重新部署

配置保存并不等于运行中的旧分支已经生效。必须重新部署目标分支，等所有服务进入运行状态后再看入口结果。

### 第六步：只使用 CDS 返回的地址

不要根据项目名、分支名或子域规则手工拼网址。使用预览地址命令读取 CDS 当前实际发布的全部入口；有多个入口时全部保留。

## 五、配置示例

下面只展示与入口有关的部分。镜像、命令、端口和环境变量按项目实际情况保留。

```yaml
services:
  admin:
    labels:
      cds.path-prefix: "/"
      cds.web-entry-name: "项目控制台"
      cds.web-entry-path: "/console/"
      cds.readiness-path: "/healthz"

  help:
    labels:
      cds.subdomain: "help"
      cds.web-entry-name: "帮助中心"
      cds.web-entry-path: "/"
      cds.readiness-path: "/healthz"

  open:
    labels:
      cds.subdomain: "open"
      cds.web-entry-name: "开放平台"
      cds.web-entry-path: "/"
      cds.readiness-path: "/healthz"

  knowledge:
    labels:
      cds.subdomain: "knowledge"
      cds.web-entry-name: "知识库"
      cds.web-entry-path: "/reader"
      cds.readiness-path: "/healthz"

  api:
    labels:
      cds.subdomain: "api"
      cds.readiness-path: "/healthz"
```

这个示例最终显示四个入口。`api` 有独立路由和健康检查，但没有 Web 入口名称，因此不会被展示为第五个入口。

## 六、人工修改时怎么做

如果不交给 Agent，人工也只维护项目根的 compose 配置：

1. 修改对应服务的入口名称、页面路径和路由。
2. 在仓库根目录运行配置校验。
3. 使用 CDS 导入命令提交这份配置。
4. 在 CDS 中批准导入并重新部署目标分支。
5. 部署完成后查询实际预览地址并逐个验收。

常用命令：

```bash
python3 .claude/skills/cds/cli/cdscli.py verify cds-compose.yml
python3 .claude/skills/cds/cli/cdscli.py import --project <项目ID> --compose cds-compose.yml
python3 .claude/skills/cds/cli/cdscli.py --human preview-url
```

如果项目安装技能的位置不同，把命令中的技能根替换为当前宿主的实际位置。不要复制一套新的地址计算脚本。

## 七、如何确认完成

### 7.1 配置检查

- Web 入口数量与产品定义一致。
- 每个入口都有用户定义名称。
- 只有一个主入口。
- 页面路径不是健康、就绪或存活地址。
- API、Worker 和构建服务没有被误标为用户页面。

### 7.2 部署检查

- 目标分支已经在配置修改后重新部署。
- 所有必需服务处于运行状态。
- CDS 返回的入口数量与配置一致。

### 7.3 公网页面检查

- 逐个打开 CDS 返回的地址，页面正文能正常显示。
- 页面引用的实际脚本和样式资源返回成功、类型正确且内容非空。
- 分支侧栏和完整详情页显示相同的名称与地址。
- 页面中没有“网关健康”和健康检查路径。
- 桌面端侧栏约占当前屏幕三分之二，仍能看到左侧项目上下文；小屏设备允许全屏。

只有配置、部署和公网检查同时通过，才能说“多入口已经完成”。

## 八、常见失败与恢复

| 现象 | 常见原因 | 处理方式 |
|---|---|---|
| 实际四个页面却显示五个 | 主页面又被当作命名入口展示 | 确认主页面唯一；升级 CDS 后重新部署 |
| 出现“网关健康”或健康地址 | 旧数据或把探活路径当页面路径 | 改为真实页面路径，重新导入和部署 |
| 名称是服务名而不是产品名 | 没有显式声明入口名称 | 使用用户定义名称，不依赖自动命名 |
| 保存后仍看到旧结果 | 分支未在配置更新后重新部署 | 重新部署并刷新当前分支面板 |
| 入口打开了另一个页面 | 页面路径没有考虑主域路由前缀 | 核对服务挂载位置和页面自己的落地路径 |
| 命令行与页面数量不同 | 一端仍在读取旧兼容字段 | 升级 CDS 技能和服务，优先使用新入口结构 |
| 下次接入后配置又变回去 | 只改了 CDS 页面，没有同步项目根 | 把现场配置写回项目根并提交 |

## 九、给 Agent 的完成汇报模板

```text
已完成多 Web 入口配置和部署。

入口数量：<N>
入口名称：<名称列表>
服务状态：<运行中数量>/<服务总数>
健康地址混入：否
重复入口：否
公网验收：<逐个页面结果>
用户还需操作：无 / <唯一明确动作>
```

汇报以结果为主。用户要求时再补充配置字段、校验命令和排障细节。
