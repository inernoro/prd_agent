# 向量模型供应商 · 债务台账

> **版本**：v1.0 | **日期**：2026-08-10 | **状态**：等外部输入

**一句话**：语义检索的代码底座已就位，唯独缺一个能出向量的供应商凭据；本文回答「用哪家、怎么绑多个、怎么给用户建议」三个问题，并说明为什么 embedding 绑多个和 chat 绑多个不是一回事。
**谁该读**：要接入向量模型的运维或工程；接手知识库语义检索续做的人。
**读完能做什么**：照着选一家供应商接上去，并避开「绑了多个模型反而检索不出东西」这个坑。

---

## 1. 为什么卡住

2026-08-10 调查本部署，事实如下：

| 已配置平台 | 有 key | 有 embedding 模型 |
|---|---|---|
| Stub 开发桩 | 否 | 有（本次新增的自测桩，非真实向量） |
| openrouter.ai | 是 | **无** |

OpenRouter 的模型列表共 399 个，**零个 embedding 模型**。它的 `/v1/embeddings` 探测返回与不存在路径同样的笼统 401，无法据此判断端点是否存在——但模型列表为空这件事本身已经决定了：走 OpenRouter 拿不到向量。

所以缺的不是代码，是一个新供应商 + key。凭据属于外部输入，工程侧造不出来。

---

## 2. 问题一：OpenAI 可以吗

**可以。** OpenAI 与 OpenRouter 是两家，不要混。实测（不带 key 探测，看的是「端点存不存在」而不是「能不能调通」）：

| 端点 | 返回 | 含义 |
|---|---|---|
| `POST api.openai.com/v1/chat/completions` | 401 需要 key | 端点存在（对照组） |
| `POST api.openai.com/v1/embeddings` | 401 需要 key | **端点存在** |
| `POST api.openai.com/v1/definitely-not-a-real-endpoint` | 404 | 不存在（对照组） |

真假路径返回不同，所以这个判据是有效的——不像 OpenRouter 那样真假都回同一个 401。

接入方式：后台加一个平台（baseUrl `https://api.openai.com`）+ key，再加一个 `modelType=embedding` 的模型（`text-embedding-3-small` 或 `-large`）。**不需要改代码**：现有的 OpenAI adapter 已经把 `embedding` 映射到 `/embeddings`。

---

## 3. 问题二：怎么绑定多个

系统本身支持：模型池（`ModelGroup`，`ModelType=embedding`）可以放多个条目，六种调度策略（FailFast / Race / Sequential / RoundRobin / WeightedRandom / LeastLatency），再把 AppCallerCode 绑到这个池。

**但 embedding 绑多个和 chat 绑多个不是一回事，这是本文最要紧的一句。**

chat 池里放不同模型是好事：A 挂了用 B，用户顶多觉得回答风格变了，看得见。
embedding 池里放**不同模型**是灾难：不同模型的向量空间互不相容，故障切换到 B 之后算出来的向量与库里 A 的向量根本不在一个空间。

所以规则是：

| 池里放什么 | 行不行 | 为什么 |
|---|---|---|
| 同一个模型名 × 多个平台（如 bge-m3 同时挂硅基流动和另一家） | **可以** | 同一份权重、同一个向量空间，这是正经的冗余与故障切换 |
| 不同模型名（如 bge-m3 + text-embedding-3-small） | **不要** | 两个向量空间。切换后查询向量与存量向量对不上 |

好消息是本次实现**已经是失效安全的**，不会静默出垃圾：每条向量都盖了 `Model + Dimension`，兼容性判据要求两者都相等（`EmbeddingVector.IsCompatible`）。真出现混池切换，查询向量匹配不到任何存量向量，结果是**检索返回空**而不是返回一堆看似合理实则无意义的结果。空结果是能被发现的，静默的错排序不能。

代价是：混池会让检索静默失效（返回空），运维会困惑「为什么什么都搜不到」。所以配置界面应当在建 embedding 池、且池内模型名不止一个时给出明确警告。**这条警告目前还没做**（见第 5 节遗留）。

换模型的正确姿势：换 = 存量向量全部作废重建。增量索引的哈希已经把模型标识拌了进去，所以换模型后所有块哈希都会变、自动触发重建，不会出现「以为增量没变化就一条都不重建」。

## 4. 问题三：怎么给用户建议

界面上不该让用户面对一个空的模型下拉框自己想。建议按「内容语言 + 预算」两档给默认推荐：

| 场景 | 建议 | 维度 | 大致成本 |
|---|---|---|---|
| 内容以中文为主（本系统的实际情况） | BAAI/bge-m3（硅基流动等国内 OpenAI 兼容平台） | 1024 | 常有免费额度，中文检索质量强于同价位英文模型 |
| 已有 OpenAI key、想省事 | `text-embedding-3-small` | 1536 | 约 $0.02 / 百万 token |
| 追求质量不在乎钱 | `text-embedding-3-large` | 3072 | 约 $0.13 / 百万 token，维度大三倍、存储与内存也大三倍 |
| 不想出网 / 数据不能外发 | 本地 TEI、Ollama、vLLM（都是 OpenAI 兼容） | 视模型 | 零 API 费用，要机器 |

本系统的量级参考：48 个知识库、1121 篇文档、正文合计约 8-10MB，首次全量建索引大约几百万 token。按 `text-embedding-3-small` 计**不到一块钱**，之后只对变化的文档增量重算。也就是说成本不是决策因素，**检索质量和数据出不出网才是**。

维度的隐含成本容易被忽略：3072 维比 1024 维的存储和进程内计算大三倍。按最大的 MAP 库（330 篇 4.24MB ≈ 5 千余块）估算，1024 维 float32 约 21MB、3072 维约 62MB。目前的方案是把作用域内的向量读进进程算余弦，所以维度直接影响一次检索的内存与耗时。

## 5. 遗留（拿到 key 后续做）

| 项 | 说明 |
|---|---|
| 建索引 Worker | 按内容哈希增量、Run/Worker 与 HTTP 解耦，长任务不随连接断开而取消 |
| 检索服务 | 作用域过滤 + 余弦 topK；作用域内块数超上限时要提示而不是硬扛 |
| 回答引用 | **两端都要加**：后端在 SSE 里新发一类 `reference` 事件，前端在 `useAskStream` 里加对应分支。一期的协议只有 `session / phase / model / typing / done / error`，没有为引用预留任何东西——原文曾写成「已预留、接上即可」，是错的 |
| 前端 | 站点挂知识库的配置、回答里的引用渲染与下钻 |
| 混池警告 | 建 embedding 池时若池内模型名不止一个，配置界面必须明确警告（见第 3 节） |
| 量化验收 | 自建临时库埋唯一暗号，量 recall@5、无答案时的拒答率、跨库隔离，跑完删库 |
| 调用方上下文 | `EmbedAsync` 目前在 `ResolveModelAsync` 之前没有打开请求上下文作用域。inproc 模式下解析租户会取不到而退到内部租户，多租户场景可能解析到别的租户的模型池。目前没有调用方，属未接线的潜在问题；接检索服务时必须把 resolve 与 send **一起**包进作用域 |
| 应答形状容错 | 上游返回合法 JSON 但根不是对象（数组 / 标量），或 `data` 里混入标量元素时，取 `data` 与 `embedding` 会抛 `InvalidOperationException`，逃出只 catch JSON 解析异常的那道网，变成未处理异常而不是一条 `UPSTREAM_ERROR`。与已修的 index / 分量校验同族，属两轮额度之后的新增项 |
| 余弦中间溢出 | 分量量级超过约 1e19 时，单精度乘法会先溢出成无穷再累加进双精度，余弦变 NaN。真实向量模型不会产出这种量级，判为推测性变体；若日后放宽分量校验，需同时把乘法提到双精度再累加 |
