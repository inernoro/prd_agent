# 向量模型供应商 · 债务台账

> **版本**：v1.0 | **日期**：2026-08-10 | **状态**：等外部输入

**一句话**：语义检索的代码底座已就位，唯独缺一个能出向量的供应商凭据；本文回答「用哪家、怎么绑多个、怎么给用户建议」三个问题，并说明为什么 embedding 绑多个和 chat 绑多个不是一回事。
**谁该读**：要接入向量模型的运维或工程；接手知识库语义检索续做的人。
**读完能做什么**：照着选一家供应商接上去，并避开「绑了多个模型反而检索不出东西」这个坑。

---

## 1. 为什么卡住

2026-08-10 调查本部署，事实如下：

| 已配置平台 | 有 key | 有 embedding 模型 |
|---|---|---|
| Stub 开发桩 | 否 | 有（本次新增的自测桩，非真实向量） |
| openrouter.ai | 是 | **无** |

OpenRouter 的模型列表共 399 个，**零个 embedding 模型**。它的 `/v1/embeddings` 探测返回与不存在路径同样的笼统 401，无法据此判断端点是否存在——但模型列表为空这件事本身已经决定了：走 OpenRouter 拿不到向量。

所以缺的不是代码，是一个新供应商 + key。凭据属于外部输入，工程侧造不出来。

---

## 2. 问题一：OpenAI 可以吗

**可以。** OpenAI 与 OpenRouter 是两家，不要混。实测（不带 key 探测，看的是「端点存不存在」而不是「能不能调通」）：

| 端点 | 返回 | 含义 |
|---|---|---|
| `POST api.openai.com/v1/chat/completions` | 401 需要 key | 端点存在（对照组） |
| `POST api.openai.com/v1/embeddings` | 401 需要 key | **端点存在** |
| `POST api.openai.com/v1/definitely-not-a-real-endpoint` | 404 | 不存在（对照组） |

真假路径返回不同，所以这个判据是有效的——不像 OpenRouter 那样真假都回同一个 401。

接入方式：后台加一个平台（baseUrl `https://api.openai.com`）+ key，再加一个 `modelType=embedding` 的模型（`text-embedding-3-small` 或 `-large`）。**不需要改代码**：现有的 OpenAI adapter 已经把 `embedding` 映射到 `/embeddings`。

---

## 3. 问题二：怎么绑定多个

系统本身支持：模型池（`ModelGroup`，`ModelType=embedding`）可以放多个条目，六种调度策略（FailFast / Race / Sequential / RoundRobin / WeightedRandom / LeastLatency），再把 AppCallerCode 绑到这个池。

**但 embedding 绑多个和 chat 绑多个不是一回事，这是本文最要紧的一句。**

chat 池里放不同模型是好事：A 挂了用 B，用户顶多觉得回答风格变了，看得见。
embedding 池里放**不同模型**是灾难：不同模型的向量空间互不相容，故障切换到 B 之后算出来的向量与库里 A 的向量根本不在一个空间。

所以规则是：

| 池里放什么 | 行不行 | 为什么 |
|---|---|---|
| 同一个模型名 × 多个平台（如 bge-m3 同时挂硅基流动和另一家） | **可以，但目前拿不到自动故障切换**（见下） | 同一份权重、同一个向量空间，配置上是安全的 |
| 不同模型名（如 bge-m3 + text-embedding-3-small） | **不要** | 两个向量空间。切换后查询向量与存量向量对不上 |

**「可以」只是说这么配不会污染向量库，不等于配了就有故障切换。** 现在实际拿不到，两道闸各挡一次：
向量调用为了防模型漂移必须钉住 `ExpectedModel`，而网关的候选重试在「指定了模型且不是逻辑模型」时直接返回单候选；
即便走到下一步，候选筛选也只留**模型名不同**的条目，同名多平台恰好被滤掉。
所以一个可重试的 429 / 5xx 会让整批失败，不会自动落到第二个平台。要真做出同名多平台冗余，
得让网关支持「保留候选但约束为同一模型名」——记在第 5 节遗留，不在向量底座这一版做。

好消息是本次实现**已经是失效安全的**，不会静默出垃圾：每条向量都盖了 `Model + Dimension`，兼容性判据要求两者都相等（`EmbeddingVector.IsCompatible`）。真出现混池切换，查询向量匹配不到任何存量向量，结果是**检索返回空**而不是返回一堆看似合理实则无意义的结果。空结果是能被发现的，静默的错排序不能。

代价是：混池会让检索静默失效（返回空），运维会困惑「为什么什么都搜不到」。所以配置界面应当在建 embedding 池、且池内模型名不止一个时给出明确警告。**这条警告目前还没做**（见第 5 节遗留）。

换模型的正确姿势：换 = 存量向量全部作废重建。增量索引的哈希已经把模型标识拌了进去，所以换模型后所有块哈希都会变、自动触发重建，不会出现「以为增量没变化就一条都不重建」。

## 4. 问题三：怎么给用户建议

界面上不该让用户面对一个空的模型下拉框自己想。建议按「内容语言 + 预算」两档给默认推荐：

| 场景 | 建议 | 维度 | 大致成本 |
|---|---|---|---|
| 内容以中文为主（本系统的实际情况） | BAAI/bge-m3（硅基流动等国内 OpenAI 兼容平台） | 1024 | 常有免费额度，中文检索质量强于同价位英文模型 |
| 已有 OpenAI key、想省事 | `text-embedding-3-small` | 1536 | 约 $0.02 / 百万 token |
| 追求质量不在乎钱 | `text-embedding-3-large` | 3072 | 约 $0.13 / 百万 token，维度大三倍、存储与内存也大三倍 |
| 不想出网 / 数据不能外发 | 本地 TEI、Ollama、vLLM（都是 OpenAI 兼容） | 视模型 | 零 API 费用，要机器 |

本系统的量级参考：48 个知识库、1121 篇文档、正文合计约 8-10MB，首次全量建索引大约几百万 token。按 `text-embedding-3-small` 计**不到一块钱**，之后只对变化的文档增量重算。也就是说成本不是决策因素，**检索质量和数据出不出网才是**。

维度的隐含成本容易被忽略：3072 维比 1024 维的存储和进程内计算大三倍。按最大的 MAP 库（330 篇 4.24MB ≈ 5 千余块）估算，1024 维 float32 约 21MB、3072 维约 62MB。目前的方案是把作用域内的向量读进进程算余弦，所以维度直接影响一次检索的内存与耗时。

| 项 | 说明 |

| 建索引 Worker（本分支已接线，待远端验收） | 对用户选定的单库按内容哈希增量；复用持久化 Run/Worker，断连不取消已提交工作 |

| 回答引用（本分支已接线，待点击验收） | 两端新增引用事件，服务端只输出已验证片段的原文摘录与阅读器链接；原协议没有预留引用，旧说法已更正 |
| 前端（本分支已接线，待预览验收） | 本人站内网页问答可按轮选择知识库、打开引用原文；不保存全站挂库配置，不向分享或团队访客开放 |
| 混池警告 | 建 embedding 池时若池内模型名不止一个，配置界面必须明确警告（见第 3 节） |
| 量化验收（仍未关闭） | 固定36题与临时Mongo桩模型链路验证已提供；真实模型四项指标、浏览器原文点击、更新删除撤权时效及验收知识库归档仍受环境访问阻塞 |
| 调用方上下文（本分支已修正并有本地回归） | 向量化解析与发送一起进入发起者作用域，并保留父上下文中的租户及团队。真实多租户运行仍需远端验收，不以本地桩模型证明线上配置正确 |
| ~~应答形状容错~~（已修） | 上游返回合法 JSON 但根不是对象（数组 / 标量），或 `data` 里混入标量元素时，取 `data` 与 `embedding` 会抛 `InvalidOperationException`，逃出只 catch JSON 解析异常的那道网。已改成先判 `JsonObject` 再取键，回归用例见 `EmbeddingResponseParseTests` 的「根不是对象」「data 里混进标量元素」两条。破例修它是因为它证伪的是本函数自己写在注释里的承诺（不兼容的应答只该变成 `UPSTREAM_ERROR`），属「声称做到但实测做不到」 |
| 同名多平台的故障切换 | 第 3 节表格里「同一模型 × 多平台」这一档，配置上安全但**目前拿不到自动切换**：向量调用钉住 `ExpectedModel` 会让网关的候选重试直接返回单候选，且候选筛选只留模型名不同的条目，同名多平台恰好被滤掉。要做得让网关支持「保留候选但约束为同一模型名」——那是网关侧的语义扩展，不在向量底座这一版 |
| ~~绑定的池被删后失败关闭失效~~（已修） | 「有没有专属绑定」原本看的是「按 id 查回来几个池」。绑定的池被删掉时查回 0 条，于是判成「没绑定」，失败关闭整条失效——绑定明明还在、池没了，解析却继续往默认池 / `expectedModel` 直连走，embedding 仍可能拿到 chat 模型。已抽成唯一判据 `ModelResolver.HasDedicatedBinding`（只看配置绑没绑），两条解析路径共用并加了共用守卫 |
| 专属绑定是「优先」不是「排他」 | 绑定的池 id 悬空（池被删）且存在默认 embedding 池时，解析会落到默认池——仍是 embedding 模型，但可能不是绑定本意的那个。判据本身声明的范围是「不许拿 chat 模型算向量」，这条已经关死；换成另一个 embedding 模型不是静默错误：向量盖了 `Model + Dimension`，`IsCompatible` 要求两者都相等，漂移的后果是**检索返回空**（看得见），不是错排序（看不见）。要升级成「有绑定就不许用默认池」是新语义，且会同时作用于 video-gen / asr，超出向量底座这一版的目标 |
| 悬空绑定不可见 | 绑定的池 id 查不到时解析静默换路，没有任何告警。配置错误本身该被看见，而不是靠下游行为间接暴露 |
| 余弦中间溢出 | 分量量级超过约 1e19 时，单精度乘法会先溢出成无穷再累加进双精度，余弦变 NaN。真实向量模型不会产出这种量级，判为推测性变体；若日后放宽分量校验，需同时把乘法提到双精度再累加 |

## 2026-11-12：知识库问答接线，效果验收仍未关闭

当前主干基线核实为“向量底座存在，索引与检索没有调用方”；网页问答只读取当前网页。基于此基线，独立分支将本人网页的“向我提问”接到单个自选知识库：索引、检索和原文选择共用持久化后台任务，模型调用继续走统一网关，索引与查询保持模型和维度一致。可读权限与阅读器共用判据，正文和权限在回答输出前复核；输出仅为服务端控制的原文摘录与条目链接。

本轮只对用户明确选择的库按需增量刷新，不启动全库扫描，不新增付费设施。容量限定为一百篇已解析文档、三千个切块、一百万字符；超过容量明确失败。下一次提问使用当前正文和权限，最长等待一百二十秒，未能完成就返回失败而非旧结果。此时限是失败关闭的服务边界，不是未经实测的性能保证。未解析正文不参与召回；尚无解析覆盖率提示。

**仍待验证**：固定三十六题已覆盖同义、跨文档、无答案和无权限，离线字面量基线与本地桩模型的工程测试均须与真实语义效果分开。当前执行环境的网络策略拒绝 MAP/CDS 域名，浏览器运行时亦无法启动，故本次不能核实线上模型目录或供应商凭据，也不能给出真实模型 recall@5、引用正确率、无依据作答率、检索延迟或预览用户路径通过结论。八月的供应商调查只代表当时状态，不能据此宣称当前仍缺 key。

**验收与剩余边界**：在可达的独立分支预览上，使用统一网关的真实 embedding 与 chat 模型跑固定评测，记录冷、热查询与全部失败分母，并人工复核摘录是否充分支持问题；正常登录后实际点击引用原文，验证更新、删除和撤权。未经这些验证不关闭 K-2。自动同名多平台故障切换、混池警告、超过当前容量的检索、跨库聚合以及自由生成的综合答案仍不在本轮闭环内。评测报告和真实路径证据待归档验收知识库，不能用本地测试替代。

补充边界：本轮未新增网页问答的断线恢复入口，断连后后台继续运行，但页面不会自动找回该次结果；索引物理残留的统一清理沿既有知识库删除与同步治理另行收口，查询可见性已由实时权限与原文复核隔离。
