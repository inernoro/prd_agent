# CDS 设置分组与数据分类 · 设计

> **版本**：v1.0 | **日期**：2026-09-02 | **状态**：已落地

**一句话**：系统设置与项目设置共用六组词表（常用、接入、运行、数据、观测、危险区），每组只回答用户一个问题；数据另分四类决定备份与清理规则。
**谁该读**：要往设置页加页签的工程师；想知道某个设置「该去哪找」的用户；给数据定备份与清理策略的人。
**读完能做什么**：给一个新页签三秒内定组；分清一份数据丢了能不能重建、要不要备份、随不随分支删。

---

## 一、为什么要分类

2026-09-02 之前，项目设置只有「接入 / 运行时 / 危险区」三组，11 个页签全塞在「运行时」里：环境变量、周期备份、统计、活动日志、缓存诊断挨在一起。用户要找「多分支共不共用数据库」这种设置时，没有一个一眼能落的位置——这正是本次「数据库隔离」页签落地时暴露的问题：它以前只能在分支抽屉里当「覆盖项」看到，项目默认藏在没人打开的 profile 里，层级倒置。

系统设置那边的组名（常用 / 接入 / 运行时）与项目设置各写各的，「运行时」在两页里装的东西也不一样。用户原话：「当前 cds 项目的分类有点问题，有没有可以借鉴的」。

## 二、借鉴了什么

看了三家的项目级设置：

| 产品 | 分组 | 共同点 |
|---|---|---|
| GitHub 仓库设置 | General / Access / Code and automation / Security / Integrations / Danger zone | 按「用户来这里要回答的问题」分，不按实现模块分；危险区永远单独垫底 |
| Vercel 项目设置 | General / Domains / Git / Environment Variables / Data Cache / Security / Advanced | 「数据」单独成组；环境变量归「运行」而不是「数据」 |
| Railway 项目设置 | General / Environment / Deploy / Networking / Danger | 组少而稳，新功能落进既有组，不新开组 |

抽出的三条原则：

1. **按问题分组，不按模块分组。** 用户脑子里是「它怎么跑」「它的数据在哪」，不是「这是 compose 模块的」。
2. **两页共用一套词表。** 系统设置与项目设置的组名、顺序完全一致，在哪一页都能凭直觉找。
3. **危险区永远单独垫底，常用只做快捷。** 危险操作不与任何常规设置同组；「常用」是入口不是分类，只允许系统设置有（项目页签少，直接按问题找）。

## 三、设置分组（六组）

| 组 | 回答的问题 | 项目设置里放什么 | 系统设置里放什么 |
|---|---|---|---|
| 常用 | 我今天最可能来点什么 | 不设 | CDS 更新、自更新历史、概览 |
| 接入 | 这是谁、从哪来、谁能进 | 基础信息、GitHub、评论模板 | 登录与认证、用户管理、AI Access Key、权限总览、GitHub 集成、GitHub 白名单、外部接入 |
| 运行 | 它怎么跑起来 | 项目配置、项目环境变量、新分支默认、交付模式 | 调度器、集群、远程主机、CDS 全局变量、加载页预览 |
| 数据 | 它的数据放哪、分不分、备不备、搬不搬 | **数据库隔离**、基础设施、存储、周期备份、迁移、缓存诊断 | 存储后端、配置快照 |
| 观测 | 它跑得怎么样 | 统计、活动日志 | 用户痕迹、Webhook 日志、Docker 网络容量 |
| 危险区 | 删了就回不来的操作 | 删除项目 | 危险操作 |

词表是代码里的唯一定义：两页的分组标签类型就是这个词表，写词表外的组名编译不过；组的先后顺序、每组非空、页签不重复登记、「常用」只出现在系统设置，由一条守卫测试盯着（位置见文末「实现来源」）。

### 落组判据（新页签三秒定组）

先问「用户来这个页签是要回答哪个问题」，答案落在上表第二列的哪一行就归哪一组。答不上来，说明页签本身没想清楚，先别加。两条易错：

- 环境变量是「怎么跑」，归运行，不归数据（它是配置，不是数据本身）。
- 缓存诊断管的是包缓存挂载这类盘上的东西，归数据；它的名字里有「诊断」，但用户来这里是修盘不是看图。

## 四、数据分类（四类）

设置分组回答「去哪找」，数据分类回答「怎么处置」。两者正交：「数据」组里的每个页签都应能说出自己管的是哪一类数据。

| 类别 | 丢了能否重建 | 周期备份管不管 | 随分支删除清理 | 例子 |
|---|---|---|---|---|
| 配置 | 能 | 管（配置快照） | 否 | BuildProfile、项目环境变量、虚拟 compose |
| 业务数据 | 不能 | 管 | 否 | Mongo / MySQL / Postgres 里的库（共享库或分支独立库） |
| 运行态 | 能 | 不管 | 是 | 容器、包缓存挂载、构建产物、worktree |
| 审计证据 | 不能 | 管 | 否 | 活动日志、Webhook 投递记录、验收报告、发布记录 |

混着管会出的事：备份把可丢弃的缓存也备了，却漏了唯一一份业务库；删分支把审计证据一起清了。数据库隔离页签管的是「业务数据」的**归属**（哪条分支用哪个库），不改变它的处置规则——分支独立库仍是业务数据，仍不随分支删除自动 drop（见 [债务台账](./debt.cds.branch-isolation.md) DBI 行）。

## 五、数据库隔离页签（本次落地的实例）

- **位置**：项目设置 → 数据 → 数据库隔离（`/settings/:projectId#db-isolation`）。
- **数据源不变**：仍只有 `BuildProfile.dbScope` 一份；分支覆盖仍在 `profileOverrides[pid].dbScope`。
- **读**：`GET /api/projects/:id/db-isolation` 给每个服务的生效档位、来源（显式 / 默认）、会被改写的库名变量、分支覆盖概况；托管交付项目标只读。
- **写**：`PUT /api/projects/:id/db-isolation`，`all` 批量或 `services` 逐服务，先全量校验再一次落盘，任何一项不合法整批拒绝；写前自动拍配置快照可回滚。
- **预期管理**：第一屏先给结论（几个共享、几个独立、几条分支有覆盖）；保存前写明「影响所有继承项目配置的分支，重新部署后生效；已有分支覆盖保持不变」，回包给出受影响分支数与保持不变的覆盖数。
- **分支侧**：抽屉保留高级覆盖，但徽标明示「项目默认 / 本分支覆盖」，有覆盖时给「恢复继承」，并把用户指回项目设置的新页签。

## 六、取舍与风险

| 取舍 | 理由 |
|---|---|
| 不新开「安全」组 | 现有页签里没有独立的安全面（密钥归接入、快照归数据）；组少而稳，需要时再开 |
| 「常用」只允许系统设置有 | 项目设置 16 个页签按问题直接可达；快捷组会让同一页签出现两次，违反「一处登记」 |
| 缓存诊断归数据而不是观测 | 它的动作是修复与迁移盘上的缓存，不是看图 |
| 数据库隔离改默认不自动重部署 | 切库是重操作，重部署时机交给用户；页面与回包都写明生效条件 |

风险：老用户按旧位置找页签会落空。缓解：页签 hash 深链全部不变（`#backup` 等照旧可达），命令面板搜索索引同步登记了新页签。
