# 头像沉浸式编辑器 · 设计

> **版本**：v1.0 | **日期**：2026-08-14 | **状态**：已落地

**一句话**：点击本人头像直接打开沉浸式编辑器，支持直传或 AI 生成两条路径，AI 预览必须经用户确认才落地，生成过程走后台任务而非同步请求。
**谁该读**：接手头像编辑/生成功能的工程师；排查「头像没换成功」「AI 头像卡住」一类问题的人。
**读完能做什么**：说清头像编辑器为什么这样设计、AI 生成为什么必须异步、以及对象键为什么带内容哈希。

---

## 一、管理摘要

- **解决什么问题**：原有头像更换只有「本地文件直传」一条路径，且缺少预览确认步骤；AI 生成头像若走同步请求，模型耗时经常超过前端请求超时，用户体验为「点了没反应」。
- **方案概述**：点击本人头像打开一个沉浸式编辑器：可直传图片（选好即生效），也可用文字描述让模型生成预览（需用户确认后才应用）；AI 路径的生成过程改造成后台任务，前端订阅进度而不是同步等待。
- **业务价值**：头像更换从「一次性、易失败的同步操作」变成「可预览、可重试、浏览器断开也不丢」的稳定流程。
- **影响范围**：prd-api 头像生成任务与查询、账户设置页、管理员头像管理入口。
- **预计风险**：低——头像是独立资源，失败不影响其他业务链路。

## 二、为什么要做成后台任务

AI 生成头像本质是一次生图请求，耗时通常几秒到几十秒，波动区间比普通文本生成更大。同步接口一旦超过反向代理或前端的超时窗口，用户看到的是一次「请求失败」，但模型可能仍在后台把图生成好——用户既不知道有没有成功，也无法找回结果。

改成任务化后：

1. 创建请求立即返回任务号，前端不再阻塞等待。
2. 任务在服务端持续推进，浏览器关闭或断网不取消任务，也不会把已经花掉的生成额度白白浪费。
3. 前端按任务号轮询/订阅可读的服务端状态（排队中、生成中、完成、失败、取消）；「预览待确认」「已应用」是前端在完成态之上叠加的本地展示阶段，不是服务端状态。任务号只存在当前浏览器会话里，同一会话内刷新页面能恢复进度；关闭浏览器后台任务仍会跑完，但需要重新打开编辑器发起新一次生成才能看到结果，暂不支持跨会话找回。

这与本仓库 Run/Worker 的通用模式一致：创建请求与执行解耦，执行结果通过状态查询而非请求响应本身传递。

## 三、AI 预览必须经确认才落地（产品决策）

AI 路径的产出是「预览图」，不是「新头像」。系统不会在生成完成后自动替换用户头像，而是把预览摆出来，用户看过之后主动点「确认替换」才真正写入。

这条决策是刻意的，理由有二：

- **生成结果不总是符合预期**：文字描述到图像存在语义偏差，直接落地相当于替用户做了一次不可逆决定。
- **保留重试空间**：不满意可以直接改描述再生成一版，不需要先撤销一次已生效的头像。

直传路径不走这个确认步骤：选好本地文件即直接上传并生效，没有预览环节。这是有意的不对称——直传的结果就是文件本身，用户选择的那一刻已经确认过；AI 路径多一步是因为「文字描述最终生成什么」在提交前无法预知，需要留一个把关点。

## 四、对象键：从「文件名」到「用户 + 内容哈希」（仅本人自服务路径）

这一点只适用于用户编辑**自己**头像的两条路径（直传与 AI 生成）：头像文件存放对象存储时，对象键（决定 CDN 缓存与访问地址的那部分）不是简单地用「用户 ID」拼出来的，而是加入了内容哈希（对图片内容本身算出的指纹）。

不这样做会踩一个常见的 CDN 缓存坑：如果对象键只由用户 ID 决定，同一个用户每次换头像都是覆盖同一个地址，CDN 边缘节点在缓存过期之前会继续把旧图返回给部分访问者，出现「后台明明换好了，别人看到的还是老头像」的不一致。对象键带上内容哈希后，头像内容一变，地址跟着变，天然绕开了这个缓存陈旧问题；旧对象则由后台清理任务负责回收，不会无限堆积。

同样出于这个原因，AI 路径的创建任务、确认应用、失败重试这几步都设计成幂等的：同一次操作被重复触发（比如网络抖动导致前端重试）时，不会诞生两个并发的生成任务，也不会把已经在处理中的旧对象提前删除。

**管理员为他人上传头像是另一条更简单的路径**：对象键固定为 `{用户名}.{扩展名}`，不带内容哈希，覆盖写。它没有 AI 生成选项、也没有预览确认步骤，行为等同于普通直传。这条路径同样存在上面说的 CDN 缓存坑，目前尚未收敛到内容哈希方案，见 [debt.prd-agent.md](./debt.prd-agent.md) 已知边界。

## 五、数据流

两条路径在「是否需要确认」这一步分叉，之后重新汇合到同一套落地逻辑：

```
点击本人头像 → 打开沉浸式编辑器（直传 或 描述生成两个入口）

直传路径：
  本地选图 → 直接上传并写入新对象键 → 头像更新对全站生效（无预览确认步骤）

描述生成（AI）路径：
  提交描述 → 创建后台任务 → 轮询任务阶段 → 生成完成得到预览
  → 用户主动点「确认替换」
     → 校验预览图片确实归属本人（防止越权把别人的生成产物设成自己头像）
     → 写入新对象键（用户 + 内容哈希）→ 更新头像地址
     → 立即尝试删除旧对象，删除失败则记录清理意图交由后台任务按退避间隔重试
  → 头像更新对全站生效
```

管理员为他人替换头像**不**走上面这条落地逻辑：编辑弹窗对管理员隐藏 AI 生成选项，只保留直传，落地方式见「四、对象键」一节末尾的固定文件名路径。

## 六、与其他模块的关系

头像生成复用视觉创作既有的生图能力与模型池，不单独维护一套生图协议；生图侧的模型池故障隔离、健康恢复行为遵循 [design.platform.llm-gateway.md](./design.platform.llm-gateway.md) 的统一规则。头像任务的部署隔离、幂等重试与旧任务回收，遵循与其他后台生成任务（如视觉创作生图任务）一致的作用域隔离原则——同一集合下的任务按当前部署身份认领，避免旧构建或另一分支预览的 Worker 抢占正在跑的头像生成任务。
