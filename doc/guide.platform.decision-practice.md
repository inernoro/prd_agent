# 从真实变更到决策记忆：产品试点与跨项目实操 · 指南

> **版本**：v1.0 | **日期**：2026-11-08 | **状态**：已落地

**一句话**：用一条真实业务变化连通用户任务、承重约定、选择理由、现行规则和验证，并让未参与讨论的人检查这些材料是否可用。
**谁该读**：要接手复杂业务、减少规则误解，或把 ADR/PDR 方法带到另一个项目的产品、业务、工程和测试人员。
**读完能做什么**：完成一次有证据的决策回放，识别何时值得新建记录，准备独立接手验证，并在其他项目按自己的约定使用这套方法。

独立读者效果与跨团队采用仍待实际观察。本文提供已整理的操作方法，不以指南成文证明采用收益。

## 一、先准备一个能完成任务的入口

选择一条已发生、仍会影响维护的变化，或一项确实待决定的新需求。写下用户要完成的任务、变化前后、证据来源与未知项。历史回放帮助找出缺口，新的重要选择才检验决策过程；二者分开记录。

材料只需要五种职责，优先补已有文档：

| 职责 | 最少留下什么 | 本项目首个试点入口 |
| --- | --- | --- |
| 产品结构 | 服务谁、核心对象、权责、依赖和承重承诺 | [一页结构](./design.product-agent.md#首个试点的一页产品结构) |
| 现行规则 | 术语、条件、状态、例外和适用对象 | [正式申领规格](./spec.product-agent.version-claims.md) |
| 决策记忆 | 真实选择、理由、代价、决定依据和重议条件 | [申领变化的补录与下一项问题卡](./pdr.product-agent.002.version-claim-boundary.md) |
| 可验证实例 | 正常、拒绝、边界、历史兼容和失败恢复的预期 | [场景及证据层次](./spec.product-agent.version-claims.md#三验收实例) |
| 未完成边界 | 影响、处理触发、责任角色和关闭条件 | [产品治理清单](./debt.product-agent.md#产品结构与决策治理2026-11-06) |

上述入口共同回答“现在怎样、为什么、对谁有效、怎么证明”。它们不必各占一个新文件。原理及八条核心原则见 [ADR 原则](./guide.doc.pri.adr.md#3-八条核心原则)；产品扩展见 [PDR 原则](./guide.doc.pri.pdr.md)。

## 二、沿一条变更做六步

1. **说清任务和事实。** 谁在什么情境遇到什么问题，原行为与期望有何差异；区分实际观察、实现事实与推测。没有用户损失证据就标明未知。
2. **找到承重约定。** 核对对象定义、生命周期、归属、权责、编号、历史承诺与外部消费者。画出改一处会牵动谁；普通展示调整不自动升级为重要决策。
3. **比较真实方案。** 包含适用时保留现状，写清收益、代价和足以选择的证据。改变重要取舍时使用 ADR/PDR；既定边界内的修复直接更新规格与测试。
4. **明确决定和适用。** 由有权角色作出选择，保留真实依据；新申请、在途、已完成、导入对象分别说明，写明承诺节点、例外优先级和恢复方式。
5. **验证行为及交付。** 用正常、异常、边界和存量实例核对实现；再核对目标环境与用户路径。接受决定、实现完成、实际可用和价值成立分别提供证据。
6. **让后来者回放。** 先不口头解释，让读者找依据并作判断。找不到就修入口，理解错就修术语或规则；只有新证据改变重要选择时才提出替代记录。

变更说明可以只增加一句：“决策依据：沿用 / 新增 / 取代 / 不涉及；记录与适用范围：……”。不要强制每次提交新建 PDR，也不要在价值尚未验证时先开发决策平台、规则引擎或自动审批。

## 三、两种业务语境的真实回放

### 案例 A：正式版本申领

任务是取得可靠编号，并让接手者查明来源与范围。历史变化允许常规 V 从有效 T 继承资料，功能和公告可后补；源记录保护、防重和权限继续成立。现状、历史证据与未知理由分别保存在[规格](./spec.product-agent.version-claims.md)和 [PDR](./pdr.product-agent.002.version-claim-boundary.md)。

| 条件或变化 | 应能解释的结果 | 触及的承重约定 |
| --- | --- | --- |
| 有有效 T，基础资料合格，公告为空 | 常规申领允许发号；不能由此推定部署已可用 | 发号资格与交付证据的区别 |
| 同一 T 重复申请或已占用编号被软删除 | 不能把重试或删除作为回收编号的依据 | 来源唯一性、历史与防重 |
| 后补公告或原 T 与新粘贴资料不同 | 保留编号和原发号时间；原 T 不被静默改写 | 原始资料与后补资料的边界 |
| 拟把公告改成发号门槛 | 先找真实需要，再说明新申请、在途和存量各如何适用 | 产品重要选择，需要新的 PDR，而非仅改表单必填 |

对“登记完成与实际交付”的下一项选择，已有[问题卡](./pdr.product-agent.002.version-claim-boundary.md#下一次变更问题卡登记完成与交付证据)。没有足够影响证据时保留现状；不为演示决策方法而制造需求。

### 案例 B：独立状态页与监控心跳

第二个语境来自独立仓库 [cds-independent-status](https://github.com/inernoro/cds-independent-status/tree/8ccf15a55e06f7f119471c8120c6197ee360a382)。它帮助接收通知的人判断当前知道什么、该去哪里处理；公开内容还必须保护内部指标、地址与凭据。

[2026-10-14 的实际变化](https://github.com/inernoro/cds-independent-status/commit/3504fba6fcd3f4e6bf913caec0b1dae9fc9cd505)加入独立心跳哨兵及持久化通知去重。这里按源码和测试回放其行为与取舍，没有为外部项目补造原始审批、会议讨论或 PDR 接受记录，也没有修改或发布该项目。

| 条件或变化 | 当前行为与可确认的边界 | 需要留给后来者的理由或问题 |
| --- | --- | --- |
| 主业务异常，但外部监控的心跳仍新鲜 | 不重复制造“监控本身失联”的告警 | 被观察的业务与观察者是两个对象 |
| 心跳年龄恰为 180 秒 / 超过 180 秒 | 前者仍新鲜，后者过期；读取失败需要跨两轮复核 | 时间边界与读取不确定性不能靠“看起来正常”解释 |
| 心跳重新出现 | 同时满足至少三次正常检查和持续至少十分钟才确认稳定恢复；中间失联或长调度间隔会打断观察 | 一次成功不能抹掉尚未确认恢复的事件 |
| 重启或发送结果不确定 | 已保存的发送意图及回执限制重复发送；不确定结果不会自动重发 | 去重不能证明对方收到；避免重复与可能漏达存在取舍 |
| 页面保留旧的成功结果 | 过期检查结果显示当前未知，不能沿用旧成功声称当前正常 | “未知”“异常”“已确认恢复”是不同承诺 |

若未来要求“不确定发送也自动重试”，需比较重复通知、外部幂等能力与漏达风险，确认角色和历史回执如何处理；它值得一份产品决定。持久化方式、并发与恢复机制可再关联架构决定。

[哨兵测试](https://github.com/inernoro/cds-independent-status/blob/8ccf15a55e06f7f119471c8120c6197ee360a382/watchdog/test-independent-watchdog.py)及[页面受控场景](https://github.com/inernoro/cds-independent-status/blob/8ccf15a55e06f7f119471c8120c6197ee360a382/watchdog/test-independent-status.mjs)可检查这些规则。它们使用模拟输入，不证明线上调度持续正常、通知实际到达或接收者理解正确。

两个案例共享的方法是：从用户任务出发，辨认对象与承诺，保留重要取舍，再用反例检查。它们不共享状态名、时间阈值、数据模型或业务决定。完成回放仅说明方法可以描述两种实际业务，不能声称第二个团队已采用或效果已经提升。

## 四、让未参与讨论的人独立回放

主持者先固定资料版本、受试者角色、任务和本次场景；只给本指南及其中入口。开始前记下以往同类任务如何找依据；没有可比记录就先建立基线，不宣称改进百分比。

请未参与材料制作的人独立回答，要求每项附上找到的依据与适用范围。作者自己的检查或 AI 自动检索只能作为预检，不能填作独立读者结果。

| 任务 | 观察什么 |
| --- | --- |
| 产品 A 的有效 T 申领 V，公告为空。能否发号？能否声称客户已可用？ | 是否能区分发号规则与交付证据，并找到当前依据 |
| 现要把公告设为必填。既有 V、在途申请和原 T 各怎么办？ | 是否先识别未裁决问题及受影响对象，而非擅自追认或补造历史 |
| 排期引用另一个产品的版本，被拒绝后原需求应怎样？ | 是否能找出归属边界、拒绝后的预期，以及验证覆盖 |
| 监控有新鲜心跳，但主业务异常；后来页面的成功结果过期。各应怎样解释？ | 是否分别识别监控、业务与证据新鲜度，承认未知 |
| 心跳第一次恢复，或通知只有不确定发送回执。能否报告稳定恢复、实际送达？ | 是否能找到确认条件，避免把中间信号当最终结果 |
| 接到“同类通知重复了”的反馈，下一步如何做？ | 是否先核对事实、事件身份及现有约定，再判断修复还是新取舍 |

主持者用案例对应规格、PDR 与固定版本源码核对答案。记录：资料版本、角色、开始/结束时间、结论、引用、错误、追问、是否需要作者救场；不要收集无关个人信息。

完成条件是读者能独立定位有效规则，正确解释正常、拒绝、边界及历史对象，识别未知和待决定项。若需要作者补充关键口径，本次不算通过；先修材料，再用未见过的同类问题复查，避免靠背答案取得通过。

独立理解通过后，还需在下一条真实变更中观察是否少返工、少重复解释，以及新增记录和审查的成本。没有这样的观察，保留“采用效果待验证”，不以文档数量或测试数量代替。

## 五、带到另一个项目的最小方法

可以复制本节与第二、四节作为起步说明。先读目标项目已有约定，五种职责可用现有文件、Wiki 或其他共享载体承接；不用照搬本仓库的前缀、目录、角色或编号。八条原则保留其精神：一个重要选择、理由、明确决定、代价、所有者、审查、历史与工作过程中的引用。

用下面五个问题开启一条真实变更，答案足够简短即可：

- **任务与事实**：谁在什么情境遇到什么问题？已知、推测和未知分别是什么？
- **承重与影响**：核心对象、状态和承诺是什么？改变后影响谁、哪些存量及外部消费者？
- **选择与依据**：候选方案、收益和代价是什么？由谁基于什么作出选择？何时重议？
- **适用与验证**：对哪些对象、版本、时间和例外生效？用什么正常、拒绝、边界与历史实例验证？
- **当前与历史**：当前有效规则在哪？旧选择如何保留、取代和追溯？谁检查实际结果？

先补一条案例，再试一次独立回放；有效才扩到第二个领域。只迁移写法仍是材料迁移，目标项目至少走过一次真实选择、实施与复查后，才可以记录为采用。尚未获得业务选择或独立读者输入时，明确负责人、所需输入与完成条件，继续可独立完成的工作，不制造批准或效果。
