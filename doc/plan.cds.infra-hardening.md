## 为什么分三步，而不是一次做完

两件事被混在一起谈过，但风险差得远：

- **端口敞着**是网络层。现在靠宿主防火墙挡着，**防火墙规则一重启就丢**，丢了立刻恢复暴露。收窄绑定不碰任何口令，回滚就是改回去。
- **没有口令**是认证层。加口令的难点从来不在设口令，在于**所有连接方要同步换**，漏一个那个应用当场连不上。

所以先做网络层：它直接消掉敞口，代价只有几十秒重建，且不牵连任何应用配置。认证层挑从容的时间窗慢慢来。

## S1：摸清消费方（只读，零风险）

对每个库回答三件事：

1. 谁在连它（哪些项目、哪些容器）
2. 从哪连（走 docker 内网用容器名，还是从宿主外面用 `IP:端口`）
3. 连接串存在哪（项目环境变量的哪个键）

第二条是 S2 的判据：**只走内网的库，收窄绑定不影响任何人**；有外部直连的，收窄之前必须先安置那个消费方。第三条是 S3 的清单：换口令时这些键一个都不能漏。

同一台机器上另有 12 个 infra 服务**不在敞口清单里**——它们的绑定已经是窄的。这说明窄绑定在这台机器上是既成事实，不是没验证过的新配置。

### 消费方怎么连（这是 S2 的判据）

CDS 自己的四条访问路径，逐条查过源码：

| 谁 | 怎么连 | 收窄绑定会不会断 |
|---|---|---|
| 数据工作台（查询 / 建表 / 初始化 SQL） | `docker exec` 进容器内部连 localhost | 不会 |
| 备份与恢复 | `docker exec` + `docker cp` | 不会 |
| 就绪探测 | 走宿主 `127.0.0.1:<端口>` | 不会（回环仍在绑定里） |
| 应用容器 | 连接串指向 `${CDS_HOST}`，也就是 **docker 网桥地址** | 不会（网桥仍在绑定里） |

所以「窄」的定义不是只绑回环——那会把应用容器全打死，它们够不到宿主的 loopback。正确的绑定是**网桥地址 + 127.0.0.1** 两个，两个都不是对外地址。

**查不到的那一类**：从这台机器**之外**直连这些端口的消费方（某人的数据库客户端、外部系统）。CDS 的账本里不会有这种连接，只能在宿主上看实时连接才能确认。这是 S2 唯一的未知数。

### 关键发现：机制早就有了

收窄绑定不需要新写代码。CDS 已经有一份统一判定，默认就把 infra 端口绑到「网桥 + 回环」，并留了逃生阀可以改回全网卡。这 8 个之所以还敞着，只是因为它们是那份判定落地**之前**创建的容器，绑定参数在创建时就定死了。

所以 S2 的动作就是**重启这 8 个容器**——重启走的是先删后建，新容器自然套用新绑定。不改任何配置、不改任何口令。

## S2：收窄端口绑定

前提：S1 清单显示该库**没有外部直连**，或外部直连方已另行安置。

一次只动一个库：重建容器让端口只绑到网桥与回环，然后对照清单确认每个消费方仍连得上。做完一个再做下一个，不批量。

代价是每个库几秒到几十秒不可达。回滚：改回原绑定重建。

## S3：加认证（E17）

顺序不能乱，否则会把自己锁在门外：

```
查清消费方 → 库里加口令 → 立刻改 CDS 里的连接串变量
  → 重新部署每个消费方 → 逐个验证连得上 → 反向验证旧口令确实失效
```

最后一步不能省。已核对过的步骤与四条通则在 [guide.cds.infra-credential-rotation.md](./guide.cds.infra-credential-rotation.md)，其中写明了一个真栽过的坑：PostgreSQL 在容器内走本地 socket 是 trust 模式，**拿错口令也会显示成功**，所以验证必须走消费方真正用的那条路。

**前置条件已清**：加口令之后备份程序得能拿到口令，否则备份会从一种红换成另一种红。CDS 现在会从自己的服务定义里取口令并经 stdin 送进容器（E34 已修，PR #1386），这条通了。
