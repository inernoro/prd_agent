# 计划文档原则：把已知目标变成可推进的行动 · 指南

> **版本**：v1.1 | **日期**：2026-11-09 | **状态**：已落地

**一句话**：把目标拆成有负责人、依赖、完成条件和先后顺序的行动，让团队知道下一步做什么以及何时需要调整。
**谁该读**：组织迭代、安排协作、推进迁移和负责交付的产品与工程人员。
**读完能做什么**：制定可检查的实施次序，识别阻塞，并将执行进度与长期设计分开维护。

## 作用与使用时机

`plan.*.md` 回答“谁按什么顺序推进”。多阶段交付、迁移、跨团队协作与需安排资源的工作适用。

## 最少写什么

目标和边界、阶段成果、责任角色或已指定人员、依赖、完成判据、关键风险与调整条件。日期未知就说明依赖条件，不编造承诺。

## 如何维护

执行中更新进度与阻塞；完成时说明实际结果并引用最终规格、设计和证据。长期事实归回权威文档，不能让已完成计划继续充当现行设计。

## 与其他前缀的边界

“为什么选这条路”去 [ADR](./guide.doc.pri.adr.md) 或 [PDR](./guide.doc.pri.pdr.md)；尚未安排的长期欠账进[债务](./guide.doc.pri.debt.md)。计划不是提交列表，也不把未经决定的方向写成已批准任务。

项目入口示例：[网关全量切换计划](./plan.platform.llm-gateway.full-cutover.md)。检验标准是接手者能否识别下一步、负责人和完成条件。
