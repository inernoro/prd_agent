# 一仓多项目与身份层的工程债务

**一句话**：身份层已经能用，但一仓多项目的招牌能力还只是地基——一个仓库现在绑不了第二个项目，所以分发永远只会命中一个。
**谁该读**：接手 CDS 分发与凭据这块的人，以及要判断「这个能力现在能不能用」的人。
**读完能做什么**：知道哪几件事声称做完但其实达不到，各自缺什么、动它要付什么代价。

版本：2026-09-02 | 关联：[plan.cds.multi-project-identity.md](plan.cds.multi-project-identity.md)

## 一、一个仓库绑不了第二个项目（已解决，2026-09-02）

**状态**：closed。

翻掉了「一个仓库只能绑一个项目」这条不变量：绑第二个项目需要一次显式确认（link 接口的 `allowShared`、建项目的 `allowSharedRepo`），不带确认仍然拦住——因为绝大多数「已被绑定」都是填错了仓库地址，静默放行等于把误操作变成两个项目抢同一条 push。

同批把捆绑的另一半做了：删分支 / 关 PR / 极速版镜像完成三条此前仍按「找一个」取项目，不变量一翻就会造出没有信号的故障（分支永久停在等待中、容器留着没人收、预览一直开着）。三条各有一条红绿闭环用例——改回只取第一个项目，对应用例变红。

留下的边界见下面第六到第十条。

## 二、作用域只有一类，声明错了会静默跳过部署

**状态**：open。**影响**：潜在，今天不触发。

项目作用域取自各服务声明的构建输入范围。但一个服务真正依赖的东西不止镜像构建输入——还有部署期、运行期读的脚本与配置。谁声明了一份漏掉这些的作用域，改到它们的推送就会被判成「未波及」，分支不刷新、预览悄悄停在旧行为上，而且没有任何信号。

今天不触发：线上项目一个都没声明作用域，作用域为空即全通配。

**修法方向**：把「部署 / 运行期输入」与「镜像构建过滤」分成两类，而不是共用一份。这是新增一个语义类别，需要单独决定。

## 三、撤销单个项目授权没有界面入口

**状态**：open。**影响**：能力在，路径不顺手。

服务端有撤销接口、有判据、有测试，但权限总览里授权只是被动展示，没有任何前端调用它。要撤掉某个主体对某个项目的访问而不停用它整个人，只能手写请求。

## 四、存量凭据无法归属到主体

**状态**：open。**影响**：存量凭据享受不到自愈。

身份层之前签发的项目级凭据没有归属主体，因此不享受「换机器自助补发」。也没有「把一张旧凭据归给某个主体」的管理入口——只能由该主体自己补一张新的、再吊销旧的。

顺带澄清一个曾经写错的说法：这类凭据**不会**在「下次使用时自动认领」，光看一把凭据被使用，认不出背后是谁。界面文案已订正。

## 五、只授权不操作是留痕，不是拦截

**状态**：已知设计取舍，不打算改。

用户级凭证本身到不了运维面，但它能为已授权的项目自助签出项目级凭据，再拿那把去操作。所以这条边界的价值是**强制审计链 + 单一吊销开关**，不是权限隔离。把它读成「拿到用户级凭证也动不了东西」会高估它。

## 六、范围推断只做建议，不自动生效

**状态**：已知设计取舍。**影响**：还是要点一下，不是零操作。

系统能从各服务的启动命令看出本项目待在哪个目录（`cd cds` → `cds/**`），界面据此直接
给建议 + 一键采纳，用户不必从空白框开始。但推断值**不会自动顶替**分发判据。

理由是失败方向不对称：判据读的是已声明的范围，空 = 全通配 = 兜底全建，猜错顶多多建
一次；让推断悄悄生效，猜窄了就会把某个项目的推送判成「未波及」而静默跳过部署，分支
停在旧行为上且没有任何信号。所以宁可多要那一下点击。

另外，只要有**任何一个**服务连线索都没有（命令里没有 `cd`、workDir 是仓库根），整个
项目就不出建议——按已知的几个收窄，会把那个未知服务需要的路径挡在外面。

## 七、声明在部署模式上的范围，界面上改不了

**状态**：已知设计取舍。**影响**：这类服务只能去改 compose。

范围可以声明在两处：构建配置顶层，或某个部署模式下。判定分发时取两者并集，但**写回**
只能写对应那一处。范围对话框写的是顶层字段，所以对「声明在部署模式上」的服务，清空
清不掉模式那份、改窄反而并集变宽——提示还会报成功。本仓库线上五个服务全是这一类
（compose 的 `cds.build-scope` 标签带上来的），所以这不是边缘情况。

现在的处理是**如实只读**：接口标出声明在哪儿，这类服务渲染成只读卡片并写明「要改就去
改这个服务在 compose 里的 `cds.build-scope` 标签后重新导入」，保存时跳过。

同一个服务在顶层**和**部署模式上都声明过时，两份都会渲染出来（2026-09-02 补）——判定
取的是并集，只显示模式那一半，顶层那些路径就成了看不见却照样生效的声明。看得见了，
但仍然改不了：删掉顶层那半需要的正是本条说的「写回声明源」能力。

**为什么不做「写回声明源」**：那等于从这个对话框反向改用户写在 compose 里的东西，而
重新导入 compose 会再覆盖回去——两边谁赢取决于操作顺序，风险比它解决的问题大。真要
做，得先决定 compose 与 CDS 配置树在这个字段上谁是权威，那是一件独立的事。

## 八、PR 预览评论与 slash command 仍只认第一个项目

**状态**：open，已知边界，**本 PR 明确不做**。**影响**：今天不触发（尚无仓库真的绑了第二个项目）。

两处都是「按仓库找项目」的老写法，但它们与已经复数化的那五处不同——不是把单数换成
复数就完事，各自要先定一个产品语义：

**PR 预览评论**。评论 id 存在 `branch.githubPreviewCommentId`，是每分支一条，所以机械
fan-out 不会互相覆盖，但会让每个 PR 挂上 N 条机器人评论。而「一条评论列出全部预览」
没有对应的模板契约：`getCommentTemplateFor(projectId)` 是按项目的、用户可编辑的，渲染
的是单分支变量。两条路都是新产品行为。

**slash command**。`/cds redeploy` 在三个项目下是「全部重部署」还是「要选一个」？前者
是新行为，后者是新命令语法；`githubEventPolicy.slashCommand` 还是逐项目开关，fan-out
之后回帖要报 N 份结果。

**为什么不在那个 PR 里做**：`AGENTS.md` §5.5 的熔断条件命中（连续第三轮 review 仍在
产生新语义类别）。自动 Reviewer 的评论不能单独授权需求扩张，这两条要做需要人明确批准
扩范围，或者单开一个 PR。

## 九、同仓关系只发给浏览器会话

**状态**：已知设计取舍。**影响**：命令行看不到「和谁共用这个仓库」。

项目接口的 `repoSharing` 只在人类 cookie 会话时计算：机器凭据可能只被授权了本项目，不该顺带认识仓库里的其它项目，更不该看到它们的环境变量撞在了哪个 key 上。代价是 cdscli 这类调用方拿不到这份关系，只能从界面看。

要改的话，正确做法不是放开这个字段，而是按调用方的授权表逐项目过滤兄弟清单——那是一件独立的事，不在本轮。

## 十、共享基础设施是「算出来的」，认漏了就不报

**状态**：已知设计取舍。**影响**：提示会漏，不会错。

「这两个项目在写同一个库」这句话不能靠「同一个仓库」推断——那取决于两边环境变量填了什么。所以判据比对的是真实取值：同一个变量名、完全相同的值，才报。

由此带来两个漏判，都是有意选的：两个项目用**不同变量名**指向同一个库（`MONGO_URL` vs `CDS_MONGO_URL`）判不出；连接串里只有主机相同、库名不同的也不报（那本来就不是共享）。宁可漏报也不误报——断言「你们共用一个库」而实际没有，比不说更糟。

## 十一、横幅文案只算构建范围这一道闸

**状态**：已知边界，本 PR 不做。**影响**：文案偏保守（说会重建，实际可能不建），不会反过来。

「往这个仓库推一次代码，谁会重建」这句话现在只按**构建范围**分档。真实链路上还有几道闸
排在它后面：项目被暂停、push 事件被关掉、机器人账号的 push 被过滤、docs-only 推送不动
CI。命中其中任何一道，这个项目这次也不会重建，而文案已经说它会。

**为什么不在本 PR 补**：这不是把措辞改准一点。要把这四件事说准，`repo-sharing` 的判据
就得读到每个兄弟项目的 `githubEventPolicy` / `paused` / 机器人过滤开关，还要把「这次推送
是不是 docs-only」这种**事件级**信息带进一个**配置级**的摘要里——那是新的数据依赖和新的
语义类别，不是同一句话的第三次润色。按 `AGENTS.md` §5.5，连续第三轮针对同一段自由文本
加条件已经命中熔断判据，且机器 review 的意见不能单独授权需求扩张。

失败方向是安全的一边：说「会重建」而实际没建，用户看到的是比预期少的动作；反过来才伤人。
真要做，建议连同「这次推送到底会怎么走」的**逐项目预演**一起做（`decideProjectScope` 已经
能给出 reason，缺的是把其余几道闸也纳入同一个判定并端到界面上）。

## 十二、构建范围会饿死「范围之外」的自动发布规则

**状态**：本 PR 缩小了它，没有消除。**影响**：项目声明了构建范围，且有指向范围外路径的
自动发布规则时，某些分支上那条规则不会触发。

范围判定加进 push 分发之后出过一次事故：出口排在发布规则点火**之前**，于是
`doc/** → docs-site` 这类规则永远不触发（规则本来就是冲着「这个项目不构建」的 push 去的）。
出口已挪到点火之后，分支**已经在 CDS 里有记录**时规则照常触发。

剩下的缺口是：**这条分支从来没被这个项目建过**时，`runPushRules` 找不到分支记录，直接返回 0。
而范围没命中就不建分支，正是范围存在的意义。所以是个真实的张力，不是漏了一行：

- 让它建分支 → 每次范围外的推送都在这个项目下建一个 worktree，范围就白划了；
- 让发布不依赖分支记录 → 发布要从某个 worktree 里取产物，没有 worktree 就没有可发的东西；
- 把「发布规则的路径过滤」并进项目级范围 → 范围这个词从此有两个含义（要不要构建 / 要不要发布），
  是新语义，得先拍板。

第三条看着最接近正解，但它会让 docs-only 推送把项目判成「被波及」，与本 PR 刚立的另一条
不变量（范围没命中不建分支）直接冲突。按 `AGENTS.md` §5.5，这属于要先定产品语义的 B 类，
且熔断判据已命中，不在本 PR 展开。

失败方向：规则少触发一次（能靠下一次命中范围的推送补上），不会误发。

## 十三、一仓多项目的 push 处理是串行的，可能顶到 GitHub 的 10 秒窗口

**状态**：已知边界，本 PR 不做。**影响**：同仓项目多、且这条分支在多个项目下都要新建时，
webhook 可能超时被 GitHub 判失败。

`handlePush` 逐个项目 `await`：建目录、建 worktree、必要时 fetch 重试。单项目时这就是原有开销；
一仓绑 N 个项目之后，最坏情况是 N 倍。而路由必须在 10 秒内回 GitHub，超时会被判投递失败。

**为什么不在本 PR 改**：两条修法都动结构。并行跑（`allSettled` + 共享 abort）要先解决同一个
仓库上并发 `git worktree add` 抢 `index.lock` 的问题；「先回 200 再干活」则要改响应契约——
现在的响应体里带着 `branchId` / `deployDispatched` / `fanoutActions`，多条既有用例按它断言，
webhook 投递记录也按它写。两条都要先拍板，属 §5.5 的 B 类，且熔断判据早已命中。

**为什么今天危害有限**：重投不会造成重复部署——派发按 `(branchId, commitSha)` 30 秒内去重，
建分支本身也是按 `(projectId, branch)` 幂等。真正的后果是那次投递在 GitHub 上显示失败，
以及重投期间的重复文件系统开销。

真要做，建议连同「同一个仓库根上的 worktree 操作要不要串一道闸」一起设计。

## 十四、手写的范围路径没按后端归一化规则校验

**状态**：已确认的缺陷，本 PR 熔断后不做。**影响**：在范围对话框的「手写路径」折叠区填
`**` / `.` / `/` / `../shared` 这类，保存会提示成功，实际却把整个项目打回全通配。

后端 `normalizeBuildScope` 会拒掉仓库根等价物、绝对路径与含 `..` 的条目；作用域解析看到
一条被拒的声明就整体全通配（第十条的修法）。但对话框的手写区不做这层校验，于是用户填完
点保存，看到的是「已更新」，得到的是「每次推送照样全部重建」——又一个**改了不生效的开关
加一句会说谎的成功提示**，与第七条、第十一条同一形状。

**为什么不在本 PR 修**：不是判它不重要，是这个 PR 已经过了 §5.5 的熔断线（Review 修复
提交 12 个，阈值 8），且最近三轮的 finding 里有五条是前一轮修复自己带出来的。在这种状态下
继续改代码，每改一次就制造下一处的概率远高于收敛。等作者决定是继续改这个 PR 还是单开。

**危害边界**：只在手写区（默认折叠）触发；失败方向是全通配 = 全部重建，属安全的一边，
不会静默漏部署。

**修法**：把 `normalizeBuildScope` 的判据端到前端（或加一个校验端点），保存前逐条校验，
被拒的当场标红并说明原因，而不是发出去再由后端静默忽略。
