# 一仓多项目与身份层的工程债务

**一句话**：身份层已经能用，但一仓多项目的招牌能力还只是地基——一个仓库现在绑不了第二个项目，所以分发永远只会命中一个。
**谁该读**：接手 CDS 分发与凭据这块的人，以及要判断「这个能力现在能不能用」的人。
**读完能做什么**：知道哪几件事声称做完但其实达不到，各自缺什么、动它要付什么代价。

版本：2026-09-02 | 关联：[plan.cds.multi-project-identity.md](plan.cds.multi-project-identity.md)

## 一、一个仓库绑不了第二个项目（已解决，2026-09-02）

**状态**：closed。

翻掉了「一个仓库只能绑一个项目」这条不变量：绑第二个项目需要一次显式确认（link 接口的 `allowShared`、建项目的 `allowSharedRepo`），不带确认仍然拦住——因为绝大多数「已被绑定」都是填错了仓库地址，静默放行等于把误操作变成两个项目抢同一条 push。

同批把捆绑的另一半做了：删分支 / 关 PR / 极速版镜像完成三条此前仍按「找一个」取项目，不变量一翻就会造出没有信号的故障（分支永久停在等待中、容器留着没人收、预览一直开着）。三条各有一条红绿闭环用例——改回只取第一个项目，对应用例变红。

留下的边界见下面第六到第九条。

## 二、作用域只有一类，声明错了会静默跳过部署

**状态**：open。**影响**：潜在，今天不触发。

项目作用域取自各服务声明的构建输入范围。但一个服务真正依赖的东西不止镜像构建输入——还有部署期、运行期读的脚本与配置。谁声明了一份漏掉这些的作用域，改到它们的推送就会被判成「未波及」，分支不刷新、预览悄悄停在旧行为上，而且没有任何信号。

今天不触发：线上项目一个都没声明作用域，作用域为空即全通配。

**修法方向**：把「部署 / 运行期输入」与「镜像构建过滤」分成两类，而不是共用一份。这是新增一个语义类别，需要单独决定。

## 三、撤销单个项目授权没有界面入口

**状态**：open。**影响**：能力在，路径不顺手。

服务端有撤销接口、有判据、有测试，但权限总览里授权只是被动展示，没有任何前端调用它。要撤掉某个主体对某个项目的访问而不停用它整个人，只能手写请求。

## 四、存量凭据无法归属到主体

**状态**：open。**影响**：存量凭据享受不到自愈。

身份层之前签发的项目级凭据没有归属主体，因此不享受「换机器自助补发」。也没有「把一张旧凭据归给某个主体」的管理入口——只能由该主体自己补一张新的、再吊销旧的。

顺带澄清一个曾经写错的说法：这类凭据**不会**在「下次使用时自动认领」，光看一把凭据被使用，认不出背后是谁。界面文案已订正。

## 五、只授权不操作是留痕，不是拦截

**状态**：已知设计取舍，不打算改。

用户级凭证本身到不了运维面，但它能为已授权的项目自助签出项目级凭据，再拿那把去操作。所以这条边界的价值是**强制审计链 + 单一吊销开关**，不是权限隔离。把它读成「拿到用户级凭证也动不了东西」会高估它。

## 六、范围推断只做建议，不自动生效

**状态**：已知设计取舍。**影响**：还是要点一下，不是零操作。

系统能从各服务的启动命令看出本项目待在哪个目录（`cd cds` → `cds/**`），界面据此直接
给建议 + 一键采纳，用户不必从空白框开始。但推断值**不会自动顶替**分发判据。

理由是失败方向不对称：判据读的是已声明的范围，空 = 全通配 = 兜底全建，猜错顶多多建
一次；让推断悄悄生效，猜窄了就会把某个项目的推送判成「未波及」而静默跳过部署，分支
停在旧行为上且没有任何信号。所以宁可多要那一下点击。

另外，只要有**任何一个**服务连线索都没有（命令里没有 `cd`、workDir 是仓库根），整个
项目就不出建议——按已知的几个收窄，会把那个未知服务需要的路径挡在外面。

## 七、声明在部署模式上的范围，界面上改不了

**状态**：已知设计取舍。**影响**：这类服务只能去改 compose。

范围可以声明在两处：构建配置顶层，或某个部署模式下。判定分发时取两者并集，但**写回**
只能写对应那一处。范围对话框写的是顶层字段，所以对「声明在部署模式上」的服务，清空
清不掉模式那份、改窄反而并集变宽——提示还会报成功。本仓库线上五个服务全是这一类
（compose 的 `cds.build-scope` 标签带上来的），所以这不是边缘情况。

现在的处理是**如实只读**：接口标出声明在哪儿，这类服务渲染成只读卡片并写明「要改就去
改这个服务在 compose 里的 `cds.build-scope` 标签后重新导入」，保存时跳过。

**为什么不做「写回声明源」**：那等于从这个对话框反向改用户写在 compose 里的东西，而
重新导入 compose 会再覆盖回去——两边谁赢取决于操作顺序，风险比它解决的问题大。真要
做，得先决定 compose 与 CDS 配置树在这个字段上谁是权威，那是一件独立的事。

## 八、同仓关系只发给浏览器会话

**状态**：已知设计取舍。**影响**：命令行看不到「和谁共用这个仓库」。

项目接口的 `repoSharing` 只在人类 cookie 会话时计算：机器凭据可能只被授权了本项目，不该顺带认识仓库里的其它项目，更不该看到它们的环境变量撞在了哪个 key 上。代价是 cdscli 这类调用方拿不到这份关系，只能从界面看。

要改的话，正确做法不是放开这个字段，而是按调用方的授权表逐项目过滤兄弟清单——那是一件独立的事，不在本轮。

## 九、共享基础设施是「算出来的」，认漏了就不报

**状态**：已知设计取舍。**影响**：提示会漏，不会错。

「这两个项目在写同一个库」这句话不能靠「同一个仓库」推断——那取决于两边环境变量填了什么。所以判据比对的是真实取值：同一个变量名、完全相同的值，才报。

由此带来两个漏判，都是有意选的：两个项目用**不同变量名**指向同一个库（`MONGO_URL` vs `CDS_MONGO_URL`）判不出；连接串里只有主机相同、库名不同的也不报（那本来就不是共享）。宁可漏报也不误报——断言「你们共用一个库」而实际没有，比不说更糟。
