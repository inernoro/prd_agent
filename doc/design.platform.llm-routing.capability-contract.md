# 模型路由能力契约与故障域隔离 · 设计

> **版本**：v1.0 | **日期**：2026-08-17 | **状态**：开发中

**一句话**：把「一个模型能拿来干什么」收敛成唯一契约，让写入、迁移、运行时、readiness 和发布门禁用同一条判据，并把「模型池不可用」这一句话拆成十种能各自定位的失败。
**谁该读**：维护 LLM 网关路由与模型池的工程师；判断「这版能不能发」的人。
**读完能做什么**：说清一次生图失败到底是配置问题还是上游故障，并判断某个能力别名、Offering、模型池或 Provider 出问题时故障会停在哪里。

---

## 一、这次要解决的不是一个报错

「模型池不可用」在本系统反复出现过多轮：同一请求被重复 Resolve、健康与半开恢复、Offering 路由、跨池重试、控制台与运行时对能力理解不一致。`ModelResolver.cs` 自 2026-08-01 起被改了约 29 次——它已经是回归热点，说明每次都在治症状。

2026-08-13 那次的形状最能说明问题：

| 环节 | 当时的事实 |
|---|---|
| 正式数据 | 逻辑生图模型的 `Capabilities` 存的是历史值 `image-gen` |
| 写入侧（控制台） | 归一化只识别规范值 `image_generation`，不认 `image-gen` |
| 运行时（MAP） | `SupportsAppCallerScenario` 也只认 `image_generation` |
| 结果 | 逻辑模型在解析阶段被整批过滤，候选数变 0 |
| 用户看到 | 「当前没有可用的生图服务」 |
| 管理员看到 | 同一句话，于是先去查供应商 |
| readiness | 绿。它只看池在不在、有没有成员、平台开没开、成员是不是 Unavailable |
| CI / 容器 | 全绿 |

模型、平台、Offering、Provider 全部真实可用。**所有灯都亮着，功能是死的。**

叠加两个已开启的 fail-closed 开关（`DisableMapConfigFallbackForRegisteredAppCallers` /
`...ForActiveAppCallers`），Gateway 路由解析一旦失败就不许退回 MAP 旧配置——这个设计本身
是对的（防止把请求发给错误类型的模型），但它让 Gateway 配置成为所有已注册 AI 功能的
**共同故障点**：配置面的一个判据写窄一点，影响范围就是全站。

止血已在 `1afa03f2` 完成（运行时同时接受两种写法），`map.ebcone.net` 已运行该版本并通过真实
生图。那只是兼容，不是治理。

## 二、系统性根因

1. **能力契约没有唯一来源。** `image-gen` / `image_generation` / `generation` / `text2img` /
   `img2img` / `vision_generation` 在不同模块被分别解释，同一个问题有四个答案。
2. **写入、迁移、展示、readiness、运行时用不同判据。** 判据一分裂就会漂移，而漂移没有任何机制会发现。
3. **ModelResolver 职责过重。** 配置读取、历史兼容、appCaller 治理、池选择、健康调度、
   Offering 解析、降级、错误诊断全在一个类里，局部改动波及所有 AI 功能。
4. **Gateway 是集中式配置权威，但按 appCaller / 能力 / 模型类型的隔离不足。**
5. **验收用新初始化数据或人工构造数据，从不回放正式环境的存量配置形态。**
6. **健康检查证明的是「服务活着」，不是「真实业务路径能解析并调用模型」。**

---

## 三、能力契约（唯一来源）

### 3.1 契约内容

契约定义三件事，写在一处：

- **规范能力 ID**：落库只允许出现这些值。图片相关的是 `image_generation`（通用）、
  `text2img` / `img2img` / `vision_generation`（场景）、`image_layering`（动作能力）。
- **有限历史别名**：旧写法到规范值的显式映射表，例如 `image-gen` → `image_generation`。
  刻意不用「kebab 自动转 snake」这类开放规则——开放规则会让任何新造的错别字都被静默接受，
  未知能力审计就永远报不出东西。新别名进表必须有出处（哪个部署、哪条数据、哪次事故）。
- **场景判定**：某个逻辑模型能不能服务某个 appCaller 的场景。顺序是：显式 allowlist →
  动作能力隔离（声明分层的只许分层 appCaller 调）→ 无场景要求则放行 → 声明了所需场景则放行 →
  兼容兜底（未声明任何场景但有通用生图能力则放行）→ 否则拒绝。

判定全程在**归一化之后**的集合上进行，所以历史别名天然被认，任何调用方都不需要再对字面量特判。

### 3.2 谁引用它

| 消费方 | 引用方式 |
|---|---|
| MAP 运行时（ModelResolver） | 直接调用契约，自身不再持有任何能力字面量 |
| llmgw serving readiness | 直接调用契约，与运行时同一个函数 |
| llmgw console-api（写入与迁移） | 按既定隔离架构不引用 MAP 代码，保留镜像 |
| 前端模型选择器 | 通过后端透出的能力标签，不自维护映射 |

**关于那份镜像**：控制台被刻意设计成不依赖 MAP（隔离目标是「剥离失败不波及主站」，
镜像构建上下文也只有控制台自己那个目录），因此这里做不到硬项目引用。折中方案是
**镜像 + 机械守卫**：守卫测试同时加载两侧，逐条比对规范能力表、别名表、契约版本、场景能力表，
并对同一组输入比对归一化**行为**。任一侧改动而另一侧没跟上，CI 立刻红。
这条守卫本身能红——把任一侧的表改一个字就会失败。

### 3.3 未知能力

不认识的能力**不丢弃**：原样保留在文档里，同时由归一化结果单独列出。发布门禁据此阻断并
点名对象（哪个逻辑模型、什么用途、哪几个 token）。未知能力不参与路由判定——它既不放行，
也不冒充「已声明场景」而关掉兼容兜底。

### 3.4 契约版本与迁移

逻辑模型文档带 `CapabilitySchemaVersion`。迁移是幂等的：只有归一结果与现值不同或版本落后才写，
第二次执行重写数为 0。迁移前统计扫描数，迁移后**回读数据库**核对残留别名数与未打版本数——
只信回读，不信「内存里算过一遍」。写入路径同时打版本，新数据不必靠迁移兜底。

## 四、故障域隔离

| 边界 | 约束 |
|---|---|
| appCaller | 一个 image appCaller 配错，只影响这个 appCaller。生图失败不得让 ASR、对话、embedding、视频同时失败 |
| Offering | 一条 Offering 失败只隔离该 Offering，同逻辑模型的其它 Offering 可接管 |
| 模型池 | 一个池失败不污染其它池的健康状态；池内单成员失败只更新该成员 |
| 配置面 | 配置数据库暂时读不到，不得与「配置配错了」共用一个失败原因 |

最后一条是本次新增的判据。配置面「读不到」是基础设施故障（重试可能恢复），
「配错了」是配置问题（重试无用）。过去两者都落到同一句「未绑定有效模型池」，
于是配置库一次抖动会被报成「所有 AI 功能的模型池全报废」，管理员按配置错误方向排查，
一开始就走反了。

### readiness 的红线口径

readiness 现在跑**生产同款场景判据**：对每个带图片场景要求的治理内 appCaller，
检查是否存在「能力匹配 + 有可用 Offering」的启用逻辑模型。

红灯口径与既有 router 组件保持一致：**单个 appCaller 配错报退化并点名，全部场景调用方
都不可路由才变红**。理由是 readiness 是实例级的——把每个 serving 实例都摘掉，会让一个错绑定
升级成全站 AI 宕机。而 2026-08-13 的形状恰恰是「全部图片 appCaller 都不可路由」，
所以那一天这条会红。逐个 appCaller 的明细同时暴露给发布门禁，门禁可以对**任意一个**坏的
appCaller 阻断——两级口径各管各的：readiness 管「这台机器还能不能接流量」，
门禁管「这版能不能发」。

## 五、错误分类

一次路由失败必须回答两个不同的问题，给两拨人：

- 用户要知道**重试有没有用**；
- 管理员要知道**去改哪个对象**。

因此结构化原因分十类：`ROUTE_CONFIG_INCOMPATIBLE`、`APPCALLER_POOL_UNBOUND`、
`MODEL_POOL_EMPTY`、`MODEL_POOL_ALL_UNAVAILABLE`、`LOGICAL_MODEL_CAPABILITY_MISMATCH`、
`OFFERING_UNRESOLVABLE`、`PLATFORM_DISABLED`、`PROVIDER_UNAVAILABLE`、
`PROVIDER_QUOTA_EXCEEDED`、`GATEWAY_CONFIG_UNAVAILABLE`。

- 每个原因有自己的用户文案与管理员处置提示，不许集体落到兜底句。
- 配置类失败的用户文案指向「联系管理员」，瞬时故障指向「稍后重试」。
- 用户文案里不出现 appCaller、池 ID、Offering ID 等内部标识。
- 管理员日志给出定位串：错误码 + 失败阶段 + appCaller + 逻辑模型 + Offering + 池 + 处置提示。
- 结构化原因跨 serving 与 MAP 的 HTTP 边界透传，否则回到进程边界另一侧就只剩自由文本。
- 「池是空的」与「成员全熔断」是两种处置动作（补成员 vs 看上游），因此判为两个原因。

前端按错误码取文案，**不再对错误文本做字符串匹配猜原因**。

## 六、算与发的边界（沿用既有原则）

一次业务请求内 Resolve 只发生一次，发送阶段只消费已解析结果，不再选模型；
禁止用 AsyncLocal、DI 装饰器或实例字段跨调用传递解析状态。这条不是本次新增，
但本次的结构化失败原因随 `RouteResolution` 一起流转，属于同一条边界上的字段扩展。

---

## 七、验收判据

「修好了」不等于「image-gen 又能用了」，而是下面几条同时成立：

1. 正式环境的存量数据形态（只有 `image-gen`、没有契约版本）在回放测试里可路由；
2. 把别名支持删掉，回放测试立刻红；
3. 能力名彻底不兼容时 readiness 在用户失败之前点名报出坏掉的 appCaller；
4. 恢复配置后 readiness 自动转绿，不需要重启；
5. 一个能力/池/appCaller 出问题时，其它能力的解析不受影响；
6. 十类失败各自返回独立错误码，用户文案能区分「重试有没有用」；
7. 两侧能力表与归一化行为一致，改一侧就红；
8. Resolver 里每一处失败返回都带结构化错误码，新增一处忘带就红。

## 八、已知边界

- 控制台侧是镜像而非硬引用，靠守卫测试保证一致。硬引用需要改控制台的镜像构建上下文，
  与「控制台不依赖 MAP」的隔离目标冲突，本次不做，记入债务台账。
- 「最后一次已验证路由」（last-known-good 快照）本次只做设计评估，未实现，理由见债务台账。
- 历史别名兼容不得撤销，直到正式数据迁移完成且有回滚方案。
