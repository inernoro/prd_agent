## 用户反馈的准确含义

第一张反馈要求把现成的多页面 ZIP 原样上传。把它重写或压成单页 HTML 会改变交付物，不能算支持 ZIP。应保留页面、脚本、样式、图片及相对路径，并核验页面间跳转。

第二张反馈明确要求“公开、永久”。网页端已有相应设置，MCP 初期只开放本人及团队可见、最长 90 天的分享。缺口在开放能力和操作说明，不能把接口限制描述为 MAP 整个平台不支持。已发布的站点地址、可匿名访问的分享地址、权限设置成功，是三件需要分别核验的事。

截图属于需求和故障证据，不是实际 ZIP 源文件，也不构成对历史站点的修改指令。验收使用新建的测试站点。

## 实施与验收目标

先完成 P0；P1 的界面与技能包可隔离并行，P2 在技能调用约定明确后接入。所有轨道合流后一起回归，界面使用既有接入台和网页托管入口。

技能正文维护一份，下载安装无需业务密钥；凭据不打入公开技能包。Codex 使用既有项目技能目录约定；WorkBuddy 使用官方技能包导入，不猜测第三种本地宿主目录。

大文件通过实际文件上传通道传输，MCP 用来取得指引与提交状态，不让模型把整个 ZIP 编进对话。业务复用既有站点与分享服务，授权仍是用户权限、密钥范围和目标对象权限的交集。

最终必须验证两条用户旅程：接入台切换 Codex、WorkBuddy，取得适配配置和技能包，检查版本、升级并实际调用；现成多页网站原样上传、更新原站、创建公开永久分享、匿名打开及撤销后拒绝访问。截图和报告使用当前提交的部署，界面检查明暗主题。根据用户进一步澄清，本轮只增加 MAP 侧的 WorkBuddy 接入方式，不操作用户的 WorkBuddy 安装、配置或账号。隔离环境的配置解析和服务端调用可证明接入契约，不能宣称完成了该客户端桌面实测。
