# 文档说人话标准（导读三行 + 人先于机器） · 规则

> **版本**：v1.0 | **日期**：2026-07-31 | **状态**：已落地

**一句话**：规定每篇长期文档都要在开头用大白话说清「讲什么、谁该读、读完能干什么」，让人十秒决定读不读。
**谁该读**：任何要新建或修改 doc/ 下文档的人和 AI；想知道这套文档该怎么写得像人话的人。
**读完能做什么**：照着导读三行的格式写文档，并用 `scripts/doc-readability-check.py` 自查是否达标。

---

## 一、为什么要有这条规则

2026-07 我们把日报、周报、验收报告改成了「说人话版本」，效果立竿见影：用户第一次说「效果好很多」。
它们做对的其实只有三件事：**第一屏是结论不是过程、结论用用户听得懂的词、重要的排在前面**。

但这三件事只落在了「每天变的报告」上。**不变的那部分文档没跟上**——设计文档、规则文档、债务台账、
指南、说明书。本规则上线前的实测：

| 事实 | 数字 |
|------|------|
| `doc/` 长期文档 | 352 篇 |
| 总字数 | 约 232 万字 |
| 全部读完需要 | 约 97 小时（按 400 字/分钟，等于两周全职只读文档） |
| 开头能让人判断「这篇关不关我事」的 | 0 篇（导读三行覆盖率 0%，见下方棘轮基线） |

**结论：不是文档写得不好，是没有入口。** 232 万字没有人能通读，而每一篇又都不告诉你「你要不要读我」，
于是读者只能靠猜文件名、靠问 AI、靠找人。这就是这套百科全书目前最大的可读性缺陷。

**注意「说人话」在参考文档上的正确含义**：不是把技术设计写成散文，也不是要求人人读完。
是**把进入成本降到十秒**——十秒内答得出「这篇讲什么、关不关我事、读完能干什么」，
答不出就不合格。真正的细节该多硬就多硬，往后放。

---

## 二、核心判据（一句话记住）

> 随便挑一篇文档，随便找一个人打开它，**十秒内**要能回答三个问题：
> **① 这篇讲什么？② 关不关我事？③ 读完我能干什么？**
> 三个里有一个答不出来，这篇文档就不合格。

---

## 三、强制条款

### 条款 1：每篇 `doc/*.md` 必须有「导读三行」

位置固定：H1 标题下、版本行之后、正文之前（第一屏，25 行以内）。格式固定：

```markdown
# 文档标题 · 类型

> **版本**：v1.0 | **日期**：2026-07-31 | **状态**：已落地

**一句话**：不用黑话，说清这篇解决什么问题。
**谁该读**：什么角色、在什么情况下会来读这篇。
**读完能做什么**：读者读完能采取的具体动作，或能回答的具体问题。
```

三行都是必填。写不出「谁该读」的文档，说明它没有读者，应该合并或删除，而不是留在库里占位。

**正例**（债务台账）：

```markdown
**一句话**：记录构建排队机制这次大修里故意先不做的六件事，以及各自什么时候必须做。
**谁该读**：接手构建队列的人；下次构建又排长队时来查「是不是已知问题」的人。
**读完能做什么**：判断当前遇到的现象是已知边界还是新故障，并知道该改哪一处。
```

**反例**（本规则上线前 [debt.cds.build-gate.md](./debt.cds.build-gate.md) 的开头，逐字摘录）：

> build-gate 可取消 + holder 身份、极速版跳闸、就绪探测容器活性早退、层内 fan-out allSettled + 共享 abort、
> manual deploy 合并、run 账本周期收割 + 部署静默期节流心跳……

一句话里九个内部黑话，没有一个字告诉读者「你要不要读」。写的人当然懂，但文档不是写给写的人看的。

### 条款 2：「一句话」必须真的是人话

机器判定的三条硬形状（`scripts/doc-readability-check.py` 会扫）：

1. **不超过 80 字**——超了就不是一句话，是一段话，说明还没想清楚。
2. **不含代码引用、文件路径**（反引号、`xxx.ts` / `xxx.cs` 这类）——路径是给机器找文件的，不是给人建立预期的。
3. **不含驼峰 / 蛇形标识符**（`buildGate`、`app_caller_code`）——标识符往下文放，第一句用中文说它是什么。

机器判不了但同样要求的一条：**缩写和内部黑话首次出现必须给一句大白话**。
写「SSOT（唯一事实来源，改这一处就够）」，不要光写「SSOT」。

### 条款 3：人先于机器 —— 第一屏放结论，不放实现

每类文档的第一屏必须回答的问题固定如下。顺序可以调整，但这些问题不许挪到后面：

| 类型 | 第一屏必须回答 | 可以往后放 |
|------|----------------|-----------|
| `spec.` 产品规格 | 给谁用、解决什么问题、做完长什么样 | 字段、接口、状态机 |
| `design.` 技术设计 | 管理摘要（30 秒看懂方案全貌）、为什么这么选 | 架构图、数据结构、接口签名 |
| `plan.` 计划 | 现在到哪一步、卡在哪、下一步做什么 | 分阶段任务拆解 |
| `rule.` 规则 | 这条规则禁止什么、什么时候会撞上它 | 判据细则、守卫实现 |
| `guide.` 指南 | 照着做能得到什么、需要什么前置 | 逐步命令、参数表 |
| `debt.` 债务 | 欠了什么、什么时候必须还、不还会怎样 | 逐条技术说明 |
| `report.` 周报 | 本周业务价值、质量闸结论 | 技术细节附录 |

`design.` 的「管理摘要必填」在 `.claude/rules/doc-types.md` 已有规定，本规则把同样的要求扩展到其余六类。

**周报是双产物，两份都要那一句话。** 周报同时产出 md 底稿（落 `doc/report.YYYY-WNN.md`）和
html 周刊版（发知识库给人读），二者同构同数：

| 产物 | 那一句话长什么样 | 由谁保证 |
|---|---|---|
| md 底稿 | 报头下的 `**本周一句话**` | 本规则的机器闸门（`doc/` 内） |
| html 周刊版 | 封面故事栏目的大标题（`kicker` + `h1`） | 周报模板 + 守卫测试断言该结构存在 |

日报只有 html 一种产物（进知识库不进 `doc/`），它的对应物是首屏「今日大事 TL;DR」，
同样由守卫测试盯住模板结构。**任何一版把那句话删了，测试就红**——不靠人记得。

### 条款 4：引用别的文档必须能点开

**正文里提到另一篇文档，一律写成相对路径链接，不许写成一段点不动的行内代码。**

```markdown
正确：详见 [rule.doc.naming.md](./rule.doc.naming.md)
错误：详见 `doc/rule.doc.naming.md`
```

- 判据（机器扫）：行内代码里出现的 `.md` 文件名，**如果它在 `doc/` 下真实存在**，就必须改成链接。
  不存在的（命名规则里的错误示范、占位模板名）不会被误伤。
- **死链零容忍**：相对链接的目标必须存在，缺一个 CI 直接 fail，不走棘轮。
- 批量修法：`python3 scripts/doc-readability-check.py --fix-links`（跳过代码块，跳过已经是链接的地方）。
- 目前只管 `doc/` 内部互引。指向 `.claude/rules/`、源码路径的引用仍用行内代码（它们不是给人点开阅读的正文，是给 AI 定位文件的）。

**为什么单列一条**：文档之间点不开，读者就只能回到「复制文件名、切到编辑器、全局搜索」的老路——
这跟没有导读一样，都是把成本转嫁给读者。一套 350 篇的知识库，价值一半在文档本身，一半在它们之间连得起来。

### 条款 5：结论要能被核对

写「已验证 / 已落地 / 已通过」时必须挂可点开的证据（验收报告链接、看板行、测试名、PR 号）。
只写结论不给证据的句子，读者无法判断可信度，等于没写。承接 `.claude/rules/living-status-board.md`
与 `.claude/rules/real-visual-acceptance.md`。

### 条款 6：存量走棘轮，新文档零欠账

```bash
python3 scripts/doc-readability-check.py                 # 看当前达标率
python3 scripts/doc-readability-check.py --list-missing   # 列出欠账文件和原因
python3 scripts/doc-readability-check.py --ratchet        # CI 闸门：欠账只许降不许升
python3 scripts/doc-readability-check.py --update-baseline # 修好一批后压低基线
```

- 基线文件：`scripts/fixtures/doc-readability-baseline.json`，按类型记录「缺导读篇数」与「裸引用处数」两组欠账。
- **新增文档必须自带导读三行**——否则欠账数上升，CI 直接 fail。
- **存量走到哪修到哪**：改一篇文档就顺手补上它的导读三行，然后跑 `--update-baseline` 把基线压低。
- 基线**上调一律 reject**。确有合理原因（如批量迁入历史文档）必须在 PR 里写明。

优先补的顺序：读者最多的先补 —— `guide.` > `spec.` > `rule.` > `debt.` > `plan.` > `design.`。

## 四、自查清单（新建或大改文档前过一遍）

- [ ] 导读三行齐了吗（一句话 / 谁该读 / 读完能做什么）？
- [ ] 「一句话」里有没有代码、路径、驼峰标识符？超过 80 字了吗？
- [ ] 「谁该读」写的是具体角色 + 具体场景，不是「所有人」？
- [ ] 第一屏回答的是结论，不是实现细节（对照条款 3 的表）？
- [ ] 缩写和黑话第一次出现时给了大白话解释？
- [ ] 写「已完成 / 已验证」的地方都挂了能点开的证据？
- [ ] 跑过 `python3 scripts/doc-readability-check.py --ratchet` 且是绿的？

## 五、已知边界（第一版没做的）

| # | 边界 | 说明 |
|---|------|------|
| 1 | 只扫 `doc/` | `.claude/rules/*.md` 和 `.claude/skills/*/SKILL.md` 同样该有导读，但它们主要面向 AI 且已有「一句话主张 + 触发词」的既有格式，第一版不上闸，避免一次改动面过大。记入 [doc/debt.doc.readability.md](./debt.doc.readability.md)。 |
| 2 | 机器只判形状，不判好坏 | 脚本能判「有没有、是不是一句话形状」，判不了「这句话是不是真说清楚了」。后者靠 review 和本规则的判据。 |
| 3 | 存量 340 篇未回填导读 | 本次只回填了各类的入口文档做示范，其余走棘轮渐进偿还。引用可点击已一次性全量修完（791 处 → 0）。 |
| 4 | 引用只管 `doc/` 内部互引 | 指向 `.claude/rules/`、源码路径的引用不强制转链接（跨目录相对路径在知识库渲染下会断）。 |

## 六、为什么之前那么多栅栏都没拦住「引用点不开」

这条值得单独写下来，因为系统里已经有 doc-sync、熵减扫描、双链、模板审查清单四道栅栏，
791 处点不开的引用照样活了很久。逐条查下来，四道栅栏**没有一道的判据覆盖这件事**：

| 栅栏 | 它实际在守什么 | 为什么漏了 |
|---|---|---|
| `/doc-sync` | 文件 ↔ `index.yml` ↔ 文档清单 三方存在性对账 | 判据是「**有没有这篇**」，从不看正文里的引用能不能点 |
| `/entropy` 熵减六维 | 命名、索引、清单、技能表、快照、changelog 覆盖 | 六个维度全是「清单类一致性」，没有一维是「正文内引用可达性」 |
| 双链（引用网络） | 知识库条目里的 `[[双链]]` 与反向链接 | 作用域是数据库里的知识库条目，`doc/` 下的仓库 markdown **从不进那条链路**，物理上够不着 |
| 文档模板审查清单 | 「文档内没有失效链接」 | 是给人看的软提醒，**没有任何机械判据**；而且它管「链接坏没坏」，从没要求「引用必须写成链接」 |

**根因归类**（对照 `.claude/rules/predicate-and-wiring-discipline.md`）：

- **形状 1（判据比该管的范围窄）**：所有栅栏都在守「文档存不存在」，没有一道守「文档之间连不连得起来」。
  把引用写成行内代码在过去**完全合规**——因为规则从没说它不合规。
- **形状 2（链路只建到一半）**：双链能力建好了，但只接到知识库，没接到仓库文档；
  模板里写了要求，但没接判据。两处都是「建了一半，删掉也不会红」。

**这次的补法**：把「引用可点」变成条款 4 的机器判据 + 死链零容忍 + 棘轮，并**一次性全量修完存量**
（791 处 → 0）。判据在机器手里，才不会再靠谁记得。

## 七、与其他规则的关系

- `.claude/rules/doc-types.md` / [doc/rule.doc.naming.md](./rule.doc.naming.md)：管**放在哪、叫什么名**（分类与命名）；本规则管**开头怎么写**（可读性）。名字帮你找到它，导读帮你决定读不读。
- [doc/guide.doc.reading-map.md](./guide.doc.reading-map.md)：本规则的对偶面——那篇管**读者怎么读整套文档**，这篇管**作者怎么写单篇文档**。
- `.claude/rules/expectation-management.md`：预期管理总纲。导读三行就是文档层面的预期管理——让读者一眼知道「接下来会读到什么」。
- `.claude/rules/report-design-system.md`：报告类产物（日报 / 周报 / 验收）的视觉与叙事标准，本规则是它在「不变的参考文档」上的对应物。
- `.claude/rules/predicate-and-wiring-discipline.md`：本规则配了机械守卫 + CI 接线，正是「改动删掉后测试仍全绿 = 需要一条守卫」的落地。

## 八、历史背景

2026-07-31 用户在看完说人话版日报后提问：「设计文档、规则文档、债务文档、教程文档、说明书文档，
是否也具备说人话的标准？人类应该如何阅读我们系统中的这本百科全书？」
实测发现 352 篇文档里有面向人的入口的是 0 篇——问题不在写作水平，在**缺入口**。本规则与
[doc/guide.doc.reading-map.md](./guide.doc.reading-map.md) 同批落地：一篇管作者怎么写，一篇管读者怎么读。
