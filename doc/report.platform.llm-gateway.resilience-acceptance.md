# LLM Gateway 故障隔离与恢复 · 测试环境验收报告

> **版本**：v1.0 | **日期**：2026-08-13 | **状态**：部分通过

**一句话**：测试环境已证明未绑定模型池故障不会清空 MAP 模型目录，且可通过恢复接口回到 Healthy；通知中心和权威部署链路仍未达到完整验收门槛。
**谁该读**：负责 MAP、LLMGW、通知中心和发布验收的产品、研发、测试与值班人员。
**读完能做什么**：知道本轮实际验证了什么、哪些结论可以接受、哪些证据不足，以及下一轮必须补齐的验收动作。

## 一、验收结论

本轮不宣布“完整自动自愈已完成”。结论分层如下：

| 能力 | 结论 | 证据 |
|---|---|---|
| MAP 模型目录不因单池故障清空 | 通过 | 未绑定 `stub-image` 池注入 5 次失败后，模型目录仍返回 5 个模型，状态均为 `Healthy` |
| 单池健康状态隔离 | 通过 | `stub-image` 从 `Healthy` 进入 `Unavailable`，未触碰视觉创作 AppCaller 使用的池 |
| 手动恢复 | 通过 | 使用恢复接口写入 1 次成功后，端点回到 `Healthy`，连续失败归零 |
| 无付费探测止血 | 通过 | 只调用测试控制面故障模拟与查询接口，没有发起上游生图请求 |
| LLMGW 半开并发、真实业务恢复 | 未完成 | 本轮没有改动真实 LLMGW 生产池，也没有发起上游请求，缺少多实例并发证据 |
| 故障与恢复站内通知新事件 | 未接受 | 预览部署明确跳过共享管理员通知写入，且探活后台默认关闭；只能确认历史事件数据存在 |
| 完整生产验收 | 未通过 | 通知权威性、四链路演练和生产回滚证据尚未齐全 |

## 二、实际执行的无费用演练

测试对象是 MAP 中未绑定业务的非默认 `stub-image` 模型池，池 ID 为 `f42a53067ad2415db77ff2343270074e`，成员为 `stub-image@platform4`。该对象不参与当前视觉创作 AppCaller 的真实请求路由。

### 1. 故障注入

- 基线：成员 `Healthy`，连续失败数为 0；模型目录可读。
- 操作：通过测试控制面注入连续 5 次失败。
- 结果：成员变为 `Unavailable`，健康分为 0；没有触发任何上游请求。

### 2. 隔离检查

- 重新读取 MAP 模型目录，返回 5 个模型：图片分层、Image 2、Nano Banana 2、Nano Banana 2 Lite、Nano Banana Pro。
- 5 个目录项仍可见且状态为 `Healthy`。
- 因此，单个未绑定池的不可用状态没有扩散成“模型目录为空”或“整个视觉创作页面不可用”。

### 3. 恢复检查

- 操作：通过恢复接口注入 1 次成功。
- 结果：成员回到 `Healthy`，连续失败数为 0，连续成功数为 1；健康总览中的该池恢复为 `healthyCount=1 / unavailableCount=0`。
- 这证明当前恢复动作没有伪造 Healthy，而是走了状态记录路径。

## 三、通知链路现状

本轮读取到了通知中心中的既有 `pool-exhausted`、`pool-recovered` 和 `llm-quota-exceeded` 事件，说明事件模型、去重键和历史状态已经存在。但这不能代替新故障的端到端验收，原因是：

1. CDS 预览部署被识别为非权威部署，后台监控会跳过共享管理员通知写入，避免测试分支污染共享通知数据。
2. 模型池后台探活默认关闭，不能通过开启循环探活来“烧额度”验证通知。
3. 本轮使用的是控制面 stub 故障注入；该接口只改变模型健康状态，不直接调用 `PoolFailoverNotifier`。

因此，通知验收必须在具备权威通知写权限的隔离测试环境，使用无费用 mock transport 或专用测试池完成，并验证“故障创建、同事故去重、恢复创建、故障通知关闭、日志深链可打开”五个断言。

## 四、合格验收门槛

今后只有同时满足以下条件，才可以把这类改动标记为“验收合格”：

- MAP 目录读取失败时保留上次成功目录，并明确标记陈旧，不覆盖为空；
- 单成员、单 Provider 或单池故障不会清空其他获准模型，不会擅自跨池；
- 用户显式选择的池耗尽时，默认返回结构化失败和换池建议，跨池代选必须有显式授权；
- 恢复使用真实业务请求的 HalfOpen 资格，不使用未经确认的付费合成探测；
- 成功、失败、用户错误和结果未知分别进入正确状态，且多实例不会重复放行；
- 故障通知和恢复通知都能在通知中心看到，并能深链到请求日志、池配置和恢复入口；
- 通知中心不可用时，数据面仍能失败隔离和恢复，通知失败不反向锁死 MAP 或 LLMGW；
- 审计能还原故障成员、AppCaller、请求 ID、错误分类、隔离、HalfOpen、恢复和回滚；
- 验收结束后测试池回到 Healthy，测试配置和临时授权已清理，无未确认的上游费用。

## 五、下一轮必须补齐

| 优先级 | 动作 | 关闭证据 |
|---|---|---|
| P0 | 在权威且隔离的测试运行时执行一次 mock 502 故障事件 | 新建的 `llmgw-upstream` 或 `pool-exhausted` 通知、去重结果和恢复通知截图/API 证据 |
| P0 | 验证通知中心、日志详情、池配置和恢复入口四条深链 | 每条链接可直达目标页面，不依赖首页二次搜索 |
| P1 | 用两个 LLMGW 实例并发争抢同一 HalfOpen 窗口 | 实际放行数不超过配置值，成功和失败各只收口一次 |
| P1 | 验证严格池路由和显式跨池授权 | 未授权不跨池，授权到期自动关闭，审计可追溯 |
| P1 | 做一次通知服务不可用演练 | 请求失败隔离、真实恢复继续，通知补偿或重试不阻塞数据面 |

本报告关闭前，P4“通知、演练与发布门禁”仍保持未完成；任何发布说明不得把本轮“部分通过”写成“完整自愈已验收”。
