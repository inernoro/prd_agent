## 明细

### D1 三个角色套装（已偿）

`pm-starter` / `dev-starter` / `qa-starter` 均已落地，对应 `pm-project` / `dev-project` /
`qa-project` 三个初始化预设。补新角色仍是「往 `scripts/skill-bundles.json` 加一个对象 +
重跑打包脚本」，机制不变。

### D2 套装不可自定义

- **是什么**：没有「勾选若干技能 → 打一个自定义 zip」的能力。
- **为什么欠着**：先验证角色套装这个形态成立，再谈组合自由度。过早做自定义会让「官方推荐组合」的价值被稀释。
- **什么条件下必须还**：出现多个用户反馈官方组合不合用时。后端已有 `ExpandWithRequires` + `PackSkills`，加一个接受 key 列表的端点即可。

### D3 sdd-init 未在真实外部空仓库验证

- **是什么**：`sdd-init` 的探测逻辑和模板本次通过自测验证了「能被正确分发」（zip 里文件齐全、frontmatter 合规、零 emoji），但没有在一个真实的外部空项目里让 AI 完整跑一遍生成流程。
- **为什么欠着**：需要一个干净的外部环境和一次真人观察，不是本次改动能自闭环的部分。
- **什么条件下必须还**：第一次真正把套装交给外部用户之前。
- **不还的后果**：生成的骨架可能有措辞不贴合、默认值不合适的地方，第一次用的人体验打折。

### D4 对外产物 de-emoji 只做了一部分

- **是什么**：[doc/debt.platform.md](./debt.platform.md) 的清理方案第一步是「先治对外产物」。本次因为把 `acceptance-checklist` 放进 PM 套装，顺带把它的 2 个 reference 文件 de-emoji 了（空心方框 U+2610 改为 `[ ]`，对勾/叉号/圆点改为文案），并在 `scripts/test-official-skill-bundles.mjs` 里加了守卫——但守卫只覆盖**套装成员**，不在套装里的上架技能没扫。
- **什么条件下必须还**：新增套装（会把更多技能纳入守卫范围）时自然推进；或按原债务文档专项排期一次性清完。
- **关联**：[doc/debt.platform.md](./debt.platform.md)

### D5 套装体积无上限

- **是什么**：`pm-starter` 当前 10 个技能 24 个文件，体积很小。但成员增加后没有任何体积告警或上限。
- **什么条件下必须还**：单个套装超过 5 MB 时。可在打包脚本加一条阈值断言。

### D6 vendored 技能的 emoji（已偿）

- **原状**：`ui-ux-pro-max` 从技能生态安装而来（非本仓库原创），其 `data/*.csv` 与 `scripts/{design_system,search}.py` 带有上游作者写的 emoji。曾以「vendored 不宜改写、改了上游升级就冲突」为由加进禁 emoji 守卫的豁免清单。
- **为什么改了**：豁免本身就是问题。规则 §0 是绝对规则，开一个「这个可以豁免」的口子，下一个 vendored 技能就会照着援引。
- **怎么还的**：直接去 emoji（状态符号改文字分级 `[OK]`/`[NO]`/`[CAUTION]` 等），校验 CSV 列数未变、`py_compile` 通过，然后**删掉守卫里的豁免机制**。现在 23 个可分发技能 82 个文件零豁免全扫。
- **遗留成本**：上游升级该技能时需要重跑一次去 emoji（不是冲突，是重做一遍替换）。这个成本比留一个规则缺口小。
- **本次已做**：`scripts/test-official-skill-bundles.mjs` 的 emoji 正则下界从 `U+1F300` 放宽到 `U+1F000`（此前漏掉 `U+1F198` 这类字符，导致 `acceptance-checklist` 两个 reference 文件的 emoji 标题混过守卫），并修掉了那两处。
- **二次补漏**：自测的 emoji 遍历此前只扫 `.md/.txt/.json/.ya?ml`，脚本文件不在范围内，于是 `create-visual-test-to-kb/scripts/harness.mjs` 控制台输出里的两处 `U+26A0` 一路混到分发包。遍历已扩到 `.mjs/.js/.ts/.py/.sh`，那两处改为文案 `[警告]`。真验证方式是从分支预览下载 qa-starter 真解压再全量扫，纸面 review 看不出来。

### D7 下载计数去重只在进程内存里

- **是什么**：下载端点（fork）改匿名后，`SkillDownloadCounter` 按「技能 + 调用方（登录取 userId、匿名取 IP 哈希）」做 10 分钟窗口去重，挡住单个客户端循环刷 `DownloadCount`。但去重表在进程内存，多实例部署时每实例各一份，分布式调用方仍可绕过。
- **为什么欠着**：真正的按 IP 限流是横切能力，不该塞进一个 controller；而本次要挡的是「一个客户端每分钟刷几百次」这种最廉价的滥用，进程内去重已经够。
- **什么条件下必须还**：热度榜单出现明显异常，或决定把 DownloadCount 用于对外排名/结算时。做法是换成 Redis 计数或在网关层做按 IP 限流。
- **不还的后果**：分布式调用方仍可缓慢抬高某个技能的热度排序。
- **补充（同轮 review 追加）**：去重的「查了再写」两步已用一把锁合成原子操作——此前并发重放能让每个请求都读到「没命中」，去重形同虚设，而并发正是这个闸要挡的形态。匿名指纹的取值口径见 D8。

### D8 防滥用分桶的信任模型：反代必须与服务同网

- **是什么**：限流分桶与下载去重都用 `HttpRequestExtensions.GetAbuseControlClientIp` 取调用方 IP。它只在 **socket 对端是回环 / 私网 / 链路本地**（即我方反代，Nginx + Docker 的实际拓扑）时才采信 `X-Real-IP`；对端是公网地址时一律回落 `RemoteIpAddress`。
- **为什么是这个形状**：这条路径上有两个方向相反的坑，都踩过。
  - 裸用 `RemoteIpAddress`：生产取到的是反代共享地址，所有匿名访客共用一个 600 RPM / 100 并发的桶，一个忙碌客户端能让所有人 429。
  - 无条件采信 `X-Real-IP`（即 `GetRealClientIp` 的语义，那条是给展示 / 统计用的）：Kestrel 直连暴露或反代不覆盖该头时，调用方每个请求换一个头值就换一份新配额，限流等于不存在。
- **已知取舍**：反代若部署在**另一台公网主机**上（云 LB 走公网回源），对端是公网地址，分桶会退化成「按 LB 一个桶」——回到共用桶的老问题。这是有意选的：分桶宁可粗，也不能被调用方自选。
- **什么条件下必须还**：真出现「反代在公网另一侧」的部署形态时。做法是引入运维提供的可信代理 CIDR 清单（`KnownProxies` / `KnownNetworks`）或全局 `UseForwardedHeaders`，代码无法自行推断这个清单。
- **不还的后果**：该形态下匿名限流粒度过粗，一个忙碌客户端仍能影响同 LB 后的其他人；但不会出现「配额可绕过」。
- **守卫**：`RateLimitClientIdGuardTests` 钉住两个方向都不许回潮（既不许裸 `RemoteIpAddress`，也不许 `GetRealClientIp`），并覆盖下载去重这个同源处；`SkillDownloadCounterTests` 有「对端是公网时不采信 X-Real-IP」用例。

### D9 技能包回源只校验档案魔数，不校验完整性

- **是什么**：CDS 两条回源路径（`skill-proxy` 取 zip、`bootstrap` 的 `UpstreamSkillPackCache` 取 tar.gz）在落盘 / 入缓存前只检查魔数（`PK\x03\x04` / `\x1f\x8b`），不解析中央目录、不校验哈希。
- **为什么加这一层**：不校验时，网关故障期常见的「200 + HTML 错误页」会被当成技能包写进十分钟缓存——客户侧解不开，而且**上游恢复了也没用**，得等缓存自己过期。魔数足以认出「根本不是档案」这一类。
- **没覆盖什么**：截断的 zip / tar.gz 同样以正确魔数开头，这里认不出来，由客户侧 `unzip` / `tar` 兜底报错（不会被误当成成功）。
- **什么条件下必须还**：给引导脚本补校验和或签名时一并做（见「后续事项」P2），届时哈希校验会同时覆盖完整性与来源可信。
- **守卫**：`skill-proxy.test.ts` 覆盖两条路径各自拒收错误页、磁盘坏缓存自愈、上游恢复后免等 TTL。
