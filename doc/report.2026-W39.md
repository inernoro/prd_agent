### 必须点名的五条

**1）通过率跌到 11.1%，但这是好事的副作用，不是坏事本身。**
把两个数放在一起看：上周 25 个落地 PR、**7 份**归档验收（通过率 28.6%），且没有一份是「PR 验收」这一档；本周 54 个落地 PR、**18 份**归档验收（通过率 11.1%），其中 11 份是逐 PR 的、覆盖 7 个 PR。
**两周的通过率不能直接比**：上周那 7 份对不上具体 PR（本报告核不出它们各自验的是哪个 PR），本周这 18 份里至少 11 份对得上。**分母不同质，所以「28.6% 掉到 11.1%」不能读成质量下滑**——但也别反过来当成「覆盖变广了」的证据，那需要能把上周那 7 份映射到 PR 才能成立，本期做不到。
再看 18 份的构成：**12 份「有条件通过」**——意思是功能能用，但作者把已知边界写下来归了档（本周新入账的边界条目集中在 09-25 那一批 `docs(debt)` 提交里）。2 份「通过」、4 份「未通过」。
**判断这周质量的正确读法不是 11.1%，是「4 份未通过分别是什么」**——下面三条就是。

**2）本周头号能力的端到端验收未通过。**
09-25「功能验收 · 网页托管 / 验收-A3 OpenDesign 精细设计：会议纪要到可分享网页（真实环境端到端）」结论 **fail**。
这条要讲清结构：这条链路被拆成八件事分别落地、分别验收，**分段的结论大多是「有条件通过」，整条串起来跑那一次是「未通过」**。同一天另一份「验收-B OpenDesign 直连设计执行服务（PR #1618）」是有条件通过——**B 段通了，A3 整条没通**。
**这不是「差一点」，这是这条链路目前最准确的状态**：八个零件都能动，装起来跑不到终点。它比任何一份分段验收都更说明本周的实际交付水位。
**下一步**：复验 A3 到出一个「通过」或「有条件通过」为止，并在报告里写清上一次卡在哪一段——本周的报告里没有这句话。

**3）核心业务稳定冒烟连续两周未通过，而且重复归档第三次发生。**
09-26 两份「发布验收 · 核心业务稳定冒烟」，**同日、同标题、同档位（L0）、结论都是未通过**。上周周报已经就「同日同标题重复归档」点过一次名，本周从 1 对变成 3 对（另两对是 #1623 与 #1624 的 PR 验收各两份）。
两件事要分开处置：**冒烟未通过**是业务问题——W38 的 P1 要求「修完之后跑一次出结论的冒烟」，这件事做到了，**结论是未通过**，所以那九项根因至少没有全部修好；**重复归档**是归档链路的问题——同一个 dailyDate + 同一个标题 + 同一个档位进了两条，说明归档那一侧没有去重判据。后者不修，通过率这个数会长期被注水或稀释，谁都不知道该信哪一份。

**4）没有 PR 号的主干提交从 7 涨到 23（同一口径重算）。**
**先把口径钉住**：按**提交的父提交个数**分（不按标题措辞猜），本周主干第一父链 79 个提交拆成四类，四类相加正好 79：

| 类别 | 条数 | 说明 |
|---|---|---|
| 有 PR 号的合并提交 | **46** | 正常的 PR 合并 |
| 有 PR 号的线性提交 | **8** | squash 合并 |
| **无 PR 号的线性提交** | **23** | 落在第一父链上、标题里没有 PR 号的那一档（**只是「没有 PR 号」这个可观测量，不代表没走评审**，见下） |
| 无 PR 号的合并提交 | **2** | 标题不含 PR 号的手工合并（`fix(llmgw): 合并手机模型列表布局与回归修复`、`merge: 合并文学MCP图文创作与私有归档修复`） |

46 + 8 = 54，正好等于附录 B 的 PR 总数，两边对得上。
那 23 个无 PR 号的线性提交里，**5 个是每日熵减的自动提交**（按设计如此），其余 18 个是 09-21 与 09-22 两天集中直落的修复（生图路由监控、自监控抖动、预览镜像复用、旧镜像假健康等）。
**两条限定**：① 从提交本身分不出「直推主干」和「快进合并的分支」——两者在第一父链上长得一样，所以准确说法只能是「**没有 PR 号**」。② **无 PR 号的合并提交单独一类，不并进上面那 23 个**——它们确实走了分支，只是标题没写 PR 号。
**不要再往前推一步**：快进合并的分支同样可能是走过 PR、评审过之后才落地的，所以「没有 PR 号」**证明不了「没有经过评审」**。本报告只报这个可观测量，不报评审有无——要断言后者，得把这 23 个提交逐个去比对真实的 PR 记录，本期没做。
**和上周比要小心**：上周报告印的是「只有 1 个直推主干」，那个数用本报告的口径复现不出来（上周统计的是全部 341 个提交而非第一父链，且未写明判据）。所以本行两周都由本报告按同一定义重算：**W38 = 7，W39 = 23**。回退是真的，但幅度是 7 → 23，不是 1 → 24。
上周把这个数从 32 压到 1 并写成了流程改善的亮点，按同一口径重算其实是 7，**本周涨到 23**。这个指标一周之内来回跳，说明它衡量的更像是「那一周的提交习惯」，而不是流程本身变了；**它只说得清有没有 PR 号，说不清有没有走评审。**

**5）09-17 那条到期线，连续第四周顺延，本周零触及。**
数据面上很干净：本周 356 个提交里，`grep` 不到任何一条涉及认证豁免、存量库或那个逃生阀的提交。W38 把这条从「给个结论」升级成「要一条会变红的判据」，**结果连那条判据也没建**。
它在 W35 排 P1、W36 升 P0、W37 再排 P0、W38 再排 P0，四周零动作。按「卡死熔断」那条规则的判定，**同一份优先级被重写四次而状态未翻转，本身就是信号**——所以本周不再原样第五次顺延，而是把它改成一个需要有人拍板的问题（见下周优先级 P0）。

### 能力 1：一份会议纪要，现在能直接变成一个可分享的网页——而且是本系统自己直连设计服务，不再借道部署平台的会话

**谁受益**：任何需要把一份资料对外发出去的人（产品、运营、售前）；以及未来想把设计执行能力单独接出去的外部团队。

**现在**：本系统按一份固定契约**直连独立的设计执行服务**，旧的会话路径保留成一个可回退的开关。同批还带上了网页的 AI 改版与版本回退。
**证据**：**有条件通过**（09-25「验收-B OpenDesign 直连设计执行服务」，L2 档）。但**整条端到端的 A3 验收未通过**——见质量闸第 2 条。
