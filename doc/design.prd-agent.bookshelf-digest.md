# 公共藏书阁 · 精读稿 · 设计

> **版本**：v1.0 | **日期**：2026-09-16 | **状态**：已落地

**一句话**：藏书阁的书页为什么要系统产出内容而不是让用户填，以及那篇稿子凭什么判断"还新鲜"。
**谁该读**：接手藏书阁的工程师；想给别的模块复用这套"按需生成 + 内容指纹"的人。
**读完能做什么**：说清一篇稿子从触发到落库经过哪几道判据，改了书目或规则之后哪些会自动重写。

---

## 为什么要有这一层

改版之前，点开一本书看到的是书名、作者、一句收获，外加一个让用户自己写心得的输入框。
用户的判词是：「你这个页面的内容，没有学习，用户点两下，什么内容都没有，没有文章，
点进去就是让用户输入，什么意思？用户提供内容？」

问题不在交互，在于**里面本来就只有索引、没有内容**。所以这一层的定位是系统产出：
第一个点进这本书的人触发生成，写完落库，之后所有人读同一篇。

稿子不是书摘——书摘网上到处都是，没有理由放在这里。它唯一不可替代的是第三段
「我们在哪儿栽过」：这本书的主张，对上团队自己写下的规则和真实事故。原料是团队自己那 60 条架构规则里带事故记录的那 40 条。

## 四层存储，权属各不相同

这是接手时最容易搞错的一件事——同一个功能的数据散在四个地方，生命周期完全不同。

| 层 | 存的是什么 | 存在哪 | 跟着什么走 |
|---|---|---|---|
| 1 | 书目与「这本书对上哪几条规则」的映射 | 前端的书目常量（策展静态数据） | git，改它要发版 |
| 2 | 喂给模型的材料 | 一份 JSON，以内嵌资源编进后端程序集 | 镜像 |
| 3 | 生成出来的稿子 | MongoDB 的 `book_digests` 集合 | 数据库 |
| 4 | 用哪个模型 | 网关侧的模型池与调用方绑定 | 部署，不在代码里 |

第 2 层由一个测试从第 1 层加规则目录生成——它既是生成器也是守卫，改了源头不重新
生成它会红。

**为什么材料要编进 dll 而不是让前端随请求发过来**：稿子是公共内容，所有人读同一篇。
上下文可篡改就等于任何登录用户都能往公共内容里注入任意 prompt。

**第 3 层是共享的**：同一个 CDS 项目下所有分支预览共用一个库，这条分支生成的稿子
兄弟分支点进去会直接读到（见 `cross-project-isolation` 通道 4）。

**第 4 层不随代码走**：换一个部署环境要重配一次模型池绑定，代码里翻不到。

## 一篇稿子还"新鲜"吗：两维判据

判据是 `BookshelfDigestPrompt.IsFresh(digest, material)`，两维都得对得上：

1. **提示词版本**（`PromptVersion`）——管 system prompt 那一半，改了文案就升版号
2. **材料指纹**（`MaterialFingerprint`）——管材料那一半

只有第一维时有个会静默发生的退化：第三段整段来自这本书挂的 `relatedRules`，给它
改挂一条规则、或者规则正文本身改了，提示词一个字没动、版本号照旧，于是库里那篇用
旧材料写的稿子会一直被当成新鲜的端给读者——第三段和当前挂的规则对不上，还没有任何
东西提示它过期。

### 指纹为什么直接对 user prompt 算

`ComputeMaterialFingerprint` 的实现是 `SHA256(BuildUserPrompt(material))` 取前 16 字节。

不挑几个字段拼起来算，是因为 user prompt 就是真正喂给模型的全部材料，一个字不多
一个字不少。手工列字段的写法会在「将来给 user prompt 加一节材料」时静默漏掉——判据
读的值和真正生效的值分了家，那正是 `predicate-and-wiring-discipline` 形状 6 说的那种错：
判据确实读到了一个真实存在的值，只是那不是系统实际用的那个。

指纹不是防篡改用的，只需要「材料变了它几乎必然跟着变」，所以截断到 32 个 hex。

### 判据只此一处

取稿（`GetDigest` 的 `stale`）与生成（SSE 复用分支）走的是同一个函数。两边各写一遍
就是形状 3：同一个判断分裂成两份，改一处忘一处，于是接口说「这篇旧了」而生成那边
照旧复用，或者反过来。

### 已知的代价

升一次提示词版本、或者批量调整 `relatedRules`，所有已生成的稿子都会在下一次点开时
重烧一篇。51 本书、内部工具，这个代价小于「留着旧材料写的稿子还得靠人记得哪些该重生成」。

存量文档没有 `MaterialFingerprint` 字段，一律当过期处理。

## 第三段的硬约束

这一段是整篇稿子的价值所在，也是最容易出事的地方——**编一条假事故比没有这一段糟得多**，
读者会照着去仓库里翻，翻不到，整篇的可信度就没了。

所以提示词里钉死两条：

- 第三段只能用给定的规则材料，材料里没有的事故一个字都不许编
- 材料不足以支撑时，直说「这本书还没有对上我们自己的事故记录」然后收尾，
  不要用泛泛的行业案例凑数

实测两种极端都守住了：《深度学习》有意不挂任何规则，第三段整段只有那一句；
《动手学深度学习》挂的两条里有一条没有事故记录，模型把规则要求讲清楚、与书的观点
接上，然后明确说「就『我们当时怎么栽的』这一项而言，这本书还没有对上我们自己的事故记录」。

## 书目挂规则的三条下限

`relatedRules` 决定第三段的厚度（挂几条写几节），逐本填时守的是：

1. **每本至少挂一条带真实事故的规则**——全挂纯原则式的那 20 条，第三段只能空转在原则上
2. **没有两本书挂一模一样的组合**——撞车会让两篇稿子的第三段写得雷同
3. **对不上就留空**——硬凑不相干的比留空更糟

当前：50 本已填（44 本两条、6 本三条），1 本有意留空，共引用 42 条规则。

守卫钉住其中可机械判定的部分：填的每个规则名都必须对应一个真实存在的规则文件
（最常犯的错是把「技能」当成「规则」），且同一本书不重复。第三条「对不上就留空」
判不了，靠人。
