> **版本**：v1.3 | **日期**：2026-08-05 | **状态**：三个阶段全部上线灰度；工具已真实跑通，模型自主调度待运行时就绪

## 管理摘要

- **问题**：平台有十几个各司其职的智能体，唯独没有一个「打开就能聊」的通用入口。用户问「你们这么多智能体，我想随便聊聊、聊着聊着让它出张图、再把结论存下来，去哪儿」，答案是没有。
- **决策**：新增一个通用对话入口。**对话循环直接用官方智能体套件，我们一行循环代码都不写**；平台侧只做四件适配：会话与消息、事件翻译、三把工具的实现、页面。
- **价值**：三个用户诉求一次答完——有地方对聊、对话里能生图、结果能沉进知识库。同时用范围契约和熔断线把「过度开发」钉死。

## 先把四个东西分清楚

这四个名字经常被混着讲，其实职责完全不同。分不清就会以为「又要自己造一个智能体框架」。

| 名字 | 它是什么 | 跑在哪 | 对外域名 | 本次动它吗 |
|---|---|---|---|---|
| 平台主体 | 就是大家天天用的这套系统，后端加管理前端 | 主服务容器 | 有 | **新增**：对话页、对话接口、事件翻译、三把工具。本次写的代码全在这里 |
| 智能体运行时 | Agent 的大脑，内核是**官方智能体套件**，循环与上下文管理都是它自带的 | 独立容器，只在内网，与主服务是邻居 | 无 | **复用**，不改它的内核代码 |
| 模型网关 | 管模型池、调度与调用日志的那一层，已有一个与模型厂商原生格式兼容的入口 | 独立容器 | 有，独立子域 | **复用**，把运行时的模型出口指过去 |
| 部署平台 | 负责把上面这些编排进分支预览 | 平台自身 | 有 | 不动 |

还有一个容易混进来的：**面向工程的那个基础设施运维功能**。它是**一个功能**，不是一个部件——它用上面那个运行时去做运维操作。用户抱怨的链路长、要二次认证、延迟高，来自**那个功能的部署姿势**（把运行时放进分支预览、隔着好几层往回打），不是运行时本身的毛病。

**本次复用运行时这个部件，不使用也不改动那个运维功能。**

## 为什么现在做

三个诉求来自真实提问，且都指向同一个缺口：

1. 「有没有类似聊天功能的智能体，我该在哪用」——缺的是**入口**，不是能力。
2. 「能不能对话里生图、能不能持久化到知识库」——两者都已是成熟能力，缺的是**接到对话里**。
3. 「不要过度开发，别又搞成一坨」——缺的是**明面上的边界与熔断机制**。

前两条说明技术风险很低（复用远多于新增），第三条说明真正的风险在工程纪律。

## 写与不写的分界线

这是本设计最重要的一条，比任何技术细节都重要。

**别人写好的，直接用，一行不碰**：对话循环（什么时候继续问、什么时候收尾）、上下文管理（历史怎么裁怎么压）、工具调用协议（模型怎么声明要用工具、结果怎么回灌）、流式事件协议、轮数上限与超时取消（都是传给运行时的参数）。

**我们只写这四样**：会话与消息的存储和断线续订（复用平台已有的任务与事件流）、把运行时事件翻译成页面上的消息与工具卡、三把工具的实现（各自转发给已有的出图与知识库能力）、对话页面本身。

**永远不写**：自研对话循环、自研智能体套件、自研工具调用协议。这不是本期不做，是永远不做；出现即熔断。

## 官方与自建的边界（逐层说清，别让「官方套件」四个字盖住自建部分）

「用官方套件」不等于「整条链路都是官方的」。这张表把每一层的归属摊开，避免读者高估集成程度。

| 层 | 归属 | 说明 |
|---|---|---|
| 模型调用客户端 | **官方套件** | 与模型厂商的协议对接由套件负责 |
| 对话循环 | **官方套件** | 何时继续问、何时收尾、上下文怎么裁，全是它的行为 |
| 工具调用协议 | **官方套件** | 模型如何声明用工具、结果如何回灌 |
| 取消与超时 | **官方套件** | 我们只传参数，机制是它的 |
| 运行时传输层 | **本仓库自建**（既有） | 把套件包成一套流式接口供平台调用，本次不改 |
| 工具执行桥 | **本仓库自建**（既有） | 套件要用工具时回调平台，本次不改 |
| 审批与审计 | **本仓库自建**（既有） | 阶段一零工具，未走到这一层 |
| 工作区与仓库工具 | **本仓库自建**（既有） | 通用对话显式关闭，不使用 |
| 运行时实例池与生命周期 | **本仓库自建**（既有） | 由部署平台的共享运行时服务提供 |
| 会话与消息、事件翻译、页面 | **本次新增** | 这四样是本次唯一新写的代码 |

结论一句话：**对话的智能行为是官方套件的，把它接进平台的那层管道是本仓库既有的，本次只在最外面加了一层薄适配。**

## 砖已经都有，缺的只是一条装配线

| 能力 | 现状 | 本次怎么用 |
|---|---|---|
| 智能体运行时 | 已有独立容器，内核是官方套件，已有流式事件协议与工具桥 | 对话循环全交给它 |
| 任务队列与事件流 | 已有，服务端跑完、客户端断线可续订 | 对话的每一轮就是一个任务 |
| 工具注册与反向调用 | 已有，运行时要用工具时回头调平台 | 三把工具注册进去 |
| 出图流水线 | 已有，产物落素材库 | 出图工具转发给它 |
| 文档空间 | 已有，含权限与分享 | 写入与检索两把工具的落点 |
| 模型网关 | 已有独立部署，且已有与厂商原生格式兼容的入口 | 运行时的模型出口指向它，模型池与调用日志自动生效 |
| 知识库工具 | 已有（搜索、读取），原先只认基础设施 Agent 会话 | 解耦用户身份后直接复用，一行没重写 |
| 消息渲染组件 | 已有 | 前端直接复用 |

因此新增部件只有两个：对话接口层与事件翻译层。这是本方案敢承诺「不会变成一坨」的物理基础——可写的代码本来就不多。

## 数据怎么流动

一轮对话的完整生命：用户在页面说一句话，主服务校验登录态后建任务并入队，入队时盖部署作用域标记；主服务把这一轮连同历史、三把工具的定义、轮数上限一起交给智能体运行时；**运行时里的官方套件自己跑循环**——问模型、判断要不要用工具、回灌结果、决定要不要再问；要用工具时它通过已有的工具桥回头调平台，由平台执行并返回；运行时把流式事件吐回主服务，主服务翻译成消息与工具卡、按序号落库并推回页面；页面刷新或换设备回来按序号续订，内容不丢。

四个鉴权点，没有一个是新发明的：

- **页面到主服务**：用户当前登录平台的那把凭据，不发第二把钥匙。
- **主服务到运行时**：运行时的内网令牌。这一跳是同一个容器网络里的邻居调用，不出机房、不经公网、用户不需要再认证一次。
- **运行时到模型网关**：网关的服务密钥，用户看不到也不需要知道。
- **工具回调读写数据**：沿用发起这次对话的人的身份，权限不放大。

失败一律显式：模型失败、运行时不可用、工具失败、轮数超限，四种情况都在页面转红并写清原因，会话不中断、可就地重试，且不留半截数据。用户中途离开不取消任务——沿用平台既有的服务端权威原则。

## 关键取舍

**取舍一：为什么用现成套件而不是自己写循环。**
对话循环看起来简单（问模型、调工具、回灌、再问），真正难的是上下文裁剪、工具调用的边界情况、流式与取消的正确性、以及长期跟进模型厂商的协议演进。自己写就要长期养这套东西，最后必然变成一个没人敢动的私有框架。用现成套件，这部分的维护成本是零。

**取舍二：为什么复用现有运行时容器，而不是因为「那个运维功能不好用」就绕开它。**
运行时本身是健康的：官方套件内核、流式协议齐全、工具桥已经在跑。不好用的是那个运维功能的部署姿势。换个姿势（放在主服务隔壁的内网、一跳就到）问题就不存在。为了躲开一个功能的毛病而重造一个运行时，是典型的因噎废食。

**取舍三：为什么模型仍然走自家网关。**
官方套件允许把模型请求指向任何格式兼容的地址，而网关正好已有这样一个入口，且带模型池路由与调用日志。于是「用别人的套件」和「模型仍归自家网关管」不矛盾：套件负责怎么思考，网关负责用哪个模型、记什么账，两边都不用为对方改代码。

**取舍四：为什么首版只开三把工具。**
用户提的三个诉求，这三把正好一一对应。多开一把就多一层权限收敛和错误路径，收益要等真实使用才知道。

**取舍五：为什么另起一套会话记录。**
现有会话结构绑着产品需求解读的角色概念，混进通用对话会互相污染。新开一套的成本远低于日后解耦的成本。

## 明确不做（本期承诺）

联网搜索与网页抓取、上传文件解析、自定义人设与角色市场、跨会话长期记忆、把工具箱内全部能力一次性接入、改动任何现有表结构或鉴权。以上六条进技术债务台账，等真实反馈到位后再排优先级。

**另加一条永久性的**：自研对话循环、自研智能体套件、自研工具调用协议——不是本期不做，是永远不做。

## 熔断线

命中任意一条立即停止推进并升级给决策者：

- 出现任何自研对话循环、自研套件、自研工具调用协议的代码。这条是红线中的红线。
- 改动伸进了智能体运行时的内核，而不是只加适配与配置。
- 连续八个提交没有新增可用功能，只在改文档、脚本或计划。
- 工具数量超过三把，或出现「顺手把某某也接上」的提议。
- 改动触碰到那个基础设施运维功能、分支预览的运行时部署、或任何鉴权代码。
- 改动行数超过第一轮基线的两倍，或文件范围扩出第一轮清单。
- 同一份计划被重写五次以上而卡点未消失。

## 验收标准

十一条判据，每条都由决策者本人、管理员或评审亲自核，不接受作者自述：

1. 连问三轮，第三轮引用第一轮的内容，它接得住。
2. 干活途中刷新或关闭页面，回来内容齐全、任务照跑完。
3. 说「画一张横版海报」，等到底，**图真的显示在对话里**；停在进度条上不算。
4. 说「记进知识库」，点它给的链接能打开，内容就是刚才那段。
5. 新开会话问上一步存过的事，答得出来且标了可点开的出处。
6. 页面上指定的模型，与网关调用日志里实际跑的模型一致。
7. **改动清单里没有任何自研循环代码**——搜不到「问模型、调工具、回灌、再问」这类实现。
8. 智能体运行时内核、那个运维功能、鉴权，三者一个字未碰。
9. 白天与黑夜两套皮肤各截一张图，均不破版。
10. 任一超过两秒的等待，屏幕上持续有内容变化，不是静止的转圈。
11. 故意触发一次失败，页面转红、写清原因、会话仍可继续。

**不算数的证据**：接口返回成功、测试全绿、通读自审、旧版本截图、以及截图里还在加载而文案写「已完成」。

## 当前状态

三个阶段全部实现并部署到灰度：对话页、会话与消息、事件翻译、按序号续订的事件流、后台轮次执行，
以及四把工具（出图、写知识库、搜知识库、读知识库）。

**已在灰度环境真实跑通的**：

- 对话骨架：建会话、发消息、任务入队、后台执行、事件翻译、事件流按序补齐、空闲即收流不白挂、
  失败转红且文案是人话、失败后会话不卡在「进行中」、刷新等价路径拿得到完整记录。
- 四把工具：从工具桥端点逐一实调。存笔记真的建出了条目并给出可打开的深链；
  检索真的搜得到刚存的那条；读取真的把正文取了回来、内容一致；
  出图真的产出了图、落进素材库、给出可访问的地址。

真实跑一遍逮到两个编译器与单测都发现不了的缺陷：一轮的提问与回答同刻插入导致排序不稳定，
实测出现「回答排在提问前面」；以及发完消息后没有任何事件流在听，增量到不了页面。两个都已修并复测通过。

**两条尚未验证，如实记下来**：

1. **模型自主调度工具**。灰度环境的 agent 运行时池没有任何运行中的实例
   （授权正常，共享运行时服务没跑起来），所以「模型自己决定该用哪把工具」这一步跑不到。
   工具本身已逐把实调验证，缺的只是决定权那一环。这是外部输入，不是本次改动的缺陷——
   同环境下既有的工程对话入口同样不可用。
2. **出图的画面质量**。出图链路全通，但灰度环境的生图模型池命中的是占位模型，
   产出的是占位图而非真实作画。链路是真的，画笔是环境配置决定的。
   换成真实生图模型后代码无需改动。

**自审 PR 时补掉的四处判据缺陷**（都属于「编译过、测试绿、通读也挑不出」那一类）：

1. 工具失败被画成完成——工具桥失败回传的是一句纯文本原因，不是带 `success` 字段的 JSON，
   而失败标记此前根本没进事件流。成败改认运行时给的失败标记，取不到时报「不知道」而非默认成功。
2. 工具名判据取错了值——官方套件把工具挂在内置 MCP server 下，回传名字带前缀，
   四把工具的标签与阶段全部静默落进兜底分支。分派前统一剥前缀。
3. 新建会话即发送时，用户自己那句话会被切会话的副作用当场抹掉（新会话服务端还没有消息可拉回来）。
4. 硬杀会把会话永久卡在「在跑」——停机时在跑的轮次没人等它把收尾写完，硬杀更是完全没机会。
   停机改为等收尾写完，启动再做一次收敛把上个进程留下的轮次判死。

**已知边界**：启动收敛按「早于本进程启动」判定上个进程的遗留轮次，
成立的前提是一个部署作用域只跑一个实例（当前部署形态如此）。
真要横向扩容，这里必须换成心跳过期收割。

## 分阶段与退出

三个阶段，每个阶段独立可验收、独立可停：

- **阶段一 纯多轮对话，零工具**。页面、转发与事件翻译、事件流、断线恢复。循环直接交给运行时，这一阶段一行循环代码都不写。判据一、二、七至十一可验。
- **阶段二 挂上出图**。工具卡交互在这一阶段定型：执行中给阶段名与进度条，完成后图片就地展示。判据三可验。
- **阶段三 挂上知识库读写**。写入、检索、读取配套上线，存得进去也查得出来、点得开。判据四、五可验。

三个阶段已全部落地。工具一共四把（出图、写知识库、搜知识库、读知识库），
其中写与搜/读是同一件事的两半，按范围契约合并计为一把，未越过「三把」那条红线。

退出方式：关掉入口权限，入口立刻消失且不影响他人；不改现有表结构，回滚无需数据迁移；不改现有鉴权，回滚不影响他人登录；新数据在独立集合里，彻底清理就是删一个集合。运行时容器本来就在跑，回滚后它照常服务原有调用方。
