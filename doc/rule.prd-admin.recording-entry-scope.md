# 录音链路：换一条录音要放掉什么

**一句话**：录音三屏是「同一条路由换参数、组件被复用」，凡是绑在某一条录音身上的状态都必须显式放掉，否则上一条的值会挂在新录音上，而且失败时永久留着。
**谁该读**：改录音采集 / 处理 / 结果三屏，或往这条链路加任何异步取值的人。
**读完能做什么**：知道新增一格状态时要不要给它加复位、令牌什么时候才准推进、锁该有多大作用域。

## 为什么要有这一条

这条链路上同一类缺陷被逐条指出来过八次以上：音频地址、run、失败说明、通知追踪、
标题与库名、整理锁、跟读组件里在飞的问答与编辑草稿、时长（时长一项就在三屏各犯一次）。
每次都是一格一格补，补完下一轮又漏一格。根因不是粗心，是**没有约定**：
这几屏靠 `entryId` 换参数而不重挂，React 复用组件，于是「谁负责在什么时候把状态放掉」
没有落到任何一处。

后果不只是显示错一个数：跟读组件那一次是 A 还开着的编辑框一保存，走的是 B 的写回、
写进去的是 A 的草稿，**直接改坏 B 的原文**。

## 三条约定

### 1. 绑在录音身上的状态，换条目就放掉

判据是一句话：**这格状态的值，换一条录音之后还成立吗？** 不成立就必须复位，
而且复位要排在**发起新请求之前**——排在后面等于没清。

典型的「绑在录音身上」：地址与元信息、进行中的任务与它的失败说明、由播放器广播上来的
时长、通知/提醒类的追踪位、在飞的流与它的草稿。

状态多到一格格清容易漏时，**换成让组件按录音重挂**（给它一个认这条录音的 key）。
跟读组件走的就是这条——它内部绑录音的状态最多，一次重挂比逐格复位可靠。
代价是播放位置回到开头，而换录音本来就该从头开始。

### 2. 版本令牌只在「内容真的换上了」之后推进

拿「上一次写入返回的时刻」当乐观并发的基线时，令牌与屏幕上的内容必须同进同退。
条目查到了、正文没取回来（或正文让位给了本机草稿）就推进令牌，会留下
「屏幕是旧文字、令牌指向新版本」的错配——用户接着离线改这段旧文字，基线一比「一样」，
补传就把新内容整篇盖掉，全程没有冲突提示。

同理，比较两个时刻要**按时刻比**，不要按字符串比：写回响应与读回来的值可能来自不同精度
（库里是毫秒，内存里是 100ns 刻度），字符串相等会把同一个时刻判成两个，变成一条
必然发生的假冲突。

### 3. 锁要认「哪条录音」，也要认「哪一发」

只用一个布尔当「正在发起」，两种方向都会坏：不认录音会跨录音卡住（A 的请求在飞，
B 上点什么都没反应）；认录音但靠「换条目就清零」补救，A 的收尾后到会把 B 刚举起的锁放掉，
B 再点一下就并发起第二条任务——两条都花模型钱，还抢着覆盖同一份产物。

正解是锁里存「哪条录音」，释放时再比一次「这一发还是不是最新那发」。

## 自查

新增一格状态或一条异步取值时，逐条问：

- 换一条录音之后这个值还成立吗？不成立 → 加复位，且排在发起新请求之前。
- 这一格是不是「一格格清早晚要漏」？是 → 让组件按录音重挂。
- 我推进的令牌，与屏幕上此刻显示的内容是同一份吗？
- 我加的锁，跨录音时会不会卡住别人、或被别人的收尾放掉？
- await 回来之后动状态之前，认过「我还在当初那条录音/那条笔记上」吗？
