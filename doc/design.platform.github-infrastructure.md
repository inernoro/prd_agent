# GitHub 基础设施层 · 设计

> **版本**：v2.0 | **日期**：2026-07-31 | **状态**：已落地

**一句话**：把「调 GitHub」做成全平台共用的一层，凭证由各应用自己带，组件只负责调用、解析和错误分类。
**谁该读**：要让自己的功能读写 GitHub 数据的产品与工程师；想知道「授权算谁的」的人。
**读完能做什么**：判断自己的场景该用哪种授权方式，以及哪些能力现成、哪些要新加。

---

## 1. 管理摘要

**目的**：GitHub 的调用能力沉淀成一层公共组件，和大模型网关同级。PR 审查、周报、未来的日报与检测类功能都用它，不再各写各的调用代码。

**三个核心关切**：

1. **不重复造轮子**——PR 审查里那套调用与错误处理是通用能力，不该锁在某一个业务目录下。
2. **授权归各应用自己**——凭证从哪来由消费方决定，组件不关心是谁的账号、怎么拿到的。
3. **零行为回归**——抽取过程对用户完全不可见：接口返回、页面、错误码一个不变。

**不做什么**：不做 AI、不做权限判定（那是接口层的事）、不强制全平台统一账号、不做响应缓存（每次打实网，避免「快照过期」的歧义）。

---

## 2. 为什么是「基础设施」而不是某个业务的一部分

### 2.1 消费方矩阵

| 消费方 | 现状 | 需要的 GitHub 能力 |
|---|---|---|
| PR 审查工作台 | 生产中 | 设备码授权 + 拉取 PR 快照 + 拉取历史（提交、评审、评论、时间线、检查结果） |
| 周报 | 生产中 | 定时轮询拉取提交记录（目前自己写了一套调用代码） |
| 日报 / 其他检测 | 未来 | 可能需要提交、PR、议题、检查结果 |
| 桌面自动更新 | 生产中 | 前端直接查最新发布版本——**不迁移**，它不在后端范围 |

三个后端消费方都要做同样三件事：调 GitHub、解析响应、分类错误。今天只有 PR 审查做得完整。抽成公共层，等于让其余消费方**直接继承同一套质量**：外部地址白名单、响应体积截断、仓库不可见与 PR 不存在的两步区分、限流识别。

### 2.2 和大模型网关的相似与差异

| 维度 | 大模型网关 | GitHub 层 |
|---|---|---|
| 定位 | 大模型调用的统一入口 | GitHub 调用的统一入口 |
| 凭证 | 按调用方标识走模型池三级调度 | 调用方自己带 token 进来 |
| 多供应商 | 需要（不同厂商协议不同） | **不需要**——GitHub 只有一家 |
| 审计日志 | 有独立日志集合 | 暂无，未来可补 |

**结论：借鉴「独立组件」的定位，不继承「多供应商调度」的复杂度。** 不需要适配器、不需要调度器、不需要池子的概念。

## 3. 它对外提供什么能力

组件对外只有两组能力，语义如下（具体方法签名以代码为准，不在此复制）：

| 能力 | 输入 | 输出 | 谁在用 |
|---|---|---|---|
| 拉取 PR 快照 | 访问令牌 + 仓库定位 + PR 号 | PR 元信息，可选带文件清单与关联议题 | PR 审查 |
| 拉取 PR 历史 | 同上，可指定某次提交 | 提交、评审、评论、时间线、检查结果 | PR 审查 |
| 分页取历史切片 | 同上 + 类型 + 页码 | 该类型的一页数据 | PR 审查前端翻页 |
| 发起设备码授权 | 用户标识 | 用户去 GitHub 输入的验证码 + 一个可轮询的凭据 | PR 审查登录 |
| 轮询授权结果 | 用户标识 + 上一步的凭据 | 授权成功后的访问令牌 | PR 审查登录 |
| 查询账号信息 | 访问令牌 | GitHub 账号名、编号、头像 | 绑定后回写用户连接 |

**三条不变的约定**（这是契约，改动要慎重）：

- **每个能力的第一个输入都是访问令牌**——凭证来源无关是整层的地基，见第 4 节。
- **当前全部是只读能力**。将来要写（评论 PR、请求评审）就在同一层追加，不另起炉灶。
- **错误一律走统一的错误类型**，调用方按错误码映射，不靠解析异常文本判断。

> 为什么这里不贴接口签名：签名会随重构变化，人类记不住也不需要记，AI 直接读源码更准。
> 文档只保留「有哪些能力、输入输出的语义、不变的约定」——这些换个语言重写也成立。

## 4. 授权模型：凭证从哪来，组件不管

> 组件**不管**凭证从哪来，只负责**用传进来的令牌调 GitHub**。

这条让三种授权模式天然并存：

| 模式 | 典型场景 | 凭证来源 | 账号归属 |
|---|---|---|---|
| 每用户授权 | PR 审查工作台 | 用户自己走设备码授权，令牌加密存在用户连接记录里 | 每个平台用户一个 GitHub 账号 |
| 每应用令牌 | 周报同步提交记录 | 配置项里的一个全局令牌 | 全应用共用一个账号 |
| 每安装授权 | 未来的机器人场景 | GitHub 应用换取的安装令牌，用时刷新 | 按仓库安装 |

**为什么这样设计**（用户当初的要求原话是「各自 app 也可以单独提起授权，并不需要把授权 GitHub 作为全局唯一，账户也不一样，组件需要剥离」）：

- 组件**不做授权判定**——谁能用这个功能，仍由接口层的登录态与权限点决定。
- 组件**不做凭证存储**——用户连接记录仍归业务侧，某个应用想改用别的方式存令牌，完全自由。
- 组件**不关心账号唯一性**——不同应用可以用不同账号，同一应用内不同用户也可以各用各的。

**安全约定**：访问令牌只在调用时传入，不落日志、不进响应体。

## 5. 错误怎么分类

错误分两层：**通用 GitHub 错误**归本层（所有消费方共用），**业务错误**归各消费方自己。调用方捕获基类即可同时吃下两类，按错误码统一映射。

| 场景 | 状态码 | 语义（给用户看的话术由前端决定） |
|---|---|---|
| 未绑定 GitHub | 412 | 先去绑定账号 |
| 令牌过期 | 401 | 重新授权 |
| PR 地址不合法 | 400 | 地址格式不对 |
| 仓库不可见 | 404 | 没有权限或仓库不存在 |
| PR 号不存在 | 404 | 仓库看得见，但这个号没有 |
| 被拒绝 | 403 | 账号权限不足 |
| 触发限流 | 429 | 带恢复时间，稍后再试 |
| 上游异常 | 502 | GitHub 侧故障 |
| 未配置授权应用 | 503 | 管理员没配 OAuth 应用 |
| 设备码授权失败 | 403 / 408 / 502 | 凭据无效、已过期、被拒绝或请求失败 |

**为什么区分「仓库不可见」和「PR 号不存在」**：GitHub 对无权限仓库同样返回 404，直接透传会让用户以为「PR 删了」。分两步探测后，才能给出「你没权限」还是「号写错了」这两种完全不同的指引。

## 6. 扩展原则

- **每加一个能力必须有真实消费者**，不做投机性空壳（对应「不为假想需求设计」）。
- **周报迁移是独立一步**：它在生产环境定时轮询，风险高于收益，等 PR 审查这条路跑稳再动。迁过去时把调用换成本层能力，业务侧的用户映射与入库逻辑保持不动。
- **第三个同类组件出现前不抽公共基类**。两个（大模型网关 + GitHub）还说明不了规律，三个才算趋势。禁止过早抽象。

可预见的下一批能力：读文件内容（日报与检测用）、列议题（缺陷联动）、评论 PR（AI 自动审查）。检查结果已经覆盖在 PR 历史里。

---

## 7. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 抽取过程改动波及 PR 审查，编译或行为回归 | 中 | 阻断合并 | 一次性替换 + 持续集成必须绿 + PR 审查全流程冒烟 |
| 错误继承关系调整后漏捕获，部分错误退化成 500 | 低 | 用户看到裸错误 | 统一捕获基类，基类覆盖子类 |
| 周报未迁移期间两套调用并存 | 低 | 一致性 | 明确列为下一步，文档与更新记录都留痕 |
| 消费方把访问令牌打进日志 | 中 | 安全 | 本层不记录令牌；消费方的日志配置由各自负责 |
| 演化出「多账号切换」等伪需求 | 低 | 过度设计 | 守住「不做权限基础设施」的边界 |

---

## 8. 验收标准

- PR 审查工作台完整走通：设备码授权 → 拉 PR → 查看历史 → 写笔记，用户可见行为与抽取前一致。
- 各类错误按上表返回对应状态码与错误码，前端提示不变。
- 周报迁移完成后，作为第二个真实消费者验证本层可用性（下一步，不在本次范围）。
