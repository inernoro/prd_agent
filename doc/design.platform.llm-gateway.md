# LLM Gateway 统一调用 · 设计

> **版本**：v2.1 | **日期**：2026-08-13 | **状态**：开发中

**一句话**：LLMGW 统一执行模型请求，但不接管 MAP 的业务选择；故障只能在池内扩散，跨池代选默认禁止。
**谁该读**：使用、维护或评审 MAP 大模型调用链路的人。
**读完能做什么**：说清 MAP、AppCaller、模型池和 LLMGW 的责任边界，并判断一次故障处理有没有越权。

---

## 一、管理摘要

LLMGW 是所有模型请求的统一执行入口，负责身份校验、池内调度、协议适配、限流、预算、健康、日志和审计。MAP 负责用户可见的模型关系、推荐、风险提示和选择体验。

统一入口不等于统一接管业务决策。用户选择了哪个模型池，是 MAP 与用户之间的业务事实；LLMGW 可以在该池内部切换 Provider 或 Offering，但只有 AppCaller 显式授权后，才可以替用户换到另一个模型池。授权默认关闭。

核心不变量：

- 单个 Provider、Offering 或模型池故障不能关闭 MAP 整体能力；
- 模型目录、请求执行、通知和人工恢复是四条独立链路；
- 自动恢复不依赖通知中心，也不依赖合成的付费探测；
- 所有隐式切换都必须可解释、可审计、可回滚。

## 二、职责边界

| 能力 | MAP | LLMGW |
|---|---|---|
| 定义 AppCallerCode 的业务含义 | 负责 | 校验并执行治理配置 |
| 配置 AppCaller 可用模型池 | 提出业务需求 | 保存权威绑定与调度策略 |
| 展示模型名称和选择器 | 负责 | 提供池目录和健康事实 |
| 推荐、排序和风险建议 | 负责 | 不参与业务推荐 |
| 池内成员选择和重试 | 不参与 | 负责 |
| 跨模型池代选 | 允许用户或业务决定 | 仅在 AppCaller 显式授权时执行 |
| Provider 协议和凭据 | 不感知 | 负责 |
| 熔断、半开和恢复 | 不修改状态 | 负责 |
| 站内通知 | 展示、确认和深链 | 产生结构化故障与恢复事件 |
| 页面是否可用 | 负责，局部降级 | 无权关闭 MAP 整体页面 |

## 三、调用流程

一次标准调用由以下阶段组成：

1. MAP 确定 AppCallerCode、用户选择的模型池和业务参数。
2. LLMGW 校验租户、团队、AppCaller 状态、池授权、预算和速率。
3. LLMGW 在所选池内计算主候选和有界重试候选。
4. 发送阶段使用已经确定的决策构造上游请求，不得再次解析并改变模型池。
5. LLMGW 记录每次实际尝试、结果、耗时和健康反馈。
6. MAP 展示用户所选池、实际执行事实和业务建议。

“先算后发”保证选择、预算、日志和发送使用同一决策，避免出现“界面选 A、预算算 A、实际上游发 B”。

## 四、AppCaller 治理

AppCallerCode 是一条业务调用身份，不是模型名称。它至少治理：

- 获准模型池集合和默认池；
- 是否允许跨池代选，默认关闭；
- 允许代选时的候选顺序和临时授权有效期；
- 参数策略、预算、速率、团队和负责人；
- 故障通知接收范围和审计归属。

真实流量只能使用 AppCaller 获准的池。全局默认池与 legacy 配置只用于受控迁移，不能绕过 AppCaller 权限，也不能在显式选择失败后静默接管请求。

## 五、调度与失败语义

### 池内调度

LLMGW 可以在同一模型池内按优先级、权重、顺序或竞争策略选择成员。池内重试只处理可安全重放且属于上游执行失败的请求。

### 跨池代选

跨池意味着用户获得了不同业务模型，必须满足全部条件：

- AppCaller 明确开启；
- 目标池属于 AppCaller 获准集合；
- 请求类型和能力兼容；
- 请求可安全重放；
- 响应和日志公开原池、实际池与代选原因；
- MAP 能向用户说明发生了模型变化。

任一条件不满足时直接失败，不得以“提高成功率”为由越权。

### 错误分类

| 错误类别 | 是否影响健康 | 是否允许池内重试 | 是否允许跨池代选 |
|---|---:|---:|---:|
| 连接失败、超时、429、5xx | 是 | 可安全重放时允许 | 仅显式授权时允许 |
| 用户输入或参数错误 | 否 | 否 | 否 |
| 权限、预算或内容政策拒绝 | 否 | 否 | 否 |
| 用户主动取消 | 否 | 否 | 否 |
| 结果未知的非幂等提交 | 记录未知 | 否 | 否 |

## 六、故障隔离与自愈

LLMGW 以池成员或 Offering 为最小熔断单位。连续受认可的失败使其从 Healthy 进入 Degraded，再进入 Open。Open 状态只阻止该执行目标接收普通流量，不删除模型池，也不改变 MAP 的模型关系。

冷却期结束后进入 HalfOpen，只允许受限的真实业务请求验证恢复。成功后自动恢复，失败则重新 Open 并指数延长冷却。默认不创建 MaxTokens 请求、生图请求或其他合成付费探测。

同一池仍有健康成员时继续池内调度；整个池耗尽时严格遵守 AppCaller 的跨池授权。所有池不可用时返回结构化错误，但目录、控制台、通知和恢复操作必须继续可用。

## 七、目录、指标与业务建议

LLMGW 的 AppCaller 模型目录返回全部获准池及其执行事实，不因短期故障删项。近期指标统一基于真实、非探针请求：

- 最近 10 次完成请求的成功率；
- 同一窗口的平均耗时与样本数；
- 当前可调度成员数、健康摘要和更新时间。

MAP 决定如何解释这些事实。它可以推荐用户暂时不要使用某个池，也可以在用户坚持时继续提交严格请求。指标缺失时显示“样本不足”，不能显示虚假的 100% 或 0 秒。

## 八、通知与人工恢复

LLMGW 对首次熔断、持续故障、跨池代选、恢复成功和恢复失败产生结构化事件。MAP 站内通知中心负责展示、聚合和跳转到对应 AppCaller、模型池和请求日志。

通知投递失败不得阻塞请求或恢复。管理员在控制台始终能找到隔离、进入半开、切默认池、临时授权跨池和回滚操作，即使当前没有任何健康池。

## 九、可观测性

每次请求必须能够回答：

- 谁调用：租户、团队、AppCallerCode、用户和请求关联标识；
- 用户选什么：请求模型池和是否自动选择；
- LLMGW 做什么：实际池、成员、Provider、协议和每次尝试；
- 为什么变化：池内重试、跨池代选、熔断或人工操作原因；
- 结果如何：状态、耗时、首字、用量、费用证据和错误分类；
- 如何恢复：健康状态变化、HalfOpen 结果和关联审计。

日志不得回显明文凭据。用户界面以业务池为主，运维详情再展示实际成员，避免泄漏实现细节或隐瞒真实切换。

## 十、安全与可用性

- 凭据只由 LLMGW 加密保存和使用，MAP 不读取；
- 请求执行与通知、控制台、指标聚合解耦，任一辅助链路故障不阻断数据面；
- 配置写入必须带权限、审计、前后值和回滚关联；
- 批量禁用、跨池授权和强制恢复属于高风险操作，需要范围预览；
- 生产恢复不得依赖 CDS 预览环境的付费探测；
- 非幂等请求在结果未知时不自动重放。

## 十一、迁移原则

现有单池绑定、逻辑模型目录和 legacy 默认链路按兼容迁移处理：

1. 先建立 AppCaller 多池授权与严格默认值，不改变现有默认池；
2. MAP 切换到 AppCaller 池目录，并保留旧选择值迁移映射；
3. 开启严格池边界，消除显式选择后的全局 fallback；
4. 接通指标、通知、HalfOpen 和恢复入口；
5. 通过故障演练后退役逻辑目录与 legacy 兼容路径。

每一步都必须可单独回滚。迁移完成前，兼容路径的存在不得被描述为目标架构。

## 十二、完成定义

- MAP 和 LLMGW 的责任可由规则、数据和界面一致证明；
- 用户选池 A 时，默认情况下不会执行池 B；
- 单成员故障自动限制在池内，单池故障不会关闭 MAP；
- Open 成员能通过零合成探测的 HalfOpen 流程恢复；
- MAP 显示最近 10 次成功率、平均耗时、样本数和风险建议；
- 所有模型不可用时仍有明确错误、通知、恢复按钮和审计回滚；
- 故障矩阵覆盖目录、执行、通知、恢复四条独立链路。

## 十三、账号自助与联邦会话

MAP 一键登录在 LLMGW 侧建号后，账号不能停在"建出来但登不进、也改不了口令"的断头状态。控制台用户菜单常驻「账号与安全」入口，展示登录名、口令是否可用，并允许设置或修改口令；登录名默认跟随 MAP 用户名，冲突时明确提示另取，不静默覆盖。

联邦会话（fed_session）承载"从 MAP 一键登录换来、允许免旧口令设置新口令"的特权。默认（未配置更短的 SSO 时长）该会话与普通会话同为滑动式，续签按正常生命周期展期，这是有意的默认体验，不是遗留漏洞。只有管理员显式把 SSO 时长配得比正常生命周期短时，会话才进入"硬截止"模式：此时改口令、切换租户、续签这三个受硬截止判据守护的入口，均不得突破那个更早的绝对到期时刻，到期或到期时间不可读时直接拒绝。这条边界是本节存在的核心理由——普通场景下账号自助的便利性靠滑动会话保障；一旦管理员收紧了 SSO 时长，免密改密特权就必须在这三个入口同步收紧，不能让续签或切租户悄悄把它续回宽松状态。（边界仅覆盖这三个显式接入硬截止判据的入口，不是对该会话下所有写操作的全局拦截；JWT 校验本身另有 1 分钟时钟偏移容忍。且该保证目前只在配置值 ≥5 分钟时成立——配 1–4 分钟时初次签发仍会被 `GwJwt.Issue` 的 5 分钟下限抬高，是已知未偿债务，见 [debt.platform.llm-gateway.md](./debt.platform.llm-gateway.md) 对应条目。）

## 十四、Provider 接入体验（2026-08-11）

### 为什么要有内置预设注册表

在预设注册表出现之前，接一个新的上游平台要求管理员自己去查供应商文档、抄接口地址、猜协议类型——这违反了「用户输入最小原则」（见 [rule.md](../.claude/rules/minimal-user-input.md)）：接口地址、协议类型这些系统本来就能内置的信息，不应该让用户去搜。

控制台内置了约 18 个常见上游平台的预设（含地址、协议类型、密钥获取指引），管理员的操作收敛为「选平台 + 填密钥」；地址、并发上限等有默认值但仍可能需要调整的字段收进「高级」折叠区，不强制用户面对。本地部署类预设（如 Ollama、vLLM）自带占位密钥，避免「文案说不需要密钥、保存却因为空值被拒绝」这种自相矛盾。

### 测试连接：填完立刻能验证，保存后自动跑一次

密钥填完不能停在「已保存」就算完事——管理员需要立刻知道这个地址能不能连上。保存新 Provider 成功后，界面不等管理员动手，立即自动发起一次连接测试；测试通过后，只要不是当前集成还不支持解析清单响应的协议类上游（如 Claude 原生协议——上游本身提供模型清单接口，只是这边尚未接上对应的响应解析，见 [debt.platform.llm-gateway.md](./debt.platform.llm-gateway.md) 已知边界），会接着自动打开模型发现结果供管理员勾选导入——全程不需要额外点击「测试连接」或「查看模型」按钮。自动测试没跑起来（如网络异常）时，界面明确提示改为手动点击「测试连接」重试。「测试连接」按钮本身（无论自动触发还是手动点击）都会实际探测上游，回报可达性、探测地址与失败时的下一步建议（耗时只统计到收到响应头为止，不含读取模型清单正文的时间，仅供参考，不是完整探测耗时）。这个结论只是连通性/模型清单探测成功，不等于「密钥已被接受」——很多上游的模型列表接口本身并不校验密钥有效性，探测通过、后续导入模型都能进行，但密钥若是错的，仍要等到真正发起推理调用时才会暴露。

### 模型发现与批量导入

测试连接探测成功后，「查看模型」会从上游拉取真实模型清单，管理员在返回结果里勾选批量导入，而不是照着供应商文档手抄模型名。这里同样不代表密钥一定有效——部分上游的模型清单接口本身不校验密钥，能拉到清单只说明连通性没问题，真正是否能正常推理仍以业务调用结果为准。导入同时尽量带入上游提供的价格信息（部分平台如 OpenRouter 会在模型清单接口里附带定价）；上游没有提供价格时如实留空，不编造一个看似合理的数字。每条模型清单会标注拉取时间，方便管理员判断这份清单是不是最新的。

### 探测的安全边界

上游探测发生在服务端，探测目标是管理员填入的任意地址，因此存在被用来做内网探测（SSRF）的风险面。探测链路对目标地址做内网地址校验，且校验发生在建立连接的那一刻（而不是提前解析域名后再连接），防止通过 DNS 解析绑定绕过检查；探测过程不跟随重定向，避免校验通过后的地址被重定向到内网。响应体读取设有字节上限与时间预算，覆盖到读完整个响应体为止，防止上游故意挂住连接拖垮控制台请求。

这道校验只对**外部租户**强制生效；MAP 自身所在的内部租户豁免，因为本地部署类预设（Ollama、vLLM）本来就要指向内网地址——这是有意的例外，不是校验遗漏。管理员看到「探测到内网地址」这类提示时，应先确认自己是否在内部租户下操作。

### 已知边界

预设的默认地址是否总是可达（例如本地部署类预设在容器化环境里能否解析到宿主机）、预设拉取失败时的界面反馈完整度等已知欠账，见 [debt.platform.llm-gateway.md](./debt.platform.llm-gateway.md) 对应条目。

## 十五、Quickstart 接入体验（2026-08-25）

### 双栏单主线，产物从空态可见地长出来

Quickstart 创建屏改为左步骤、右产物的双栏布局：接入方式横铺展示、月预算与负责人并排，主行动固定在卡片右下角，整屏在常见分辨率下一屏装完不需要滚动。签发只有一个主按钮，点下去之后右侧产物区从空态直接长出接入地址、一次性密钥与请求片段——这三样是管理员拿到密钥后立刻要用的东西，其余信息压成弱化的一行，不与它们抢注意力。

### 试跑失败按错误码归因，而不是甩出一堆日志

一键测试失败时，界面不展示原始错误堆栈，而是把错误码归到三类自检环节之一：密钥鉴权、团队与作用域、调用用途到模型池的路由。每类给出一句归因判断和一个可执行的下一步；如果问题出在调用用途没有绑定可用模型池，主行动直接提供「绑定默认模型池并重验」，租户名下确实没有可用池时才降级为「去模型池创建」的引导。

### 密钥与调用用途：填用途自动生成、用途本身保持可选

接入密钥的新建表单从「手填 appCallerCode」改为「填用途 + 选调用类型」，appCallerCode 由系统自动生成并当场展示，签发的同时顺带完成调用用途登记。考虑到一把密钥本来就可以授权多条 appCallerCode，用途字段最终改回可选（给合法默认值、当场显示生成的用途码），不因为选择了一个用途就锁死这把密钥的其它用法。高级设置里原本要手抄团队 ID 的输入框，换成真实的团队下拉选择，留空仍表示这是一把租户级密钥。

### 一键测试选模型：只能选真正会被路由到的健康成员

一键测试的模型选择从下拉枚举改为搜索式（输入联想），且只列出当前调用用途会被路由到的那一个模型池里的健康成员——避免管理员选中一个池外或不健康的模型、测试结果却和实际路由行为对不上。选中非健康成员时禁用执行按钮，清空输入即回退到自动路由；提示文案写明当前池的健康数与总成员数，让「为什么测不了」有直接答案。

## 十六、Quickstart 演进：从三步表单到一句话生成（2026-08-26～08-27）

### 调用用途改为必选，产物屏补齐「调用用途卡 + 一键测试条」

十五节的表单在实测中发现「用途可选」会漏登记：不选用途时主按钮被禁用、点不出任何写请求，调用用途码统一由用途预设派生，不再允许空缺。产物屏左侧新增「调用用途」卡，把本次登记的 `appCallerCode` 直接露出并支持复制；右侧新增一键测试条，按调用类型从模型池成员里选模型、就地试跑，cURL 随所选模型联动。

### 一键测试拆分为「安全试跑」与「真实调用」

安全试跑不打上游、只验证链路可达；真实调用会真正发到上游，OpenAI 兼容协议走流式、文字边收边渲染。测试支持上传输入（图片理解传图、文字对话传文本），上传内容同时进请求体和 cURL 示例，避免「示例代码里没有的字段，真实调用时才发现要传」。新增模型返回面板，按响应形状自动判断图片 / 音频 / 文字并分别渲染。产物屏视觉层次同步拉开：密钥卡加重（警示描边 + 染色底 + 大等宽字），地址与用途卡压到次一档。

### 密钥归属收敛到团队，不再挂个人负责人

密钥的「负责人」个人归属被移除，改为只归属团队；签发时不再向 `appCaller` 写 `owner` 字段。创建卡同时去掉 1080px 宽度上限、改为铺满内容区，宽屏不再留大片空白。

### 创建屏与产物屏两屏互斥，决定收敛到三个

创建流程收敛为「接入方式、月预算、负责人」三个决定，其余选项收进高级设置；签发时把负责人（默认当前登录用户）与月度预算（留空即不限）写到 `appCaller` 上。产物屏对「API 与 Agent」等预设不再重复展示与环境变量相同的客户端配置标签，成功态补回 `requestId` 回查深链。

### 一句话生成码：创建线从「填表单」改为「模型推导」

在两屏互斥的基础上进一步收敛：第一屏改为全屏一个输入框「我想做什么」，提交后交给网关自己的模型推导 `appCallerCode`，SSE 边推边渲染推导过程；后端 `console-api` 新增推导端点，调 serving 侧的兼容接口两段码，模型未配置或调不通时返回明确的「不可用码」而非静默瞎猜。产物屏改为三页签：接入信息（地址/密钥/用途码）、cURL（含一键试跑）、提示词（系统提示词 / Agent Skill / 客户端配置）——「怎么接进去」不再是创建步骤里要回答的问题，挪到产物屏的提示词页签，创建线最终收敛为「说清用途 → 看码 → 算谁的」三屏。

推导提示词经过两轮实测修正：一是模型请求默认带 `temperature` 参数会被部分上游用 400 拒绝（`temperature does not support 0 with this model`），改由提示词本身约束确定性输出；二是同一句话偶发返回中文段的情况，补了「两段禁止出现中文」的硬约束和两个中文输入的示例，避免中文码落到本地兜底判定。

## 十七、颁码前置门槛：两段都落实才放行，模型推导优先、关键词表兜底（2026-08-27）

Quickstart 签发调用用途码前，要求那句「我想做什么」必须能同时看出「谁在调用」与「要做什么」两段，两段都识别到才放行。识别优先交给网关自己的模型推导，模型不可用时退回本地一张有限关键词表按最长命中判定，并在界面上明确标出这是降级判定、允许手动改选，不再让"模型推的"和"猜的"长得一样而分不清可信度。任一段缺失都会提示具体缺哪一段并引导从下方清单里挑选，不再兜底成一个谁也看不懂的占位码。调用类型（chat / vision 等）随场景自动切换，不需要用户额外选择。创建屏的主操作从页面底部固定按钮改为常驻可见的粘性定位，滚动过程中始终可点。

## 十八、产物屏试跑区改版：上输入下输出，试跑正文与 cURL/真实请求体同源（2026-08-28）

Quickstart 产物屏的试跑区改为「上输入下输出」布局——用户在上方输入框直接写要发送的内容，模型返回贴在正下方，两块保持同宽同圆角，空态也占固定高度，避免有输出后页面整体跳动。这次试跑不再是脱离真实链路的演示脚手架：输入框里的文字、cURL 示例和真正发出去的请求体永远是同一份内容，用户上传的文本也会先落进输入框（可见、可改），不再单独藏在附件里；附件只保留看图这一种场景。输出区在流式返回期间给出动效与耗时提示，完成后展示实际执行的模型、耗时与请求 ID 的可回查入口，并把主按钮切换为「再跑一次」。

## 十九、内置模型名录与导入白名单（2026-08-28）

网关新增一份内置的已知模型名录，登记主流供应商（OpenAI 含 o 系列、Anthropic、Google、DeepSeek、通义、智谱、Kimi、豆包等）每个模型真实的用途与是否收图 / 必须给图的约束，并对模型标识做归一化，让厂商前缀、日期快照、`-latest` 后缀等价写法落回同一条登记。模型用途的判定顺序改为"名录优先、上游声明其次、按名字猜测兜底"，并把判定来源如实标注在界面上——名录内是可信的绿标事实，靠猜的是灰标并提示需要核对，不再让两者长得一样而无法分辨。

名录同时充当导入白名单：名录外的模型默认在导入这一步被拦下，管理员需要显式放行才能让名录外模型入库，放行记录进审计；拦截点选在入库而非请求时，因为请求只会打到已入池的成员。Quickstart 试跑同步按调用类型区分输入形态，看图类调用把"要看的图"独立成一格，未提供图片时如实提示当前发的是占位测试图，只能证明链路可达而非验证真实识别能力。

## 二十、接入流程与设置页版式收敛（2026-08-28）

Quickstart 第二步（用途确认）按设计稿重新分层为"那句话 / 推导结果 / 最终决定"三段，层间留白与分隔线拉开视觉节奏；推导结果由左右横条改为纵向叙述，调用类型单列一个字段。创建屏与网关设置页统一收紧内边距与间距档位，不影响其余页面。同时修复了几处样式缺陷：嵌套引用块在浅色主题下与外层背景撞色而不可见、flex 容器缺失生效条件导致层间距形同虚设、窄屏覆盖样式因声明顺序被基础规则压掉、重置按钮丢失默认底色。
