# MAP 自动化测试教程口播与节奏 · 指南

> **版本**：v0.3 | **日期**：2026-10-20 | **状态**：草案

**一句话**：以“代码写完以后，怎样证明它真的能用”为主线，给出五章教程的口播、画面、实操与停顿安排。
**谁该读**：教程文案、配音、录制和剪辑人员，以及审核课程内容的产品与开发负责人。
**读完能做什么**：按章节录制可跟练的课程，知道每段讲什么、画什么、何时操作、何时停下来核对结果。

## 课程文案定位

对外课程名建议用“用 Codex 做好一次测试交付”，副标题为“代码审查、视觉测试、单元测试、联合测试与严格验收”。开场从一个具体失败进入，结尾让学员独立交出证据。核心表达是“每一次说通过，都能指出依据”。

目标读者会使用 Codex，测试经验较少。讲清楚当前动作和判断依据，再引入术语；第一次出现“断言”解释为“把预期结果写成机器能检查的条件”，第一次出现“版本标识”说明它用来确认测的是哪份代码。

主案例沿用项目的授权探测历史问题，用它串起从入口到持久化的验证；第三章先用已试做的“10 件免运费”小案例解释红绿过程，再回到主案例。历史问题只在隔离环境复现，不能暗示当前线上仍存在同一缺陷。实际录制与结论以当次证据为准。

方法与可复制指令以 [五步法指南](./guide.platform.testing.methodology.md) 为准；验收结论、档位和风险分级以 [企业级验收规范](./rule.acceptance.map-enterprise.md) 为准。本稿负责教学表达，不另设判定规则。

### 口播与现场内容怎样使用

各节“固定口播”可以直接试读。标为“现场观察”的文字由讲师对着真实结果讲解，先提出问题、停两秒让学员找证据，再读出观察到的事实。不能预先录制“已经通过”，然后配上另一版本的画面。

每章都交出一份小产物，下一章接着使用：审查记录、页面证据、回归用例、链路证据、交付卡。学员一路在完善同一张任务卡。

### 渲染前先验收能否跟做

原有文案与章节预算保留，另配 27 张操作卡。每张写清开始位置、具体动作、可观察预期、失败后的下一步和事实来源。需要填写的入口、版本与项目必须说明取得方式；讲师不能临时补一句口头提示，随后把学员卡住归因于经验不足。

先核对操作卡，再做真实环境走查与低成本粗样，最后让目标学员独立跟做。真实界面或命令输出确定后再校正文案、标注和停顿。粗样检查包括关键画面抽帧、命令与提示词复制、暂停问答、投影可读性及手机页面溢出；正式教程还需要相应实操证据与真人试学记录。

本轮已经提供可离线翻页的讲解版，支持逐步操作、复制提示词、暂停问答、输入保存和试学记录导出。它与渲染前检查共用同一套操作卡。自动检查能发现缺步骤、失效来源、时间不符和证据记录问题，不能证明学员理解；本机组件演示也不能代替线上验收。

当前网络策略阻断平台访问，用户已允许先不操作线上部分。MAP 实际入口按用户指定从 CDS 返回的第一个分支取得，不能猜域名。本机市场与 CDS 报告画面全程标明真实组件、演示数据及未验证的线上范围；Codex 登录后的设置、正式归档与在线查收继续保留待核验状态。讲师可先用操作卡与明确标注的粗样讲解步骤。

## 全片章节与时间安排

原版 50 分钟内容完整保留。本版追加评审设置 8 分钟、视觉技能操作 10 分钟、SSOT 与两个案例 12 分钟，合计约 80 分钟，可拆章及补充段播放。表内包括解释、演示、读结果和练习提示；学员暂停后自行操作的时间另计。它是录制预算，不是配音完成前就锁死的逐秒时间线。位置采用累计分秒，例如 69:30 表示第 69 分 30 秒。

| 合辑位置 | 章节标题 | 时长 | 本章学会的判断 |
|---|---|---:|---|
| 00:00—01:30 | 开场 这次真的测到了吗 | 1 分 30 秒 | 交付要有与目标对应的证据 |
| 01:30—05:30 | 准备 先说清要证明什么 | 4 分钟 | 写出一个具体预期，确认版本与环境 |
| 05:30—20:30 | 第一章 Codex 代码审查 找到值得验证的问题 | 原 7 分钟加设置 8 分钟 | 开启 GitHub PR 评审，确认实际运行，再处理发现 |
| 20:30—38:30 | 第二章 视觉测试 看见用户真正得到的结果 | 原 8 分钟加技能操作 10 分钟 | 获取并使用验收技能，在 CDS 找到可读回的报告 |
| 38:30—58:30 | 第三章 单元测试 让测试抓住原来的缺陷 | 原 8 分钟加 SSOT 案例 12 分钟 | 对齐规则、单元和所有消费者，防止另一个出口继续出错 |
| 58:30—69:30 | 第四章 联合测试 把整条链路走完 | 11 分钟 | 验证交界、持久化、负面与恢复 |
| 69:30—75:30 | 第五章 严厉版标准 每个结论都拿得出依据 | 6 分钟 | 区分产品失败、覆盖缺口和完整通过 |
| 75:30—80:00 | 独立练习 换一个问题再做一遍 | 4 分 30 秒 | 独立交付可复查的结果 |

五章的推进关系是：先找到疑点，再看到实际表现；用小范围测试锁住规则，沿完整链路验证，最后检查结论是否站得住。教学章节沿用用户指定顺序，实际开发时可以先跑便宜的检查和单测。

## 开场 这次真的测到了吗

### 固定口播

> Codex 说完成了，检查也是绿色的。你打开页面，点一下“探测”，却失败了。
>
> 我们先把这次操作还原出来。代码审查读过什么？测试实际跑了什么？用户点击以后，页面和数据发生了什么？
>
> 这套课，就带你把这些问题逐个查清。我们会从一次具体改动出发，完成代码审查、视觉测试、单元测试和联合测试，再按严格标准核对交付。
>
> 你不需要先成为测试专家。每章照着做一件事，留下一个结果。最后，你要能指着证据说：这一项通过了，这一项还没有测到。
>
> 现在，选一个你正在处理的问题。接下来，我们就用它练习。

### 画面与节奏

| 本节位置 | 画面 | 节奏安排 |
|---|---|---|
| 00:00—00:15 | 先出现“完成”和绿色检查，再呈现授权探测历史问题的示意 | 前两句慢讲；失败出现后停两秒 |
| 00:15—00:45 | 手臂依次连起“审查—运行—页面—数据” | 每提出一个问题才画出对应节点 |
| 00:45—01:10 | 五章地图逐项出现 | 中速报出章节；一屏不展开细则 |
| 01:10—01:30 | 一张空任务卡进入画面 | 留出阅读时间，提示学员准备自己的问题 |

屏幕主句用“这次真的测到了吗”，副句用“从一次改动，到一份可复查的交付”。示意画面注明历史案例；正式录屏另标当次版本。

## 准备 先说清要证明什么

### 固定口播

> 先写一句话：谁，在什么条件下，做什么，应该得到什么。
>
> 比如，测试账号完成授权以后，回到页面点击探测，应该看到连接可用。如果这个功能需要长期保存连接，我们还要确认服务重启以后，它仍然可用。
>
> 这句话就是我们判断对错的起点。先把预期写清楚，再让 Codex 找实现和测试。
>
> 接着确认版本。目标版本是你想验证的代码，实测版本是环境里真正运行的代码。两个标识不同，就先解释差异，不能拿新版本的截图替旧版本作证。
>
> 最后准备测试账号、练习数据和依赖服务。我们在隔离环境里操作，记录本轮创建的资源，方便结束后清理。
>
> 暂停，把你的问题、预期、版本和环境填进任务卡。能说清这些，再开始第一章。

### 实操与停留

先手绘一条“条件—动作—预期”，再切任务卡填写。给“目标版本”和“实测版本”各一个可见位置，用一次真实查询解释它们如何取得。环境配置只讲本课所需的前置条件，复杂安装进入配套指南。

本节预算：解释 1 分 20 秒、任务卡与版本演示 2 分钟、读回与暂停提示 40 秒。暂停卡显示“写出一个可观察预期；记录目标与实测版本”，至少停留八秒。

## 第一章 Codex 代码审查 找到值得验证的问题

### 开章与原理口播

> 第一章，我们先找出值得验证的问题。
>
> 把任务目标和比较基线交给 Codex，请它沿真实调用路径检查。比如，授权后要做探测，就要看凭据怎样生成、怎样保存，又怎样被探测请求使用。
>
> 一条有用的发现，应当说清：什么条件会触发，用户会受到什么影响，代码证据在哪里，以及怎样复现。只写“可能有问题”，还不够我们动手修。

### 新增 GitHub PR 评审的设置与生效确认

本段增加 8 分钟，安排在原理之后、原有审查实操之前。这里讲 GitHub PR 的云端代码评审；本地阅读 diff 与权限设置里的动作自动审批，是不同的操作。

截至 2026-10-20，[OpenAI 官方配置说明](https://learn.chatgpt.com/docs/third-party/github) 给出的直达入口是 [代码评审设置](https://chatgpt.com/settings/code-review)。录制时同时展示从已登录界面定位设置的过程和直达入口，并框选菜单、仓库行及开关。公开文档能核对流程，具体账户的界面需正式录制时再确认。

| 步骤 | 学员照着做 | 看见什么才能继续 |
|---|---|---|
| 1 | 登录正确账户与工作区，连接 GitHub 仓库，确认有相应 push 或 admin 权限 | 仓库可以选择；权限不足时明确由谁配置 |
| 2 | 打开代码评审设置，选择教学仓库 | 仓库身份清楚，不只拍一枚开关 |
| 3 | 在仓库 Review code 区域启用 Automatic review，核对作用范围 | 仓库级策略覆盖要演示的 PR |
| 4 | 核对 Personal preferences；跟随个人偏好的仓库还要确认个人开关及 Review trigger | 记录实际选择的触发事件，不能凭“已打开”判断生效 |
| 5 | 用符合策略的练习 PR 事件验证自动触发；手动验证使用 PR 评论 `@codex review` | 自动与手动分开记，不能用手动结果证明自动配置生效 |
| 6 | 等待实际评审完成，核对所审提交与本轮版本 | 有完成结果；只收到请求、等待中或额度不足均不算完成 |

触发事件以录制当日页面为准。保存设置不代表所有既有 PR 已重新评审。教程讲清操作，由有权限的操作者在练习仓库验证；本次文案工作不调整线上策略，也不发布 PR 评论。

新增口播：

> 先把 GitHub 上的代码评审开起来。这里最容易漏的，是入口和作用范围。
>
> 打开配套设置链接，先确认账户、工作区和仓库。选中仓库，找到代码评审的自动开关。再检查它是否跟随个人偏好，以及什么事件会触发评审。
>
> 画面里要看见仓库名、开关和触发条件。这样换一个同事照做，也知道自己开的是哪一个仓库。
>
> 最后验证一次。自动评审用符合配置的事件；手动评审在 PR 评论里发出明确指令。两条路径分别记录。
>
> 收到请求以后，继续等它完成。没有意见、没有运行、运行失败，是三种不同状态。确认它实际审过这次提交，再进入原来的审查与处理流程。

| 新增段位置 | 内容 | 节奏要求 |
|---|---|---|
| 00:00—01:30 | 找入口、选仓库 | 正常速度，首次到达入口停三至五秒，框选位置 |
| 01:30—04:00 | 仓库开关、个人偏好与触发事件 | 每次只改读一项，说明它影响哪一类 PR |
| 04:00—06:30 | 触发、运行状态及结果读回 | 保留实际触发与最终结果，长等待说明省略 |
| 06:30—08:00 | 不生效排查与暂停卡 | 核对连接、权限、开关、个人策略、事件与运行失败原因 |

暂停卡：“找到自己的仓库；记录开关与触发条件；确认一次评审实际完成”。报错或额度不足留在排查分支，不剪成开启成功。

### 进入实操的口播

> 现在打开配套指令，填入本轮目标和版本。先让 Codex 读取已有规则、调用方和相关测试，再开始审查。
>
> 等它返回以后，我们先选一条与本轮目标直接相关的意见，检查它的证据。不要同时追着所有建议修改。

### 现场观察

指向一条实际意见，问“它能说明用户怎样触发这个问题吗”，停两秒后读出触发条件和代码位置。有直接缺陷就演示如何复现；没有发现直接缺陷，就如实显示“本次审查未发现直接缺陷”，转到下一层运行验证。环境或额度导致未执行时显示“未执行”，不能替换成无发现。

### 读结果与收尾口播

> 把意见分成三类：直接影响本轮目标的缺陷，在这次修复并复测；有价值但扩大范围的建议，单独记录；找不到真实调用路径的推测，先补证据。
>
> 审查结束时，我们留下发现、处理决定和验证办法。它帮助我们确定接下来测哪里。
>
> 暂停，挑一条实际发现，写成一个可以复现的场景。如果没有发现，也保留审查范围，继续做运行验证。
>
> 下一章，我们回到页面，看用户真正遇到了什么。

### 原有7分钟内容的节奏表

| 本章位置 | 内容 | 剪辑和学习动作 |
|---|---|---|

| 00:40—01:30 | 手绘凭据的生成、保存和消费 | 先问消费端是否接受，再画连接线 |
| 01:30—04:20 | 提交实际指令，检查一条审查意见 | 保留输入、证据展开和定位；长等待说明省略 |

屏幕主句用“发现要能复现”。练习产物是一条可验证场景，或一份明确范围的无发现记录。

## 第二章 视觉测试 看见用户真正得到的结果

### 开章与原理口播

> 页面能打开以后，我们继续往前走。
>
> 视觉测试要看清用户在哪里进入、能不能操作，以及操作后得到什么反馈。我们会先从正常入口走到目标功能，再完成任务卡里的动作。
>
> 看布局时，留意文字是否读得清、按钮是否点得到、滚动和弹层有没有挡住操作。执行任务时，留意等待、成功、失败和恢复是不是表达清楚。

### 新增 验收技能的获取下载使用与 CDS 报告

本段增加 10 分钟，按“获取—下载—识别—使用—看报告”录制，随后完整执行原有视觉测试内容。用户提到的 `/create-visual-to-kb`，在本仓库对应的正式技能名是 `create-visual-test-to-kb`，常用触发词为“/验收”或“视觉验收”。课程展示正式名称，不把简称当作已存在的别名。

本章围绕这项技能操作。规范、模板和判定由技能读取权威主源，口播不另维护一份。技能与源码依据见文末。

| 步骤 | 获取或使用方式 | 做到什么才能继续 |
|---|---|---|
| 获取 | 从 MAP 海鲜市场选择技能，搜索正式名称，核对作者、版本与内容 | 找到目标技能；仓库已有时先核对本地版本 |
| 下载 | 点击技能卡片的下载动作取得 ZIP；也可让海鲜市场操作技能搜索并下载 | 得到实际下载包，不拿介绍页面代替文件 |
| 官方入口 | 需要直链时，使用当前实例的官方技能下载接口，路径见文末 | 实例地址来自实际页面或配置，不猜域名 |
| 安装识别 | 放进当前工具识别的项目级技能目录，多宿主分别确认 | 工具实际读取到技能正文；必要时重新加载或新开会话 |
| 检查依赖 | 确认测试设计、场景编排依赖及规则快照 | 官方包声明了两项依赖；旧包或不完整包先补齐 |
| 准备使用 | 填目标、提交、实际入口和验收范围，配置正确 CDS 项目 | 凭据安全配置，截图与运行产物放仓库外 |

## 第三章 单元测试 让测试抓住原来的缺陷

### 手绘概念段口播

> 代码写好了，测试全绿，就能放心吗？看一个例子：数量达到十件，应该免运费。但恰好十件，仍然收了六元。

### 新增 SSOT 与单元及出口对齐

本段增加 12 分钟。保留原有小例子、失败归因、项目规则和回归，再讲：“为什么这一处修好了，另一个地方还在错？”

SSOT 指同一条规则的唯一权威来源。多个入口或出口可以是合理设计，风险在于各自抄了一份本应相同的规则。共享函数存在，也不代表所有消费者都已使用它。

用户提出的三类原因，作为可以重叠的排查线索：

| 排查线索 | 转成可以观察和修复的问题 | 判断证据 |
|---|---|---|
| 写代码的 AI 不行 | 漏读上下文、误解预期、遗漏调用者、测试未执行 | 任务输入、真实调用路径、diff 与执行结果 |
| 写代码的人不行 | 预期不清、只改症状、审查或回归遗漏 | 可观察预期、审查记录、相关路径与复测 |
| 没有 SSOT 对齐，出现多个独立出口 | 同一规则各写一份，只修其中一份；或共享逻辑未接入消费者 | 权威源、消费者清单、逐出口证据与防漂移检查 |

反复出现本身不能证明属于哪一类，还要核对版本、环境与覆盖。课程先复现再归因，不用能力评价代替定位。语义不同的规则保留各自契约，不为“统一”而硬合并。

按四层对齐：需求给出独立预期；单测验证权威规则；消费与接线检查确认各出口实际使用它；工作流检查确认测试真正执行。不能只测共享函数，也不能把源码字符串检查叫作完整业务验证。

### 案例一 CDS 预览地址改了一处还有旧出口

依据本仓库真实历史注释与现有测试选取。预览地址规则更新后，多个技能仍使用旧公式，用户反复拿到错误入口。课程不让学员重背地址公式，而是追踪权威计算及消费者。具体代码与测试见文末。

| 步骤 | 操作与观察 | 要锁住的结果 |
|---|---|---|
| 看差异 | 对同一项目和分支，比较平台、页面、CLI 与交付材料 | 各出口对应同一实际入口，差异可定位 |
| 找权威源 | 定位统一计算、项目身份与 API 返回 | 新生成行为归同一规则；消费者读取权威结果 |
| 测规则 | 使用已有单测检查同分支不同项目、普通与长分支等边界 | 项目不串、长度合法、行为符合独立确认的预期 |
| 测消费者 | 追踪页面、CLI、技能交付，并运行防旧公式和绕过共享入口的守卫 | 共享函数正确但一个出口仍另算时，检查能报警 |
| 逆向验证 | 在隔离副本接回一个旧计算出口，确认对应检查失败，再恢复 | 证明防漂移检查能抓住“又抄了一份” |

合法的旧链接解析兼容和明确白名单按边界保留，不能当作新的生成出口误删。扫描守卫辅助发现漂移，地址实际可用与用户路径还需运行验证。

案例口播：

> 第一个案例，预览地址在一个地方修对了，另一个技能还在自己算。只给共享函数补单测，旧出口可能继续存在。
>
> 先找权威规则，再列出谁在使用它。平台、页面、命令行和交付材料，针对同一对象，都要回到同一个实际入口。

> 接着做第二次探测：在隔离练习环境重启服务，再用已经保存的连接试一次。这样才能验证结果有没有依赖暂时留在内存里的状态。
>
> 最后检查本轮相关的负面和恢复路径。例如，撤销后还能否被错误使用，重新授权能否恢复，无权限身份能否越过边界。

### 现场观察

每走完一段，就在同一张链路图上标出实际状态。首次探测与重启后探测并列比较；重启、撤销和清理仅对隔离练习资源执行。外部等待可以剪短，注明等待阶段和实际耗时；不能剪掉失败过程，让恢复看起来像首次就成功。

在负面路径里，除了看错误提示，还核对是否留下不应产生的副作用。恢复后回到页面完成同一核心动作，确认用户能够继续。

### 读结果与收尾口播

> 这里的一条成功链路，可以同时证明多个相关断言。但每条断言仍要找到自己的证据位置，不能用一张总览图包办所有结论。
>
> 假服务能帮助定位接口约定；真实依赖没有验证的部分，继续保留缺口。页面显示成功但数据没保存，也不能算完整闭环。
>
> 失败时，从页面症状向请求、权限、存储和外部依赖逐层定位。先把观察到的事实写清，再判断原因。
>
> 结束前清理本轮测试数据，记录清理结果。
>
> 暂停，在你的链路图上指出：正常路径、一个相关的负面路径，以及恢复后的结果。下一章，用这些证据核对是否可以交付。

### 本章节奏表

| 本章位置 | 内容 | 剪辑和学习动作 |
|---|---|---|
| 00:00—01:30 | 手绘完整链路，提出重启后的问题 | 每画一段只解释一个交界，先问后揭示 |
| 01:30—04:40 | 授权、回跳、探测及关联证据 | 操作后回到同一张链路图，不切去无关后台 |
| 04:40—06:40 | 隔离环境重启后再次探测 | 保留前后对象标识，明确服务已经重启 |

## 第五章 严厉版标准 每个结论都拿得出依据

### 开章与原理口播

> 到这里，我们已经有了审查记录、页面证据、回归用例和链路结果。最后一章，核对这些材料能支持什么结论。
>
> 先看测的是不是目标版本，再看核心行为有没有执行。接着核对证据能不能打开，以及适用主题、移动端、相关负面和恢复路径是否覆盖。
>
> 严格执行，还包括把未知写清楚。没有测到，不等于产品一定坏了；它意味着这一部分暂时没有足够依据作质量承诺。

### 进入实操的口播

> 我们把结论分开写。产品质量回答发现了什么缺陷，核心用例是否通过。验收完整性回答哪些已覆盖，哪些无法验证或尚未执行。
>
> 然后按现有规范给出综合结论，写清发布建议和判定性质。不要只留一句“全部通过”。

### 现场观察

准备两份明确标为教学示例的报告：一份有可复现的核心失败，一份未发现产品缺陷但缺少必要覆盖。让学员先判断，再打开对应证据，分别解释产品失败与覆盖不足。使用规范的五项结论和既有枚举，不用总分掩盖阻断问题。

### 读结果与收尾口播

> 对发现的阻断问题，要指出触发条件、影响和复测办法。对覆盖缺口，要指出缺什么、由谁补、补到什么程度才能关闭。
>
> 同时守住范围。轻微问题按它的实际影响记录；关键风险已经覆盖，继续加测也不会改变判断时，就停止追加无关测试。
>
> 最后打开一次交付链接，确认别人能读到证据，能找到每个结论的依据。
>
> 暂停，给你自己的结果写出五项结论。每写一个“通过”，就指向一份证据。

### 本章节奏表

| 本章位置 | 内容 | 剪辑和学习动作 |
|---|---|---|
| 00:00—00:45 | 将前四章产物放回交付卡 | 快速回顾，沿同一张任务卡收束 |
| 00:45—02:10 | 核对版本、实际执行和证据 | 每次只展开一个结论及其依据 |
| 02:10—03:40 | 比较产品失败与覆盖不足的教学示例 | 先给五秒判断时间，再讲答案 |
| 03:40—05:00 | 填五项结论、关闭动作与停止条件 | 放慢读判断，不再堆规范术语 |
| 05:00—05:35 | 实际打开标准报告链接 | 保留从链接进入证据的完整过程 |
| 05:35—06:00 | 暂停卡 | 暂停卡至少八秒；带走可复查交付卡 |

屏幕主句用“每个结论，都拿得出依据”。完整通过、原则性通过和失败的具体使用条件继续引用主规范；本章演示判断过程。

## 独立练习 换一个问题再做一遍

### 固定口播

> 现在换一个相似问题。不要直接复制刚才的答案，先独立写出它的预期。
>
> 你要交出五样东西：任务卡、审查与处理记录、有效失败和修复后的测试结果、真实用户路径证据，以及交付结论。
>
> 遇到无法执行的步骤，把阻塞条件和缺口写清楚。它不能变成一项悄悄打勾的通过。
>
> 完成以后，请另一位同事只看你的材料，回答三个问题：这次测了什么？为什么可以这样判断？还有什么没有验证？
>
> 如果他能找到证据，你也能说明边界，这次交付才有了可复查的依据。下一次改动，就从这张任务卡重新开始。

本节用一张新的练习卡演示如何起步，用一份交付示例讲清评分依据，最后留十秒暂停卡。采用已提供好环境与身份的等价问题；学员实际练习时间另计。带教者观察卡点，不代替点击和填写。

## 节奏与剪辑执行标准

### 整体节奏

每章保持“问题—解释—操作—读结果—练习—连接下一章”的顺序。前 20 至 40 秒让观众知道要解决什么；中段只演示一条主闭环；末尾明确本章产物。复杂分支用独立短段补充，不在主操作中突然展开另一套任务。

讲解以能听懂为先，不以信息密度取胜。试读可从每分钟约 200 至 240 个汉字起步，数字、命令、术语和判断句另留停顿；最终以实际录音及目标学员试听为准。不要通过压缩停顿，让原来较长的口播勉强塞进 82 秒。

原有 50 分钟内容与新增 30 分钟均以真实操作和读结果占主要时间，固定口播只是骨架。若实际演示比预算短，就缩短成片；若过长，先剪重复输入与无信息等待，保留本轮要求的内容。不能重复播放画面或拉慢声音来填时长。

### 具体的快慢与停顿

| 场景 | 建议节奏 | 可观察的剪辑要求 |
|---|---|---|
| 说明目标、章节连接 | 中速，句子短 | 画面对象先被点名，再切换 |
| 解释因果、失败归因、交付判断 | 放慢 | 一个判断讲完停约两秒，再揭示依据 |
| 手臂逐笔绘图 | 按解释分段 | 一个关系才画一条线，跨笔画抬笔；图画完后退出 |
| 命令输入、关键点击、错误出现 | 正常速度 | 保留动作前状态、动作和结果；不在关键处倍速 |
| 重复输入、构建与服务等待 | 可缩短或有限加速 | 标明省略阶段、实际等待；保留失败和最终结果 |
| 新图、新结果或对照表出现 | 留三至五秒阅读窗口 | 先给观众找信息，再开始解释；信息多则拆屏 |
| 可复制提示词 | 简短解释意图 | 完整文字进讲义，不逐字念长命令 |
| 暂停练习卡 | 停八至十秒 | 只写当前动作、预期产物和继续条件 |
| 章节切换 | 约半秒柔和转场 | 先交代上一章产物怎样交给下一章 |

以上是制作起点，可随内容和试学调整。旁白中的自然停顿与画面阅读时间分别安排；阅读时不同时讲新的规则。

### 三个明确的节奏转折

第一处在视觉测试：从“入口可达”走到“动作后的真实反馈”，让观众先预测结果。第二处在单元测试：核对原失败的实际值，再看到同一断言修复后转绿。第三处在联合测试：首次成功后重启再测，将注意力从当前可用推进到持久可用。

第五章收束前面所有产物，降低转场频率，让学员读证据、做判断。严格标准的力量来自清晰的事实和边界，配乐与快速切镜不承担判定作用。

### 屏幕文字与口播的分工

屏幕主句每次只表达一个判断，优先控制在一行；图中只保留对象、条件、结果与必要标识。字幕按语义拆分，避免把“预期为零”与“实际为六”断成难以比较的片段。

旁白负责解释关系，图负责展示关系，录屏负责证明实际操作。命令和长提示词进可复制讲义。图形逐笔绘制与汉字标签排版分别标注，不声称做到了汉字规范笔顺。

## 开录前与试学后的核对

| 阶段 | 检查内容 | 完成依据 |
|---|---|---|
| 文案试读 | 语句能否自然读出、术语是否有解释、实际结果分支是否齐全 | 标出难读句与过长段，修订后重读 |
| 录音与定时 | 实际声音、停顿、字幕和手臂动作是否对应 | 以音频重新排时间，不按旧字幕时长硬套 |
| 实操录制 | 目标版本、账号、操作、结果与证据是否一致 | 逐章读回，未执行处如实标注 |
| 剪辑审片 | 是否切掉关键输入、失败、反馈或恢复 | 关键动作前后连续可观察 |
| 新人试学 | 能否独立交出每章产物 | 至少两位目标学员跟练；记录求助点、误判和耗时 |
| 课程收口 | 文案与实际画面有无矛盾，交付链接是否有效 | 修正后再验，视频播完不代替练习通过 |

手绘制作方式已通过用户方向确认。现有试片为字幕版，中文旁白尚未生成；本稿的时间安排须在实际声音到位后精校。课程方法可按本稿先评审，不以配音能力缺口阻塞文案工作。
