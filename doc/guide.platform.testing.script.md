# MAP 自动化测试教程口播与节奏 · 指南

> **版本**：v0.5 | **日期**：2026-10-20 | **状态**：草案

**一句话**：以“代码写完以后，怎样证明它真的能用”为主线，给出五章教程的口播、画面、实操与停顿安排。
**谁该读**：教程文案、配音、录制和剪辑人员，以及审核课程内容的产品与开发负责人。
**读完能做什么**：按章节录制可跟练的课程，知道每段讲什么、画什么、何时操作、何时停下来核对结果。

## 课程文案定位

对外课程名建议用“用 Codex 做好一次测试交付”，副标题为“代码审查、视觉测试、单元测试、联合测试与严格验收”。开场从一个具体失败进入，结尾让学员独立交出证据。核心表达是“每一次说通过，都能指出依据”。

目标读者会向 Codex 下达任务，测试经验较少；本公司项目使用者不操作代码。讲清楚当前动作和判断依据，再引入术语；第一次出现“断言”解释为“把预期结果写成机器能检查的条件”，第一次出现“版本标识”说明它用来确认测的是哪份代码。

主案例沿用项目的授权探测历史问题，用它串起从入口到持久化的验证；第三章先用已试做的“10 件免运费”小案例解释红绿过程，再回到主案例。历史问题只在隔离环境复现，不能暗示当前线上仍存在同一缺陷。实际录制与结论以当次证据为准。

方法与可复制指令以 [五步法指南](./guide.platform.testing.methodology.md) 为准；验收结论、档位和风险分级以 [企业级验收规范](./rule.acceptance.map-enterprise.md) 为准。本稿负责教学表达，不另设判定规则。

### 口播与现场内容怎样使用

各节“固定口播”可以直接试读。标为“现场观察”的文字由讲师对着真实结果讲解，先提出问题、停两秒让学员找证据，再读出观察到的事实。不能预先录制“已经通过”，然后配上另一版本的画面。

所有代码操作、查询和命令执行均由 Agent 完成；人只说明业务目标、登录授权和确认页面结果。原有章节中的运行、修复、读取测试，均按此分工拍摄，不出现要求学员打开终端或编辑文件的演示。

每章都交出一份小产物，下一章接着使用：审查记录、页面证据、回归用例、链路证据、交付卡。Agent 一路维护同一份测试记录，学员确认目标与结果。

### 渲染前先验收能否跟做

保留原有章节内容，按新反馈调整表达与执行分工，另配 42 张操作卡。本轮把“填写任务卡”“确认入口与权限”改为 Agent 执行；技术动作全部由 Agent 完成。每张写清开始位置、具体动作、可观察预期、失败后的下一步和事实来源。入口、版本与项目由 Agent 从实际来源取得，返回地址前实际打开目标页面；讲师不能临时补一句口头提示，随后把学员卡住归因于经验不足。

先核对操作卡，再做真实环境走查与低成本粗样，最后让目标学员独立跟做。真实界面或命令输出确定后再校正文案、标注和停顿。粗样检查包括关键画面抽帧、命令与提示词复制、暂停问答、投影可读性及手机页面溢出；正式教程还需要相应实操证据与真人试学记录。

本轮已经提供可离线翻页的讲解版，支持逐步操作、复制提示词、暂停问答、输入保存和试学记录导出。它与渲染前检查共用同一套操作卡。自动检查能发现缺步骤、失效来源、时间不符和证据记录问题，不能证明学员理解；本机组件演示也不能代替线上验收。

本轮重试仍未取得平台页面，已有“先不操作无法访问部分”的安排继续适用。MAP 实际入口按用户指定从 CDS 返回的第一个分支取得，不能猜域名。本机市场与 CDS 报告画面全程标明真实组件、演示数据及未验证的线上范围；Codex 登录后的设置、正式归档与在线查收继续保留待核验状态。讲师可先用操作卡与明确标注的粗样讲解步骤；本轮新增的CDS获取、本地化与报告读回尚未取得线上实录，不把旧四分钟样段称为覆盖新内容。

## 全片章节与时间安排

原版 50 分钟内容及前两轮补充保留。本轮再加视觉接入与工程闭环 6 分钟、测试统计及统计SSOT 4 分钟、最后收尾 5 分钟，共约 101 分钟。原五章与练习保持，收尾另成一节；等待和学员练习时间另计。预算不等于已有101分钟成片。

| 合辑位置 | 章节 | 预算 | 交出什么 |
|---|---|---:|---|
| 00:00—01:30 | 开场：这次真的测到了吗 | 1.5 分钟 | 能说明每个通过结论所依据的证据。 |
| 01:30—05:30 | 准备：说清版本与环境 | 4 分钟 | 能区分目标代码、实测代码和环境。 |
| 05:30—26:30 | 第一章：Codex代码审查 | 21 分钟 | 能连接并授权自己的仓库、开启评审，让Agent修复后反复复审至最新版本无开放P0/P1，并查看缺陷分析。 |
| 26:30—50:30 | 第二章：视觉验收从接入到问题闭环 | 24 分钟 | 能从MAP或CDS取得技能，交Agent安装并本地化，触发验收、读懂报告并将缺陷变为永久回归。 |
| 50:30—74:30 | 第三章：单元测试与SSOT对齐 | 24 分钟 | 能读懂各模块测试数量与边界，把一次统计定义对齐到所有消费者、回归检查和真实执行流程。 |
| 74:30—85:30 | 第四章：联合测试走完整链路 | 11 分钟 | 能检查页面到持久化与恢复的完整业务链路。 |
| 85:30—91:30 | 第五章：严厉版交付核对 | 6 分钟 | 能交付别人可复查的结论，明确未执行项。 |
| 91:30—96:00 | 独立练习：换一个问题再做 | 4.5 分钟 | 能用自己的问题完成同样流程。 |
| 96:00—101:00 | 收尾：何时用什么方法，开发按什么顺序 | 5 分钟 | 能按风险选择方法、说明每步解决的问题，并把发现回流到下一次开发。 |

五章的推进关系是：先找到疑点，再看到实际表现；用小范围测试锁住规则，沿完整链路验证，最后检查结论是否站得住。教学章节沿用用户指定顺序，实际开发时可以先跑便宜的检查和单测。

## 开场 这次真的测到了吗

### 固定口播

> Codex 说完成了，检查也是绿色的。你打开页面，点一下“探测”，却失败了。
>
> 我们先把这次操作还原出来。代码审查读过什么？测试实际跑了什么？用户点击以后，页面和数据发生了什么？
>
> 这套课，就带你把这些问题逐个查清。我们会从一次具体改动出发，完成代码审查、视觉测试、单元测试和联合测试，再按严格标准核对交付。
>
> 你不需要先成为测试专家。每章照着做一件事，留下一个结果。最后，你要能指着证据说：这一项通过了，这一项还没有测到。
>
> 现在，选一个你正在处理的问题。接下来，我们就用它练习。

### 画面与节奏

| 本节位置 | 画面 | 节奏安排 |
|---|---|---|
| 00:00—00:15 | 先出现“完成”和绿色检查，再呈现授权探测历史问题的示意 | 前两句慢讲；失败出现后停两秒 |
| 00:15—00:45 | 手臂依次连起“审查—运行—页面—数据” | 每提出一个问题才画出对应节点 |
| 00:45—01:10 | 五章地图逐项出现 | 中速报出章节；一屏不展开细则 |
| 01:10—01:30 | 一张空任务卡进入画面 | 留出阅读时间，提示学员准备自己的问题 |

屏幕主句用“这次真的测到了吗”，副句用“从一次改动，到一份可复查的交付”。示意画面注明历史案例；正式录屏另标当次版本。

## 准备 先说清要证明什么

### 固定口播

> 先告诉 Agent：谁，在什么条件下，做什么，应该得到什么。你不用填技术表，也不用操作代码。
>
> 比如，测试账号完成授权以后，回到页面点击探测，应该看到连接可用。如果这个功能要长期保存连接，我们还要确认服务重启以后，它仍然可用。
>
> 把这句话发给 Agent，让它查项目、版本和环境，再用普通话返回：这次测什么、到哪个页面看结果、看到什么才算成功、还缺什么条件。
>
> 版本也由 Agent 查。它要分清想验证的版本和环境真正运行的版本，不能拿另一版的截图作证。你只确认它理解的业务目标是否正确。
>
> 接下来，Agent 检查应用能否访问、测试身份是否可用、报告能否查收。它先实际打开正确页面，再给你链接和接下来要点的位置。需要你登录或授权时，就在对应页面完成。
>
> 暂停，给 Agent 发出你的目标。读回它的准备结果，确认页面与预期正确，再开始第一章。

### 实操与停留

画面只保留 Agent 对话与返回的页面，不出现要求学员执行的终端或代码编辑器。先显示人的一句目标，再显示 Agent 查询后的四项结果：目标、实际入口、成功标准、阻塞。技术版本留在可展开的记录中，不能让观众先理解 SHA 才能继续。

本节仍为 4 分钟：解释 1 分 20 秒、发送指令与读回 2 分钟、确认与暂停 40 秒。暂停卡写“告诉 Agent 你要测什么；确认它返回的页面与成功标准”，至少停留八秒。

## 第一章 Codex 代码审查 找到值得验证的问题

### 开章与原理口播

> 第一章，我们先找出值得验证的问题。
>
> 把任务目标和比较基线交给 Codex，请它沿真实调用路径检查。比如，授权后要做探测，就要看凭据怎样生成、怎样保存，又怎样被探测请求使用。
>
> 一条有用的发现，应当说清：什么条件会触发，用户会受到什么影响，代码证据在哪里，以及怎样复现。只写“可能有问题”，还不够我们动手修。

### GitHub 连接、安装、授权和评审设置

原有设置讲解 8 分钟保留；本轮另补连接授权、复审闭环和缺陷分析 6 分钟。本章共 21 分钟，学员实际等待和练习另计。人完成账户登录及明确的权限确认，Agent 完成技术操作。

先显示地址，再走步骤，最后在真实页面给按钮画圈。每屏只圈本步要点，并保留地址、仓库名和动作后的结果。复用时把教学仓库换成自己的仓库，三处身份必须一致：连接账户、GitHub 安装所属账户或组织、所选仓库。

| 顺序与入口 | 逐步操作 | 能继续的结果与圈注 |
|---|---|---|
| 1. [ChatGPT](https://chatgpt.com/) | 登录当前工作区，从 Codex 项目或仓库选择器的 Connect to GitHub 发起；当前界面若从 Settings → Plugins → GitHub 连接，就按实际入口走 | 圈实际入口、GitHub 项和连接按钮；通用插件能读取不单独证明 Codex 写入及评审授权 |
| 2. [ChatGPT Codex Connector](https://github.com/apps/chatgpt-codex-connector) | 核对发布者 openai；按页面 Install 或 Configure，选仓库所属个人或组织；用 Only select repositories 选择自己的仓库，提交安装或申请 | 圈安装动作、所属身份、仓库选择和确认按钮；等待组织批准时明确未完成 |
| 3. 安装流程实际回跳页面 | 完成流程要求的用户授权，回到发起连接的账户与工作区；让 Agent 实际读取目标仓库规则 | 圈授权确认与仓库选择结果；安装完成、用户授权、组织批准及仓库可读取分别确认 |
| 4. [代码评审设置](https://chatgpt.com/settings/code-review) | 搜索自己的仓库全名并进入，在 Review code 核对 Automatic review；跟随个人偏好时再查 Personal preferences 和 Review trigger | 先圈仓库行，再分别圈策略和触发条件；账户没有相应权限时先解决授权 |
| 5. Agent 返回的实际 PR 和本轮评审结果链接 | Agent 跟进已有 PR，验证符合设置的自动事件；手动请求时由 Agent 发布评审指令并等待完成 | 圈被审版本、完成状态和一条实际发现；手动成功不替代自动策略验证 |
| 6. [缺陷数量分析](https://chatgpt.com/settings/usage?tab=analytics) | 打开用户确认的分析入口，核对账户、日期范围及实际出现的评审指标；问题详情回到同一 PR | 先圈范围，再圈发现总数与实际可见分级；累计发现不等于未解决 |

当日入口核对：GitHub 公开应用页可读取，发布者为 openai；代码评审与用户给出的分析地址均能被公开读取工具访问，但未登录时回到 ChatGPT 登录/首页。因此只确认了链接来源与未登录落点，尚未确认当前账户登录后的页面、按钮和权限。不能把登录页、HTTP 成功或官方示例画面说成用户账户验证完成。真实圈注取证未完成前，这些卡保持待核验；不给出编造的回跳地址、仓库安装编号或评审结果链接。

### 本段口播

> 先从你的账户开始连接 GitHub。我们打开画面上的地址，从当前 Codex 项目找到连接 GitHub 的入口；界面不同，就按当前实际入口走。
>
> 接着安装 ChatGPT Codex Connector。这里要选仓库属于谁，再选你自己的仓库。组织需要管理员批准时，先等批准，不能把申请成功当成权限已经生效。
>
> 安装以后，继续完成页面要求的用户授权，再回到原来的账户。让 Agent 确认它确实能读到刚才选择的仓库，再到评审设置确认同一仓库。普通 GitHub 插件能读文件，不能单独证明 Codex 的写入和评审权限。安装应用和授权自己的账户，都要完成。
>
> 现在打开代码评审设置，搜索你自己的仓库。看清仓库策略、个人偏好和触发条件。以后换仓库，就沿同样路径选新仓库，不需要操作代码。
>
> 让 Agent 跟进这一条 PR。它会给你真实的评审结果链接。你打开以后，要看它有没有完成，以及审的是不是最新版本。收到请求、执行失败和完成后无发现，是不同状态。

### 修复后必须继续复审

> 第一轮发现问题以后，让 Agent 核实、修复并运行相关测试。修复提交上去，还要让最新版本重新接受评审。
>
> 只要这一轮又发现有效问题，就继续修复、测试和复审。完成条件是最新版本的评审已经结束，未解决的 P0 和 P1 都为零，已修问题有实际复测证据。关掉评论不等于修好了，审过旧版本也不能算新版本通过。
>
> 每一轮让 Agent 给出一张小表：发现多少、修好并测过多少、多少待复测、还剩多少 P0 或 P1。同一个问题跨轮出现，要去重，不能反复累加成不同缺陷。
>
> 现在打开缺陷分析页。先看日期范围，再看页面实际提供的评审数量和问题数量。这里帮助你看一段时间的情况，某个问题修好了没有，还要回到同一条 PR 的最新结果确认。
>
> 如果额度耗尽、权限不足，或者审查持续扩范围，Agent 应该说明卡在哪里。流程暂停不等于评审通过。

数量演示只用当次真实结果。Agent 按轮给“本轮提交、发现数、有效问题数、已修并复测、待复测、开放 P0/P1、结果链接”；累计数量另列。分析页中的时间、仓库或成员筛选器只讲实际可见项，不预设当前账户一定提供全部维度。数字为零时先确认时间与数据覆盖，不能据此推断零缺陷。

### 用一份真实历史结果解释数量

已通过 GitHub 连接器读取 [本项目历史 PR #1281](https://github.com/inernoro/prd_agent/pull/1281) 的实际记录。只统计 Codex 机器人带文件路径、非回复的行内发现评论，以评审编号分组，得到 8 轮共 23 条发现评论：7 条 P1、16 条 P2。这是评论数量，没有把重复问题、有效缺陷、已修复和当前开放状态混为一谈，也不是 OpenAI 分析页的截图。

| 历史轮次 | 本轮P1发现评论 | 本轮P2发现评论 |
|---|---:|---:|
| 1 | 1 | 2 |
| 2 | 1 | 2 |
| 3 | 1 | 1 |
| 4 | 3 | 1 |
| 5 | 0 | 3 |
| 6 | 0 | 3 |
| 7 | 0 | 2 |
| 8 | 1 | 2 |

> 看这份真实历史记录，中间三轮都没有新报 P1，后面一轮又报出了一条。所以数字不一定一路下降，也不能凭某轮的零就宣布整个任务完成。
>
> 这些是每轮新报的评论，历史问题可能重复，也可能还没有关闭。让 Agent 核实有效问题、修复与复测，再对最新版本继续审，才能判断这次是否真的完成。

本次未核实该历史 PR 的去重缺陷数、修复完成数及当前开放数，不展示虚构的修复率或最终绿灯。配套材料保存逐轮评审编号和原始结果链接，分析环节用来训练读数边界；登录后的 OpenAI 分析页仍须单独录制。此案例放入新增段 10:00—13:20，不额外拉长预算。

### 出问题后怎样反哺系统工程

| 事实分类 | Agent下一步 | 留下的长期改进与关闭依据 |
|---|---|---|
| 产品业务或页面真的失败 | 保留复现、版本、预期实际和截图，核实并修复 | 补能抓住原问题的回归；原场景和相邻路径复验 |
| 同一规则不同出口不一致 | 找SSOT和所有真实消费者，统一接线 | 单测与消费者守卫；单处破坏会失败、恢复通过，并进入实际执行流程 |
| 脚本误报、等错状态或截图不对应 | 修测试与取证逻辑，不让产品迎合错断言 | 重取真实证据并读回，保留原失败原因 |
| 登录、环境、版本或报告链路失败 | 修对应接入与环境，记录具体阻塞 | 正确版本可测、目标可访问、报告和证据能查收；未测到不叫产品坏了 |
| 预期不清或规则缺失 | 回到业务负责人确认，修改权威规范 | 场景与预期可观察，后续用例消费同一判据 |
| 同根因反复逃逸 | 查以前为什么没拦住，补永久回归并接入应运行的CI或稳定探针 | 下次同类错误有能变红且实际执行的检查；issue关闭不代替复测 |

反馈不是在报告留一句“有问题”就结束。问题按项目既有台账追踪到“待解决→已解决待验收→已验收”；记录去向、责任角色和关闭条件。对外发消息或创建事项按当次授权及既有流程处理，教程不擅自执行。

> 看到失败，先分清是哪一层。产品坏了就修产品；脚本错了修脚本；没有登录、环境不可达或报告没交成功，就写这次还没测出来。

### 查阅报告，怎样发现它有问题

本项目CDS路径：实际实例→侧栏“验收报告”（收缩时为“报告”）→正确项目与文件夹→报告台账中的本轮标题→正文→证据图。先看单份正文，不拿上方聚合卡或列表绿标代替结果。其他项目按适配时确认的实际入口查收。

| 阅读顺序 | 用户要问的问题 | 可发现的错误 |
|---|---|---|
| 目标与版本 | 这份报告测的是我这次改动吗 | 旧版本、另一分支、范围不对应 |
| 首屏结论 | 产品能用吗，测完了吗 | 没测到却说能用；缺口被绿色结论掩盖 |
| 执行覆盖 | 计划、执行、失败、跳过和未执行有哪些 | 只给总数，没有未测原因和补跑条件 |
| 问题与证据 | 什么动作触发，预期与实际怎样不同 | 截图不对应、异常不在图内、无可定位标注 |
| 复测与查收 | 修好后重新测了吗，别人也能看到吗 | 只关评论、只给本机草稿、图或内部链接打不开 |

## 第三章 单元测试 让测试抓住原来的缺陷

### 先用真实统计解释SSOT与单元测试

本章保留原有红绿、边界和两例消费者漂移，新增4分钟统计读回，共24分钟。先展示本次机器盘点页，按“主系统业务模块、LLMGW、CDS”说明数量及各自保护范围，再用原有案例解释统计背后的意义。

> 先看我们到底有多少测试。这里的文件数、用例数和实际跑过的数，是三件不同的事。每个数字都要说明来自哪个版本、覆盖哪里、有没有真正执行。
>
> 接着看这些测试守住什么。主系统的规则和页面、网关的身份与模型调用、CDS的预览与部署，各有自己的风险。不是数字越大就越可靠，而是关键规则有没有用例、所有出口有没有接上、工作流有没有真正跑。
>
> 网关的一些测试放在主系统后端目录，不能加两次。收集失败也不能写零测试，更不能把扫描到的数量写成全部通过。

用业务话展开“规则→权威源→所有消费者→测试断言→实际工作流→未覆盖范围”。这些测试应阻止已覆盖的已知回归悄悄进入，不能保证所有问题永远不会出现。讲义另列本次实际运行的窄范围检查，避免把它们扩成整个系统通过。

### 统计本身也要SSOT

本轮已用实际统计主源和讲义统计页演练：基线一致，在仓库外副本只将CDS文件选择数写回旧基线，检查出现预期失败，恢复后通过；把“框架选择的文件”改叫“已通过用例”也被拒绝。这个演练保护的是统计展示，不等于线上业务全部通过。

页面、教程和交付报告消费同一份有版本的清单；模块归属、去重、静态与执行口径也由同一规则定义。若只把数字抄成三份，下一次刷新就会出现N+1出口。要能发现某个出口写回旧数、把文件数改叫通过数，或将缺数据变成0。

> 统计本身也会漂移。页面叫文件数，报告却说通过用例数，虽然数字一样，结论已经错了。让Agent维护一份统计来源，每个出口都引用它；没有采集到就保留未知。

### 新增 SSOT 与单元及出口对齐

本段增加 12 分钟。保留原有小例子、失败归因、项目规则和回归，再讲：“为什么这一处修好了，另一个地方还在错？”

SSOT 指同一条规则的唯一权威来源。多个入口或出口可以是合理设计，风险在于各自抄了一份本应相同的规则。共享函数存在，也不代表所有消费者都已使用它。

用户提出的三类原因，作为可以重叠的排查线索：

| 排查线索 | 转成可以观察和修复的问题 | 判断证据 |
|---|---|---|
| 写代码的 AI 不行 | 漏读上下文、误解预期、遗漏调用者、测试未执行 | 任务输入、真实调用路径、diff 与执行结果 |
| 写代码的人不行 | 预期不清、只改症状、审查或回归遗漏 | 可观察预期、审查记录、相关路径与复测 |
| 没有 SSOT 对齐，出现多个独立出口 | 同一规则各写一份，只修其中一份；或共享逻辑未接入消费者 | 权威源、消费者清单、逐出口证据与防漂移检查 |

反复出现本身不能证明属于哪一类，还要核对版本、环境与覆盖。课程先复现再归因，不用能力评价代替定位。语义不同的规则保留各自契约，不为“统一”而硬合并。

按四层对齐：需求给出独立预期；单测验证权威规则；消费与接线检查确认各出口实际使用它；工作流检查确认测试真正执行。不能只测共享函数，也不能把源码字符串检查叫作完整业务验证。

### 案例一 CDS 预览地址改了一处还有旧出口

依据本仓库真实历史注释与现有测试选取。预览地址规则更新后，多个技能仍使用旧公式，用户反复拿到错误入口。课程不让学员重背地址公式，而是追踪权威计算及消费者。具体代码与测试见文末。

| 步骤 | 操作与观察 | 要锁住的结果 |
|---|---|---|
| 看差异 | 对同一项目和分支，比较平台、页面、CLI 与交付材料 | 各出口对应同一实际入口，差异可定位 |
| 找权威源 | 定位统一计算、项目身份与 API 返回 | 新生成行为归同一规则；消费者读取权威结果 |
| 测规则 | 使用已有单测检查同分支不同项目、普通与长分支等边界 | 项目不串、长度合法、行为符合独立确认的预期 |
| 测消费者 | 追踪页面、CLI、技能交付，并运行防旧公式和绕过共享入口的守卫 | 共享函数正确但一个出口仍另算时，检查能报警 |
| 逆向验证 | 在隔离副本接回一个旧计算出口，确认对应检查失败，再恢复 | 证明防漂移检查能抓住“又抄了一份” |

合法的旧链接解析兼容和明确白名单按边界保留，不能当作新的生成出口误删。扫描守卫辅助发现漂移，地址实际可用与用户路径还需运行验证。

案例口播：

> 第一个案例，预览地址在一个地方修对了，另一个技能还在自己算。只给共享函数补单测，旧出口可能继续存在。
>

## 第五章 严厉版标准 每个结论都拿得出依据

### 开章与原理口播

> 到这里，我们已经有了审查记录、页面证据、回归用例和链路结果。最后一章，核对这些材料能支持什么结论。
>
> 先看测的是不是目标版本，再看核心行为有没有执行。接着核对证据能不能打开，以及适用主题、移动端、相关负面和恢复路径是否覆盖。
>
> 严格执行，还包括把未知写清楚。没有测到，不等于产品一定坏了；它意味着这一部分暂时没有足够依据作质量承诺。

### 进入实操的口播

> 我们把结论分开写。产品质量回答发现了什么缺陷，核心用例是否通过。验收完整性回答哪些已覆盖，哪些无法验证或尚未执行。
>
> 然后按现有规范给出综合结论，写清发布建议和判定性质。不要只留一句“全部通过”。

### 现场观察

准备两份明确标为教学示例的报告：一份有可复现的核心失败，一份未发现产品缺陷但缺少必要覆盖。让学员先判断，再打开对应证据，分别解释产品失败与覆盖不足。使用规范的五项结论和既有枚举，不用总分掩盖阻断问题。

### 读结果与收尾口播

> 对发现的阻断问题，要指出触发条件、影响和复测办法。对覆盖缺口，要指出缺什么、由谁补、补到什么程度才能关闭。
>
> 同时守住范围。轻微问题按它的实际影响记录；关键风险已经覆盖，继续加测也不会改变判断时，就停止追加无关测试。
>
> 最后打开一次交付链接，确认别人能读到证据，能找到每个结论的依据。
>
> 暂停，给你自己的结果写出五项结论。每写一个“通过”，就指向一份证据。

### 本章节奏表

| 本章位置 | 内容 | 剪辑和学习动作 |
|---|---|---|
| 00:00—00:45 | 将前四章产物放回交付卡 | 快速回顾，沿同一张任务卡收束 |
| 00:45—02:10 | 核对版本、实际执行和证据 | 每次只展开一个结论及其依据 |
| 02:10—03:40 | 比较产品失败与覆盖不足的教学示例 | 先给五秒判断时间，再讲答案 |

## 独立练习 换一个问题再做一遍

### 固定口播

> 现在换一个相似问题。不要直接复制刚才的答案，先独立向 Agent 说明它的预期；让它完成代码和测试操作。
>
> 让 Agent 整理五样东西给你核对：测试记录、修复与复审记录、有效失败和修复后的测试结果、真实用户路径证据，以及交付结论。
>
> 遇到无法执行的步骤，把阻塞条件和缺口写清楚。它不能变成一项悄悄打勾的通过。
>
> 完成以后，请另一位同事只看你的材料，回答三个问题：这次测了什么？为什么可以这样判断？还有什么没有验证？
>
> 如果他能找到证据，你也能说明边界，这次交付才有了可复查的依据。下一次改动，就从这张任务卡重新开始。

本节用一张新的练习卡演示如何起步，用一份交付示例讲清评分依据，最后留十秒暂停卡。采用已提供好环境与身份的等价问题；学员实际练习时间另计。带教者观察卡点，不代替点击和填写。

## 收尾 何时触发什么方法，真实开发怎么做

### 方法与场景速查

主片先讲四个：MECE式风险拆分、真实链路追踪、Agent模拟反向检查、真人网页验收。其余方法放查询表，不要求新人背命令。

| 什么时候 | 方法与本项目实际入口 | 解决什么 | 不能替代什么 |
|---|---|---|---|
| 需求说不清 | 需求校验 /validate | 目标歧义、不可观察或重复功能 | 业务负责人确认正确预期 |
| 想查漏了哪些风险 | MECE式六维风险 /risk | 只测正常路径，遗漏权限、容量、恢复等 | 真实测试与风险判断 |
| 想知道功能怎样串起来 | 链路追踪 /trace | 用户动作到页面、接口、存储与依赖的交界 | 各交界实际运行证据 |
| 代码写完换视角挑错 | human-verify /verify | Agent模拟反向质疑、边界与状态检查 | 真人已经实际操作 |
| 前后端/桌面字段对不上 | 跨层检查 /deep-trace | 字段、类型、序列化与异常接缝 | 用户完整旅程 |
| 模型选A却跑B | 模型链路 /llm-trace | 从真实请求到实际上游模型定位 | 通用全系统验收 |
| 要真正的人试用 | 真人验收 /uat | 是否看懂、找到入口并完成业务 | 自动化测试、技术前置准备 |
| 验收不断逃逸同类问题 | /验收债务，补永久回归 | 发现旧绿灯为什么没拦住 | 当次修复与复验 |

本仓库没有查到独立的“/mece”或“/humen”命令；按已有真实技能讲方法，不造快捷名。human-verify的执行者仍是Agent，/uat由Agent准备网页步骤、真人亲自操作；技术准备与诊断仍全部交Agent。

### 真实开发的顺序

| 顺序与触发点 | 人做什么 | Agent做什么、留下什么 |
|---|---|---|
| 收到需求或缺陷 | 说目标、预期或症状 | 查询项目和版本，澄清成功标准；缺陷先保留现场 |
| 方案与范围确定前 | 确认业务约束 | 风险拆分、链路追踪、SSOT与消费者盘点，设计需要哪些证据 |
| 实现与低成本检查 | 确认目标没有误解 | 实现、有效失败、修复、单测与边界、必要构建及影响回归 |
| 提交与代码评审 | 必要授权和范围决定 | 核实发现、修复复测、对最新版本复审；无开放P0/P1再进入后续交付 |
| 预览真正可测时 | 必要登录授权 | 查询实际入口与运行版本，融合视觉和联合验证，展示用户动作与结果 |
| 发现失败时 | 业务预期有歧义才确认 | 分类根因，修对应层，补同类回归，更新后重跑受影响验证 |
| 报告与真人查收 | 从真实入口体验业务并读结论 | 按项目正式位置交报告，检查证据可读，提供真人步骤和未测关闭条件 |
| 运行后或定期 | 反馈真实症状 | 按已配置触发巡检，将逃逸问题反哺回归、SSOT与工作流 |

这是执行建议，不声称仓库已经自动串起所有环节。纯文档或低风险非运行变更按风险裁剪，不能机械重复全部方法；教学五章顺序也不要求日常先跑昂贵截图再跑便宜单测。修改后要重新核对版本和受影响验证，失败回到对应环节，不跳成通过。

### 最后五分钟口播与节奏

> 今天我们从一个真实问题开始。你负责把目标说清，Agent负责代码、版本、测试和修复。每次说通过，都要找到对应证据。
>
> 代码评审帮我们找值得验证的问题；修复以后继续审最新版本。视觉验收看用户从哪里进入、点完得到什么，也看报告有没有真正交到项目约定的位置。
>
> 单元测试把一条规则守住；SSOT让所有出口使用同一份定义。统计要分清文件、用例、执行和未执行，数量不能替代保护范围。联合测试继续看这些层串起来，用户能不能完成整件事。
>
> 遇到问题别只修表面。先保留现场、分清根因，修复后复测，把会再犯的问题放进有效且实际执行的回归。需求和规则有缺口，就回到权威来源补齐，不再复制一套。
>
> 方法也按场景选：担心遗漏先拆风险，不知道断在哪先追链路，写完让Agent换视角查，真正的使用体验再请人按网页步骤走一遍。AI模拟审查，不等于真人已经验收。
>
> 真正开发时，先目标和风险，再实现与便宜检查；代码评审修复复审，可用预览上做视觉和联合验证，最后查收报告与适用的真人验收。你可以在下任务时约定完成后验收，也可以手动、修复后、发布前或按已配置的定时流程触发。
>
> 最后用一页回答：从哪里触发，用了什么方法，解决了什么问题，哪些有证据，哪些还未知，报告在哪里。让下一位同事能复查，也让下一次同类改动有回归可守。

节奏：前1分30秒按场景选方法，接下来2分钟沿真实开发顺序串一次任务，最后1分30秒回顾五类方法、工程反馈与交付。最后暂停卡停10秒：“选一个真实任务，把目标交给Agent；用证据解释结果。”

## 节奏与剪辑执行标准

### 整体节奏

每章保持“问题—解释—操作—读结果—练习—连接下一章”的顺序。前 20 至 40 秒让观众知道要解决什么；中段只演示一条主闭环；末尾明确本章产物。复杂分支用独立短段补充，不在主操作中突然展开另一套任务。

讲解以能听懂为先，不以信息密度取胜。试读可从每分钟约 200 至 240 个汉字起步，数字、命令、术语和判断句另留停顿；最终以实际录音及目标学员试听为准。不要通过压缩停顿，让原来较长的口播勉强塞进 82 秒。

原有50分钟与三轮新增51分钟均以真实操作和读结果占主要时间，固定口播只是骨架。若实际演示比预算短，就缩短成片；若过长，先剪重复输入与无信息等待，保留本轮要求的内容。不能重复播放画面或拉慢声音来填时长。

### 具体的快慢与停顿

| 场景 | 建议节奏 | 可观察的剪辑要求 |
|---|---|---|
| 说明目标、章节连接 | 中速，句子短 | 画面对象先被点名，再切换 |
| 解释因果、失败归因、交付判断 | 放慢 | 一个判断讲完停约两秒，再揭示依据 |
| 手臂逐笔绘图 | 按解释分段 | 一个关系才画一条线，跨笔画抬笔；图画完后退出 |
| 发送 Agent 指令、关键点击、错误出现 | 正常速度 | 保留动作前状态、动作和结果；不在关键处倍速 |
| 重复输入、构建与服务等待 | 可缩短或有限加速 | 标明省略阶段、实际等待；保留失败和最终结果 |
| 新图、新结果或对照表出现 | 留三至五秒阅读窗口 | 先给观众找信息，再开始解释；信息多则拆屏 |
| 可复制提示词 | 简短解释意图 | 完整文字进讲义，不逐字念长命令 |
| 暂停练习卡 | 停八至十秒 | 只写当前动作、预期产物和继续条件 |
| 章节切换 | 约半秒柔和转场 | 先交代上一章产物怎样交给下一章 |

以上是制作起点，可随内容和试学调整。旁白中的自然停顿与画面阅读时间分别安排；阅读时不同时讲新的规则。

### 三个明确的节奏转折

第一处在视觉测试：从“入口可达”走到“动作后的真实反馈”，让观众先预测结果。第二处在单元测试：核对原失败的实际值，再看到同一断言修复后转绿。第三处在联合测试：首次成功后重启再测，将注意力从当前可用推进到持久可用。

第五章收束前面所有产物，降低转场频率，让学员读证据、做判断。严格标准的力量来自清晰的事实和边界，配乐与快速切镜不承担判定作用。

### 屏幕文字与口播的分工

屏幕主句每次只表达一个判断，优先控制在一行；图中只保留对象、条件、结果与必要标识。字幕按语义拆分，避免把“预期为零”与“实际为六”断成难以比较的片段。

旁白负责解释关系，图负责展示关系，录屏负责证明实际操作。可复制讲义提供给 Agent 的完整任务，技术执行细节留在证据中。图形逐笔绘制与汉字标签排版分别标注，不声称做到了汉字规范笔顺。

## 开录前与试学后的核对

| 阶段 | 检查内容 | 完成依据 |
|---|---|---|
| 文案试读 | 语句能否自然读出、术语是否有解释、实际结果分支是否齐全 | 标出难读句与过长段，修订后重读 |
| 录音与定时 | 实际声音、停顿、字幕和手臂动作是否对应 | 以音频重新排时间，不按旧字幕时长硬套 |
| 实操录制 | 目标版本、账号、操作、结果与证据是否一致 | 逐章读回，未执行处如实标注 |
| 剪辑审片 | 是否切掉关键输入、失败、反馈或恢复 | 关键动作前后连续可观察 |
| 新人试学 | 能否独立交出每章产物 | 至少两位目标学员跟练；记录求助点、误判和耗时 |
| 课程收口 | 文案与实际画面有无矛盾，交付链接是否有效 | 修正后再验，视频播完不代替练习通过 |

手绘制作方式已通过用户方向确认。现有试片为字幕版，中文旁白尚未生成；本稿的时间安排须在实际声音到位后精校。课程方法可按本稿先评审，不以配音能力缺口阻塞文案工作。
