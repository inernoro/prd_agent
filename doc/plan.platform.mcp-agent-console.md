# MCP 智能体接入台 · 计划

> **版本**：v0.2 | **日期**：2026-09-03 | **状态**：第一期已实现，PR #1484 评审中

**一句话**：把平台的五块核心能力做成外部智能体可直接调用的 MCP 工具，并在侧栏左下角给一个三步就能连上的接入入口。
**谁该读**：要决定这件事做不做、怎么做的人，以及接下来动手的工程师。
**读完能做什么**：知道现在已经有什么、还缺什么、分几期做、有哪些坑必须提前避开，以及有哪几个问题需要拍板。

## 二、调研结论：已经有什么

后端的 MCP 协议层**已经落地并在跑**，不需要从零建：

| 已有件 | 位置 | 说明 |
|---|---|---|
| MCP 网关 | `POST /api/mcp`（`McpGatewayController`） | Streamable HTTP + JSON-RPC 2.0，支持 initialize / ping / tools/list / tools/call，无状态 |
| 鉴权 | `sk-ak-*` AgentApiKey + `scope` claim | 网关只读 claim，不自己验密钥 |
| 内置工具 | `McpBuiltinTools` | 5 个：海鲜市场搜索、技能详情、知识库列库、列条目、读正文（全是只读） |
| 动态工具 | `AgentOpenEndpoint` 登记表 | 登记一条开放接口 = 自动多一个工具，零代码 |
| 权限桥 | `AdminPermissionMiddleware.HasScopeGrant` | scope `a:b` 自动满足后台权限位 `a.b`，且写蕴含读 |
| 用户文档 | [doc/guide.platform.mcp-connector.md](./guide.platform.mcp-connector.md) | 三步接入 + curl 验证 + 排障表 |

**缺口正好是用户这次点名的部分**：

1. 前端入口从未落地（原设计的 P2 阶段）。今天用户要连上，得自己看文档、去海鲜市场页面找「接入 AI」、手工拼 URL。
2. 五块点名能力里，只有海鲜市场（读写都有开放接口）和知识库（只有读）到位；**视觉创作、文学创作、网页托管三块完全没有对外开放层**。
3. 没有按 Key 的用量配额与审计视图，agent 侧循环调用无人拦。

### 五块能力现状对照

| 能力 | 现有接口 | 认证形态 | 差什么 |
|---|---|---|---|
| 海鲜市场 | `/api/open/marketplace/skills`（搜索/详情/下载/上传/收藏） | sk-ak + scope，已就绪 | 只差把写工具接进 MCP |
| 知识库 | 读走 `/api/open/document-store`；写走 `DocumentStoreController`（JWT） | 读就绪；写不对 sk-ak 开放 | 需要一个写入开放层 |
| 视觉创作 | `/api/visual-agent/image-gen/*`（异步 run 队列） | JWT + `visual-agent.use` + 读 `sub` | 需要开放层，且要把复杂契约收敛 |
| 文学创作 | `/api/literary-agent/*`（工作区、提示词、配图 run） | 同上 + `literary-agent.use` | 同上 |
| 网页托管 | `/api/web-pages/*`，其中 `from-content` 是纯 JSON 建站 | JWT + `web-pages.read/write` | 同上，`from-content` 天然适配 MCP |

## 三、拦路的那一件事，以及为什么这么选

三块创作类能力的接口全部用 `GetRequiredUserId()` 取身份，而它只读 JWT 的 `sub`；`sk-ak` **有意不注入 `sub`**（避免最小权限密钥摇身变成账号主人）。所以密钥直接打过去必然 401。三条路：

| 方案 | 做法 | 判断 |
|---|---|---|
| A 薄开放层 | 每块建 `/api/open/*` 控制器，显式 scope + 读 `boundUserId`，内部调同一套 Service | **推荐** |
| B 回环降权票据 | 网关回环时签发 60 秒内部票据（`sub` = 密钥主人，权限位取 scope 子集） | 常数工作量，但等于新造一套鉴权面，一处判据有洞即全权限泄漏 |
| C 给 sk-ak 注入 sub | 一行改动 | 否决。全站走 JWT 的接口对密钥敞开，越权面无法枚举 |

选 A 的关键理由不是安全（那是底线），而是**开放层同时是契约收敛层**：现有生图接口要 `platformId + modelId + size + items + responseFormat + maxConcurrency`，直接暴露给智能体只会让它猜参数猜到失败。MCP 工具必须收敛成「给一句话就出图」（最小输入原则：系统查得到的值不许摆成输入框，对智能体同理）。这层收敛无论走哪条路都要写，那就写在有权限闸门的地方。

## 四、第一期开放哪些能力

按能力讲，不逐个列工具名与 scope —— 那份清单在 `McpCapabilityCatalog` 与 `McpBuiltinTools` 里，
是唯一事实源，也只有它跟得上代码。这里写的是「用户勾了这块能力，智能体能替他做什么」。

| 能力 | 勾了它，智能体能做什么 | 第一期不做什么 |
|---|---|---|
| 视觉创作 | 一句话生图，图落进用户自己的视觉创作空间；任务在服务端跑，关掉客户端也不会断 | 不做图片编辑与批量重跑 |
| 文学创作 | 开工作区、写正文、接着往下写，产出留在文学创作空间 | 追加写不可重试（见「已知边界」），删除不开放 |
| 知识库 | 读用户的文档空间，把整理好的稿子写回自己的库 | 只收纯文本；带结构模板的库（如验收报告库）不开放写；**自己没有文档空间读/写权限的人签不出这块能力**（这个 scope 等价于那两个权限位） |
| 网页托管 | 写完一页 HTML 直接托管，回一条能点开的地址；建 owner-only 分享链 | 不做删除、不做公开发布、不收 zip |
| 海鲜市场 | 找技能、把技能取到自己名下 | 不做上传：技能包是 zip，MCP 传不了二进制 |

**默认不全开**。接入向导按能力勾选，只签发被勾中的 scope；没勾的能力在那把密钥下根本不出现 ——
既省智能体的上下文，也是最小权限。写入档要单独再确认一次。

**异步任务的契约**：生图入队即返回 `runId`，用户与智能体都靠它查进度；服务端权威 ——
客户端断开不取消任务。图片回可访问地址，不回 base64（一次几张就能把智能体的上下文顶满）。

## 五、左下角入口长什么样

侧栏账号菜单（`AppShell` 的账号下拉，目前有「我的空间 / 学习进度 / 个人主页 / 设置 / 模型网关 / …」）新增一条「连接我的智能体」，点开是三步向导弹窗：

1. **选能力**：五张卡（视觉创作 / 文学创作 / 知识库 / 网页托管 / 海鲜市场），勾选即决定 scope；每张卡下面一行大白话写「勾了它，你的智能体就能替你做什么」。默认只勾读，写入项要单独确认。
2. **生成密钥**：一键出 `sk-ak-*`，默认 90 天，明文只显示一次，就地给复制按钮。
3. **接进客户端**：直接给三份可一键复制的配置——Claude Code 的一行 `claude mcp add` 命令、Claude 桌面自定义连接器的 JSON、Codex 的 toml 片段。端点地址一律取 CDS 返回的真实预览/生产地址，不在前端拼域名（`CLAUDE.md` 规则 11）。

向导底部常驻一块「连通自检」：点一下由后端代发一次 `tools/list`，当场显示这把密钥能看到哪几个工具。接入类流程不给自测，就等于让用户蒙眼填表。

密钥管理（列表、最近调用、用量、撤销、续期）放 `/settings` 下一个 tab，向导里给一个「管理我的密钥」跳转，不把两件事挤在一个弹窗。

## 六、会遇到的特殊情况

### 授权与安全

1. **密钥 scope 可能越过用户自己的权限**（现存缺口，必须在 P1 堵）。现在创建密钥只校验 scope 格式与白名单，不校验密钥主人是否真有那个后台权限位；而权限中间件见到 scope 就放行。一旦把 `visual-agent:use`、`web-pages:write` 加进白名单，普通用户自建密钥即可绕过管理员分配的权限。**处置**：创建/更新密钥时取「用户自身权限位」与「请求 scope」的交集，超出部分直接拒绝并说明原因；用户权限被回收时，已签发密钥的对应 scope 同步失效（调用时二次校验，不只在签发时校验）。
2. **破坏性动作没有二次确认**。MCP 没有「弹窗让用户点确认」这回事，智能体一句话就能删站点、删文档、把技能发到公开市场。**处置**：删除与公开发布类动作首批**不进工具清单**；确有需要时单列 `:destructive` scope，并要求参数显式带 `confirm: true`，且工具描述里写明不可撤销。
3. **密钥会被明文写进智能体配置文件**，用户还可能把配置贴给同事。**处置**：默认 90 天有效期、支持一键撤销与重签、密钥列表展示「最近调用时间与来源」，让异常可见。
4. **一把密钥当作多台设备共用**，撤销时误伤。**处置**：向导默认按客户端命名（如「我的 Claude Code」），鼓励一机一钥。

### 协议与客户端

5. **各客户端认证方式不统一**：有的支持自定义 Header 直传 Bearer，有的只认 OAuth，有的只吃本地 stdio。**处置**：v1 给 Header 方案 + 一个 `npx` stdio 代理兜底；P5 上 OAuth 才算真正「点一下就连上」。
6. **工具名与描述有硬限制**（名称正则与 64 字长度、描述会被截断）。动态工具名已带 32 位 id 后缀占位，新增内置工具要预留长度。
7. **协议版本演进**：网关目前只声明一个版本，客户端版本对不上时行为由客户端定。**处置**：接入向导写明已验证过的客户端与版本，排障表补一行。

### 数据与上下文

8. **上下文爆炸**：知识库长文、生图 base64、市场大结果集。**处置**：所有列表工具强制分页与条数上限，正文类工具带 `maxChars` 并在截断处给出续读指引，图片默认给链接。
9. **二进制上传进不了 MCP**（知识库传 PDF、网页托管传 zip、图生图传参考图）。**处置**：首批只做文本直传（Markdown / HTML / 纯文本）；二进制走两步式——工具返回一个一次性上传地址，让智能体用 shell 上传后回执 id。首批把这条明确写进「暂不支持」，不含糊。
10. **智能体重试导致重复产出**（重复建站、重复入库、重复烧图）。**处置**：写入类工具一律接受 `clientRequestId` 做幂等键，生图复用现有的 `Idempotency-Key`。

### 运行与成本

11. **循环调用烧钱**：生图与文学创作背后是真实模型调用。**处置**：按 Key 的日请求数与日 token 配额（`AgentApiKey` 已有字段，接进这条链路）、每分钟速率上限，触顶时返回可读原因而不是裸 429。
12. **模型未配置时的裸报错**。现有生图接口在默认模型没配时返回 `VISUAL_MODEL_NOT_ALLOWED`。**处置**：工具错误里要带「去哪配、谁能配」的下一步，让智能体能把话转达给用户，而不是回一句失败。
13. **长任务与断线**：MCP 连接断开不得取消服务端任务，重连后能用 `runId` 接回。

### 部署与环境

14. **分支预览与生产共享同一套数据**（跨项目隔离规则的通道 4 与通道 8）。在预览环境生成的密钥能读写共享库里的真实数据；新增的 run 类工具必须沿用 `DeploymentSlug` 作用域，禁止裸状态认领。
15. **端点地址不能手拼**。向导展示的 URL 只能来自 CDS 的 `previewUrl`，本地 slugify 有专门的守卫在扫。
16. **sk-ak 打 JWT 接口必 401** 这个坑已经踩过一次并记在指南里；新增开放层时必须走 `boundUserId`，不要图省事登记一条指向 JWT 接口的动态工具。

## 七、分期与验收判据

| 期 | 内容 | 判据（缺一不算完） |
|---|---|---|
| P1 授权收口 | scope 白名单扩容、用户权限交集校验、调用时二次校验、按 Key 配额与速率 | 单元测试证明「用户无 `visual-agent.use` 时签发该 scope 被拒」且「权限回收后旧密钥调用被拒」 |
| P2 能力开放层 | 四个 `/api/open/*` 薄控制器 + 14 个新工具接进 `McpBuiltinTools` | 每个工具有 curl 级冒烟；生图走完「入队 → 出图 → 可访问」全程 |
| P3 左下角入口 | 账号菜单入口 + 三步向导 + 连通自检 + 密钥管理 tab | 真人路径进入，双主题各看一遍 |
| P4 验收 | 真实客户端（Claude Code 与 Codex 各一）连上并跑通五块能力各一条链路 | 产物真的出现在截图里，不接受停在「生成中」的图（验收闭环原则：截图里必须出现真实产物） |
| P5 OAuth | 标准授权流，用户不再手工贴密钥 | 点「连接」跳授权页勾能力回跳即用 |

P1 与 P3 弱耦合，可并线；P2 内部四块彼此也不阻塞，可各占一条轨道（并线开发原则）。

## 八、需要拍板的四个问题

1. **写入权限的默认姿态**：向导默认只勾只读、写入要用户显式确认，还是默认把五块的读写全给（更方便，但一把密钥泄漏的后果大得多）？建议前者。
2. **破坏性动作**：删除类、公开发布类工具首批是否一律不做？建议不做，等 OAuth 与二次确认机制齐了再说。
3. **配额默认值**：按 Key 的日生图张数与日请求数默认给多少？没有默认值就等于不限。
4. **OAuth 排期**：P5 是紧跟 P4 做，还是先让密钥方案跑一段时间收反馈？
