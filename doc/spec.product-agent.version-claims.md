# 产品管理正式申领与历史追溯 · 规格

> **版本**：v1.2 | **日期**：2026-11-08 | **状态**：已落地

**一句话**：说明常规正式版本如何继承立项、校验申领与保留后续公告，并用具体业务实例区分编号、状态和交付证据。
**谁该读**：使用版本申领、解释历史记录、实现关联流程或验收产品规则的产品、工程与测试人员。
**读完能做什么**：判断一个申领是否符合当前源码规则，解释新旧资料的适用方式，并知道现有验证能证明到哪一层。

## 一、范围与依据

本规格从工作区基线 `c0ec71f15` 中已有的正式申领变化开始回放，后续已针对发现的需求版本引用和流转请求缺陷实施修复。正式申领与公告后补的业务选择保持原有语义；修复不回收编号、不迁移历史资料。产品结构见[现状设计](./design.product-agent.md)，申领理由与代价见[决策补录](./pdr.product-agent.002.version-claim-boundary.md)。

本规格区分“源码中可确认的行为”“已有测试表达的要求”“本轮执行的检查”和“待验证的用户效果”。对未来生效规则的选择仍由对应决策说明，不能用本页将实现现状自动批准为永久业务承诺。

## 二、术语、用户路径与规则

### 先区分五种事实

| 用语 | 本试点中的含义 | 不能由它单独推导 |
| --- | --- | --- |
| 申领成功 | 来源与资料通过当前规则，正式编号和记录已保存 | 环境部署成功、所有需求均已推进 |
| 登记为已上线 | 当前正式 V 记录的状态；申领时写入 | 真实产物可访问、客户已经验收 |
| 资料完整 | 对指定对象、指定阶段所需资料已齐；常规发号不要求公告非空 | 公告存在就证明所有交付内容正确 |
| 部署可用 | 指定版本的目标环境和产物有实际可用证据 | 所有用户任务或合同验收均完成 |
| 验收通过 | 明确范围内的任务、场景及预期结果经验证 | 未覆盖的对象、其他版本、其他环境也已通过 |

同一词需要注明对象。例如需求的“已上线”来自其流转路径，不能拿正式 V 的同名状态替代需求自身结果；后补公告也不改写原发号事实。

### 当前流程

常规路径为：用户选择产品及已有有效 T → 查看继承资料与历史对照 → 填写必要基础信息 → 服务端复查来源、权限、历史关系和重复申领 → 生成并保存 V 记录 → 尝试推进关联需求 → 后续补充或匹配公告。

| 规则 | 当前行为 | 边界 |
| --- | --- | --- |
| 立项来源 | 常规正式申领使用同产品、已通过且有有效 T 号的立项 | 不接受手填 T 号绕开已有记录 |
| 资料继承 | 方案名称、资料与原立项需求等来自所选 T | 正式申领不能静默改写原 T；显式追加与历史继承按实际路径分别解释 |
| 基础信息 | 检查成员、上线时间、有效负责人及适用的培训时长等 | 具体字段条件以当前服务端规则为准，不因页面隐藏而绕过 |
| 防重与历史 | 同一 T 来源有正式记录、旧登记或占用时拒绝重复申领；历史歧义需要匹配本次候选的确认 | 不以浏览器旧结果当作永久资格 |
| 功能与公告 | 常规申领允许空功能清单、空公告地址 | 不是放松全部业务规则；临时优化仍要求自己的功能清单 |
| 记录状态 | 当前 V 创建时写入已上线及对应时间 | 不能据此证明真实环境已部署或用户已验收 |
| 需求推进 | 关联需求在流程存在对应流转边时尝试推进 | 无边时可能跳过；正式记录成功不保证全部需求同步完成 |
| 公告后补 | 后续可补链接；自动更新以应用与完整 V 号唯一匹配 | 匹配歧义或地址冲突保留原数据，不猜测覆盖 |

旧规划版本、正式 V、功能版本和导入存档必须分别理解，不能把“有版本号”当成“有完整规则快照”。

## 三、验收实例

以下产品 A、T 和人员代号均为示意。服务端聚焦测试使用隔离数据库，公告测试使用受控响应；公网排期验证使用独立命名的测试对象并已清理，未修改既有业务对象。覆盖层次分别标注，不能把服务端测试当成完整登录态验收。

| 场景 | 输入与前置 | 当前预期 | 证据与待补项 |
| --- | --- | --- | --- |
| S01 正常常规申领 | 产品 A 的有效 T，必需基础资料有效，功能与公告均为空 | 允许产生正式 V，继承 T 的需求，公告留空 | 隔离数据库申领测试通过；完整公网申领路径待验 |
| S02 保护原始方案 | 选择有效 T，额外提交另一方案名称或资料 | 常规正式记录仍继承 T；原 T 不被改写 | 原 T 保护的隔离数据库测试通过 |
| S03 重复或历史占用 | 相同 T 已有正式记录、旧正式登记或来源占用 | 拒绝第二次发号，给出冲突而不是重新编号 | 来源防重、保留编号、并发申领等聚焦测试通过；不宣称所有中断场景均覆盖 |
| S04 来源不成立 | 手填 T、另一产品的 T、未通过或没有有效号的 T | 拒绝常规正式申领 | 来源无效且无写入的隔离数据库测试通过；公网身份路径待验 |
| S05 临时优化边界 | 临时路径带 T，或不带 T 但无功能清单 | 按专用条件拒绝，不能套用常规简化规则 | 临时路径及功能清单校验测试通过；组合与公网路径未全量验收 |
| S06 公告后补 | 对既有 V 后补合法地址 | 保留 V 号及原发号时间，只补相关资料 | 隔离数据库测试通过，断言补链接后原编号与发号时间不变 |
| S07 公告冲突 | 同应用同完整 V 号出现多个候选或原地址不同 | 不猜测覆盖，保留原资料并计入冲突 | 公告同步受控响应与隔离数据库测试通过；真实上游全量匹配未在此试点触发 |
| S08 需求排期 | 手动转已排期但版本缺失、不存在、已删除或属于另一产品 | 前端要求补字段，服务端拒绝无效依据，原状态与引用不被部分改写 | 隔离数据库拒绝测试通过；公网确认跨产品拒绝不改原数据，有效排期保存状态和双向关联 |
| S09 自动状态推进 | V 保存成功，某关联需求没有对应流程边 | 该需求可被跳过，不能报告全部已推进 | 已有流程边的正向服务端测试通过；多流程、缺边及正式发号后中断恢复仍开放 |
| S10 已填写关联的流转请求 | 弹窗填写有效立项、上线关联、版本或缺失标题后提交 | 控件填写后仍可见，发送内容保留填写值；功能对象不被错误要求需求专用依据 | 6项组件回归通过；公网捕获版本选择提交且控件保留。立项、上线选择有组件诊断，未逐一走公网路径 |
| S11 历史失效版本关联 | 需求已有被删除、不存在或属于其他产品的版本引用 | 编辑关联时显示失效项；用户显式取消后可选择本产品版本或清空。列表加载失败不误判或保存，服务端拒绝不关闭弹窗、不报告成功 | 组件回归覆盖可见修复、清空、加载重试与保存拒绝；隔离数据库回归覆盖修复旧引用后完成排期。此项是 PR 审查修订，不属于旧基线已完成的公网验证 |

## 四、一次变更应检查的影响

未来若重新把公告或功能清单变成发号门槛，首先要明确是针对新申请、在途申请还是已有记录；是否改变“已上线”的含义；是否需要独立的部署与验收证据；以及重复提交、公告匹配、历史确认和需求推进怎样兼容。

变更应关联新的 PDR，更新本规格及相关实例，再以测试与真实环境证据验证。不能只改一处按钮必填校验就宣布规则整体生效，也不能依据旧计划静默恢复已取消的门槛。

| 受影响对象 | 变更前必须回答的问题 | 本试点的保护边界 |
| --- | --- | --- |
| 新申请与在途申请 | 从哪次提交、哪个业务节点起使用新条件；旧表单重试怎么办 | 不把浏览器刷新或重试当成重新取得申领资格 |
| 原始 T 与已发 V | 继承资料能否改变；后补是否改变原发号事实 | 不回收编号，不用新要求静默重写原 T 或既有 V |
| 导入与历史记录 | 当时没有部署或验收证据时如何显示 | 明确未知，保留来源；不能批量补造“已交付” |
| 需求与跨产品关联 | 状态由哪个入口推进；依据属于哪个产品 | 服务端继续核对有效归属；无边或失败不能声称全部推进 |
| 报表、通知与外部消费者 | 谁把状态当成什么承诺；是否依赖原字段与编号 | 新含义需要逐个核对消费方，不以界面改名代替兼容设计 |
| 权限、恢复与验证 | 谁能改证据；部分失败如何恢复；哪些实例应继续成立 | 采用真实权限与可追溯结果，代码回退不等于撤销已经发出的承诺 |

## 五、验证层次与当前边界

基础运行证据对应 `fc26e26c6`。[该提交 CI](https://github.com/inernoro/prd_agent/actions/runs/42212137020)与[镜像构建](https://github.com/inernoro/prd_agent/actions/runs/42212120734)均通过。后续失效关联修复与最终检查跟踪于 [PR #1905](https://github.com/inernoro/prd_agent/pull/1905)，不借旧提交的绿灯证明新行为。CI 的常规测试也不代替需要数据库的集成测试。

隔离数据库检查已执行申领、防重、来源、原 T 保护、公告后补、需求版本引用和流转闸门；公告匹配使用受控上游响应验证冲突与失败不改写成功进度。组件交互检查验证填写与请求。公网浏览器则从登录、百宝箱、产品管理进入测试需求，确认选择版本后控件保留、请求携带版本、状态进入已排期且双向关联正确；跨产品引用被拒绝，原标题与关联不变，测试对象清理成功。

尚未完成的范围是常规正式申领的完整公网路径、立项与上线选择的逐项公网操作、自动推进的多流程与中断覆盖，以及使用者是否正确理解状态。用户价值观察按[实操指南](./guide.platform.decision-practice.md#四让未参与讨论的人独立回放)执行，记录查找时间、错误与追问；本页不预填改善幅度，也不因文档齐全关闭这些待办。
