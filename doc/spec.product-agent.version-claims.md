# 产品管理正式申领与历史追溯 · 规格

> **版本**：v1.1 | **日期**：2026-11-06 | **状态**：关联与请求修复已完成聚焦验证；预览验收待补

**一句话**：说明常规正式版本如何继承立项、校验申领与保留后续公告，并用具体业务实例区分编号、状态和交付证据。
**谁该读**：使用版本申领、解释历史记录、实现关联流程或验收产品规则的产品、工程与测试人员。
**读完能做什么**：判断一个申领是否符合当前源码规则，解释新旧资料的适用方式，并知道现有验证能证明到哪一层。

## 一、范围与依据

本规格从工作区基线 `c0ec71f15` 中已有的正式申领变化开始回放，后续已针对发现的需求版本引用和流转请求缺陷实施修复。正式申领与公告后补的业务选择保持原有语义；修复不回收编号、不迁移历史资料。产品结构见[现状设计](./design.product-agent.md)，申领理由与代价见[决策补录](./pdr.product-agent.002.version-claim-boundary.md)。

本规格区分“源码中可确认的行为”“已有测试表达的要求”“本轮执行的检查”和“待验证的用户效果”。对未来生效规则的选择仍由对应决策说明，不能用本页将实现现状自动批准为永久业务承诺。

## 二、用户路径与规则

常规路径为：用户选择产品及已有有效 T → 查看继承资料与历史对照 → 填写必要基础信息 → 服务端复查来源、权限、历史关系和重复申领 → 生成并保存 V 记录 → 尝试推进关联需求 → 后续补充或匹配公告。

| 规则 | 当前行为 | 边界 |
| --- | --- | --- |
| 立项来源 | 常规正式申领使用同产品、已通过且有有效 T 号的立项 | 不接受手填 T 号绕开已有记录 |
| 资料继承 | 方案名称、资料与原立项需求等来自所选 T | 正式申领不能静默改写原 T；显式追加与历史继承按实际路径分别解释 |
| 基础信息 | 检查成员、上线时间、有效负责人及适用的培训时长等 | 具体字段条件以当前服务端规则为准，不因页面隐藏而绕过 |
| 防重与历史 | 同一 T 来源有正式记录、旧登记或占用时拒绝重复申领；历史歧义需要匹配本次候选的确认 | 不以浏览器旧结果当作永久资格 |
| 功能与公告 | 常规申领允许空功能清单、空公告地址 | 不是放松全部业务规则；临时优化仍要求自己的功能清单 |
| 记录状态 | 当前 V 创建时写入已上线及对应时间 | 不能据此证明真实环境已部署或用户已验收 |
| 需求推进 | 关联需求在流程存在对应流转边时尝试推进 | 无边时可能跳过；正式记录成功不保证全部需求同步完成 |
| 公告后补 | 后续可补链接；自动更新以应用与完整 V 号唯一匹配 | 匹配歧义或地址冲突保留原数据，不猜测覆盖 |

旧规划版本、正式 V、功能版本和导入存档必须分别理解，不能把“有版本号”当成“有完整规则快照”。

## 三、验收实例

以下产品 A、T 和人员代号均为示意，未操作实际账号或记录。“现有测试”表示查到相应断言，不等于本轮已执行服务端测试。

| 场景 | 输入与前置 | 当前预期 | 证据与待补项 |
| --- | --- | --- | --- |
| S01 正常常规申领 | 产品 A 的有效 T，必需基础资料有效，功能与公告均为空 | 允许产生正式 V，继承 T 的需求，公告留空 | 源码与现有服务端测试均明确；本轮未运行该服务端场景 |
| S02 保护原始方案 | 选择有效 T，额外提交另一方案名称或资料 | 常规正式记录仍继承 T；原 T 不被改写 | 源码与既有原 T 保护测试；运行待验 |
| S03 重复或历史占用 | 相同 T 已有正式记录、旧正式登记或来源占用 | 拒绝第二次发号，给出冲突而不是重新编号 | 来源与历史检查、现有服务端断言；前端历史对照契约本轮已测 |
| S04 来源不成立 | 手填 T、另一产品的 T、未通过或没有有效号的 T | 拒绝常规正式申领 | 服务端判断；完整身份与数据路径待验 |
| S05 临时优化边界 | 临时路径带 T，或不带 T 但无功能清单 | 按专用条件拒绝，不能套用常规简化规则 | 服务端判断；运行待验 |
| S06 公告后补 | 对既有 V 后补合法地址 | 保留 V 号及原发号时间，只补相关资料 | 现有服务端测试有断言；本轮未执行 |
| S07 公告冲突 | 同应用同完整 V 号出现多个候选或原地址不同 | 不猜测覆盖，保留原资料并计入冲突 | 匹配服务与模块既有边界；运行待验 |
| S08 需求排期 | 手动转已排期但版本缺失、不存在、已删除或属于另一产品 | 前端要求补字段，服务端拒绝无效依据，原状态与引用不被部分改写 | 新增真实数据库测试覆盖非法请求及既有失效引用；其它引用与并发边界另见债务 |
| S09 自动状态推进 | V 保存成功，某关联需求没有对应流程边 | 该需求可被跳过，不能报告全部已推进 | 服务端路径；需运行证据确认实际覆盖 |
| S10 已填写关联的流转请求 | 弹窗填写有效立项、上线关联、版本或缺失标题后提交 | 控件填写后仍可见，发送内容保留填写值；功能对象不被错误要求需求专用依据 | 新增6项真实组件交互测试，先复现失败再修复；浏览器组件诊断确认三类关联实际发送，完整预览用户路径另验 |

## 四、一次变更应检查的影响

未来若重新把公告或功能清单变成发号门槛，首先要明确是针对新申请、在途申请还是已有记录；是否改变“已上线”的含义；是否需要独立的部署与验收证据；以及重复提交、公告匹配、历史确认和需求推进怎样兼容。

变更应关联新的 PDR，更新本规格及相关实例，再以测试与真实环境证据验证。不能只改一处按钮必填校验就宣布规则整体生效，也不能依据旧计划静默恢复已取消的门槛。

## 五、验证层次与当前边界

现有前端字段与源码契约检查继续保留；新增组件测试通过实际渲染、选择与提交验证请求内容，新增服务端测试使用隔离数据库验证真实查询、写入与拒绝时的存储结果。浏览器组件诊断也核对了关联控件和发送内容。它们分别提供不同层次的证据，不能合并冒充预览环境完整用户验收。

下一层业务验收需要在明确授权的隔离数据与登录态中执行 S01—S09，核对返回记录、实际存储和状态联动；S10 需要捕获真实发送内容。用户价值观察再请未参与原讨论的人完成同一任务，记录查找时间、错误与追问次数。本轮不预填效果改善数字，也不因整理完成就关闭这些待办。
