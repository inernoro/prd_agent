# Agent 规则作用域 · 债务台账

> **版本**：v1.0 | **日期**：2026-08-04 | **状态**：开发中

**一句话**：记录架构规则从「每次全量加载」改成「按路径命中才加载」之后，作用域划得不够宽的已知缺口，以及为什么守卫抓不到它们。
**谁该读**：给规则加或改作用域的人；发现某条规则「该加载却没加载」时来查是不是已知项。
**读完能做什么**：知道哪些缺口是已知待补的、判断自己撞上的是不是新问题、以及补的时候该按什么判据来定作用域。

---

## 背景

PR #1324 把 52 条规则的 frontmatter 键名从不被识别的旧键改成规范要求的键名。修好之后作用域
第一次真正生效——也第一次暴露出：**作用域是当初凭印象划的，不是照着规则正文自己声明的触发
条件划的**。

守卫能验证一条作用域**非空**（匹配不到任何文件的作用域会让规则永不加载，比不写还差），但验证
不了它**够不够宽**。四轮自动评审共提出 15 条「规则正文点名要管的入口，作用域没覆盖」，前 12 条
已在 PR #1324 内修复，余下的记在这里。

尝试过的通用解法及其失败原因：想拿规则正文里的触发声明去跟作用域对账，但 52 条规则里**只有
1 条**（页面新手指引那条）有可机器提取的「触发范围」小节，其余触发条件都写在散文里。做启发式
只会产生噪声闸门，所以没做——宁可留一条诚实的债，不端一个假守卫。

## 未偿项

| # | 规则 | 缺口 | 建议补法 |
|---|------|------|---------|
| 1 | 禁用 localStorage | 不覆盖网关前端，而规则正文点名管着它的 API 客户端，该前端有多个 storage 消费方 | 把网关前端的 TS 与 TSX 纳入作用域 |
| 2 | 后台双皮肤 | 只覆盖组件与样式文件，漏掉定义调色板与主题选择的纯 TS 源（应用商店色板、主题色 hook、规则自己点名的移动端主题 store） | 把后台前端的 TS 源纳入作用域 |
| 3 | 内容填满画布 | 只覆盖组件文件，漏掉 CDS 前端的共享样式表——而规则正文把该文件里的撑满类认定为撑高链的外层必要环节，也是历史回归的出处 | 把共享样式表面纳入作用域 |

三条都属于共用规则 SSOT 里 Review 范围熔断的 **B 类（有价值但扩范围）**：建议本身成立，但在
第 4 轮评审时命中熔断条件（连续 3 轮仍在产生同类新条目），按规则记账而非在原 PR 继续展开。

## 偿还判据

补作用域时**先读规则正文自己声明的触发条件**，别凭印象猜。判据顺序：

1. 规则正文点名的具体文件或目录，逐个确认被作用域命中
2. 规则「什么时候撞上」那行描述的场景，对应到真实存在的文件类型
3. 宁宽勿窄——多加载一条规则的代价，远小于该加载时没加载
4. 如果发现要枚举的表面接近全仓（判定与接线纪律那条就是），说明这条规则本就是跨切面的，
   删掉 frontmatter 改成常驻，比维护一份必然漏项的清单诚实

改完跑作用域契约守卫，它至少保证不会写出匹配不到文件的死作用域。

## 有意不还的

- **查询型参考资料的作用域**：代码库快照那条规则是「平台有什么功能 / 哪些集合 / 哪些废弃概念」
  的查询表。「不改任何文件、只想查一下」这个场景**任何作用域都捕捉不到**——这是路径作用域对
  参考资料的固有局限，不是配置没写好。补文档目录只覆盖了写文档那一半。根治方向是把它从规则
  改成按需加载的技能，属于独立改动，未排期。
