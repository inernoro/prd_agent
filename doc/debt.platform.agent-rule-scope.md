# Agent 规则作用域 · 债务台账

> **版本**：v1.0 | **日期**：2026-08-04 | **状态**：开发中

**一句话**：记录架构规则从「每次全量加载」改成「按路径命中才加载」之后，作用域划得不够宽的已知缺口，以及为什么守卫抓不到它们。
**谁该读**：给规则加或改作用域的人；发现某条规则「该加载却没加载」时来查是不是已知项。
**读完能做什么**：知道哪些缺口是已知待补的、判断自己撞上的是不是新问题、以及补的时候该按什么判据来定作用域。

---

## 背景

PR #1324 把 52 条规则的 frontmatter 键名从不被识别的旧键改成规范要求的键名。修好之后作用域
第一次真正生效——也第一次暴露出：**作用域是当初凭印象划的，不是照着规则正文自己声明的触发
条件划的**。

守卫能验证一条作用域**非空**（匹配不到任何文件的作用域会让规则永不加载，比不写还差），但验证
不了它**够不够宽**。八轮自动评审共提出 22 条「规则正文点名要管的入口，作用域没覆盖」，熔断前修掉的
已落地，熔断后的记在这里。

## 这批债有多大：一半可机械枚举

最初判断是「没有廉价的机械判据」——**这话说宽了**，得订正。按「触发范围」小节对账确实做不成
（52 条里只有 1 条有那种小节），但换一个更窄的判据就成立：**规则正文用反引号点名的具体文件，
它自己的作用域盖不盖得住**。

跑文末列的审计脚本得到当前清单。写下这段时是 38 条按需加载规则里有 9 条
命中，每条各漏一个真实存在的文件；其中三条正是评审第 4、5 轮独立发现的同一批，说明判据可信。
这个子集**不必等评审逐条捡**，照着脚本输出一次改完即可。

**脚本查不到的那一半**：触发条件写在散文里的规则。「任何队列 / 并发闸 / 连接池」这句话足以让
人判断网关的信号量代码在管辖范围内，但没有可提取的路径——上表第 7、8 条就是这么漏的，它们
不出现在脚本输出里。这部分仍然只能靠阅读理解，所以**脚本全绿不等于作用域完整**。

## 未偿项

| # | 规则 | 缺口 | 建议补法 |
|---|------|------|---------|
| 1 | 禁用 localStorage | 不覆盖网关前端，而规则正文点名管着它的 API 客户端，该前端有多个 storage 消费方 | 把网关前端的 TS 与 TSX 纳入作用域 |
| 2 | 后台双皮肤 | 只覆盖组件与样式文件，漏掉定义调色板与主题选择的纯 TS 源（应用商店色板、主题色 hook、规则自己点名的移动端主题 store） | 把后台前端的 TS 源纳入作用域 |
| 3 | 内容填满画布 | 只覆盖组件文件，漏掉 CDS 前端的共享样式表——而规则正文把该文件里的撑满类认定为撑高链的外层必要环节，也是历史回归的出处 | 把共享样式表面纳入作用域 |
| 4 | 导航登记 | 只覆盖前端，而规则正文自己写明「走后端菜单目录加权限菜单时前端无需改动」——那条路径整条都在后端，作用域却一个后端文件都不含 | 把后端菜单目录纳入作用域 |
| 5 | 移动端密度 | 只覆盖组件文件，漏掉后台前端的样式 token 表——而规则正文点名其中的移动端内边距变量是全局密度杠杆，改它会波及每个移动页 | 把共享样式 token 纳入作用域 |
| 6 | CDS 主题 token | 漏掉 Tailwind 配置（规则正文认定它是语义色到 token 的映射源）与纯 TS 调色板源，改这两处可绕过 HSL token 与双主题约束 | 把主题配置与 TS 调色板源纳入作用域 |
| 7 | 服务器权威性 | 只覆盖主后端，漏掉网关的 28 个 C# 文件——而网关的 SSE 端点与请求生命周期无关的持久化正是这条规则的实现处 | 把网关的 C# 表面纳入作用域 |
| 8 | 并发闸纪律 | 同样漏掉网关——而网关的提供方并发实现与信号量协调正是「任何队列 / 并发闸 / 连接池」这条描述指向的东西 | 把网关的 C# 表面纳入作用域 |
| 9 | 海鲜市场 | 只列了三个具体文件，漏掉市场相关的实体与控制器——而那才是 `IMarketplaceItem` / `IForkable` 契约与发布/复制端点的实现面 | 按契约实现面而非单个文件划作用域 |

九条都属于共用规则 SSOT 里 Review 范围熔断的 **B 类（有价值但扩范围）**：建议本身成立，但在
第 4 至 8 轮评审时命中熔断条件（连续 3 轮仍在产生同类新条目），按规则记账而非在原 PR 继续展开。

这九条有共同形状：**规则正文自己点名的入口，作用域没覆盖**。第 4 条尤其典型——规则明说那条
路径「前端无需改动」，而作用域却只有前端文件，等于规则对自己描述的主要场景失效。

还有一条跨条目的规律值得记下：**新模块诞生时，没人回头去拓宽既有规则的作用域**。第 1 条
（网关前端 storage）、第 7 条（网关后端 SSE）、第 8 条（网关并发闸）是网关从主仓剥离后留下的同一个洞——规则写于
剥离之前，作用域自然只写了当时存在的目录。偿还时应当整批扫一遍「哪些规则的作用域还停留在
网关剥离之前」，而不是等评审逐条捡。

## 偿还判据

补作用域时**先读规则正文自己声明的触发条件**，别凭印象猜。判据顺序：

1. 规则正文点名的具体文件或目录，逐个确认被作用域命中
2. 规则「什么时候撞上」那行描述的场景，对应到真实存在的文件类型
3. 宁宽勿窄——多加载一条规则的代价，远小于该加载时没加载
4. 如果发现要枚举的表面接近全仓（判定与接线纪律那条就是），说明这条规则本就是跨切面的，
   删掉 frontmatter 改成常驻，比维护一份必然漏项的清单诚实

改完跑作用域契约守卫，它至少保证不会写出匹配不到文件的死作用域。

## 另一类：模块记忆的实际体积

在模块目录下工作时，Agent 拿到的是**根记忆 + 该模块记忆**（二者拼接，不是覆盖）。所以逐个文件
量「有没有超 200 行」会低估真实注入量。

现状：五个模块的累计值分别是 394 / 223 / 222 / 219 / 217 行，全部超过单文件目标。其中 CDS
那份自身就有 197 行，是唯一一个真正偏大的——把它压下来是 CDS 模块自己的活，不在记忆契约这个
PR 的范围内。

守卫已把这五个数字钉成上限，只降不升，所以体积不会再悄悄涨；上限值写在守卫源码里并注明
「这是今天的值，不是理想值」。要还这笔债就去压 CDS 那份，压完顺手把上限调低。

注意根记忆的增长会被放大：根多一行，五个模块的累计各多一行，守卫会同时报五处。这是有意的
——根记忆的边际成本本来就是模块数的倍数。

## 有意不还的

- **查询型参考资料的作用域**：代码库快照那条规则是「平台有什么功能 / 哪些集合 / 哪些废弃概念」
  的查询表。「不改任何文件、只想查一下」这个场景**任何作用域都捕捉不到**——这是路径作用域对
  参考资料的固有局限，不是配置没写好。补文档目录只覆盖了写文档那一半。根治方向是把它从规则
  改成按需加载的技能，属于独立改动，未排期。
