# CDS 数据库隔离三档（共享库 / 分支独立库 / 隔离库）· 设计

> **版本**：v1.1 | **日期**：2026-09-02 | **状态**：已落地（三档现状）+ 设计中（同步策略收敛与可信数据面）

**一句话**：把共享库、分支独立库、复制集隔离库看成同一把梯子的三级，库名定位、后缀派生、数据初始化、回收四件事只许一套规则；每一档都必须用实测数字向用户证明「做对了」，而不是靠一句「已隔离」。
**谁该读**：定多分支数据策略的负责人；改数据库隔离或复制集代码的工程师；排查「隔离像没隔离」的人。
**读完能做什么**：说清一条分支的某个服务此刻到底连着哪个库、这个库从哪来、会不会被别人写坏、删掉分支后它去哪。

---

## 一、管理摘要

CDS 现在有两条彼此独立长出来的数据隔离路径：

- **分支独立库**（2026-05 落地）：项目级开关，给每条分支的库名加分支后缀，分支各用一个空库，重跑迁移。
- **复制集隔离库**（2026-07 落地）：服务级动作，先把当前库整库克隆，副本改连克隆出来的库，实验随便写，主库零风险。

两条路解决的是同一个问题（多份代码同时跑，别互相写坏数据），却各自定义了「库名从哪个变量找」「新库叫什么」「连接串怎么跟着改」「用完怎么处理」。已经出过的事故都落在这四件事的分叉上：per-branch 认白名单变量、复制集认框架变量与连接串 scheme，同一个服务在一条路上「可隔离」、另一条路上「切了像没切」。

本文把两条路收敛成**一把三级梯子 + 一套同步策略**：

```
共享库 ──► 分支独立库 ──► 隔离库
 所有分支同一库   每条分支一个库     一个服务的一份实验副本
 (项目默认)      (项目默认 / 分支覆盖)  (复制集动作，建立在上一级之上)
```

每往上一级，只做一件事：在下一级折算出的库名上**再派生一层后缀**。四件事的规则来自同一处：

| 四件事 | 唯一规则 | 今天的分叉（要收敛） |
|---|---|---|
| 库名从哪找 | 一份库名变量分类器（白名单家族 + 框架家族 + 引擎中立家族按连接串判引擎） | 分支独立库只认白名单；复制集认三家族 |
| 新库叫什么 | 下一级库名 + 本级后缀；后缀由本级作用域派生 | 分支独立库用可读分支 slug，隔离库用分支加服务哈希加成员 id（两者理由不同，见四.2） |
| 连接串怎么跟 | 库名变量改了，引用它的连接串自动跟；硬编码的关系型连接串按 scheme 识别后改写 | 分支独立库只靠模板引用，硬编码串静默失效；复制集会改写 |
| 用完怎么办 | 一律**保留**，进同一本快照台账，手动或按策略回收 | 隔离库进台账可见；分支独立库残留没有台账 |

三个已拍板的决策：

1. **策略是数据，档位是参数。** 「初始化 / 运行中同步 / 回写 / 回收」四个策略维度对三档统一建模；分支独立库今天的「空库 + 重跑迁移」只是初始化策略的一个取值，不再是它的定义。
2. **上一级永远是下一级的输入。** 隔离库在「分支独立库折算后的库」上派生，副本服务的档位被钉成共享库以免二次加后缀。这条已经在代码里成立，本文把它定成不变式。
3. **不做实例级隔离。** 三档都在同一个数据库实例里靠库名区分（mongo 专用实例是隔离库的引擎特例，不改变模型）。每分支一个实例太重，且与「省资源、看真数据」的设计初衷相悖。

## 二、背景与现状

### 2.1 两条路各自的样子

| 维度 | 分支独立库 | 复制集隔离库 |
|---|---|---|
| 触发 | 项目设置「数据库隔离」页签（项目默认）或分支抽屉覆盖 | 复制集页签「隔离数据库」，或数据库资源卡的保护罩（设计中） |
| 作用域 | 一条分支上某个服务的所有容器 | 一条分支上某个服务的副本成员（零副本也可隔离） |
| 新库来源 | 空库，应用启动时自己建库、跑迁移 | 时间点整库克隆（mongo 导出导入、mysql 导出导入、postgres 导出导入） |
| 命名 | `<库名>_<分支 slug>`，可读 | `<库名>_rs_<分支加服务哈希 6 位>_<成员 id>`，保证全局唯一 |
| 库名定位 | 固定白名单家族（`CDS_POSTGRES_DB` 这一类） | 白名单家族 + 框架家族（.NET 双下划线）+ 引擎中立家族（`DB_NAME` 借连接串 scheme 判引擎） |
| 连接串 | 依赖 `${变量}` 模板引用自动跟随；硬编码串不改 | 显式改写关系型连接串（识别与改写共用一条 scheme 规则） |
| 生效时机 | 重新部署后 | 副本启动前克隆完成，切换时先摘流再改连 |
| 保留 | 分支删除不 drop，无台账 | 成员下线、复制集解散不 drop，进快照台账可见 |
| 回收 | 待专项 | 手动删除快照即 drop（mongo 专用实例连容器一起移除） |
| 回写 | 无（视为测试数据） | 波 5 设计中：按引擎重放增量，隔离库赢 + 冲突清单 |

### 2.2 为什么必须同源

分叉不是风格问题，是同一个服务在两条路上会得到不同答案：

- 一个 .NET 项目只有 `MongoDB__DatabaseName`：项目设置里切「分支独立库」什么都不会改写（白名单不认），页面已经会提示「没声明库名变量」；复制集却能定位并克隆。用户看到的是「隔离在这里能用、在那里不能用」。
- 一个 Java 项目把库名硬编码在 `SPRING_DATASOURCE_URL` 里：分支独立库改了 `DB_NAME`，应用读的是那条 URL，流量继续打共享库；复制集会改写这条 URL。前者正是 2026-07 复制集修过两轮的「隔离是假的」在另一条路上的复现。
- 分支删了，独立库留在实例里没人知道；隔离库至少在台账里。两种残留最终要同一套 GC 处理，却没有同一本账。

## 三、目标与非目标

**目标**

- 三档共用一份库名定位规则、一份后缀派生规则、一份连接串改写规则、一本保留与回收台账。
- 用户在任何入口看到的都是同一组词：共享库 / 分支独立库 / 隔离库；同一组承诺：改配置不自动重部署、克隆是时间点、残留保留可查。
- 分支独立库获得「带数据初始化」的选项（从共享库时间点克隆），复用复制集已经验证过的三引擎克隆管线。

**非目标**

- 不做实例级隔离，不做跨实例复制。
- 不改变「共享库是默认」：多分支看同一份真数据仍是有意设计。
- 回写（把实验数据合并回主库）沿用复制集波 5 的设计，本文不重复展开，只规定分支独立库也走那一套。

## 四、核心模型

### 4.1 数据归属

一个服务在一条分支上的「数据归属」= （数据库实例，库名）。三档的区别只在库名怎么派生：

| 档位 | 库名派生 | 派生输入 | 谁能改 |
|---|---|---|---|
| 共享库 | 原库名 | 项目环境变量或服务底座的库名变量 | 项目设置（项目默认） |
| 分支独立库 | 原库名 + `_` + 分支 slug | 上一级库名 + 分支名 | 项目设置（项目默认）、分支抽屉（本分支覆盖） |
| 隔离库 | 上一级库名 + `_rs_` + 哈希 + 成员 id | 上一级**折算后**的库名 + 分支 id + 服务 id + 成员 id | 复制集页签、数据库保护罩 |

不变式：**隔离库的输入永远是分支独立库折算之后的库名**。副本服务在物化时档位被钉成共享库，就是为了不让部署路径在克隆出来的库名上再加一次分支后缀。这条今天已经成立，任何重构不得破坏。

### 4.2 后缀为什么不统一成一种

- 分支独立库的后缀要**可读**：运维在数据库工作台里看到 `shop_feat_x` 就知道是哪条分支的库，这是它存在的价值之一。分支名在项目内唯一，可读 slug 足够。
- 隔离库的后缀要**全局唯一**：成员 id 是确定性的（`res-1`、`guard-1`），不同分支、同分支不同服务都会重复；mongo 专用实例的容器名又由库名派生，重名会让第二次克隆摧毁第一个实例。所以必须把分支加服务揉进哈希。

两种后缀由同一个模块生成，输入语义写死在模块里，调用方不许自己拼字符串。这是「同源」的落点，不是「同形」。

### 4.3 库名定位：一份分类器

今天复制集那份分类器是超集（白名单家族、框架家族、引擎中立家族），分支独立库那份是子集（白名单家族）。收敛方向：

- **定位**（这个服务用的是哪个库、在哪个引擎）三档共用超集分类器。项目设置页签里「会改写哪些变量」的展示也用它，让用户在项目设置里看到的答案与复制集页签一致。
- **改写**（真的给哪些变量加后缀）分支独立库仍按白名单执行，但差异要**显式可见**：分类器认得、白名单不改的变量（例如 .NET 的框架变量）在页签上标成「已识别，按项目约定不加后缀」，而不是像今天一样静默跳过。这是 prd-agent 自己的既有约定，保留但不再隐形。

### 4.4 连接串改写：一条规则

关系型连接串的识别与改写今天在复制集里已经是同一条规则（识别得出引擎的串，就是要跟着改库名的串）。分支独立库接入同一条：库名变量加了后缀，硬编码在连接串里的库名同步改写；改写发生在模板展开之前，`${变量}` 引用的串照旧自动跟随。

不能识别的串（无 scheme、非关系型）保持不动，并在配置检查器的逐 key 溯源里标出「库名已改写、此串未跟随」，让「隔离是假的」在部署前就可见。

## 五、同步策略（策略是数据）

把「一个库怎么诞生、活着的时候和主库什么关系、死了怎么办」拆成四个维度，三档各有默认取值，用户可在允许的范围内改：

| 维度 | 取值 | 共享库 | 分支独立库 | 隔离库 |
|---|---|---|---|---|
| 初始化 | 无 / 空库重跑迁移 / 时间点克隆 | 无 | **空库重跑迁移**（默认）；时间点克隆（新增可选） | **时间点克隆** |
| 运行中同步 | 无 / 停快照 | 无（就是同一个库） | 无 | 停快照（克隆后不追增量，页面明示克隆时间点） |
| 回写 | 无 / 隔离库赢加冲突清单 | 不适用 | 无（默认）；波 5 落地后可选 | 波 5：隔离库赢加冲突清单 |
| 回收 | 保留 / 手动删除 / 随作用域删除 | 不适用 | **保留**（默认，进台账）；随分支删除（可选，删分支时提示） | 保留，手动删除 |

三条规则：

1. **保留是默认，删除要看见。** 任何档位的残留库都进同一本快照台账（来源库、派生库、引擎、实例、产生时间、产生原因）；删分支、解散复制集时列出会留下什么，用户勾选才删。
2. **克隆只有一条管线。** 分支独立库选「时间点克隆」时，走复制集已验证的三引擎克隆，包括凭据不落命令行、库名只允许安全字符集、克隆期间作用域被删则清理克隆物的栅栏。
3. **回写只有一种冲突策略。** 波 5 落地时，分支独立库与隔离库共用「隔离库赢 + 冲突清单人工确认」，不为分支独立库另发明一套。

## 六、数据怎么流（部署路径）

```
项目底座 dbScope ──► 分支覆盖 dbScope ──► 生效档位
                                              │
      项目环境变量 + 分支变量 + 服务底座变量   │
                    │                         ▼
                    └──► 合并 env ──► 按生效档位给库名变量加分支后缀（分支独立库）
                                          │
                                          ├──► 关系型连接串跟随改写（本文四.4 收敛后）
                                          │
                                          ▼
                                     模板展开 ──► 容器 env
                                          │
      复制集副本：在此结果之上 ──► 定位库（分类器）──► 克隆成隔离库 ──► 副本 env 指向隔离库
                                                                       （副本档位钉成共享库）
```

配置检查器对每个库名变量给出溯源：值从哪层来、被哪一档改写、连接串有没有跟随。这是用户判断「此刻到底连着哪个库」的唯一权威视图。

## 七、用户可见的承诺

三个入口用同一组词和同一组承诺，文案不得各写各的：

| 承诺 | 项目设置页签 | 分支抽屉 | 复制集页签 |
|---|---|---|---|
| 生效时机 | 「重新部署后生效」 | 「重新部署后生效」 | 「克隆完成后副本才启动」 |
| 影响范围 | 影响所有继承项目配置的分支；已有分支覆盖保持不变 | 只改本分支这个服务 | 只改这个服务的副本 |
| 数据从哪来 | 空库重跑迁移，或从共享库时间点克隆 | 同左 | 时间点克隆，标明克隆时间 |
| 残留 | 保留可查 | 保留可查 | 保留可查，手动删除 |
| 切了没效果 | 没声明库名变量时当场提示 | 同左 | 定位不到库时拒绝并说明原因 |

## 八、取舍与风险

| 取舍 | 理由 |
|---|---|
| 分支独立库默认仍是空库，不默认克隆 | 克隆是重操作，且很多项目的迁移脚本就是要在空库上验证；克隆做成可选 |
| 白名单改写规则保留 | prd-agent 刻意让框架变量不随分支加后缀；改成超集改写会打破既有约定。用「可见的不改写」替代「静默的不改写」 |
| 后缀不统一 | 可读性与唯一性是两种需求，强行统一会让其中一方退化 |
| 不做实例级隔离 | 每分支一个实例的资源开销与「看真数据」的初衷相悖 |

| 风险 | 等级 | 缓解 |
|---|---|---|
| 连接串改写接入分支独立库后改错硬编码串 | 中 | 复用复制集同一条识别与改写规则，那条已有回归测试；配置检查器先展示再部署 |
| 台账合并后旧残留库无来源信息 | 低 | 扫描实例里符合两种后缀形态的库名做一次性补录，标「来源未知」 |
| 分支独立库克隆与复制集克隆并发抢同一实例资源 | 中 | 克隆管线已有作用域栅栏；同实例同时只跑一个克隆任务，其余排队并显示进度 |

## 九、用户看得见、信得过（评审补充）

评审意见（2026-09-02）：每一种隔离机制都要让用户有察觉；要想方设法让用户感知到我们做对了；最重要的是数据表达出来的精准程度。本节把这三句话变成硬约束。

### 9.1 两列并排：配置说的、实测到的

用户不信配置，只信探测。任何展示「这个服务连着哪个库」的地方，必须并排给两列：

| 列 | 来源 | 举例 | 拿不到时 |
|---|---|---|---|
| 配置说的 | 配置树折算（档位、后缀、连接串改写） | 应连 `shop_feat_x` | 永远算得出 |
| 实测到的 | 进容器向数据库问「你是谁」（当前库名、实例地址、引擎版本），带探测时间 | 实际连着 `shop_feat_x`，实测于 14:32:07 | 明确写「未探测」或「探测失败：原因」，不许用配置值冒充 |

两列不一致就是一条缺陷，页面直接标红并说明差在哪（旧容器未重部署、连接串没跟随、库不存在）。这条把「隔离是假的」从事故变成页面上的一行红字。

### 9.2 精准数据面：每个数字都带来源与时间

用户判断「做对了」靠的是能核对的数字，不是形容词。三档共用一张数据面，字段固定：

| 字段 | 含义 | 来源 |
|---|---|---|
| 实例与库名 | 引擎、实例容器、库名 | 实测 |
| 体量 | 表或集合数、总行数或文档数、字节数 | 实测，逐表列出 |
| 最后写入时间 | 库里最新一条数据的时间戳，或引擎的最后修改时间 | 实测 |
| 血缘 | 从哪个库、在什么时间点派生；是否又被谁派生 | 台账 |
| 克隆校验 | 源库与目标库逐表行数对比、抽样校验和；有差异逐行列出 | 克隆完成时实测并落台账 |
| 备份与还原 | 最近一次备份时间、备份体量、最近一次还原演练时间与结果 | 备份台账 |

三条规矩：

1. 实测值与推断值用不同的视觉样式，推断值必须带「按配置推断」字样，绝不混排。
2. 每个实测值带探测时间；超过约定时限（默认 10 分钟）自动灰掉并提示「已过期，点击重测」。
3. 对比类数据（克隆校验、切换前后）只给逐项明细加一句结论，不给「大致一致」。行数对不上就是对不上，差几行写几行。

### 9.3 每一次状态翻转都有可见信号

隔离机制的每一步都要在界面上留下痕迹，用户不看日志也能复述发生了什么：

| 状态翻转 | 可见信号 | 证据 |
|---|---|---|
| 配置改了、还没生效 | 服务行标「已配置，等待重新部署」，列出受影响分支 | 配置快照 id |
| 重新部署完成 | 标「已生效」，容器 env 里的库名与配置一致 | 配置检查器逐 key 溯源 |
| 应用连上了库 | 标「已连接」，附实测库名与时间 | 探测记录 |
| 数据到位 | 标「已就绪」，附体量与校验结果 | 克隆校验表或迁移日志 |
| 备份完成 | 标「可还原」，附备份时间与体量 | 备份台账 |
| 还原演练通过 | 标「已验证」，附演练时间与比对结果 | 还原记录 |

没有走到的状态就显示没走到，不许跳格。

## 十、数据不丢：替换、丢弃、备份、还原

评审意见：隔离之后想替换、丢弃或备份，我们要做足准备，避免数据丢失找回问题。

四个动作各自的前置条件与产物：

| 动作 | 含义 | 前置条件 | 产物 |
|---|---|---|---|
| 替换 | 用另一个库的内容覆盖当前库（例如用共享库刷新独立库，或用隔离库回写主库） | 目标库先自动备份且备份可读；替换前展示体量对比让用户确认 | 替换前快照进台账，可一键回退 |
| 丢弃 | 删掉某个派生库 | 该库已有一份不早于最后写入时间的备份，或用户明确勾选「不备份直接删」并复述库名 | 台账记录谁、何时、删了什么、体量多少 |
| 备份 | 把某个库导出成可还原的文件 | 无 | 备份文件、体量、校验和、来源血缘 |
| 还原 | 把备份导回某个库 | 目标库先自动备份；还原后逐表行数比对 | 还原记录与比对结果 |

三条铁律：

1. **删之前必有备份，备份必须还原验证过一次。** 从没成功还原过的备份不算备份；周期备份页签已有的「恢复演练」结论直接复用。
2. **不做静默覆盖。** 任何会让旧数据不可见的动作（替换、还原、丢弃）都先拍快照，界面上显示「可回退到 时间」。
3. **一本台账。** 分支独立库、隔离库、备份、还原全部记在同一本数据台账里，按血缘成树：谁从谁派生、谁被谁替换、谁被删了。删分支、解散复制集时先展示这棵树的相关分支，用户勾选才动。

## 十一、能借鉴的就不自己造

评审意见：市面上有这类东西就学习，避免产生开发调试问题。对照下来，本文的模型与业界数据库分支产品是同构的，差别只在我们不做存储层的写时复制：

| 业界做法 | 出自 | 我们怎么用 |
|---|---|---|
| 数据库分支 = 从父库某个时间点派生一份，可「重置回父库」、可「提升为主库」、有血缘图 | Neon、Supabase、PlanetScale 的 database branching | 三档梯子就是这套模型；「重置回父库」对应替换，「提升」对应回写，血缘图对应数据台账 |
| 分支有保护标记与过期时间，主库不可删，实验分支到期自动清理 | 同上 | 共享库默认受保护不可删；派生库带可选到期时间，到期只提醒不自动删（保留是默认） |
| 引擎原生导出导入做时间点复制 | mongodump、mysqldump、pg_dump 与 postgres 的模板库 | 克隆管线已经在用，不自研同步引擎 |
| 增量回写走引擎原生日志 | mysql binlog、mongo oplog 或 change stream、postgres 逻辑复制 | 波 5 回写按此实现，不自研差量算法 |
| 迁移脚本管理与版本表 | Flyway、Liquibase、各 ORM 的迁移表 | 空库初始化靠应用自己的迁移；我们只保证库名与连接串对，不碰迁移逻辑 |
| 用行数、校验和、时间戳报告复制结果 | 各家数据迁移工具的校验报告 | 9.2 的数据面直接照抄这套字段 |

明确不借鉴的：存储层写时复制（Neon 的做法需要自己的存储引擎）；跨实例物理复制（与「同实例靠库名区分」的取舍冲突）。

## 十二、以测试驱动递进，对抗审查前置

评审意见：良好的对抗审查能更早发现问题，建议以 TDD 为基础递进。每一步收敛都先写会红的测试，再改代码；审查者的职责是把「隔离是假的」的每一种形状写成用例。

四层测试梯子，逐层递进，上一层全绿才进下一层：

| 层 | 测什么 | 例子 |
|---|---|---|
| 纯函数 | 库名定位分类器、后缀派生、连接串改写 | 只有硬编码 JDBC 串的 env 切独立库后，串里的库名被改写；引擎判不出的串保持原样并被标出 |
| 契约 | 项目级与分支级 API 的原子性、权限、幂等 | 同一请求重放两次结果一致；一项非法整批不落盘；跨项目 key 被拒 |
| 真引擎集成 | 在真实 mongo、mysql、postgres 容器里跑克隆、校验、备份、还原 | 克隆后逐表行数与源库一致；还原后与备份一致；库名含非法字符被拒 |
| 端到端与故障注入 | 真人路径加故障矩阵（见十三） | 克隆到一半杀掉数据库容器，台账无孤儿库，成员进错误态并可重试 |

对抗审查清单（每次评审必问）：

- 我改的是配置，用户看到的「实测到的」那一列会跟着变吗？还是只有「配置说的」变了？
- 这个服务的库名变量在三个入口看到的清单一样吗？
- 我删掉这处改动，哪条测试会红？没有就先补。
- 这条判据取的是变更前还是变更后的状态？会不会用旧容器的状态去判断新配置？
- 同一操作并发两次、中途断电、容器宕机，台账会不会出现半截记录或孤儿库？

## 十三、状态机与故障矩阵

评审意见列出的链条（切换、生效、连接、拉数据、备份、还原，多分支多项目，并发幂等、队列、停复机、容器宕机）在本节逐项落位。

### 13.1 一条库的状态链

```
未切换 ──► 已配置未生效 ──► 已生效 ──► 已连接 ──► 已就绪 ──► 可还原 ──► 已验证
          (改了配置)      (重新部署)   (实测库名)  (数据到位   (有备份)   (还原演练
                                                   并校验)              通过)
```

每个箭头都可能停住，停在哪就显示在哪，界面用 9.3 的信号表；不许用后面的状态词描述前面的状态。

### 13.2 故障矩阵

| 环节 | 典型失败 | 怎么发现 | 怎么处置 |
|---|---|---|---|
| 切换 | 配置写了，用户以为已生效 | 服务行标「等待重新部署」，受影响分支数 | 一键重新部署入口就在旁边 |
| 生效 | 重部署了，容器 env 还是旧库名（分支覆盖、旧构建、连接串没跟随） | 配置检查器逐 key 溯源与「实测到的」列对比 | 标红差异项，给出具体原因 |
| 连接 | 库不存在、无权限、实例没起 | 实测探测失败 | 显示失败原因，独立库首次部署自动建库或提示应用需自建 |
| 拉数据 | 克隆半截、行数对不上 | 克隆校验表 | 半截克隆物按栅栏清理；校验不一致不许标「已就绪」 |
| 备份 | 备份失败、产物不在了 | 周期备份页签的目标状态 | 复用备份健康结论，缺备份时阻止「丢弃」 |
| 还原 | 还原到错库、还原后不一致 | 还原前自动快照，还原后比对 | 比对不一致自动回退到快照 |
| 多分支多项目 | 同名库撞车、作用域串项目 | 后缀派生输入含项目与分支身份 | 派生规则单元测试覆盖跨项目同名分支 |
| 并发 | 同一库同时两次隔离或克隆 | 幂等键 = 项目 + 分支 + 服务 + 目标库 + 动作 | 重放返回同一结果；同实例克隆串行排队并显示队列位置 |
| 停复机 | CDS 重启时克隆或还原正在跑 | 任务状态持久化，重启后扫描「进行中」 | 未完成的标「中断」并给重试；不静默丢 |
| 容器宕机 | 数据库容器或副本容器在克隆中被杀 | 克隆管线的作用域栅栏 | 清理克隆物、写台账、成员进错误态并可重试 |

## 十四、验收标准

- 同一个服务在项目设置页签、分支抽屉、复制集页签三处看到的「库名变量」清单一致。
- 任何展示「连着哪个库」的地方都有「配置说的」与「实测到的」两列，且实测值带探测时间；人为让旧容器不重部署时，两列不一致被标红并说明原因。
- 一个只有硬编码 JDBC 连接串的服务切分支独立库后，配置检查器显示连接串已跟随，副本与主容器实际连到不同库（用数据库工作台各写一条记录互不可见）。
- 克隆完成后页面给出逐表行数对比；人为在克隆中途向源库写入一行，对比表能指出差的那一行。
- 丢弃一个没有备份的派生库被拒绝；有备份且还原演练通过后才允许，删除记录进台账。
- 分支删除对话框列出将保留的独立库与隔离库；勾选删除后实例里确实不存在，不勾选则进台账可查。
- 分支独立库选「时间点克隆」初始化后，新分支首次部署不需要重跑迁移即可读到克隆时间点之前的数据。
- 故障矩阵每一行至少有一条自动化用例，克隆中杀容器、并发双击隔离、CDS 重启三种场景有端到端证据。
