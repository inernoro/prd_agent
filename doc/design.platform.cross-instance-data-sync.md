# 跨 MAP 实例数据同步（动态授权） · 设计

> **版本**：v1.0 | **日期**：2026-08-20 | **状态**：已实现，待真人验收

**一句话**：让一台 MAP 向另一台 MAP 申请一次性授权，对方管理员当场勾选范围并同意，然后只执行一次数据拉取。
**谁该读**：要把正式环境的数据搬到另一套环境的人；评审这条链路安全性的人。
**读完能做什么**：判断这次同步会带走什么、不会带走什么、出了问题从哪里看。

---

## 为什么要有这个东西

2026-08 服务器被攻击、prdagent 库被清空之后，恢复手段只剩「从备份归档还原」一条，
而备份是整实例的、恢复要停机、还挑不了库。真正缺的是一条**在线的、可挑范围的、
带人工批准的**数据搬运通道：把正式环境的业务内容同步到另一套环境，不停机、不动密钥、
不把访问权一起搬过去。

## 授权模型：为什么是「跳过去同意」而不是配一把钥匙

预共享密钥（在两台机器上各配一份 secret）是更省事的做法，但它有三个不能接受的性质：

1. 配好之后**长期有效**，谁都能在任何时候把数据拉走，事后看不出是谁批的；
2. 密钥落在配置里，等于又多了一份要轮换、要防泄漏的凭据；
3. 「批准」这个动作消失了——没有任何一刻有人看着「要拿走什么」做过判断。

动态授权把这三条反过来：每次同步都要人到源站点一次同意，同意的范围写在票据里，
票据 60 秒过期、只能用一次，换出来的导出令牌绑定这一次同步，跑完即废。

两台机器是同一套代码的两次部署，之间没有共享密钥，所以用 **PKCE** 证明「来换票的
就是发起跳转的那一位」：目标站生成随机 verifier 留在自己内存里，只把它的 SHA-256
放进跳转链接；换票时出示 verifier。中途截获授权码的人拿不出 verifier，码就是废的。

## 一次同步的六步

```
目标站                                源站
  │  1. 管理员填源站地址
  │  1.5 先握一次手：对方是谁、协议版本对不对、有没有开对外同步
  │  2. 生成 verifier（留内存）+ challenge
  ├─────────── 浏览器跳转（带 challenge / state / 回跳地址）──────────►
  │                                    │  3. 源站管理员登录后看到「要走哪些、
  │                                    │     不会走哪些」，默认全给 → 同意
  ◄────────── 浏览器回跳（fragment 带一次性授权码）───────────────────┤
  │  4. 服务端用 码 + verifier 换导出令牌（码在此作废）                │
  │  5. 拉清单：每个集合源站多少条 / 本地多少条 → 人确认              │
  │  6. 分页拉取并写库，SSE 推进度                                     │
```

第 1.5 步是**跳转前**做的，不是跳完才做。握手端点匿名可读，只报站点名、协议版本、
构建号和「对外同步开没开」四样东西——都是对方本来就愿意让人知道的。版本对不上就在
这里拦住：让人跳过去勾一遍范围、回来才发现两站说的不是一种话，是最没必要的一种浪费。

协议版本只表达「这条同步链路的字段契约」，不表达业务集合的字段结构；后者继续靠
Mongo 无 schema 的宽容度兜着（见台账 DS7）。

第 5 步不能省。它是操作者唯一一次看清「要往哪个数据库写」的机会——本项目的分支预览
**共享同一个 Mongo 库**，在任何一条分支上跑同步，同库的其它分支立刻看得见。

## 带走什么，不带走什么

范围由一份**导出白名单**定死，它把本系统在库里注册的每一个集合都分了类：

| 类别 | 举例 | 处理 |
|---|---|---|
| 业务内容 | 缺陷、知识库、周报、项目管理、产品、评审、创作素材、网页托管 | 可勾选导出 |
| 平台与模型配置 | 平台、模型、模型池、AppCaller、提示词、水印 | 可勾选导出，**密钥字段清空** |
| 带凭据的业务集合 | 知识库跨环境同步令牌、各类分享链令牌、周报数据源令牌、群组与团队邀请码 | 可勾选导出，**凭据字段清空** |
| 账号与组织 | 用户、用户组、团队、个人偏好 | 可勾选导出；口令散列**默认跟着走**（见下节），取消勾选才清空 |
| 本站自有状态 | 实例身份、对外同步开关与允许名单、SSO 回跳地址、是否禁用口令登录 | 可勾选导出，**这些字段清空**——它们描述的是「这台机器是谁、信任谁、怎么登录」，跨站复制会撞身份或把目标站锁死 |
| 凭据嵌在结构里的集合 | 工作流及其定时任务、自动化规则 | **永不导出**——密钥藏在变量与动作的数组内部，而出口脱敏只认顶层字段名，登记了也是空转 |
| 凭据与票据 | API Key、SSO 票据、外部授权、分享链接、会话 | 永不导出 |
| 日志与埋点 | 各类 request log、行为事件、影子比对 | 永不导出 |
| 运行时与派生 | Agent 会话、各类 run、上传分片、向量 | 永不导出 |

**白名单而不是黑名单**：黑名单下，日后新增一个装凭据的集合会被默认导出，而且没有任何
东西会报错。白名单反过来——新集合不在名单里就同步不到，最坏是漏，不会是泄。代价是
新集合必须登记一次，这个代价由一条 CI 守卫强制：库里注册的每个集合，要么在某个分组里，
要么在排除表里写明不导出的理由，二者缺一就变红。

**「哪些字段要清空」同样不靠人记**。第一版只手写了五个集合的脱敏字段，评审一眼指出知识库的
跨环境同步令牌被原样导出——那是永久有效、能直接读写对方知识库的凭据。手写清单永远只覆盖得到
写的人当时想到的那几个，所以改成机器逐个逼问：可导出集合对应的实体类里，凡是字段名带
token / secret / password 这类词的，要么已登记脱敏，要么写进「看过了，不是凭据」名单并说明理由，
两边都没有就 CI 变红。这一轮横扫补上了 15 个集合的脱敏登记。

### 敏感字段在源站出口清空

不是到目标站再删。后删删不掉已经过网络、过目标站请求日志、过失败重试临时文件的副本。
出口清空之后，那些字节从头到尾没离开过源站。

清空而不是删字段：字段留着但值为空，目标站才认得出「这里本来有东西、需要补」，
于是同步完能列出**待补密钥清单**。整个字段删掉的话，缺什么就只有人脑记得。
补填由操作者手工完成——这是明确的产品决定，不做任何形式的密钥搬运。

### 口令散列：默认搬，因为「同步完要能直接用」

用户账号是唯一一处**默认少脱敏**的地方。同意页上有一个默认勾上的选项，勾着就把
用户集合的口令散列一起搬过去——目标站的人用原账号密码直接能登。这是产品上的取舍：
一份搬过去谁都登不进的数据，等于没搬；而口令散列是 BCrypt，搬的是散列不是明文，
且这个决定由**源站管理员**在同意那一屏做出，目标站单方面要不来。

取消勾选就回到「不搬凭据」的严格模式：出口清空散列，同时给每个账号打上「必须重设密码」
的标记，让目标站管理员在用户列表上一眼看出这批账号在等什么。

这个口子只对用户集合的口令散列这一个字段开——其余凭据字段、其余集合一律照旧清空，
并有守卫钉死它不会被顺手改宽。

## 三道门

| 门 | 挡的是什么 |
|---|---|
| 只有真人管理员浏览器会话能批准 | 合成测试会话、Agent Key、机器人被挡在外 |
| 回跳地址必须命中源站白名单，且路径精确等于那一个固定的回跳落地页 | 前者挡「把数据送到陌生站点」，后者挡「白名单域名下有个开放重定向页」 |
| 白名单为空即功能关闭 | 「没配过」不等于「允许所有」——钓鱼面正在这里 |
| 名单可以在同意页上当场加，但要单独勾一次 | 「谁能开这道门」从「能改配置并重启的人」收敛成「此刻正看着这一屏、看得见对方是谁、又额外确认了一次的管理员」。门没拆，只是不必再绕一圈去改配置（原 DS6）。回跳地址的**形状**（https / 路径精确 / 无 query）不在可放宽之列，任何人都不能当场改 |
| 两侧每一个人机端点各自判管理员 | 控制器上的「已登录」不是「是管理员」。目标站少判一处，普通用户拿到一次待确认的同步就能把别人授权来的数据覆盖写进共享库；源站少判一处（列可授权范围的那一个），全站集合清单与逐集合条数就摊给了任何登录用户 |

### 授权的范围冻结在签发那一刻

批准动作产生的凭据里，记的不是「他勾了哪几个分组」，而是**那一刻这些分组展开成的具体
集合清单**。之后清单、导出一律按这份快照放行，不再重新展开分组。

差别在票的有效期内才显现：只记分组的话，源站中途上线一个新集合并把它归进某个已批准的
分组，那张还没过期的老票立刻就能读到批准人从没在同意页上见过、也从没同意过的数据。
批准人当时看的是一屏具体的集合，授权就该是对那一屏的授权。

冻结**只收窄不放宽**：快照之后本站又把某个集合移出白名单，它就不再出现在清单里，
目标站的对照表会显示成「源站没报告、不会同步」。

跑到终态（成功或失败）时，目标站会主动把导出令牌交还源站作废。少了这一步，界面上写着
「这次一次性同步已经结束」，而那张票在源站眼里还能再用近两小时——「一次性」就只剩文案。
交还失败不改变同步的结局（票据本来就有硬过期），但会留一条日志。

导出令牌只活在目标站的**进程内存**里，不落库。落库等于在共享 Mongo 里长期存一份可重放的
访问权。代价是进程重启后这次同步作废、要重新授权——而「重新授权」恰恰是这个功能的设计意图。
顺带的好处：只有握着令牌的那个进程能执行这条 Run，共享库上别的部署（含跑着旧构建的分支预览）
抢不走，不会重演「旧 worker 抢走新 run」那类事故。

## 落库策略

- 按主键（Mongo 的 `_id`）升序分页拉取，不用 skip：skip 在几万条上越翻越慢，中途有写入还会漏或重。
- 默认**只新增、不覆盖**：本地已存在同主键的记录原样保留。恢复空库是主场景，
  这样一次误操作最多是「什么都没变」。
- 勾「以源站为准覆盖」才会替换本地记录，界面上写明这会盖掉本地改动。
- 没有主键的文档一律丢弃：插进去会拿到本地新生成的 id，下次同步再插一遍，每同步一次翻一倍。
- 「先试跑」只统计不写库。

## 出了问题从哪里看

- 目标站：同步页的 SSE 进度按集合给真实条数；失败时那次同步记录上有错误原因。
  起始屏列最近 20 次同步（源站、时间、拉取/写入条数、终态），点进去能回看任意一次的逐集合明细，
  也能直接拿上次的源站地址再发起一次——「上次从哪台机器同步的」是系统知道的事，不该让人自己记。
- 源站：批准动作写日志（谁批准了向哪个 origin 导出哪些分组）。
- 两边都不打印任何密钥或令牌明文。
