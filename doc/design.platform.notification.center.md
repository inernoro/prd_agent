# 通知中心与故障接力 · 设计

> **版本**：v1.0 | **日期**：2026-11-20 | **状态**：分支预览已验证，待上线验收

**一句话**：把重复告警收敛为可跟进的故障，首屏分别显示请求结果、原线路状态和接手情况，并用真实请求证明恢复。
**谁该读**：需要从通知中判断业务影响的值班人员，以及负责分诊规则、故障排查和上线验收的产品、研发与测试人员。
**读完能做什么**：判断哪些事件值得提醒，读懂故障卡的三种状态，用请求证据排查原因，并按明确的门槛验收上线。

## 管理摘要

模型网关可能在主线路失败后通过备用线路完成请求。通知首屏要让值班人员同时知道这笔请求的结果、原线路现在是否异常、有没有人接手。把这三项放在同一张状态卡中，才能在故障恢复后继续核对之前失败的任务。

单次波动和轻微预警留在面板。连续失败才升级提醒，已证实的额度耗尽、访问拒绝、网关拦截在首次发生时就做分诊。手机提醒只占用用户处理重要事件的时间，通知中心保留有权查看的完整记录。分支预览已完成桌面、手机和隔离数据流程验证，下一步是历史回放和五人盲测。

## 产品定位

MAP 通知中心负责发现、跟进和复盘网关告警。网关提供真实请求及线路尝试的证据，自动恢复和请求调度由网关负责。CDS 持续入口异常由值班人员查看独立探测和采集记录。分诊技能提供排查方法，告警等级由服务端根据已观察到的事实计算。

| 面板 | 用户要做的事 | 展示与排序 |
| --- | --- | --- |
| 待关注 | 先处理需要注意的通知 | 未确认的紧急、重要通知，紧急优先，同级按最近更新排序 |
| 故障接力 | 判断服务影响，找人接手或核对恢复 | 已识别的紧急、重要网关故障，进行中排在已恢复前。确认通知后仍可跟进 |
| 全部记录 | 查找轻微信息和历史结果 | 查看权限内的全部级别，按最近更新排列，可用优先级筛选 |
| 已归档 | 回看已确认和已关闭的通知 | 保留原通知结果和时间。故障是否恢复以线路状态为准 |

## 用户场景与首屏

第一句写结果，第二行写环境，再补充影响对象、线路和时间。桌面并排显示三项，手机按「请求影响、线路状态、跟进状态」顺序排列。图标和文字同时表达状态。

| 场景 | 请求影响 | 线路状态 | 跟进状态 |
| --- | --- | --- | --- |
| 同一故障中一笔失败，一笔由备用线路完成 | 两种结果分别计数，每笔请求只计自己的结果 | 红叉 · 原线路仍异常 | 待接手，或显示接手人和时间 |
| 原线路后来有一笔真实请求成功 | 历史失败仍待核对，备用成功继续保留 | 绿勾 · 原线路已恢复。旁边显示成功时间，可查看对应线路和请求证据 | 保留本轮接手记录 |
| 已恢复的原线路再次出现失败 | 列出新一轮已收录的请求影响 | 红叉 · 原线路再次异常 | 新一轮待接手 |
| 旧告警缺少可靠观测 | 请求结果待核实 | 灰色问号 · 当前状态待核实。标记最后有效观测时间，只有通知记录时间时明确写明 | 接手状态待核实，已有可信记录时显示已知负责人 |

「标记接手」由当前有权操作的第一位负责人取得。只有本人可以取消接手。并发接手或记录已进入新一轮时，刷新详情后重新判断。「确认通知」更新通知处理状态，共享通知的确认会同步给有权查看的人。线路状态始终随证据更新。

首屏提供当前阶段的下一步。故障期优先打开失败请求，恢复后优先查看成功请求证据。证据回放默认折叠，展开后可查各次失败、备用成功、恢复及当时的请求编号。卡片计数用已收录的请求，统计整个时段的影响需要继续查网关请求记录。

## 分诊与提醒

| 已证实的信号 | 分级与提醒 | 应核对的证据 |
| --- | --- | --- |
| 余额或额度耗尽、访问被拒 | 首次分诊。业务请求失败为紧急，备用成功或最终结果待核实为重要 | 账户额度、凭据权限、受影响线路、可用备路 |
| 网关保护规则已拦截 | 首次为重要 | 命中的限额、调用方、计量窗口，区分网关拦截与上游拒绝 |
| 上游普通限流 | 单次为一般。同线路五分钟内连续影响至少三笔不同请求后为重要 | 限流类型、恢复窗口、影响的独立请求及备用结果 |
| 普通可用性失败 | 单次为一般。同线路五分钟内连续影响至少三笔不同请求后升级。有业务请求失败为紧急，其他为重要 | 检查请求链路、故障类型和同线路成功结果 |
| 接近限额、流量预警、网关故障恢复 | 保存在面板。恢复通过状态和证据可见 | 触发条件、原故障和恢复请求 |
| CDS 入口探测持续失败 | 先定位入口或采集链路。采集读不到时，记录业务状态待核实 | 对照同一环境的独立探测，检查域名解析、证书、入口响应和采集日志 |

网关的重要、紧急告警经现有权限和订阅决定投递。同一故障内追加证据，首次达到提醒条件、优先级上升或故障复发才会开启新的告警投递。同一请求编号下的线路重试和多次采集均不重复计入连续失败门槛。网关恢复留在面板，避免恢复短讯盖过未处置故障。

补扫跨越多个时间窗口时，同一段尚未恢复的连续异常中，任一五分钟窗口达到门槛即可分级。同线路成功后，本轮结束，后续再次失败独立计数。

## 事实如何变成故障记录

1. 从网关请求和线路尝试识别整次请求结果、失败发生在哪条线路、发生的时间和确定性原因。一个请求可同时产生故障线路失败和业务请求经备路成功的事实。
2. 环境、部署、租户和线路由同一故障标识约束。入口故障用调用入口识别。证据不足的旧通知保留原记录，跨环境或线路的事件各自跟进。
3. 按时间合并当前故障的观察结果，计算分级，保留失败请求、备用结果以及有权限可查的证据入口。已收录的记录保留原观测时间，过时信号无法覆盖当前状态。
4. 原线路在故障之后成功完成真实请求才确认恢复。后续同线路再次失败时，开启新一轮并清除上一轮的接手人，历史失败和恢复记录仍可查。升级提醒与复发分别处理，升级时保留本轮的接手人。

| 记录 | 保留的业务信息 |
| --- | --- |
| 通知 | 信号来源、环境、优先级、确认或归档状态、投递记录 |
| 故障与轮次 | 故障身份、当前线路状态、开始与最近观测时间、当前接手人及接手时间 |
| 请求证据 | 观察时间、请求结果、证明恢复的线路及请求，和按权限打开日志的入口 |

查看通知和查看网关日志分别校验权限。恢复时间和结论可在获准查看故障时呈现。请求编号、具体恢复线路及日志入口按网关权限展示。演练从故障接力空态也可进入，样例操作只在该页生效。

## 上线验收与下一步

**当前证据**。分支预览已通过桌面及手机浏览器验证，隔离数据已走通真实通知中心的接手、共享确认、原线路恢复、证据回放和复发，并验证告警规则的关键场景。正式故障时段的历史回放、五人盲测和正式投递验证仍待完成。

| 顺序 | 参与角色 | 步骤与通过条件 |
| --- | --- | --- |
| 1. 历史回放 | 网关研发和值班人员 | 用同一批脱敏历史请求对照旧规则和新规则，只计算候选提醒。逐笔核对已证实的额度耗尽、访问拒绝和网关拦截均被关注，普通单次波动只留记录，重试与跨环境记录未造成误升级。记录新旧提醒数、漏报和首次提醒时间。 |
| 2. 五人盲测 | 产品与测试组织，值班人员及日常使用者参加 | 在手机和桌面随机展示备用成功、恢复、复发和旧记录样例。先不给解释，请每人十秒内指出请求结果、原线路状态、接手情况。至少四人三项全对，记录错读源于标题、图标还是状态文字。 |
| 3. 受控投递 | 负责告警配置的运维与发布人员 | 前两项达标后，在授权订阅范围内验证一条可追踪告警的首句、环境、图标、送达和证据跳转。对照真实记录，全程保留恢复和复发证据。 |

发现确定性告警漏报、同一故障重复打扰或错误标为恢复时，先停扩大投递。回到对应请求、线路和采集事实修正规则，再用同一批样本复验。
