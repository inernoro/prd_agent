## 执行与比较

先选择同一个不可变基准提交，三次运行各自创建并销毁全新数据库：

```bash
BASE=$(git rev-parse origin/main)
for attempt in 1 2 3; do
  node e2e/performance/run.mjs --ref "$BASE" --profile normal --out "work/performance/base-$attempt"
done
node e2e/performance/calibrate.mjs work/performance/base-{1,2,3}/result.json --out work/performance/baseline.json
node e2e/performance/run.mjs --ref HEAD --profile all --baseline work/performance/baseline.json --out work/performance/candidate
```

`normal` 为 2 个并发用户、每用户每秒开始一次事务、持续 60 秒；两个用户先各执行20次实际核心路径预热。`all` 再执行 2/4/8/16/32/64/128 并发用户，各 15 秒无思考间隔；最后以正常负载持续 120 秒。压力阶段事务错误率超过 10% 时停止继续加压，仍执行持续运行阶段。间隔只控制负载节奏；所有登录、导航、正文加载、保存和写后校验都等待实际响应或可见内容，无固定 UI 等待。

每轮另外以三个独立浏览器上下文走完整核心路径，采集首页、知识库列表、文档打开、无模型写入并刷新可用的真实耗时。首页等待实际「手边的活儿」工作卡片可用，不用已经出现的侧栏替代首页完成。浏览器计时与 API 指标均参与门禁：三次干净环境共至少九个样本，用观测最大值及极差校准上限；候选各步 p95 超限即失败。少量浏览器样本用于早期退化预警，不宣称构成生产 SLO。

每次运行记录 `execution.profile` 和 `execution.state`。阶段快照始终为 `running`；全部所需阶段、浏览器闭环及本轮资源清理结束后，才写入 `complete` 和 `finishedAt`。性能退化可以是「执行完整、比较失败」，不能与执行中断混为一谈。`all` 必须包含连续的并发档位及持续运行；只有实际达到既定错误率停止条件时才允许缩短并发序列。缺少终态、浏览器失败、阶段缺失、清理失败均不能校准或比较为通过。

构建时显式将目标提交写入 API 的编译元数据和 Web 的生产构建 ID；运行时的声明 SHA 独立注入。准备数据前，通过真实 `/api/version` 与已托管 HTML 核对 API 实际编译 SHA、声明 SHA、Web 入口构建 SHA 三者均等于 `--ref` 解析出的不可变提交。对账失败立即停止，不能用测试执行器所在分支的 SHA 冒充被测应用版本；旧构建缓存不会复用。

历史参考数据仍保留原结论与采集版本。未记录终态的旧结果在新判定器中会被拒绝，必须重新采集；不通过手工补 `complete` 将历史快照升级为通过证据。

正常基线每场景至少100个样本，默认约120个；候选及注入负例每场景不足30个即拒绝比较。预热不进入统计。各阶段独立报告 p50/p95/p99、错误率、成功吞吐和各容器进程树 CPU/内存消耗。CPU 从 Linux `/proc` 的进程累计时钟增量计算，100% 表示一个核；内存是各进程 RSS 之和，包含共享页重复计算，不等于 PSS。原始请求留在 `requests.ndjson`，阶段资源样本范围在 `result.json`。吞吐以实际阶段墙钟时间为分母，包括尾部完成时间。请求错误保留状态与异常，成功延迟分位数不混入超时；同时必须查看错误率。

负例执行会返回 1；必须再验证失败确实来自应用性能退化：

```bash
node e2e/performance/run.mjs --ref "$BASE" --profile normal --inject-ms 350 --baseline work/performance/baseline.json --out work/performance/injected
node e2e/performance/prove.mjs work/performance/injected/result.json
```

还必须证明 API 仍快时，用户看到的首页变慢也会失败。在本地隔离浏览器中延迟真实首页 JS 分块的交付，不替换脚本、页面内容或 API：

```bash
node e2e/performance/run.mjs --ref "$BASE" --profile normal --inject-browser-ms 10000 --baseline work/performance/baseline.json --out work/performance/injected-browser
node e2e/performance/prove-browser.mjs work/performance/injected-browser/result.json
```

该负例预期返回 1；证明器要求三个上下文都实际命中首页资产、页面业务最终完成、全部 API 门禁正常，并且 `browser/home` 用户可用时间被拒绝。没有命中脚本或仅基础设施失败不算退化识别。撤除注入后必须以新实例恢复通过，CI 同样执行这一恢复步骤，保留负例原始结果。

## 场景与数据

浏览器每轮从真实登录表单开始，等待首页接口和知识库入口，点击进入知识库、选择固定文档、编辑正文、保存，再刷新验证可见内容及服务端持久化。每步截图，失败保留截图及 DOM；接口成功不能替代浏览器路径成功。

负载事务依次覆盖首页「继续上次」、知识库带预览列表（与前端一致取最多 500 项）、文档正文，以及与实际页面一致的已有文档编辑保存、写后读取、版本历史。6 个知识库各 20 篇固定阅读文档，再为最多 128 个并发用户预先准备 128 篇互不重复的写入文档，共 248 篇。每次保存为 8 KiB Markdown，尾部唯一标记保持每轮确有不同内容并用于回读核对。创建只在准备数据时执行；清理由销毁本轮隔离数据库、卷及容器完成，计时流程不执行文档删除。使用一个本地播种管理员，代表有写权限的知识工作者，不覆盖多租户权限分布。首页完整渲染由浏览器验收，接口压力仅覆盖其核心聚合请求；不能把它解释成全首页所有后台请求的并发容量。

路径来自实际页面导航与服务调用，数据规模则是受控 fixture，目前没有用真实用户数据分布证明其为典型规模。获得预览访问后只读核对获准使用的非生产元数据规模与角色分布；未核对前容量只对该 fixture 有效，不借「代表性」措辞外推生产。

写入走真实正文存储、版本快照、摘要索引与双链更新，不依赖模型生成。重复编辑同一用户的文档保留实际版本与活动增长影响。合同版本2将业务写入与回收操作分开，合同3延长正常采样并预热两个用户；旧合同的90条409及合同2的两次正常阶段超限原始证据继续保留，不能跨合同混比。合同2的超限项在同提交复核中从正文/回读切换为首页，原因未被宣称已定位；合同3不改变阈值公式，不将旧候选加入新基线，重新在三个全新环境校准。执行 `node e2e/performance/prove-write.mjs RESULT_DIRECTORY` 核对每个并发用户的独立文档，以及原始请求的流程、成功与失败计数；CI 同样执行这一核验。

默认每账号 600 请求/分钟、100 并发会让共享账号的 VU 和数据准备争抢同一桶。执行器记录原配置，并通过既有管理 API 仅把本次临时实例调为 100000 请求/分钟、1024 并发；实际 Redis 限流链仍执行，未使用豁免身份。此配置纳入比较契约。默认准入限流与应用资源饱和必须分别解释，不能把这里的测得容量套到默认单账号配额。

## 归因、阈值与容量含义

测试专用 HostingStartup 探针由执行器注入，不改动产品代码，也不进入生产构建。`Server-Timing` 的 `server` 是从测试中间件到响应头开始发送，`external_http` 是期间 HttpClient 依赖调用的时间并集，`app` 为两者之差，包含数据库、Redis、排队和应用处理。客户端往返还包含 Nginx、传输和响应体读取。外部 HTTP 流式正文在响应头后的读取不算入该探针的依赖时间；本套流程均为 JSON、本地文本且不调用此类服务。

数据库和 Redis 属于本次被测系统；不能把 `app` 当作纯 CPU 时间。模型/订阅/云存储在本隔离网络不可达，此路径外部 HTTP 为零。另有真实 Kestrel/HttpClient 归因自测：两个并行慢依赖按并集统计，350ms 应用注入归到应用耗时。

阈值按同提交三次干净环境的正常阶段实测校准：p95 上限取「三次 p95 最大值 × 1.3」「p95 最大值 + 3 × 极差」及「基线 p99 最大值」的最大者，避免短基线丢弃自己已观测到的长尾；零错误基线错误率上限为 `3 / 总样本数`（近似 95% 零事件上界）；成功吞吐下限为三次最小值的 70%。正常及持续阶段都检查客户端和应用 p95、错误率、吞吐、覆盖率；并发增长阶段用于探边界，不套正常负载门禁。

`baseline.reference.json` 保存 2026-11-12 对 `3035365de` 的三次实测校准：40/40/40 次事务均零错误，事务 p95 分别约 212/252/225ms。它是本次环境的可审计参考，不能跨机器直接套用；CI 仍按上述流程在同一 runner 上重新校准。

原始结果不可因门禁策略调整而覆盖。`compare.mjs` 支持将同一采集契约的历史结果与重新校准的基线离线比较，输出原始比较、当前比较、双方文件哈希及策略版本：`node e2e/performance/compare.mjs RESULT BASELINE --out work/performance/evaluation.json`。本轮保留了策略 1 的 23.35ms/22.97ms 误报；策略 2 使用原基线已测到的 24.76ms p99 包络复评，同时必须继续拒绝 350ms 应用注入。

容量边界记录首个「任一场景错误率 >1% 或 p95 超过正常负载两倍」的并发档位。它是给定数据、账号、CPU/内存配额和无思考时间下的相对退化起点，不是生产可承诺用户数。若最高档位仍未退化，明确记为未触及边界。120 秒持续测试是短期稳定性基线，不足以证明小时级内存泄漏不存在。

契约包含负载/数据规模、探针与执行代码、SDK、Node 主版本、CPU 型号/架构、镜像 digest 和容器配额。任一变化拒绝比较，须同机重新校准。提交号不属于契约，可比较不同提交。构建只复用按不可变提交、SDK 和架构隔离的本地缓存；每次运行均重建容器与数据。

## 隔离与 CI

执行器无目标 URL 参数，输出限于仓库 `work/`，拒绝覆盖已有结果。每轮创建独立 `--internal` Docker 网络，Mongo、Redis、API 不发布端口；仅固定路由的静态 Web 代理额外加入本轮入口网络，并发布到随机的 `127.0.0.1` 端口（Docker 29 不对纯内部网络发布端口）。容器显式清空代理，浏览器拒绝非本地请求。API 限 1 CPU/1 GiB，Mongo 1 CPU/768 MiB，Redis 与 Web 各 0.5 CPU/256 MiB，禁用额外 swap。镜像按 digest 固定。API 的测试运行镜像以 Mongo 官方 Ubuntu/OpenSSL 基础环境补装固定版本 ICU，以只读挂载的同一 .NET SDK 启动，替换入口，不启动该容器的 mongod；API 进程沿用执行用户 UID/GID。成功和异常退出都会清理本次容器、匿名卷和网络，不接触其他实例。进程被硬终止或宿主崩溃时仍需按本次 `map-perf` 标签清理遗留资源。

执行器核对容器内实际 cgroup 的 CPU 和内存限制，并记录进比较契约。上段是请求的配额；无 cgroup 委派的 rootless Docker 可能不执行这些限制，此时明确标记 `requestedLimitsEnforced=false`，不能把请求配额写成实际容量条件。资源始终按各容器 PID 的独立进程树采样，不采信共享 cgroup 的 `docker stats`。本次云环境若使用共享 4 CPU/16 GiB，容量报告只适用于这组实测条件；支持 cgroup 的 CI runner 则使用实际容器配额重新校准，二者不可混比。

现有 **Preview Acceptance** 增加隔离性能 job：相关 PR 自动校准基准 SHA 并比较候选 SHA，手动执行可提供 `perf_ref` / `perf_base_ref` / `perf_profile`。默认正常负载门禁，`all` 执行全部三类测试；同一 runner 先测基准再测候选，最后必须证明受控退化被拒绝。该 job 不使用环境密钥、不部署、不购买资源；报告作为 Actions artifact 保留 14 天。没有 PR 时可手动 dispatch；本任务不自动创建 PR。

如被硬终止，只清理该结果 `environmentId` 对应标签的资源，不使用全局 prune。查看 `result.json` 的 `failure`、`comparison` 和截图确定是基础设施、功能失败还是性能回归；基础设施失败不能算作成功识别退化。
